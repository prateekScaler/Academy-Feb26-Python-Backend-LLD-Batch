Typing & Generics

LLD-09 • Python Advanced-1

Python lets you write code without types. That's a feature for scripts.
It's a liability for systems.

Concurrency Recap

Before We Move On...

4 classes of concurrency. These concepts should be crystal clear. Not syntax — the reasoning.

Your teammate says: "We don't need locks in Python because of the GIL." Are they right?

GIL ≠ thread safety. The GIL prevents parallel execution but NOT context switching. counter += 1 is LOAD + ADD + STORE — a thread can be interrupted between these. You still need locks for shared mutable state.

Highway has 5 toll booths. 20 cars arrive. You use a Mutex. What happens?

Mutex is binary: 1 at a time. Even though there are 5 booths, mutex only allows 1 car through. You need Semaphore(5) to allow 5 at once. Mutex = lock/unlock. Semaphore = counter 0 to N.

Producer-Consumer: buffer is full. Why can't a mutex make the producer WAIT until space is free?

Mutex protects. Semaphore signals. A mutex is locked/unlocked — it can't express "wait until a condition changes." Holding lock + looping = consumer blocked = deadlock. Semaphore's release() WAKES UP a blocked acquire(). That's signalling.

You write time.sleep(2) inside an async def function. What happens?

time.sleep() is blocking. It doesn't yield to the event loop. The entire async system freezes. Use await asyncio.sleep(2) instead — it yields control so other coroutines run. The #1 async bug.

You need to resize 1000 images in Python. Which concurrency approach?

CPU-bound = Processes. Image resize is pure computation. GIL prevents threads from running in parallel. Async doesn't help (no I/O wait). Only ProcessPoolExecutor gives true parallelism across cores.

FastAPI app calls 3 external APIs. Best approach?

Async + async library. FastAPI runs on an async event loop. Use asyncio.gather() with aiohttp. One thread handles all 3 concurrently. Threads would add unnecessary overhead inside an already-async framework.
The Problem

Why Types?

Let's start with a bug. A real one.

Read this code. Can you spot the bug?
▼
def calculate_total(items):
    total = 0
    for item in items:
        total += item["price"] * item["quantity"]
    return total

def apply_discount(total, discount):
    return total - (total * discount)

def process_order(order):
    total = calculate_total(order["items"])
    final = apply_discount(total, order["discount"])
    return final

A new developer calls: process_order({"items": [...], "discount": "10%"}). What happens?

apply_discount(250, "10%") tries to compute 250 * "10%" — crash. The function expected a float like 0.1 but got a string. You'd never know until production. With types: def apply_discount(total: float, discount: float) -> float — mypy catches this before you even run the code.

The real question isn't "what's the bug?"

It's: how would the new developer have KNOWN that discount should be a float and not a string? The function signature def apply_discount(total, discount) tells them nothing. They have to read the implementation. In a 50,000-line codebase, that's not sustainable.

Fundamentals

Type Hints — One Scenario at a Time

We'll introduce each type through a problem. You tell me what should happen.

Scenario 1: "What does this function accept?"

Without types
▼
def greet(name):
    return f"Hello, {name}!"

def add(a, b):
    return a + b

What happens when you call add("hello", " world")?

Python doesn't enforce types. add("hello", " world") returns "hello world". Python sees + and uses string concatenation. There's no way to know from the function signature that add was meant for numbers. Type hints fix this:
With types — crystal clear
▼
def greet(name: str) -> str:
    return f"Hello, {name}!"

def add(a: int, b: int) -> int:
    return a + b

def is_adult(age: int) -> bool:
    return age >= 18

# Python STILL doesn't enforce at runtime!
add("hello", " world")  # Runs fine!
# But mypy catches it: Argument 1 has incompatible type "str"; expected "int"
Key insight: Types are hints, not constraints. Python ignores them at runtime. Three things USE them:
1. Your IDE — autocomplete, hover info, red squiggles
2. mypy — static checker that catches bugs before you run code
3. Humans — reading the code 6 months later

Scenario 2: "What's INSIDE this list?"

A list of... what?
▼
def process(items):
    for item in items:
        print(item.upper())  # Will this work? Who knows!

Someone calls process([1, 2, 3]). What happens?

The function calls .upper() which only works on strings. list alone doesn't tell you what's inside. You need list[str]:
Collection types — what's inside matters
▼
# Python 3.9+ syntax (recommended)
def process_names(names: list[str]) -> list[str]:
    return [name.upper() for name in names]

def get_scores() -> dict[str, int]:
    return {"Alice": 95, "Bob": 87}

def get_coordinates() -> tuple[float, float]:  # exactly 2 elements
    return (28.6139, 77.2090)

def get_unique_tags() -> set[str]:
    return {"python", "backend", "lld"}

# Nested collections:
def get_class_scores() -> dict[str, list[int]]:
    return {"Alice": [95, 88, 92], "Bob": [87, 91]}

Scenario 3: "Your app crashes at 3am..."

You wrote find_user(user_id). It works great in development. Then in production, a request comes in with a user_id that doesn't exist.

The 3am crash
▼
def find_user(user_id):
    users = {1: {"name": "Alice"}, 2: {"name": "Bob"}}
    return users.get(user_id)  # returns None if not found

# Works perfectly in development:
user = find_user(1)
print(user["name"])  # "Alice" ✔

# 3am in production — a user_id that doesn't exist:
user = find_user(999)
print(user["name"])  # TypeError: 'NoneType' object is not subscriptable
# user is None. You never checked.

How do we tell the caller "this function might return None"?

With -> dict | None, mypy will error if the caller does user["name"] without checking for None first. The caller is forced to write if user is not None:. The bug is caught at write time, not at 3am.

Optional — "This value might not exist"

Optional[X] is just shorthand for X | None. It means: "this could be X, or it could be None." Both syntaxes mean the exact same thing.

Optional — the fix
▼
from typing import Optional

# These three are IDENTICAL:
def find_user_v1(uid: int) -> Optional[dict]:   # typing module syntax
    ...
def find_user_v2(uid: int) -> dict | None:      # Python 3.10+ pipe syntax
    ...
# Both mean: "returns a dict OR None"

# The real function:
def find_user(user_id: int) -> dict | None:
    users = {1: {"name": "Alice"}, 2: {"name": "Bob"}}
    return users.get(user_id)

# Now mypy FORCES you to handle None:
user = find_user(999)
user["name"]  # mypy ERROR: Item "None" has no attribute "__getitem__"

Three Ways to Handle Optional

Pattern 1: if-check (most common)
▼
user = find_user(999)

if user is not None:
    print(user["name"])  # mypy happy — inside the if, user is dict (not None)
else:
    print("User not found")
Pattern 2: early return (guard clause)
▼
def get_user_name(user_id: int) -> str:
    user = find_user(user_id)
    if user is None:
        return "Unknown"        # bail out early
    return user["name"]          # mypy knows: user is dict here (None was returned above)
Pattern 3: raise if missing
▼
def get_user_or_404(user_id: int) -> dict:
    user = find_user(user_id)
    if user is None:
        raise ValueError(f"User {user_id} not found")
    return user                   # mypy knows: user is dict (None raised above)
# This is the Django/FastAPI pattern: get_object_or_404()

Where does Optional / None show up in real code? (Select the best answer)

None is everywhere in Python. dict.get() returns it, list.find() equivalents return it, DB queries return it when no row matches, config values may be unset, API fields may be missing. Optional makes all of these explicit. Tony Hoare (who invented null) called it his "billion dollar mistake" — Optional is Python's way of making that mistake visible.
Common pitfall: Optional in function parameters.

def greet(name: Optional[str] = None) means the parameter is optional to provide (has a default) AND the value might be None.

def greet(name: str = "World") means the parameter is optional to provide but is never None — it always has a string value. Don't use Optional here!

Rule: use Optional[X] only when None is a valid value you need to handle.

Union — "Could be either type"

Optional[X] is just X | None. But Union is more general — it means "could be any of these types."

Union and the | syntax
▼
# Accepts int or str — must handle both
def format_id(id_value: int | str) -> str:
    if isinstance(id_value, int):
        return f"ID-{id_value:05d}"   # mypy knows: int in this branch
    return f"ID-{id_value}"          # mypy knows: str in this branch

format_id(42)       # "ID-00042"
format_id("ABC")    # "ID-ABC"
format_id(3.14)     # mypy error: float is not int | str

# Syntax evolution (all equivalent):
# Python 3.9:  Union[int, str]   /  Optional[str] = Union[str, None]
# Python 3.10: int | str         /  str | None
# Prefer the | syntax — it's cleaner
mypy's "type narrowing": When you write if isinstance(x, int) or if x is not None, mypy narrows the type inside that branch. It knows x is int (not str) inside the if-block. This is why the patterns above work — mypy tracks your control flow.

Scenario 4: "How do you type a function that accepts a function?"

Remember the strategy pattern? Decorators? Callbacks? They all take functions as parameters. How do you type that?

What does 'handler' expect? No idea.
▼
# Without types: WHAT should handler look like?
def retry(handler, max_retries):
    for i in range(max_retries):
        try:
            return handler()
        except Exception:
            if i == max_retries - 1: raise
Callable[[params], return] — type a function
▼
from typing import Callable

# Callable[[param_types...], return_type]
def retry(handler: Callable[[], str], max_retries: int = 3) -> str:
    # Now it's clear: handler takes NO args, returns str
    ...

# More examples:
MathOp = Callable[[int, int], int]  # (int, int) -> int

def apply(a: int, b: int, op: MathOp) -> int:
    return op(a, b)

apply(5, 3, lambda x, y: x + y)   # ✔
apply(5, 3, lambda x, y: "hi")  # mypy error: expected int return

# Real-world uses: decorators, event handlers, middleware, strategies
EventHandler = Callable[[str, dict], None]
Middleware = Callable[[Request, Response], Response]

Type syntax summary so far:
• Primitives: int, str, float, bool
• Collections: list[str], dict[str, int], tuple[float, float], set[int]
• Optional: str | None — "might not be there"
• Union: int | str — "could be either"
• Callable: Callable[[int, str], bool] — "a function with this shape"
• Any: Any — escape hatch, disables all checking

The Big Idea

TypeVar & Generics

This is the hardest concept today. Let's build up to it with a problem.

Step 1: The Problem — A Container with No Type Safety

Box that holds anything
▼
class Box:
    def __init__(self, item):
        self.item = item
    def get(self):
        return self.item

int_box = Box(42)
str_box = Box("hello")

result = int_box.get()  # What type is result?
result.upper()          # Runtime crash! But IDE gave no warning.

When you hover over int_box.get() in your IDE, what type does it show?

The IDE shows Any (or just gives up). It can't know what get() returns because item has no type annotation. So result.upper() looks fine to the IDE... but crashes at runtime because 42 is an int.

Step 2: How do we fix it?

Attempt A: Separate classes

class IntBox:
    def __init__(self, item: int): ...
    def get(self) -> int: ...

class StrBox:
    def __init__(self, item: str): ...
    def get(self) -> str: ...

IntBox, StrBox, FloatBox, UserBox, OrderBox... doesn't scale.

Attempt B: Use Any

from typing import Any

class AnyBox:
    def __init__(self, item: Any): ...
    def get(self) -> Any: ...

Any = "give up type checking." We're back to square one.

We need ONE class that:

1. Works with ANY type (int, str, User, Order...)
2. Remembers which type was put in
3. IDE knows Box(42).get() returns int, not Any

Step 3: TypeVar — A Placeholder for "Some Type"

TypeVar is like a variable, but for types. Instead of holding a value like x = 42, it holds a type like T = int.

TypeVar: the key concept
▼
from typing import TypeVar

T = TypeVar("T")  # T = "some type, to be determined later"

# Think of it like algebra:
# In math: f(x) = x + 1    ← x is "some number"
# In types: def first(items: list[T]) -> T    ← T is "some type"

Step 4: Generic Functions — TypeVar in Action

Return type follows input type
▼
T = TypeVar("T")

def first(items: list[T]) -> T:
    """Return first element. Return type matches element type."""
    return items[0]

# When you call first([1, 2, 3]):
#   T = int (inferred from list[int])
#   return type = int
num = first([1, 2, 3])       # IDE knows: int
word = first(["a", "b"])     # IDE knows: str
user = first([alice, bob])  # IDE knows: User

# Multiple TypeVars:
K = TypeVar("K")
V = TypeVar("V")

def get_or_default(d: dict[K, V], key: K, default: V) -> V:
    return d.get(key, default)

scores: dict[str, int] = {"Alice": 95}
get_or_default(scores, "Bob", 0)   # ✔ K=str, V=int
get_or_default(scores, 42, 0)      # ✘ mypy: key must be str!

What does first(["apple", "banana"]) return, according to the type system?

The input is list[str], so T = str. The return type T becomes str. The IDE now knows first(["apple", "banana"]) returns a str and offers .upper(), .split(), etc. The type flows through the TypeVar.

Step 5: Generic Classes — Solving the Box Problem

Generic[T] — the solution
▼
from typing import TypeVar, Generic

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, item: T):
        self.item = item
    def get(self) -> T:
        return self.item
    def replace(self, new_item: T) -> None:
        self.item = new_item

# Usage: T is filled in at creation
int_box = Box[int](42)       # T = int for this instance
str_box = Box[str]("hello")  # T = str for this instance

val = int_box.get()   # IDE KNOWS: int  (not Any!)
val2 = str_box.get()  # IDE KNOWS: str
val2.upper()          # IDE offers string methods! ✔

int_box.replace("oops")  # mypy ERROR: expected int, got str ✔
ONE class. ANY type. Full type safety. When you write Box[int](42), every T in the class becomes int. The IDE and mypy track this. No separate IntBox, StrBox needed.

Real-World: Generic Repository

This is how Django QuerySets, SQLAlchemy sessions, and FastAPI dependencies work under the hood.

One Repository for any model
▼
class Repository(Generic[T]):
    def __init__(self) -> None:
        self._items: dict[int, T] = {}

    def add(self, id: int, item: T) -> None:
        self._items[id] = item

    def get(self, id: int) -> T | None:
        return self._items.get(id)

    def get_all(self) -> list[T]:
        return list(self._items.values())

# Type-safe for each model:
user_repo = Repository[User]()
order_repo = Repository[Order]()

user_repo.add(1, User("Alice"))
user_repo.add(2, some_order)  # mypy ERROR: expected User, got Order

Surprise: you've been using generics all along. Which of these is a generic type?

list is Generic[T] under the hood! When you write list[int], you're parameterizing a generic type — just like Box[int]. Same with dict[K, V], set[T], tuple[T, ...]. You've been using generics since the collections slide.

More Patterns: Generic Stack

Any data structure that holds "items of some type" is a candidate for generics.

Stack<T> — push/pop with type safety
▼
class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

    def peek(self) -> T:
        return self._items[-1]

# Usage:
int_stack = Stack[int]()
int_stack.push(10)
int_stack.push(20)
val = int_stack.pop()    # IDE knows: int

str_stack = Stack[str]()
str_stack.push("hello")
str_stack.push(42)       # mypy ERROR: expected str, got int

You have Stack[User]. What type does .pop() return?

Stack[User] binds T = User. Every method using T now uses User. pop() -> T becomes pop() -> User. The IDE knows it, mypy verifies it. You get autocomplete for .name, .email, etc.

Pattern: Result<T, E> — Multiple TypeVars

What if your function can succeed with a value OR fail with an error? Instead of returning Any or raising exceptions, use a typed Result.

Result pattern — success or failure, both typed
▼
from dataclasses import dataclass

T = TypeVar("T")
E = TypeVar("E")

@dataclass
class Success(Generic[T]):
    value: T

@dataclass
class Failure(Generic[E]):
    error: E

def divide(a: float, b: float) -> Success[float] | Failure[str]:
    if b == 0:
        return Failure("Division by zero")
    return Success(a / b)

result = divide(10, 3)
if isinstance(result, Success):
    print(result.value)   # IDE knows: float
else:
    print(result.error)   # IDE knows: str
Where you'll see generics in the wild:
• Django: QuerySet[User] — query results know the model type
• FastAPI: Response[UserSchema] — auto-generates API docs from the type
• SQLAlchemy: Session.query(User) returns typed results
• Pydantic: BaseModel subclasses are validated generic containers
• Standard lib: list[T], dict[K,V], Optional[T], Future[T]

Limiting TypeVar: "T, but only these types"

You write def double(x: T) -> T. Someone calls double("hello"). Is that OK?

T = TypeVar("T") is completely unrestricted — any type goes. If you want double to only accept numbers, you need a constrained TypeVar.
Constrained vs Bounded TypeVar
▼
# Constrained: T can ONLY be one of these specific types
Number = TypeVar("Number", int, float)

def double(x: Number) -> Number:
    return x * 2

double(5)       # ✔ T=int, returns int
double(3.14)    # ✔ T=float, returns float
double("hi")    # ✘ mypy: "str" is not "int" or "float"

# Bounded: T must be this class or ANY subclass
class Animal:
    def speak(self) -> str: return "..."

class Dog(Animal):
    def speak(self) -> str: return "Woof!"

A = TypeVar("A", bound=Animal)

def loudest(animals: list[A]) -> A:
    return max(animals, key=lambda a: len(a.speak()))

# Key insight: returns Dog, NOT just Animal!
dogs: list[Dog] = [Dog(), Dog()]
result = loudest(dogs)  # IDE knows: Dog (preserves the subtype)

TypeVar cheatsheet:
• T = TypeVar("T") — any type, completely open
• TypeVar("T", int, float) — constrained: pick from fixed list
• TypeVar("T", bound=Animal) — bounded: Animal or any subclass
• class Box(Generic[T]) — make a class generic
• def first(items: list[T]) -> T — return type flows from input
• You've been using generics: list[int] IS generic!
• Real-world: Repository<T>, Stack<T>, Result<T, E>, Response<T>

Structural Typing

Protocol — Duck Typing Made Safe

Remember ABC from OOP class? Protocol is the alternative when you don't control the classes.

You have a third-party logging library with a Logger class that has a log(msg: str) method. You want your function to accept ANY logger with a log() method. Can you use ABC?

You can't force third-party classes to inherit from your ABC. ABC requires the class author to opt in. Protocol doesn't — any class with the right methods automatically satisfies the Protocol. No inheritance needed.

ABC (Nominal Typing)

Classes MUST inherit from the base.
Can't use third-party classes without wrapping.
Forces a hierarchy.

Protocol (Structural Typing)

Classes just need the right methods.
Works with ANY class, even third-party.
No forced inheritance. Like Go interfaces.

Protocol in action
▼
from typing import Protocol

class Drawable(Protocol):
    """Any class with draw() -> str satisfies this."""
    def draw(self) -> str: ...

# These DON'T inherit from Drawable!
class Circle:
    def draw(self) -> str: return "○"

class Square:
    def draw(self) -> str: return "□"

# This accepts ANYTHING with draw() -> str:
def render_all(shapes: list[Drawable]) -> None:
    for s in shapes:
        print(s.draw())

render_all([Circle(), Square()])  # ✔ Works! No inheritance needed.

The Tool

mypy — The Type Checker

You've written type hints. Now meet the tool that actually checks them.

What is mypy?

mypy is a static type checker for Python. It reads your code and type hints WITHOUT running it, and finds type errors. Think of it as a compiler for Python types — except Python still runs fine without it.

Origin story: Created by Jukka Lehtosalo at the University of Cambridge as his PhD project (2012). Guido van Rossum (Python's creator) joined the project at Dropbox and helped make it the standard. Dropbox had 4 million lines of Python that kept breaking — mypy was their solution.

Installing and Running

Getting started with mypy
▼
# Install (once per project)
pip install mypy

# Check one file
mypy my_file.py

# Check entire project
mypy src/

# Strict mode (recommended for new projects)
mypy src/ --strict

# Ignore one specific line (escape hatch)
result = sketchy_function()  # type: ignore

What Does mypy Catch? — 5 Real Scenarios

Scenario 1: Wrong argument type

▼ 
def add(a: int, b: int) -> int:
    return a + b

add(10, "20")
# mypy: Argument 2 to "add" has incompatible type "str"; expected "int"

Python would concatenate or crash. mypy catches it at check time.

Scenario 2: Not handling None

▼ 
def find_user(uid: int) -> dict | None:
    return {1: {"name": "Alice"}}.get(uid)

user = find_user(999)
print(user["name"])
# mypy: Value of type "dict[str, str] | None" is not indexable
# Fix: if user is not None: print(user["name"])

The #1 production crash. mypy forces you to handle it.

Scenario 3: Wrong return type

▼ 
def get_age() -> int:
    return "twenty-five"
# mypy: Incompatible return value type (got "str", expected "int")

Easy to miss in refactoring. mypy catches silently wrong returns.

Scenario 4: Accessing non-existent attribute

▼ 
class Dog:
    def __init__(self, name: str):
        self.name = name
    def bark(self) -> str:
        return f"{self.name}: Woof!"

dog = Dog("Rex")
dog.speak()  # mypy: "Dog" has no attribute "speak"

Typos in method names are caught instantly.

Scenario 5: Wrong container element

▼ 
items: list[str] = ["apple", "banana", 42]
# mypy: List item 2 has incompatible type "int"; expected "str"

Mixed-type lists are a common source of downstream bugs.

When does mypy run?

mypy is static analysis. It reads your code and type hints without running it. That's why it can catch bugs before you deploy. It doesn't slow down your program — it never runs at the same time as your program.
Real World

How Production Code Enforces Types

Having type hints is useless if nobody checks them. Here's how teams make sure types are always verified.

Git Hooks — "What even are these?"

You know git commit. But did you know git can run code automatically before or after certain actions?

The Lifecycle of a Git Commit
You type
git commit
→
pre-commit hook
Runs BEFORE commit is created
→
Commit created
(only if hook passes)
→
post-commit hook
Runs after (notifications, etc.)
If the pre-commit hook fails (returns non-zero), the commit is rejected. Your code doesn't get committed.

You set up a pre-commit hook that runs mypy. You try to commit code with a type error. What happens?

Pre-commit hooks block the commit. If mypy finds an error, it returns a non-zero exit code. Git sees this and refuses to create the commit. You must fix the error first. This means type-broken code can never enter the repository.

Where Do Hooks Live?

Git hooks are just shell scripts
▼
# Every git repo has a .git/hooks/ folder with sample hooks:
ls .git/hooks/
pre-commit.sample    pre-push.sample    commit-msg.sample

# To create a pre-commit hook manually:
# 1. Create the file
cat > .git/hooks/pre-commit << 'EOF'
#!/bin/bash
echo "Running mypy..."
mypy src/
EOF

# 2. Make it executable
chmod +x .git/hooks/pre-commit

# Now every `git commit` runs mypy first!

pre-commit Framework — The Easy Way

Writing raw shell scripts is fragile. Most teams use the pre-commit framework instead:

.pre-commit-config.yaml
▼
# Install the framework:

Pre-commit hooks run locally. But what if someone skips them? (git commit --no-verify). That's where CI/CD comes in.

on: [push, pull_request]

jobs:
  mypy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5

          python-version: "3.12"
      - run: pip install mypy
      - run: mypy src/ --strict

# If mypy fails, the PR gets a red X.
# Most teams require all checks to pass before merging.

A developer skips the pre-commit hook with --no-verify and pushes code with a type error. What happens?

Defense in depth. Pre-commit hooks are the first layer (local). CI/CD is the second layer (server-side). Even if someone skips hooks, the CI pipeline catches type errors on the PR. The PR shows a red X and the team can block merging until all checks pass. This is standard at companies like Stripe, Instagram, and Dropbox.

Doubt Clarification

Callable — Explained Simply

A function that takes another function as a parameter. How do you type "the function I'm passing in"?

Step 1: Functions are objects in Python

You already know this. You can store a function in a variable, pass it around, return it from another function.

Functions are just objects
▼
def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

# Store a function in a variable (NO parentheses = the function itself)
operation = add
print(operation(3, 4))   # 7

operation = multiply
print(operation(3, 4))   # 12

Step 2: Pass a function to another function

Without types — what is 'func'?
▼
def do_math(a, b, func):
    """What should func look like? 1 arg? 2 args? What does it return?"""
    return func(a, b)

do_math(5, 3, add)       # 8  — passed the add function
do_math(5, 3, multiply)  # 15 — passed the multiply function

The problem: A new developer sees func as a parameter. They ask: "What kind of function do I pass? How many arguments? What should it return?" There's no way to know without reading the implementation.

Step 3: Callable — "here's the shape of the function"

Callable[[parameter types], return type]

Think of it as a blueprint: "I need a function that takes these inputs and gives back this output."
With Callable — crystal clear
▼
from typing import Callable

def do_math(a: int, b: int, func: Callable[[int, int], int]) -> int:
    #                                ^^^^^^^^^^^^^^^^^^^^^^^^
    #                                func takes (int, int)
    #                                and returns int
    return func(a, b)

# Now any developer knows EXACTLY what to pass:
do_math(5, 3, add)       # ✔ add takes (int, int) returns int
do_math(5, 3, multiply)  # ✔ multiply takes (int, int) returns int
do_math(5, 3, len)       # ✘ mypy error! len takes 1 arg, not 2

Reading the Syntax

Callable TypeMeansExample Function
Callable[[int, int], int] Takes 2 ints, returns an int def add(a: int, b: int) -> int
Callable[[str], None] Takes 1 string, returns nothing def log(msg: str) -> None
Callable[[], str] Takes nothing, returns a string def greet() -> str
Callable[[dict], list[str]] Takes a dict, returns list of strings def get_keys(d: dict) -> list[str]

What does Callable[[str, int], bool] describe?

Read it as: Callable[[inputs...], output]. First bracket = what goes IN. After the bracket = what comes OUT. So Callable[[str, int], bool] = a function like def is_valid(name: str, age: int) -> bool.

Where You'll See Callable in Real Code

Real-world uses
▼
# 1. Event handler / callback
def on_click(handler: Callable[[int, int], None]) -> None:
    handler(100, 200)  # call it when user clicks

# 2. Retry logic
def retry(func: Callable[[], str], times: int = 3) -> str:
    for i in range(times):
        try:
            return func()
        except:
            pass

# 3. Strategy pattern (from OOP classes!)
def sort_users(users: list, key: Callable[[User], int]) -> list:
    return sorted(users, key=key)

# 4. Decorator
def timer(func: Callable[..., Any]) -> Callable[..., Any]:
    # ... wraps func with timing logic
    ...

Callable in one sentence:
It's the type hint for a function. Just like int describes "a number" and str describes "text", Callable[[int, int], int] describes "a function that takes two ints and returns an int."

When to use it: Any time a function accepts another function as a parameter — callbacks, strategies, decorators, middleware, retry logic, event handlers, sorted(key=...), map(func, ...).
