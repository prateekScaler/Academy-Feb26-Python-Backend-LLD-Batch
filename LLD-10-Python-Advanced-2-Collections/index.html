Python's built-in list and dict are great. But for specific problems, the collections module has purpose-built tools that are faster, cleaner, and less buggy.

Recap — Last Class

Typing, Generics & AI Agents

Quick check on last class's concepts before we move on.

Read this code. When does it crash?
▼
def find_user(user_id: int) -> dict | None:
    users = {1: {"name": "Alice"}, 2: {"name": "Bob"}}
    return users.get(user_id)

user = find_user(999)
print(user["name"])    # ← What happens here?

When does this bug surface?

Types are hints, not constraints. Python happily runs user["name"] and crashes with TypeError: 'NoneType' object is not subscriptable at runtime. mypy would have caught it — it sees dict | None and errors if you don't check for None. But mypy is a separate tool. That's why you need it in your CI/CD pipeline.
What type does result get?
▼
from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T:
    return items[0]

result = first(["apple", "banana"])
result.???   # What methods does the IDE offer?

What type does the IDE show for result?

TypeVar flows through. Input is list[str], so T = str. Return type T becomes str. The IDE knows result is a str and offers .upper(), .split(), .startswith() etc. That's the power of generics — the type is preserved, not erased to Any.

You want your AI coding agent (Claude, Cursor, Copilot) to always use type hints and follow your project conventions. Where do you put these instructions?

Project-level instructions for AI agents. CLAUDE.md is read automatically by Claude Code at the start of every session. .cursorrules does the same for Cursor. You write rules like "always use type hints", "use dataclasses not plain dicts", "follow PEP 8" — and the agent follows them for every file it touches. One file, every session, no repeating yourself.

You create a CLAUDE.md with: "Always add type hints to all function parameters and return types." What happens when the agent writes new code?

CLAUDE.md is your project's "agent constitution." Every time Claude Code starts a session in your repo, it reads this file first. Rules you put here apply to ALL code it writes — type hints, naming conventions, import styles, test patterns. Think of it as .editorconfig but for AI. Same concept: .cursorrules for Cursor, .github/copilot-instructions.md for Copilot.

Your team has a pre-commit hook running mypy. A developer writes code without type hints. What happens when they git commit?

Pre-commit hooks block bad commits. If mypy returns a non-zero exit code (type errors found), git refuses to create the commit. The developer must fix the type errors first. This is layer 1 of defense. Layer 2 is CI/CD on the PR. Type-broken code never reaches main.
From Last Class

The Journey: Nothing → ABC → Protocol

We didn't start with Protocol. We got here step by step. Let's retrace the path.

1 No Contract — Just Hope

In early OOP classes, we wrote code like this. Anyone can pass anything.

Step 1: No contract at all
▼
def render_all(shapes):
    for shape in shapes:
        shape.draw()   # Hope it has draw()... no guarantee!

class Circle:
    def draw(self): print("Drawing circle")

class Cat:
    def meow(self): print("Meow")

render_all([Circle()])   # ✔ works
render_all([Cat()])      # ✘ AttributeError at RUNTIME! No draw() method.
# Bug found in production, not at write time.
Problem: No way to enforce that shapes have a draw() method. The error only shows up at runtime when someone passes a Cat. In a 50K-line codebase, this could sit undetected for weeks.

2 ABC — Enforce a Contract

In the OOP-3 class, we introduced Abstract Base Classes. Now Python refuses to create an object that doesn't implement the required methods.

Step 2: ABC enforces the contract
▼
from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self) -> str: ...

class Circle(Drawable):            # MUST inherit from Drawable
    def draw(self) -> str:
        return "Drawing circle"

class BadShape(Drawable):           # Inherits but forgets draw()
    pass

Circle()     # ✔ works — draw() is implemented
BadShape()   # ✘ TypeError: Can't instantiate abstract class!
# Bug caught at object CREATION, not at draw() call. Much better!
ABC is great! It catches missing methods at object creation, not at runtime deep inside your code. But...

You're using a third-party logging library. It has a Logger class with a log(msg) method. You want your function to accept any logger with log(). Can you use ABC?

ABC requires the class author to opt in by inheriting from the ABC. You can't change a library's source code to add class Logger(YourABC). ABC only works when you own all the classes. For third-party code, duck typing, or plugins — you need something else.

3 Protocol — "If It Has the Methods, It's Valid"

Protocol checks the shape of the class, not its family tree. No inheritance needed.

Step 3: Protocol — structural typing
▼
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> str: ...

# These DON'T inherit from Drawable. They just have draw().
class Circle:
    def draw(self) -> str:
        return "Drawing circle"

class Square:
    def draw(self) -> str:
        return "Drawing square"

# Third-party class you didn't write:
class ThirdPartyWidget:
    def draw(self) -> str:
        return "Drawing widget"

def render_all(shapes: list[Drawable]) -> None:
    for shape in shapes:
        print(shape.draw())

# ALL work — even the third-party class!
render_all([Circle(), Square(), ThirdPartyWidget()])
Protocol = duck typing + type safety. "If it walks like a duck and quacks like a duck..." — but now mypy verifies it at check time. No runtime surprises, no forced inheritance.

When to Use Which?

ApproachHow It WorksWhen to Use
Nothing
plain duck typing		 No contract. Hope for the best. Quick scripts, prototypes. You know what's being passed. Small team, small codebase.
ABC
nominal typing		 Must inherit. Error at object creation if methods missing. You own ALL the classes. Building a framework with a class hierarchy (Shape, Animal, PaymentGateway). Want runtime enforcement.
Protocol
structural typing		 Just needs the right methods. No inheritance. mypy checks at analysis time. Third-party code, plugins, duck typing. You can't (or don't want to) force inheritance. Go-style interfaces.

You're building a payment system. You own all payment classes (Razorpay, Stripe, PayPal). Which approach?

ABC is the right choice here. You own all the classes. You want Python to refuse to create a Razorpay() that forgot to implement process_payment(). ABC catches this at object creation. Protocol would only catch it when mypy runs (static check), not at runtime. Use ABC when you own the hierarchy and want runtime safety. Use Protocol when you can't control the classes.

The evolution:
• Nothing → bugs found at runtime, deep in the call stack
• ABC → bugs found at object creation (runtime), but requires inheritance
• Protocol → bugs found by mypy (before runtime), no inheritance needed

Rule of thumb: Own the classes? → ABC. Don't own them? → Protocol. Quick script? → Neither.

The Premise

Why Not Just Use list and dict?

You can build a house with just a hammer and nails. But a screwdriver, level, and drill make you 10x faster and less error-prone.

Part 1: Built-in Collections — Quick Primer

Before we touch the collections module, let's make sure the built-ins are solid. These need no import.

list — ordered, mutable, allows duplicates

▼ 
nums = [3, 1, 4, 1, 5]       # duplicates OK
nums.append(9)                    # [3, 1, 4, 1, 5, 9]
nums.sort()                        # [1, 1, 3, 4, 5, 9]
nums[0]                            # 1 — O(1) random access
nums.insert(0, 99)                # O(n)! Shifts everything right
print(3 in nums)                 # True — O(n) membership check

tuple — ordered, immutable, allows duplicates

▼ 
point = (3, 7)                   # fixed, immutable
x, y = point                       # unpacking
point[0]                           # 3 — O(1) access
# point[0] = 10                    # TypeError! Can't mutate.

# Multiple return values:
def get_user():
    return "Alice", 25             # actually returns a tuple
name, age = get_user()

# Can be a dict key (immutable = hashable):
locations = {(28.6, 77.2): "Delhi", (19.0, 72.8): "Mumbai"}

dict — key-value pairs, O(1) lookup, ordered (3.7+)

▼ 
scores = {"Alice": 95, "Bob": 87}
scores["Alice"]                    # 95 — O(1) lookup
scores["Charlie"]                  # KeyError!
scores.get("Charlie", 0)           # 0 — safe, no error
scores["Charlie"] = 92             # O(1) insert

# Iteration (Python 3.7+: insertion order preserved)
for name, score in scores.items():
    print(f"{name}: {score}")

# Keys must be HASHABLE (immutable):
valid   = {"name": 1, 42: 2, (1,2): 3}   # str, int, tuple → OK
invalid = {[1,2]: 3}                     # list → TypeError: unhashable type

set — unordered, unique elements, O(1) membership

▼ 
tags = {"python", "backend", "python"}  # {'python', 'backend'} — deduped
tags.add("django")
print("python" in tags)            # True — O(1) membership!

# Set algebra:
a = {1, 2, 3}
b = {2, 3, 4}
a | b   # {1, 2, 3, 4}  union
a & b   # {2, 3}        intersection
a - b   # {1}           difference

# No indexing: s[0] is TypeError! Sets are unordered.
# Elements must be hashable: strings, ints, tuples OK. Lists NO.

frozenset — immutable set, hashable (can be a dict key!)

▼ 
# Regular set can't be a dict key:
# {{"python", "backend"}: "team_a"}  → TypeError!

# frozenset can:
tags = frozenset({"python", "backend"})
teams = {tags: "team_a"}  # Works! frozenset is hashable.

# All set operations work (return new frozensets):
a = frozenset({1, 2})
b = frozenset({2, 3})
a | b   # frozenset({1, 2, 3})
a & b   # frozenset({2})

Why Must Dict Keys Be Immutable?

A dict is a hash table. When you store d["alice"] = 95, Python computes a hash of the key to decide where in memory to put the value. Lookup works the same way — hash the key, jump to that slot.

How d["alice"] = 95 works internally
Key: "alice"
immutable string
→
hash("alice")
= 3248679812
→
3248.. % 8
= slot 4
→
Slot 4: 95
value stored here
Now imagine the key was a list...
Key: [1, 2]
hash = 789
→
Stored in
slot 5
→
key.append(3)
[1, 2, 3]
hash is now 142!
→
Lookup: slot 2
Wrong slot! Value lost.
If the key mutates, its hash changes. The value is still in slot 5, but the new hash points to slot 2. The dict can never find it again. That's why Python refuses mutable keys — list, dict, set all raise TypeError: unhashable type. Only immutable types (str, int, tuple, frozenset) have a stable hash.

Built-in Gotchas — Interview Favorites

What type is a?  a = {}

{} is always a dict. For an empty set, you must use set().

a = {} # type(a) → <class 'dict'> b = set() # type(b) → <class 'set'> c = {1, 2, 3} # type(c) → <class 'set'> (values make it a set)

What does this print?  t = (42) then print(type(t))

(42) is just parentheses around the number 42 — it's an int. For a single-element tuple, you need (42,) with the trailing comma. This is a classic Python gotcha. (1, 2, 3) works without because the commas make it a tuple, not the parentheses.

What does s = {1, 2, 3}; print(s[0]) do?

Sets have no order and no indexing. You can iterate, add, remove, and check membership (x in s is O(1)), but you can't access by position. If you need order + uniqueness, use dict.fromkeys() (Python 3.7+ dicts preserve insertion order).

Which of these is valid?  d1 = {(1, 2): "a"}  vs  d2 = {[1, 2]: "a"}

Dict keys must be hashable. Tuples are immutable → hashable → valid keys. Lists are mutable → unhashable → TypeError. Same rule for set elements. This is why frozenset exists — an immutable, hashable set.
What does the second call print?
▼
def add(name, students=[]):
    students.append(name)
    return students

add("Alice")
print(add("Bob"))   # What prints here?

What does add("Bob") return?

Mutable default arguments are shared. The default [] is created ONCE when the function is defined, not on each call. Every call appends to the SAME list.

# Fix: use None as default, create new list inside def add(name, students=None): if students is None: students = [] students.append(name) return students

No More KeyError

defaultdict

Group, count, or collect — without checking if the key exists first.

Problem: Group words by their first letter. What if we skip the boilerplate?

What happens if we just do grouped[key].append(word)?
▼
words = ["apple", "banana", "avocado", "blueberry"]
grouped = {}

for word in words:
    grouped[word[0]].append(word)   # No if-check. What happens?

What happens when this runs?

KeyError! grouped["a"] doesn't exist yet, so Python can't call .append() on it. You must create the empty list first. That's why you see this boilerplate everywhere:

if key not in grouped: grouped[key] = [] # create the list first grouped[key].append(word) # now append works
This is exactly what defaultdict eliminates.

Plain dict (verbose)

The hard way
▼
words = ["apple", "banana", "avocado", "blueberry"]
grouped = {}

for word in words:
    key = word[0]
    if key not in grouped:   # Boilerplate!
        grouped[key] = []     # Every. Single. Time.
    grouped[key].append(word)

defaultdict (clean)

The right way
▼
from collections import defaultdict

words = ["apple", "banana", "avocado", "blueberry"]
grouped = defaultdict(list)  # Missing key? Create []

for word in words:
    grouped[word[0]].append(word)  # Just use it!

# {'a': ['apple', 'avocado'], 'b': ['banana', 'blueberry']}

What happens when you access a key that doesn't exist in a plain dict?

KeyError. Plain dict throws KeyError for missing keys. That's why you see if key not in d everywhere. defaultdict eliminates this by auto-creating a default value.

📈 defaultdict(int) — Counting

▼
Count occurrences
▼
from collections import defaultdict

votes = ["alice", "bob", "alice", "charlie", "bob", "alice"]
counts = defaultdict(int)  # Missing key? Start at 0

for name in votes:
    counts[name] += 1

# defaultdict(int, {'alice': 3, 'bob': 2, 'charlie': 1})

🎯 defaultdict(set) — Unique Values

▼
Unique tags per user
▼
user_tags = defaultdict(set)

user_tags["alice"].add("python")
user_tags["alice"].add("django")
user_tags["alice"].add("python")  # Duplicate ignored

# {'alice': {'python', 'django'}}
⚠️ Gotcha: Simply accessing a missing key in a defaultdict creates it. d = defaultdict(list); d["ghost"] now has key "ghost" with value []. This can cause subtle bugs if you check "ghost" in d after accessing it.

Factory functions: The argument to defaultdict is a callable (a factory). list → [], int → 0, set → set(), lambda: "N/A" → "N/A". It calls the factory every time a missing key is accessed.

Real-life use cases:
• Grouping API responses — group orders by customer_id, logs by severity level
• Building adjacency lists — graph representation: graph = defaultdict(list); graph[node].append(neighbor)
• Inverted index — search engines: word → list of documents containing it
• Collecting unique tags — defaultdict(set) to track unique categories per user

Count Everything

Counter

A dict subclass designed for counting. Handles the common case so you don't have to.

Question: You need word frequencies from a paragraph. You could use defaultdict(int) and loop. But what if Python had a one-liner?

Counter basics
▼
from collections import Counter

words = ["apple", "banana", "apple", "cherry", "banana", "apple"]
counts = Counter(words)

print(counts)
# Counter({'apple': 3, 'banana': 2, 'cherry': 1})

# Missing key? Returns 0, not KeyError!
print(counts["mango"])  # 0

# Top N most common
print(counts.most_common(2))
# [('apple', 3), ('banana', 2)]
Real-world: Vote counting
▼
votes = ["Alice", "Bob", "Alice", "Charlie", "Alice", "Bob"]
vote_counts = Counter(votes)
# Counter({'Alice': 3, 'Bob': 2, 'Charlie': 1})

winner = vote_counts.most_common(1)[0]
print(f"Winner: {winner[0]} with {winner[1]} votes")
# Winner: Alice with 3 votes
Key difference from dict: counter["missing_key"] returns 0, not KeyError. And unlike defaultdict(int), it doesn't create the key either. It just returns 0.
What does this print?
▼
from collections import Counter

c1 = Counter(["a", "b", "c", "a"])
c2 = Counter(["a", "b", "d"])

result = c1 + c2
print(result["a"])   # What prints here?

What does (c1 + c2)["a"] return?

c1 + c2 adds the counts for each key:

c1 = {'a': 2, 'b': 1, 'c': 1} c2 = {'a': 1, 'b': 1, 'd': 1} c1 + c2 = {'a': 3, 'b': 2, 'c': 1, 'd': 1} # a: 2+1 = 3
Counter arithmetic treats counts like numbers. Subtraction drops results ≤ 0.

✅ Counter Arithmetic

▼
+, -, &, |
▼
inventory_a = Counter({"apple": 5, "banana": 3})
inventory_b = Counter({"apple": 2, "cherry": 7})

# Addition: combine inventories
print(inventory_a + inventory_b)
# Counter({'cherry': 7, 'apple': 7, 'banana': 3})

# Subtraction: what's left after selling?
print(inventory_a - inventory_b)
# Counter({'banana': 3, 'apple': 3})  # Negative counts dropped!

# Intersection (&): minimum of each
print(inventory_a & inventory_b)
# Counter({'apple': 2})

# Union (|): maximum of each
print(inventory_a | inventory_b)
# Counter({'cherry': 7, 'apple': 5, 'banana': 3})

Counter("mississippi") — which letter is most common?

Counter('mississippi') gives {'i': 4, 's': 4, 'p': 2, 'm': 1}. Both 'i' and 's' appear 4 times. most_common(1) returns one of the tied elements. The key insight: Counter works on any iterable, including strings (which iterate over characters).

Real-life use cases for Counter:
• Word frequency — NLP, search engines: find most common terms in a document
• Vote counting — elections, polls: Counter(votes).most_common(1) = winner
• Inventory management — combine warehouse stock (c1 + c2), track sold items (c1 - c2)
• Log analysis — count error types: how many 404s vs 500s today?
• Feature usage metrics — which buttons do users click most?
• Duplicate detection — [x for x, count in Counter(items).items() if count > 1]

Performance Matters

deque

A double-ended queue. When you need fast operations on both ends.

Problem: list.insert(0, x) is O(n) — it shifts every element. If you're building a queue (FIFO), this kills performance. What if prepending was O(1)?

⏰ Performance reality: list.insert(0, x) on a list of 1,000,000 elements shifts ALL of them. deque.appendleft(x) does it in constant time. For queue-like operations, deque can be 1000x faster.
deque operations
▼
from collections import deque

d = deque([1, 2, 3])

# Add to both ends — both O(1)
d.append(4)         # [1, 2, 3, 4]
d.appendleft(0)     # [0, 1, 2, 3, 4]

# Remove from both ends — both O(1)
d.pop()              # 4  → [0, 1, 2, 3]
d.popleft()          # 0  → [1, 2, 3]

📋 maxlen — Sliding Window / Recent Logs

▼
Bounded deque
▼
# Keep only the last 3 log entries
recent_logs = deque(maxlen=3)

recent_logs.append("Login")
recent_logs.append("View page")
recent_logs.append("Add to cart")
recent_logs.append("Checkout")  # "Login" is auto-evicted!

print(list(recent_logs))
# ['View page', 'Add to cart', 'Checkout']

When the deque is full and you append, the oldest item is automatically removed. Perfect for "last N items" patterns.

Real-life use cases for deque:
• BFS traversal — process graph/tree nodes in discovery order (append + popleft)
• Task queue — Celery-like job processing: add tasks, workers pick from front

Readable Tuples

namedtuple

Give your tuples names. Stop guessing what index 0 means.

Problem: point = (3, 7) — is point[0] the x or the y? With plain tuples, you're reading code like it's a puzzle.

Plain tuple

Confusing
▼
point = (3, 7)
print(point[0])  # What is 0? x? y? z?
print(point[1])  # Hope you remember...

namedtuple

Self-documenting
▼
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(3, 7)
print(p.x)  # 3 — crystal clear
print(p.y)  # 7

📝 Typed NamedTuple (modern syntax)

▼
typing.NamedTuple
▼
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float
    label: str = "origin"  # Default value

p = Point(3.0, 7.0)
print(p.label)  # "origin"

🔧 _replace, _asdict, unpacking

▼
Useful methods
▼
Point = namedtuple("Point", ["x", "y"])
p = Point(3, 7)

# _replace — returns NEW tuple (immutable!)
p2 = p._replace(x=10)
print(p2)  # Point(x=10, y=7)

# _asdict — convert to dict
print(p._asdict())  # {'x': 3, 'y': 7}

# Unpacking — works like regular tuple
x, y = p
print(x, y)  # 3 7

namedtuple vs dataclass — which is immutable by default?

namedtuple is always immutable — it's a tuple subclass. p.x = 5 raises AttributeError. Dataclasses are mutable by default; you need @dataclass(frozen=True) to make them immutable. Use namedtuple for simple, immutable records. Use dataclass for complex, mutable objects.

Tricky: t = ([1, 2], 3). Can you do t[0].append(99)?

Tuple immutability is shallow. You can't reassign t[0] = [4, 5] (that changes the tuple), but you CAN mutate the list inside it: t[0].append(99) works fine because the tuple still holds the same list object — the list's contents changed, not the tuple's reference. This is a classic interview question.

Real-life use cases for namedtuple:
• Database rows — row.name instead of row[0]. Python's sqlite3 can return namedtuples.
• API responses — parse JSON into HTTPResponse(status=200, body=...)
• Coordinates / Points — Point(x=3, y=7) instead of (3, 7)
• Function return values — return Result(success=True, data=...) instead of a plain tuple
• Config — immutable settings objects, less memory than dict, hashable (can be cached)

Special-Purpose

OrderedDict, ChainMap & frozenset

Niche tools that solve specific problems elegantly.

📚 OrderedDict — Order-Sensitive Equality

▼

Since Python 3.7, regular dict preserves insertion order. So why does OrderedDict still exist?

Order matters for equality
▼
from collections import OrderedDict

# Regular dict: order doesn't affect equality
d1 = {"a": 1, "b": 2}
d2 = {"b": 2, "a": 1}
print(d1 == d2)  # True — same keys & values

# OrderedDict: order IS part of equality
od1 = OrderedDict({"a": 1, "b": 2})
od2 = OrderedDict({"b": 2, "a": 1})
print(od1 == od2)  # False — different order!

# move_to_end — useful for LRU cache
od1.move_to_end("a")  # Move to end (most recent)
od1.move_to_end("b", last=False)  # Move to front

🔗 ChainMap — Layered Dict Lookups

▼
Config layering
▼
from collections import ChainMap

defaults = {"theme": "light", "lang": "en", "debug": False}
env_config = {"debug": True}
user_config = {"theme": "dark"}

# Lookup priority: user > env > defaults
config = ChainMap(user_config, env_config, defaults)

print(config["theme"])  # "dark"  (from user_config)
print(config["debug"])  # True   (from env_config)
print(config["lang"])   # "en"   (from defaults)

# Writes go to the FIRST dict only
config["lang"] = "fr"
print(user_config)  # {'theme': 'dark', 'lang': 'fr'}

ChainMap doesn't merge dicts — it searches them in order. Changes go to the first dict. Think of it like scope resolution: local > enclosing > global > built-in.

❄️ frozenset — Immutable Set

▼
Hashable sets
▼
# Regular set — mutable, NOT hashable
s = {1, 2, 3}
# d = {s: "value"}  # TypeError: unhashable type: 'set'

# frozenset — immutable, IS hashable
fs = frozenset([1, 2, 3])

# Set of sets (using frozenset)
groups = {
    frozenset(["alice", "bob"]),
    frozenset(["charlie", "dave"]),
}

# frozenset supports all read operations
print(fs & frozenset([2, 3, 4]))  # frozenset({2, 3})

Can you use a regular set as a dictionary key?

Dict keys must be hashable. Mutable types (list, set, dict) are unhashable — their hash could change if contents change. frozenset is immutable, so it has a stable hash and can be a dict key or set element.

Real-life use cases:

OrderedDict:
• LRU Cache — move_to_end() marks recently used, popitem(last=False) evicts oldest
• JSON output with guaranteed key order — when API contract requires specific field order
• Test assertions — when order of items matters for correctness

ChainMap:
• Django settings — base.py → dev.py → local.py: each overrides the previous
• CLI tools — ChainMap(cli_args, env_vars, config_file, defaults): first match wins
• Template engines — variable scopes: local block → parent template → global context
• Python itself — scope resolution uses this pattern: local → enclosing → global → builtin

frozenset:
• Caching — use frozenset(args) as a cache key when order doesn't matter
• Graph edges — frozenset({A, B}) = undirected edge (A-B same as B-A)
• Permissions — immutable set of roles: frozenset({"admin", "editor"})
• Feature combinations — ML: dict key = frozenset of feature names

Don't Subclass dict!

Custom Collections

When you need to customize built-in behavior, use UserDict, UserList, and UserString. But first — why does subclassing break?

The Bug

Broken: subclassing dict

BrokenUpperDict
▼
class BrokenUpperDict(dict):
    def __setitem__(self, key, val):
        super().__setitem__(key.upper(), val)

d = BrokenUpperDict()
d["hello"] = 1            # ✔ "HELLO"
d.update({"world": 2})   # ✘ "world" lowercase!
print(d)
# {'HELLO': 1, 'world': 2}  ← BROKEN!

Correct: UserDict

UpperDict
▼
from collections import UserDict

class UpperDict(UserDict):
    def __setitem__(self, key, val):
        super().__setitem__(key.upper(), val)

d = UpperDict()
d["hello"] = 1
d.update({"world": 2})
print(d)
# {'HELLO': 1, 'WORLD': 2}  ← CORRECT!

But WHY does it break?

Python's built-in dict, list, and str are implemented in C for speed. When you subclass them and override a method in Python, the C methods don't know about your override.

The root cause: dict is written in C. Its update(), __init__(), setdefault(), etc. are all C functions that directly manipulate the internal hash table. They don't call your Python __setitem__. UserDict is a pure Python wrapper around a regular dict (stored as self.data). All its methods go through __setitem__, so your overrides always work. Same applies to list/UserList and str/UserString.

Why does subclassing dict directly break when you override __setitem__?

C code doesn't call Python code. dict.update() is a C function that writes directly to the hash table. It never calls your Python __setitem__. UserDict.update() is Python code that loops through items and calls self.__setitem__() for each one. That's the entire difference.

📜 UserList — Validated list (only positive numbers)

▼
PositiveList
▼
from collections import UserList

class PositiveList(UserList):
    def append(self, item):
        if item <= 0:
            raise ValueError(f"Only positive: got {item}")
        super().append(item)

    def __setitem__(self, index, item):
        if item <= 0:
            raise ValueError(f"Only positive: got {item}")
        super().__setitem__(index, item)

nums = PositiveList([1, 2, 3])
nums.append(4)     # ✔ [1, 2, 3, 4]
nums.append(-1)    # ✘ ValueError! Only positive
nums[0] = -5       # ✘ ValueError! Validation on assignment too

# Why not subclass list?
# list.extend() and list.__init__() are C code.
# They'd bypass your append() override. Same bug as dict.

Use case: Validated data structures — a list that enforces types, ranges, or business rules on every modification. Think: a playlist that only allows Song objects, an order list that rejects negative quantities.

📝 UserString — Custom string behavior

▼

Python's str is immutable and implemented in C. You can't override __eq__ or __contains__ reliably by subclassing str because many operations return a plain str, not your subclass.

CaselessString — case-insensitive comparison
▼
from collections import UserString

class CaselessString(UserString):
    def __eq__(self, other):
        return self.data.lower() == str(other).lower()

    def __contains__(self, item):
        return str(item).lower() in self.data.lower()

s = CaselessString("Hello World")
print(s == "HELLO WORLD")     # True
print(s == "hello world")     # True
print("WORLD" in s)           # True

# self.data holds the actual string
print(s.data)                   # "Hello World" (original case preserved)
print(s.upper())                # "HELLO WORLD" — all str methods still work
Why not subclass str? Because str is immutable C code. When you do "Hello" + " World" on a str subclass, Python returns a plain str, not your subclass. Your custom behavior vanishes. UserString stores the string in self.data and delegates all operations through Python methods, so your overrides always apply.

Use cases: Case-insensitive strings (configuration keys, HTTP headers), strings with validation (email format, max length), strings that auto-sanitize HTML, currency/phone number formatting.

📦 queue.Queue — Thread-Safe by Design

▼
Producer-Consumer
▼
import queue
import threading

q = queue.Queue(maxsize=10)

def producer():
    for i in range(5):
        q.put(i)         # Blocks if full
        print(f"Produced {i}")

def consumer():
    while True:
        item = q.get()   # Blocks if empty
        print(f"Consumed {item}")
        q.task_done()

t1 = threading.Thread(target=producer)
t2 = threading.Thread(target=consumer, daemon=True)
t1.start(); t2.start()
t1.join()
⚠️ Don't rely on the GIL. PEP 703 (accepted) introduces a no-GIL build of CPython. In future Python versions, even list.append() may not be thread-safe. Use queue.Queue, threading.Lock, or concurrent.futures for thread-safe code.

Is list.append() thread-safe in CPython?

Currently safe, but don't depend on it. list.append() is a single bytecode op, so the GIL makes it atomic in CPython. But this is an implementation detail, not a language guarantee. PEP 703 (no-GIL Python) will break this assumption. Use proper synchronization for production code.

Wrap Up

Key Takeaways

📑
defaultdict & Counter
defaultdict eliminates key-existence checks with factory functions (list, int, set). Counter counts elements in one line and supports arithmetic (+, -, &, |).
⚡
deque
O(1) operations on both ends. Use for queues (FIFO), stacks (LIFO), sliding windows (maxlen), and BFS. Don't use for random access.
🏷️
namedtuple
Immutable, lightweight, self-documenting records. Use typing.NamedTuple for type hints. Supports _replace, _asdict, and unpacking.
🔧
User* Classes
Never subclass dict/list/str directly. Use UserDict, UserList, UserString for reliable method overrides. C implementations bypass your Python overrides.
