Collections

LLD-10 • Python Advanced-2

Python's built-in list and dict are great. But for specific problems, the collections module has purpose-built tools that are faster, cleaner, and less buggy.

Recap — Last Class

Typing, Generics & AI Agents

Quick check on last class's concepts before we move on.

find_user(999) returns None. You call user["name"] without checking. When does the bug surface?

Types are hints, not constraints. Python happily runs user["name"] and crashes with TypeError at runtime. mypy would catch it if you run it — but mypy is a separate tool, not part of Python's execution. That's why you need mypy in your CI/CD pipeline or pre-commit hooks.

def first(items: list[T]) -> T — you call first(["apple", "banana"]). What type does the IDE show for the return value?

TypeVar flows through. Input is list[str], so T = str. Return type T becomes str. The IDE offers .upper(), .split() etc. That's the power of generics — the type is preserved, not erased to Any.

You want your AI coding agent (Claude, Cursor, Copilot) to always use type hints and follow your project conventions. Where do you put these instructions?

Project-level instructions for AI agents. CLAUDE.md is read automatically by Claude Code at the start of every session. .cursorrules does the same for Cursor. You write rules like "always use type hints", "use dataclasses not plain dicts", "follow PEP 8" — and the agent follows them for every file it touches. One file, every session, no repeating yourself.

You create a CLAUDE.md with: "Always add type hints to all function parameters and return types." What happens when the agent writes new code?

CLAUDE.md is your project's "agent constitution." Every time Claude Code starts a session in your repo, it reads this file first. Rules you put here apply to ALL code it writes — type hints, naming conventions, import styles, test patterns. Think of it as .editorconfig but for AI. Same concept: .cursorrules for Cursor, .github/copilot-instructions.md for Copilot.

Your team has a pre-commit hook running mypy. A developer writes code without type hints. What happens when they git commit?

Pre-commit hooks block bad commits. If mypy returns a non-zero exit code (type errors found), git refuses to create the commit. The developer must fix the type errors first. This is layer 1 of defense. Layer 2 is CI/CD on the PR. Type-broken code never reaches main.
From Last Class

Protocol — Duck Typing with Type Safety

ABC forces inheritance. Protocol doesn't. "If it has the methods, it's valid." — structural subtyping, not nominal.

Protocol example
▼
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> str: ...

# No inheritance! Just has the method.
class Circle:
    def draw(self) -> str:
        return "Drawing circle"

class Square:
    def draw(self) -> str:
        return "Drawing square"

def render_all(shapes: list[Drawable]) -> None:
    for shape in shapes:
        print(shape.draw())

# Works! Circle and Square satisfy Drawable protocol.
render_all([Circle(), Square()])

You have a third-party Logger class with a log() method. You want type-safe logging. Can you use ABC?

Protocol is the answer. ABC requires the class to inherit from it. You can't modify third-party source code to add inheritance. Protocol only checks if the methods exist — no inheritance needed.
No More KeyError

defaultdict

Group, count, or collect — without checking if the key exists first.

Problem: You have a list of words. Group them by first letter. With a plain dict, every key access needs an if-check or try-except. Can we do better?

Plain dict (verbose)

The hard way
▼
words = ["apple", "banana", "avocado", "blueberry"]
grouped = {}

for word in words:
    key = word[0]
    if key not in grouped:   # Boilerplate!
        grouped[key] = []     # Every. Single. Time.
    grouped[key].append(word)

defaultdict (clean)

The right way
▼
from collections import defaultdict

words = ["apple", "banana", "avocado", "blueberry"]
grouped = defaultdict(list)  # Missing key? Create []

for word in words:
    grouped[word[0]].append(word)  # Just use it!

# {'a': ['apple', 'avocado'], 'b': ['banana', 'blueberry']}

What happens when you access a key that doesn't exist in a plain dict?

KeyError. Plain dict throws KeyError for missing keys. That's why you see if key not in d everywhere. defaultdict eliminates this by auto-creating a default value.

📈 defaultdict(int) — Counting

▼
Count occurrences
▼
from collections import defaultdict

votes = ["alice", "bob", "alice", "charlie", "bob", "alice"]
counts = defaultdict(int)  # Missing key? Start at 0

for name in votes:
    counts[name] += 1

# defaultdict(int, {'alice': 3, 'bob': 2, 'charlie': 1})

🎯 defaultdict(set) — Unique Values

▼
Unique tags per user
▼
user_tags = defaultdict(set)

user_tags["alice"].add("python")
user_tags["alice"].add("django")
user_tags["alice"].add("python")  # Duplicate ignored

# {'alice': {'python', 'django'}}
⚠️ Gotcha: Simply accessing a missing key in a defaultdict creates it. d = defaultdict(list); d["ghost"] now has key "ghost" with value []. This can cause subtle bugs if you check "ghost" in d after accessing it.

Factory functions: The argument to defaultdict is a callable (a factory). list → [], int → 0, set → set(), lambda: "N/A" → "N/A". It calls the factory every time a missing key is accessed. You can pass any zero-argument callable.

Count Everything

Counter

A dict subclass designed for counting. Handles the common case so you don't have to.

Question: You need word frequencies from a paragraph. You could use defaultdict(int) and loop. But what if Python had a one-liner?

Counter basics
▼
from collections import Counter

words = ["apple", "banana", "apple", "cherry", "banana", "apple"]
counts = Counter(words)

print(counts)
# Counter({'apple': 3, 'banana': 2, 'cherry': 1})

# Missing key? Returns 0, not KeyError!
print(counts["mango"])  # 0

# Top N most common
print(counts.most_common(2))
# [('apple', 3), ('banana', 2)]
Key difference from dict: counter["missing_key"] returns 0, not KeyError. And unlike defaultdict(int), it doesn't create the key either. It just returns 0.

✅ Counter Arithmetic

▼
+, -, &, |
▼
inventory_a = Counter({"apple": 5, "banana": 3})
inventory_b = Counter({"apple": 2, "cherry": 7})

# Addition: combine inventories
print(inventory_a + inventory_b)
# Counter({'cherry': 7, 'apple': 7, 'banana': 3})

# Subtraction: what's left after selling?
print(inventory_a - inventory_b)
# Counter({'banana': 3, 'apple': 3})  # Negative counts dropped!

# Intersection (&): minimum of each
print(inventory_a & inventory_b)
# Counter({'apple': 2})

# Union (|): maximum of each
print(inventory_a | inventory_b)
# Counter({'cherry': 7, 'apple': 5, 'banana': 3})

Counter("mississippi") — which letter is most common?

Counter('mississippi') gives {'i': 4, 's': 4, 'p': 2, 'm': 1}. Both 'i' and 's' appear 4 times. most_common(1) returns one of the tied elements. The key insight: Counter works on any iterable, including strings (which iterate over characters).

Real-world uses: Word frequency analysis, inventory management (combine/subtract stock), finding duplicate elements, voting/polling systems, log analysis (count error types). Counter is one of the most underused tools in Python interviews.

Performance Matters

deque

A double-ended queue. When you need fast operations on both ends.

Problem: list.insert(0, x) is O(n) — it shifts every element. If you're building a queue (FIFO), this kills performance. What if prepending was O(1)?

⏰ Performance reality: list.insert(0, x) on a list of 1,000,000 elements shifts ALL of them. deque.appendleft(x) does it in constant time. For queue-like operations, deque can be 1000x faster.
deque operations
▼
from collections import deque

d = deque([1, 2, 3])

# Add to both ends — both O(1)
d.append(4)         # [1, 2, 3, 4]
d.appendleft(0)     # [0, 1, 2, 3, 4]

# Remove from both ends — both O(1)
d.pop()              # 4  → [0, 1, 2, 3]
d.popleft()          # 0  → [1, 2, 3]

📋 maxlen — Sliding Window / Recent Logs

▼
Bounded deque
▼
# Keep only the last 3 log entries
recent_logs = deque(maxlen=3)

recent_logs.append("Login")
recent_logs.append("View page")
recent_logs.append("Add to cart")
recent_logs.append("Checkout")  # "Login" is auto-evicted!

print(list(recent_logs))
# ['View page', 'Add to cart', 'Checkout']

When the deque is full and you append, the oldest item is automatically removed. Perfect for "last N items" patterns.

BFS (Breadth-First Search) uses a queue. You need FIFO: first in, first out. Which pair of operations?

FIFO = append() + popleft(). Items enter from the right and leave from the left. This is the standard BFS pattern. Using a list for this would be O(n) per popleft equivalent (list.pop(0)). Deque makes it O(1).

Use cases: Queue (append + popleft), Stack (append + pop), Sliding window (maxlen), BFS traversal, Recent history (undo/redo), Rate limiting (track last N requests with timestamps).

Readable Tuples

namedtuple

Give your tuples names. Stop guessing what index 0 means.

Problem: point = (3, 7) — is point[0] the x or the y? With plain tuples, you're reading code like it's a puzzle.

Plain tuple

Confusing
▼
point = (3, 7)
print(point[0])  # What is 0? x? y? z?
print(point[1])  # Hope you remember...

namedtuple

Self-documenting
▼
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(3, 7)
print(p.x)  # 3 — crystal clear
print(p.y)  # 7

📝 Typed NamedTuple (modern syntax)

▼
typing.NamedTuple
▼
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float
    label: str = "origin"  # Default value

p = Point(3.0, 7.0)
print(p.label)  # "origin"

🔧 _replace, _asdict, unpacking

▼
Useful methods
▼
Point = namedtuple("Point", ["x", "y"])
p = Point(3, 7)

# _replace — returns NEW tuple (immutable!)
p2 = p._replace(x=10)
print(p2)  # Point(x=10, y=7)

# _asdict — convert to dict
print(p._asdict())  # {'x': 3, 'y': 7}

# Unpacking — works like regular tuple
x, y = p
print(x, y)  # 3 7

namedtuple vs dataclass — which is immutable by default?

namedtuple is always immutable — it's a tuple subclass. p.x = 5 raises AttributeError. Dataclasses are mutable by default; you need @dataclass(frozen=True) to make them immutable. Use namedtuple for simple, immutable records. Use dataclass for complex, mutable objects.

Use cases: API responses (parse JSON into named fields), database rows (row.name vs row[0]), function return values (return multiple named values), config objects (immutable settings). namedtuple uses less memory than a dict and is hashable (can be a dict key or set element).

Special-Purpose

OrderedDict, ChainMap & frozenset

Niche tools that solve specific problems elegantly.

📚 OrderedDict — Order-Sensitive Equality

▼

Since Python 3.7, regular dict preserves insertion order. So why does OrderedDict still exist?

Order matters for equality
▼
from collections import OrderedDict

# Regular dict: order doesn't affect equality
d1 = {"a": 1, "b": 2}
d2 = {"b": 2, "a": 1}
print(d1 == d2)  # True — same keys & values

# OrderedDict: order IS part of equality
od1 = OrderedDict({"a": 1, "b": 2})
od2 = OrderedDict({"b": 2, "a": 1})
print(od1 == od2)  # False — different order!

# move_to_end — useful for LRU cache
od1.move_to_end("a")  # Move to end (most recent)
od1.move_to_end("b", last=False)  # Move to front

🔗 ChainMap — Layered Dict Lookups

▼
Config layering
▼
from collections import ChainMap

defaults = {"theme": "light", "lang": "en", "debug": False}
env_config = {"debug": True}
user_config = {"theme": "dark"}

# Lookup priority: user > env > defaults
config = ChainMap(user_config, env_config, defaults)

print(config["theme"])  # "dark"  (from user_config)
print(config["debug"])  # True   (from env_config)
print(config["lang"])   # "en"   (from defaults)

# Writes go to the FIRST dict only
config["lang"] = "fr"
print(user_config)  # {'theme': 'dark', 'lang': 'fr'}

ChainMap doesn't merge dicts — it searches them in order. Changes go to the first dict. Think of it like scope resolution: local > enclosing > global > built-in.

❄️ frozenset — Immutable Set

▼
Hashable sets
▼
# Regular set — mutable, NOT hashable
s = {1, 2, 3}
# d = {s: "value"}  # TypeError: unhashable type: 'set'

# frozenset — immutable, IS hashable
fs = frozenset([1, 2, 3])
d = {fs: "value"}  # Works! Can be a dict key

# Set of sets (using frozenset)
groups = {
    frozenset(["alice", "bob"]),
    frozenset(["charlie", "dave"]),
}

# frozenset supports all read operations
print(fs & frozenset([2, 3, 4]))  # frozenset({2, 3})

Can you use a regular set as a dictionary key?

Dict keys must be hashable. Mutable types (list, set, dict) are unhashable — their hash could change if contents change. frozenset is immutable, so it has a stable hash and can be a dict key or set element. Same logic: tuple is hashable, list is not.
Don't Subclass dict!

Custom Collections

When you need to customize built-in behavior, use UserDict, UserList, and UserString.

Problem: You want a dict where all keys are automatically uppercased. You subclass dict and override __setitem__. But update() bypasses your override. Your "upper dict" silently stores lowercase keys.

Broken: subclassing dict

BrokenUpperDict
▼
class BrokenUpperDict(dict):
    def __setitem__(self, key, val):
        super().__setitem__(key.upper(), val)

d = BrokenUpperDict()
d["hello"] = 1     # Works: "HELLO"
d.update({"world": 2})  # BUG: "world" (lowercase!)
print(d)
# {'HELLO': 1, 'world': 2}  ← BROKEN!

Correct: UserDict

UpperDict
▼
from collections import UserDict

class UpperDict(UserDict):
    def __setitem__(self, key, val):
        super().__setitem__(key.upper(), val)

d = UpperDict()
d["hello"] = 1
d.update({"world": 2})
print(d)
# {'HELLO': 1, 'WORLD': 2}  ← CORRECT!

📜 UserList example: PositiveList

▼
Only positive numbers
▼
from collections import UserList

class PositiveList(UserList):
    def append(self, item):
        if item <= 0:
            raise ValueError(f"Only positive numbers: got {item}")
        super().append(item)

    def __setitem__(self, index, item):
        if item <= 0:
            raise ValueError(f"Only positive numbers: got {item}")
        super().__setitem__(index, item)

nums = PositiveList([1, 2, 3])
nums.append(4)   # OK
# nums.append(-1)  # ValueError!

📝 UserString example: CaselessString

▼
Case-insensitive comparison
▼
from collections import UserString

class CaselessString(UserString):
    def __eq__(self, other):
        return self.data.lower() == str(other).lower()

    def __contains__(self, item):
        return str(item).lower() in self.data.lower()

s = CaselessString("Hello World")
print(s == "HELLO WORLD")  # True
print("hello" in s)        # True

Why does subclassing dict directly break when you override __setitem__?

CPython's dict is implemented in C for speed. Methods like update() and __init__() directly manipulate the internal hash table without calling your Python __setitem__ override. UserDict is implemented in pure Python, so all operations go through __setitem__ properly.

📦 queue.Queue — Thread-Safe by Design

▼
Producer-Consumer
▼
import queue
import threading

q = queue.Queue(maxsize=10)

def producer():
    for i in range(5):
        q.put(i)         # Blocks if full
        print(f"Produced {i}")

def consumer():
    while True:
        item = q.get()   # Blocks if empty
        print(f"Consumed {item}")
        q.task_done()

t1 = threading.Thread(target=producer)
t2 = threading.Thread(target=consumer, daemon=True)
t1.start(); t2.start()
t1.join()
⚠️ Don't rely on the GIL. PEP 703 (accepted) introduces a no-GIL build of CPython. In future Python versions, even list.append() may not be thread-safe. Use queue.Queue, threading.Lock, or concurrent.futures for thread-safe code.

Is list.append() thread-safe in CPython?

Currently safe, but don't depend on it. list.append() is a single bytecode op, so the GIL makes it atomic in CPython. But this is an implementation detail, not a language guarantee. PEP 703 (no-GIL Python) will break this assumption. Use proper synchronization for production code.

Wrap Up

Key Takeaways

📑
defaultdict & Counter
defaultdict eliminates key-existence checks with factory functions (list, int, set). Counter counts elements in one line and supports arithmetic (+, -, &, |).
⚡
deque
O(1) operations on both ends. Use for queues (FIFO), stacks (LIFO), sliding windows (maxlen), and BFS. Don't use for random access.
🏷️
namedtuple
Immutable, lightweight, self-documenting records. Use typing.NamedTuple for type hints. Supports _replace, _asdict, and unpacking.
🔧
User* Classes
Never subclass dict/list/str directly. Use UserDict, UserList, UserString for reliable method overrides. C implementations bypass your Python overrides.
