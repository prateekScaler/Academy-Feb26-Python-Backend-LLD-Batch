SOLID Principles

LLD-13 • Design Principles

Five principles that separate code that survives from code that rots. Every design pattern you will ever learn is built on these.

Motivation

Why SOLID?

You have written code that works. But six months later, adding one feature breaks three others. Why?

📚 Recall from LLD-01: The Four Qualities of Good Code

We talked about four qualities every codebase should have:
1. Readability — can a new dev understand it in a day?
2. Extensibility — can you add features without rewriting?
3. Maintainability — can you fix bugs without breaking other things?
4. Testability — can you test pieces in isolation?

SOLID is how we achieve these qualities. Each principle directly fixes one or more of them — SRP enables testability, OCP enables extensibility, DIP enables both, and so on.

Kaarthik built a Restaurant class that handles menu management, order processing, billing, notifications, and reporting — all in one 500-line file. Now Ajit needs to add SMS notifications. He touches the Restaurant class and accidentally breaks billing. Why did this happen?

The God Class Anti-Pattern
▼
class Restaurant:
    # 500+ lines that does EVERYTHING

    def add_menu_item(self, name, price): ...
    def remove_menu_item(self, item_id): ...
    def update_price(self, item_id, price): ...

    def create_order(self, customer, items): ...
    def cancel_order(self, order_id): ...
    def update_order_status(self, order_id, status): ...

    def calculate_bill(self, order_id): ...
    def apply_discount(self, order_id, code): ...
    def process_payment(self, order_id, method): ...

    def send_email_notification(self, customer, msg): ...
    def send_sms_notification(self, phone, msg): ...

    def generate_daily_report(self): ...
    def generate_monthly_report(self): ...
The Problem: This class has at least 5 reasons to change (menu logic, order logic, billing logic, notification logic, reporting logic). Any change risks breaking unrelated functionality. This is called a God Class and it is the #1 sign of code rot.

SOLID gives you 5 rules to prevent this rot. Each letter stands for one principle:

S
Single Responsibility
One class, one reason to change
O
Open/Closed
Open for extension, closed for modification
L
Liskov Substitution
Subtypes must be substitutable for base types
I
Interface Segregation
No client forced to depend on unused methods
D
Dependency Inversion
Depend on abstractions, not concretions
Principle 1

S — Single Responsibility Principle

“A class should have only one reason to change.” — Robert C. Martin

If you need to change the billing logic, should you be touching the notification code? If yes, your class is doing too much.

The Violation

❌ Before: One class does everything

order_processor.py
▼
class OrderProcessor:
    def validate_order(self, order):
        # validation logic
        ...

    def save_to_database(self, order):
        # DB persistence logic
        ...

    def send_confirmation_email(self, order):
        # email sending logic
        ...

    def generate_invoice(self, order):
        # PDF generation logic
        ...

    def update_inventory(self, order):
        # stock management logic
        ...

5 reasons to change = 5 responsibilities = SRP violation

✔ After: Each class has one job

separated_classes.py
▼
class OrderValidator:
    def validate(self, order): ...

class OrderRepository:
    def save(self, order): ...

class EmailNotifier:
    def send_confirmation(self, order): ...

class InvoiceGenerator:
    def generate(self, order): ...

class InventoryService:
    def update_stock(self, order): ...

Each class has exactly one reason to change. Easy to test, easy to maintain.

Spot the violations:

🔬 Quick Test: Ask “How many reasons would this class have to change?”
  • Discount logic changes? → Class changes!
  • Database changes? → Class changes!
  • Email provider changes? → Class changes!
If the answer is > 1, it violates SRP.

🔬 Myth vs Reality — SRP (True or False?)

True or False: “Every class should have only one method.”

Reality: SRP says one reason to change, not one method. A UserRepository with find_by_id(), find_by_email(), save(), delete() is fine — all serve the same responsibility (user persistence).

True or False: “SRP means tiny classes everywhere.”

Reality: Over-splitting is just as bad. If two things always change together, they belong together. SRP is about cohesion, not class size.

True or False: “A class with 10 methods automatically violates SRP.”

Reality: Method count is irrelevant. A Calculator with 50 math methods has one responsibility — arithmetic. Count reasons to change, not methods.

True or False: “SRP is exactly the same as separation of concerns.”

Reality: Related but not identical. Separation of concerns is about modules / layers; SRP is the same idea applied at the class level.
Principle 2

O — Open/Closed Principle

“Software entities should be open for extension but closed for modification.”

Every time Sneha adds a new discount type, she edits the DiscountCalculator class. Student discount, premium discount, employee discount, festival discount... The class now has 20 elif branches. What happens when she introduces a bug in the “premium” branch while adding “festival”?

The Violation

❌ Before: Modify existing code for every new type

discount_calculator.py
▼
class DiscountCalculator:
    def calculate(self, order, discount_type):
        if discount_type == "student":
            return order.total * 0.15
        elif discount_type == "premium":
            return order.total * 0.20
        elif discount_type == "employee":
            return order.total * 0.30
        elif discount_type == "festival":
            return order.total * 0.25
        # Every new discount = modify this class
        # Risk breaking existing discounts!
        else:
            return 0

✔ After: Extend without modifying

discount_strategy.py
▼
from abc import ABC, abstractmethod

class Discount(ABC):
    @abstractmethod
    def calculate(self, order):
        pass

class StudentDiscount(Discount):
    def calculate(self, order):
        return order.total * 0.15

class PremiumDiscount(Discount):
    def calculate(self, order):
        return order.total * 0.20

# Adding a new discount = new class, ZERO changes to existing code
class FestivalDiscount(Discount):
    def calculate(self, order):
        return order.total * 0.25

Restaurant Example: Adding a New Cuisine

menu/pricing.py

from abc import ABC, abstractmethod

class PricingRule(ABC):
    @abstractmethod
    def apply(self, base_price: float) -> float:
        pass

class IndianCuisinePricing(PricingRule):
    def apply(self, base_price):
        return base_price  # standard pricing

class ItalianCuisinePricing(PricingRule):
    def apply(self, base_price):
        return base_price * 1.2  # 20% premium for imported ingredients

# Gobi wants to add Japanese cuisine pricing?
# Just add a new class. Existing pricing rules are UNTOUCHED.
class JapaneseCuisinePricing(PricingRule):
    def apply(self, base_price):
        return base_price * 1.35  # premium for fresh fish imports

Quiz: Which design follows the Open/Closed Principle?

Correct! OCP says we extend behavior by adding NEW classes, not by modifying existing ones. Creating a new class that implements an interface = extension without modification.
Key insight: If adding a feature requires modifying existing working code, OCP is violated. The fix is almost always: define an abstraction (interface/base class) and let new behavior come from new subclasses.

🚩 Signs of Violation

Red Flags — if you see these, OCP is being violated:
  • Growing if/elif chains on a string/type parameter (“credit_card”, “paypal”, “crypto”...)
  • isinstance() type checks that branch on subclass: if isinstance(shape, Circle)
  • Switch-on-type serialization or dispatch: if obj.type == "json"
  • Every new feature requires editing an existing class (not adding one)
  • You find yourself repeatedly opening the same file to add a new branch

Red Flag in Code: isinstance Dispatch

❌ Before: isinstance dispatch

✔ After: polymorphic .area()

shapes_area_fixed.py
▼
from abc import ABC, abstractmethod
import math

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, radius): self.radius = radius
    def area(self): return math.pi * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h


def total_area(shapes):
    return sum(s.area() for s in shapes)

# Add Triangle? Just a new class with .area()
# total_area() never changes.
class Triangle(Shape):
    def __init__(self, b, h): self.b, self.h = b, h
    def area(self): return 0.5 * self.b * self.h

💡 How to Apply OCP — Worked Example: Report Exporter

Suppose we have a function that exports a report in multiple formats. Today it supports PDF and HTML. Marketing wants CSV next week, and Sales wants Excel after that. Let's walk the 5 steps:

Step 1: Find the variable behavior (the thing that keeps changing)
Step 2: Define an abstraction (ABC) for it
Step 3: Each existing branch becomes a subclass
Step 4: The caller accepts the abstraction — never the concrete type
Step 5: Adding a new behavior = new class, zero edits to existing files

❌ Before: starting point

class ReportExporter:
    def export(self, data, fmt):
        if fmt == "pdf":
            return self._to_pdf(data)
        elif fmt == "html":
            return self._to_html(data)
        # CSV? Edit. Excel? Edit. JSON? Edit.
        raise ValueError("unknown format")

Step 1 diagnosis: the format is the variable behavior. The class is forced open every time a new format arrives.

✔ After: 5 steps applied

from abc import ABC, abstractmethod

# Step 2: abstraction for the variable behavior
class ReportFormat(ABC):
    @abstractmethod
    def render(self, data) -> bytes: ...

# Step 3: each existing branch becomes a subclass
class PdfFormat(ReportFormat):
    def render(self, data): return make_pdf(data)

class HtmlFormat(ReportFormat):
    def render(self, data): return make_html(data)

# Step 4: caller depends on the abstraction
class ReportExporter:
    def export(self, data, fmt: ReportFormat):
        return fmt.render(data)

# Step 5: new format = new class, zero edits
class CsvFormat(ReportFormat):
    def render(self, data): return make_csv(data)

class ExcelFormat(ReportFormat):
    def render(self, data): return make_xlsx(data)

🔬 Myth vs Reality — OCP (True or False?)

True or False: “You should NEVER modify existing code.”

Reality: Bug fixes, refactoring, and requirement changes are fine. OCP is about adding new features — adding a new payment method should not require editing PaymentProcessor. Your code is not frozen forever.

True or False: “Every if/else is an OCP violation.”

Reality: Simple, stable conditionals are fine. OCP matters when the if/elif chain keeps growing with each new feature.

True or False: “OCP means you must use inheritance everywhere.”

Reality: OCP is about abstraction, not inheritance specifically. Composition, callbacks, plugins, and configuration all achieve OCP. The point is: extend without modifying. See the four examples below.

Four ways to honor OCP without inheritance

🧰 1. Composition — inject a behavior object

▼

Hold a list of validators. Adding a new validator = appending a new object — no class hierarchy needed.

# Validator is just a plain class - no ABC required
class MinLengthValidator:
    def __init__(self, n): self.n = n
    def check(self, s): return len(s) >= self.n

class NoSpacesValidator:
    def check(self, s): return " " not in s

class PasswordChecker:
    def __init__(self, validators):
        self.validators = validators       # composition!

    def is_valid(self, pw):
        return all(v.check(pw) for v in self.validators)

# Adding a new rule = new validator object, no PasswordChecker edits
checker = PasswordChecker([
    MinLengthValidator(8),
    NoSpacesValidator(),
])

⚡ 2. Callbacks / first-class functions

▼

No class at all — just pass a function. Sorting key= is OCP-in-the-standard-library.

# sorted() is closed for modification, open via the key callback.
people = [User("A", 30), User("B", 22)]
sorted(people, key=lambda u: u.age)        # by age
sorted(people, key=lambda u: u.name.lower())  # by name
# A new sort criterion = a new lambda. sorted() never changes.


# Event bus: subscribers register callbacks
class EventBus:
    def __init__(self): self.handlers = []
    def on(self, fn): self.handlers.append(fn)
    def emit(self, ev):
        for h in self.handlers: h(ev)

bus = EventBus()
bus.on(lambda e: print("log:", e))
bus.on(lambda e: send_metric(e))
# Adding a new reaction = bus.on(...) - no EventBus edits

🔌 3. Plugins / registry pattern

▼

A registry collects handlers by name. New plugins register themselves — the dispatcher never learns about them.

EXPORTERS = {}

def register_exporter(name):
    def wrap(fn):
        EXPORTERS[name] = fn
        return fn
    return wrap


@register_exporter("pdf")
def _pdf(data): return make_pdf(data)

@register_exporter("csv")
def _csv(data): return make_csv(data)


def export(name, data):
    return EXPORTERS[name](data)   # closed for modification

# Adding "json" exporter = just write a new file with @register_exporter

⚙️ 4. Configuration-driven dispatch

▼

A dictionary maps inputs to behaviors. The behavior set is changed by editing the table, not the dispatcher.

# Tax rules per country - data, not code branches
TAX_RULES = {
    "IN": lambda p: p * 0.18,
    "US": lambda p: p * 0.07,
    "GB": lambda p: p * 0.20,
}

def tax_for(country, price):
    return TAX_RULES[country](price)   # dispatcher unchanged

# Adding Germany? Add one line to the dict. No tax_for() edit.
TAX_RULES["DE"] = lambda p: p * 0.19

True or False: “Make every class extensible, just in case.”

Reality: Premature abstraction is its own anti-pattern. Apply OCP where change is happening — usually after the second or third edit to the same file.
Before LSP

Concept Check: Polymorphism & Substitution

4 quick questions to set up LSP. These warm up the muscle — if you get the last one right, you have already grasped LSP.

Question 1: What does this print?

class Animal:
    def sound(self):
        return "Some sound"

class Dog(Animal):
    def sound(self):
        return "Bark"

pet: Animal = Dog()
print(pet.sound())
Correct! The reference type is Animal but the actual object is Dog. At runtime, Python resolves .sound() on the actual object type — this is dynamic / runtime polymorphism.

Question 2: What does this print?

class Parent:
    def display(self):
        return "Parent"

class Child(Parent):
    pass

obj = Child()
print(obj.display())
Correct! Child doesn't override display(). Python's MRO walks the chain: Child → Parent → object, finds it on Parent, calls it. This is method inheritance.

Question 3: What happens?

class Vehicle:
    def start(self):
        return "Vehicle starting"

class Car(Vehicle):
    def honk(self):
        return "Beep beep!"

v: Vehicle = Car()
print(v.honk())
Correct! Python is dynamically typed — v: Vehicle is just a hint, not enforced at runtime. The actual object is a Car, which has honk(), so it runs. Mypy would flag this, but Python itself does not.

Question 4 — the punchline: What happens?

class Calculator:
    def divide(self, a, b):
        if b == 0:
            raise ValueError("Cannot divide by zero")
        return a / b

class StrictCalculator(Calculator):
    def divide(self, a, b):
        if b == 0:
            raise ZeroDivisionError("Division by zero")
        return a / b

def compute(calc: Calculator):
    try:
        result = calc.divide(10, 0)
    except ValueError:
        print("Handled")

compute(StrictCalculator())
Correct! Parent contract: throws ValueError. Child changed it to ZeroDivisionError. The client caught only ValueError — so the substitution silently broke the caller. This is exactly what LSP prevents. We can substitute syntactically, but the child must honor the parent's contract (return types, exceptions, pre/post-conditions, invariants).

The journey to LSP, in 4 steps:
Q1 → Method calls resolve at runtime on the actual object.
Q2 → If a subclass doesn't override, MRO finds the parent's version.
Q3 → Python allows substitution dynamically — type hints are not enforced.
Q4 → But just because we can substitute doesn't mean we should. If the child breaks the parent's contract, callers crash. LSP is the rule that says: do this right.

Principle 3

L — Liskov Substitution Principle

“Subtypes must be substitutable for their base types without altering program correctness.”

If FinalSaleOrder extends Order, can every function that works with Order also work with FinalSaleOrder without breaking? If not, your inheritance is lying.

Restaurant Example: Discountable vs Final-Sale Orders

In our restaurant, regular orders can have a discount applied. The team decides: “Festival-special orders are final — no discounts allowed.” A natural-but-wrong instinct is to make FinalSaleOrder extend Order and reject discounts.

Read the code below carefully. What is the problem here? The coupon code worked perfectly yesterday for every kind of order. Today, festival orders go live in production. What breaks — and why?

orders/models.py — spot the problem
▼
class Order:
    def __init__(self, items):
        self.items = items
        self.discount = 0

    def set_discount(self, percent):
        self.discount = percent

    def calculate_total(self):
        subtotal = sum(i.price for i in self.items)
        return subtotal * (1 - self.discount)


class FinalSaleOrder(Order):
    """Festival specials — no discounts allowed"""
    def set_discount(self, percent):
        raise Exception("Final sale — no discounts!")


# Coupon system: works on any Order
def apply_promo(order: Order):
    order.set_discount(0.10)   # 10% off
    return order.calculate_total()


regular = Order([Item(100)])
apply_promo(regular)        # works -> 90

festival = FinalSaleOrder([Item(100)])
apply_promo(festival)       # ??? what happens here
The diagnosis: FinalSaleOrder claims to be an Order (it inherits from it), so apply_promo happily accepts it. But the moment apply_promo calls set_discount, the child throws an exception the parent never threw. Result: the entire promo flow crashes for festival orders — a caller written against Order cannot trust a FinalSaleOrder. The substitution is broken. This is the LSP violation.

The Fix: Restructure the Hierarchy

Now compare the broken design side-by-side with the corrected one. The fix isn't to patch the exception — it's to admit that “final-sale” is a sibling of “discountable”, not a subtype of it.

❌ LSP Violation

class Order:
    def set_discount(self, percent):
        self.discount = percent
    def calculate_total(self): ...


class FinalSaleOrder(Order):
    def set_discount(self, percent):
        raise Exception("No discounts!")


def apply_promo(order: Order):
    order.set_discount(0.10)
    return order.calculate_total()

apply_promo(FinalSaleOrder(...))
# CRASH at runtime!

✔ Proper Design

class Order(ABC):
    @abstractmethod
    def calculate_total(self): pass

class DiscountableOrder(Order):
    def set_discount(self, percent):
        self.discount = percent
    def calculate_total(self): ...

class FinalSaleOrder(Order):
    def calculate_total(self): ...


# Promo targets only the right contract
def apply_promo(order: DiscountableOrder):
    order.set_discount(0.10)
    return order.calculate_total()

# FinalSaleOrder is never passed to apply_promo
# at the type level - the bug becomes impossible.

The 4 Contracts a Subclass Must Honor

1. Preconditions
Cannot be strengthened
2. Postconditions
Cannot be weakened
3. Exceptions
Cannot throw new ones
4. Invariants
Must be preserved

🔢 1. Preconditions cannot be strengthened

▼

A precondition is what the method requires from the caller. The child cannot demand more than the parent did — otherwise calls that worked on the parent suddenly fail on the child.

class User:
    def set_email(self, email):
        # Parent accepts ANY non-empty string
        self.email = email

class AdminUser(User):
    def set_email(self, email):
        # Child demands MORE: must end with @company.com
        # This is a tightened precondition - LSP violation!
        if not email.endswith("@company.com"):
            raise ValueError("company email required")
        self.email = email

def register(u: User, email):
    u.set_email(email)        # works for User

register(AdminUser(), "alice@gmail.com")  # CRASH

🔢 2. Postconditions cannot be weakened

▼

A postcondition is what the method guarantees to the caller. The child cannot promise less.

class UserRepo:
    def find_all(self):
        # Parent guarantees: returns a list sorted by name
        return sorted(self._users, key=lambda u: u.name)

class FastUserRepo(UserRepo):
    def find_all(self):
        # Child guarantees LESS: returns unsorted
        # Postcondition weakened - LSP violation!
        return self._users

# Caller relied on parent's sorted guarantee:
def first_user(repo: UserRepo):
    return repo.find_all()[0]   # expects alphabetical first

first_user(FastUserRepo())   # returns RANDOM user - silent bug

🔢 3. No new exceptions (the LSP smoking gun)

▼

The child cannot throw exception types the parent never promised. This is exactly the Q4 pre-LSP quiz pattern.

class PaymentGateway:
    def charge(self, amount):
        # Parent's contract: throws PaymentError on failure
        if amount < 0:
            raise PaymentError("invalid amount")
        ...

class CryptoGateway(PaymentGateway):
    def charge(self, amount):
        # Child throws a DIFFERENT exception type - LSP violation
        if amount < 0:
            raise CryptoNetworkError("bad amount")
        ...

def process(gw: PaymentGateway, amt):
    try:
        gw.charge(amt)
    except PaymentError:
        log("refunding...")

process(CryptoGateway(), -5)   # CryptoNetworkError escapes

🔢 4. Invariants must be preserved

▼

An invariant is a property of the object that is always true. The child cannot break it.

class BankAccount:
    """Invariant: balance is never negative."""
    def __init__(self, balance=0):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientFundsError()
        self.balance -= amount


class OverdraftAccount(BankAccount):
    def withdraw(self, amount):
        # Allows negative balance - INVARIANT BROKEN
        self.balance -= amount       # can go below 0

# Any code that assumed balance >= 0 now has a silent corruption.
def render_ui(acc: BankAccount):
    assert acc.balance >= 0     # used to be safe; now fails

Classic LSP violation sign: A collection that claims to be a List but throws NotImplementedError on .add(). Or a “ReadOnlyUser” that extends “User” but raises errors on .save().

Quiz: Ajit creates a FreeUser class that extends User. The FreeUser.download() method raises PermissionError instead of downloading. Is this an LSP violation?

Correct! If you need to check isinstance(user, FreeUser) before calling .download(), then FreeUser is NOT a proper substitute for User. LSP is violated. The fix: restructure the hierarchy so FreeUser does not promise behavior it cannot deliver.

🚩 Signs of Violation

  • Override raises NotImplementedError or a custom exception the parent never threw
  • Empty / no-op override: subclass quietly does nothing where the parent did something
  • Tightened precondition: subclass rejects inputs the parent accepted
  • Weakened postcondition: subclass returns a less specific / less guaranteed result
  • Callers need isinstance(x, SubClass) before calling a method

🔬 Myth vs Reality — LSP (True or False?)

True or False: “Subclasses must be identical to the parent.”

Reality: Subclasses can add new behavior and override methods. LSP only requires they don't break the parent's contract. A PremiumOrder can have extra methods — it just cannot break the ones from Order.

True or False: “If isinstance() passes, LSP is satisfied.”

Reality: LSP is about behavioral substitutability, not type identity. FinalSaleOrder IS-A Order by type, but it behaves differently when set_discount() is called.

True or False: “LSP is the same as polymorphism.”

Reality: Polymorphism is the mechanism (different objects respond to the same call). LSP is the rule that says they must respond in a way that doesn't surprise the caller.

True or False: “If Square IS-A Rectangle in real life, the code can inherit too.”

Reality: Real-world IS-A is not the same as behavioral IS-A. Always ask: “Can my subclass replace the parent everywhere without breaking callers?” If no, use composition or a sibling hierarchy. See the two code fixes below.

When inheritance is wrong, what do we use instead?

🏠 Option A: Sibling hierarchy

▼

Don't put Square under Rectangle. Put them next to each other — both are kinds of Shape. Neither claims to be a substitute for the other.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

# SIBLINGS, not parent/child
class Rectangle(Shape):
    def __init__(self, w, h):
        self.w, self.h = w, h
    def area(self): return self.w * self.h

class Square(Shape):
    def __init__(self, side):
        self.side = side
    def area(self): return self.side ** 2

# Both work where Shape is expected.
# Neither pretends to substitute for the other.
def total_area(shapes: list[Shape]):
    return sum(s.area() for s in shapes)

🧰 Option B: Composition (“has-a” instead of “is-a”)

▼

If a Square really does need Rectangle's storage logic, give it a Rectangle as a field, not a parent. Square then exposes only the operations that make sense for a square.

class Rectangle:
    def __init__(self, w, h):
        self.w, self.h = w, h
    def area(self): return self.w * self.h

class Square:
    def __init__(self, side):
        # Square HAS-A Rectangle internally
        self._rect = Rectangle(side, side)

    def area(self):
        return self._rect.area()

    def resize(self, side):
        # Only ONE setter - matches a square's behavior
        self._rect = Rectangle(side, side)

# No inheritance lie. Square reuses Rectangle without
# promising to be substitutable for one.
Principle 4

I — Interface Segregation Principle

“No client should be forced to depend on methods it does not use.”

Should a KitchenDisplay class be forced to implement send_email() just because it implements the INotification interface? That makes no sense. The kitchen display only needs show_order().

The Fat Interface Problem

Read the code below. Spot the problem. A waiter at the restaurant is being told to cook(), manage inventory, and generate reports — even though no real waiter ever does those things. What is the smell here, and what does it cost us?

fat_interface.py — spot the problem
▼
from abc import ABC, abstractmethod

class IWorker(ABC):
    @abstractmethod
    def cook(self): pass

    @abstractmethod
    def serve(self): pass

    @abstractmethod
    def clean(self): pass

    @abstractmethod
    def manage_inventory(self): pass

    @abstractmethod
    def generate_report(self): pass


# A Waiter is forced to implement cook()??
class Waiter(IWorker):
    def cook(self):
        raise NotImplementedError       # dead method
    def serve(self): ...
    def clean(self): ...
    def manage_inventory(self):
        raise NotImplementedError       # dead method
    def generate_report(self):
        raise NotImplementedError       # dead method
The diagnosis: IWorker bundles cooking, serving, cleaning, inventory, and reporting into one interface. Every concrete class is forced to implement methods it has no business implementing — the NotImplementedError blocks are the smell. Worse, any caller that takes an IWorker can't trust the methods it calls. This is an ISP violation: clients depend on methods they do not use.

The Fix: Split the Interface

Each role gets its own small interface. A class composes the ones it actually needs.

❌ One bloated interface

    @abstractmethod

    @abstractmethod

        raise NotImplementedError
    def serve(self): ...
    def clean(self): ...
    def manage_inventory(self):
        raise NotImplementedError
    def generate_report(self):
        raise NotImplementedError

✔ Segregated interfaces

Quiz: Vipul sees a class with 3 methods that raise NotImplementedError. Which SOLID principle is most likely violated?

Correct! When a class is forced to implement methods it cannot fulfill (raising NotImplementedError), the interface is too fat. Split it into smaller, focused interfaces so each class only implements what it actually uses.
Prefer many small interfaces over one big one. In Python, this often means using multiple abstract base classes with multiple inheritance, or using Protocols (structural subtyping) from the typing module.

🚩 Signs of Violation

  • Empty / stub implementations: methods that just pass or raise NotImplementedError
  • One ABC with too many methods — not all clients use all of them
  • Clients only use a subset of the interface but are forced to depend on the whole thing
  • Interface names like IService, IManager — usually fat-by-default

💡 How to Apply ISP — Worked Example: Order Service

Imagine an e-commerce backend where one fat OrderService interface has grown to 6 methods. Three different clients depend on it: the customer-facing portal, the warehouse system, and the accounting team. Let's walk the steps.

Step 1: List every client and the methods that client actually uses
Step 2: Group methods by client role (creator, shipper, accountant)
Step 3: Each group becomes its own small ABC / Protocol
Step 4: A concrete class can implement multiple small interfaces — clients only see the one they need

❌ Before: one fat interface

class IOrderService(ABC):

🔬 Myth vs Reality — ISP (True or False?)

True or False: “Every interface should have exactly one method.”

Reality: ISP says no client should depend on methods it doesn't use. An interface with read(), readline(), readlines() is fine if every client uses all three.

True or False: “Python doesn't have interfaces, so ISP doesn't apply.”

Reality: Python has abc.ABC and typing.Protocol. ISP applies to any base class or mixin that forces subclasses to implement unnecessary methods.

True or False: “ISP just means split everything into tiny interfaces.”

Reality: ISP is client-driven. The split is determined by which methods real callers use together — not by your aesthetic preference.

True or False: “ISP is the same as SRP.”

Reality: SRP is about classes having one reason to change. ISP is about interfaces being slim enough that clients don't drag along unused methods. They are siblings, not synonyms.
Clarification

LSP vs ISP — They Are Not the Same

Both can be triggered by the same code smell (NotImplementedError in a subclass). But they fix different things. Learn to tell them apart.

  LSP (Liskov) ISP (Interface Segregation)
What it cares about Behavior of subclasses Size of the interface
The question it asks Can I use the child anywhere the parent is expected, without breaking callers? Is this client being forced to depend on methods it never calls?
Typical smell Child overrides a method and changes its contract (raises new exception, weakens output, etc.) Class implements an interface but several methods are pass / NotImplementedError
Typical fix Restructure the inheritance hierarchy so subclasses only claim contracts they can honor Split the fat interface into smaller ones — each class implements only what it needs
Direction of pain The caller gets surprised by subclass behavior The implementer is forced to write methods it doesn't need

The Penguin Example — Both at Once

penguin_problem.py
▼
class Bird(ABC):
    @abstractmethod
    def fly(self): pass

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("Penguins can't fly!")

🤡 ISP perspective

The Bird interface is too fat. It forces every bird to implement fly(). Fix: Split into IFlyable, ISwimmable, IWalkable — Penguin only implements the ones it can actually do.

🔎 LSP perspective

Penguin claims to be a Bird but breaks fly()'s contract by throwing an exception the parent never threw. Any function def takeoff(b: Bird): b.fly() will crash when given a Penguin. Fix: Restructure so Penguin isn't a Bird-that-flies.

📝 The fix in code

penguin_fixed.py
▼
from abc import ABC, abstractmethod

# Step 1 (ISP): split the fat Bird interface into capabilities
class IFlyable(ABC):
    @abstractmethod
    def fly(self): pass

class ISwimmable(ABC):
    @abstractmethod
    def swim(self): pass

class IWalkable(ABC):
    @abstractmethod
    def walk(self): pass


# Step 2 (LSP): each bird only claims what it can deliver
class Sparrow(IFlyable, IWalkable):
    def fly(self):  return "flapping"
    def walk(self): return "hopping"

class Penguin(ISwimmable, IWalkable):
    # NOT IFlyable - no fly() at all
    def swim(self): return "swimming"
    def walk(self): return "waddling"

class Duck(IFlyable, ISwimmable, IWalkable):
    def fly(self):  return "flying"
    def swim(self): return "paddling"
    def walk(self): return "walking"


# Callers now target the capability they need:
def takeoff(b: IFlyable):
    print(b.fly())

# Type checker (and your brain) catches this at the call site:
takeoff(Duck())       # OK
takeoff(Penguin())    # type error - Penguin is not IFlyable

🎧 Another example: the multi-function printer

Same smell appears in real systems. A Printer interface that bundles printing, scanning, and faxing forces a basic inkjet to throw NotImplementedError on the methods it doesn't support.

❌ The smell

class IMultiFunction(ABC):
    @abstractmethod
    def print(self, doc): pass
    @abstractmethod
    def scan(self): pass
    @abstractmethod
    def fax(self, num): pass

class BasicInkjet(IMultiFunction):
    def print(self, doc): ...
    def scan(self):
        raise NotImplementedError   # LSP + ISP smell
    def fax(self, num):
        raise NotImplementedError

✔ The fix

class IPrinter(ABC):
    @abstractmethod
    def print(self, doc): pass

class IScanner(ABC):
    @abstractmethod
    def scan(self): pass

class IFax(ABC):
    @abstractmethod
    def fax(self, num): pass


class BasicInkjet(IPrinter):
    def print(self, doc): ...

class OfficeMFP(IPrinter, IScanner, IFax):
    def print(self, doc): ...
    def scan(self): ...
    def fax(self, num): ...
🎯 Final verdict: When you see NotImplementedError in an override, both LSP and ISP are usually being violated at once. The fix is always the same shape: split capabilities into smaller interfaces, and let each class claim only the ones it actually delivers.
  • ISP says: “Stop forcing Penguin to depend on fly().”
  • LSP says: “Stop letting Penguin pretend to honor fly().”
  • Same smell — different diagnostic angle. Real codebases usually need both fixes together.
Principle 5

D — Dependency Inversion Principle

“High-level modules should not depend on low-level modules. Both should depend on abstractions.”

If OrderService directly creates MySQLDatabase() inside its constructor, what happens when you switch to PostgreSQL? You have to rewrite OrderService. But OrderService should not care WHICH database it uses.

The Tight Coupling Problem

❌ High-level depends on low-level

tightly_coupled.py
▼
class MySQLDatabase:
    def save(self, data):
        # MySQL-specific save logic
        ...

class OrderService:
    def __init__(self):
        # Directly creates the dependency!
        self.db = MySQLDatabase()  # TIGHT COUPLING

    def place_order(self, order):
        # ... business logic ...
        self.db.save(order)

# Problems:
# 1. Cannot switch to PostgreSQL without editing OrderService
# 2. Cannot test without a real MySQL connection
# 3. OrderService "knows" it is using MySQL

✔ Both depend on abstraction

dependency_injection.py
▼
from abc import ABC, abstractmethod

class Database(ABC):
    @abstractmethod
    def save(self, data): pass

class MySQLDatabase(Database):
    def save(self, data): ...

class PostgreSQLDatabase(Database):
    def save(self, data): ...

class OrderService:
    def __init__(self, db: Database):
        # Dependency is INJECTED from outside
        self.db = db

    def place_order(self, order):
        self.db.save(order)

# Usage: inject whatever you want
service = OrderService(PostgreSQLDatabase())
# For testing:
test_service = OrderService(MockDatabase())

🚩 Signs of Violation

  • Concrete instantiation inside __init__: self.db = MySQLDatabase(), self.smtp = smtplib.SMTP(...)
  • Importing concrete classes from a low-level module in your business logic file
  • Hard-coded configuration: host names, ports, API keys baked into a class
  • Test setup needs a real database / real API — you can't mock
  • Switching one library forces edits across unrelated business classes

💡 How to Apply DIP — Worked Example: Signup Flow

Imagine a SignupService that saves a user to Postgres, sends a welcome email via SendGrid, and logs to a file. Today it works. Tomorrow we need to test it (without hitting Postgres / SendGrid) and migrate to a different email provider. Let's walk the 4 steps.

Step 1: List every concrete dependency the class touches (DB, email, payment, cache, clock, ...)
Step 2: Create an ABC / Protocol for each one — named after the role, not the technology (Database, not MySQLClient)
Step 3: Inject via constructor: def __init__(self, db: Database, notifier: Notifier)
Step 4: Wire concrete implementations at the composition root (main.py / app factory) — never inside business logic

❌ Before: concrete dependencies hard-coded

import psycopg2
import sendgrid

class SignupService:
    def __init__(self):
        # Step 1: concrete deps the class touches
        self.db = psycopg2.connect("...")
        self.email = sendgrid.Client("API_KEY")
        self.logfile = open("signup.log", "a")

    def signup(self, user):
        self.db.execute("INSERT ...", user)
        self.email.send(user.email, "Welcome")
        self.logfile.write(f"signed up {user.id}")

# Can't test without real Postgres + SendGrid.
# Migrating away from SendGrid = editing SignupService.

✔ After: 4 steps applied

from abc import ABC, abstractmethod

# Step 2: role-named abstractions
class UserRepository(ABC):
    @abstractmethod
    def save(self, user): pass

class EmailSender(ABC):
    @abstractmethod
    def send(self, to, msg): pass

class Logger(ABC):
    @abstractmethod
    def info(self, msg): pass


# Step 3: inject through the constructor
class SignupService:
    def __init__(self,
                 repo: UserRepository,
                 mail: EmailSender,
                 log:  Logger):
        self.repo, self.mail, self.log = repo, mail, log

    def signup(self, user):
        self.repo.save(user)
        self.mail.send(user.email, "Welcome")
        self.log.info(f"signed up {user.id}")


# Step 4: wire concretes at the composition root
# main.py
def build_app():
    return SignupService(
        repo=PostgresUserRepo("..."),
        mail=SendGridSender("KEY"),
        log =FileLogger("signup.log"),
    )

# tests/test_signup.py
def test_signup():
    svc = SignupService(
        repo=FakeRepo(),
        mail=InMemoryMailer(),
        log =NullLogger(),
    )
    svc.signup(User(1, "x@y.com"))
    assert svc.mail.sent_count() == 1

🔬 Myth vs Reality — DIP (True or False?)

True or False: “DIP means you need a Dependency Injection framework.”

Reality: In Python, constructor injection is enough: def __init__(self, db: Database). You don't need Spring or a DI container. Just pass dependencies in instead of creating them inside.

True or False: “Every class needs an abstract interface.”

Reality: Only create abstractions at boundaries — database, external APIs, email, payment. Internal helpers that are unlikely to change don't need an interface.

True or False: “DIP and Dependency Injection are the same thing.”

Reality: DI is one technique for achieving DIP. The principle says “depend on abstractions”; injection is the most common way to honor that, but factories, service locators, and config-based wiring also count.

True or False: “DIP is just OCP renamed.”

Reality: They overlap but differ in focus. OCP is about extending behavior without modifying. DIP is about which direction your dependencies point — high-level policy must not import low-level details.

Takeaways

Key Takeaways

What to remember from today.

⚒
SRP prevents God Classes
If you use the word "AND" to describe a class, it needs splitting. One class, one reason to change, one owner.
🔒
OCP prevents fragile code
Use polymorphism (abstract base classes + subclasses) so new features are new classes, not edits to existing ones.
🔄
LSP prevents lying hierarchies
If a subclass cannot honor the contract of its parent, the inheritance relationship is wrong. Restructure, do not patch.
✂
ISP prevents bloated interfaces
Many small interfaces (Python ABCs or Protocols) beat one fat interface. Clients should only see what they need.
🔌
DIP enables testability
Inject dependencies via constructors. High-level policy should never import low-level details. Both point to abstractions.

Interview tip: When asked “How would you design X?”, mention which SOLID principles guide your choices. For example: “I would separate the payment processing from the notification logic (SRP), use a PaymentGateway interface so we can add new providers without modifying existing code (OCP/DIP), and ensure each gateway implementation can be used interchangeably (LSP).”
