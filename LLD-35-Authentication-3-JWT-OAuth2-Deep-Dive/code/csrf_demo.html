3. What evil.com contains

<!-- the user never sees this; it submits itself on page load -->
<form action="https://yourbank.com/transfer" method="POST" id="f">
  <input name="to"     value="attacker">
  <input name="amount" value="5000">
</form>
<script>document.getElementById('f').submit()</script>

Notice: evil.com has no idea what your session cookie is. It doesn’t need to — it just points a request at the bank, and the browser attaches your cookie for it. That’s the whole trick.

🔑 The takeaways

  • None → the transfer succeeds. The browser attached your bank cookie to evil.com’s forged POST, and the bank couldn’t tell it apart from a real one.
  • SameSite=Lax → the browser withholds the cookie on this cross-site POST, so the request arrives with no session → rejected.
  • CSRF token → the bank requires a secret token that only its own pages have; evil.com can’t know it → rejected. (The classic pre-SameSite defence, still used.)
  • Bearer header → the token lives in an Authorization header your JS adds by hand; the browser never auto-attaches it, so evil.com’s form has nothing → rejected. That’s why header-based APIs are “CSRF-immune”.
