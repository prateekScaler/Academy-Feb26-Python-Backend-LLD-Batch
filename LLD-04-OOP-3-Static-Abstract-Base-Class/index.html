Warm-Up

Quick Recap — OOP-2

Code-driven questions. Read the snippet, then answer.

What does print(b.name) output?

class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

class Food(MenuItem):
    def __init__(self, name, price, cal):
        self.cal = cal

b = Food("Biryani", 300, 450)
print(b.name)   # ???
Food's __init__ replaces MenuItem's. Without super().__init__(name, price), the parent never sets name and price.

Food doesn't define describe(). Does b.describe() work (assuming super was called properly)?

class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price
    def describe(self):
        return f"{self.name} - Rs.{self.price}"

class Food(MenuItem):
    def __init__(self, name, price, cal):
        super().__init__(name, price)
        self.cal = cal
    # No describe() here

b = Food("Biryani", 300, 450)
b.describe()   # ???
Regular inherited methods work automatically. __init__ is special because defining it in the child overrides the parent's. Other methods are inherited unless explicitly overridden.

What does D().greet() return?

class A:
    def greet(self): return "A"

class B(A):
    def greet(self): return "B"

class C(A):
    def greet(self): return "C"

class D(B, C):
    pass
class D(B, C) → B is listed first, so B's greet() wins.

What happens when you run this?

class Calc:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c

calc = Calc()
print(calc.add(1, 2))    # ???
Why no overloading? Python is dynamically typed — it can't distinguish methods by parameter types at definition time like Java. In Java, add(int, int) and add(int, int, int) are different signatures. In Python, the name is all that matters — second def add overwrites the first.

What does f.show() output?

class MenuItem:
    def __init__(self, name):
        self.name = name
        self.__secret = "recipe"

class Food(MenuItem):
    def __init__(self, name):
        super().__init__(name)

    def show_secret(self):
        return self.__secret

f = Food("Biryani")
f.show_secret()  # ???
Use self._protected for attributes children need. __private is for the defining class only.
New Concept

Static Methods — No self Needed

Sometimes a function is related to a class but doesn't need any object data.

Step 1: You have utility functions floating around as globals:

step1_globals.py — homeless functions
▼
# These are about menu items... but live outside the class
def is_valid_price(price):
    return isinstance(price, (int, float)) and price > 0

def format_currency(amount):
    return f"Rs.{amount:.2f}"

class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

Step 2: You encapsulate them inside the class (from OOP-1 — related things should live together). But since methods need self, you add it:

step2_inside_class.py — moved inside, but...
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def is_valid_price(self, price):   # self is here...
        return isinstance(price, (int, float)) and price > 0

# To validate, you MUST create an object first:
item = MenuItem("temp", 0)           # Create a useless object...
print(item.is_valid_price(300))      # ...just to call validation

Look at is_valid_price(self, price). Does it actually USE self anywhere in its body?

Step 3: If a method doesn't use self, make it @staticmethod. Two changes: add the decorator, remove self from params.
The fix — @staticmethod — click to reveal
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    @staticmethod                          # No self parameter!
    def is_valid_price(price):
        return isinstance(price, (int, float)) and price > 0

# Now call it WITHOUT creating an object:
print(MenuItem.is_valid_price(300))   # True — no object needed!
print(MenuItem.is_valid_price(-50))   # False

Two things changed:
1. Added @staticmethod decorator
2. Removed self from the parameter list

Now you don't need to create an object just to validate a price. The function lives inside the class for organization but doesn't need instance data.

Should apply_discount be @staticmethod?

class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    @staticmethod
    def apply_discount(percent):
        return self.price * (1 - percent/100)
Rule: if you use self.anything, it's NOT static. Static methods have no access to self. Only make a method static if it uses ONLY its own parameters.

Will this work?

class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price

    @staticmethod
    def describe_item():
        return f"{self.name} - Rs.{self.price}"

MenuItem("Biryani", 300).describe_item()
Static = "I don't need any object data." If you find yourself needing self, remove @staticmethod and add self as the first parameter.

When to Use Static Methods

✅
Validation helpers
MenuItem.is_valid_price(300)
User.is_valid_email("a@b.com")
Password.is_strong("abc123")
✅
Formatting / conversion
MenuItem.format_currency(299.5)
Temperature.celsius_to_fahrenheit(100)
DateUtils.format_date(dt)
✅
Pure utility logic
MathHelper.gcd(12, 8)
StringUtils.slugify("Hello World")
FileUtils.get_extension("a.pdf")

Popular static methods in Python's standard library

str.maketrans("aeiou", "12345") — creates a translation table
os.path.join("/home", "user") — joins path components (technically module-level, but static in spirit)
json.dumps(data) / json.loads(text) — serialize/deserialize (module-level functions, same pattern)

Python uses module-level functions more than @staticmethod. But in YOUR classes, @staticmethod is the right way to keep utility functions organized.

New Concept

Class Methods — Alternative Constructors

Your API sends menu items as dicts. Your CSV import sends them as strings. How do you create objects from both?

the_problem.py — creation logic scattered outside
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

# Creation logic is OUTSIDE the class — scattered, not encapsulated
def create_from_dict(data):
    return MenuItem(data["name"], data["price"])

def create_from_csv(line):
    name, price = line.split(",")
    return MenuItem(name.strip(), float(price))

These functions create MenuItem objects. Should this logic live outside the class or inside?

This is what @classmethod solves. It gets cls (the class itself) as its first parameter, so it can create objects:
the_fix.py — @classmethod — click to reveal
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    @classmethod
    def from_dict(cls, data):              # cls = the class itself
        return cls(data["name"], data["price"])  # same as MenuItem(...)

    @classmethod
    def from_csv(cls, line):
        name, price = line.split(",")
        return cls(name.strip(), float(price))

# Three ways to create the same object:
m1 = MenuItem("Biryani", 300)
m2 = MenuItem.from_dict({"name": "Biryani", "price": 300})
m3 = MenuItem.from_csv("Biryani, 300")

Is @classmethod a type of @staticmethod?

No. They're siblings, not parent-child.
@staticmethod = no self, no cls. Completely independent of the class. Just organized inside it.
@classmethod = no self, but gets cls. It KNOWS which class called it. It can create objects of that class.

Think of it this way: static is a tenant (lives in the building but has no keys). Classmethod is the building manager (has the master key = cls).

📈 How are they stored in memory?

▼ 
# Memory layout (simplified):
#
# MenuItem CLASS object (in memory ONCE)
# ┌─────────────────────────────────────────┐
# │ __init__        → function(self, ...)   │  Instance method
# │ describe        → function(self, ...)   │  Instance method
# │ is_valid_price  → function(price)       │  Static — no self/cls
# │ from_dict       → function(cls, data)   │  Class — gets cls
# └─────────────────────────────────────────┘
#
# biryani INSTANCE object (one per object created)
# ┌─────────────────────────────────────────┐
# │ name = "Biryani"                        │  Instance data
# │ price = 300                             │  Instance data
# │ (methods live in CLASS, not here)       │
# └─────────────────────────────────────────┘
#
# Key: ALL methods (instance, static, class) are stored in the
# CLASS object. Instances only store their DATA (attributes).
# When you call biryani.describe(), Python finds describe() in
# the class and passes biryani as self.

Instance methods = stored in class, Python auto-passes the object as self
Static methods = stored in class, Python passes nothing extra
Class methods = stored in class, Python auto-passes the class as cls

Why cls and not MenuItem?

Compare these two versions:

version_A.py — uses cls
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"], data["price"])

class Food(MenuItem): pass

f = Food.from_dict({"name": "Biryani", "price": 300})
print(type(f))  # ???
version_B.py — hardcodes MenuItem
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price

    @classmethod
    def from_dict(cls, data):
        return MenuItem(data["name"], data["price"])  # hardcoded!

print(type(f))  # ???

In version A (cls), type(f) is Food. In version B (hardcoded MenuItem), type(f) is...?

Class-level vs Instance-level data — with example

▼
class_vs_instance_data.py
▼
class MenuItem:
    tax_rate = 0.05    # CLASS-LEVEL: shared by ALL instances

    def __init__(self, name, price):
        self.name = name   # INSTANCE-LEVEL: unique per object
        self.price = price  # INSTANCE-LEVEL: unique per object

    def final_price(self):
        return self.price * (1 + MenuItem.tax_rate)

    @classmethod
    def set_tax_rate(cls, rate):
        cls.tax_rate = rate  # Changes for ALL instances at once

biryani = MenuItem("Biryani", 300)
chai = MenuItem("Chai", 40)

print(biryani.final_price())   # 315.0 (5% tax)
print(chai.final_price())      # 42.0  (5% tax)

MenuItem.set_tax_rate(0.12)    # Government changes GST to 12%

print(biryani.final_price())   # 336.0 (12% tax) — changed!
print(chai.final_price())      # 44.8  (12% tax) — changed!

Class-level (tax_rate) = ONE copy, shared by all objects. Change it once, all objects see the change. Use for: configs, tax rates, default values.

Instance-level (self.name, self.price) = each object has its OWN copy. Changing biryani's name doesn't change chai's. Use for: object-specific data.

When to use @classmethod for class data: when the change should affect ALL existing and future instances (like a tax rate update). Don't use it for data that varies per object.

The Problem

Abstract Base Classes — Why?

Duck typing from OOP-2 has a dangerous weakness.

duck_typing_weakness.py
▼
class EmailNotification:
    def send(self, msg): print(f"EMAIL: {msg}")

class BrokenNotification:
    pass  # Forgot to implement send()

def notify(notifier, msg):
    notifier.send(msg)

notify(EmailNotification(), "Order ready")
notify(BrokenNotification(), "Order ready")

What happens when notify(BrokenNotification(), "Order ready") runs?

The object was created fine. The crash happens later, at the worst possible time.

What would be better?

ABC makes this possible. It prevents broken objects from being created at all.
The Solution

ABC + @abstractmethod

Define a contract. Children MUST implement it, or they can't be created.

abc_fix.py
▼
from abc import ABC, abstractmethod

class Notification(ABC):        # ← Inherits from ABC
    @abstractmethod               # ← Children MUST implement
    def send(self, message): pass

class EmailNotification(Notification):
    def send(self, message): print(f"EMAIL: {message}")  # ✓

class BrokenNotification(Notification):
    pass                          # ✗ Forgot send!

email = EmailNotification()         # ✓ Works
broken = BrokenNotification()       # ✗ TypeError IMMEDIATELY

Before (duck typing): BrokenNotification created successfully, crashes later at runtime.
After (ABC): BrokenNotification can't even be created. TypeError the moment you try.

Deep Dive

ABC Syntax & Edge Cases

When to use concrete inheritance vs ABC, and what happens in tricky scenarios.

Concrete Class vs ABC — When to Use Which?

Concrete Parent — children CAN override

class MenuItem:
    def describe(self):  # Working default
        return f"{self.name} - Rs.{self.price}"

class Food(MenuItem):
    pass  # Uses parent's describe() as-is

class Beverage(MenuItem):
    def describe(self):  # Overrides (optional)
        return f"{self.name} ({self.volume_ml}ml)"

ABC Parent — children MUST implement

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amt): pass  # No default

class Razorpay(PaymentGateway):
    def charge(self, amt):  # MUST implement
        print(f"Razorpay: {amt}")

class Broken(PaymentGateway):
    pass  # TypeError at creation!

Can a class be ABC if it has NO abstract methods?

Technically valid, but useless. ABC without abstract methods = a regular class with extra steps.

Can a class have @abstractmethod WITHOUT inheriting from ABC?

class NotAnABC:   # No ABC parent!
    @abstractmethod
    def do_something(self): pass

obj = NotAnABC()  # ???
Always pair @abstractmethod with class Parent(ABC). Without ABC, the decorator is just decoration.

Can you create an instance of the ABC itself?

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): pass

s = Shape()  # ???
ABCs define RULES. Only concrete children that implement all abstract methods can be instantiated.

The Full Picture

Static + Class + Abstract Together

One complete example using everything from today.

complete_menu.py
▼
from abc import ABC, abstractmethod

class MenuItem(ABC):
    def __init__(self, name, price):
        if not MenuItem.is_valid_price(price):
            raise ValueError(f"Invalid price: {price}")
        self.name = name
        self.price = price

    @abstractmethod
    def calculate_price(self): pass

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"], data["price"])

    @staticmethod
    def is_valid_price(price):
        return isinstance(price, (int, float)) and price > 0

class Food(MenuItem):
    def calculate_price(self): return self.price * 1.05

class Beverage(MenuItem):
    def calculate_price(self): return self.price + 10

# All three in action:
MenuItem.is_valid_price(300)                              # Static
biryani = Food.from_dict({"name": "Biryani", "price": 300})  # Classmethod
print(biryani.calculate_price())                          # Abstract (impl by Food)

MenuItem("Biryani", 300) directly — what happens?

ABCs are blueprints. MenuItem defines the rules. Food and Beverage follow them.
Watch Out

Common Mistakes

Making everything @staticmethod
If you use self.anything inside, it's NOT static. Static = no object data needed.
@abstractmethod without ABC
Without class Parent(ABC), the decorator does nothing. No enforcement. Silent failure.
@staticmethod for constructors
If your method creates objects, use @classmethod with cls. @staticmethod with hardcoded class breaks inheritance.
