Decorator & UML Diagrams

LLD-20 • Wrap to add behaviour — draw to communicate design

Two unrelated topics, both about composition: Decorator wraps an object to add behaviour around it without changing the object or its callers. UML diagrams are the shared language we use to talk about any composition — the patterns we've learned so far, the ones still ahead, and the systems you'll design in interviews.

Recap — Strategy & Observer

Tricky & Variation Questions

Not the easy "what is Strategy" recall — these are the questions that catch people who only memorised the textbook UML. Each one tests an edge case, a misuse, or a subtle distinction.

🎮 Strategy — the edge cases

Quiz 1 — Which design pattern is implemented in the code below?

from django.db.models import Q

def search_users(query: str, scope_filter):
    qs = User.objects.filter(name__icontains=query)
    if scope_filter is not None:
        qs = qs.filter(scope_filter)
    return qs

# Usage:
search_users("ada", scope_filter=Q(team="eng") | Q(team="design"))
search_users("ada", scope_filter=Q(role__in=["admin", "owner"]))
search_users("ada", scope_filter=None)
B — Strategy. The scope_filter parameter is the strategy. The fixed algorithm is the search itself (icontains then optional filter); the swappable piece is the Q object passed in — the caller decides how the "narrow the results" step runs.

Strategy doesn't require a class hierarchy with ABC + concrete subclasses — that's just the textbook UML. The pattern is "fixed algorithm + one open parameter that parameterises a step." A Django Q object passed into a function that runs a fixed query pipeline is exactly that. So is a SQL WHERE clause string passed into a reporting function, a regex pattern passed into a redactor, or a comparator passed into a tree's insert(). The shape of the parameter doesn't change what pattern it represents.

A is wrong because Builder constructs an object step by step; here we're invoking a search, not building a Query object. C (Adapter) needs two mismatched interfaces — there's no translation happening. D (no pattern) is wrong because the open callable parameter is the Strategy signature.

Interview soundbite: "If you can answer the question 'what one open parameter changes how the algorithm runs?', you've found the Strategy — class hierarchy or not."

Quiz 2 — Which of these is Strategy, and which is "just a config parameter"?

Both pieces of code "vary behaviour at runtime." Only one is the Strategy pattern.

Code A

def connect(host: str, port: int, timeout_seconds: int = 5):
    sock = socket.create_connection((host, port), timeout=timeout_seconds)
    return sock

Code B

def connect(host: str, port: int, backoff: Callable[[int], float]):
    for attempt in range(5):
        try:
            return socket.create_connection((host, port))
        except OSError:
            time.sleep(backoff(attempt))
    raise ConnectionError

# Usage:
connect("db.example.com", 5432, backoff=lambda n: 2 ** n)     # exponential
connect("db.example.com", 5432, backoff=lambda n: n * 0.5)    # linear
C is right. The line between "config" and "Strategy":
  • A config parameter is a value the function uses directly (a number, a string, an enum). The function still controls what it does; the value just tunes the result.
  • A Strategy parameter is a piece of executable behaviour (a callable, a class with a method) that the function calls into. The caller controls how a sub-step is performed.

Code A: timeout=5 means "wait 5 seconds." That's a knob.

Code B: backoff is the wait-formula itself. The function calls backoff(attempt) — the caller has injected the algorithm. That's Strategy.

Heuristic: if the parameter type is Callable[...] / a class instance / a function reference — it's Strategy. If it's int / str / bool / Enum — it's config.

Quiz 3 — Constructor injection. When does this wiring fit best?

class Checkout:
    def __init__(self, discount: DiscountStrategy):
        self._discount = discount

    def total(self, order, user):
        return order.total - self._discount.calculate(order, user)

# usage
checkout = Checkout(discount=LoyaltyDiscount())     # picked once at creation
B is right. Constructor injection is the cleanest wiring when the strategy is decided once, at object creation, and doesn't change.

When this fits:

  • Configured at app startup from a config file or env var (discount = LoyaltyDiscount() if tenant.has_loyalty else NoDiscount()).
  • Dependency-injected by a framework (FastAPI's Depends(), Spring's @Autowired).
  • Used in tests — swap a real strategy for a fake in setUp().

When to AVOID: when the strategy genuinely needs to change after construction. Then use a setter (next quiz) or per-call (the one after).

Quiz 4 — Setter-based wiring. When is this the right fit?

class Game:
    def __init__(self):
        self._difficulty = EasyAI()

    def set_difficulty(self, ai: DifficultyStrategy):
        self._difficulty = ai

    def next_move(self):
        return self._difficulty.pick_move(self.board)

# usage
game = Game()
game.set_difficulty(EasyAI())
# ... user clicks "Hard" in the settings menu ...
game.set_difficulty(HardAI())
B is right. Setter wiring earns its keep only when the strategy genuinely needs to swap during the object's life. Most natural fit: stateful UI objects.

Good fits:

  • Game with a difficulty selector in the menu.
  • Editor with a "switch theme" command.
  • Music player with a shuffle-strategy picker.

Avoid when:

  • Context is shared across threads or async tasks — the race condition from Q4 bites.
  • The strategy is fixed for the object's life anyway — constructor injection is simpler.

Quiz 5 — Per-call wiring. When is this the cleanest fit?

def sort_search_results(items, key):    # key is the strategy
    return sorted(items, key=key)

# usage — caller picks PER REQUEST based on URL param
sort_search_results(items, key=lambda p: p.price)
sort_search_results(items, key=lambda p: -p.rating)
B is right. Per-call wiring is the cleanest fit when the strategy is determined by request data, not by long-lived configuration.

Where it shines:

  • HTTP handlers — URL params or request headers decide the strategy for that one call.
  • Stdlib functions — sorted(key=), min(key=), max(key=), filter(predicate, ...).
  • Concurrency-safe code — no shared mutable state on the Context, so nothing to synchronise.

Trade-off: every caller has to supply the strategy — risks repetition. Pair with a default if the strategy is usually the same:

def total(order, user, discount: DiscountStrategy = NoDiscount()):
    ...   # callers can override, default is sensible

Quick decision table

WiringPick when…
Constructorstrategy decided once at startup; fixed for the object's life
Setterstrategy changes mid-life (user clicks something); single-threaded
Per-callstrategy decided per request; want concurrency safety for free

📣 Observer — the edge cases

Quiz 6 — A long-lived price ticker. A short-lived chart popup. Where does memory grow forever?

A trading app has one app-global PriceTicker that lives forever. Users open chart popups that subscribe to the ticker. They close the popup — UI disappears. They reopen another — new subscription. After 1000 open/close cycles, the app is using 4 GB of RAM. Where's the leak?

class PriceTicker:
    def __init__(self):
        self._listeners = []
    def subscribe(self, listener):
        self._listeners.append(listener)
    def tick(self, price):
        for l in self._listeners: l(price)

ticker = PriceTicker()     # app-global, lives forever

class ChartWidget:
    def __init__(self, ticker):
        self._prices = []
        ticker.subscribe(self._on_tick)
    def _on_tick(self, price):
        self._prices.append(price)

def show_chart_popup():
    widget = ChartWidget(ticker)
    render(widget)
    # <-- popup closes; `widget` goes out of THIS function's scope
B is right. When the widget calls ticker.subscribe(self._on_tick), it's handing over a bound method — and a bound method keeps a strong reference to self. So the ticker's list now points to the widget. When the popup closes and widget goes out of scope, the local reference dies — but the ticker still holds one. The widget can't be garbage-collected.

Why the widget never dies

_listeners, all growing on each tick.

The fix — one of three options. Cleanest: use Python's weakref so the ticker holds a weak reference. GC can collect the widget the moment everyone else stops holding it.

Bad — strong ref (the leak) 
class PriceTicker:
    def __init__(self):
        self._listeners = []

    def subscribe(self, listener):
        self._listeners.append(listener)

    def tick(self, price):
        for l in self._listeners:
            l(price)
Good — weak ref to method 
import weakref

class PriceTicker:
    def __init__(self):
        self._listeners = []

    def subscribe(self, listener):
        self._listeners.append(weakref.WeakMethod(listener))

    def tick(self, price):
        for ref in list(self._listeners):
            l = ref()         # resolve weak ref
            if l is None:
                self._listeners.remove(ref)  # prune dead
            else:
                l(price)

Three valid fixes — pick by your constraints:

  • Manual unsubscribe — ticker.unsubscribe(self._on_tick) in the widget's close() / __del__. Simple, but somebody always forgets.
  • weakref.WeakMethod (shown above) — works for bound methods specifically.
  • weakref.WeakSet for plain function listeners. Django Signals uses this by default.
📖 Primer — Python's GC and what weakref actually does

1. Reference counting is Python's primary GC. Every object has a counter of how many things point to it. When the count hits zero, the object is freed immediately. No mark-sweep pause.

import sys

x = object()
sys.getrefcount(x)   # 2  (x  +  the argument to getrefcount)

y = x
sys.getrefcount(x)   # 3

del y
sys.getrefcount(x)   # 2 again — the moment count hits 0, memory is freed

2. The cyclic GC handles the one case refcounting can't: objects that point at each other. Their refcounts never reach 0 even when nothing outside the cycle references them. A background generational collector (gc.collect()) walks the heap periodically, finds these orphan cycles, and reclaims them.

class Node: pass

a, b = Node(), Node()
a.peer = b
b.peer = a              # cycle: a→b→a→b→...

del a, b                # refcounts stay at 1 each (the cycle holds them)
# memory is reclaimed only when the cyclic GC runs.

import gc
gc.collect()             # force a sweep

3. The Observer-leak case isn't a cycle — it's a one-way strong reference. The ticker holds the listener; the listener holds the widget. Reference count of widget never reaches 0 because the ticker (which lives forever) keeps pointing at it. GC can't help — the references are real, just unwanted.

4. weakref lets you point at an object without bumping its refcount. The other strong references decide when it dies. Your weak ref just gets notified.

import weakref

class Widget: pass

w = Widget()
ref = weakref.ref(w)         # weak reference — does NOT raise refcount

print(ref())                 #  — still alive

del w                          # strong ref gone → refcount 0 → freed
print(ref())                 # None — the weak ref auto-clears

5. Two flavours you'll actually use in Observer code:

  • weakref.WeakMethod(obj.method) — weak ref to a bound method. Plain weakref.ref doesn't work on bound methods (Python creates a new bound-method object every time you access obj.method, and a weak ref to that is already dead).
  • weakref.WeakSet() — like set() but every member is a weak ref. Members vanish from the set automatically when the strong refs disappear. Django Signals uses this for its receiver registry.

Mental model: a normal reference is "I want to keep this alive". A weak reference is "I want to look at this if someone else is keeping it alive". In a publish/subscribe registry, the second one is almost always what you actually mean.

Quiz 7 — Two observers care about OrderPaid. The "send email" observer must run AFTER the "warehouse reserve" observer (because the email includes the tracking number that warehouse generates). How do you handle this?

B is right. Observer's core promise is each observer is independent. The moment one observer's output feeds another, you've violated that — and any ordering scheme you bolt on (priorities, sort keys, registration order) is a workaround that hides the real coupling.

Observer vs Chain of Responsibility

Two clean shapes:

  • Chain of Responsibility / pipeline: a single handle_paid_order function calls tracking = warehouse.reserve(); email.send(tracking). Explicit in code — read more: Refactoring.Guru — Chain of Responsibility · faif/python-patterns — CoR (Python).
  • Two-stage events: warehouse subscribes to OrderPaid; when it finishes, warehouse publishes WarehouseReserved(tracking_number); email subscribes to that. The coupling is encoded in the event types, not in priorities.
Either way: observers stay independent within each event type.

Quiz 8 — A new analytics observer is added at 2pm. It needs the order events from 9am-2pm. Can plain Observer handle this?

C is right. "Late subscriber needs old events" is the textbook reason to graduate from in-process Observer to an event broker. Plain Observer holds no history — events are fire-and-forget against whoever is registered at notification time.

Observer (no history) vs Broker (durable log)

Concrete options:

  • Kafka / Redis Streams: events persist on disk; subscribers replay from any committed offset.
  • EventStore / event sourcing: the source of truth IS the event log; new subscribers replay from the beginning to rebuild state.

Interview soundbite: "Observer = ephemeral, in-process, no history. Broker = durable, cross-process, replayable. Same pattern shape, different scaling axis."

Part 1 — Decorator

Decorator — add behaviour around an object

When you want to add caching, logging, retry, auth, or timing to an object's behaviour without changing the object and without changing its callers, wrap it.

🤯 The problem — subclass explosion

  • Ajit has a working ApiClient with one method: get(url).
  • Requirements pile up — 5 cross-cutting features needed: cache, retry, log, auth, rate-limit.
  • Each feature is orthogonal — any combination, any order.
  • Inheritance can't handle this without exploding.
Bad — subclass per combination 
class CachingApiClient(ApiClient): ...
class RetryingApiClient(ApiClient): ...
class LoggingApiClient(ApiClient): ...
# Want caching + retry?
class CachingRetryingApiClient(ApiClient): ...
# Want all five?
class CachingRetryingLoggingAuthRateLimited …
# 2⁵ = 32 classes. Order locked into each.
Good — stackable wrappers 
client = Logging(Retry(Caching(BasicApiClient())))

# Want a different order? Reorder the wrapping.
# Want only 2 features? Drop the others.
# Want a NEW feature? One new class.

Three failures of the inheritance approach:

  • Combinatorial explosion — N features → up to 2N subclasses.
  • Order is locked — "cache-then-retry" and "retry-then-cache" need different classes.
  • Multiple inheritance breaks MRO — mixing them via class X(A, B) creates super() resolution bugs.

The shape of the problem: one core behaviour + several orthogonal behaviours that should compose freely. Each cross-cutting concern wants to be its own unit.

🪟 The pattern — wrap, don't subclass

One-line idea: small wrapper classes that implement a common interface AND hold an object of that same interface. Stack to compose.

Four roles, in one line each:

  • Component — the interface (e.g. ApiClient).
  • ConcreteComponent — the thing being wrapped (BasicApiClient).
  • Decorator — implements Component AND holds one (self._inner).
  • ConcreteDecorators — one class per added feature (CachingDecorator, RetryDecorator…).

The self-similar shape (implements what it holds) is what makes wrappers stackable.

Ajit's API client, rewritten:

from abc import ABC, abstractmethod

# 1. The Component interface — what every layer exposes
class ApiClient(ABC):
    @abstractmethod
    def get(self, url: str) -> dict: ...


# 2. The ConcreteComponent — does the actual HTTP work
class BasicApiClient(ApiClient):
    def get(self, url: str) -> dict:
        return requests.get(url).json()


# 3. Decorators — each wraps an ApiClient and exposes the same interface
class CachingDecorator(ApiClient):
    def __init__(self, inner: ApiClient):     # HOLDS a Component
        self._inner = inner
        self._cache: dict[str, tuple[float, dict]] = {}

    def get(self, url: str) -> dict:
        now = time.time()
        if url in self._cache:
            ts, payload = self._cache[url]
            if now - ts < 60:
                return payload                       # cache hit
        payload = self._inner.get(url)                # delegate to wrapped
        self._cache[url] = (now, payload)
        return payload


class RetryDecorator(ApiClient):
    def __init__(self, inner: ApiClient, attempts: int = 3):
        self._inner = inner
        self._attempts = attempts

    def get(self, url: str) -> dict:
        last_exc = None
        for i in range(self._attempts):
            try:
                return self._inner.get(url)
            except requests.RequestException as e:
                last_exc = e
                time.sleep(2 ** i)
        raise last_exc


class LoggingDecorator(ApiClient):
    def __init__(self, inner: ApiClient):
        self._inner = inner

    def get(self, url: str) -> dict:
        log.info("GET %s", url)
        payload = self._inner.get(url)
        log.info("GET %s → %d bytes", url, len(str(payload)))
        return payload

Now the magic — stack them in any order:

# Plain client, no features
client = BasicApiClient()

# Add caching
client = CachingDecorator(BasicApiClient())

# Add caching + retry + logging — read the wrapping order outside-in:
# LoggingDecorator wraps RetryDecorator wraps CachingDecorator wraps BasicApiClient
client = LoggingDecorator(RetryDecorator(CachingDecorator(BasicApiClient())))

# Use it — every caller still just calls .get(). They don't know about the wrapping.
client.get("https://api.example.com/users/1")

Why this works: the Decorator is a Component from the outside (same interface as what it wraps) and a holder of a Component from the inside. That self-similar shape is what allows wrappers to wrap wrappers indefinitely. UML calls this a recursive composition — we'll draw it precisely in the UML section.

🍋 Python's @-syntax — same idea, function-level

  • When the thing being wrapped is a function, Python's @ ships the pattern in syntax.
  • @deco is sugar for fn = deco(fn) — the function is replaced by its wrapped version.
  • Stacking reads inside-out: @log @cache def f ⇒ f = log(cache(f)); closest decorator runs first inside.
from functools import wraps
import time, logging

# A function decorator wraps the function and adds behaviour around it
def log_calls(func):
    @wraps(func)                                  # preserve func.__name__, __doc__
    def wrapper(*args, **kwargs):
        logging.info("calling %s", func.__name__)
        result = func(*args, **kwargs)            # delegate to wrapped
        logging.info("→ %s", result)
        return result
    return wrapper


@log_calls                                           # equivalent to: greet = log_calls(greet)
def greet(name: str) -> str:
    return f"Hello, {name}"

greet("Ada")
# INFO calling greet
# INFO → Hello, Ada
Bad — wrap by hand 
def greet(name): return f"Hi {name}"
greet = log_calls(greet)
greet = cache(greet)
greet = timed(greet)
# noisy, easy to forget one
Good — @ stack 
@timed
@cache
@log_calls
def greet(name): return f"Hi {name}"
# reads top-down, same semantics

Pattern vs @-syntax — one-line distinction:

  • GoF Decorator wraps objects (multi-method interfaces).
  • Python @ wraps functions (single callable).
  • Same trick, different granularity. functools.cache, @login_required, @app.route, FastAPI middleware — all decorator-pattern instances.

☕ The canonical worked example — a coffee shop POS

  • Two base beverages: FilterCoffee (₹60), MasalaChai (₹40).
  • Add-ons that change both price AND description: Milk (+₹15), Sugar (+₹5), Elaichi (cardamom, +₹10), Adrak (ginger, +₹8).
  • Customer can pick any combination, any number of each (double milk!).
  • Bill prints the full breakdown: "Espresso, Milk, Milk, Whip — ₹135".
Bad — subclass per combination 
class MasalaChaiWithMilk: ...
class MasalaChaiWithMilkAndElaichi: ...
class MasalaChaiWithDoubleAdrak: ...
class MasalaChaiWithAllAddOns: ...
# 2 bases × every combination = explosion
# Double-adrak needs its own class too!
Good — stack add-on wrappers 
chai = Adrak(Elaichi(Milk(MasalaChai())))
print(chai.description())
# Masala Chai, Milk, Elaichi, Adrak
print(chai.cost())     # 73
# Any combination, any multiplicity, no new classes.

The full code — tiny and self-similar:

from abc import ABC, abstractmethod

# Component — the interface every layer respects
class Beverage(ABC):
    @abstractmethod
    def cost(self) -> int: ...
    @abstractmethod
    def description(self) -> str: ...


# ConcreteComponents — the actual drinks
class FilterCoffee(Beverage):
    def cost(self): return 60
    def description(self): return "Filter Coffee"

class MasalaChai(Beverage):
    def cost(self): return 40
    def description(self): return "Masala Chai"


# Decorator base — implements Beverage AND holds a Beverage
class AddOn(Beverage):
    def __init__(self, inner: Beverage):
        self._inner = inner

# ConcreteDecorators — each adds one ingredient
class Milk(AddOn):
    def cost(self):        return self._inner.cost() + 15
    def description(self): return self._inner.description() + ", Milk"

class Sugar(AddOn):
    def cost(self):        return self._inner.cost() + 5
    def description(self): return self._inner.description() + ", Sugar"

class Elaichi(AddOn):                          # cardamom
    def cost(self):        return self._inner.cost() + 10
    def description(self): return self._inner.description() + ", Elaichi"

class Adrak(AddOn):                            # ginger
    def cost(self):        return self._inner.cost() + 8
    def description(self): return self._inner.description() + ", Adrak"


# --- usage ---
chai = Adrak(Elaichi(Milk(Milk(MasalaChai()))))
print(chai.description())    # Masala Chai, Milk, Milk, Elaichi, Adrak
print(chai.cost())           # 40 + 15 + 15 + 10 + 8 = 88

Why this example sells the pattern in a way an API client can't:

  • Both properties (price, description) are computed by walking the wrapper stack — the self-similar shape is visible.
  • Multiplicity is natural — "double adrak" is just Adrak(Adrak(...)), not a special-case subclass.
  • Order is meaningful in print — the order you wrap determines the order in the receipt.

⚠️ The trap — subclass-per-combination ("inheritance explosion")

The naive instinct: "every drink variant gets its own class." Watch what happens.

40+ classes Why this trap kills you: ✖ Classes explode combinatorially — 2 drinks × 2^n add-ons. Add a third drink and the count triples. ✖ "Double milk" / "extra sugar" can't be expressed — would need yet another subclass per repetition. ✖ A new add-on (say Saunf) means recreating every existing class with-and-without it. OCP violated.

Sniff test: if your class name reads like a specification (X-with-Y-and-Z-and-double-W), inheritance is the wrong axis — you need composition at runtime. That's exactly what Decorator gives you.

🌐 Decorator in the wild

🧰 functools.lru_cache / functools.cache — memoisation as a decorator

▼

The most-used Decorator in the Python stdlib. @cache wraps a function so repeated calls with the same arguments return a stored result. Same shape, same trick.

from functools import cache

@cache
def expensive_query(user_id: int) -> dict:
    return db.execute("SELECT ... WHERE id = %s", user_id).fetchone()

🌍 Django / FastAPI middleware — HTTP request decorators

▼

Both frameworks let you stack middleware classes that wrap every request. Each middleware sees the request, optionally modifies it, calls the next layer, sees the response, optionally modifies it. That's literally the Decorator pattern at the request level.

# Django settings.py — order matters, outermost first
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",         # outermost wrapper
    "django.middleware.gzip.GZipMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "myapp.middleware.RateLimitMiddleware",                  # innermost wrapper
]
# Effective wrapping: Security(GZip(Csrf(Auth(RateLimit(view)))))

📚 Java I/O streams — the textbook Decorator example

▼

Every GoF book uses this example. Java's I/O classes stack precisely as Decorator: BufferedInputStream wraps FileInputStream wraps the file. DataInputStream wraps the BufferedInputStream to read int/long/String. Each layer adds one orthogonal capability.

// Java: classic Decorator stacking
DataInputStream in = new DataInputStream(
    new BufferedInputStream(
        new FileInputStream("data.bin")));
// FileInputStream — reads raw bytes from disk
// BufferedInputStream — adds an in-memory buffer for fewer syscalls
// DataInputStream — adds typed reads (readInt, readUTF, ...)

✅ @login_required, @app.route, @pytest.fixture — everyday Python

▼

Every web framework decorates view functions: @login_required wraps the view to check auth before running it; @app.route("/users") wraps the view to register it with the URL router. Test frameworks decorate fixtures (@pytest.fixture) to inject setup/teardown around tests. None of these subclass the wrapped function — they all wrap.

⚠️ Pitfalls — quiz-driven

Quiz — Same decorators, different order. What's different?

order_A = CachingDecorator(RetryDecorator(BasicApiClient()))
order_B = RetryDecorator(CachingDecorator(BasicApiClient()))

Both stack a Cache + Retry around the basic client. What's the difference on a request that fails the first time and succeeds the second?

B is right. The order in which you compose decorators changes which behaviour wraps which. The classic gotchas:
  • Cache outside Retry: cache check runs first; on miss, retry does the work and the successful response is cached. (Usually what you want.)
  • Retry outside Cache: retry runs first; each retry hits the cache. If cache stores errors, retries are no-ops. If cache only stores successes, the inner cache is wasted on a single request.
  • Logging outside Auth: log entries see unauthed requests. Useful for debugging, sensitive for auditing.
  • Logging inside Auth: only authed requests are logged. Cleaner audit log, but you miss attempted-auth-failed cases.
The rule: each combination has a meaning — pick the order deliberately, document it, write a test for it.

Quiz — What does this print?

def add_timing(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@add_timing
def do_work():
    """The real work."""
    pass

print(do_work.__name__)
print(do_work.__doc__)
B is right. When you write @add_timing, Python evaluates do_work = add_timing(do_work) — do_work now is wrapper. So __name__, __doc__, __module__, the type signature — all become wrapper's. This breaks:
  • Sphinx / pdoc / Pydantic documentation generation — all your functions appear named wrapper.
  • Mock-and-spy in tests that match on func.__name__.
  • Stack traces that print the wrapper's frame instead of the meaningful function name.

The fix is one line: use @functools.wraps inside your decorator.

from functools import wraps

def add_timing(func):
    @wraps(func)                # <-- copies __name__, __doc__, signature, etc.
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper
Every Python decorator you write should have @wraps(func) on its inner wrapper. No exceptions.

Quiz — You wrap a Pizza with ExtraCheese. What does isinstance(wrapped, Pizza) return?

class Pizza:
    def cost(self): return 200

class ExtraCheese:                       # NOT inheriting from Pizza
    def __init__(self, inner): self._inner = inner
    def cost(self): return self._inner.cost() + 50

wrapped = ExtraCheese(Pizza())
isinstance(wrapped, Pizza)        # ?
B is right. Duck typing covers method calls — wrapped.cost() works. But isinstance() checks the actual class tree. If your wrapper class doesn't inherit from the Component, it isn't one by type.

Why this matters:

  • Code that branches on isinstance(x, Pizza) breaks silently when a decorated pizza arrives.
  • Pydantic / dataclass type validation rejects wrapped instances.
  • match-case with class patterns fails.

The fix: make the decorator base extend (or register as a virtual subclass of) the Component — either via ABC inheritance:

class PizzaDecorator(Pizza):                 # <-- inherit
    def __init__(self, inner): self._inner = inner

class ExtraCheese(PizzaDecorator):
    def cost(self): return self._inner.cost() + 50

isinstance(ExtraCheese(Pizza()), Pizza)   # True ✓

Quiz — Decorator stacks vs boolean flags — what can the stack do that flags cannot?

B is right. The bonus property of Decorator vs flags: quantity matters and order matters, both naturally.

However — one honest gotcha: once you've wrapped, removing a layer is hard. There's no order.unwrap("milk"). If your app needs to add/remove individual decorations at runtime (a customer says "actually, no whip"), you have two options:

  • Rebuild the stack from scratch with the new combination.
  • Use a different pattern — usually Strategy with a list of behaviours, or just a settings object.

✅ When Decorator earns its keep

Use Decorator when
  • You're adding cross-cutting concerns (caching, logging, retry, auth, timing) to existing behaviour
  • You'd otherwise be writing N×M subclasses
  • Different combinations and orders are needed in different code paths
  • The wrapped thing has a small, stable interface
Skip Decorator when
  • There's only one cross-cutting concern — just add it directly
  • You need to change the interface, not just augment it — that's Adapter
  • The component has 20 methods — you'd need to forward them all; consider __getattr__ or composition without a strict interface
  • You want to control access (lazy-load, remote-call) rather than add behaviour — that's Proxy
Part 2 — UML Diagrams

UML — the language for talking about design

Every pattern UML you've seen so far uses the same handful of arrows and box decorations. Today we name them, distinguish the lookalikes, and learn the two diagram types you'll actually use in interviews.

🤯 Why UML at all?

  • Interviews — "design X on a whiteboard" expects boxes + arrows + the right vocabulary.
  • Onboarding — new teams hand you a diagram, not the code. You'll read one before you read a single function.
  • RFCs / design docs — reviewers debate the diagram before debating the code.

📚 Brief history — the Three Amigos

  • UML emerged in the early-to-mid 1990s when three OO methodology gurus — Grady Booch (Booch Method), James Rumbaugh (OMT), and Ivar Jacobson (Objectory) — merged their notations. The trio became known as the Three Amigos.
  • Released as a standard in 1997, adopted by the Object Management Group (OMG). Current version: UML 2.5.1.
  • Impact: the first widely-adopted shared notation for OO design. Before UML, every company drew its own boxes-and-arrows. Today every IDE, framework doc, system-design book, and interview problem assumes UML conventions — even if nobody draws "pure UML" anymore.
  • Want to see them? Search for "Grady Booch Three Amigos UML" — there's a well-known photo of the three together circa 1995, often included in software-engineering history slides (the Wikipedia article above links to it).

📝 Class diagrams — the box and arrow conventions

Each class = a 3-section rectangle: name · attributes · methods. Visibility markers: + public, - private, # protected. Underline = static, italic = abstract.

Five relationship arrows — this is where most students lose precision. Each one has a tiny SVG showing the arrow shape + nuance:

1. Inheritance — is-a

Nuance: identity + interface + behaviour all inherited. Subclass must satisfy LSP — substitutable everywhere the parent is.

2. Realisation — implements an abstract contract

Nuance — Python doesn't have interface: the classic UML <<interface>> stereotype is a Java/C# thing. In Python you mark the box as <<abstract>> (or <<ABC>> to be explicit) when the parent inherits abc.ABC and uses @abstractmethod — or <<Protocol>> when it's a typing.Protocol (structural / duck-typed contract, PEP 544). Whichever you pick, the arrow stays dashed + open triangle — that's what makes it Realisation, not Inheritance.

# Option 1 — ABC: nominal, explicit subclass declaration
from abc import ABC, abstractmethod
class PaymentGateway(ABC):        # UML box → <<abstract>> / <<ABC>>
    @abstractmethod
    def charge(self, amount: int) -> str: ...

class RazorpayAdapter(PaymentGateway):  # dashed --▷ arrow in UML
    def charge(self, amount): ...


# Option 2 — Protocol: structural, no inheritance needed (duck typing)
from typing import Protocol
class PaymentGateway(Protocol):    # UML box → <<Protocol>>
    def charge(self, amount: int) -> str: ...

class RazorpayAdapter:                # NO base class — yet still "realises" it
    def charge(self, amount): ...    # matches the shape → mypy accepts

Picking one: use ABC when you want an explicit contract and runtime errors at instantiation time (you forgot a method → TypeError). Use Protocol when you want the contract to be enforced only at type-check time and want callers to be free of any import (true structural typing).

3. Composition — has-a (strong)

Nuance: demolish the House → Rooms gone. Rooms can't belong to two houses. Part's lifetime is bounded by the whole's.

4. Aggregation — has-a (weak)

Nuance: disband the Team → Players still exist; can play for another team. Whole "holds" but doesn't "own".

5. Association — "knows about"

Nuance: A talks to B. Neither owns the other; B's lifetime is managed elsewhere. Most service-to-service wiring is association.

6. Dependency — "uses transiently"

Nuance: A uses B only inside one method (parameter, local). No stored reference. Reach for this when the relationship is genuinely temporary.

Quiz — Composition or Aggregation?

A Order has a list of OrderLines.

  • When the order is deleted, the order lines are deleted.
  • An OrderLine belongs to exactly one Order.
  • You never reference an OrderLine outside its Order.
A is right. The discriminator is lifetime ownership:
  • Composition when the contained object cannot exist without the container and dies with it. Order/OrderLine, House/Room, Document/Paragraph, Folder/File-on-Windows.
  • Aggregation when the contained object exists independently and may be shared. Team/Player (players play for many teams over a career), Playlist/Song (songs exist on their own), Course/Student (students enrol/leave).

One-line discriminator: "Can the part be passed to a different whole, or used after the whole is gone?" Yes → aggregation. No → composition.

🥇 is-a vs has-a — the four relationships with code & scenarios

The table above lists five arrows. They split into two semantic families that every interviewer cares about:

  • is-a (inheritance / realisation): "A car is a vehicle." Sharing identity + interface + behaviour.
  • has-a (composition / aggregation / association): "A car has a engine." Sharing structure — one object holds another. The differences inside has-a are lifetime and exclusivity.

1. is-a — Inheritance

  • UML arrow: solid line + open triangle.
  • Read as: "Subclass is a kind of superclass."
  • Code shape: class Child(Parent).
  • Lifetime: trivially yes — one object is both at once.
  • Caution: only use when the LSP holds — a Child should be substitutable wherever Parent is expected.
Scenario — SavingsAccount is-a BankAccount 
class BankAccount:
    def deposit(self, amt): ...
    def withdraw(self, amt): ...

class SavingsAccount(BankAccount):
    def apply_interest(self, rate): ...

s = SavingsAccount()
s.deposit(100)        # inherited
s.apply_interest(0.04) # its own
isinstance(s, BankAccount) # True
When NOT to reach for it
  • If you only want to reuse some behaviour — prefer composition. Inheritance ties you to the parent's interface forever.
  • If the relationship is "uses" or "has" — not "is" — use composition / aggregation.
  • If LSP fails (a Square "is a" Rectangle but breaks setWidth()) — don't inherit.

2. has-a (strong) — Composition  ♦—

  • UML arrow: filled diamond on the whole side.
  • Read as: "Whole owns the part. Part cannot exist without the whole."
  • Code shape: the part is created and destroyed by the whole; usually constructed inside the whole's __init__.
  • Lifetime: bound. When the whole dies, the part dies.
  • Exclusivity: the part belongs to exactly one whole.
Scenario — Order has OrderItems 
class OrderItem:
    def __init__(self, sku, qty, price):
        self.sku, self.qty, self.price = sku, qty, price

class Order:
    def __init__(self, lines):
        # Order CREATES its OrderItems. They live and die with it.
        self.items = [OrderItem(*l) for l in lines]

order = Order([("sku1", 2, 100), ("sku2", 1, 50)])
del order
# the OrderItems are now unreachable — gone with the order
More examples
  • House has Rooms — demolish the house, rooms are gone.
  • Document has Paragraphs — close without saving, paragraphs vanish.
  • HTTP Request has Headers — request ends, headers are released.
  • Tree has Nodes (a Node belongs to one Tree) — not shared between trees.

3. has-a (weak) — Aggregation  ◇—

  • UML arrow: open (empty) diamond on the whole side.
  • Read as: "Whole uses a part. Part exists independently."
  • Code shape: the part is passed into the whole — constructed elsewhere. Often shared across multiple wholes.
  • Lifetime: independent. Whole dies → part lives on.
  • Exclusivity: usually shared (one player on multiple teams; one student in multiple courses).
Scenario — Team has Players 
class Player:
    def __init__(self, name): self.name = name

class Team:
    def __init__(self, players):
        # Team RECEIVES players. Doesn't construct them.
        self.players = players

virat   = Player("Virat")
team_in = Team([virat])
team_t20 = Team([virat])      # SAME player, two teams ✓

del team_in
# virat is still alive — referenced by team_t20
More examples
  • Playlist has Songs — delete the playlist, songs are still on the platform.
  • Course has Students — students enrol/unenrol; the course doesn't own them.
  • Manager manages Employees — if the manager leaves, employees stay.
  • Cache has Entries — entries can be inserted/evicted independently.

4. has-a (loose) — Association  →

  • UML arrow: plain solid line with an arrowhead (no diamond).
  • Read as: "A knows about / collaborates with B." No ownership, no lifetime claim.
  • Code shape: stored as a reference, or passed in as a method parameter.
  • Use it when: neither aggregation nor composition feels honest — the relationship is just "A talks to B."
Scenario — OrderService talks to PaymentGateway 
class OrderService:
    def __init__(self, gateway: PaymentGateway):
        self._gateway = gateway     # just collaborates

    def checkout(self, order):
        result = self._gateway.pay(order.total, "INR")
        ...

# PaymentGateway has its own life — managed by the DI container,
# shared across many services, etc. OrderService doesn't OWN it.
When to use association
  • Service-to-service wiring (most DI graphs are associations).
  • Method parameter usage — def transfer(self, src: Account, dst: Account) — the service knows both accounts but owns neither.
  • Bidirectional "knows about" — Author knows the list of Books; Book knows its Author.

🥇 Pick the right one — in three questions

Ask…Yes →No →
Q1. Is B literally a kind of A?Inheritance (is-a)Go to Q2
Q2. When A dies, does B die too?CompositionGo to Q3
Q3. Does A own B (B doesn't exist without an A somewhere)?AggregationAssociation

If you can answer the three questions in order, you can label any arrow correctly — even on a whiteboard under interview pressure.

🎯 Multiplicity — the numbers on the arrows

  • 1 — exactly one
  • 0..1 — zero or one (optional)
  • * or 0..* — zero or more
  • 1..* — one or more (non-empty collection)
  • n..m — specific range (2..4)

Read endpoint + arrow + endpoint: Order 1 ♦—— 1..* OrderLine means "one Order owns one-or-more OrderLines".

⏱️ Sequence diagrams — flow over time

A class diagram tells you what objects can talk to each other. A sequence diagram tells you which calls actually happen, in what order, when a specific scenario plays out.

The conventions:

  • Actors / participants sit across the top, each with a vertical lifeline hanging down (a dashed line representing the participant's existence over time).
  • Time runs top to bottom. A message higher up happens before a message lower down.
  • Messages are horizontal arrows from sender to receiver. Solid for synchronous calls, dashed for return values, open-triangle for async.
  • Activation bars (small narrow rectangles on the lifeline) mark when a participant is "busy" executing.

Three things this sequence diagram makes obvious that a class diagram couldn't:

  • The fan-in / fan-out shape — the outermost decorator is called once; the innermost is called twice (due to retry).
  • The red dashed return on the first attempt — an exception that didn't propagate further than RetryDecorator (it caught and retried).
  • The self-message ("sleep") on RetryDecorator — behaviour between two outgoing calls is visible because time runs vertically.

⚠️ The mistakes every junior makes

Mistake 1 — Using inheritance arrow for everything

"Class A has a B" is not inheritance. The open triangle is reserved for "A is-a B". Mixing them up makes your diagram lie about the design.

Mistake 2 — Composition vs Aggregation by feel

Most students draw composition (filled diamond) for anything that "feels owned." The discriminator is lifetime: can the part exist after the whole is gone? If yes → aggregation. If no → composition.

Mistake 3 — Missing multiplicity

"User has Order" is ambiguous: one Order? Many Orders? Without numbers on the arrow endpoints, your reviewer has to guess. Always add multiplicity for collections (1..*, 0..*).

Mistake 4 — Drawing every getter and setter

UML is for communication, not documentation. Include the methods that matter for the design discussion — the public API and the methods that participate in patterns. Skip the noise.

Mistake 5 — Class diagram when you meant sequence

If your point is "A calls B then C", you need a sequence diagram. A class diagram won't show ordering. Pick the right tool.

👤 Use-case diagrams — "what can users do?"

When to draw one: the very first sketch in any LLD interview — lists the actors and the actions they can perform. It scopes the problem before any class diagram.

💾 From class diagram to DB schema — the leap

UML class diagrams describe code. ER diagrams describe a database. Most interviews ask for both, in sequence.

Translating a class diagram to a relational schema:

  • Each class → one table. Attributes become columns; pick types from your DB (VARCHAR, INT, TIMESTAMP, …).
  • Add a primary key (usually a synthetic id) unless one of the attributes is naturally unique.
  • Relationships become foreign keys — with the side of the FK chosen by the cardinality:
CardinalityWhere the FK livesExample
1 ↔ 1FK on either side (pick the one that's optional). Or merge tables if they always coexist.User ↔ UserProfile
1 ↔ *FK on the "many" side, pointing at the "one"OrderItem.order_id → Order.id
* ↔ *A join table with two FKs (and any attributes of the relationship)StudentCourse with student_id, course_id, enrolled_at, grade

Decorator vs Adapter vs Proxy vs Facade — the structural quartet

Now that we've covered Adapter (LLD-18) and Decorator (today), let's put the full structural family side by side — including the two we haven't built yet but will recognise in the wild.

All four structural patterns share the same UML shape on paper — one class holds another and forwards calls. The pattern name says why the wrapping exists, not how it's coded.

Pattern Intent Wrapped's interface Wrapper's interface Example
Adapter Make an existing object usable where a different interface is expected Old / incompatible The Target interface (different from wrapped) RazorpayAdapter wraps RazorpayClient to expose PaymentGateway
Decorator Add behaviour around an object without changing it Some interface X Same interface X, plus extra behaviour CachingDecorator wraps ApiClient to add caching
Proxy Stand in for an object — control access, lazy-load, or remote-call it Some interface X Same interface X (transparent stand-in) ORM lazy-loading: a Proxy looks like a User object but fetches from DB on first access
Facade Hide a complex subsystem behind one simple front-door API Many objects with many interfaces A small, simpler new interface OnboardTenant.start() that orchestrates 8 services

The four-question litmus test:

  • Does the wrapper expose a different interface? → Adapter (translate) or Facade (simplify many→one).
  • Does the wrapper expose the same interface as what it wraps?
  •   ...to add behaviour around calls? → Decorator.
  •   ...to control when/whether the call happens? → Proxy.

Decorator vs Proxy — the subtle pair. Both share an interface with the wrapped object. The discriminator: Decorator's goal is to enhance (cache, log, retry, format); Proxy's goal is to gate-keep (lazy-load, check permissions, batch remote calls, refuse forbidden ones). A Proxy may add nothing functional; it just stands in. A Decorator always adds something the caller can observe.

🥇 Cross-family one-question test — updated for Decorator

"I want to vary something at runtime." — vary what?

  • Which concrete class to instantiate → Factory
  • How interfaces fit together → Adapter
  • What behaviour wraps an existing object's calls → Decorator
  • Which algorithm to use for one job → Strategy
  • Who reacts to one event → Observer

🥇 Decorator vs Strategy — the tricky cross-family pair

Both wrap behaviour. The difference:

  • Strategy replaces an algorithm: the Context picks one Strategy for a method call. There's no chaining; the Strategy is the algorithm for this call.
  • Decorator wraps an existing algorithm: each layer runs behaviour around the call to the next layer. Multiple Decorators stack.

If you can stack two of them and both run → Decorator. If picking the second discards the first → Strategy.

🎪 DECORATOR — structural · "wrap to add behaviour"

  • Use when: adding cross-cutting concerns (cache / log / retry / auth / rate-limit) to an existing object's behaviour
  • Three roles: Component (interface) · ConcreteComponent (real work) · Decorator (implements Component, holds Component)

  • Python flavours: class-based wrappers for objects · @decorator syntax for functions (FastAPI/Django middleware, functools.cache)
  • Skip when: one cross-cutting concern (just add it) · need different interface (Adapter) · need to control access not enhance (Proxy)
  • #1 bug: forgetting @functools.wraps — the decorated function loses its __name__, __doc__, signature
  • #2 bug: order matters — Cache-then-Retry and Retry-then-Cache behave differently. Document the order; test it.

  • When you need it: interviews · onboarding · RFCs / design docs
  • Two diagram types do 95%: Class diagrams (structure) · Sequence diagrams (flow over time)

  • Same interface, adds behaviour? → Decorator
  • Same interface, controls access? → Proxy

🎯 Interview cheat sheet

If asked "when would you use Decorator?": lead with the cross-cutting concerns. Cache, log, retry, auth, rate-limit applied to existing behaviour. Mention functools.cache as the everyday Python example. Bonus: distinguish from Adapter (different interface) and Proxy (controls access).

If asked "what's @functools.wraps?": "It copies the original function's metadata (__name__, __doc__, signature) onto the wrapper so the decorator is transparent to introspection." Bonus: name what breaks without it (Sphinx, stack traces, type checkers).

If asked "what's the difference between composition and aggregation?": "Lifetime ownership. With composition, the part can't exist without the whole; with aggregation, it can." Bonus example: Order/OrderLine vs Team/Player.

Pattern Cheat Sheet — quick reference

Every pattern we've covered (plus a few we've only met in passing) on one screen each. Same format throughout: bad vs good code · minimal UML · real use cases.

Adapted & expanded from kanmaytacker/design-patterns — same one-line motivations, with code + UML added so each entry is self-contained.

🏭 Creational — how is the object made?

1. Singleton

  • One liner: exactly one instance, globally accessible.
  • Steps: hide constructor · expose a static get_instance() · cache the instance.
Bad — two configs in flight 
cfg_a = Config()           # reads disk
cfg_b = Config()           # reads disk again
cfg_a.timeout = 30
print(cfg_b.timeout)      # still default — surprise!
Good — one shared instance 
class Config:
    _i = None
    def __new__(cls):
        if cls._i is None:
            cls._i = super().__new__(cls)
        return cls._i

Use: database connection pool · app-wide logger · shared cache. Skip: when "global state" makes testing painful.

2. Builder

  • One liner: step-by-step construction of complex / validated objects without telescoping constructors.
  • Steps: separate Builder class · fluent setters · .build() validates and returns the immutable Product.
Bad — telescoping constructor 
p = Pizza("large", True, False, True,
          True, False, True, False)
# Which True is mushrooms?
Good — named fluent steps 
p = (PizzaBuilder()
        .size("large")
        .cheese().mushrooms()
        .build())

Use: any class with 6+ optional fields · HTTP request builders · SQL query builders. Skip: 2-3 simple fields — just use a constructor.

3. Prototype

  • One liner: clone an existing instance instead of building from scratch when __init__ is expensive.
  • Steps: clone() method on the class · optionally a registry mapping names to prototypes.
Bad — rebuild each time 
for exp in experiments:
    cfg = BaseConfig()    # 1.2s × 50 = 60s
    cfg.flags[exp.flag] = exp.val
Good — build once, clone many 
proto = BaseConfig()       # 1.2s once
for exp in experiments:
    cfg = proto.clone()    # <1ms each
    cfg.flags[exp.flag] = exp.val

Use: game NPC spawning · document templates · test data factories. Skip: simple @dataclass — use dataclasses.replace().

4. Simple Factory

  • One liner: centralise "which concrete class to instantiate" behind one static method.
  • Steps: common interface · a single create(kind) with the if/elif hidden inside.
Bad — if/elif at every call site 
if kind == "email":   n = Email()
elif kind == "sms": n = SMS()
elif kind == "push": n = Push()
# every caller copy-pastes this
Good — one factory 
class NotificationFactory:
    @staticmethod
    def create(kind):
        return {"email": Email,
                "sms": SMS,
                "push": Push}[kind]()

Use: notification picker · payment gateway picker · deserialiser picker. Trade-off: still an OCP violation — new kind = edit factory.

5. Factory Method

  • One liner: let subclasses decide which concrete class to instantiate.
  • Steps: abstract create() on a Creator class · one Creator subclass per product type · no central if/elif.
Bad — Simple Factory grows 
# Adding "slack" = edit the factory
class NotificationFactory:
    def create(self, kind):
        if kind == "slack":   # <-- diff
            return Slack()
        ...
Good — subclass per product 
class Creator(ABC):
    @abstractmethod
    def create(self): ...

class SlackCreator(Creator):
    def create(self): return Slack()
# adding new kind = NEW subclass, no edits

Use: framework hooks (you ship Creator, user extends it) · OCP-clean factories. Skip: 2-3 fixed types — Simple Factory is enough.

6. Abstract Factory

  • One liner: create families of related products so they're guaranteed consistent.
  • Steps: one factory per family · each produces ALL related products via the family's interface.
Bad — mixed family 
btn   = make_button("mac")
hdr   = make_header("windows")   # oops!
toast = make_toast("mac")
# 3 unrelated calls, no consistency check
Good — one factory per family 
f = MacFactory()    # ONE choice
btn   = f.button()    # ✓ mac-style
hdr   = f.header()    # ✓ mac-style
toast = f.toast()     # ✓ mac-style

Use: cross-platform UI toolkits · multi-cloud SDK families · multi-DB connection sets. Skip: products aren't a family — Factory Method per product is simpler.

🧱 Structural — how are objects composed?

7. Adapter

  • One liner: translate one class's interface into another the client expects.
  • Steps: Target interface · Adapter implements Target, holds Adaptee · delegates with shape translation.
Bad — SDK leaks everywhere 
# views.py / billing.py / webhooks.py
import razorpay
o = razorpay.order.create({"amount": ...})
razorpay.payment.capture(o["id"])
# every file sees Razorpay shapes
Good — SDK in one file 
class RazorpayAdapter(PaymentGateway):
    def pay(self, amount, ccy):
        ...   # SDK calls hidden here
# everyone else calls gateway.pay()

Use: payment gateways · cloud-storage SDKs · Django auth backends. Skip: you control both sides — just fix the interface.

8. Flyweight

  • One liner: share the immutable "intrinsic" part across many objects to save memory; pass the "extrinsic" part as parameters.
  • Steps: split state into intrinsic (shared) + extrinsic (per-use) · a factory returns the cached intrinsic instance.
Bad — 1M objects 
# 1M chars, each owns its font glyph
chars = [Char(c, font, Glyph(c, font))
         for c in document]
# memory blows up
Good — share glyphs 
glyphs = {}    # intrinsic cache
def glyph(c, font):
    if (c, font) not in glyphs:
        glyphs[(c, font)] = Glyph(c, font)
    return glyphs[(c, font)]
# 1M chars, ~100 unique glyphs

Use: text editors (chars share glyphs) · game engines (instances share meshes) · Python's small-int cache · sys.intern. Skip: objects already small or count is low.

9. Decorator

  • One liner: wrap an object to add behaviour around it — same interface, stackable.
  • Steps: Component interface · Decorator implements AND holds Component · stack at runtime.
Bad — subclass explosion 
class CachingRetryingLoggingClient(...): ...
# 2^N subclasses for N features
Good — stackable wrappers 
client = Log(Retry(Cache(Basic())))
# any order, any combination

Use: middleware stacks · @functools.cache · Java I/O streams · auth/rate-limit wrappers. Skip: single cross-cutting concern — just inline it.

10. Facade

  • One liner: one simple entry point for a complex subsystem.
  • Steps: Facade class with high-level methods · orchestrates the subsystem internally · clients never touch subsystem classes directly.
Bad — caller orchestrates 
Provisioning().create(t)
Billing().setup(t)
RBAC().seed(t)
Email().welcome(t)
# every caller knows 4 subsystems
Good — one front door 
OnboardTenant().start(t)
# 4 subsystems orchestrated inside
# callers see one method

Use: tenant onboarding · e-commerce checkout (cart + payment + inventory + email) · requests.get() over httplib + url parsing + connection mgmt. Skip: the "subsystem" is one class.

🧠 Behavioural — how do objects collaborate?

11. Strategy

  • One liner: swap the algorithm at runtime via an injected object/function.
  • Steps: Strategy interface · concrete strategies · Context holds & calls the strategy · constructor / setter / per-call wiring.
Bad — if/elif chain grows 
def discount(order, kind):
    if kind == "flat": ...
    elif kind == "pct": ...
    elif kind == "loyalty": ...
    # 11 more branches
Good — one class per algorithm 
checkout = Checkout(discount=Loyalty())
checkout.total(order)
# new variant = new class, no edits

Use: sort/filter algorithms · discount/pricing rules · ML optimizers. In Python, often just a callable (no class hierarchy). Skip: 2 short branches — if/else reads cleaner.

12. Observer

  • One liner: one Subject, many Observers — state change notifies everyone subscribed.
  • Steps: Subject keeps observer list · observers register a callback · Subject loops and notifies on event.
Bad — hardcoded reactions 
class Order:
    def mark_paid(self):
        email.send(self)
        warehouse.queue(self)
        analytics.track(self)
        # Order knows everyone
Good — subscribe & react 
class Order:
    def mark_paid(self):
        for obs in self._observers:
            obs.on_paid(self)
# Order knows nobody. Add listener = subscribe.

Use: Django Signals · addEventListener · pub/sub (in-process). Skip: one fixed reaction — just call it. Need durable delivery — use Kafka/Redis Streams instead.
