the problem

“Works on my machine”

The oldest fight in software: dev says it works, ops says it 500s, and both are right.

Your Django app runs perfectly on your laptop. Deployed to the prod server: ImportError, then missing env vars, then a Pillow crash. The code is IDENTICAL. What actually broke?

You deployed the app, not its world.
  • requirements.txt pins Python packages — it says nothing about the Python version itself, OS libraries (libjpeg for Pillow!), env vars, or system config. Closer, but a fraction of the world.
  • Hardware is the rare cause; environment drift is the everyday one — and it bites again with every new teammate’s laptop (“day one: 6 hours of setup”).
  • So the requirement writes itself: ship the whole world — interpreter, OS libs, code, and a config contract — as ONE artifact. That artifact is the image.
The joke is the actual architecture: an image IS your machine — frozen, versioned, and shipped.

The idea: standardize the box

📌 Scenario: Before 1956, loading a ship took an army of dockers hand-stacking crates for days. Malcom McLean’s steel box didn’t make cargo lighter — it made cargo uniform, so every port in the world could handle any cargo the same way. Docker (2013) did the same for software: the image is the steel box; laptop, CI and cloud are the ports.
  • Image — the sealed box: app + dependencies + interpreter + OS libs, as one immutable, versioned artifact.
  • Container — one running instance of an image (box, opened and working). Many containers can run from one image.
  • Registry — the warehouse: push images, pull them anywhere (Docker Hub, ECR, GHCR).
under the hood

What a container actually is

Before the commands: kill the biggest misconception in the room.

First, the older trick: the hypervisor

Your cloud provider sells you a “4-CPU Linux server” for ₹3000/month. In reality it’s one slice of a monster physical machine running dozens of such “servers” for different customers — some running Ubuntu, one running Windows. What software makes this possible, and what does it actually do?

The hypervisor is an illusionist: it sells the same hardware many times.
  • It intercepts each guest’s hardware access and answers with fakes — which is how Ubuntu, Windows and Debian run simultaneously on one board, fully isolated: each has its own entire OS, unaware the hardware is shared. (The diagram above is the whole trick.)
  • This IS the cloud: an EC2/GCE “instance” is a VM under a hypervisor (KVM, Xen, AWS Nitro). Your “server” has neighbours on the same metal it will never see.
  • Two flavours: Type-1 runs on bare metal (prod clouds: KVM/Xen/ESXi); Type-2 runs as an app on YOUR OS — VirtualBox, and the hidden VM that Docker Desktop runs (you’ll meet it again shortly).
  • The scheduler answer is a beautiful wrong answer — “isolated heavyweight processes on a shared kernel” is a preview of exactly what CONTAINERS are. Hold that thought for the next question. (Bootloader = dual-boot: one OS at a time, no isolation between customers.)

A VM takes ~a minute to boot; a container starts in ~50 ms. Both give an isolated Linux environment. Where does the ×1000 difference come from?

It’s a process, not a machine.
  • A VM boots a full guest operating system per app — kernel init, services, the lot. That’s the minute, and the gigabytes.
  • There is no hypervisor in the container path at all — and nothing is “paused”: docker run is fork+exec plus some kernel bookkeeping.
  • The bookkeeping is two kernel features: namespaces (what the process can SEE) and cgroups (what it can USE). That’s the whole magic trick.
📌 Scenario: Run docker run -m 512m webapp and then ps aux ON THE HOST: your python process is right there in the list, plain as day. It just believes it’s PID 1 on a machine called a3f9c2 with 512 MB of RAM — because that’s all the kernel lets it see and use. The cgroup limit is your LLD-38 bulkhead, enforced by the kernel.
Isolation ≠ virtualization. VMs isolate by simulating hardware; containers isolate by lying to a process. Cheaper lie, same practical effect for most backend work — and the reason a laptop happily runs 30 containers but chokes on 4 VMs.

Plot twist: what “Docker on a Mac” really is

You just said containers are “processes on the host kernel using Linux namespaces and cgroups.” But you develop on macOS — which has neither. How is Docker running containers on your Mac at all?

One hidden VM, all your containers inside it.
  • Containers are a Linux-kernel feature, full stop. No Linux kernel → no containers — so Mac/Windows get a slim managed VM (you’ve seen it: that’s what Docker Desktop is starting when the whale bounces).
  • This resolves the apparent contradiction with the VM-vs-container lesson: on your laptop it’s VM(1) + containers(N) — one fixed VM cost, then cheap processes; NOT one VM per app.
  • Syscall translation at that scale doesn’t exist in Docker (macOS’s sandboxing is unrelated) — the VM is the whole answer, and it’s also why file-mount I/O on Mac is slower than on Linux: every file crosses the VM boundary.
  • In prod (Linux servers) the VM disappears and containers run truly native — dev/prod behavior stays identical because the KERNEL the containers see is Linux either way.
  • Two products, one name: Docker Engine (the Linux daemon — free, open source, what prod runs) vs Docker Desktop (the Mac/Windows app bundling a VM + GUI — paid license for larger companies since 2021, which is why many ban it).
  • Free alternatives that run the same VM + engine: Rancher Desktop (closest GUI swap), Colima (CLI-only Mac favourite: brew install colima), Podman (daemonless, docker-compatible CLI), WSL2 + engine on Windows. Your Dockerfiles and compose files work unchanged on all of them — OCI standards at work.
the artifact

Images, layers & registries

The image is the deliverable now — not a zip of code, but a frozen, runnable world. Its internal structure is the clever part.

Your image is 900 MB. You change ONE line of Python and docker push again — it uploads in 2 seconds. How?

Nothing is diffed — the unchanged layers were never sent.
  • Each Dockerfile instruction bakes a layer; layers are addressed by content hash. Push sends only hashes the registry hasn’t seen — your base+deps layers are already there.
  • Compression exists but is irrelevant here: 900 MB compressed still isn’t 2 seconds. The point is what’s NOT uploaded.
  • Server-side diffing would require the server to reconstruct your image first — the layer model makes dedup automatic on both sides (pulls work the same way: only missing layers download).
  • Same trick you know from git: content-addressed objects, shared history, cheap increments.
📌 Scenario: Deploy day, old world: ssh to the server, git pull, pray pip install works, restart, discover the server’s Python is older. Deploy day, image world: docker pull app:v43 && docker run — and rollback is docker run app:v42, the exact bytes that worked yesterday. Versioned environments, not just versioned code.
Pin your tags. FROM python:latest means “whatever was newest at build time” — Friday’s build works, Monday’s breaks, and the Dockerfile never changed. Pin (python:3.12-slim) for reproducibility — the same reason LLD-38 pinned library versions in requirements.txt.
the recipe

The Dockerfile — a build script for worlds

Ten lines that bake the image. Two of the ten cause 90% of real-world pain — so both get a question.

Your Dockerfile does COPY . . then RUN pip install -r requirements.txt. Every time you edit ANY Python file, the next build re-installs every package — 3 minutes. Why?

Cache reads top-down; order by change-frequency.
  • A layer is reused only if ITS instruction and every layer above it are unchanged. Your code edit invalidates COPY . . — and everything after it, pip included.
  • Flip the order: COPY requirements.txt → pip install → COPY . .. Now code edits only rebuild the last, thin layer: 2-second builds.
  • General law: order instructions from least to most frequently changing — base, then deps (monthly), then code (hourly).
  • pip has no say in this — the layer cache decides whether the RUN line executes at all.

A teammate’s COPY . . shipped the project’s .env (real API keys) into the image, which got pushed to Docker Hub. They delete the file and push a new image. Problem solved?

Layers are immutable history — like git, deleting the file doesn’t delete the past.
  • The old image (and its layers) remain pullable by tag/digest — anyone who pulled it has the keys forever. Treat them as leaked: rotate now (the LLD-38 secrets rule).
  • .dockerignore is the seatbelt: .env, venv, .git, __pycache__ never enter the build context at all.
  • Secrets don’t belong IN images — images are shared artifacts. Inject at RUN time: docker run -e API_KEY=... / compose environment: / k8s Secrets — exactly the 12-factor ladder from LLD-38.
  • Rotating the Hub token doesn’t un-ship the layers — it just closes the door the horse already left through.

The production Dockerfile, line by line

📁 Code for this section: 02-django-docker/ — this exact Dockerfile, heavily commented, on a real single-file Django app  ·  run docker build -t webapp .  ·  docker run -p 8040:8040 webapp
# the same file, as text — read the comments in code/02-django-docker/Dockerfile
FROM python:3.12-slim              # pinned base — never :latest
WORKDIR /app
COPY requirements.txt .            # deps first…
RUN pip install --no-cache-dir -r requirements.txt   # …so this layer caches
COPY . .                           # code last — it changes hourly
RUN useradd -m appuser
USER appuser                       # containers get compromised too — don't be root when it happens
EXPOSE 8040
HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost:8040/health || exit 1
CMD ["python", "webapp.py", "runserver", "0.0.0.0:8040", "--noreload"]
💬 What it does: One image = one process (CMD). The HEALTHCHECK line is LLD-38’s liveness idea shipped IN the artifact — any platform that runs this image knows how to ask “are you ok?”.

Multi-stage builds — the pro move for small images

# stage 1: the kitchen — build tools allowed, mess allowed
FROM python:3.12 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt   # compiles C extensions etc.

# stage 2: the dining room — only the finished dishes enter
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local     # ONLY the installed packages cross over
COPY . .
USER nobody
CMD ["python", "webapp.py", "runserver", "0.0.0.0:8040", "--noreload"]
💬 What it does: The build stage (with gcc, headers, caches — hundreds of MB) is thrown away; the final image contains only the runtime. Typical result: 1.1 GB → 180 MB. Smaller = faster pulls, smaller attack surface, cheaper storage. Same idea powers compiled languages (build in a Go/Node stage, ship a scratch/slim stage).
  • Size hygiene: prefer -slim bases (full Debian − docs/toolchains). alpine is smaller still but uses musl instead of glibc — some wheels don’t exist for it and pip falls back to compiling; try slim first.
  • Combine & clean in one RUN: each RUN is a layer — apt-get update && apt-get install -y X && rm -rf /var/lib/apt/lists/* in ONE line, or the cleanup lands in a separate layer and saves nothing.
day-2 basics

Running containers: data, config, ports

Three things every running container needs decided: where its data lives, where its config comes from, and who can reach it.

Your containerized Django app stores user uploads in /app/uploads/. Ops redeploys the new version Tuesday night. Wednesday: every upload is gone. What happened?

Containers are cattle; data is sacred.
  • Redeploy = old container deleted (its thin writable layer with it), new container created from the image. The image never contained the uploads — they existed only in the doomed layer.
  • COPY happens at BUILD time into the image; it can’t touch a running container’s files. And Docker never silently prunes your data.
  • Fix: docker run -v uploads-data:/app/uploads — a named volume on the host, mounted in; survives any number of redeploys. (Prod-grade answer for uploads specifically: object storage like S3.)
  • Design consequence: containers should be stateless — state lives in volumes, databases, caches. Kill any container without fear. That’s what made LLD-38’s “instances come and go” world normal.

One image, three environments (dev / staging / prod) with different DB URLs and API keys. What’s the container-world way?

Same build, different environment — LLD-38, now enforced.
  • Three images = three artifacts to build, test, and get mixed up (“did prod get the staging image?”). The whole point of the box is ONE tested artifact promoted through environments.
  • A mounted config file works (k8s does it for some things) but env vars are the 12-factor default: no file paths to manage, visible in one place, and exactly what pydantic-settings (LLD-38) reads.
  • Tier-1 demo shows it live: docker run -e GREETING="config from outside" hello-lld40 — same image, different behavior, zero rebuilds.
  • Secrets specifically: runtime injection (or a secrets manager) — never baked in; see the burned-.env question above.
  • Ports: containers live on a private network; -p 8040:8040 (host:container) is the ONE door you open. Nothing is reachable unless mapped — secure by default.
  • Lifecycle: images are built and pulled; containers are created, run, stopped, removed. The table below is 95% of your daily typing.

🛠️ When it doesn’t work — the four classic beginner walls

▼
  • “Container exits immediately.” Containers live as long as their CMD: if the process ends (or daemonizes itself!), the container is done. Check docker logs; run foreground servers (our --noreload runserver stays in front).
  • “Works in the container, can’t reach it from my browser.” Two doors, both must be open: the app must listen on 0.0.0.0 (not 127.0.0.1 — that’s loopback INSIDE the container) and the port must be mapped with -p. Our CMD says 0.0.0.0:8040 for exactly this reason.
  • “Port already allocated.” Something on the host owns it — often your OWN previous container: docker ps, stop it, or map a different host port (-p 8041:8040).
  • “My code change isn’t showing.” You edited the file but ran the OLD image — rebuild (docker build) and re-run; the image froze your code at build time. (Dev-loop fix: bind-mount the source, -v $(pwd):/app.)

many boxes

docker-compose: the whole stack in one file

Real apps are web + database + cache. Starting three containers by hand with the right network, order and volumes — every morning — is a job for a file, not a human.

Your compose file declares web with depends_on: [db]. docker compose up — and web still crashes with “connection refused” to Postgres, but only sometimes. Why?

“Started” ≠ “ready” — you met this distinction in LLD-38.
  • The container being up means the PROCESS launched — Postgres still needs seconds to init. Classic startup race; “only sometimes” is the tell.
  • The fix is a healthcheck on db + depends_on: {db: {condition: service_healthy}} — now compose waits for READINESS, not just start. (Belt-and-braces: the app also retries its DB connection — LLD-38 resilience.)
  • Networking isn’t the issue — compose puts all services on a shared private network automatically.
  • This is liveness-vs-readiness from LLD-38/39 again, in its most common everyday costume.
# code/03-compose-stack/docker-compose.yml — the whole demo stack
services:
  web:
    build: .
    ports: ["8040:8040"]
    environment:
      - REDIS_HOST=redis          # the SERVICE NAME is the hostname (DNS!)
    depends_on:
      redis:
        condition: service_healthy   # wait for READY, not just started
  redis:
    image: redis:7-alpine          # pinned, like every image
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
    volumes:
      - redis-data:/data           # the counter survives down/up
volumes:
  redis-data:
💬 What it does: Read it as the diagram above: two named services on a private network, one mapped port, one volume, readiness-gated startup. docker compose up --build is the whole morning routine now — and the file is the documentation.
📌 Scenario: New teammate, day one, old world: a 40-step setup wiki, half of it stale, all day lost. Image world: install Docker Desktop, git clone, docker compose up — coffee still warm. The compose file IS the onboarding doc, and it can’t go stale because it’s executed daily.

metrics & alerts

Observing containers — the essentials

Last class ended at logs. The metrics-and-alerting half lives HERE instead — main ideas only, question-first, answers drawn as diagrams.

Inside the container your app writes its logs to /var/log/app.log (rotated, tidy, like the old VM days). What’s wrong with this in the container world?

In containers, stdout isn’t a convention — it’s the API.
  • Last class’s rule (“JSON to stdout, the platform ships it”) becomes mechanical here: the log driver tails stdout; agents ship it; the aggregator indexes it. Files are outside the pipe.
  • A volume WOULD preserve the files — preserved and still invisible: a very durable black hole.
  • The tier-2 demo prints one JSON line per request to stdout precisely so docker logs shows it working.

Measuring speed: which number tells the truth?

Checkout’s dashboard shows AVERAGE latency: a healthy 90 ms, green all day. Support keeps getting “checkout hangs” complaints. Ops says the users are wrong — the graph is green. Who’s right?

Averages describe nobody; percentiles describe the victims.
  • Do the arithmetic once and you never trust an average again: 99 × 60 ms + 1 × 3000 ms = 89 ms average (“green!”) — while 1 user in 100 waits 3 seconds.
  • p95 = 1 in 20 requests is slower than this; p99 = 1 in 100. And sessions compound it: at ~30 requests per session, roughly 1 in 4 SESSIONS hits the p99 pain at least once.
  • So dashboards graph p50 (the typical user), p95, p99 — never the average. The diagram above shows the same service both ways.
  • Rising p99 with flat p50 has a classic smell: some resource at its limit (a pool, a lock, memory) hurting only the requests that queue — which is exactly the next question.

Which numbers go on the dashboard? RED and USE

Brand-new containerized service, empty dashboard, and you may pick only FOUR numbers to start with. Which four?

RED says users are hurting; USE says why.
  • RED — Rate, Errors, Duration — is the service as users feel it. Example of a healthy day: 120 req/s, 0.4% errors, p95 = 210 ms.
  • USE — Utilization, Saturation, Errors — is for the resources underneath (CPU, memory, DB pool, queue). Saturation = work waiting — the early-warning signal.
  • They chain. Friday sale: rate 2×, errors flat, p95 +40% (RED: mild symptom) — and the DB pool at 9/10 with 3 waiters (USE: cause). That’s tomorrow’s outage, visible today.
  • The trap answers: users don’t feel CPU — they feel errors and duration. And uptime%/image size measure nothing you can act on before lunch.
From metric to 3 AM page — the whole alerting idea in one line: errors/requests > 5%  FOR 10m  → page (+ runbook link). A user-facing ratio (survives traffic spikes; 50 errors means nothing without traffic) + a threshold + a duration (one bad second is normal — sustained breach is an incident) + a runbook. Slow-burning causes (disk 82%, growing 1%/day) become tickets, not pages — every false page trains the on-call to ignore the next one.

Your container has -m 512m. At 2 AM it dies: exit code 137, NO traceback, no ERROR log — then restarts and dies again an hour later. The error-rate alert pages you. Which dashboard number would have warned you HOURS earlier?

137 = 128 + 9: SIGKILL from the kernel — the app never got to say anything.
  • OOM-kill is instant and silent: no exception, no log line — which is exactly why LOGS can’t warn you here. Only the METRIC sees the leak climbing.
  • Alert design per the box above: the memory gauge at ~80% of the limit → a ticket (“leak, fix this week”); the error-rate page at 2 AM is what firing looks like when you ignored it.
  • Latency MAY degrade first (GC thrash) but often doesn’t — the kernel kills at the limit regardless. Never rely on it.
  • Per-container CPU/memory come free: docker stats → cAdvisor → Prometheus — USE applied to cgroups. Metrics and containers are one story.

Your Dockerfile’s HEALTHCHECK hits /health, which returns 200 if the process is up. Redis goes down; the app can’t serve a single real request — but every healthcheck passes and traffic keeps flowing. What’s the design fix?

A health endpoint that checks nothing is a rubber stamp.
  • “Process up” and “able to do work” are different claims — LLD-38’s liveness/readiness split, now as one if statement in your /health view.
  • Faster polling of a wrong answer just gives you the wrong answer more often.
  • Restarting web because REDIS is down is the classic anti-pattern: restarts can’t fix a dependency — readiness fails, liveness passes.
  • Tier-3’s webapp does exactly this: /health pings Redis, 503 while down, 200 on recovery — run it and kill Redis to watch.
📌 Scenario: One section, the whole loop: stdout → aggregator (logs) · RED + USE → the dashboard · percentiles → the truth about speed · one ratio+FOR rule → the 3 AM page · /health → the platform’s automatic response. The full detail lives in the LLD-39 notes — these are the load-bearing ideas.
the bigger picture

Beyond one machine: Kubernetes & the ecosystem

Compose manages containers on ONE machine. The moment you need many machines, self-healing and zero-downtime deploys, you’ve outgrown it — by design.

Your compose-run product is growing: you need 3 servers, automatic failover when one dies, and rolling deploys with no downtime. What’s the honest assessment of docker compose here?

Right tool, right scale — and knowing the boundary is the skill.
  • Compose-per-server + LB “works” until a server dies at 3 AM: nothing reschedules those containers, nothing drains traffic, deploys mean ssh-ing to N machines. You’d slowly reinvent a bad scheduler.
  • Day-one k8s is the opposite failure: enormous operational complexity a single-host product doesn’t need. Compose (or one k8s-lite like Fly/Render/Cloud Run) is the right start.
  • Kubernetes’ core move: you declare desired state (“3 replicas of web:v42”), a control loop makes reality match — including at 3 AM (see diagram: node dies → replacement scheduled, no page).
  • And you already know its vocabulary: Service = discovery DNS (LLD-38), probes = liveness/readiness (LLD-38/39), ConfigMap/Secret = 12-factor config (LLD-38), limits = cgroups (today).

Interview corner

Container questions are judgment questions: do you know what the box IS, and when each tool stops being enough.

“What’s the difference between a container and a VM?”

▼

🎯 What they’re really testing: The #1 filter question — they’re listening for ‘process’, not ‘lightweight VM’.

  • A VM virtualizes hardware and boots a full guest OS; a container is a normal host process isolated by namespaces (what it sees) and limited by cgroups (what it uses).
  • Hence the numbers: ms vs minutes to start, MBs vs GBs of overhead, 30 containers per laptop vs 4 VMs.
  • Trade-off flip side: containers share the host kernel — weaker isolation boundary than a VM (why multi-tenant clouds still wrap tenants in VMs, and why gVisor/Firecracker exist).
  • Close with: “a container is a process wearing blinkers with a meter running” — interviewers remember the phrase.

“Why is your Docker build slow, and how do you fix it?”

▼

🎯 What they’re really testing: Layer-cache literacy — the single most practical Dockerfile skill.

  • Diagnose: the cache is invalidated top-down at the first changed instruction — if COPY . . sits above pip install, every code edit reinstalls the world.
  • Fix: order by change-frequency — base → requirements.txt + install → code. Also: .dockerignore (don’t send venv/.git as build context), slim base images, --no-cache-dir.
  • Bonus points: multi-stage builds (build deps in one stage, copy artifacts into a clean runtime stage) for compiled deps and small final images.
  • Numbers land well: “took our builds from 3 minutes to 4 seconds by moving one COPY line.”

“How do containers change logging and monitoring?” (the LLD-39 bridge)

▼

🎯 What they’re really testing: Whether your observability knowledge survives contact with the platform.

  • Logs: stdout is the API — the log driver/agent pipeline captures it; files inside containers are invisible and mortal.
  • Metrics: cgroups give per-container CPU/memory for free (docker stats → cAdvisor → Prometheus); alert on saturation vs the LIMIT, not the host total — exit 137 means the kernel killed you and only the gauge saw it coming.
  • Health: bake a HEALTHCHECK/probes; readiness checks dependencies (fail = stop routing), liveness stays bare (fail = restart) — and restarts can’t fix a dead dependency.
  • One line to sound senior: “a container platform is an observability opinion, enforced.”

“When would you NOT use Kubernetes?”

▼

🎯 What they’re really testing: Judgment over hype — a favourite senior-round question.

  • Single host / small team / early product: compose or a managed container platform (Cloud Run, Fly, Render) delivers 90% of the value at 5% of the operational cost.
  • k8s earns its complexity at: many hosts, many services, autoscaling, multi-team platform needs.
  • The middle path most companies actually take: managed k8s (EKS/GKE) or serverless containers — someone else runs the control plane.
  • Strong answer shape: name the boundary (scheduling across machines) rather than reciting features.

Containers in the AI era

The AI stack didn’t replace the box — it became its biggest customer.

  • Agent sandboxes: when an LLM writes and runs code, that code is untrusted by definition — so it runs in a throwaway container: no network, tight cgroup caps, deleted after. Today’s namespaces/cgroups lesson IS the safety model of every code-interpreter tool.
  • Model images: inference server + CUDA + weights in one pinned image — “works on my GPU” is the same old disease with the same cure. Scale = replicas of the same image behind a Service (LLD-38’s discovery, unchanged).
  • Cost bulkheads: per-model cgroup limits cap the blast radius of a runaway inference process — the LLD-38 bulkhead + LLD-39 cost-burn alerting, applied to GPUs.
  • Reproducible experiments: a training run pinned as an image = rerunnable in a year — the science answer to environment drift.
📌 Scenario: An agent product lets the model execute user-requested Python. One prompt-injected request tries rm -rf / and a crypto-miner. Damage: one disposable container with no network and a 256 MB cap, deleted 4 seconds later. The 1979 chroot idea, 2026’s hottest safety feature.
