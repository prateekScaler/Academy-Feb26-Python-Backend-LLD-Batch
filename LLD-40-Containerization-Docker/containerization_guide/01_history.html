History & Core Concepts

How we got from bare metal to containers

The Linux Kernel Magic

Here's a secret: containers aren't actually a new technology. The core concepts have existed in Linux since 2008. Docker just made them really easy to use in 2013.

Containers are possible because of two Linux kernel features: namespaces and cgroups. Let's understand what these do.

Namespaces: Isolation (What Processes Can See)

Imagine you're in a large office building, but you're placed in a room with frosted glass walls. You can't see other rooms, you think you're alone in the building. That's what namespaces do for processes.

Namespace What It Isolates Effect
PID Process IDs Container sees its own PID 1 (but it's actually PID 4523 on host)
NET Network interfaces Container has its own IP address, ports, routing tables
MNT Mount points Container sees its own filesystem hierarchy
USER User/Group IDs Root inside container ≠ root on host (rootless containers)
UTS Hostname Container can have its own hostname

Cgroups: Resource Limits (What Processes Can Use)

Namespaces handle isolation, but what stops a container from eating all your RAM? That's where cgroups (control groups) come in. They're the resource police.

💰 The Budget Analogy

Think of cgroups like giving each container a budget. "You get 512MB of RAM and 50% of one CPU core. That's it. No negotiation." The container can't exceed these limits, preventing one misbehaving app from taking down the entire system.

What's Actually in a Container Image?

Here's something that confuses beginners: when you see FROM ubuntu:22.04, you're NOT getting a full Ubuntu OS with a kernel. Containers share the host kernel.

Key Insight: A container image contains the userland — binaries like /bin/bash, libraries like glibc, package managers like apt — everything EXCEPT the kernel. That's why the Ubuntu image is ~77MB, not 2GB.

This means you can run a CentOS container on an Ubuntu host. The CentOS image provides yum, rpm, and CentOS-specific tools, but it uses the Ubuntu host's Linux kernel. Same kernel family = works fine.

Layers: The Efficiency Trick

Docker images are built in layers. Each instruction in a Dockerfile creates a new read-only layer. This is brilliant for two reasons:

  1. Caching: If you change line 8 of your Dockerfile, only layers 8+ rebuild. Layers 1-7 are cached.
  2. Sharing: If 10 containers use python:3.11, the base image is stored once on disk, not 10 times.
Dockerfile                     Image Layers (read-only)
────────────────────           ──────────────────────────
FROM python:3.11-slim    →     [Layer 1: Python base     ] 125 MB  ← Shared across images
COPY requirements.txt .  →     [Layer 2: requirements.txt]   1 KB
RUN pip install ...      →     [Layer 3: pip packages    ]  45 MB  ← Cached if unchanged
COPY . .                 →     [Layer 4: Your code       ]  50 KB  ← Only this rebuilds
CMD ["python", "app.py"] →     [Layer 5: CMD metadata    ]   0 KB
                               ────────────────────────────
                               Total: ~170 MB

Container runs with a thin writable layer on top (for logs, temp files, etc.)
Why This Matters: Always order your Dockerfile with rarely-changing things first (base image, system packages) and frequently-changing things last (your code). This maximizes cache hits.

Union Filesystem

How do these layers stack together? Through a Union Filesystem (like OverlayFS). It presents multiple directories as a single merged view.

📚 The Transparent Sheets Analogy

Imagine stacking transparent sheets of paper. You can see through to all layers, but when you write, you only write on the top sheet. Lower sheets are untouched. That's copy-on-write — the container can "modify" files, but changes go to its private writable layer.

The same idea, as an actual worked example. Say your image has two layers, and you start a container: 
layer 1 (read-only):  /app/requirements.txt
layer 2 (read-only):  /app/manage.py, /app/settings.py
writable top (this container only):  (empty at start)

what the container SEES at /app:  requirements.txt, manage.py, settings.py
                                  — one merged folder, as if it were normal
The kernel (OverlayFS) is doing a simple trick: when the app opens a file, look top-down through the stack and serve the first copy it finds. Now watch what each kind of change actually does:

1. CREATE a new file — app saves /app/uploads/cat.jpg → written to the writable top. The image layers never change.

2. EDIT an "image" file — app modifies settings.py, which lives in read-only layer 2. It can't be edited in place — so the kernel first copies the file UP to the writable layer, then edits the copy. From now on the container sees its own edited copy (it's found first, top-down); layer 2 still holds the original, untouched. This is copy-on-write — and it's why 50 containers can share ONE image safely: each one only ever changes its own top sheet.

3. DELETE an "image" file — app deletes manage.py. The read-only layer can't lose a file — so the writable layer records a whiteout marker ("pretend this doesn't exist"). The merged view hides it; the image still has it.

See it live: docker diff <container> prints exactly the writable layer's contents — A added, C changed (copied-up), D deleted (whiteout). And docker rm throws away just that top sheet — which is why container changes vanish on restart (and why anything precious belongs in a volume).

A) Namespaces

C) OverlayFS

2. Does a container image include the Linux kernel?

A) No — containers share the host kernel
B) Yes — each container has its own kernel

A) Docker requires this order
B) To maximize layer caching — unchanged layers don't rebuild
