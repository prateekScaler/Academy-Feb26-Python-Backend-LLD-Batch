The Problem

Why Version Control?

Before we learn Git, let's understand what problem it solves.

You've Already Used Version Control

📄
Google Docs
Multiple people edit the same document. You can see history, who changed what, and restore previous versions.
📁
The "Final" Folder
report_final.docx
report_final_v2.docx
report_FINAL_FINAL.docx
report_ACTUALLY_FINAL.docx
💾
Ctrl+Z
Undo/Redo is version control — but only within a single session. Close the app and history is gone.

⚠️ Google Docs Limitations

What it does well:

  • Real-time collaboration
  • Automatic saving
  • Version history

What it can't do:

  • Branching (work on features in parallel)
  • Meaningful checkpoints with descriptions
  • Merge different people's changes intentionally
  • Work offline

Code Has Special Needs

Unlike documents, code needs:

🌿
Parallel Development
Work on a new feature while someone else fixes a bug — without stepping on each other's toes.
📍
Meaningful Checkpoints
Not just "autosave at 3:42 PM" but "Added user authentication" — checkpoints with purpose.
⏪
Time Travel
"The app worked last Tuesday. What changed?" — go back to any point in history.
🔀
Intentional Merging
Combine two different streams of work carefully, resolving conflicts manually when needed.

🎮 Trivia: How Git Was Born

In 2005, Linus Torvalds (creator of Linux) built Git in just 2 weeks because the existing version control tool (BitKeeper) revoked Linux's free license. His goals were simple:

  • Speed — Operations should be nearly instant
  • Distributed — Everyone has the full history, no central server required
  • Data integrity — Impossible to change history without detection
  • Simple design — The core is ~10 commands, everything else builds on them

"I'm an egotistical bastard, and I name all my projects after myself. First Linux, now Git." — Linus Torvalds (Git means "unpleasant person" in British slang)

Core Concepts

Git Mental Model

Understanding these 4 concepts will make everything else click.

📁
Repository (Repo)
Your project folder + hidden .git folder containing all history. The recipe book.
📸
Commit
A snapshot of your project at a specific moment. Like a save point in a video game with a note: "Defeated the dragon".
🌿
Branch
A parallel timeline. Work on features without affecting the main code. Multiple chefs working on different recipes.
📍
HEAD
"You are here" marker. Points to the current commit you're viewing/working on.

Commits Are Like a Linked List

Each commit knows its parent. You can traverse backward through history.

a1b2c3 parent: null
d4e5f6 parent: a1b2c3
g7h8i9 parent: d4e5f6
j0k1l2 parent: g7h8i9

← HEAD points here. Each commit stores a reference to its parent.

The Three Areas

📝
Working Directory
Your actual files. What you see in VS Code. Untracked changes.
📦
Staging Area
Files you've marked for the next commit. "These changes are ready."
💾
Repository
Committed history. Permanent snapshots saved in .git folder.
# Initialize a new repository
$ git init

# Check status (what's changed?)
$ git status

# Stage specific file
$ git add filename.py

# Stage all changes
$ git add .

# Commit with message
$ git commit -m "Add user login feature"

# View commit history
$ git log --oneline
🤔 Quick Check
You modified 5 files but only want to commit 2 of them. What should you do?
A git commit -m "message" — commits everything
B git add file1.py file2.py then git commit
C git add . — adds everything
D Delete the other 3 files first

💡 Staging = Selective Commits

The staging area lets you choose exactly which changes go into each commit. You can modify 10 files but commit them in logical groups: "Fix login bug" (2 files), "Add logout button" (3 files), etc.

Parallel Work

Branching

Work on features in isolation without breaking the main code.

Why Branches?

Imagine you're building an e-commerce site. The main branch (main) is live in production. You need to:

🛒
Add Shopping Cart
New feature that takes 2 weeks. Can't push half-done code to production.
🐛
Fix Payment Bug
Critical bug reported today. Needs to be fixed and deployed ASAP.
🧪
Experiment with AI
Try adding AI recommendations. Might not work out — that's okay.

Without branches: Everything in one timeline. Can't deploy bug fix without deploying half-done cart.
With branches: Each task is isolated. Fix bug on hotfix/payment, merge to production, continue cart work on feature/cart.

# See all branches
$ git branch
* main

# Create new branch
$ git branch feature/cart

# Switch to branch
$ git checkout feature/cart
Switched to branch 'feature/cart'

# Or create + switch in one command
$ git checkout -b feature/cart

# Modern alternative (Git 2.23+)
$ git switch -c feature/cart

📍 What is HEAD?

HEAD is a pointer to the current commit you're working on. Think of it as "You are here" on a map.

  • When you switch branches, HEAD moves to that branch's latest commit
  • When you commit, HEAD moves forward to the new commit
  • git checkout abc123 — moves HEAD to a specific commit (detached HEAD)
Combining Work

Merge vs Rebase

Two ways to integrate changes. Both useful, for different situations.

🔀

Merge

Creates a new commit that combines both branches. Preserves complete history.

$ git checkout main
$ git merge feature
  • ✅ Safe — never changes existing commits
  • ✅ Shows exactly when branches were combined
  • ✅ Easy to undo
  • ⚠️ Creates "merge commits" (can clutter history)
📏

Rebase

Replays your commits on top of another branch. Creates a linear history.

$ git checkout feature
$ git rebase main
  • ✅ Clean, linear history
  • ✅ No merge commits
  • ⚠️ Rewrites commit history (changes hashes)
  • ❌ Never rebase shared/public branches

🚨 Why Does Merge Create a New Commit?

A merge commit records: "At this moment, I combined these two branches."

  • It has two parents — points to both branches' last commits
  • This preserves the fact that work happened in parallel
  • If something breaks, you know exactly when integration happened
  • You can easily revert the entire merge with one command

When to Use Which?

Has anyone else seen these commits?
(pushed to shared repo)
Yes, shared with team
Use MERGE
No, only on my machine
Rebase is OK
✅ Use Merge When:
  • Combining feature branch into main
  • Working with shared branches
  • You want to preserve "when did we integrate"
  • Default choice when unsure
✅ Use Rebase When:
  • Cleaning up local commits before pushing
  • Updating feature branch with latest main
  • You want a clean, linear history
  • Commits haven't been shared yet
🤔 Scenario
You've been working on feature/login for 3 days with 5 commits. Your teammate pushed new commits to main. You want to get those updates. What should you do?
A git rebase main — replay your commits on top of updated main
B git merge main — creates merge commit in your feature branch
C Delete your branch and start over
D Wait until you're done to deal with it

💡 Rebase for Updating Your Feature Branch

Since your 5 commits haven't been pushed yet (only on your machine), rebase is perfect. It replays your work on top of the latest main, keeping history clean. If you'd already pushed, merge would be safer to avoid rewriting shared history.

Write Better History

Best Practices

Good habits that separate junior devs from senior devs.

Why Commit Messages Matter

❌ Bad
abc123 fix
def456 update
ghi789 wip
jkl012 final fix
mno345 ok now it works
✅ Good
abc123 Add user authentication with JWT
def456 Fix password validation regex
ghi789 Add rate limiting to login endpoint
jkl012 Update error messages for clarity
mno345 Add unit tests for auth module

6 months from now: "Why did we change this?" Good commit messages answer that instantly. Bad ones require archaeology.

📝 Commit Message Formula

[type]: [what changed]

# Examples:
feat: Add shopping cart functionality
fix: Resolve payment timeout on slow connections
refactor: Extract validation logic to separate module
docs: Update API documentation for v2 endpoints
test: Add integration tests for checkout flow

Other Good Habits

📦
Commit Often
Small, focused commits. Not one giant commit at end of day. Each commit should do one thing.
🏷️
Meaningful Branch Names
feature/user-auth, fix/payment-bug, refactor/api-cleanup — not my-branch
🔍
Review Before Commit
git diff to see changes. git diff --staged to see what's about to be committed.
🚫
Never Commit Secrets
API keys, passwords, .env files — add to .gitignore. Once committed, they're in history forever.

🎯 Interview Questions You Can Now Answer

👆 Click each question to reveal the answer

1. What is Git and why do we use it?
Git is a distributed version control system. It tracks changes to files, enables collaboration, allows branching for parallel work, and maintains complete history. We use it because code needs meaningful checkpoints, parallel development, and the ability to roll back changes.
2. What's the difference between git add and git commit?
git add stages changes (marks them for next commit). git commit saves staged changes permanently to history with a message. Think: add = "I want to include this", commit = "Save snapshot now".
3. When would you use merge vs rebase?
Merge: When combining shared branches, preserving history of parallel work, or when unsure. Rebase: When cleaning up local commits, updating your feature branch with latest main (before pushing), or when you want linear history. Never rebase commits that have been pushed/shared.
4. What is HEAD in Git?
HEAD is a pointer to the current commit you're on. It's like "You are here" on a map. Usually it points to the tip of a branch. When you checkout a specific commit (not a branch), you're in "detached HEAD" state.
5. Why does merge create a new commit?
A merge commit records the integration of two branches. It has two parents (both branches' last commits), preserving the history that work happened in parallel. This makes it easy to see when integration happened and revert if needed.
