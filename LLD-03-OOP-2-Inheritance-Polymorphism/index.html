OOP-2: Inheritance & Polymorphism

LLD-03 • Pillars 3 & 4 of Object-Oriented Programming

Last class: Abstraction & Encapsulation.
Today: Reuse code without copy-pasting, and write code that works with types it hasn't met yet.

Warm-Up

Quick Recap — OOP-1

Let's make sure the foundations are solid.

What does self refer to inside a method?

self = this specific object. c1.increment() → self is c1. c2.increment() → self is c2.

What's the difference between self.name, self._name, and self.__name?

self.name = open to all.
self._name = "please don't touch unless you're a subclass."
self.__name = Python renames it to _ClassName__name to prevent accidents.

Today you'll see why protected (_name) matters in inheritance.

Why should a constructor require essential parameters?

Parameterized constructors = objects that can't be broken. Today child classes will call super().__init__() to pass data up to the parent.
The Problem

Inheritance — "Reuse and Extend"

Stop copy-pasting code. Let classes share what they have in common.

Real-world analogy

A child inherits traits from their parents — eye color, last name. The child doesn't re-learn walking from scratch. But the child CAN do new things (like play guitar). Get the parent's stuff for free, add your own on top.

Your restaurant has Food and Beverages. Spot the duplication:

menu_v1.py — spot the duplication
▼
class Food:
    def __init__(self, name, price, calories):
        self.name = name           # duplicated
        self.price = price         # duplicated
        self.calories = calories

    def describe(self):          # duplicated
        return f"{self.name} - Rs.{self.price}"

class Beverage:
    def __init__(self, name, price, volume_ml):
        self.name = name           # duplicated
        self.price = price         # duplicated
        self.volume_ml = volume_ml

    def describe(self):          # duplicated
        return f"{self.name} - Rs.{self.price}"

What's the problem?

The fix: extract common parts into a parent class.

The Syntax

class Food(MenuItem): — means Food inherits from MenuItem.

Food automatically gets everything MenuItem has: its attributes AND its methods. Food can then add its own stuff on top (like calories).

Great, so now we know the syntax. Let's write Food inheriting from MenuItem. Does this look right?

menu_attempt.py — our first try at inheritance
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def describe(self):
        return f"{self.name} - Rs.{self.price}"

class Food(MenuItem):
    def __init__(self, name, price, calories):
        self.calories = calories

biryani = Food("Biryani", 300, 450)
print(biryani.calories)     # 450
print(biryani.describe())   # ???
print(biryani.name)         # ???

Food inherits from MenuItem. We create a Food object with name, price, and calories. Will biryani.name work?

Inheritance gives you the parent's methods, but __init__ doesn't run on its own. You must EXPLICITLY call super().__init__(name, price) to let the parent do its setup. Here's the fix:
menu_v2.py — the fix with super().__init__() — click to reveal
▼
class MenuItem:                    # Parent (base class)
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def describe(self):
        return f"{self.name} - Rs.{self.price}"

class Food(MenuItem):              # Child — inherits name, price, describe()
    def __init__(self, name, price, calories):
        super().__init__(name, price)  # ← Tell parent to set up name & price
        self.calories = calories      # Then set up food-specific attr

class Beverage(MenuItem):          # Child — inherits name, price, describe()
    def __init__(self, name, price, volume_ml):
        super().__init__(name, price)  # ← Same: let parent handle name & price
        self.volume_ml = volume_ml

biryani = Food("Biryani", 300, 450)
chai = Beverage("Chai", 40, 200)
print(biryani.name)         # "Biryani" — now it works!
print(biryani.describe())   # "Biryani - Rs.300" — inherited!
print(chai.describe())      # "Chai - Rs.40" — inherited!

What inheritance gives you

1. No duplication — name, price, describe() written ONCE in MenuItem.

2. Fix once, fixed everywhere — update describe() in MenuItem, all children get the fix.

3. Each child adds only what's unique — Food adds calories, Beverage adds volume_ml.

If Food inherits from MenuItem, does a Food object have a describe() method?

The child gets ALL of the parent's methods automatically. That's the whole point of inheritance.
Key Concept

Method Overriding & Protected Access

A child can change the parent's behavior. There are two ways to do it.

Overriding: Replace vs Extend

When a child defines a method with the same name as the parent, that's called overriding. Both of these are overriding:

Replace — completely new behavior

class Food(MenuItem):
    def describe(self):
        # Ignores parent's version entirely
        return f"{self.name} ({self.calories} cal)"

# "Biryani (450 cal)"
# Parent's "Biryani - Rs.300" is gone

Use when the parent's logic doesn't apply to this child at all.

Extend — parent's behavior + more

class Food(MenuItem):
    def describe(self):
        base = super().describe()  # Get parent's result
        return f"{base} ({self.calories} cal)"

# "Biryani - Rs.300 (450 cal)"
# Parent's output + child's addition

Use when you want everything the parent does PLUS more. More common.

Both are called "overriding." The difference is whether you call super().method() inside.
Replace = don't call super. Extend = call super first, then add to the result.

biryani.describe() — which describe() runs?

The OBJECT's type decides. biryani is a Food, Food has describe(), so Food's version runs. super().describe() inside it explicitly calls MenuItem's version.

Protected Access — _name and Inheritance

Remember from OOP-1: self._name (single underscore) means "protected." Now you see WHY it exists:

protected_demo.py
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name           # Public — anyone can access
        self._base_price = price   # Protected — children can access, outsiders shouldn't
        self.__secret = "hidden"  # Private — only MenuItem can access

class Food(MenuItem):
    def calculate_price(self):
        return self._base_price * 1.05   # ✓ Child CAN access _protected
        # return self.__secret             ✗ Child CANNOT access __private
        # (would need self._MenuItem__secret — ugly and wrong)

Public (self.name) — everyone, including outside code.
Protected (self._base_price) — the class itself + its children. Signals: "internal, but subclasses need it."
Private (self.__secret) — only the class itself. Children can't access it directly.

Protected is the sweet spot for inheritance: outsiders can't touch it, but children can use it to extend behavior.

A child class Food tries to access self.__secret (defined in parent MenuItem as self.__secret). What happens?

This is why protected (_name) exists: it's the right level for attributes that children need. Private (__name) is too restrictive for inheritance. Public is too open.

super vs super()

super — the built-in class itself (a type object). Rarely used alone.
super() — creates a proxy object that follows the MRO to find the next class in the chain.

You almost always want super() with parentheses: super().__init__(), super().describe().

Deep Dive

Types of Inheritance & MRO

Four types of inheritance, and how Python decides which method to call when there's ambiguity.

1 Single Inheritance

▼ 
#   Animal
#     |
#    Dog

class Animal:
    def breathe(self): return "breathing..."

class Dog(Animal):
    def bark(self): return "Woof!"

dog = Dog()
print(dog.breathe())  # inherited from Animal
print(dog.bark())     # its own method

One parent, one child. The most common and simplest type.

2 Hierarchical Inheritance

▼ 
#     MenuItem
#    /   |   \
#  Food  Bev  Dessert

class MenuItem:
    def describe(self): return f"{self.name} - Rs.{self.price}"

class Food(MenuItem): pass
class Beverage(MenuItem): pass
class Dessert(MenuItem): pass
# All three share MenuItem's describe()

Multiple children, same parent. Our restaurant menu is exactly this.

3 Multilevel Inheritance

▼ 
#  Animal
#    |
#   Dog
#    |
#  GuideDog

class Animal:
    def breathe(self): return "breathing"

class Dog(Animal):
    def bark(self): return "Woof!"

class GuideDog(Dog):
    def guide(self): return "guiding owner"

buddy = GuideDog()
buddy.breathe()  # from Animal (grandparent)
buddy.bark()     # from Dog (parent)
buddy.guide()    # its own

Grandparent → Parent → Child chain. Keep to 2-3 levels max.

4 Multiple Inheritance (Python only — Java says no!)

▼ 
#  Car    Plane
#    \   /
#  FlyingCar

class Car:
    def drive(self): return "driving on road"

class Plane:
    def fly(self): return "flying in sky"

class FlyingCar(Car, Plane):  # Inherits from BOTH
    pass

fc = FlyingCar()
fc.drive()  # from Car
fc.fly()    # from Plane

One child, MULTIPLE parents. Python allows this. Java does NOT. This leads to the Diamond Problem — which is where MRO comes in.

MRO — Method Resolution Order

When a child has multiple parents with the same method, which one runs? Python uses C3 Linearization to decide.

mro_demo.py — the diamond problem
▼
#      A          (has greet)
#     / \
#    B   C        (both have greet)
#     \ /
#      D          (no greet — which parent's greet runs?)

class A:
    def greet(self): return "Hello from A"

class B(A):
    def greet(self): return "Hello from B"

class C(A):
    def greet(self): return "Hello from C"

class D(B, C):
    pass

d = D()
print(d.greet())   # ???

D inherits from both B and C. Both have greet(). What does D().greet() print?

Python goes left-to-right in the parent list. class D(B, C) → B is listed first, so B wins.

You can check the full order with D.__mro__:
D → B → C → A → object

This is called C3 Linearization (MRO). Rule: left-to-right, depth-first, each class appears only ONCE.

Java vs Python: Java bans multiple class inheritance entirely (only interfaces). Python allows it and uses MRO to resolve conflicts. You can always check with ClassName.__mro__ or ClassName.mro().

Pillar 4

Polymorphism — "Many Forms"

poly (many) + morph (forms).

Definition

Polymorphism = the ability of different objects to respond to the SAME method call in their OWN way. The caller doesn't know or care about the specific type — it just calls the method and the right behavior happens.

The problem polymorphism solves: you're writing print_bill() and it needs to calculate prices. Without polymorphism:

print_bill_bad.py — if/elif spaghetti
▼
def print_bill(items):
    for item in items:
        if isinstance(item, Food):
            price = item.price * 1.05   # 5% GST
        elif isinstance(item, Beverage):
            price = item.price + 10     # container deposit
        elif isinstance(item, Dessert):
            price = item.price * 1.12   # 12% GST
        # New type? Add another elif. Breaks Open/Closed.

We add Dessert, then Combo, then Snack, then DrinkRefill. What happens to print_bill()?

Polymorphism eliminates the if/elif entirely. Each type knows how to calculate its own price — print_bill() just calls the method:
print_bill_good.py — polymorphism — click to reveal
▼
def print_bill(items):
    for item in items:
        price = item.calculate_price()   # Each type handles its own logic!
        print(f"  {item.name}: Rs.{price:.2f}")
# New type? Just add a class with calculate_price(). ZERO changes here.

Duck Typing — "If It Quacks Like a Duck..."

duck_typing.py
▼
class EmailNotification:
    def send(self, msg): print(f"EMAIL: {msg}")

class Pigeon:  # Not a notification class at all!
    def send(self, msg): print(f"PIGEON carries: {msg}")

def notify(notifier, msg):
    notifier.send(msg)  # Python doesn't check TYPE, only: "does it have send()?"

notify(EmailNotification(), "Order ready")  # Works
notify(Pigeon(), "Order ready")              # Also works!

Python doesn't care about the TYPE — it only cares if the method EXISTS. "If it walks like a duck and quacks like a duck, it IS a duck." In Java you'd need implements Notifiable. Python just tries it.

PM says "add WhatsApp notifications." How much existing code changes?

Polymorphism means new types slot in with zero changes to existing code. This is extensibility from LLD-01.
Polymorphism in Operators

Operator Overloading — Dunder Methods

+ works on ints, strings, and lists — differently each time. How? Dunder methods.

What are dunder methods?

"Dunder" = double underscore. Methods like __str__, __add__, __len__ are called dunder methods (or magic methods).

Python calls them behind the scenes when you use operators or built-in functions:

print(obj) → Python internally calls obj.__str__()
a + b → Python internally calls a.__add__(b)
len(obj) → Python internally calls obj.__len__()
a == b → Python internally calls a.__eq__(b)

By defining these methods in YOUR class, you teach Python how print, +, len, == should work for your objects.

1 __str__ — what print() calls

▼ 
class Dish:
    def __init__(self, name, price):
        self.name = name; self.price = price

    def __str__(self):
        return f"{self.name} - Rs.{self.price}"

print(Dish("Biryani", 300))  # "Biryani - Rs.300" (not <Dish object at 0x...>)

2 __add__ — what + calls

▼ 
class Money:
    def __init__(self, amount, currency="INR"):
        self.amount = amount; self.currency = currency

    def __add__(self, other):
        if self.currency != other.currency:
            raise ValueError("Can't add different currencies")
        return Money(self.amount + other.amount, self.currency)

    def __str__(self): return f"{self.currency} {self.amount}"

total = Money(300) + Money(54)  # Calls __add__
print(total)                       # "INR 354"

3 __len__ — what len() calls

▼ 
class Cart:
    def __init__(self):
        self.items = []

    def add(self, item): self.items.append(item)

    def __len__(self):
        return len(self.items)

cart = Cart()
cart.add("Biryani"); cart.add("Naan")
print(len(cart))  # 2 (calls cart.__len__())

4 __eq__ — what == calls

▼ 
class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price

    def __eq__(self, other):
        return self.name == other.name and self.price == other.price

a = MenuItem("Biryani", 300)
b = MenuItem("Biryani", 300)
print(a == b)  # True (without __eq__, this would be False — different objects)

Without __str__, what does print(Dish("Biryani", 300)) show?

__str__ makes your objects printable. Without it, Python shows the memory address.
Gotcha

Method Overloading

In Java you can have multiple methods with the same name but different parameters. What about Python?

Read this code carefully:

overloading.py
▼
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c

calc = Calculator()
calc.add(1, 2, 3)   # ???
calc.add(1, 2)      # ???

Will both calc.add(1, 2, 3) and calc.add(1, 2) work?

Python does NOT support method overloading. If you define two methods with the same name, the second silently replaces the first. The Pythonic way is default parameters or *args:
The Pythonic way — click to reveal
▼
class Calculator:
    def add(self, *args):      # Accept any number of arguments
        return sum(args)

calc = Calculator()
print(calc.add(1, 2))          # 3
print(calc.add(1, 2, 3))       # 6
print(calc.add(1, 2, 3, 4, 5)) # 15
Tricky Scenarios

Which Method Gets Called?

The OBJECT's type decides, not the variable's type. Each scenario has its own code — no scrolling needed.

Scenario 1: Child overrides the method

class MenuItem:
    def describe(self): return f"{self.name} - Rs.{self.price}"

class Food(MenuItem):
    def describe(self): return f"{self.name} ({self.calories} cal)"

biryani = Food("Biryani", 300, 450)
biryani.describe()  # ???
The OBJECT is a Food. Food has describe(). Python starts at the object's class and looks there first.

Scenario 2: Child does NOT override the method

class MenuItem:
    def describe(self): return f"{self.name} - Rs.{self.price}"

class Beverage(MenuItem):
    def calculate_price(self): return self.price + 10
    # No describe() here!

chai = Beverage("Chai", 40, 200)
chai.describe()  # ???
Python looks at Beverage first → not found → goes up to MenuItem → found! The chain goes child → parent → grandparent → ... until found.

Scenario 3: Variable typed as parent, object is child

class MenuItem:
    def calculate_price(self): return self.price

class Food(MenuItem):
    def calculate_price(self): return self.price * 1.05

class Beverage(MenuItem):
    def calculate_price(self): return self.price + 10

items: list[MenuItem] = [Food("Biryani", 300, 450), Beverage("Chai", 40, 200)]
for item in items:
    print(item.calculate_price())  # ???
This IS polymorphism. The variable says MenuItem, but the OBJECT decides which method runs. Python doesn't have static typing that restricts method dispatch.

Scenario 4: Multilevel inheritance — which level's method runs?

class Animal:
    def speak(self): return "..."

class Dog(Animal):
    def speak(self): return "Woof!"

class GuideDog(Dog):
    pass   # No speak() override

buddy = GuideDog()
buddy.speak()  # ???
Python walks the MRO: GuideDog → Dog → Animal. Finds speak() in Dog, stops there. It doesn't go all the way to the top — it stops at the first class that has the method.

The rule

Python starts at the object's actual class and walks UP the inheritance chain (following MRO). It uses the first version it finds. It NEVER goes back down. The variable's type annotation doesn't matter — only the object's real class.

The Full Picture

Inheritance + Polymorphism Together

Adding a new type requires ZERO changes to existing code.

menu_system.py
▼
class MenuItem:
    def __init__(self, name, price):
        self.name = name; self.price = price
    def calculate_price(self): return self.price

class Food(MenuItem):
    def calculate_price(self): return self.price * 1.05

class Beverage(MenuItem):
    def calculate_price(self): return self.price + 10

def print_bill(items):  # Works with ANY MenuItem
    total = sum(item.calculate_price() for item in items)
    for item in items:
        print(f"  {item.name}: Rs.{item.calculate_price():.2f}")
    print(f"  TOTAL: Rs.{total:.2f}")

PM says "add Desserts with 12% GST." How many existing lines change?

Open/Closed Principle (SOLID). Open for extension (add Dessert), closed for modification (MenuItem, Food, Beverage, print_bill untouched).
Watch Out

Common Mistakes

Too-deep hierarchies
Animal → Mammal → Pet → Dog → GuideDog
Keep to 2-3 levels. If deeper, use composition.
Forgetting super().__init__()
Parent attributes never get set. AttributeError when accessing them.
"Is-a" vs "Has-a"
IS-A = inheritance: Food IS a MenuItem.
HAS-A = composition: Order HAS items.
class Order(list) — wrong! Order is NOT a list.
