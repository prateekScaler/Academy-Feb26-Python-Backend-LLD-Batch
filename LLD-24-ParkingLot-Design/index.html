Defaults we'll use:
  • Vehicles & spots: vehicles are bike / car / truck; spots are small / medium / large — two separate enums, related by one mapping (bike→small, car→medium, truck→large). "Can a bike take a car spot?" becomes a policy change in that one mapping, never a code change.
  • Floors: multiple, each with a fixed mix of typed spots.
  • Pricing: tiered hourly per spot size — first hour at one rate, every extra hour at another (50/80, 80/100, 100/120); the scheme must be swappable.
  • Payment: pay at exit, exactly once per ticket (cash / card / UPI); the gate opens only for a paid ticket.
  • Full lot: the vehicle is turned away at the gate.
  • Gates: ONE for the MVP — multiple gates is the named Step-7 headline (it's the concurrency question).
  • Future scope, named and parked: passes, valet, reservations, EV, display boards.

Step 2 — Requirements

From scope to requirements

The art of it — how do you know WHICH questions to ask?

You don't memorise a list — you generate it. Four moves turn a blank "design a parking lot" into the exact MVP questions:

  • Follow one actor end-to-end. Walk the driver's journey out loud: arrive → find a spot → park → (time passes) → pay → leave. Every step that could differ is a question.
  • Probe five lenses at each step — the inputs (what drives in?), the resource (the spots — typed? limited?), the money (how much, when, how?), the failure (full? unpaid?), the scale (one gate or many?).
  • Draw the MVP line with one test: "does removing this change the core entities or their relationships?" If no → name it and park it (passes, valet, reservations) — don't design it now.
  • Prefer the simplest answer that still shows the design. One lot, in-memory, one gate is enough to demonstrate every pattern; anything more is future scope.

Run those lenses over a parking lot and the questions almost write themselves — each answer becomes an FR:

LensThe question you ask
Inputs1. Which vehicle types — bike / car / truck?
Resource2. Are spots sized per type — can a bike take a car spot?  ·  3. One floor or many?
Money4. Pricing — hourly? per size? can the scheme change?  ·  6. How and when does the driver pay?
Failure5. What happens when the lot is FULL?
Scale7. One entry gate or several? (the concurrency question)

The nine functional requirements, full sentences

  1. The parking lot has one or more floors, and each floor has a fixed set of parking spots.
  2. Every spot has a size — small, medium, or large — and every vehicle type maps to exactly one spot size it can use (bike→small, car→medium, truck→large).
  3. A vehicle entering the lot is assigned a free spot of its type, and the driver receives a ticket recording the vehicle, the spot, and the entry time.
  4. If no suitable spot is free, the vehicle is turned away at the gate.
  5. A vehicle leaving the lot surrenders its ticket and pays a fee computed from the parked duration and the size of the spot it occupied.
  6. The moment a vehicle leaves, its spot becomes free for the next vehicle.
  7. The lot can report the number of free spots per vehicle type — per floor and in total.
  8. The spot-assignment policy and the pricing scheme can each change independently of everything else.
  9. A ticket is paid exactly once, before exit — the gate opens only for a paid ticket. Payment can be cash, card, or UPI.

NFRs (non-functional):

  • In-memory — no database or network yet, just the model and its logic.
  • One gate thread for the MVP (multiple gates = the Step-7 trade-off).
  • Rates and lot layout live as configuration in one place.
On concurrency — deliberately out of scope today. With a single gate there's no race, so we set it aside. In a real interview you should still raise it (two gates grabbing the last free spot at the same instant) — we'll tackle that contention head-on in the BookMyShow case study, where the seat race is the main event.
Step 3 — Entities

Every FR donates something

Same drill as TTT: per requirement — think first, answer the quiz where there is one, then reveal the discussion.

FR-1 — "The parking lot has one or more floors, and each floor has a fixed set of parking spots."

Decision quiz — does Floor deserve to be a class, or is it just a list of spots inside the lot?

C is right — Floor earns class-hood.
  • It has identity — its number; tickets and display boards reference "Floor 2" by name.
  • It has its own behaviour — FR-7 wants per-floor free counts, and the assignment strategy asks each floor for its free spots.
  • State + behaviour → class. Contrast TTT: a board row stayed a bare list — nothing ever addressed "row 2" by name. Same test, different answer.
  • Not A / B — putting floor-level queries on the lot is feature envy, the same smell as Board.is_empty(r,c).
  • Not D — a floor is not a kind of lot; that's has-a, not is-a.

💬 Reveal the discussion

▾

Re-read the requirement — the highlighted nouns are the classes, hiding in plain sight:

"The parking lot has one or more floors, and each floor has a fixed set of parking spots."

The lot is the orchestrator (the Game analogue). Floors are owned by the lot and spots by their floor — a composition chain. "Fixed set" means the layout is constructor input, not something that mutates mid-day.

FR-1 donates: ParkingLot ✔ class (orchestrator)  ·  Floor ✔ class (identity + queries)  ·  layout ✔ constructor configuration

FR-2 — "Every spot has a size, and every vehicle type maps to exactly one spot size it can use."

💬 Reveal the discussion

▾
  • The trap: fusing two concepts because they correlate — a "car spot" welds the vehicle to the spot.
  • Keep them apart: VehicleType (what drives in) and SpotSize (what the floor offers) are two enums, related by one mapping — SPOT_SIZE_FOR = {BIKE: SMALL, CAR: MEDIUM, TRUCK: LARGE}.
  • Policy as data: "add scooters and buses" is one entry each; "let bikes use car spots on weekends" edits a dict, not a class.
  • Vehicle is a frozen dataclass — plate + type, no behaviour.
  • The fit rule needs a home — it lands on Spot.can_fit(vehicle) (next beat).
FR-2 donates: VehicleType + SpotSize ✔ two enums  ·  SPOT_SIZE_FOR ✔ policy as data  ·  Vehicle ✔ frozen dataclass  ·  the fit rule ✔ a method on Spot

FR-3 — "…a vehicle entering the lot is assigned a free spot, and the driver receives a ticket."

Decision quiz — if Ticket is a class, what does it store?

B is right — and notice how it stores the spot.
  • The ticket is the lot's record (its "Move"): vehicle + spot + entry time (+ exit time later). Everything reads from it — the fee is computed FROM it (FR-5), the audit trail IS the ticket log, persistence = "store the tickets".
  • It stores the spot's id, not a live Spot object — that's the trap in C. A ticket outlives the parking session (billing, disputes, a DB row long after the car's gone), so it must not pin live objects. The lifetime question is deciding a field type here.
  • Not A — an id-only ticket can't be billed or audited without re-deriving everything. Not D — the Floor holds current state, not the history a ticket needs.

💬 Reveal the discussion

▾

So the fields fall out: Ticket(id, vehicle, floor_no, spot_id, entry_time, exit_time) — the parking lot's Move, and the only entity that records history. The quiz nailed the key call: ids over live references, because the ticket outlives the session.

FR-3 donates: Ticket ✔ dataclass — the event record  ·  ids over references ✔ tickets outlive sessions

FR-4 — "If no suitable spot is free, the vehicle is turned away at the gate."

Decision quiz — the lot is full. Does park() raise an exception, or return None?

D is right — and notice the answer FLIPPED from Tic-Tac-Toe. The criterion: is the failure a contract violation or an expected outcome?
  • TTT's illegal move broke the rules of the conversation — the caller did something wrong → InvalidMoveError.
  • A full lot on a Tuesday morning is nobody's mistake — it's a normal answer to a normal question → park() → Ticket | None, and the gate's display says "FULL".
  • The exceptions DO come back where the contract IS violated: an unknown or reused ticket, paying twice, exiting unpaid (FR-9) — InvalidTicketError, AlreadyPaidError, UnpaidExitError.
A (always raise) and B (performance) apply a blanket rule where a judgement call is being tested; C is real but the type hint Ticket | None makes mypy do the remembering. Interviewers accept either design if you state the criterion — the reference design raises; we return None; both defensible, neither accidental.

💬 Reveal the discussion

▾

FR-4 donates a signature decision, not an entity. The deeper lesson: exception-vs-Optional is not a style war, it's one question — whose fault is it? Contract violations raise; expected outcomes return.

FR-4 donates: park() → Ticket | None ✔  ·  the criterion ✔ which FR-9's three exceptions will pass

FR-5 & FR-6 — "…pays a fee computed from duration and spot size" · "the spot becomes free the moment the vehicle leaves."

Decision quiz — what is a Spot in code?

B is right — a Spot is TTT's Cell in a hi-vis vest.
  • Two facts: size and status.
  • Two rules that relate them live right here: is_free() and can_fit(vehicle) — free AND the right size (FR-2's rule finds its home).
  • Status is an enum, not a bool — see the contrast below.
  • Future-proof: when EV charging arrives, Spot grows one more fact — the class was the right call before the requirement landed.
✖ occupied: bool

Only two answers: free or taken. The admin's "mark a spot out of order" (oil spill, broken sensor) has nowhere to go — a bool can't say neither.

✔ status: SpotStatus

FREE · OCCUPIED · OUT_OF_ORDER — three real states. The same lesson GameStatus taught when "draw" arrived: count the states before reaching for a bool.

Why not the others? A models the status but loses the size · C leaks the logic to callers (a bare dataclass) · D splits one spot's truth across two objects.

💬 Reveal the discussion

▾

FR-5 names the fee inputs — duration and spot size — which is already a function signature: fee(size, seconds). Note what it does not take: the vehicle. You pay for the resource you occupied, not the vehicle you drove. The rates are tiered (first hour, then each extra hour, per size), and "the scheme can change" (FR-8) makes it a Strategy, next beat. FR-6 is a lifecycle rule on exit: free the spot, stamp the exit time — in that breath.

FR-5/6 donate: Spot ✔ class (size + SpotStatus; is_free/can_fit)  ·  exit lifecycle ✔ free → stamp → settle

FR-7 — "The lot can report free spots per type — per floor and in total."

💬 Reveal the discussion

▾

No new entity — FR-7 donates query methods at two altitudes. The highlighted behaviours are what become the methods on the class diagram: Floor.free_count(kind) (the floor answers for itself) and ParkingLot.available(kind) / per_floor(kind) (the lot sums its floors). Display boards read these; they never write. Same render/logic boundary as TTT's FR-8.

FR-7 donates: query methods ✔ at floor and lot altitude  ·  reads-never-write boundary ✔ for displays

FR-8 — "The spot-assignment policy and the pricing scheme can each change independently."

Decision quiz — where does "which spot do I pick?" live?

C is right. FR-8 says it in plain words: the policy changes — that's the open variable, the same evidence that made WinRule a Strategy. FirstFit (minimise walking) vs LeastCrowded (spread congestion) vs tomorrow's NearestToExit — one new class each, zero edits to the lot. A welds today's policy into the orchestrator (the if-tree returns the day valet parking lands). B can only see ONE floor — the policy is a cross-floor decision. D inverts control for no benefit. Note the second Strategy rides the same sentence: PricingStrategy (TieredHourly → WeekendFlat) — a parking lot has TWO open variables from day one, and they vary independently, which is exactly why they're two objects, not one "ConfigStrategy".

💬 Reveal the discussion

▾
FR-8 donates: ParkingStrategy ✔ ABC (FirstFit / LeastCrowded)  ·  PricingStrategy ✔ ABC (TieredHourly / WeekendFlat)  ·  both injected ✔ the lot never knows which

What kind of strategies? FirstFit walks floors lowest-first and grabs the first free spot of the right size — minimises walking from the gate. LeastCrowded picks the floor with the most free spots of that size — spreads cars out so no single floor jams. Both implement the same pick(floors, vehicle); the lot calls it blind to which is plugged in. (Pricing's pair: TieredHourly = first hour, then per-extra-hour by size · WeekendFlat = one flat fee.)

FR-9 — "A ticket is paid exactly once, before exit — the gate opens only for a paid ticket."

Design quiz — how do you model "paid exactly once, and the gate opens only for a paid ticket"?

B is right — the record IS the enforcement.
  • One Payment per ticket makes both rules one existence check: a Payment exists → already paid (block the second pay); none exists → unpaid (block the exit). Two rules, one query.
  • Not A — a bool loses the amount, method, and time, so you can't print a receipt or handle a refund. Payment is a record for the same reason Ticket is.
  • Not C — you still need the ticket at exit (which spot to free, the entry time), and deleting it throws away the audit trail.
  • Not D — a side set scatters one ticket's truth across two places, the same smell as splitting the Spot. Keep the fact with the entity that owns it.

💬 Reveal the discussion

▾
  • A second record entity — Payment(payment_id, ticket_id, amount, method, paid_at). Like the Ticket, it stores ids and outlives the visit (refund disputes read it).
  • PaymentMethod is a small enum (cash / card / UPI) — data, not subclasses, because the methods don't behave differently in our scope.
  • The contract rules raise (the FR-4 criterion, on the throwing side): paying twice → AlreadyPaidError; exiting unpaid → UnpaidExitError.
  • The flow each actor sees: park → amount_due() on the booth display (a read) → pay → exit.
FR-9 donates: Payment ✔ dataclass (the second record)  ·  PaymentMethod ✔ enum  ·  AlreadyPaidError / UnpaidExitError ✔ contract violations raise

ParkingLot — Floor  ·  Floor — Spot

▾

Ask: can a floor exist outside its lot? A spot outside its floor?

No — both are Composition (filled ◆): a composition chain. Demolish the lot, the floors go; remove a floor, its spots go. Nothing shares them.

ParkingLot — ParkingStrategy / PricingStrategy

▾

Ask: could two lots share one strategy instance?

Yes — Aggregation (open ◇): both are stateless. A 50-lot operator hands every lot the same FlatHourly(). Same answer as TTT's WinRule, same reason.

Ticket — Vehicle / Spot  ·  Payment — Ticket  ·  ParkingLot — Vehicle

▾

Ask: does the ticket own anything? Does the lot own vehicles?

Associations only. The ticket references a vehicle and a spot id; the payment references its ticket by id — one per ticket, and the pay-once rule enforces exactly that. Both records outlive the visit (billing, disputes), so ids, not live objects. Vehicles exist entirely outside the lot — the lot borrows them for a few hours. No diamonds anywhere here.

Same framework, different building

Two structural siblings — click to compare

📚 Library system — park/unpark wearing a cardigan

▾
  • issue_book / return_book ≈ park / unpark: a resource is claimed, a record (BookLoan ≈ Ticket) is written, a fee accrues with time (fine ≈ parking fee).
  • Late fines are a FinePolicy Strategy — the PricingStrategy seat, exactly.
  • Reservations = a hold with a TTL on the resource — the same future-scope shape as parking reservations.
  • The flip to notice: a Book is not consumed in place — it LEAVES the building. The "spot" (shelf slot) usually isn't modelled at all. Run the three-way test before copying the design.

🛗 Elevator system — the same parts, now in motion

▾
  • The same nouns map over: Floor ≈ Floor (literally), the elevator car ≈ the resource (the Spot's role), and a Request / Trip ≈ Ticket — the record of who wants to go from where to where.
  • The dispatch algorithm is a Strategy — which car answers a call (nearest-car / SCAN / LOOK) swaps without touching the rest, exactly the ParkingStrategy seat (the assignment policy).
  • State machine, not a bool — a car is IDLE / MOVING_UP / MOVING_DOWN / DOORS_OPEN, and a request carries a Direction (UP / DOWN). Count the real states — the SpotStatus / GameStatus lesson, again.
  • The flip to notice: the resource moves and serves a queue over time — so an elevator adds a scheduling dimension a parking spot never has. That's why it's its own design problem — and a great one to try next.
