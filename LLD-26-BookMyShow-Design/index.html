BookMyShow — Design (Part 1)

LLD-26 • Steps 1–5 of the playbook

Pick seats for a show and pay — the way real ticketing works. Design today, code in LLD-27.

Step 0 — Overview

First, get on the same page

Before any requirement, say the system back in one or two sentences — so you and the interviewer are picturing the same thing. Exactly how we opened Tic-Tac-Toe and Parking Lot.

The one-liner: “A user finds a movie, opens a show, sees its seat map, picks a few seats and pays — and the one rule that must never break is that no two users end up with a ticket for the same seat.”

A good overview names three things:

  • The actor & goal — a user wants to watch a movie, so they pick seats for a show and pay.
  • The core noun — what the design rotates around. Parking had the spot; here it's the seat of a show.
  • The twist — the new thing this class adds: concurrency. Many users want the same seat at once, and only one may get it.

Land it — “same page?” — then move to the scope questions.

Step 2 — Requirements

From a blank prompt to the MVP

The art of it — generate the list, don't memorise it

You never recall a canned list of FRs — you produce them on the spot. Four moves turn “design BookMyShow” into the exact MVP requirements:

  • Follow one actor end-to-end. Walk the user's journey out loud: browse → open a show → see the seat map → pick seats → hold → pay → booked. Every step that could differ is a requirement waiting to be written.
  • Probe a few lenses at each step — the inputs (what's bookable?), the resource (seats — typed? per-show?), the money (price — by type? scheme changes?), the failure (taken? unpaid in time?), the scale (how many at once? — the headline).
  • Draw the MVP line with one test: “does removing this change the core entities, their relationships, or the hard invariant?” If no → name it and park it (recommendations, food, refunds, loyalty) — don't design it now.
  • Cap it at ~8–10. An MVP that shows the whole design fits in eight to ten FRs. More than that and you're designing features, not the core — the interviewer wants the spine, not the catalogue.

Two kinds of FR — structural vs behavioural

As you write each requirement, sort it into one of two buckets. This split is not academic — each kind feeds a different part of the design, so labelling them tells you what to draw next.

🏗️ Structural — the nouns (what exists)

Describe the static shape: the things and how they're related. “A movie plays on screens; a screen has typed seats; availability is per-show.”

Feed → the entities & the class diagram. Each structural FR donates a class, a field, or a relationship (a diamond).

⚡ Behavioural — the verbs (what happens)

Describe actions and rules over time. “Search & filter movies; select seats; pay; cancel before cutoff — no two users get the same seat.”

Feed → the methods, APIs, sequence & state diagrams. Each behavioural FR becomes a verb someone has to own.

Why bother labelling? Because the two answer different questions. Structural FRs → nouns → the class diagram (Step 4). Behavioural FRs → verbs → the sequence & state machines (the code class). When you finish requirements, you read the structural ones to draw boxes, and the behavioural ones to draw arrows. Same trick we used on Tic-Tac-Toe and Parking — just named out loud this time.

Non-functional requirements (the “non-FRs”)

FRs say what the system does; NFRs say how well — qualities, not features. They rarely add classes.

  • Highly concurrent — many users hit the same show at once. For requirements we commit only to the invariant (FR-9: one seat, one ticket); how we lock seats is a design concern, not stated here.
  • Responsive reads — the seat map is read far more often than written; reads must stay cheap.
  • Config, not code — prices and seat layout live as data; a new pricing rule is one new strategy.
  • Extensible payments — a new payment mode plugs in without touching the booking flow.
We name concurrency, but we don't design it here. The requirement is just the invariant (FR-9). The locking mechanism — the LOCKED seat status, who wins the race — is a separate, later discussion, so the requirements stay about what, not how.

🧠 Round 2 — the subtle one (think harder)

FR-4 said availability is per-show. That doesn't hand you a noun — you have to think. Seat A1 is free for the 6pm show but booked for the 9pm. So where does that per-show status (and price) belong?

Decision quiz — seat A1 is free for the 6pm show but booked for the 9pm. Where do that per-show status AND price live?

C. The seat×show pairing has its own data — a status AND a price — and its own lifecycle (AVAILABLE → LOCKED → BOOKED). That is exactly when a pairing earns its own class.
✗ A — Seat is shared across every show; a flag on it would be wrong for all but one. ✗ B — a bare map carries status but has nowhere clean to put the per-seat price. ✗ D — the status must exist before any ticket does.

Why ShowSeat earns its own class — the heuristic:

  • A pairing earns a class when the pairing itself carries data. Seat alone → a type. Show alone → a time. Seat × show → status + price — brand-new data that belongs to neither parent.
  • It has a lifecycle. A ShowSeat moves AVAILABLE → LOCKED → BOOKED; a plain map value can't own that transition cleanly.
  • It has identity. A Ticket points at specific ShowSeats (a foreign key), not at “seat 12 of show 5” reconstructed every time.
  • Contrast Parking: a Spot's status lived ON the spot — there was no second dimension. Here the show is that second dimension, and it pushes the pairing out into its own object. Same three-way test, different answer because the FR changed.
  • When NOT to: if a seat had only a free/taken bool and no per-show price, a map on Show would do — don't over-model. It's the price + the lock lifecycle that tip it over.

And the record? The durable one is the Ticket (user + show-seats + payment + status). The transient “hold” isn't a separate entity here — it's just the LOCKED status on the ShowSeat while a user pays.

Step 4b — Classes → schema

Class or table? The ShowSeat question, settled

“Should ShowSeat be a class, or just a join table for the many-to-many between Show and Seat?” — the right answer is both, at two layers. Here's why that's not a cop-out.

A class diagram and a schema are the same model — objects in memory vs rows on disk.

  • Show ↔ Seat is many-to-many — one show has many seats; one (physical) seat appears in many shows.
  • A plain M:N with no extra data → you don't need a class at all; the DB just gets a bare join table of two foreign keys.
  • But this pairing carries its own data — a status and a price. That tips it over the line: in OOP it becomes an association class (so yes, ShowSeat is a real class), and in the DB it becomes an associative table show_seat(show_id, seat_id, status, price).
  • Same entity, two layers. The ShowSeat class maps 1:1 to the show_seat table. They don't compete — you have both.

The rule: a many-to-many with attributes ⇒ promote the relationship to a first-class thing — a class in code, a table-with-columns in the DB. A many-to-many with nothing on it stays a bare join table.

Show ↔ Seat is many-to-many, and the pairing has a status + price. What's technically correct?

C. M:N + attributes ⇒ an association class (OOP) that is exactly an associative table (DB) — one idea at two layers, with a composite/surrogate key and FKs to both sides.
✗ A is right only when the relationship has no data. ✗ B forgets it must persist. ✗ D can't index a seat, enforce per-seat status, or stop a double-book.

Deriving the schema — the rote rules

  • Each class → a table; each field → a column.
  • 1:N (the composition / aggregation chains) → a foreign key on the many side: cinema.city_id, screen.cinema_id, seat.screen_id, show.movie_id, ticket.user_id.
  • M:N → an associative table; M:N with data → that table carries the extra columns (the association class) — that's show_seat.
  • Enum → a VARCHAR + CHECK (... IN (...)) (or a small lookup table).
  • An invariant → a constraint. No-double-book (FR-9) = UNIQUE(show_id, seat_id) on show_seat; pay-once = UNIQUE(ticket_id) on payment. The DB enforces what application code would otherwise race on.

First, derive the relationships — where does each FK go?

Before drawing the ER diagram, reason out every link. The rule to keep firing: the FK lives on the “many” side, and an M:N with its own data becomes a table.

A city has many cinemas (1:N). Where does the foreign key go?

B. In a 1:N relationship the foreign key always lives on the many side — each cinema row stores its one city_id. (You never put a list of cinema ids on the city.) Same for screen.cinema_id and seat.screen_id.

What kind of relationship is Show ↔ Seat?

C. One show has many seats; one physical seat appears in many shows — that's many-to-many. M:N can't be a single FK on either side; it needs a table in between.

That Show ↔ Seat M:N (with a status + price on it) becomes…?

A. The M:N becomes the show_seat associative table — one row per (show, seat), holding the two FKs show_id + seat_id plus its own status & price. That's the association class as a table.

A ticket holds 1+ show_seats; each show_seat is sold once. Where's the FK between ticket and show_seat?

B. A ticket has many show_seats but each show_seat is sold on at most one ticket — so it's 1:N, and the FK ticket_id goes on the many side (show_seat), nullable until booked. No join table needed here.

Put those answers together and the ER diagram draws itself:

Where does “no two users book the same show-seat” (FR-9) live in the schema?

B. The DB makes a second booking of the same (show, seat) physically impossible — the data-layer twin of the in-memory invariant.
✗ A alone races: two requests both read “free” and both insert. ✗ C / D guard other things. The UNIQUE constraint is the real enforcement; the application lock just makes the failure friendlier.
Step 5 — The booking flow & concurrency (a peek)

How do two users NOT get the same seat?

The booking flow is a hold that becomes a booking or expires (HOLD → pay → CONFIRM) — and the one invariant is one show-seat → one ticket. Several simple ways to guarantee it; think about which fits — we go deep in LLD-27.

The danger, in one line: two requests both read seat A1 as free, both write “booked” → two tickets for one seat. The fix is always the same idea — make “check it's free and take it” a single, un-interruptible step. How you do that is the choice below.

A few simple approaches — which fits BookMyShow?

🧳
1 · Lock in the code ↗

A mutex in the app around the seat update — only one thread at a time. Dead simple, but works on one server only. (Python threading.Lock)
🔒
2 · Pessimistic DB lock ↗

SELECT … FOR UPDATE locks the seat row until you commit; the second request waits its turn. One database, many app servers. (Vlad Mihalcea)
🎯
3 · Optimistic concurrency ↗

Don't lock — UPDATE … WHERE status='AVAILABLE' (or a version column) and check rows-affected; the loser simply retries. Scales beautifully when conflicts are rare.
🌐
4 · DB constraint / Redis lock ↗

Let the DB refuse the 2nd booking — UNIQUE(show_id, seat_id) — or a Redis lock with a TTL across many services. (Redis Redlock)
⏳
5 · Reserve-then-pay (a hold)

Mark the seats LOCKED for a few minutes while the user pays — the HOLD → pay → CONFIRM flow; unpaid holds expire and free up. What BookMyShow actually does — sitting on top of one of the locks above.

Prefer video? Search “pessimistic vs optimistic locking” or “database row locking” — plenty of short, clear walkthroughs.

Your turn — think about it. Which of these would you pick for BookMyShow, and why? Jot down one approach and its main trade-off. There's no single right answer — it depends on scale: one server → a code lock; one database → a row lock or a UNIQUE constraint; many servers → optimistic updates or a distributed lock, usually behind a hold. We compare all of them and build the winner live in LLD-27. For now, just hold the invariant in your head: one seat, one ticket.

Step 6 — Trade-offs

Design choices to say out loud

The design-level forks today — the concurrency trade-offs (lock granularity, holds & TTLs, oversell) we tackle in LLD-27.

🪑
ShowSeat rows: when?

Pre-generate every ShowSeat when a show is created (simple reads, more rows) vs create on first touch (lean, more logic). A storage-vs-simplicity call.

💰
Pricing: object or data?

A PricingStrategy object (swap behaviour) vs rules-as-data in a table (edit without deploy). Both fine — depends how often the rules change.

🔍
Search & filter at scale

As the catalogue grows, name/location/language filters need indexes — or a search service. Reads dwarf writes, so optimise the read path.

↩️
Cancellation & cutoff

A cancelled ShowSeat returns to AVAILABLE; refunds run through Payment; the 1-hour cutoff is a guard on the booking lifecycle.
