What's Actually Happening

🏪

Merchant's Page

The checkout page, branding, address fields, discount code logic — all of this is Frido's code running on frido.com.

💳

Stripe's iframe

The card input field (highlighted with dashed border) is actually an <iframe> served from js.stripe.com. It just looks like it's part of Frido's page.

🔒

Same-Origin Policy (SOP)

Browser security prevents Frido's JavaScript from reading what you type in the Stripe iframe. Your card number goes directly to Stripe, never touching Frido's servers.

✅

PCI Compliance

Frido gets the benefits of a seamless checkout without the burden of PCI compliance. They never see or store card data.

How it's embedded:

<div id="card-element"></div>

const stripe = Stripe('pk_live_...');
const elements = stripe.elements();
const card = elements.create('card');
card.mount('#card-element');

This creates an iframe that looks native but is actually Stripe's domain.

🔒 Same-Origin Policy Explained (For Beginners)

The browser has a built-in security feature called Same-Origin Policy. It prevents JavaScript on one website from reading data on another website.

What is "Origin"?

An origin is: protocol + host + port

URL Origin
https://frido.com/checkout https://frido.com
https://js.stripe.com/v3/ https://js.stripe.com

These are different origins → browser blocks cross-reading!

What does SOP block?

Action Allowed?
Frido's JS reading Stripe iframe content ❌ BLOCKED
Frido's JS accessing card number input value ❌ BLOCKED
Stripe iframe sending data to Stripe servers ✅ ALLOWED
Stripe iframe styling to match Frido's page ✅ ALLOWED

See it yourself in DevTools!

  1. Open any Stripe checkout page (e.g., Stripe Demo)
  2. Right-click the card input → "Inspect"
  3. Notice the <iframe> tag with src="https://js.stripe.com/..."
  4. Try to access its content from Console: document.querySelector('iframe').contentDocument
  5. You'll see: Blocked a frame with origin... from accessing a cross-origin frame
