step 4 · edge cases

parametrize — one test, a table of cases

Copy-pasting a test with different numbers is a smell. Turn the test into a table — and fill the table from the boundaries.

😭 First, the painful “before” — six near-identical tests

▼
# ...the same assertion, copy-pasted six times, numbers tweaked
def test_split_100_by_3():
    assert sum(split_equal_paise(10_000, 3)) == 10_000

def test_split_100_by_1():
    assert sum(split_equal_paise(10_000, 1)) == 10_000

def test_split_zero():
    assert sum(split_equal_paise(0, 4)) == 0

def test_split_1_paisa_by_3():
    assert sum(split_equal_paise(1, 3)) == 1

def test_split_total_equals_n():
    assert sum(split_equal_paise(7, 7)) == 7

def test_split_total_less_than_n():
    assert sum(split_equal_paise(6, 7)) == 6
💬 Why this hurts:
  • The logic (“shares sum back to the total”) is written once but duplicated six times — change the assertion and you edit it in six places.
  • Adding a boundary means copy-paste-tweak a whole new function, and inventing yet another name.
  • The six names hide the truth: this is one behaviour tested with six inputs, not six different behaviours.
  • Miss a case? It’s invisible — there’s no single place that shows the whole input table at a glance.

The fix — say the logic once, list the inputs as data:

@pytest.mark.parametrize("total, n", [
    (10_000, 3),      # the typical ₹100 / 3
    (10_000, 1),      # n = 1 — one person pays everything
    (0,      4),      # zero — every share zero
    (1,      3),      # 1 paisa among 3 — someone pays it
    (7,      7),      # total == n — everyone pays exactly 1
    (6,      7),      # total < n — some pay 1, some pay 0
])
def test_split_conserves_the_total(total, n):
    assert sum(split_equal_paise(total, n)) == total
💬 What it does: One test function, six independent runs — pytest names each row (test_split[...10000-3]), so a failure points at its exact case. New regression? Add one line to the table.

🧭 Where do the rows come from? Boundaries.

  • For every numeric input ask: 0 · 1 · typical · the value where behaviour changes · the extreme.
  • Bugs cluster at the cutoffs — the ≥-vs-> decisions. Test the cutoff itself and a neighbour on each side.
  • Values deep inside a band add rows, not information.

Testing late_fee(days_overdue): free for 0, ₹10/day for 1–7, ₹20/day beyond 7. Which value set earns its keep?

Test the cutoffs.
  • The behaviour flips at 0→1 and 7→8 — that’s where an off-by-one lives; you need those exact values plus a neighbour.
  • One-per-band (1, 4, 8) sails through even when the ≤7 vs <7 boundary is wrong.
  • 0–14 exhaustively is eleven redundant rows that bury the table’s intent.
  • Rule: edges + one representative per band.
step 5 · reuse the arrange

Fixtures — Arrange once

When every test starts with the same setup, extract it into a fixture — and ask for it by name.

😭 First, without fixtures — setup & teardown in every test

▼
# a MODULE-LEVEL lot, shared by every test  ->  the trap
lot = ParkingLot(spots=2)

def test_parking_assigns_the_first_free_spot():
    # setup, by hand, at the top of every test
    lot.free = [0, 1]; lot.occupied = {}
    ticket = lot.park("KA-01-AA-1111")
    assert ticket.spot == 0
    # ...and teardown, by hand, at the bottom of every test
    lot.free = [0, 1]; lot.occupied = {}

def test_full_lot_returns_none():
    lot.free = [0, 1]; lot.occupied = {}          # repeated setup
    lot.park("a"); lot.park("b")
    assert lot.park("c") is None
    lot.free = [0, 1]; lot.occupied = {}          # repeated teardown

def test_unpark_frees_a_spot():
    lot.park("a")                                  # forgot the reset here!
    lot.unpark(Ticket(0, "a"))
    assert lot.park("b").spot == 0                 # passes or fails by ORDER
💬 Two problems, both nasty:
  • Not DRY: the same reset is copy-pasted at the top and bottom of every test — the actual behaviour (the Act + Assert) drowns in bookkeeping.
  • Leaked state: the shared lot means one test’s leftovers become the next test’s starting point. Forget one reset (see test_unpark) and a test passes or fails depending on the order tests happen to run — the classic Independence bug.
  • Teardown that isn’t safe: if an assert fails, the manual teardown line below it never runs — so one failure poisons every test after it.

The fix — declare the setup once; every test gets a fresh, isolated copy:

@pytest.fixture
def empty_lot():
    return ParkingLot(spots=2)             # a fresh lot for every test

def test_parking_assigns_the_first_free_spot(empty_lot):
    ticket = empty_lot.park("KA-01-AA-1111")
    assert ticket.spot == 0
💬 What it does: Declare the setup once with @pytest.fixture; a test names empty_lot in its signature and pytest injects a fresh one. That’s dependency injection — the same idea you’ll use all through Part 2.
  • Fresh per test by default — two tests asking for empty_lot get two different lots (Independence, mechanised).
  • Fixtures compose — a full_lot fixture can build on the same class, pre-filled.
  • Shared across files? Move it to conftest.py.
step 6 · sad paths

Testing errors, and the float trap

The happy path is half the job.

def test_overdraw_raises_and_leaves_the_balance_untouched():
    wallet = Wallet(balance_paise=500_00)
    with pytest.raises(InsufficientFunds) as excinfo:
        wallet.withdraw(600_00)
    assert excinfo.value.needed == 600_00      # the error carries data
    assert wallet.balance == 500_00            # nothing half-applied
💬 What it does: pytest.raises asserts the block raises that exception (and fails if it doesn’t). Then assert on excinfo.value — and that the failed op changed nothing.
  • Rule violation → raises (overdraw). Expected outcome → value (a full lot returns None). Don’t raise for answers the caller asked about.
  • Floats lie: 0.1 + 0.2 != 0.3. Use pytest.approx for genuinely continuous values — but for money, use integer paise and equality is exact, no epsilon.
part 2 · mocking

Why fake a dependency at all?

Some collaborators simply can’t run inside a fast, repeatable unit test. Start with your gut, then we’ll name the pattern.

A gut check — before we define anything. Here’s place_order(): to take payment it calls a PaymentGateway; it also adds amounts with a Money object and checks the cart isn’t empty with an OrderValidator. You want this test to run in milliseconds, offline, on every commit. Which collaborator is going to fight you?

Trust that instinct — it is Part 2.
  • The gateway is the one that reaches out of your process — network, real money, and it fails sometimes; you can’t hit it on every commit.
  • Money and OrderValidator are pure, fast, in-memory logic — leave them real; swapping them out would test the swap, not your code.
  • So here’s the plan for this part: drop a fast, predictable stand-in where the gateway sits — then work out which kind of stand-in and how to slot it in. Keep reading and this stops being a guess.
🐌
Slow
An HTTPS round-trip to a payment gateway is ~800ms. A thousand of those and the suite stops being run.
💰
Paid / risky
Real money moves. Real emails/SMS go to real people. You can’t do that on every commit.
🌬️
Flaky
The network fails sometimes. A test that fails 1% of the time for reasons outside your code trains people to ignore red.
🎲
Non-deterministic
An LLM, the clock, random — different answer each run, so == has nothing to compare to.
The fix is always a test double: a stand-in for the real collaborator that’s fast, free, and predictable. The question is only which kind of double, and how you slot it in.
the vocabulary

Five kinds of test double

“Mock” is often used loosely for all of them. The precise names help you pick.

1 · Dummy

The problem: A function’s signature demands an argument — a logger, a request, a config — but the branch you’re testing never touches it. You still have to pass something.

The dummy: Pass a dummy: an inert placeholder (None, an empty object, a bare Mock()) that exists only to fill the slot.

Reach for it when a parameter is required by the signature but irrelevant to this test.

def test_report_builds_when_logging_is_off():
    report = build_report(sales, logger=None)   # dummy: unused on this path
    assert report.total == 4200
2 · Stub

The problem: Your code asks a collaborator a question — “what’s the exchange rate?”, “did the charge succeed?” — and branches on the answer. The real answer is slow, paid, or unpredictable.

The stub: A stub hands back a canned answer, so your code receives a fixed, known input every run.

Reach for it when you need to steer the code down a specific path (the “rate is 83” case, the “payment declined” case).

def test_pay_returns_the_stubbed_receipt():
    gateway = Mock()
    gateway.charge.return_value = "rcpt_9"       # canned answer
    assert Checkout(gateway).pay(500_00) == "rcpt_9"

def test_declined_charge_raises():
    gateway = Mock()
    gateway.charge.side_effect = PaymentError    # stub the failure path
    with pytest.raises(PaymentError):
        Checkout(gateway).pay(500_00)
3 · Spy

The problem: The behaviour you care about has no return value to check — “did we send the email?”, “did we charge exactly once?”. There’s no output to assert on.

The spy: A spy is a stub that also records every call, so after the act you can ask: was it called, how many times, with what arguments?

Reach for it when the outcome is an interaction with a collaborator rather than a returned value.

def test_receipt_email_is_sent_once():
    mailer = Mock()                                # the spy
    checkout(gateway=Mock(), mailer=mailer, amount_paise=500_00, email="a@b.com")
    mailer.send.assert_called_once_with(to="a@b.com", subject="Receipt")
4 · Mock

The problem: You want the test to fail when a required interaction is missing or wrong — the charge that must happen, the audit row that must be written.

The mock: A mock is set up with that expectation and verifies it; the assertion is about the interaction, not a return value.

Reach for it when pinning down a mandatory side effect. (In Python, Mock + assert_called_* serves as spy and mock — the difference is only what you assert.)

def test_placing_an_order_charges_the_card_exactly_once():
    gateway = Mock()                               # the mock
    place_order(gateway, amount_paise=500_00)
    gateway.charge.assert_called_once_with(500_00)   # fail if it didn't
5 · Fake

The problem: Mocking a database means pre-scripting every get/save — brittle, and it never proves the data was stored correctly. You want to actually store and read back.

The fake: A fake is a real, working implementation kept lightweight — an in-memory dict standing in for the DB — so you assert on real state.

Reach for it when the collaborator holds state (repositories, caches, queues). Mock the things you merely poke; fake the things you store into.

def test_signup_actually_stores_the_user():
    repo = InMemoryUserRepo()                    # the fake: a dict inside
    SignupService(repo, notifier=Mock()).register(7, "a@b.com")
    assert repo.get(7) == {"id": 7, "email": "a@b.com", "status": "ACTIVE"}

Python’s unittest.mock.Mock is a Swiss-army knife — it can act as stub (return_value), spy (assert_called_with), or mock. A Fake is different: you write it, because it holds real state. Rule of thumb: fake what you store into, mock what you just poke.

You need to test a SignupService that (a) saves the user to a repo and (b) fires a welcome email. Best doubles?

Fake what holds state; mock what you poke.
  • The repo holds state — a fake lets you assert the user was actually stored, correctly (behaviour), not merely that save was called.
  • The mailer just gets poked — a mock’s assert_called_once_with is the right check; you don’t want to send real mail.
  • Mocking the repo too would couple the test to how saving works; the real mailer/DB would make it slow and non-deterministic.
three ways in

Slotting the double in: DI → monkeypatch → patch

Three techniques, in order of preference. Reach for the earliest one the code allows.

1️⃣ Dependency injection — the cleanest

class Checkout:
    def __init__(self, gateway):           # the seam
        self.gateway = gateway

def test_pay():
    checkout = Checkout(FakeGateway(receipt="rcpt_42"))   # inject a double
    assert checkout.pay(500_00, "tok")["receipt"] == "rcpt_42"
💬 What it does: If the code takes its collaborator as a parameter, a test just passes a different one. No patching machinery at all — and it makes the design better (the same reason we inject Strategies and Clocks).

2️⃣ monkeypatch — when there’s no seam

def promo_discount():
    return 10 if os.environ.get("PROMO") == "on" else 0

def test_promo(monkeypatch):
    monkeypatch.setenv("PROMO", "on")      # swapped for this test only
    assert promo_discount() == 10          # ...and undone automatically after
💬 What it does: pytest’s built-in monkeypatch fixture replaces an attribute / env var / function for one test and restores it automatically when the test ends. Great for code you can’t (or won’t) refactor.

3️⃣ unittest.mock — Mock + patch

from unittest.mock import Mock, patch

gateway = Mock()
gateway.charge.return_value = "rcpt_9"      # stub: canned answer
gateway.charge.side_effect = TimeoutError   # or make it raise

with patch(f"{__name__}.fetch_rate", return_value=83.0):
    ...                                     # replace a looked-up name
💬 What it does: Mock() conjures any method you touch and records the call. .return_value stubs the answer, .side_effect raises or yields a sequence. patch temporarily swaps a name (decorator or with-block).

A function reads settings.FEATURE_X (a module global) directly — no parameter to pass a double through. Cleanest way to control it in a test?

Match the tool to the seam you have.
  • No injection point → monkeypatch is the low-friction fix, and it cleans up after itself.
  • A full redesign is the right long-term move sometimes, but it’s overkill just to read one setting in a test.
  • Mutating the real global by hand breaks Independence — a later test inherits your value; that’s the bug monkeypatch exists to prevent.
the classic gotcha

Where to patch: the #1 mocking bug

You wrote a perfect mock, the test still calls the real thing. Almost always this rule.

🎯 Patch the name where it is looked up, not where it is defined.
# rates.py
def get_rate(): ...            # the real, slow one

# billing.py
from rates import get_rate     # billing now has its OWN reference
def invoice(usd): return usd * get_rate()

# test — patch billing's reference, NOT rates':
with patch("billing.get_rate", return_value=83.0):   # ✅
    ...
# patch("rates.get_rate", ...) would MISS — billing already bound its own name
💬 What it does: When billing does from rates import get_rate, it copies the name into its own module. Patching rates.get_rate now changes a name billing no longer looks at. Patch billing.get_rate.

report.py has import emailer and calls emailer.send(...). What do you patch?

Follow how the name is resolved at call time.
  • import emailer keeps a reference to the module; emailer.send is resolved on that module each call — so patch emailer.send.
  • Contrast with from emailer import send: then you’d patch report.send, the local copy.
  • Injection is a fine alternative, but patch works here without changing the code.
verify the interaction

Spying — assert HOW it was called

Some behaviour has no return value to check — the point is the interaction: charge once, email once, don’t email on failure.

gateway, mailer = Mock(), Mock()
checkout(gateway, mailer, 500_00, "a@b.com")

gateway.charge.assert_called_once_with(500_00)          # exactly one charge
mailer.send.assert_called_once_with(to="a@b.com", subject="Your receipt")

# and the important NEGATIVE, when the charge fails:
gateway.charge.side_effect = PaymentError
mailer.send.assert_not_called()                         # no receipt on failure
💬 What it does: A Mock records every call. assert_called_once_with pins down the count and the args; assert_not_called guards the sad path (the “we didn’t double-charge / didn’t email on failure” tests).

A colleague’s test mocks the repo, the mapper, the serializer, and the validator — then asserts each was called. It’s green. What’s the risk?

Over-mocking tests the plumbing, not the promise.
  • Mocking everything freezes how the code is built; rename a helper or reorder two calls and the test goes red though behaviour is unchanged — green-to-red with no bug trains people to distrust the suite.
  • Coverage of interactions isn’t coverage of behaviour — assert outcomes (via a fake) where you can.
  • Mocks are fast; slowness isn’t the issue — brittleness is. Mock the boundaries, use real/fake for the rest.
part 3 · the web layer

Testing the API endpoint

Move one rung up the pyramid: an integration test that drives a real request through your DRF view to a real (test) database.

📡 DRF’s APIClient + pytest-django

  • pytest-django spins up a throwaway test database and rolls it back after each test — mark tests with @pytest.mark.django_db.
  • APIClient makes real requests in-process — no running server, no network, but the full middleware → view → serializer → ORM path.
import pytest
from rest_framework.test import APIClient

@pytest.fixture
def client():
    return APIClient()

@pytest.mark.django_db
def test_create_event_persists_and_returns_201(client):
    resp = client.post("/api/events/",
                       {"title": "Standup", "starts_at": "2026-07-06T10:00Z"},
                       format="json")
    assert resp.status_code == 201                  # the contract
    assert resp.data["title"] == "Standup"
    assert Event.objects.count() == 1               # the side effect
💬 What it does: One test checks the whole request/response contract and the DB effect: status code, response body, and that exactly one row landed. This is the “POST /events authenticates, validates, persists” integration test from LLD-31’s pyramid.

🔒 Auth — skip the login dance

@pytest.mark.django_db
def test_the_owner_can_delete_their_event(client, django_user_model):
    vipul = django_user_model.objects.create_user("vipul")
    event = Event.objects.create(title="Standup", owner=vipul)   # vipul OWNS it
    client.force_authenticate(vipul)                             # act as vipul

    resp = client.delete(f"/api/events/{event.id}/")

    assert resp.status_code == 204              # owner allowed -> deleted

@pytest.mark.django_db
def test_a_non_owner_is_forbidden(client, django_user_model):
    vipul   = django_user_model.objects.create_user("vipul")
    mallory = django_user_model.objects.create_user("mallory")
    event = Event.objects.create(title="Standup", owner=vipul)
    client.force_authenticate(mallory)                          # NOT the owner

    resp = client.delete(f"/api/events/{event.id}/")

    assert resp.status_code == 403              # forbidden
    assert Event.objects.filter(id=event.id).exists()   # still there
💬 Where does “owner” actually come from?
  • The rule lives in the view, not the test. Deletion is guarded by a DRF permission — e.g. an IsOwner class that checks obj.owner == request.user (or a get_queryset filtered to owner=request.user). The test doesn’t enforce ownership; it verifies the view does.
  • Ownership is data: Event.objects.create(title=…, owner=vipul) is what makes vipul the owner — the row stores that foreign key.
  • Identity is the request: force_authenticate(vipul) makes request.user == vipul. Now the permission sees obj.owner (vipul) == request.user (vipul) → allowed → 204.
  • The negative proves the rule bites: authenticate mallory instead — same event, but obj.owner (vipul) ≠ request.user (mallory) → 403, and the row is still there.
  • So: who owns it = the FK on the event; only the owner may delete = the view’s permission; the test wires the two together and checks both outcomes.

force_authenticate only skips the login step (authentication) — the authorization rule still runs for real in the view.

💡 Mocking meets the web: when an endpoint calls something external mid-request — a payment gateway, an email send, an LLM — you patch that call inside the API test. Real request + real DB + a mocked gateway = fast, deterministic, and still end-to-end enough. Part 2 and Part 3 combine here.

🤝 The combination in one test

@pytest.mark.django_db
@patch("orders.views.stripe_gateway")          # patch WHERE the view looks it up
def test_checkout_charges_the_card_and_saves_a_paid_order(mock_gateway, client):
    mock_gateway.charge.return_value = "rcpt_42"        # stub the boundary
    Cart.objects.create(id=7, total_paise=500_00)

    resp = client.post("/api/checkout/", {"cart_id": 7}, format="json")

    assert resp.status_code == 201                      # the HTTP contract
    mock_gateway.charge.assert_called_once_with(500_00) # we really charged (spy)
    assert Order.objects.get(cart_id=7).status == "PAID"  # the real DB effect
💬 What it does:
  • Real request + real DB: APIClient drives POST /api/checkout/ through routing, validation, the view and the ORM; @django_db gives a throwaway DB, so Order.objects.get(...) checks a row that actually landed.
  • Mocked boundary: @patch("orders.views.stripe_gateway") replaces Stripe — patched where the view looks it up (the where-to-patch rule) — so the test is fast, offline, and charges no card.
  • Three assertions, three layers: the status code (the contract), assert_called_once_with (we charged, and exactly once — the spy), and the persisted order status (the side effect).
📦 Run these for real: code/django_demo/ is a self-contained Django+DRF project — the event CRUD contract, the owner-only 403, and this checkout-with-a-patched-gateway test, all runnable with pip install django djangorestframework pytest-django then pytest. 6 tests, green.

Your POST /checkout view calls Stripe. In the API test you should…

Real request, real DB, mocked boundary.
  • patch the Stripe call so the test is fast and deterministic, while APIClient + the test DB still exercise routing, validation, the view, and persistence.
  • The real sandbox reintroduces network flakiness and slowness into a test you want to run on every commit (and can charge test cards).
  • Skipping the endpoint leaves the wiring — routing, auth, serialization — untested; that’s exactly what an integration test is for.
part 4 · the new frontier

Evals — testing what has no single right answer

The teaser from LLD-31, in full. The moment your backend calls an LLM, assert actual == expected stops working — run it twice, get two good-but-different answers.

🧮 Two layers, cleanly separated

  • Layer A — unit tests with the LLM mocked. The code around the model (prompt building, parsing, fallbacks, retries) is ordinary deterministic code. Mock the model (Part 2!) and test it fast and free.
  • Layer B — the eval. The model’s quality can’t be pinned to one string. Instead you grade outputs against a rubric, over a golden set of inputs, and assert the pass rate.
# Layer A — deterministic, mocked
def test_summarize_trims_and_keeps_the_ticket():
    llm = Mock(); llm.complete.return_value = "  Refund #4521 for 1499.  "
    assert summarize(llm, ticket) == "Refund #4521 for 1499."

# Layer B — the eval: grade, don't ==
def grade(summary):                       # a rubric, scored 0..1
    facts = sum(f in summary.lower() for f in ["#4521","1499","refund"]) / 3
    return facts * (1.0 if len(summary.split()) <= 25 else 0.5)

def test_summarizer_pass_rate_stays_above_80_percent():
    scores = [grade(model(t)) for t in GOLDEN_TICKETS]   # 20 inputs
    assert sum(s >= 0.7 for s in scores) / len(scores) >= 0.80
💬 What it does: Layer A is a normal mock-based unit test. Layer B replaces == with a graded, statistical assertion: score many outputs against a rubric and require the rate to clear a bar. One sloppy answer doesn’t fail the build — a degraded model does.

⚖️ What’s an LLM-as-judge?

▼
  • For rubric items a keyword check can’t score (“is the tone professional?”, “does the answer actually address the question?”), you ask another model to grade the output — a second, softer gate.
  • It’s powerful but not free: the judge itself can be wrong, so you spot-check the judge against human labels and keep the cheap keyword checks for anything they can cover.
  • The grader — keyword or judge — is code, so it gets ordinary unit tests: pin it on a known-good and a known-bad output. Your deterministic skills supervise the new layer.

Your team ships “AI reply suggestions.” How should CI guard the feature?

Two layers, two tools.
  • The deterministic plumbing (prompt build, parse, fallback) gets fast mocked unit tests on every commit; the model’s quality gets a graded eval on a golden set, nightly.
  • Exact-string asserts break on every model update even when quality is fine — brittle and meaningless.
  • Humans-only doesn’t scale to every commit and drifts between reviewers; use them to calibrate the rubric/judge, not as the gate.

The feature — note the LLM is injected, so a test can pass a fake one:

# the feature: an LLM is INJECTED, so tests can swap it
def suggest_reply(llm, ticket) -> str:
    prompt = build_prompt(ticket)          # our code
    raw = llm.complete(prompt)             # the model
    return sanitize(raw)                    # our code: strip PII, truncate, tone

Job 1 — Layer A, on every PR (blocks merge). Mock the model; test your code:

# runs on EVERY commit — LLM mocked, so it's deterministic, fast, free
def test_suggest_reply_strips_pii_and_truncates():
    llm = Mock()
    llm.complete.return_value = "Sure, call me at 555-1234! " * 20   # long + PII
    out = suggest_reply(llm, a_ticket)
    assert "555-1234" not in out          # sanitize() removed the phone number
    assert len(out) <= 280                # and truncated
# NOTE: this tests OUR code (prompt build + sanitize), never the model's words

Job 2 — Layer B, nightly. Real model, rubric-graded, gate on the pass rate:

# runs NIGHTLY — real model, graded against a golden set
GOLDEN = load_cases("golden_tickets.jsonl")   # ~50 representative tickets

def grade(reply, case) -> float:              # the rubric, 0..1
    checks = [
        case.intent in reply.lower(),         # did it address the ask?
        len(reply.split()) <= 60,             # concise?
        judge_is_polite(reply),               # tone — an LLM-as-judge call
    ]
    return sum(checks) / len(checks)

def test_reply_quality_on_the_golden_set():
    scores = [grade(suggest_reply(real_llm, c.ticket), c) for c in GOLDEN]
    pass_rate = sum(s >= 0.7 for s in scores) / len(scores)
    assert pass_rate >= 0.85, f"quality dropped to {pass_rate:.0%}"
💬 Why this split works:
  • Job 1 is a normal unit test — fast, free, deterministic — so it runs on every commit and blocks a merge that breaks the prompt-building or sanitising. It never asserts the model’s wording.
  • Job 2 measures quality the only way you can when there’s no single right answer: many real outputs, each scored 0..1 against a rubric, and a threshold on the rate. One weak reply doesn’t fail the build; a drop in the rate does — catching a bad prompt tweak or a model version bump.
  • It runs nightly, not per-commit, because real model calls cost money and time; track the pass rate over days to spot slow regressions.
  • The grader is code — grade() and judge_is_polite() get their own unit tests (pin them on a known-good and known-bad reply), so you trust the gate.
