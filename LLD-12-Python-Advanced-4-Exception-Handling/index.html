Quiz 1: What happens when this Django view runs?

views.py
▼

Correct! .get() raises Model.DoesNotExist when no matching row exists. Without try/except, Django returns a 500 error to the user — showing the full traceback in DEBUG mode.

Quiz 2: When does the else block run?

try/except/else/finally
▼
try:
    dish = MenuItem.objects.get(id=dish_id)
except MenuItem.DoesNotExist:
    print("Not found!")
else:
    print("Found it!")   # when does this run?
finally:
    print("Always runs")
Correct! The else block runs only when the try block completes without raising any exception. It lets you separate "happy path" code from the try block, keeping the try block minimal.

Quiz 5: What does each one do?

map, filter, reduce
▼
nums = [1, 2, 3, 4, 5]

a = list(map(lambda x: x * 10, nums))
b = list(filter(lambda x: x > 3, nums))
c = reduce(lambda acc, x: acc + x, nums)
Correct! map transforms every element (×10). filter keeps only elements where the condition is True (>3 keeps 4,5). reduce combines all elements into one value (1+2+3+4+5=15, not 120 which would be product).

Order Matters — Specific Before General

Quiz 6: What gets printed when a KeyError is raised?

config = {}

try:
    host = config["database"]
except Exception as e:
    print("A: caught by Exception")
except KeyError as e:
    print("B: caught by KeyError")
"A: caught by Exception" prints. Python checks except blocks top to bottom and stops at the first match. Since KeyError is a subclass of Exception, the except Exception block catches it first — the except KeyError below it never runs.

Fix: always put specific exceptions first: 
try:
    host = config["database"]
except KeyError as e:        # specific first ✓
    print(f"Missing key: {e}")
except Exception as e:      # general last (catch-all) ✓
    print(f"Unexpected: {e}")
Custom Exceptions

Build Your Own

When ValueError means ten different things, it's time to create your own exception classes.

Problem: Your app raises ValueError("Insufficient stock") in one place and ValueError("Invalid email") in another. How does the caller tell them apart? Parsing the string message? That's fragile.

1 The Simplest Custom Exception

simple custom exception
▼
class PaymentError(Exception):
    """Base exception for all payment-related errors."""
    pass

2 Build a Hierarchy with Data

payment exception hierarchy
▼
class PaymentError(Exception):
    """Base for payment errors."""
    pass

class InsufficientFundsError(PaymentError):
    """Raised when account balance is too low."""
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        self.deficit = amount - balance
        super().__init__(
            f"Cannot charge ${amount}. Balance: ${balance} (short ${self.deficit})"
        )

class PaymentGatewayError(PaymentError):
    """Raised when the payment gateway is unreachable."""
    def __init__(self, gateway_name, status_code):
        self.gateway_name = gateway_name
        self.status_code = status_code
        super().__init__(
            f"Gateway '{gateway_name}' returned status {status_code}"
        )

3 Using It — Catching the Parent Catches All Children

catching custom exceptions
▼
def process_payment(user, amount):
    if user.balance < amount:
        raise InsufficientFundsError(user.balance, amount)

try:
    process_payment(user, 150.00)
except InsufficientFundsError as e:
    print(f"Short by ${e.deficit}. Top up?")  # access structured data!
except PaymentError as e:
    print(f"Payment failed: {e}")            # catches any PaymentError subclass

Hierarchy Visual

Exception
↓
PaymentError
↓ ↓
InsufficientFundsErrorbalance, amount, deficit
PaymentGatewayErrorgateway_name, status_code
Catching PaymentError catches BOTH children. Data attributes let callers react specifically.

Quiz 8: You write except PaymentError. Will it catch InsufficientFundsError?

Correct! Since InsufficientFundsError inherits from PaymentError, catching the parent catches all children. This is the power of exception hierarchies — catch broadly or narrowly as needed.
Context Managers

The with Statement

Guarantee cleanup happens even when exceptions blow up your code.

Problem: What happens when an exception occurs between open() and close()? The file handle leaks.

1 The Bug — Forgetting to Close

BUG: File Never Closed

broken
▼
f = open("data.csv")
data = f.read()
process(data)  # if this crashes...
f.close()       # ...this never runs!

FIX: with Statement

correct
▼
with open("data.csv") as f:
    data = f.read()
    process(data)
# f.close() called automatically
# even if process() crashes!

2 How It Works: __enter__ and __exit__

custom context manager (class-based)
▼
class DatabaseConnection:
    def __init__(self, db_url):
        self.db_url = db_url
        self.connection = None

    def __enter__(self):
        print("Connecting...")
        self.connection = connect(self.db_url)
        return self.connection  # this becomes the 'as' variable

    def __exit__(self, exc_type, exc_val, exc_tb):
        print("Closing connection...")
        self.connection.close()    # ALWAYS runs, even on exception
        return False               # don't suppress the exception

# Usage:
with DatabaseConnection("postgres://...") as conn:
    conn.execute("SELECT * FROM menu")
# connection is closed here, no matter what
Key Point: __enter__ runs at the start of the with block and returns the value for as. __exit__ runs at the end — even if an exception was raised. If __exit__ returns True, the exception is suppressed.

3 contextlib.suppress — Silencing Expected Exceptions

suppress()
▼
from contextlib import suppress

# Instead of:
try:
    os.remove("temp.log")
except FileNotFoundError:
    pass

# Write:
with suppress(FileNotFoundError):
    os.remove("temp.log")  # no crash if file doesn't exist

Quiz 9: What does __exit__ do in a context manager?

Correct! __exit__ is the cleanup method. It always runs when the with block finishes — whether it completed normally or an exception was raised. It receives the exception info (or None) and can choose to suppress it by returning True.
Exception Chaining

raise X from Y

When you catch one exception and raise another, keep the original cause visible.

Problem: You catch a ConnectionError from the database and raise UserNotFoundError. Now a developer debugging sees UserNotFoundError but has no idea it was caused by a connection problem.

1 Without Chaining — Cause is Lost

cause lost
▼
def get_user(user_id):
    try:
        return db.query(f"SELECT * FROM users WHERE id = {user_id}")
    except ConnectionError:
        raise UserNotFoundError(f"User {user_id} not found")
        # Original ConnectionError is shown in traceback as
        # "During handling of the above exception, another exception occurred"
        # but it's an implicit chain, and misleading

2 With Chaining — raise X from Y

explicit chaining
▼
def get_user(user_id):
    try:
        return db.query(f"SELECT * FROM users WHERE id = {user_id}")
    except ConnectionError as original_error:
        raise UserNotFoundError(f"User {user_id} not found") from original_error

When this crashes, Python prints a traceback — a full report of what went wrong and where. Here's what it looks like:

What Python prints when this crashes (the traceback)
▼
# Python prints this error report (called a "traceback"):

Traceback (most recent call last):        # ← "here's what happened"
  File "app.py", line 4, in get_user
    return db.query(...)
ConnectionError: database connection refused  # ← original error

The above exception was the direct cause of the following exception:

Traceback (most recent call last):        # ← "which caused this"
  File "app.py", line 10, in <module>
    user = get_user(42)
  File "app.py", line 6, in get_user
    raise UserNotFoundError(...) from original_error
UserNotFoundError: User 42 not found       # ← new error you raised
What is a traceback? It's Python's error report — printed when an unhandled exception crashes your program. It shows:
• Which file and line the error happened on
• The call chain — which function called which (bottom = where it crashed)
• The exception type and message

With raise X from Y, the traceback shows both exceptions linked together — so when you're debugging at 2am, you see the real cause (ConnectionError) not just the symptom (UserNotFoundError).

3 Suppress the Chain: from None

from None
▼
def parse_config(raw):
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        raise ConfigError("Invalid config format") from None

4 Accessing the Cause Programmatically

__cause__ attribute
▼
try:
    get_user(42)
except UserNotFoundError as e:
    print(f"Error: {e}")

        print(f"Root cause: {e.__cause__}")

Quiz 10: What does raise AppError("msg") from original do?

Correct! raise X from Y sets X.__cause__ = Y. The traceback explicitly says "The above exception was the direct cause of the following exception" — giving debuggers full context.
EAFP vs LBYL

Two Philosophies of Error Handling

Should you check first, or just try and handle failure?

EAFP = Easier to Ask Forgiveness than Permission — "just do it, handle the error if it happens"
LBYL = Look Before You Leap — "check everything before doing it"

At a glance

Example 1: Dictionary access

LBYL

Check first
▼
if "name" in user_dict:
    name = user_dict["name"]
else:
    name = "Unknown"

EAFP

Try it
▼
try:
    name = user_dict["name"]
except KeyError:
    name = "Unknown"
Best of both worlds: For dict access, use user_dict.get("name", "Unknown") — clean and no exception overhead.

Example 2: Converting user input to int

LBYL

Check first
▼
user_input = "42abc"

if user_input.isdigit():
    age = int(user_input)
else:
    age = 0

# Problem: isdigit() doesn't handle
# "-5" or "3.14" correctly

EAFP

Try it
▼
user_input = "42abc"

try:
    age = int(user_input)
except ValueError:
    age = 0

# Handles everything: "abc", "-5",
# "3.14", "" — all caught cleanly

Example 3: Accessing a list index

LBYL

Check first
▼
items = ["a", "b", "c"]
index = 5

if index < len(items):
    val = items[index]
else:
    val = None

EAFP

Try it
▼
items = ["a", "b", "c"]
index = 5

try:
    val = items[index]
except IndexError:
    val = None

Example 4: File access — LBYL has a race condition!

LBYL — Race Condition Bug

LBYL race condition
▼
import os

if os.path.exists("data.csv"):
    # Another process deletes
    # the file RIGHT HERE!
    f = open("data.csv")  # BOOM!

EAFP — No Race Condition

EAFP safe
▼
try:
    f = open("data.csv")
except FileNotFoundError:
    print("File not found")
# No gap between check and use
TOCTOU Bug: "Time Of Check vs Time Of Use" — between checking os.path.exists() and calling open(), another process can delete the file. EAFP eliminates this race condition entirely.

Example 5: Accessing an object attribute

LBYL

Check first
▼
if hasattr(user, "email"):
    email = user.email
else:
    email = "no-email@example.com"

EAFP

Try it
▼
try:
    email = user.email
except AttributeError:
    email = "no-email@example.com"

Quiz 11: Which approach is considered more "Pythonic"?

Correct! EAFP is the Pythonic idiom. Python exceptions are fast (C-level), and EAFP avoids race conditions. The official Python glossary explicitly says: "This clean and fast style is characterized by the presence of many try and except statements."

1 gettext_lazy for Translatable Strings

translatable exception
▼
from django.utils.translation import gettext_lazy as _

class AppError(Exception):
    """Base exception with i18n and API-friendly output."""
    def __init__(self, message, error_code=None, status_code=400):
        self.message = message          # translatable string
        self.error_code = error_code    # machine-readable code
        self.status_code = status_code  # HTTP status
        super().__init__(str(message))

    def to_dict(self):
        return {
            "error": str(self.message),
            "error_code": self.error_code,
            "status": self.status_code,
        }

2 Using It with Translatable Messages

InsufficientStockError with i18n

class InsufficientStockError(AppError):
    def __init__(self, available, requested):
        self.available = available
        self.requested = requested
        message = _(
            "Only %(available)s items in stock. You requested %(requested)s."
        ) % {"available": available, "requested": requested}
        super().__init__(
            message=message,
            error_code="INSUFFICIENT_STOCK",
            status_code=400,
        )

Copy Semantics

Shallow vs Deep Copy

Assignment is NOT copying. Understand the difference or debug mysterious shared-state bugs forever.

Question: If you write b = a and then modify b, does a change too? Sometimes yes, sometimes no. Why?

1 Assignment is NOT Copying

assignment = same object
▼
a = [1, 2, 3]
b = a             # b is NOT a copy — it's the SAME list

b.append(99)
print(a)           # [1, 2, 3, 99]  — a changed too!
print(a is b)      # True — same object in memory

Assignment: Two Names, One Object

a
→
[1, 2, 3, 99]
←
b
Both variables point to the exact same list object in memory.

2 So how DO you make a real copy?

Use .copy() or list() — this creates a new, independent list:

.copy() creates a new object
▼
a = [1, 2, 3]
b = a.copy()        # or: b = list(a)

b.append(99)
print(a)             # [1, 2, 3]     — original is SAFE!
print(b)             # [1, 2, 3, 99] — only b changed
print(a is b)        # False — two separate objects
Great, problem solved? For simple (flat) lists — yes. But what happens when there's a list inside a list?

3 The surprise — objects inside objects

This is where it gets tricky. .copy() creates a new outer object, but the things inside are still shared:

Wait, what?
▼
original = [[1, 2], [3, 4]]
copied = original.copy()

# Outer list IS separate:
print(original is copied)       # False ✓

# But inner lists are SHARED:
print(original[0] is copied[0]) # True ← same object!

# So if you modify the inner list through one...
copied[0].append(99)
print(original[0])               # [1, 2, 99] ← original changed too!
This is called a "shallow copy". It copies the container (the outer list), but the items inside are still the same objects. Think of it like photocopying a folder of documents — you get a new folder, but the documents inside are the same sheets of paper.

Shallow Copy: New Folder, Same Documents

→

↓ ↓
[1, 2, 99]
[3, 4]
↑ ↑
copied
→
[ref, ref]
Different outer lists, but both point to the SAME inner lists.

4 Real bug: Shopping cart duplication

Here's a practical scenario where shallow copy creates a nasty bug:

The bug: customer carts leak into each other
▼
# A "template" cart with default items
default_cart = {
    "items": [{"name": "Welcome Drink", "qty": 1}],
    "discount": 0,
}

# Give each new customer a copy of the template
cart_a = default_cart.copy()     # shallow copy!
cart_b = default_cart.copy()

# Customer A adds Paneer Tikka
cart_a["items"].append({"name": "Paneer Tikka", "qty": 2})

# Customer B checks their cart...
print(cart_b["items"])
# [{'name': 'Welcome Drink', 'qty': 1}, {'name': 'Paneer Tikka', 'qty': 2}]
# BUG! Customer B sees Customer A's Paneer Tikka!

# Fix: use copy.deepcopy(default_cart) instead

5 Deep Copy — Completely Independent

deep copy
▼
import copy

original = [[1, 2], [3, 4]]
deep = copy.deepcopy(original)

deep[0].append(99)
print(original[0])  # [1, 2] — original is UNAFFECTED!
print(deep[0])      # [1, 2, 99] — completely independent

quiz
▼
original = [[1, 2], [3, 4]]

shallow[0].append(99)
Correct! .copy() creates a shallow copy. The outer list is new, but the inner lists are shared references. When you append(99) to the inner list via shallow[0], original[0] sees it too because they point to the same inner list.

6 Copy with Objects

Student with shared grades
▼
import copy

class Student:
    def __init__(self, name, grades):
        self.name = name
        self.grades = grades   # mutable list!

alice = Student("Alice", [90, 85, 92])

# Shallow copy:
clone = copy.copy(alice)
clone.grades.append(100)
print(alice.grades)   # [90, 85, 92, 100] — SHARED!

# Deep copy:
clone2 = copy.deepcopy(alice)
clone2.grades.append(50)
print(alice.grades)   # [90, 85, 92, 100] — unaffected

7 Custom __copy__ and __deepcopy__

custom copy behavior
▼
import copy

class CachedConfig:
    def __init__(self, settings, cache=None):
        self.settings = settings    # should be copied
        self._cache = cache or {}   # should NOT be copied

    def __copy__(self):
        # Shallow copy settings, but start with fresh cache
        return CachedConfig(self.settings.copy(), cache={})

    def __deepcopy__(self, memo):
        # Deep copy settings, fresh cache
        return CachedConfig(
            copy.deepcopy(self.settings, memo),
            cache={},
        )

Best Practices

DO and DON'T

Rules that will save you from common exception handling mistakes.

DON'T

  • Write bare except:
  • Catch Exception and silently pass
  • Use exceptions for normal flow control
  • Put too much code inside try blocks
  • Raise generic Exception("msg")
  • Lose the original cause when re-raising
  • Forget to close resources (files, connections)

DO

  • Catch specific exception types
  • Log errors, then handle or re-raise
  • Use EAFP for Pythonic patterns
  • Keep try blocks minimal
  • Create custom exception hierarchies
  • Use raise X from Y to preserve cause
  • Use with statements for resource cleanup

Decision Table

Situation Use
Opening files, DB connections, lockswith statement (context manager)
Multiple related error typesCustom exception hierarchy
Dict key might not existdict.get(key, default)
File might not existEAFP: try/except FileNotFoundError
Catching and re-raising different errorraise NewError from original
Ignoring an expected exceptioncontextlib.suppress()

Interview Summary: Python uses an exception hierarchy rooted at BaseException. Always catch Exception, never bare except. Use custom exceptions with data attributes for structured error handling. Context managers guarantee cleanup via __enter__/__exit__. EAFP is more Pythonic than LBYL and avoids TOCTOU race conditions. Use raise X from Y to chain exceptions. Quiz 14: You catch an exception and want to log it, then re-raise without changing the traceback. What do you write?

Correct! A bare raise inside an except block re-raises the current exception with its original traceback intact. raise Exception(e) would create a NEW exception and lose the original traceback.
