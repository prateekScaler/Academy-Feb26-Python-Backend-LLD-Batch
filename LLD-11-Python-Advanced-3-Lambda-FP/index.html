LLD-11 • Python Advanced-3

Functions are objects. Once you see that, lambda, map, filter, closures, and decorators all click.

Recap

Quick Check — Collections

Before we move on, let's make sure last class stuck.

What happens here?
▼
from collections import defaultdict

d = defaultdict(list)
d["existing"].append(1)

result = d["new_key"]
print(result)

What does d["new_key"] return?

defaultdict(list) calls list() for any missing key, which returns []. That's the whole point — no more if key not in d: d[key] = [].
deque with maxlen
▼
from collections import deque

q = deque(maxlen=3)
for i in range(1, 6):  # 1, 2, 3, 4, 5
    q.append(i)

print(q)

After appending 1, 2, 3, 4, 5 to a deque(maxlen=3), what's left?

maxlen=3 means it keeps only the last 3 items. When you append beyond capacity, items are silently dropped from the left (oldest). Perfect for sliding windows and "last N items" buffers.
Counter
▼
from collections import Counter

c = Counter("mississippi")
print(c['s'])

What is c['s']?

"mississippi" has: m=1, i=4, s=4, p=2. Counter counts every element. c.most_common(1) would return [('i', 4)] or [('s', 4)].
The Foundation

Functions Are Objects

This one idea unlocks everything else in this class. Take it slow.

What IS a function, really? In Python, a function is not some magical special thing. It's just an object — like an int, a string, or a list. You can store it, pass it, return it.

1 A function IS an object

type() proves it
▼
def greet(name):
    return f"Hello, {name}!"

print(type(greet))
# <class 'function'>

print(type(42))
# <class 'int'>

# Both are objects. Both have a type. Both live in memory.

2 Store a function in a variable

No parentheses = the function itself
▼
def greet(name):
    return f"Hello, {name}!"

say_hi = greet           # No parentheses! Storing the function object
print(say_hi("Vipul"))  # "Hello, Vipul!"

# say_hi and greet point to the SAME function object
print(say_hi is greet)  # True

What's the difference between greet and greet()?

greet is a reference to the function object in memory. greet() calls (invokes) that function and evaluates to whatever it returns. This distinction is crucial — when you pass a function to map(), sorted(key=...), etc., you pass the name without parentheses.

3 Pass a function as an argument

Higher-order function
▼
def add(a, b):
    return a + b

def subtract(a, b):
    return a - b

def apply(func, x, y):
    """Takes a function and two numbers, applies the function."""
    return func(x, y)

print(apply(add, 5, 3))       # 8
print(apply(subtract, 5, 3))  # 2

# apply() is a "higher-order function" — it takes a function as input

4 Return a function from a function

Function factory
▼
def make_greeter(greeting):
    """Returns a NEW function that uses the greeting."""
    def greeter(name):
        return f"{greeting}, {name}!"
    return greeter  # Return the function object (no parentheses!)

hello = make_greeter("Hello")
hola = make_greeter("Hola")

print(hello("Vipul"))  # "Hello, Vipul!"
print(hola("Kaarthik"))    # "Hola, Kaarthik!"

# Each call to make_greeter() creates a brand new function

💰 Another example: Discount calculator factory

▼

A more practical example — imagine an e-commerce site where different user tiers get different discounts:

Function that creates discount functions
▼
def make_discount(percent):
    """Returns a function that applies the given discount."""
    def apply_discount(price):
        return price * (1 - percent / 100)
    return apply_discount

# Create specific discount functions
student_discount = make_discount(10)   # 10% off
premium_discount = make_discount(25)   # 25% off
employee_discount = make_discount(40)  # 40% off

price = 1000
print(student_discount(price))   # 900.0
print(premium_discount(price))   # 750.0
print(employee_discount(price))  # 600.0

# Each function "remembers" its own percent value
# We created 3 functions from 1 factory — no code duplication!
This is WHY lambda, map, filter, decorators, and closures work. They all depend on one fact: functions are objects you can store, pass, and return. Everything in the rest of this class builds on these 4 steps.
Anonymous Functions

Lambda — A Function Without a Name

Sometimes you need a tiny function for just one line. Lambda gives you that.

Problem: You want to sort a list of dicts by age. You need a function that extracts the age. Do you really need a whole def for return person["age"]?

def vs lambda — side by side

Regular def

2 lines
▼
def double(x):
    return x * 2

print(double(5))  # 10

Lambda equivalent

1 expression
▼
double = lambda x: x * 2

print(double(5))  # 10

Building the syntax step by step

Lambda variations
▼
# One parameter
lambda x: x * 2
# "given x, return x * 2"

# Two parameters
lambda a, b: a + b
# "given a and b, return a + b"

# No parameters
lambda: 3.14
# "takes nothing, returns 3.14"

# With a ternary (conditional)
lambda x: "even" if x % 2 == 0 else "odd"
# "given x, return 'even' or 'odd'"
Lambda syntax breakdown
lambdakeyword
x, yparameters
:separator
x + yexpression (returned)
No return keyword. No function name. One expression only.

What's wrong with this code?

# Is this good Python?
double = lambda x: x * 2
print(double(5))  # 10
PEP 8 says: don't assign a lambda to a variable. Lambda is for anonymous, inline use (inside sorted(), map(), etc.). If you're giving it a name, you've just made a worse def — no docstring, no name in tracebacks.

The correct way: 
# Instead of: double = lambda x: x * 2
# Write:
def double(x):
    return x * 2

print(double(5))  # 10 — same result, better practice

Where lambda actually shines

1. Sorting by a key

Lambda (concise)

One-liner
▼
students = [
    {"name": "Vipul", "age": 22},
    {"name": "Kaarthik", "age": 20},
    {"name": "Ajit", "age": 25},
]

sorted(students, key=lambda s: s["age"])
# Kaarthik(20), Vipul(22), Ajit(25)

Without lambda

More code for same result
▼
def get_age(student):
    return student["age"]

sorted(students, key=get_age)
# Same result — but we created a whole
# function just to extract one field

2. Finding max/min by a key

Lambda (concise)

Quick inline
▼
oldest = max(students, key=lambda s: s["age"])
# {'name': 'Ajit', 'age': 25}

shortest_name = min(students, key=lambda s: len(s["name"]))
# {'name': 'Ajit', 'age': 25}  (4 chars)

Without lambda

Verbose alternative
▼
def get_age(student):
    return student["age"]

def get_name_length(student):
    return len(student["name"])

oldest = max(students, key=get_age)
shortest_name = min(students, key=get_name_length)
# 2 extra functions just for one-time use

3. Dictionary of operations (mini calculator)

Lambda (concise)

Compact dispatch table
▼
ops = {
    "+": lambda a, b: a + b,
    "-": lambda a, b: a - b,
    "*": lambda a, b: a * b,
}
print(ops["+"](3, 4))  # 7

OOP approach

Class-based calculator
▼
class Calculator:
    def add(self, a, b): return a + b
    def sub(self, a, b): return a - b
    def mul(self, a, b): return a * b

    def compute(self, op, a, b):
        if op == "+": return self.add(a, b)
        if op == "-": return self.sub(a, b)
        if op == "*": return self.mul(a, b)

calc = Calculator()
print(calc.compute("+", 3, 4))  # 7
# Works, but way more code for a simple lookup

Lambda rules to remember:
• One expression only — no statements, no assignments, no loops
• No name — that's the point. Use inline with sorted(), map(), filter()
• Implicit return — the expression's value IS the return value
• Use def if: the function needs a name, docstring, multiple lines, or appears in tracebacks

You need a function to validate email addresses with regex, logging, and error messages. Lambda or def?

Use def. This function needs: a descriptive name (validate_email), multiple lines of logic, a docstring explaining the validation rules, and a clear name in error tracebacks. Lambda can only handle one expression.

You're sorting a list of tuples [(3, 'c'), (1, 'a'), (2, 'b')] by the second element. Lambda or def?

Lambda is perfect here. It's a tiny, one-expression function used inline as a key= argument. No name needed, no docstring needed, used only once. This is exactly what lambda was designed for: sorted(data, key=lambda x: x[1]).
Before We Continue

Iterable vs Iterator

You'll see the words "iterable" and "iterator" everywhere in map(), filter(), and reduce(). Let's clear this up first.

Quick question: When you write for x in [1, 2, 3], what is [1, 2, 3]? And what is Python doing behind the scenes to give you one item at a time?

Iterable = "I can be looped over"

An iterable is any object you can put after in in a for loop. It's like a book — it contains pages, and you can read through it.

These are all iterables
▼
# Lists, tuples, strings, dicts, sets, files — all iterable
for x in [1, 2, 3]:       # list ✓  → loops over elements
    pass
for x in (1, 2, 3):       # tuple ✓ → loops over elements
    pass
for ch in "hello":         # string ✓ → loops over each character
    pass

# Yes, dict and set are iterable too!
d = {"name": "Vipul", "psp": 85}
for k in d:               # dict ✓  → loops over KEYS ("name", "psp")
    pass
for k, v in d.items():   # dict.items() → loops over (key, value) pairs
    pass

s = {10, 20, 30}
for x in s:               # set ✓   → loops over elements (unordered!)
    pass

for n in range(5):        # range ✓ → loops over 0, 1, 2, 3, 4
    pass

# An iterable knows HOW to create an iterator
# Think: "I'm a book — ask me and I'll give you a bookmark"

Which of these can you NOT loop over with for x in ...?

42 is not iterable. If you try for x in 42, Python raises TypeError: 'int' object is not iterable.

Not iterable (you CANNOT loop over these): 
for x in 42:         # ✗ int — it's a single value, not a collection
for x in 3.14:       # ✗ float — same reason
for x in True:       # ✗ bool — True/False are single values
for x in None:       # ✗ NoneType — "nothing" can't be looped
for x in len:        # ✗ function — it's callable, not iterable

# All of these raise: TypeError: '...' object is not iterable
# Rule of thumb: if it's a SINGLE value (not a collection),
# you can't loop over it.

Iterator = "I am looping — and I remember where I am"

An iterator is the object that actually does the work of producing values one at a time. It's the bookmark that keeps track of which page you're on.

Iterables create iterators
▼
nums = [10, 20, 30]          # This is an ITERABLE (the book)

it = iter(nums)                # This creates an ITERATOR (the bookmark)

print(next(it))               # 10  — first value
print(next(it))               # 20  — remembers position, gives next
print(next(it))               # 30  — next value
print(next(it))               # StopIteration error — no more items!

# A for loop does exactly this behind the scenes:
# 1. Calls iter() on the iterable to get an iterator
# 2. Calls next() repeatedly until StopIteration
Iterable vs Iterator
Iterable[1, 2, 3], "hello", range(5)
⟶
iter()creates
⟶
Iteratorproduces values one by one
Iterable = the data source (book). Iterator = the cursor walking through it (bookmark).
You can create multiple iterators from one iterable — like multiple bookmarks in the same book.

Why does this matter?

map(), filter(), and range() all return iterators, not lists. That means:

Lazy = memory efficient
▼
# This does NOT create a list of 10 million numbers in memory
result = map(lambda x: x * 2, range(10_000_000))
# result is an iterator — nothing computed yet!

print(next(result))  # 0  — computes just this one
print(next(result))  # 2  — computes just this one

# To get ALL values at once, wrap in list():
# all_values = list(result)  — but careful with 10M items!

# Iterator = lazy (one at a time, saves memory)
# List     = eager (all at once, uses memory)

Which of these is an iterator (not just an iterable)?

A map object is an iterator. Lists, strings, and sets are iterables — they can produce an iterator via iter(), but they store all data in memory. A map object IS the iterator itself — it computes values lazily, one at a time. That's why you need list() to see all values: list(map(...)).
TL;DR: An iterable is anything you can loop over (list, str, dict, range). An iterator is the lazy worker that gives you values one at a time (map(), filter(), iter() result). Iterators save memory because they don't store everything upfront. When you see map() and filter() returning iterators — now you know why.

📚 A bit of history: map/filter vs comprehensions

▼
WhatAdded inOrigin
map(), filter(), lambdaPython 1.0 (1994)Borrowed from Lisp / functional programming languages
reduce()Python 1.0 (1994)Also from Lisp — was a built-in until Python 3
List comprehensionsPython 2.0 (2000)Inspired by Haskell — more readable for Python's style
Generator expressionsPython 2.4 (2004)Lazy version of list comprehensions: (x for x in ...)
Dict/set comprehensionsPython 2.7 / 3.0Extended comprehension syntax to dicts and sets

So map() and filter() came 6 years before comprehensions. When comprehensions arrived in Python 2.0, they quickly became the preferred way to do most transformations because they're more readable.

Then why do map/filter still exist?

Great question. Guido van Rossum (Python's creator) actually wanted to remove map(), filter(), reduce(), and lambda from Python 3. He argued comprehensions made them redundant. But the community pushed back hard. Here's what survived and why:

Kept as built-ins
map() — cleaner than comprehension when you already have a named function: map(int, strings) beats [int(s) for s in strings]

filter() — same reason: filter(str.isdigit, chars) is clean

lambda — too useful for key= arguments in sorted(), max(), etc.
Demoted to functools
reduce() — moved to functools.reduce() in Python 3. Guido argued it's rarely needed since sum(), max(), min(), ''.join() cover 90% of use cases. Making it an import signals: "think twice before using this."
Bottom line: Comprehensions are the Pythonic default for 90% of cases. But map()/filter() earn their place when you already have a named function, and lambda is essential for inline key= arguments. They're not competing tools — they complement each other.

Problem: You have prices in dollars: [10, 20, 30, 40]. Convert them all to euros (multiply by 0.85). How many ways can you do it?

Approach 1: for loop

The explicit way
▼
prices = [10, 20, 30, 40]
euros = []
for p in prices:
    euros.append(p * 0.85)
# [8.5, 17.0, 25.5, 34.0]

Approach 2: list comprehension

Pythonic
▼
euros = [p * 0.85 for p in prices]
# [8.5, 17.0, 25.5, 34.0]
What is a list comprehension? It's Python's shortcut for "build a new list by transforming each item": [expression for item in iterable]. It reads like English: "give me p * 0.85 for each p in prices". Comprehensions are considered more Pythonic (idiomatic Python) than map() because they're easier to read at a glance.

Approach 3: map()

Functional style
▼
euros = list(map(lambda p: p * 0.85, prices))
# [8.5, 17.0, 25.5, 34.0]

📚 What is an Iterator?

▼

An iterator is an object that produces values one at a time, on demand — instead of storing everything in memory at once.

You already use iterators without realizing it:

Iterators you already know
▼
# range() is an iterator — it doesn't create a list of 1 million numbers
for i in range(1_000_000):  # generates one number at a time
    pass

# file reading is an iterator — reads one line at a time
for line in open("data.txt"):  # doesn't load entire file into memory
    pass

# enumerate() is an iterator
for i, val in enumerate(["a", "b", "c"]):
    pass

# map() and filter() also return iterators!

Why lazy? Imagine processing 10 million rows from a database. A list loads ALL 10M rows into memory. An iterator processes them one at a time — constant memory, no matter the size.

map() returns...

map() is lazy. It returns a map object (an iterator). Values are computed one at a time, on demand. Wrap in list() to get all values at once. This laziness saves memory for large datasets.

🌡️ map() with a named function — to_celsius

▼
Named function with map
▼
def to_celsius(f):
    return (f - 32) * 5 / 9

fahrenheit = [32, 72, 100, 212]
celsius = list(map(to_celsius, fahrenheit))
# [0.0, 22.22, 37.78, 100.0]

# When the function already exists and has a name,
# map(to_celsius, data) reads better than a lambda.
map vs comprehension — comprehension usually wins in Python.

Comprehensions are more readable, more Pythonic (meaning: they follow Python's philosophy of "readability counts"), and just as fast.

Use map() when:
• You already have a named function: map(str.upper, words) — cleaner than [s.upper() for s in words]
• You're chaining with other FP tools
• You want lazy evaluation without writing a generator expression

Use comprehension when:
• The transformation is a simple expression
• You also need filtering: [x*2 for x in nums if x > 0]
• You want readability (90% of cases)

🎓 Real-world: Filter students by PSP (Problem Solving Points)

▼
Strong performers
▼
students = [
    {"name": "Vipul", "psp": 85},
    {"name": "Gobi", "psp": 45},
    {"name": "Kaarthik", "psp": 92},
    {"name": "Ajit", "psp": 38},
]

Which is more readable for "get names of students with PSP >= 70"?

# Option B: comprehension
[s["name"] for s in students if s["psp"] >= 70]
Comprehensions win for readability. The chained map(lambda, filter(lambda, ...)) reads inside-out and requires two lambdas. The comprehension reads left-to-right: "give me name for each student if PSP >= 70". Guido van Rossum himself prefers comprehensions over map/filter.

reduce() — Combine Into One

Take a list of things, boil them down to a single value.

Syntax: reduce(function, iterable[, initial])
Takes: a function with two parameters (accumulator, current_item), an iterable, and an optional initial value
Returns: a single value — the final accumulated result
What it does: applies the function cumulatively — takes first two items, combines them, then combines result with next item, and so on
Import: from functools import reduce — it's NOT a built-in

reduce examples

from functools import reduce

# Sum
reduce(lambda acc, x: acc + x, [1, 2, 3, 4, 5])
# 15  (but just use sum()!)

# Product
reduce(lambda acc, x: acc * x, [1, 2, 3, 4, 5])
# 120

# Find max (manually)
reduce(lambda acc, x: acc if acc > x else x, [3, 7, 2, 9, 1])
# 9  (but just use max()!)

# Flatten nested lists
reduce(lambda acc, x: acc + x, [[1,2], [3,4], [5,6]])
# [1, 2, 3, 4, 5, 6]

reduce(lambda acc, x: acc * x, [1, 2, 3, 4, 5]) = ?

1 * 2 = 2, 2 * 3 = 6, 6 * 4 = 24, 24 * 5 = 120. It's 5 factorial. reduce applies the function cumulatively, using the result of each step as the accumulator for the next.
Note: reduce is in functools, not built-in. Guido van Rossum moved it out of built-ins because Python has better alternatives for most cases: sum(), max(), min(), math.prod(), "".join(). Use reduce only when no built-in does what you need.

Functions That Remember

Closures

When a function remembers variables from its enclosing scope, even after that scope is gone.

Question: In make_greeter("Hello"), the parameter "Hello" should vanish when make_greeter finishes. But the returned function still uses it. How?

1 Inner function accesses outer variable

Just scope rules
▼
def outer():
    message = "Hello"  # outer variable

    def inner():
        print(message)   # inner accesses it — normal scope rules

    inner()  # "Hello"

outer()

2 Return the inner function — it REMEMBERS

This is a closure
▼
def make_greeter(greeting):
    def greeter(name):
        return f"{greeting}, {name}!"  # "greeting" comes from outer scope
    return greeter  # Return the function. outer scope is now "gone".

hello = make_greeter("Hello")
# make_greeter has finished executing.
# But "hello" still remembers greeting = "Hello"!

print(hello("Vipul"))  # "Hello, Vipul!"
print(hello("Kaarthik"))    # "Hello, Kaarthik!"

3 Each closure has its own state

make_counter — private state
▼
def make_counter(start=0):
    count = [start]  # Use a list so inner function can modify it

    def counter():
        count[0] += 1
        return count[0]

    return counter

c1 = make_counter()
c2 = make_counter(100)

print(c1())  # 1
print(c1())  # 2
print(c2())  # 101
print(c1())  # 3 — c1 and c2 are independent!

4 Closures with lambda

make_multiplier
▼
def make_multiplier(factor):
    return lambda x: x * factor  # lambda closes over "factor"

double = make_multiplier(2)
triple = make_multiplier(3)

print(double(5))  # 10
print(triple(5))  # 15

After hello = make_greeter("Hello"), what does hello("Vipul") return?

Closures remember. Even though make_greeter has finished executing, the inner greeter function holds a reference to greeting = "Hello". Python keeps the variable alive as long as the closure exists. This is called a "closure" because the function "closes over" the variable.

THE GOTCHA: Lambda in a Loop

Bug: [4, 4, 4, 4, 4]

What you'd expect to work
▼
funcs = []
for i in range(5):
    funcs.append(lambda: i)

# You'd expect [0, 1, 2, 3, 4]
print([f() for f in funcs])
# [4, 4, 4, 4, 4]  ← BUG!

Fix: capture the value

Default argument trick
▼
funcs = []
for i in range(5):
    funcs.append(lambda i=i: i)
    #                 ^^^ capture current value!

print([f() for f in funcs])
# [0, 1, 2, 3, 4]  ← CORRECT
Lambda captures the VARIABLE, not the VALUE. All 5 lambdas share the same variable i. By the time you call them, the loop is done and i = 4. The fix: lambda i=i: i evaluates i at definition time and stores it as a default argument. This is a classic Python interview gotcha.
Closures in Disguise

Decorators Preview

Decorators are just closures with syntactic sugar. Once you see it, they're not magic anymore.

Problem: You want to measure how long a function takes. You could add timing code inside every function... or you could wrap the function.

1 A function that wraps another function

timer decorator (manual)
▼
import time

def timer(func):
    """Takes a function, returns a new function that times it."""
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)   # Call the original
        end = time.time()
        print(f"{func.__name__} took {end - start:.4f}s")
        return result
    return wrapper

def calculate():
    return sum(range(1_000_000))

# Manually wrap it:
calculate = timer(calculate)
calculate()
# "calculate took 0.0312s"

2 @timer is just syntactic sugar

The @ syntax
▼
@timer                   # This is identical to: calculate = timer(calculate)
def calculate():
    return sum(range(1_000_000))

calculate()
# "calculate took 0.0312s"

# @decorator is NOT magic. It's just:
# function = decorator(function)

📝 Another decorator: log_calls

▼
Logging every function call
▼
def log_calls(func):
    def wrapper(*args, **kwargs):
        print(f"Calling {func.__name__}({args}, {kwargs})")
        result = func(*args, **kwargs)
        print(f"{func.__name__} returned {result}")
        return result
    return wrapper

@log_calls
def add(a, b):
    return a + b

add(3, 4)
# Calling add((3, 4), {})
# add returned 7

What is @timer equivalent to?

@timer above a function definition is shorthand for calculate = timer(calculate). The decorator receives the original function, wraps it in a new function (the closure), and the name calculate now points to the wrapper. When you call calculate(), you're actually calling wrapper(), which calls the original inside.

Real decorators you'll use in production:
• @functools.cache — memoize expensive function calls (cache results)
• @login_required — Django: block unauthenticated users
• @app.route("/path") — Flask/FastAPI: register URL routes
• @property — make a method behave like an attribute
• @staticmethod, @classmethod — OOP method types
• @pytest.fixture — test setup/teardown

Decision Guide

FP vs OOP — When to Use Which

The same problem solved three ways. Then a guide for choosing.

Problem: Apply a 10% discount to all prices over $100 and get the total.

OOP approach
▼
class PriceCalculator:
    def __init__(self, prices):
        self.prices = prices

    def apply_discount(self, threshold=100, discount=0.10):
        return [
            p * (1 - discount) if p > threshold else p
            for p in self.prices
        ]

    def total(self):
        return sum(self.apply_discount())

calc = PriceCalculator([50, 150, 200, 80])
print(calc.total())  # 445.0
FP approach
▼
from functools import reduce

prices = [50, 150, 200, 80]

discounted = map(lambda p: p * 0.9 if p > 100 else p, prices)
total = reduce(lambda acc, p: acc + p, discounted)
print(total)  # 445.0
Pythonic approach (mix both)
▼
prices = [50, 150, 200, 80]

total = sum(p * 0.9 if p > 100 else p for p in prices)
print(total)  # 445.0

📈 Example 3: Process sales data — filter, transform, aggregate

▼
Data
▼
sales = [
    {"product": "Laptop", "amount": 80000, "category": "electronics"},
    {"product": "Pen", "amount": 50, "category": "stationery"},
    {"product": "Phone", "amount": 45000, "category": "electronics"},
    {"product": "Notebook", "amount": 200, "category": "stationery"},
]
# Task: total revenue from electronics only

OOP

class SalesReport:
    def __init__(self, data):
        self.data = data

    def by_category(self, cat):
        return [s for s in
                self.data
                if s["category"] == cat]

    def total(self, items):
        return sum(
            s["amount"]
            for s in items)

r = SalesReport(sales)
e = r.by_category("electronics")
print(r.total(e))
# 125000

FP

from functools import reduce

reduce(
    lambda acc, s:
        acc + s["amount"],
    filter(
        lambda s:
            s["category"]
            == "electronics",
        sales
    ), 0
)
# 125000 — hard to read!

Comprehension ✅

sum(
    s["amount"]
    for s in sales
    if s["category"]
       == "electronics"
)
# 125000 — clean!
Winner: Comprehension. Data pipeline = filter + transform + aggregate. Comprehension + sum() does it in one readable expression. OOP is overkill for a one-off query. FP chain is inside-out and hard to read.

🍕 Example 4: Django-style — OOP structure + FP data transforms

▼
Best of both worlds
▼
class Restaurant:
    def __init__(self, name):
        self.name = name
        self.menu = []   # OOP: state lives in the object

    def add_dish(self, name, price, veg=False):
        self.menu.append({"name": name, "price": price, "veg": veg})

    def veg_dishes(self):
        # Comprehension inside OOP method
        return [d["name"] for d in self.menu if d["veg"]]

    def avg_price(self):
        # Generator expression inside OOP method
        return sum(d["price"] for d in self.menu) / len(self.menu)

    def sorted_menu(self):
        # Lambda inside OOP method
        return sorted(self.menu, key=lambda d: d["price"])

r = Restaurant("Scaler Bites")
r.add_dish("Paneer Tikka", 250, veg=True)
r.add_dish("Chicken Biryani", 350)
r.add_dish("Dal Makhani", 200, veg=True)

print(r.veg_dishes())     # ['Paneer Tikka', 'Dal Makhani']
print(r.avg_price())      # 266.67
print(r.sorted_menu())    # sorted by price ascending
This is Pythonic. The Restaurant class manages state (menu items). But inside the methods, we use comprehensions and lambda for data transforms. OOP for structure, FP for computation. This is exactly how Django works — OOP models + FP-style querysets.
Pythonic = mix both. Use classes for structure and state management. Use comprehensions and built-ins for data transformations. Don't force everything into one paradigm. The best Python code uses the right tool for each job.

Deep Dive

Comprehensions — The Full Picture

We've seen comprehensions beat map/filter all class. Let's master the syntax — from basic to advanced.

The anatomy of a list comprehension

Syntax breakdown
[
expressionwhat to produce
for item in iterablewhere to get data
if condition(optional filter)
]
Read it like English: "give me expression for each item in iterable if condition"

1 Basic — Transform every element

[expression for item in iterable]
▼
# Square every number
nums = [1, 2, 3, 4, 5]
squares = [n ** 2 for n in nums]
# [1, 4, 9, 16, 25]

# Convert to uppercase
names = ["vipul", "kaarthik", "ajit"]
upper = [name.upper() for name in names]
# ['VIPUL', 'KAARTHIK', 'AJIT']

# Add GST to prices
prices = [100, 250, 500]
with_gst = [p * 1.18 for p in prices]
# [118.0, 295.0, 590.0]

# Equivalent to: list(map(lambda n: n**2, nums))
# But more readable!

2 With filter — Keep only matching elements

[expression for item in iterable if condition]
▼
# Only even numbers
evens = [n for n in range(1, 11) if n % 2 == 0]
# [2, 4, 6, 8, 10]

# Students with PSP >= 70
students = [
    {"name": "Vipul", "psp": 85},
    {"name": "Gobi", "psp": 45},
    {"name": "Kaarthik", "psp": 92},
]
strong = [s["name"] for s in students if s["psp"] >= 70]
# ['Vipul', 'Kaarthik']

# Filter + transform in ONE line
# "give me name for each student if PSP >= 70"

# Equivalent to:
# list(map(lambda s: s["name"], filter(lambda s: s["psp"] >= 70, students)))
# Which one would you rather read? 😄

3 With ternary — Transform differently based on condition

Don't confuse if at the END (filter) vs if/else in the EXPRESSION (ternary).
• [x for x in nums if x > 0] — filter: keeps only positives, drops the rest
• [x if x > 0 else 0 for x in nums] — ternary: keeps ALL items, replaces negatives with 0
[expr_if_true if condition else expr_if_false for item in iterable]
▼
# Label each number
nums = [1, -3, 5, -7, 10]
labels = ["positive" if n > 0 else "negative" for n in nums]
# ['positive', 'negative', 'positive', 'negative', 'positive']

# Replace negatives with zero
cleaned = [n if n > 0 else 0 for n in nums]
# [1, 0, 5, 0, 10]

# Pass/fail based on PSP
results = [
    f"{s['name']}: Pass" if s["psp"] >= 70 else f"{s['name']}: Needs Improvement"
    for s in students
]
# ['Vipul: Pass', 'Gobi: Needs Improvement', 'Kaarthik: Pass']

What's the difference between these two?

# Version A:
[x ** 2 for x in nums if x > 0]

# Version B:
[x ** 2 if x > 0 else 0 for x in nums]
They produce different results!
For nums = [1, -3, 5, -7]:
• A: [1, 25] — only 2 items (negatives dropped)
• B: [1, 0, 25, 0] — 4 items (negatives replaced with 0)

Position of if matters: at the END = filter. In the EXPRESSION (before for) with else = ternary transform.

4 Nested loops — Multiple for clauses

[expression for x in iter1 for y in iter2]
▼
# All combinations of two lists
colors = ["red", "blue"]
sizes = ["S", "M", "L"]

combos = [f"{c}-{s}" for c in colors for s in sizes]
# ['red-S', 'red-M', 'red-L', 'blue-S', 'blue-M', 'blue-L']

# This is equivalent to:
# combos = []
# for c in colors:
#     for s in sizes:
#         combos.append(f"{c}-{s}")
Flatten a nested list
▼
# Flatten [[1,2], [3,4], [5,6]] → [1, 2, 3, 4, 5, 6]
nested = [[1, 2], [3, 4], [5, 6]]

flat = [item for sublist in nested for item in sublist]
# [1, 2, 3, 4, 5, 6]

# Read order: outer for first, then inner for
# "for each sublist in nested, for each item in sublist, give me item"

# Equivalent to:
# flat = []
# for sublist in nested:
#     for item in sublist:
#         flat.append(item)

5 Dict & Set comprehensions

Same syntax, different brackets: {} for dict/set instead of [] for list.

Dict comprehension: {key: value for item in iterable}
▼
# Student name → PSP lookup
students = [
    {"name": "Vipul", "psp": 85},
    {"name": "Kaarthik", "psp": 92},
    {"name": "Ajit", "psp": 78},
]

name_to_psp = {s["name"]: s["psp"] for s in students}
# {'Vipul': 85, 'Kaarthik': 92, 'Ajit': 78}

# With filter — only strong performers
strong_lookup = {s["name"]: s["psp"] for s in students if s["psp"] >= 80}
# {'Vipul': 85, 'Kaarthik': 92}

# Swap keys and values
psp_to_name = {v: k for k, v in name_to_psp.items()}
# {85: 'Vipul', 92: 'Kaarthik', 78: 'Ajit'}
Set comprehension: {expression for item in iterable}
▼
# Unique first letters
names = ["Vipul", "Kaarthik", "Ajit", "Gobi", "Sneha", "Kavya"]
first_letters = {name[0] for name in names}
# {'V', 'K', 'A', 'G', 'S'} — 'K' appears once even though 2 names start with K

# Unique word lengths in a sentence
sentence = "the quick brown fox jumps over the lazy dog"
lengths = {len(word) for word in sentence.split()}
# {3, 4, 5} — only unique lengths

6 Generator expression — Lazy comprehension

Replace [] with () and you get a generator — an iterator that computes values one at a time instead of building the whole list in memory.

(expression for item in iterable) — lazy!
▼
# List comprehension — builds entire list in memory
total = sum([x ** 2 for x in range(1_000_000)])  # 1M items in memory!

# Generator expression — computes one at a time
total = sum(x ** 2 for x in range(1_000_000))   # almost zero memory!
#          ^ no brackets — that makes it a generator

# Use generators when:
# 1. You're passing to sum(), max(), min(), any(), all()
# 2. You have large data and only need one pass
# 3. You don't need to index or reuse the result

Comprehension cheat sheet

Type Syntax Result
List [expr for x in iter] click to reveal
List + filter [expr for x in iter if cond] click to reveal
List + ternary [a if cond else b for x in iter] click to reveal
Nested [expr for x in iter1 for y in iter2] click to reveal
Dict {k: v for x in iter} click to reveal
Set {expr for x in iter} click to reveal
Generator (expr for x in iter) click to reveal
When NOT to use comprehensions:

• More than 2 conditions or nested loops — if you can't read it in 5 seconds, use a regular loop
• Side effects (printing, writing to file, modifying external state) — use a for loop instead
• Complex multi-step logic — break it into readable steps

# ✗ BAD — too complex, nobody can read this
result = [f(x, y) for x in a if g(x) for y in b if h(x, y) if y != x]

# ✓ GOOD — just use a loop
result = []
for x in a:
    if not g(x):
        continue
    for y in b:
        if h(x, y) and y != x:
            result.append(f(x, y))

Convert this loop to a comprehension:

result = []
for s in students:
    if s["psp"] >= 70:
        result.append(s["name"].upper())
[s["name"].upper() for s in students if s["psp"] >= 70]
Read it: "give me s["name"].upper() for each s in students if s["psp"] >= 70".
Option A is wrong because s is a dict, not a string. Option C would give a set (curly braces), not a list.

What does this produce?

{s["name"]: "Pass" if s["psp"] >= 70 else "Fail" for s in students}
{'Vipul': 'Pass', 'Gobi': 'Fail', 'Kaarthik': 'Pass'}
It's a dict comprehension (curly braces with key: value). The ternary "Pass" if psp >= 70 else "Fail" is the value expression. Each student name maps to their pass/fail status.

Key Takeaways

🛠
Functions as Objects
Functions can be stored in variables, passed as arguments, and returned from other functions. This is the foundation for everything else.
λ
Lambda
Anonymous, one-expression functions. Use inline with sorted(key=...), map(), filter(). Don't assign to a variable — use def instead.
⚙
map / filter / reduce
map transforms, filter selects, reduce combines. All return iterators (lazy). Comprehensions are usually more Pythonic.
🔒
Closures
Inner functions that remember outer variables. Each closure gets its own copy. Watch out for the loop variable gotcha (lambda i=i: i).

Decorators
@decorator = func = decorator(func). Just closures with syntactic sugar. Used everywhere: @cache, @login_required, @app.route.
