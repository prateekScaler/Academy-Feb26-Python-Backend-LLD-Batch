Step 1 — relationships first: re-derive every line before you see it drawn

From LLD-22, the one question that decides every diamond: "can the part outlive the whole — or be shared?" Pair names visible; answer out loud, then reveal. The wrong answers below are the ones that actually showed up in submissions.

Game — Board  ·  Board — Cell

▾

Ask: can this board exist after its game ends? Can a cell move to another board?

  • No, twice → Composition — filled ◆ at the owner's end; a composition chain
  • Game ◆ Board — created with the game, dies with it · multiplicity 1—1
  • Board ◆ Cell — cells never leave their board · multiplicity 1—N×N. One fact today (symbol) — the final design keeps the tiny class anyway, so tomorrow's facts have a home
  • ⚠️ Submission smell: an open diamond here implies someone else might hold the board — who?

Game — Player

▾

Ask: when this game ends, do Ajit and Vipul stop existing?

  • They outlive it → Aggregation — open ◇ at the Game end
  • Game ◇ Player — the game borrows two players; a tournament hands the same objects to the next game
  • Multiplicity: has 2 — the FR-2 guard in the constructor enforces distinct symbols
  • ⚠️ Most common submission mistake: a filled diamond here — it welds a player's lifetime to one game; tournaments become impossible

Game — WinRule  ·  BotPlayer — MoveStrategy

▾

Ask: could one KInARowRule() serve a hundred games at once?

  • Yes → Aggregation (open ◇) — for the other reason: not "outlives" but stateless & shareable
  • Game ◇ WinRule — one rule object can judge every game in the building
  • BotPlayer ◇ MoveStrategy — injected at construction, chosen by Difficulty, swappable without touching BotPlayer
  • Reading rule: the diamond always sits at the WHOLE (the borrower) — never at the part

HumanPlayer / BotPlayer → Player  ·  KInARowRule → WinRule

▾

Ask: is a HumanPlayer a kind of Player, or does it have one?

  • Is-a → the hollow triangle, always pointing at the parent
  • Solid line = inherits a class · dashed line = implements an abstract contract (realisation)
  • That's why KInARowRule's line is dashed — WinRule promises winner(board); the rule fulfils it
  • No diamonds on these lines, ever — inheritance is not ownership
  • The plug-in socket: Connect-Four and Gomoku rules dock at that dashed triangle with zero other edits

Game → GameStatus  ·  Player — Symbol

▾

Ask: does Game own a GameStatus? Does Player own its Symbol?

  • Neither needs a diamond
  • Game ⇢ GameStatus — status() returns an enum value: a dashed dependency arrow ("uses / returns"), the weakest line in UML
  • Player — Symbol — a plain attribute: enum members are shared values, not parts with a lifetime
  • Rule of thumb: diamonds manage lifetimes; enums, strings and numbers ride along as fields — ownership arrows on them is diagram noise

Step 3 — behaviours from the FRs: every FR donates a method too

Same derivation as the entities, second pass. Re-read each FR as a verb, and the question is always the same: whose job is it? Warm up on the hardest one:

Warm-up — "where does make_move() live?"

B is right. make_move() does FOUR things: validate, mutate the board, switch turn, check win/draw. Three of those are coordination — that's the Game's job. Board only knows about grid cells; it should expose place(r, c, sym) and is_full(), not the whole turn dance. Putting it on Player (C) means Player needs a reference back to Board AND turn state — circular ownership. A free function (D) shoves state into globals.

FR-1 — "an N×N board of cells" → whose behaviours?

▾
  • Board — geometry + occupancy:
    place(row, col, sym) — mutate + validate + raise
    cell(row, col) · symbol_at(row, col) — the reads
  • Cell — the smallest class in the build:
    is_empty() — one fact today; tomorrow's facts (blocked? bonus?) land HERE with a can_place() rule — that's why the final design keeps the class (the hint comment in place() marks the spot)
  • ❌ Not Game — reaching into squares it doesn't own is feature envy (the train-wreck game.board.grid[r][c])

FR-3 — "players take turns alternately" → whose behaviour?

▾
  • Game — turns are flow, flow is the orchestrator's:
    _turn stays private · current_player() is the only window
  • Why expose it at all? The UI needs "whose turn?" to prompt — nothing more
  • ❌ Not Board — it doesn't know players exist

FR-4 — "only in an empty cell inside the board" → whose behaviour?

▾
  • Board — geometry violations (occupied / out-of-bounds):
    place() raises InvalidMoveError
  • Game — flow violations (moving after the game is over):
    make_move() refuses FIRST, before touching the board
  • The contract detail the demo proves: a rejected move never flips the turn

FR-5 — "K consecutive symbols wins" → whose behaviour?

▾
  • WinRule — the open variable gets its own object:
    winner(board) → Symbol | None
  • Takes a Board, not a Game — it needs the grid, nothing else
  • Returns a Symbol, not a Player — the rule lives one abstraction below people; Game maps symbol → player

FR-6 — "board full and nobody won → draw" → whose behaviour?

▾
  • Board — states the grid fact:
    is_full() — "every square taken"
  • Game — turns facts into the verdict:
    status() → GameStatus
  • Order matters: win is checked before full — a winning ninth move is a win, not a draw

FR-7 — "human or bot, bots have difficulty" → whose behaviour?

▾
  • Player (abstract) — the contract IS the method:

  • HumanPlayer — prompts row, then column (see the CLI section)
  • BotPlayer — delegates to MoveStrategy.choose(board), picked from Difficulty at construction

FR-8 — "players can see the board after every move" → whose behaviour?

▾

  • Game — surfaces it: render() is a pass-through
  • Returns a string, prints nothing — presentation stays out of the mutation path; the engine never learns it's a CLI (the NFR)

▾

Why this is the Python version of "good packaging"

  • The module is the unit, not the class.
    • A module = one .py file = one namespace — models/player.py simply is models.player; no declaration, the path is the name
    • It holds as many related classes as cohesion allows — the whole Player family in player.py, all three enums in enums.py
    • The grouping test: "do these change together?" — Player / HumanPlayer / BotPlayer do; Board and Player don't
    • Java has no such unit — one public class per file, enforced by the compiler; twelve one-class files in Python is "Java with a Python accent" (full contrast just below ↓)
  • __init__.py makes a folder a package — and re-exporting there (from .board import Board) keeps imports short at the call site.
  • Imports read like the architecture. A reviewer opens main.py and the design is the import block: from models.board import Board; from strategies.win_rule import KInARowRule; from game import Game.
  • Circular imports are a design alarm, not a Python annoyance. If board.py needs player.py, an arrow on your diagram points the wrong way — the language just told you.
  • cli.py quarantines I/O. The engine never imports it — FR-8's "render, don't print" boundary becomes a file boundary. And HumanPlayer lives here, not in models/ — its "brain" is the console, so it's the input adapter. That's exactly how code/tictactoe/ is laid out.

Quick check — models/__init__.py contains from .board import Board. A teammate deletes that line (the file stays, empty). Which import in main.py BREAKS?

C breaks. A and B are full-path imports — they walk directly to the module file models/board.py and never need the package namespace. D imports the package object itself, which still exists. C is the short form: it reads the name Board out of the package's namespace — and that name only exists because the re-export line put it there. That's the whole job of the re-export: a curated front door. Bonus nuance: since Python 3.3, deleting __init__.py entirely still leaves A and B working (namespace packages) — so what __init__.py really buys you is the front door, an explicit "this folder is a package" signal, and a home for package docs. In an interview: keep it.

The circular-import alarm, in code

✖ The cycle — board stores people 
# models/board.py
from models.player import Player   # board needs players?!

class Board:
    def place(self, row, col, player: Player):
        self._grid[row][col] = player

# models/player.py
from models.board import Board    # players need boards

class Player:
    def choose_move(self, board: Board): ...

# ImportError: cannot import name 'Player' from
# partially initialized module 'models.player'
# (most likely due to a circular import)
✔ The fix — both depend DOWNWARD 
# enums.py — the shared vocabulary, imports nothing
class Symbol(Enum):
    X = "X"; O = "O"

# models/board.py
from enums import Symbol          # points DOWN

class Board:
    def place(self, row, col, sym: Symbol):
        ...   # stores the MARK, not the person

# models/player.py
from models.board import Board    # one direction only

class Player:
    def choose_move(self, board: Board): ...
  • What the error really says: Board storing a Player means the grid knows about people — an arrow your class diagram doesn't have. The language enforced your diagram for free.
  • The fix is always the same shape: extract what both sides need into a lower module (here: Symbol in enums.py) and point both arrows down.
  • Escape hatch, used honestly: if the cycle is only in type hints, from __future__ import annotations (or TYPE_CHECKING) dissolves it — but if you need the cycle for runtime objects, that's not a hint problem, that's the design alarm ringing. Snippet + reading below ↓

🔧 The escape hatch in code — TYPE_CHECKING

▾ 
# referee.py — needs Player ONLY in a type hint, never at runtime
from __future__ import annotations          # PEP 563: hints become strings,
                                             #   evaluated only if someone asks
from typing import TYPE_CHECKING

if TYPE_CHECKING:                            # True for mypy / your IDE,
    from models.player import Player       #   False when the program runs —
                                             #   so NO import happens at runtime

class Referee:
    def warn(self, player: Player) -> None:   # hint still checks fine
        print(player.name)                       # attribute use needs no import
  • Two tools, one job: from __future__ import annotations makes ALL hints lazy strings; the if TYPE_CHECKING: block imports only during static analysis — together, hint-only cycles simply vanish
  • The honesty test: the moment you need the import to construct or isinstance the object at runtime, the hatch doesn't apply — extract a lower module instead (the fix on the left)
  • Read more: Adam Johnson — Python type hints: how to fix circular imports · mypy docs — import cycles · PEP 563

Step 4 — APIs

Method signatures — no bodies yet

Commit to the contract before bodies bake it in. And now that the packaging is decided, the order writes itself: start with the simplest class — the leaf furthest down the tree (Cell) — write only its signatures, then climb one file at a time.

from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from enum import Enum

BOARD_SIZE = 3
WIN_LEN    = 3

class Symbol(Enum):
    X = "X"
    O = "O"

class GameStatus(Enum):
    IN_PROGRESS = "in_progress"
    WON         = "won"
    DRAW        = "draw"

class Difficulty(Enum):
    EASY = "easy"
    HARD = "hard"

class Player(ABC):
    def __init__(self, name: str, symbol: Symbol): ...
    @abstractmethod
    def choose_move(self, board: Board) -> tuple[int, int]: ...

class HumanPlayer(Player):
    def choose_move(self, board: Board) -> tuple[int, int]: ...  # prompts row, then col (ask helper)

class MoveStrategy(ABC):
    @abstractmethod
    def choose(self, board: Board) -> tuple[int, int]: ...

class BotPlayer(Player):
    def __init__(self, name: str, symbol: Symbol, difficulty: Difficulty): ...
    def choose_move(self, board: Board) -> tuple[int, int]: ...  # delegates to strategy

@dataclass
class Cell:
    symbol: Symbol | None = None   # one fact today — tomorrow's facts land here
    def is_empty(self) -> bool: ...

class Board:
    def __init__(self, n: int = BOARD_SIZE): ...
    def place(self, row: int, col: int, sym: Symbol) -> None: ...
    def cell(self, row: int, col: int) -> Cell: ...
    def symbol_at(self, row: int, col: int) -> Symbol | None: ...  # the name says what comes back
    def is_full(self) -> bool: ...   # any square free?
    def render(self) -> str: ...

class WinRule(ABC):
    @abstractmethod
    def winner(self, board: Board) -> Symbol | None: ...

class KInARowRule(WinRule):
    def __init__(self, k: int = WIN_LEN): ...
    def winner(self, board: Board) -> Symbol | None: ...

class InvalidMoveError(Exception): pass

class Game:
    def __init__(self, players: list[Player], board: Board, rule: WinRule): ...
    def make_move(self, row: int, col: int) -> None: ...
    def status(self) -> GameStatus: ...
    def winner(self) -> Player | None: ...
    def current_player(self) -> Player: ...
    def render(self) -> str: ...

Notice four things by reading the signatures:

  1. Constants BOARD_SIZE + WIN_LEN — honours the 3×3-only scope while making N×N a one-line change (the Step-7 trade-off answer you've already earned).
  2. Board.place() raises, doesn't return bool — failure is exceptional, not a normal return value. Caller doesn't have to remember to check.
  3. InvalidMoveError is a custom exception — lets Game.make_move() raise something callers can catch specifically without swallowing other bugs.
  4. Game.winner() returns Player | None, WinRule.winner() returns Symbol | None — the rule only knows symbols (one-step lower abstraction); Game maps symbols back to players. Each class operates at exactly its own altitude.

Why these behaviours and not others — one question per class

The methods weren't handed down — each one survives a "why not the alternative?" challenge. Ask the question yourself, then reveal.

Why does Board get place / cell / symbol_at / is_full / render — and nothing more?

▾
  • Everything it has is about the grid — geometry, occupancy, display. Nothing about turns or rules.
  • Why not Board.check_winner()? Winning is game policy, not grid bookkeeping — put it there and Connect-Four's board diverges from ours for no reason.
  • Why not Board.make_move(player, r, c)? Then Board needs turn state — and two classes own the flow. One owner per concern.
  • Why keep symbol_at() when cell() exists? Sugar for the 90% of callers (WinRule scans symbols) who shouldn't poke at Cell objects — and the name says exactly what comes back (it was at() in an earlier draft; board.at(2, 1) reads like a riddle).

Why does Game get make_move / status / winner / current_player?

▾
  • make_move is coordination — validate flow, delegate placement, check end, flip turn. Four steps, three of them about flow → the orchestrator's job.
  • Why status() as a pull, not a callback push? The CLI asks after each move; a web UI polls. Pull works for both with zero coupling. (Spectators — the Observer push — was parked in future scope.)
  • Why expose current_player()? The presentation layer needs "whose turn?" to prompt — without it, the UI would reach into private state.
  • Why is there no Game.run()? A run-loop reads input — that's the CLI layer's job (NFR: the engine never knows it's a CLI).

Why does WinRule get exactly winner(board) → Symbol | None?

▾
  • Takes a Board, not a Game — the rule needs the grid, nothing else. Pass Game and every rule could meddle with turns.
  • Returns Symbol, not Player — the rule lives one abstraction below people. Game maps symbol → player. Swap rules and nobody re-teaches them who's playing.
  • Why not is_won() → bool? Then Game must do a second scan to find WHO won — same work twice.

Why do Cell and Player get methods at all?

▾
  • Cell.is_empty(): the one rule a square owns today. One fact (symbol) — but the final design keeps the tiny class anyway: when squares gain a second fact (blocked? bonus?), it lands here with a can_place() rule, and nothing outside Cell changes. The hint comment in place() marks the spot.
  • Player.choose_move(board): the one question Game ever asks a player. Human parses input, bot consults its strategy — Game can't tell, which is the whole point (FR-7).
  • Why not BotPlayer.set_difficulty()? Difficulty picks the strategy at construction; changing it mid-game is a new bot, not a mutation. Fewer states, fewer bugs.
Patterns we'll reach for

The patterns in today's build

1. Strategy — WinRule

Open variable: the win condition.
Default impl: KInARowRule(k).
Future swaps: FourInARowRule, DiagonalOnlyRule, GomokuRule(k=5).
Game doesn't isinstance-check; it just calls rule.winner(board). New rules are pure additions.

2. State (lite) — GameStatus

An enum for now (IN_PROGRESS → WON / DRAW) — we don't need full GoF State for 3 states.
If asked to expand: introduce GameStateMachine with explicit transitions when "paused", "abandoned", "rematch" enter scope.

3. Factory — assembling players

Player is already an abstract contract (FR-7): HumanPlayer reads input; BotPlayer picks via its MoveStrategy.
A PlayerFactory.create("bot", difficulty=Difficulty.HARD) hides which class + which strategy gets built — Game just receives Players.
LLD-23 MVP wires two HumanPlayers; the bot is the live extension.

4. The Move record — undo-ready

The classic follow-up: "now add undo." We didn't build it — we built its prerequisite.
make_move() appends Move(player, row, col) to moves — the game's memory.
When asked: undo() = pop the last Move, clear that square, hand the turn back — ten lines.
Why not snapshot the whole board each turn? Deep copies cost N×N per move and carry no extra information — the move list IS the memory (in Chess it's also the notation — see the trade-offs).

The hygiene rule from LLD-21: introduce these patterns silently in the code, not as announcements. When the interviewer asks "why is WinRule a separate class?" the answer is "because the win condition is the open variable across Tic-Tac-Toe, Gomoku, and Connect-Four-style games — making it a Strategy means each new game is one new class, not a forked codebase." That's how you name a pattern: in service of a trade-off, not as a chest-thump.

2. models/board.py — geometry + occupancy, nothing else

Read the import block first — it IS the architecture: enums and exceptions from below, Cell from next door, nothing from above. Bounds violations raise; occupancy asks the Cell; the hint comment in place() marks where tomorrow's blocked flag lands.

collapse▾
"""Board — geometry + occupancy, nothing else. No turns, no rules, no I/O."""

from __future__ import annotations

from enums import Symbol
from exceptions import InvalidMoveError
from models.cell import Cell

BOARD_SIZE = 3


class Board:
    def __init__(self, n: int = BOARD_SIZE):
        self.n = n
        self._grid = [[Cell() for _ in range(n)] for _ in range(n)]

    def cell(self, row: int, col: int) -> Cell:
        if not (0 <= row < self.n and 0 <= col < self.n):
            raise InvalidMoveError(f"({row}, {col}) is out of bounds")
        return self._grid[row][col]

    def symbol_at(self, row: int, col: int) -> Symbol | None:
        return self.cell(row, col).symbol

    def place(self, row: int, col: int, sym: Symbol) -> None:
        # Hint: when squares gain a second fact — say, BLOCKED cells that
        # nobody may play — Cell grows `blocked` plus a can_place() rule,
        # and THIS check asks the cell. One class changes; nothing else here.
        cell = self.cell(row, col)
        if not cell.is_empty():
            raise InvalidMoveError(f"cell ({row}, {col}) is occupied")
        cell.symbol = sym

    def is_full(self) -> bool:
        return not any(c.is_empty() for row in self._grid for c in row)

    def render(self) -> str:
        return "\n".join(" ".join(c.symbol.value if c.symbol else "." for c in row)
                         for row in self._grid)

"""WinRule — the FR-5 Strategy. Gomoku = KInARowRule(k) on a bigger Board."""

from __future__ import annotations

from abc import ABC, abstractmethod

from enums import Symbol
from models.board import Board

WIN_LEN = 3


class WinRule(ABC):
    @abstractmethod
    def winner(self, board: Board) -> Symbol | None: ...


class KInARowRule(WinRule):
    def __init__(self, k: int = WIN_LEN):
        self.k = k

    def winner(self, board: Board) -> Symbol | None:
        n, k = board.n, self.k
        directions = [(0, 1), (1, 0), (1, 1), (1, -1)]
        for r in range(n):
            for c in range(n):
                start = board.symbol_at(r, c)
                if start is None:
                    continue
                for dr, dc in directions:
                    end_r, end_c = r + (k - 1) * dr, c + (k - 1) * dc
                    if not (0 <= end_r < n and 0 <= end_c < n):
                        continue
                    if all(board.symbol_at(r + i * dr, c + i * dc) == start for i in range(k)):
                        return start
        return None

Optimising the win check — when the DSA round crashes the design round

The winner check runs after EVERY move. Three tiers — guess each tier's time complexity BEFORE you reveal it:

Tier 1 — the naive scan (what we wrote, on purpose)

▾
  • The approach: after each move, walk every cell and probe 4 directions from it
  • The complexity: O(n²·k) — every cell × every direction × k steps
  • Why we still chose it: simple, obviously correct — and on a 3×3 board the whole scan is a few dozen probes; optimising it unasked is solving a problem nobody has. Clarity first, optimise when asked

Tier 2 — only the last move can win

▾
  • The insight: a player can only win on the move they just made — so check just the 4 lines THROUGH (row, col): its row, its column, its two diagonals
  • The complexity: O(k) — four short walks, board size irrelevant
  • The signature grows: winner(board, last_move) — and notice who supplies that argument: the Move record, again. The pattern keeps paying

Tier 3 — don't scan at all

▾
  • The trick: keep row_counts[player][r], col_counts[player][c], and two diagonal counters — make_move() increments three or four integers; any counter reaching n = win
  • The complexity: O(1) — a few increments and comparisons, regardless of board size
  • ⚠️ The honest caveat: counters need a FULL line (k = n). Gomoku — five-in-a-row anywhere on 15×15 — can't be counted this way; there, Tier 2 IS the optimum
🎯 Why this block exists: some companies deliberately fuse the DSA round into the design round at exactly this point — "your design is clean; now make the win check O(1)." Name the three tiers, state which one the board size justifies, and you've answered both rounds in one breath. (And because WinRule is a Strategy, an O1CounterRule is one new class — the optimisation never touches Game.)

"""Game — the orchestrator. Exactly the API the class derived: make_move /
status / winner / current_player / render.
No input(), no print() — the engine never learns it's a CLI."""

from __future__ import annotations

from dataclasses import dataclass

from enums import GameStatus
from exceptions import InvalidMoveError
from models.board import Board
from models.player import Player
from strategies.win_rule import WinRule


@dataclass(frozen=True)
class Move:
    player: Player
    row: int
    col: int


class Game:
    def __init__(self, players: list[Player], board: Board, rule: WinRule,
                 starting_index: int = 0):
        symbols = [p.symbol for p in players]
        if len(players) < 2 or len(set(symbols)) != len(symbols):
            raise ValueError("need >= 2 players with distinct symbols (FR-2)")
        self.players = players
        self.board = board
        self.rule = rule
        self._turn = starting_index
        self._status = GameStatus.IN_PROGRESS
        self._winner: Player | None = None
        self.moves: list[Move] = []   # the game's memory: audit, replay —
                                      # and the ten-line undo(), the day it's asked for

    # --- queries --------------------------------------------------------
    def status(self) -> GameStatus:
        return self._status

    def winner(self) -> Player | None:
        return self._winner

    def current_player(self) -> Player:
        return self.players[self._turn]

    def render(self) -> str:
        return self.board.render()

    # --- commands -------------------------------------------------------
    def make_move(self, row: int, col: int) -> None:
        if self._status is not GameStatus.IN_PROGRESS:
            raise InvalidMoveError("game already over")
        player = self.current_player()
        self.board.place(row, col, player.symbol)      # validates; raises on bad move
        self.moves.append(Move(player, row, col))
        winning_symbol = self.rule.winner(self.board)  # win BEFORE full
        if winning_symbol is not None:
            self._status = GameStatus.WON
            self._winner = next(p for p in self.players if p.symbol == winning_symbol)
        elif self.board.is_full():
            self._status = GameStatus.DRAW
        else:
            self._turn = (self._turn + 1) % len(self.players)

console.py — the whole toolkit, one screen

One core loop, five question shapes built on it — every helper is just ask() with a different parse / valid pair plugged in.

code/tictactoe/console.py
collapse▾
"""
console.py — the game-AGNOSTIC console toolkit. Master once, reuse everywhere.

One core loop (ask) + the four question shapes nearly every CLI round needs:
a bounded number, a non-empty string, a menu, a yes/no. Zero dependencies.
In a machine-coding interview: copy this file in, then write only the game.
"""

from __future__ import annotations

from enum import Enum
from typing import Callable, TypeVar

T = TypeVar("T")


def ask(prompt: str, parse: Callable[[str], T] = str,
        valid: Callable[[T], bool] = lambda v: True,
        error: str = "invalid input") -> T:
    """The validated-input loop: prompt -> parse -> validate -> retry.

    The ONLY input() loop in the whole project. Bad input is re-asked here,
    at the boundary — the engine never sees a raw string.
    """
    while True:
        raw = input(prompt).strip()
        try:
            value = parse(raw)
            if valid(value):
                return value
        except (ValueError, KeyError):
            pass
        print(f"  {error}")


def ask_nonempty(label: str) -> str:
    return ask(f"{label}: ", valid=lambda s: s != "", error="can't be empty")


def ask_int(label: str, lo: int, hi: int) -> int:
    return ask(f"{label} [{lo}-{hi}]: ", parse=int,
               valid=lambda v: lo <= v <= hi,
               error=f"please enter a number between {lo} and {hi}")


def ask_choice(label: str, options: dict[str, T]) -> T:
    """A menu. options maps UPPERCASE keys to values; typing is case-insensitive."""
    keys = "/".join(options)
    return ask(f"{label} [{keys}]: ",
               parse=lambda raw: options[raw.upper()],   # KeyError -> retry
               error=f"please type one of: {keys}")


def ask_enum(label: str, enum_cls: type[Enum]) -> Enum:
    """A menu built straight from an Enum — accepts member values."""
    return ask_choice(label, {m.value.upper(): m for m in enum_cls})


def ask_yes_no(label: str) -> bool:
    return ask_choice(label, {"Y": True, "N": False})

Three things to say while the file is on screen:
  • The return type follows parse. parse=int makes the call return an int — that's the quiet TypeVar T at work, and mypy tracks it at every call site. One generic function, many concrete types
  • except (ValueError, KeyError) is deliberately narrow. int("abc") raises ValueError; options["Q"] raises KeyError — both mean "bad input, ask again". except Exception would also swallow YOUR bugs (a typo'd validator dies silently) — catch exactly what bad input raises, nothing more

Step 7 — trade-offs

The last ten minutes — say these out loud

↩️
Undo — one ask away

We didn't ship undo() — nobody asked (YAGNI).
But make_move() records Move(player, row, col) from day one, so when the interviewer says "now add undo": pop the last Move · clear its square · hand the turn back — ten lines.
The alternative — snapshot the whole board every turn — works, at N× the memory. The Move is the minimal diff.
Why chess breaks this — reveal below.

💾
Persistence — save the moves, not the board

The moves list IS the save format: replaying it through make_move() rebuilds the exact state — board, turn, status.
The same record that makes undo a ten-line ask doubles as the serialisation story.
"Save/resume" = store (players, board config, moves); "spectate from move 1" = the same replay.

🔵
Connect Four — one method away

Board.drop(col): find the lowest cell in the column with can_place(), call the same place().
Win rule: KInARowRule(4) — already written.
Gravity is the only new physics; everything else is reuse.

♟️ Why undo NEEDS a Move class — and why chess makes it hard

▾
  • A bare (row, col) tuple cannot undo. Reversal needs WHO moved (to hand the turn back) and WHAT changed (to restore it) — the Move class is the unit of reversal: each record carries enough to reverse itself
  • Tic-Tac-Toe reversal is the easy case: placing has a clean inverse — set the square back to None. Nothing else on the board changed, so Move(player, row, col) is already complete
  • Chess move 1 problem — captures: the destination square may have held a piece. clear() would erase it from history — the Move must store captured_piece
  • Chess move 2 problem — the capture isn't always AT the destination: en passant removes a pawn from a different square — so it's captured_piece + captured_square
  • Chess move 3 problem — one move, two pieces: castling moves king AND rook; promotion changes a piece's identity (the pawn that comes back must be a pawn again)
  • Chess move 4 problem — invisible state dies too: moving the king destroys castling rights; any move destroys the en-passant window — rights aren't on any square, yet undo must restore them
# TTT — the record IS the inverse:
@dataclass(frozen=True)
class Move:
    player: Player
    row: int
    col: int

# Chess — the record grows into "everything needed to un-happen it":
@dataclass(frozen=True)
class Move:
    piece: Piece
    from_sq: Square
    to_sq: Square
    captured: Piece | None          # may be None
    captured_sq: Square | None      # en passant: != to_sq!
    promoted_to: PieceType | None
    prior_castling_rights: CastlingRights
    prior_en_passant_sq: Square | None
  • The general lesson: undo turns every action into a command that ships with its own inverse data — that's the Command/Memento idea in one sentence. The harder the game's side-effects, the fatter the Move record
  • The honest alternative: snapshot the whole board each turn (Memento proper) — trivially correct, simple to write, N× the memory. Real chess engines store reversible Move records for exactly this reason
