start here · the problem

One process was easy. Many is a different game.

The moment your app is more than one process on one box — a web tier, workers, a payments service, a third-party API — three questions appear that a monolith never had to answer.

⚙️
How do I get my config?
The DB URL, the API keys, the timeouts — different in dev, staging and prod. Hardcoding them means a redeploy to change a value, and secrets leaking into git.
🔍
How do I find the others?
Service B lives at… which IP? It autoscales, restarts, moves between hosts. http://10.0.1.5:8000 is wrong five minutes from now.
💥
How do I survive their failures?
When Payments goes slow, every request that touches it piles up — and takes down features that have nothing to do with payments.

🔥 Why the third one is the scary one

Config and discovery are setup problems. Failure is a runtime problem, and it spreads. A single slow dependency, with no protection, doesn’t just fail one call — it exhausts your thread pool (remember last class?) and the failure cascades to everything upstream.

🌐 Real world: A classic outage shape: a third-party dependency slows from 50ms to 5s. Each web thread now holds for 5s instead of 50ms, so the pool saturates in seconds and the entire site 503s — even pages that never call that dependency. The dependency was never down; it was just slow. Resilience patterns exist for exactly this.

Your API calls a third-party service with no timeout. That service slows from 50ms to 5s (not down — just slow). What happens to the rest of your API?

A thread stuck waiting is a thread nobody else can use — slowness spreads.
  • With no timeout, every request that touches the slow service holds its worker for the full 5s. Your pool is finite, so it saturates fast.
  • Now every route — even /home — queues behind those stuck workers. One slow dependency took down the whole service. This is a cascading failure.
  • The fixes are today’s topic: a timeout (never wait forever), a circuit breaker (stop calling a sick dependency), and a bulkhead (isolate its pool).
pattern 1 · the setup

Externalized configuration

Rule of thumb from the 12-factor app: config is everything that differs between deploys — URLs, credentials, toggles. It belongs in the environment, not baked into the code.

🔑 Secrets — the one rule

A secret never lives in the code or the repo. It comes from the environment (or a secrets manager) at runtime. A local .env file is fine for dev convenience — but it must be gitignored, and you ship a committed .env.example with placeholder values so teammates know what to set.

⚠️ We’ve hit this on this very repo: a real Google client_secret.json and a Redis dump once sat in a class folder and nearly got committed. Secrets and generated data belong in .gitignore, always.

🔢 Which value wins? Config precedence

When the same setting is defined in more than one place, the most specific source wins: a real environment variable overrides the .env file, which overrides the default written in code. That’s exactly how pydantic-settings resolves things.

# config_demo.py  (pydantic-settings)
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    service_name: str = "orders"          # default (lowest priority)
    db_url: str                            # required -> must come from env / .env
    timeout_seconds: float = 2.0
    api_key: str                           # a secret -> env only, never in code

    model_config = {"env_file": ".env"}    # dev convenience; .env is GITIGNORED

settings = Settings()   # reads env vars, then .env, then the defaults above
# DB_URL=... in a real env var beats the same key in .env beats the default.
💬 What it does: Typed & validated: pass timeout_seconds="abc" and it fails loudly at startup, not deep in a request. One Settings object, imported everywhere — no os.environ scattered across the code.

⚙️ How the values actually get set — laptop to cloud

Same Settings object everywhere; only the environment changes. Here is how an env var gets injected at each layer — and, first, how to override one yourself to watch precedence win:

# 1) Your laptop -- override for a SINGLE run (a real env var beats .env):
SERVICE_NAME=payments-prod REQUEST_TIMEOUT_SECONDS=0.25 python3 config_demo.py

# ...or export it for the whole shell session:
export DB_URL="postgres://localhost/orders"
python3 config_demo.py
💬 What it does: Prefix KEY=value before the command and it is set for just that process — the quickest way to see a real env var beat the .env value.
# 2) Docker -- pass env at run time; the image stays generic:
docker run -e DB_URL="postgres://db/orders" -e ENVIRONMENT=production myapp
docker run --env-file prod.env myapp          # ...or a whole file of them
💬 What it does: One image, dev and prod — only the -e flags differ. No secrets baked into the image.
# 3) Kubernetes -- non-secrets from a ConfigMap, secrets from a Secret:
# deployment.yaml (excerpt)
env:
  - name: ENVIRONMENT
    value: "production"
  - name: DB_URL
    valueFrom: { configMapKeyRef: { name: app-config,  key: db_url } }
  - name: PAYMENT_API_KEY
    valueFrom: { secretKeyRef:    { name: app-secrets, key: payment_api_key } }
💬 What it does: Plain config comes from a ConfigMap; the secret from a Secret (or an external manager like Vault/SSM). Your code just reads env vars -- it never knows the difference.
💡 Managed platforms wrap the same idea: Heroku heroku config:set DB_URL=…, an AWS ECS task-def’s environment/secrets, fly secrets set, Render/Railway dashboards. They all end up as env vars your process reads at startup — which is the whole point of externalised config.

Where should your production database password live?

Secrets come from the environment at runtime — never from the repo.
  • Anything committed to git is effectively public to everyone with repo access, and it stays in history even after you delete it. A password in settings.py is a leak.
  • A committed .env is the same leak with extra steps — that’s why .env is gitignored and only .env.example (placeholders) is committed.
  • Inject it as an env var (from your orchestrator or a secrets manager). Same build promotes dev→prod; only the environment changes.
pattern 2 · finding each other

Service discovery

You can’t hardcode http://10.0.1.5:8000 when instances autoscale, crash, and get rescheduled onto new hosts every day. Something has to answer “where is payments right now?”

🔍 A registry + health checks

Each instance registers itself (“I’m payments at 10.0.1.5:8000”) and sends a periodic heartbeat. A client that needs payments asks the registry for a healthy address. Miss your heartbeats and you’re dropped from rotation — so traffic never goes to a dead instance.

The registry, health checks and load-balancing are built into the platform — the pattern didn’t vanish, it moved into the infrastructure.

Why not just put service B’s IP address in service A’s config?

Addresses are dynamic — discovery exists so callers always reach a live instance.
  • In a fixed-server world you could hardcode it. In the cloud, instances come and go constantly (autoscaling, crashes, deploys, rescheduling), each with a fresh address.
  • A registry (or Kubernetes DNS) always hands back a currently healthy instance — and load-balances across them — so callers never chase a stale or dead IP.
  • Health checks are the other half: an instance that stops heartbeating is removed from discovery, so no request is routed to it.
pattern 3 · surviving failure

Resilience patterns

The big one. Dependencies will be slow or down — the goal is to fail gracefully and locally instead of cascading. Four patterns, layered together.

⏱️ 1) Timeouts — never wait forever

The simplest and most-forgotten one. Every network call gets a timeout, so a slow dependency costs you 2 seconds, not a hung thread forever. No timeout = the cascading failure we just saw.

💻 In code — generic Python & Django

▼

🐍 Generic Python

import httpx
# ALWAYS pass a timeout. Without one, a slow server holds your
# thread until IT decides to answer -- which may be never.
resp = httpx.get("https://payments/charge", timeout=2.0)   # 2s hard cap

🌱 Django

import httpx
def charge(order):                 # a service calling another service
    return httpx.post(settings.PAYMENTS_URL, json=order, timeout=2.0).json()

# settings.py -- cap the DB wait too
DATABASES["default"]["OPTIONS"] = {"connect_timeout": 3}

How it works: The timeout turns ‘hang forever’ into ‘fail in 2s’ — the single most important line. Once it fails fast, you can retry or fall back.

🔄 2) Retries with backoff + jitter

Most failures are transient — retry after a growing delay with a little randomness (straight from last class). Two rules: cap the attempts, and only retry safe/idempotent operations. Auto-retrying a non-idempotent charge card is how you double-charge someone.

🔗 Callback to LLD-37: retries + backoff + jitter + idempotency are the same tools that made the queue reliable. Same lesson, one layer up: at-least-once + idempotent = safe to retry.

💻 In code — generic Python & Django

▼

🐍 Generic Python

from tenacity import (retry, wait_exponential_jitter,
                      stop_after_attempt, retry_if_exception_type)
import httpx

@retry(wait=wait_exponential_jitter(initial=0.2, max=5),   # 0.2, 0.4, 0.8s ... + jitter
       stop=stop_after_attempt(3),                          # cap the attempts
       retry=retry_if_exception_type(httpx.TransportError)) # only transient errors
def get_quote():
    return httpx.get(QUOTES_URL, timeout=2.0).json()

🌱 Django

# In Django the queue already does retries (last class!). A Celery task:
from celery import shared_task

@shared_task(autoretry_for=(ConnectionError,), retry_backoff=True,
             retry_jitter=True, max_retries=3)
def send_invoice(order_id):
    ...   # a transient failure is retried automatically, with growing backoff

How it works: Retry only safe / idempotent work, and cap the attempts. A growing, jittered delay lets the dependency breathe instead of getting stampeded.

🎛️ The knobs, in plain words

  • wait=wait_exponential_jitter(initial=0.2, max=5) — the pause between tries grows — ~0.2s, ~0.4s, ~0.8s… (doubling), each nudged by a little random jitter, capped at 5s. Growing = give the dependency room to recover; jitter = 10,000 clients don’t all retry in the very same instant.
  • stop=stop_after_attempt(3) — give up after 3 total tries. Without a cap, a genuinely-dead dependency gets retried forever.
  • retry=retry_if_exception_type(httpx.TransportError) — only retry transient failures (a network blip). A 400 Bad Request won’t fix itself on a re-run, so it is not retried.
  • Together: try at most 3 times, waiting a growing + jittered delay between each, but only for errors worth retrying.

🔋 3) The circuit breaker — stop hammering a dead dependency

Retrying a dependency that’s truly down just wastes time and piles on load. A circuit breaker wraps the call and watches failures. After too many, it trips open and every call fails instantly — no waiting, no load on the sick service. After a cooldown it lets one trial through: works → close and resume; still failing → stay open. Like the breaker in your house.

🔌 The home-electrics analogy — and yes, a fuse works the same way

wiring from burning — you flip it back on once the fault is fixed. Your software breaker is the same idea.

A fuse runs on the exact same premise — too much current and it breaks the circuit to protect the wiring. The one difference is recovery: a fuse is one-shot (the wire melts, you replace it), while a breaker resets (you flip it back on). Software circuit breakers copy the breaker, not the fuse — after a cooldown they auto-recover via the HALF-OPEN trial, so nobody swaps a part at 3am.

And here’s how it plays out between two real services — an order service calling a payment service:

💻 In code — generic Python & Django

▼

🐍 Generic Python

import pybreaker
# trip after 5 failures; stay OPEN 30s before a trial call
payments_cb = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

@payments_cb
def charge(order):
    return httpx.post(PAYMENTS_URL, json=order, timeout=2.0).json()

# while OPEN, calling charge() raises CircuitBreakerError instantly -- no network hit

🌱 Django

# one breaker per dependency, shared across requests (module-level)
payments_cb = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

class PaymentClient:
    @payments_cb
    def charge(self, order):
        return httpx.post(settings.PAYMENTS_URL, json=order, timeout=2.0).json()

How it works: Keep one breaker instance per dependency at module level so every request shares its state. OPEN = fail fast; after reset_timeout it half-opens and probes once.

🎛️ The knobs, in plain words

  • fail_max=5 — trip to OPEN after 5 failures in a row. Lower = more trigger-happy (protects sooner, but more false trips); higher = more forgiving.
  • reset_timeout=30 — stay OPEN for 30s before allowing one trial call — the ‘give the dependency time to recover’ window.
  • Together: after 5 straight failures, stop calling for 30s, then let one probe through — success closes it, failure restarts the 30s.
📁 Code for this section: code/circuit_breaker.py — the state machine in ~80 lines, no installs

▶️ Run it: python3 circuit_breaker.py — a checkout calls a flaky PaymentGateway and you watch the breaker go CLOSED → OPEN (calls now fail fast, the gateway is left alone) → HALF-OPEN after the cooldown → CLOSED once it recovers.

A circuit breaker around a dependency is in the OPEN state. A request comes in that needs that dependency. What happens?

OPEN = fail fast, don’t call. Protect yourself and the sick dependency.
  • An OPEN breaker short-circuits: it returns an error (or triggers a fallback) instantly, without making the network call at all.
  • That does two things: your threads aren’t stuck waiting on a dead service, and the dead service gets a break from the retry storm so it can actually recover.
  • After a cooldown the breaker goes HALF-OPEN and lets one probe through — success closes it, failure re-opens it. Automatic recovery, no human paged at 3am.
pattern 3 · continued

Bulkheads, fallbacks & health checks

Three more that round out the toolkit — contain the blast radius, degrade gracefully, and let the platform route around sick instances.

🚒 4) Bulkheads — contain the blast radius

Named after a ship’s watertight compartments: a leak floods one, not the whole hull. Give each dependency its own pool of workers/connections. If Payments goes slow, it can only exhaust its pool — Email and everything else keep running on theirs.

Payments is slow, and it’s taking your whole app down with it — even the parts that never call Payments. Which pattern directly fixes that blast radius?

Isolation is the fix for ‘one slow thing drowns everything’.
  • Retries don’t help — if anything they add load to the slow dependency.
  • A bulkhead caps how many workers Payments can ever tie up. Even fully saturated, it only drowns its own compartment; the rest of the app keeps serving.
  • A single bigger pool just delays the drowning — a slow enough dependency will still eat all of it. Isolation, not size, is the fix. (Pair it with a circuit breaker + timeout.)

💻 In code — generic Python & Django

▼

🐍 Generic Python

import threading
# cap how many callers can be inside the slow dependency AT ONCE
payments_slots = threading.Semaphore(4)

def charge(order):
    if not payments_slots.acquire(timeout=0.1):
        raise RuntimeError("payments pool full")   # fail fast, don't pile on
    try:
        return httpx.post(PAYMENTS_URL, json=order, timeout=2.0).json()
    finally:
        payments_slots.release()

🌱 Django

# give each slow dependency its own budget. Options:
#   - a bounded Semaphore around the client (below)
#   - a dedicated Celery queue + its own workers
#   - a separate DB connection pool
payments_slots = threading.Semaphore(4)   # module-level, shared

def charge(order):
    with payments_slots:      # limits to 4 concurrent callers
        return httpx.post(settings.PAYMENTS_URL, json=order, timeout=2.0).json()

How it works: The semaphore caps concurrency to that one dependency. Even if payments hangs, only 4 workers are ever stuck — the rest keep serving everything else.

🎛️ The knobs, in plain words

  • Semaphore(4) — at most 4 callers can be inside this one dependency at a time — that’s its entire budget of your workers.
  • acquire(timeout=0.1) — wait at most 0.1s for a free slot; if none, fail fast instead of queuing up behind the slow dependency (which would defeat the point).
  • Together: cap concurrency to 4, and don’t even wait long for a slot — so a slow payments can never tie up more than 4 workers.

🧩 5) Fallbacks — degrade gracefully

When a call fails (or the breaker is open), return something useful instead of an error: a cached value, a sensible default, a “recommendations unavailable” placeholder. A degraded page beats a 500. (Never fall back in a way that hides a money error, though — know when failing loudly is correct.)

💻 In code — generic Python & Django

▼

🐍 Generic Python

def recommendations(user):
    try:
        return live_recos(user)        # real call (already has timeout + breaker)
    except Exception:
        return cached_recos(user) or DEFAULT_RECOS   # degrade, never 500

🌱 Django

from django.core.cache import cache

def recommendations(user):
    try:
        data = live_recos(user)
        cache.set(f"recos:{user.id}", data, 3600)    # keep a warm copy
        return data
    except Exception:
        return cache.get(f"recos:{user.id}") or DEFAULT_RECOS

How it works: Serve the last good value when the live call fails — a degraded page beats a 500. (But never fall back in a way that hides a money error.)

🏥 6) Health checks — liveness vs readiness

Two probes the platform calls on your service, answering different questions. Mixing them up is a classic bug: a slow dependency should fail readiness (stop sending traffic), not liveness (don’t restart a perfectly alive process).

💻 In code — generic Python & Django

▼

🐍 Generic Python

# liveness: is the process alive? (cheap, no dependencies)
def liveness():  return 200

# readiness: can I serve traffic right now? (check dependencies)
def readiness():
    return 200 if db_ok() and cache_ok() else 503

🌱 Django

# urls.py -> two tiny views the load balancer / orchestrator calls
from django.http import JsonResponse
from django.db import connection

def livez(request):                       # liveness: am I up?
    return JsonResponse({"status": "ok"})

def readyz(request):                      # readiness: are my deps up?
    try:
        connection.cursor().execute("SELECT 1")
        return JsonResponse({"status": "ready"})
    except Exception:
        return JsonResponse({"status": "not-ready"}, status=503)

How it works: Liveness failing → the pod is restarted. Readiness failing → it’s pulled from the load balancer, not killed. A slow dependency should fail readiness only. (Or use django-health-check.)

🎓 A concrete moment — the database blips for 10 seconds

▼
  • Readiness checks the DB, so it starts returning 503. The load balancer stops sending new requests to this pod — users are served by other healthy pods instead of seeing errors.
  • Liveness does not check the DB (it only says ‘the process is running’), so it stays green. The pod is not killed — it’s a healthy process just waiting on a dependency.
  • When the DB recovers, readiness flips back to 200, the LB adds the pod back, and traffic returns — no restart, nothing lost.
  • The classic bug: putting the DB check in liveness. Now the 10-second blip makes the orchestrator kill and restart every pod — turning a tiny hiccup into a full outage plus a restart storm.
🎯 The stack, together: wrap every remote call in a timeout, add bounded retries for transient blips, put a circuit breaker around it so a dead dependency fails fast, isolate it with a bulkhead, and give a fallback for when it’s all down. That’s a resilient client.

📜 A 30-second history

  • Today: the CNCF Landscape tracks 1000+ projects; ‘graduated’ ones (Kubernetes, Prometheus, Envoy, etcd, Helm, Argo…) are the battle-tested core.

prep

Cloud-native in interviews

System-design rounds lean on these once you have more than one service. Trade-offs, not definitions — say each out loud first.

“A downstream service is slow and it’s taking your API down. What do you do?”

▼

🎯 What they’re really testing: whether you can stop a failure from cascading.

  • Timeout every call so a slow dep costs seconds, not a hung thread; add a circuit breaker so once it’s clearly failing you stop calling it and fail fast.
  • Bulkhead it — give it an isolated pool so it can’t exhaust the workers other features need; add a fallback so users get a degraded response, not a 500.
  • Name the shape: this is a cascading failure, and the fix is failing fast + locally.

“Walk me through the states of a circuit breaker.”

▼

🎯 What they’re really testing: that you actually understand the pattern, not just the name.

  • CLOSED — calls pass, failures are counted; at a threshold it trips.
  • OPEN — calls fail fast without touching the dependency, for a cooldown window (protects you and lets it recover).
  • HALF-OPEN — after the cooldown, one trial call: success → CLOSED, failure → OPEN. Automatic recovery.

“Where do secrets and config go?”

▼

🎯 What they’re really testing: 12-factor instincts — and that you won’t commit a password.

  • Config that differs between deploys lives in the environment, not the code; one typed settings object reads it.
  • Secrets come from env vars or a secrets manager (Vault/SSM), injected at runtime, rotatable, never in git. .env is gitignored; only .env.example is committed.
  • Same build promotes dev→staging→prod; only the environment changes.

“How does service A find service B in the cloud?”

▼

🎯 What they’re really testing: service discovery — and that you know hardcoding IPs breaks.

  • Instances register + heartbeat; a registry hands out healthy addresses and load-balances — client-side (Eureka/Consul) or server-side (a load balancer).
  • On Kubernetes it’s built in: call a stable Service DNS name and kube-proxy routes to a healthy pod.
  • Health checks remove dead instances from discovery, so traffic never hits them.

The same patterns in the agentic-AI era

Here’s the payoff. An AI agent or inference harness is just a distributed system — one whose dependencies (LLM APIs, tools, vector DBs, GPUs) happen to be unusually slow, flaky, and expensive. So these patterns don’t merely still apply — they matter more.

✨ Two twists agents add on top

  • Loop & budget guards — an agent can loop forever or quietly blow your bill. Cap iterations, tokens, and cost per task. It’s a bulkhead + circuit breaker for money.
  • Semantic caching — cache answers by meaning, not exact text, so “what’s our refund policy?” and “how do refunds work?” share one answer. A cache hit is a fallback and a big cost/latency win.

🐍 A resilient LLM call, in a few lines

from tenacity import retry, wait_exponential_jitter, stop_after_attempt

@retry(wait=wait_exponential_jitter(2, max=30),   # rate-limits love backoff
       stop=stop_after_attempt(4))
def ask(model, prompt):
    return client.chat(model=model, messages=prompt, timeout=30)   # never hang

def ask_resilient(prompt):
    try:
        return ask("gpt-4", prompt)                  # primary model
    except Exception:
        return (semantic_cache.get(prompt)           # 1) a cached answer, or
                or ask("gpt-4o-mini", prompt))       # 2) a cheaper / faster model
💬 What it does: A timeout so it never hangs, retry + backoff for the constant rate-limits, and a fallback chain (cache → cheaper model) for when the primary is down — the exact stack from this class, pointed at a model.
🌐 Real world: This is why LLM gateways exist — LiteLLM, Portkey, Cloudflare AI Gateway, OpenRouter all bundle retries, fallbacks, caching, rate-limiting, and load-balancing across models. They are a resilient client + service discovery for models, because an AI app is a distributed system with an unusually temperamental dependency.
🎯 The takeaway: nothing about ‘AI’ is exempt from distributed-systems reality. If anything, the slow, flaky, costly nature of inference makes timeouts, retries, breakers, bulkheads, fallbacks and idempotency table stakes for anyone building agents.
