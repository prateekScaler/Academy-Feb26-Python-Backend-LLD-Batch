The Factory Family

LLD-17 • Creational Patterns

Stop scattering EmailNotification(host, port, key, ...) across 30 files. Centralize object creation — then learn the three flavors that solve three different versions of "where should the new live?"

Recap — Builder

Quick Recall — Builder Pitfalls

Three checks from LLD-16 before we move on. Builder centralized construction logic; Factory is going to centralize which concrete class to instantiate — related but different problems.

Quiz 1 — What's the main advantage of Approach B?

# Approach A
class Database:
    def __init__(self, host, port, username, password):
        if not self._validate_host(host):
            raise ValueError("Invalid host")
        if port < 1024:
            raise ValueError("Invalid port")
        self.host = host
        self.port = port
        self.username = username
        self.password = password

# Approach B
@dataclass
class Database:
    host: str;  port: int
    username: str; password: str

    class Builder:
        def build(self):
            self._validate()
            return Database(...)
Correct — B. The other three options each describe a real Builder negative falsely dressed up as a positive. Spotting that is the test:
  • A is false — Builder writes more code, not less. You now have two classes where one constructor used to do. The boilerplate is the price of the separation.
  • B is the real advantage — Product = data; Builder = workspace. Separation of concerns at the class level.
  • C is false — Python has no access control. Database(host, port, ...) still works. The Builder is a convention, not enforcement — a real limitation, not a feature.
  • D is false — the setter chain is dynamic. A typo like .set_prt only blows up at runtime, not at the call site. With a plain constructor, the type checker catches misnamed arguments immediately. Late-discovered typos are a real Builder downside.

The generic Builder UML — recall the shape:

Product (immutable)
+ host: str
+ port: int
+ username: str
+ password: str
+ connect()
← creates
Builder (mutable)
- _host
- _port
- _username
- _password
+ set_host(): Builder
+ set_port(): Builder
…
+ build(): Product
Each setter returns the Builder itself — return self — enabling fluent chaining. build() validates and produces an immutable Product.

But Builder isn't free — the honest negatives:

  • More code per Product — you write two classes where one constructor used to do.
  • No "frozen" enforcement in Python — callers can still bypass the Builder by calling Database(...) directly. The Builder is a convention.
  • Easier to leak state if you reuse a Builder for two Products (Q3 below).
  • Two-step construction means a typo in the chain (.set_port → .set_prt) shows up at runtime, not at the call site.
  • Overkill for 2-3 required fields — you trade clarity for ceremony (Q2 below).

Quiz 2 — Which class would Builder be overkill for?

# A
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

# B
class HttpRequest:
    def __init__(self, url, method, headers, body,
                 timeout, retry, verify_ssl, cookies, auth):
        ...   # 9 params

# C
class User:
    def __init__(self, name, email):
        self.name, self.email = name, email
Correct! Point(1, 2) and User("Alice", "a@x.com") have 2 required args and no validation — the constructor is already perfect. HttpRequest with 9 optional params is exactly where Builder earns its keep.

Rule of thumb: 2–3 required fields with no validation → plain constructor. 4+ params or optional fields or complex validation → Builder.

🎲 Where Builder shines in classic LLD interview problems — the kind you'll face later in this module:

  • TicTacToe — Game needs: board size (3×3 or 5×5), player count, player symbols, win condition (rows-only? include diagonals? N-in-a-row?), undo support. Validating that "5 players don't fit on a 3×3 board" or "win-condition N must be ≤ board size" is exactly a multi-field rule that belongs in build(), not __init__.
  • Snake & Ladder — Board needs: size, snake positions list, ladder positions list, dice config, player count. Cross-field validation: "no snake and ladder on the same cell," "snakes go from high to low," "no ladders on the last cell". The constructor would be a nightmare; the Builder reads like a setup checklist.
  • Chess — Game needs: time control, players, opening position (standard / custom FEN), undo enabled, move-validator strictness. Multiple optional fields with combined rules ("custom FEN forbidden in tournament mode") — classic Builder territory.
  • BookMyShow / Parking Lot — same shape: Show, ParkingLot have many optional fields and cross-field invariants. You'll write a Builder almost reflexively once you've seen the pattern.

In every one of these, the __init__ approach drowns in if-checks within seconds. Builder lets the Product stay a @dataclass and pushes all the "is this a legal game setup?" logic into build().

Quiz 3 — What does report1.data print?

class ReportBuilder:
    def __init__(self):
        self._title = None
        self._data = []

    def set_title(self, t):  self._title = t; return self
    def add_data(self, d):   self._data.append(d); return self

    def build(self):
        return Report(self._title, self._data)

builder = ReportBuilder()
report1 = builder.set_title("Q1").add_data(100).build()
report2 = builder.set_title("Q2").add_data(200).build()

print(report1.data)
Correct! Two distinct bugs collaborate here:
  1. Builder reuse: the same ReportBuilder instance is used for both reports, so its _data list grows across both calls.
  2. No defensive copy in build(): it passes the same list reference into the Product — so report1.data and report2.data are the same list.

Two fixes: (a) one Builder per Product (fresh chain each time), and (b) a defensive copy of the mutable list inside build():

class ReportBuilder:
    def __init__(self):
        self._title = None
        self._data = []                                # still mutable on the builder

    def set_title(self, t):  self._title = t; return self
    def add_data(self, d):   self._data.append(d); return self

    def build(self):
        return Report(self._title, list(self._data))   # fix (b): defensive copy

# fix (a): fresh Builder per Product
report1 = ReportBuilder().set_title("Q1").add_data(100).build()
report2 = ReportBuilder().set_title("Q2").add_data(200).build()

print(report1.data)     # [100]
print(report2.data)     # [200]

Either fix alone would prevent the cross-contamination shown above; in real codebases, do both.

What's next: Builder controlled how a complex object is assembled. Factory controls which concrete class gets instantiated — especially when the caller shouldn't (or can't) name the concrete class itself. Different problem, same family (Creational).

What & Why

What is the Factory Pattern?

A family of patterns that share one job: centralize "which concrete class to instantiate" so callers don't have to know.

❌ Without Factory
if ch == "email":
  n = EmailNotification(host, port, key, ...)
elif ch == "sms":
  n = SMSNotification(api_key, country, ...)
# ... repeated in every caller
→
✔ With Factory
n = NotificationFactory.create(ch, user)
n.send("Welcome!")

# Caller doesn't know or care
# which concrete class came back
The messy creation logic moves into one place. Everyone else just asks for "a notification" by type.

🎯 The three flavors — from simplest to most powerful

🧰
SIMPLE FACTORY
"one place to call new"
Factory.create("email")
A single static method with an if/elif chain. Add a new type? Modify the factory.
🧮
FACTORY METHOD
"subclass decides the concrete"
EmailSender().send(msg)
An abstract creator + one subclass per concrete type. Add a new type? New subclass, no edits.
🏠
ABSTRACT FACTORY
"families that belong together"
f = WindowsUIFactory()
f.create_button()
f.create_menu()
A factory that produces a whole family of related objects together. Use when consistency across products matters.
⚠️ A note about the name. In conversation, "Factory pattern" usually means "any of the three." In an interview, it's worth being precise — Simple Factory is the easiest, Factory Method follows the Open-Closed Principle, Abstract Factory guarantees consistency across product families. Today we'll build all three, in order.
Pre-flight Check

Prerequisites — What Factory Solves

One warm-up to set up the family. Each variant will introduce its own “OK, but what about this case?” question as we go.

Question 1 — The scattered-creation smell

def send_welcome(user, ch):
    if ch == "email":
        n = EmailNotification(user.email, "smtp.x.com", 587, "noreply@x", "pw")
    elif ch == "sms":
        n = SMSNotification(user.phone, "twilio_key", user.country_code)
    n.send("Welcome!")

def send_reminder(user, ch):
    if ch == "email":
        n = EmailNotification(user.email, "smtp.x.com", 587, "noreply@x", "pw")
    elif ch == "sms":
        n = SMSNotification(user.phone, "twilio_key", user.country_code)
    n.send("Reminder!")

# ... 28 more functions, each repeating the same if/elif

What's the worst part of this design?

Correct! The constructor args (SMTP host, port, API key, country code) are configuration — not business decisions. They're now hardcoded in 30 functions. Rotate the SMTP password? Hunt down 30 places. Add a Discord notification? 30 edits.

The principle being broken here isn't even one of the fancy SOLID letters — it's the most fundamental one: DRY (Don't Repeat Yourself). The same construction logic is copy-pasted 30 times. Every copy is a place a future bug can hide. Whenever you find yourself writing the same shape of code in many call sites, the question to ask is "where should this live once?"

The fix: push all that creation logic into one place — a Factory. Each caller asks for "a notification of this kind" without knowing the constructor args. This is Simple Factory.

Got Q1? The duplication smell is what Simple Factory cures. But Simple Factory will itself reveal a new smell — and that smell will lead us to Factory Method. Then Factory Method will reveal yet another smell — and that one leads us to Abstract Factory. We'll meet each follow-up question right at the point where it bites, not as abstract trivia up front.

Motivation

The Problem — a Concrete Scenario

Let's watch a notification service grow into a maintenance disaster — the same story behind every Factory pattern.

Ajit is building the notification layer of a SaaS product. Today it sends email. Next quarter: SMS. Then push. Then Slack. Then Discord. Each notification type has its own constructor signature — SMTP host for email, API key for SMS, device token for push. The first version was a 4-line function. Eighteen months later it's spread across 30 files and nobody wants to touch it.

Smell 3 — business logic and creation logic tangled together

on_payment_received shouldn't know what an SMTP port is. It shouldn't import twilio. Its job is to react to a payment — nothing else. But the constructor calls drag all of that infrastructure into the business module.

The fix in one sentence: move the "which class do I instantiate, and with which constructor args" question into one place — a Factory. Each caller asks for "a notification for this user on this channel" and gets a ready-to-use object back. That's where we're headed next.
Variant 1 of 3

Simple Factory — Centralized Creation

The smallest possible move: take the if/elif out of every caller and put it in one place. Not even a real GoF pattern — just good housekeeping.

Step 1 — common abstract interface

Every notification class promises the same send() method. Callers will talk to Notification, not to EmailNotification or SMSNotification directly.

from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, message: str) -> None: ...


class EmailNotification(Notification):
    def __init__(self, to, smtp_host, smtp_port, user, password):
        self.to, self.smtp_host = to, smtp_host
        self.smtp_port = smtp_port
        self.user, self.password = user, password
    def send(self, msg):
        print(f"[email] {self.to}: {msg}")


class SMSNotification(Notification):
    def __init__(self, phone, api_key, country_code):
        self.phone, self.api_key, self.country_code = phone, api_key, country_code
    def send(self, msg):
        print(f"[sms] {self.country_code}{self.phone}: {msg}")


class PushNotification(Notification):
    def __init__(self, device_id, fcm_key):
        self.device_id, self.fcm_key = device_id, fcm_key
    def send(self, msg):
        print(f"[push] dev={self.device_id}: {msg}")

Step 2 — the Factory class with one static create()

All construction logic + configuration now lives here. Each call site simply asks "give me a notification of type X" and gets a ready-to-use object.

import os

class NotificationFactory:
    @staticmethod
    def create(channel: str, user) -> Notification:
        if channel == "email":
            return EmailNotification(
                to=user.email,
                smtp_host=os.environ["SMTP_HOST"],
                smtp_port=int(os.environ["SMTP_PORT"]),
                user=os.environ["SMTP_USER"],
                password=os.environ["SMTP_PASS"],
            )
        elif channel == "sms":
            return SMSNotification(
                phone=user.phone,
                api_key=os.environ["TWILIO_KEY"],
                country_code=user.country_code,
            )
        elif channel == "push":
            return PushNotification(
                device_id=user.device_id,
                fcm_key=os.environ["FCM_KEY"],
            )
        raise ValueError(f"unknown channel: {channel}")

Step 3 — callers become trivial

# users.py
def on_signup(user, channel):
    NotificationFactory.create(channel, user).send("Welcome aboard!")

# billing.py
def on_payment_received(user, channel):
    NotificationFactory.create(channel, user).send("Payment received")

# auth.py, security.py, marketing.py ... same one-liner pattern

What Simple Factory bought us:
  • DRY restored — construction logic exists in one place
  • Configuration centralized — SMTP password rotates? One file changes
  • Callers are clean — billing.py no longer imports twilio
  • Easy to mock in tests — patch NotificationFactory.create once

🤯 But wait — is Simple Factory really clean?

Question — A new requirement arrives: add Slack and Discord. What SOLID principle does our Simple Factory itself break?

class NotificationFactory:
    @staticmethod
    def create(channel, user):
        if channel == "email":    return EmailNotification(...)
        elif channel == "sms":    return SMSNotification(...)
        elif channel == "push":   return PushNotification(...)
        elif channel == "slack":  return SlackNotification(...)     # NEW
        elif channel == "discord": return DiscordNotification(...)  # NEW
        raise ValueError(f"unknown channel: {channel}")
Correct — OCP. From LLD-13: open for extension, closed for modification. Simple Factory cured the duplication smell (the if/elif was in 30 callers; now it's in 1). But we didn't eliminate it — we just moved it. And every new channel still forces us to edit tested code in the factory.

The next move: get rid of the central if/elif entirely by letting each notification type live in its own factory subclass. That's Factory Method.

When Simple Factory is enough

✔ Reach for Simple Factory when…

  • You have 3–5 concrete classes behind one interface
  • The set is stable (not adding new types every sprint)
  • You want clients to not know the concrete names
  • "One if/elif in one file" is fine for your codebase's lifetime

❌ Skip it when…

  • You're adding new types frequently — the factory becomes an OCP violation
  • The concrete class has per-instance behavior that varies (not just construction)
  • You need families of related products (Abstract Factory)

🧰 Two more places you'll meet Simple Factory

Example A — Document parser factory

A backend service receives uploaded files. Based on the extension, it picks the right parser. Simple Factory is the right tool because the set of parsers is small and stable.

from abc import ABC, abstractmethod

class Parser(ABC):
    @abstractmethod
    def parse(self, raw: bytes) -> dict: ...


class JsonParser(Parser):
    def parse(self, raw): import json; return json.loads(raw)

class CsvParser(Parser):
    def parse(self, raw): import csv, io; return list(csv.DictReader(io.StringIO(raw.decode())))

class XmlParser(Parser):
    def parse(self, raw): ...


class ParserFactory:
    @staticmethod
    def for_extension(ext: str) -> Parser:
        if ext == ".json": return JsonParser()
        if ext == ".csv":  return CsvParser()
        if ext == ".xml":  return XmlParser()
        raise ValueError(f"unsupported: {ext}")


# Caller
data = ParserFactory.for_extension(".json").parse(raw_bytes)

Example B — Logger factory

Pick a logging sink based on environment (dev / staging / prod). Two or three concrete types, no plans to grow — Simple Factory is the sweet spot.

class Logger(ABC):
    @abstractmethod
    def log(self, level: str, msg: str): ...


class ConsoleLogger(Logger):
    def log(self, level, msg): print(f"[{level}] {msg}")

class FileLogger(Logger):
    def __init__(self, path): self.path = path
    def log(self, level, msg):
        with open(self.path, "a") as f:
            f.write(f"[{level}] {msg}\n")

class DatadogLogger(Logger):
    def __init__(self, api_key): self.api_key = api_key
    def log(self, level, msg): ...   # POST to Datadog


class LoggerFactory:
    @staticmethod
    def for_env(env: str) -> Logger:
        if env == "dev":        return ConsoleLogger()
        if env == "staging":    return FileLogger("/var/log/app.log")
        if env == "production": return DatadogLogger(api_key=os.environ["DD_KEY"])
        raise ValueError(f"unknown env: {env}")


log = LoggerFactory.for_env("production")
log.log("INFO", "server started")

📊 How often you'll see Simple Factory in real codebases: very common — roughly 7–8 out of 10 production codebases use this informally, often without anyone calling it a "pattern." It's the default response to "I've copy-pasted this if channel == ... three times." If you've written a function called get_parser(...), build_client(...), or make_xxx(...) that returns one of N implementations, you've shipped a Simple Factory.

Variant 2 of 3

Factory Method — Subclasses Decide

Instead of one factory class with if/elif, give each concrete type its own factory subclass. New type — new class. Old factories untouched. OCP restored.

The code

from abc import ABC, abstractmethod

class NotificationCreator(ABC):
    """Abstract creator. Subclasses pick which Notification to make."""

    @abstractmethod
    def create_notification(self, user) -> Notification: ...

    def notify(self, user, message):
        # Template method - uses the factory method internally
        n = self.create_notification(user)
        n.send(message)


# Each concrete creator: one class, one create_notification()
class EmailCreator(NotificationCreator):
    def create_notification(self, user):
        return EmailNotification(
            to=user.email,
            smtp_host=os.environ["SMTP_HOST"],
            smtp_port=int(os.environ["SMTP_PORT"]),
            user=os.environ["SMTP_USER"],
            password=os.environ["SMTP_PASS"],
        )

class SMSCreator(NotificationCreator):
    def create_notification(self, user):
        return SMSNotification(
            phone=user.phone,
            api_key=os.environ["TWILIO_KEY"],
            country_code=user.country_code,
        )

class PushCreator(NotificationCreator):
    def create_notification(self, user):
        return PushNotification(
            device_id=user.device_id,
            fcm_key=os.environ["FCM_KEY"],
        )


# Add Discord later? Just add a new class. ZERO edits to old creators.
class DiscordCreator(NotificationCreator):
    def create_notification(self, user):
        return DiscordNotification(
            webhook_url=os.environ["DISCORD_WEBHOOK"],
            user_handle=user.discord_handle,
        )

Callers pick a creator instead of a string

def on_signup(user, creator: NotificationCreator):
    creator.notify(user, "Welcome aboard!")

# The "which creator?" choice happens at the edge:
on_signup(user, EmailCreator())
on_signup(user, SMSCreator())
on_signup(user, DiscordCreator())   # works without any prior on_signup change
The trade-off:
  • ✔ OCP restored — new types are added, not edited in
  • ✔ Each concrete creator is small and focused
  • ✔ Easy to swap for tests — FakeCreator() sits beside EmailCreator()
  • ❌ More classes — 5 channels = 5 creator classes (plus 5 product classes)
  • ❌ The "channel → creator" string-to-class lookup has to live somewhere — often in a tiny registry dict at the composition root

When Factory Method earns its keep

  • You're regularly adding new types behind one abstract interface
  • You want strict Open/Closed compliance (interview answer + many library codebases)
  • Each type has some logic beyond construction (e.g. a template method that uses the product)
  • Real examples: logging.getLogger(name) uses a factory method internally; SQLAlchemy dialect classes; requests.adapters.HTTPAdapter

🔌 Bonus — Factory Method follows DIP too

Look at the caller signature one more time:

def on_signup(user, creator: NotificationCreator):
    creator.notify(user, "Welcome aboard!")

Recall the Dependency Inversion Principle from LLD-14: high-level modules should depend on abstractions, not concretions. Three stakeholders here:

High-level (on_signup) — the business logic. It only knows it needs some notification sent.
↓ depends on ↓
Abstraction (NotificationCreator)
<<abstract>> create_notification() · notify()
↑ ALSO depends on ↑
Low-level (EmailCreator, SMSCreator, …) — concrete implementations. They depend on the abstraction (they implement it).

→ Both the high-level code and the low-level code depend on the abstraction. Neither knows about the other directly. That's DIP. Swap EmailCreator for FakeCreator in tests — on_signup doesn't care. Add a brand new SlackCreator — on_signup doesn't care. The arrows all point at the abstraction.

Compare with the Simple Factory version: on_signup would have to call NotificationFactory.create(channel, user) — importing the concrete factory class and passing a string. Now on_signup depends on NotificationFactory directly. Factory Method's caller depends only on NotificationCreator (the abstraction). One small win for DIP.

📝 A note on naming — *Creator vs *Factory

We called the abstract class NotificationCreator, but the same pattern is equally valid (and very common in real code) with a *Factory suffix. The pattern is not about the name — it's about the shape: an abstract class whose abstract method is the factory, plus concrete subclasses that each fix the choice of product.

Same pattern, two perfectly fine naming styles — pick the one your team already uses
Naming style A: *Creator
NotificationCreator (abstract)
  + create_notification()
  + notify()
EmailCreator · SMSCreator
PushCreator · DiscordCreator
Naming style B: *Factory
NotificationFactory (abstract)
  + create_notification()
  + notify()
EmailFactory · SMSFactory
PushFactory · DiscordFactory

Same UML. Same code. Same OCP & DIP win. Only the suffix is different.

Convention you'll meet in the wild: Java/.NET codebases tend toward *Factory; many Python codebases prefer *Creator, *Provider, *Builder, or even just a method like build_*(). If the structure matches the pattern, it is the pattern — regardless of what the file is named.

🧰 Another Factory Method — Document export service

An e-commerce backend can export invoices in different formats (PDF, Excel, HTML for the web). Each format is its own subclass.

from abc import ABC, abstractmethod

class Document(ABC):
    @abstractmethod
    def render(self, data) -> bytes: ...


class PdfDocument(Document):
    def render(self, data): return b"%PDF-1.4 ..."

class ExcelDocument(Document):
    def render(self, data): return b"PK\x03\x04 ..."      # xlsx bytes

class HtmlDocument(Document):
    def render(self, data): return b"<table>...</table>"


class ExportService(ABC):
    @abstractmethod
    def create_document(self) -> Document: ...

    def export(self, data, path: str):                    # template method
        doc = self.create_document()
        with open(path, "wb") as f:
            f.write(doc.render(data))


class PdfExportService(ExportService):
    def create_document(self): return PdfDocument()


class ExcelExportService(ExportService):
    def create_document(self): return ExcelDocument()


class HtmlExportService(ExportService):
    def create_document(self): return HtmlDocument()


# Caller picks the service. New format = new service class, no edits to old ones.
PdfExportService().export(invoice_data, "invoice.pdf")
ExcelExportService().export(invoice_data, "invoice.xlsx")

📊 How often you'll see Factory Method: common in library & framework code — roughly 4–5 out of 10 codebases use it explicitly. Less common in everyday app code (Simple Factory or just plain dependency injection usually wins there). Show up most often in: ORM drivers (each DB dialect is a subclass), web frameworks (each request handler is a subclass), CI/CD task runners (each runner type subclasses a base). Variant 3 of 3

Abstract Factory — Families of Related Products

When the products come in families that must stay together — all Windows widgets, all dark-theme components, all production-AWS resources — you need a factory that hands over the entire family in one call. Anything less allows mixing.

Setup — cross-platform UI widgets

Imagine you're building an app that renders on Windows, Mac, and Linux. Each platform has its own Button, Checkbox, Menu. The constraint: a single window must contain widgets all from the same platform — never a Mac checkbox next to a Windows button.

🧨 Starting point — no pattern at all

The most natural first cut. The Application class does all the construction itself.

class Application:
    def __init__(self, os_type: str):
        if os_type == "Windows":
            self.button   = WindowsButton()
            self.checkbox = WindowsCheckbox()
            self.menu     = WindowsMenu()
        elif os_type == "Mac":
            self.button   = MacButton()
            self.checkbox = MacCheckbox()
            self.menu     = MacMenu()
        elif os_type == "Linux":
            self.button   = LinuxButton()
            self.checkbox = LinuxCheckbox()
            self.menu     = LinuxMenu()
Four things hurt right away:
  • Construction logic inside Application — the business class knows every concrete widget name.
  • If/elif on a string — adding a fourth platform means modifying this code (OCP smell).
  • Triplet duplication — every dialog/window/popup that wants widgets repeats this pattern.
  • Nothing prevents accidental mixing — a junior dev refactoring this can typo self.checkbox = MacCheckbox() inside the Windows branch and ship a mixed-platform UI.

Let's see how far each pattern we already know gets us.

🧮 Attempt 1 — reach for Simple Factory

class WidgetFactory:
    @staticmethod
    def create_button(os_type):
        if os_type == "Windows": return WindowsButton()
        elif os_type == "Mac":   return MacButton()

    @staticmethod
    def create_checkbox(os_type):
        if os_type == "Windows": return WindowsCheckbox()
        elif os_type == "Mac":   return MacCheckbox()

    @staticmethod
    def create_menu(os_type): ...


# Caller
class Application:
    def __init__(self, os_type):
        self.button   = WidgetFactory.create_button(os_type)
        self.checkbox = WidgetFactory.create_checkbox("Mac")   # typo!
        self.menu     = WidgetFactory.create_menu(os_type)
The bug: nothing prevented us from passing "Mac" as the checkbox's platform string while everything else got os_type. The code runs. Tests pass. Users see a mixed-platform UI in production. Simple Factory has no concept of "family."

🧮 Attempt 2 — reach for Factory Method (per widget)

class ButtonCreator(ABC):
    @abstractmethod
    def create(self) -> Button: ...


class WindowsButtonCreator(ButtonCreator):
    def create(self):
        return WindowsButton()


class MacButtonCreator(ButtonCreator):
    def create(self):
        return MacButton()


class LinuxButtonCreator(ButtonCreator):
    def create(self):
        return LinuxButton()


# ... and the same triple-pattern repeats for Checkbox and Menu
# (CheckboxCreator + WindowsCheckboxCreator + MacCheckboxCreator + LinuxCheckboxCreator)
# (MenuCreator     + WindowsMenuCreator     + MacMenuCreator     + LinuxMenuCreator)


# Caller: three SEPARATE creator parameters - nothing holds them together
class Application:
    def __init__(self, button_c, checkbox_c, menu_c):
        self.button   = button_c.create()
        self.checkbox = checkbox_c.create()
        self.menu     = menu_c.create()


# Mixing is still possible:
app = Application(
    WindowsButtonCreator(),
    MacCheckboxCreator(),       # still nothing stops this
    WindowsMenuCreator(),
)
Same bug, different surface. We can still hand Application three creators from three different platforms. Factory Method gave us extensibility but did nothing for family consistency.

✅ Attempt 3 — Abstract Factory: one factory for the whole family

class WidgetFactory(ABC):
    """Abstract Factory: each subclass produces a COMPLETE family."""
    @abstractmethod
    def create_button(self) -> Button: ...
    @abstractmethod
    def create_checkbox(self) -> Checkbox: ...
    @abstractmethod
    def create_menu(self) -> Menu: ...


class WindowsWidgetFactory(WidgetFactory):
    def create_button(self):   return WindowsButton()
    def create_checkbox(self): return WindowsCheckbox()
    def create_menu(self):     return WindowsMenu()

class MacWidgetFactory(WidgetFactory):
    def create_button(self):   return MacButton()
    def create_checkbox(self): return MacCheckbox()
    def create_menu(self):     return MacMenu()


class Application:
    def __init__(self, factory: WidgetFactory):
        # ONE factory. Family-consistent BY CONSTRUCTION.
        self.button   = factory.create_button()
        self.checkbox = factory.create_checkbox()
        self.menu     = factory.create_menu()


# Mixing is IMPOSSIBLE - you can pass exactly one factory.
win_app = Application(WindowsWidgetFactory())
mac_app = Application(MacWidgetFactory())

The key win: The type system / class structure now enforces what was previously a runtime invariant. You cannot accidentally hand Application a mix — there's only one factory parameter, and the family travels together.

Real-world Abstract Factories you've already touched

  • Database drivers: connection + cursor + transaction come as a Postgres family or a MySQL family — never mixed. sqlalchemy.create_engine picks the family.
  • Cloud SDKs: boto3.client("s3") hands you the AWS-S3 family of resources; you don't accidentally get an Azure blob client.
  • UI toolkits: QtWidgets on Windows vs. Mac — the OS-native theme is wired in via an abstract factory under the hood.
  • Test doubles: a "fake" abstract factory that produces fake DB, fake email sender, fake clock — lets your service swap its entire infra family in tests.

🧰 Worked example A — Test infrastructure factory

A service needs a database, email sender, and clock. In production you want the real things; in tests you want fakes. The constraint: they must match — if you're using the fake DB, you also want the fake clock and fake mailer (otherwise tests are flaky and slow).

from abc import ABC, abstractmethod

# --- Abstract products ---
class Database(ABC):
    @abstractmethod
    def save(self, record): ...


class Mailer(ABC):
    @abstractmethod
    def send(self, to, msg): ...


class Clock(ABC):
    @abstractmethod
    def now(self): ...


# --- Production family ---
class PostgresDatabase(Database):
    def save(self, record): print("→ postgres INSERT")


class SmtpMailer(Mailer):
    def send(self, to, msg): print(f"→ SMTP send to {to}")


class SystemClock(Clock):
    def now(self):
        import datetime; return datetime.datetime.utcnow()


# --- Test family (all fakes that work together) ---
class InMemoryDatabase(Database):
    def __init__(self): self.records = []
    def save(self, record): self.records.append(record)


class CapturingMailer(Mailer):
    def __init__(self): self.sent = []
    def send(self, to, msg): self.sent.append((to, msg))


class FrozenClock(Clock):
    def __init__(self, fixed): self.fixed = fixed
    def now(self): return self.fixed


# --- Abstract Factory ---
class InfraFactory(ABC):
    @abstractmethod
    def create_db(self) -> Database: ...
    @abstractmethod
    def create_mailer(self) -> Mailer: ...
    @abstractmethod
    def create_clock(self) -> Clock: ...


# --- Concrete factories: one per family ---
class ProductionInfraFactory(InfraFactory):
    def create_db(self):     return PostgresDatabase()
    def create_mailer(self): return SmtpMailer()
    def create_clock(self):  return SystemClock()


class TestInfraFactory(InfraFactory):
    def create_db(self):     return InMemoryDatabase()
    def create_mailer(self): return CapturingMailer()
    def create_clock(self):
        import datetime
        return FrozenClock(datetime.datetime(2026, 1, 1))


# --- Service depends on the abstract factory ---
class OrderService:
    def __init__(self, infra: InfraFactory):
        self.db     = infra.create_db()
        self.mail   = infra.create_mailer()
        self.clock  = infra.create_clock()


# In production:
prod_service = OrderService(ProductionInfraFactory())

# In tests:
test_service = OrderService(TestInfraFactory())
# Guaranteed: in-memory DB + capturing mailer + frozen clock - all consistent

🧰 Worked example B — Cloud provider SDK

A multi-cloud app needs file storage, a queue, and a notification service. Each cloud provider has its own native services — AWS S3 + SQS + SNS, GCP GCS + Pub/Sub + ... etc. The constraint: once you pick a cloud, everything has to match.

class CloudFactory(ABC):
    @abstractmethod
    def create_blob_store(self) -> BlobStore: ...
    @abstractmethod
    def create_queue(self) -> Queue: ...
    @abstractmethod
    def create_notifier(self) -> Notifier: ...


class AwsCloudFactory(CloudFactory):
    def create_blob_store(self): return S3BlobStore(...)
    def create_queue(self):      return SqsQueue(...)
    def create_notifier(self):   return SnsNotifier(...)


class GcpCloudFactory(CloudFactory):
    def create_blob_store(self): return GcsBlobStore(...)
    def create_queue(self):      return PubSubQueue(...)
    def create_notifier(self):   return FcmNotifier(...)


class AzureCloudFactory(CloudFactory):
    def create_blob_store(self): return AzureBlobStore(...)
    def create_queue(self):      return ServiceBusQueue(...)
    def create_notifier(self):   return AzureNotificationHub(...)


# Caller picks ONE cloud factory. Everything below is consistent by construction.
cloud = AwsCloudFactory()    # or GcpCloudFactory(), or AzureCloudFactory()
files = cloud.create_blob_store()
queue = cloud.create_queue()
notif = cloud.create_notifier()

📊 How often you'll see Abstract Factory: rare — roughly 1–2 out of 10 codebases use it. It's the right tool for a narrow problem (matching product families) and overkill for everything else. Show up most often in: cross-platform UI toolkits, multi-cloud SDKs, multi-DB ORMs, test-double infrastructure, theme/skin systems. Recognize it when you see it; don't reach for it unless you have a real family-matching constraint.

Do callers need to pick a concrete class?
No — one obvious class → just use the constructor

One last check — when no factory is the right answer

Question — Why is PointFactory a bad idea?

class PointFactory:
    @staticmethod
    def create(x, y):
        return Point(x, y)

# vs. just:
p = Point(10, 20)
Correct! Factory shines when there's a choice to centralize — which concrete class, which configuration, which family. Point(x, y) has no choice. The "factory" just adds an indirection that hides... nothing.

Rule of thumb: if removing the factory and inlining ConcreteClass(...) at the call site makes the code shorter and equally clear, you didn't need the factory.

The three triggers that justify a factory, in order of strength:
1. The same construction logic appears in many call sites (DRY) → Simple Factory
2. You're adding new types and want to stop modifying existing code (OCP) → Factory Method
3. Products travel in families that must match (consistency) → Abstract Factory

If none of these are true, just call the constructor.

Mindmap Summary

The Factory Family at a Glance

Three patterns, three different problems, one mental model.

FACTORY FAMILY
Centralize the “which concrete class do I instantiate?” choice
1. Simple Factory
One static create() method with an if/elif. Centralizes where objects are constructed.
Cures: DRY violation (scattered construction)
Breaks: OCP — adding types means editing the factory
Frequency: 📊 ~7–8/10 codebases
2. Factory Method
Abstract creator + one subclass per type. Each subclass owns its create_x().
Cures: OCP — new types are added, not edited in. Also DIP for callers.
Costs: more classes; string→creator lookup must live somewhere
Frequency: 📊 ~4–5/10 codebases (library/framework heavy)
3. Abstract Factory
Abstract factory producing many related products. Each concrete factory hands over the whole family.
Cures: family-mixing bugs — structurally impossible to combine products from different families
Costs: most ceremony of the three; needs a real cross-product invariant to justify
Frequency: 📊 ~1–2/10 codebases (cross-platform UI, multi-cloud, multi-DB, theme/skin systems, test doubles)
⚠️ The anti-pattern: PointFactory
No choice to centralize → no factory. Point(x, y) doesn't need a factory; it needs a constructor. The three triggers that justify any factory: DRY (duplicated construction across callers), OCP (new types added often), family consistency (products that must match).

🎯 Decision tree — pick by question

Do callers need to choose a concrete class?
No, only one concrete class exists → just call the constructor
Yes, few stable types → Simple Factory (one static method)
Yes, types added often → Factory Method (abstract creator + subclasses)
Yes AND products travel in matching families → Abstract Factory

🎯 Interview cheat sheet

If asked “implement Factory for X”:

  1. Sketch the abstract product first (the interface every concrete class will honor).
  2. Show the concrete products — same shape, different bodies.
  3. Add the simplest variant first: a @staticmethod create() on a Factory class with the if/elif. Name the OCP problem in this version out loud.
  4. Refactor to Factory Method: AbstractCreator + one subclass per type. Point out the DIP win (caller depends only on the abstraction).
  5. If asked “but what if the products must come in matching families?” — that's the cue for Abstract Factory.
  6. Mention the anti-pattern: PointFactory. Naming the over-engineering case shows pattern fluency.

🎯 One-line summary

Factory patterns centralize the “which concrete class do I create, with what configuration?” choice. Simple Factory cures duplication. Factory Method additionally cures OCP and gets you DIP for free. Abstract Factory additionally enforces family consistency. Each step up adds machinery — reach for it only when the problem fits the shape.
