Design Patterns & The Singleton

LLD-15 • Low Level Design

Patterns are vocabulary — the shorthand experienced engineers use to communicate proven solutions. Today we meet the family, then go deep on the most famous (and most abused) member: Singleton.

What & Why

What Are Design Patterns?

Proven, named solutions to problems that keep showing up in software design.

📚 The book that started it all: In 1994, four authors (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides — the “Gang of Four”) published Design Patterns: Elements of Reusable Object-Oriented Software. They catalogued 23 patterns they had seen experienced engineers reinvent across projects, and gave each one a name. That book is still the reference 30 years later.

Patterns Are Vocabulary, Not Code

❌ Without patterns

  • Reinvent the wheel every time
  • Inconsistent solutions across the codebase
  • Hard to communicate designs in reviews / interviews
  • “That class with the static factory method that returns…” (10 sentences)

✔ With patterns

  • Proven solution, ready to apply
  • Consistent shape across the codebase
  • Common vocabulary: “let's use a Strategy here”
  • Shorthand both readers and reviewers understand

Important framing: a pattern is a recipe, not source code. Two implementations of the same pattern in two languages can look totally different — what makes them “the same pattern” is the shape of the problem they solve and the shape of the solution. When you say “I used Strategy here,” you are pointing at a structure, not pasting code.

The Map

The Three Categories

The Gang of Four split the 23 patterns into three groups based on what kind of problem they solve.

🌍 Creational
"How do I CREATE this?"
🏗️ Structural
"How do I COMPOSE this?"
🧐 Behavioral
"How do these COMMUNICATE?"

🌍 1. Creational — Object Creation

When the question is “how should objects come into existence?”

PatternPurposeReal-world example
SingletonExactly one instance of a classApp config, connection pool, logger
FactoryCreate objects without naming the exact classDifferent DB drivers, payment gateways
BuilderConstruct complex objects step-by-stepQuery builders, HTTP request builders
PrototypeClone an existing object as a templateCloning configurations, copying records

🏗️ 2. Structural — Object Composition

When the question is “how do I assemble objects into larger structures?”

PatternPurposeReal-world example
AdapterMake a class fit an unrelated interfaceWrapping a legacy API
DecoratorAdd behavior to an object without changing its classLogging, caching, auth wrappers
FacadeOne simple interface in front of a complex subsystemA “PaymentService” over 5 vendor SDKs
ProxyA stand-in object that controls access to the real oneLazy loading, access control, remoting

When the question is “how should objects talk to each other?”

⚠️ Patterns are tools, not rules. If a 10-line function solves your problem, do not force a pattern on it. Patterns earn their keep when:
  • The same problem is recurring
  • The team already knows the pattern (shared vocabulary)
  • You're at a system boundary where flexibility actually matters

Today's focus: Singleton — the most commonly used, most commonly misused, simplest pattern in the catalog. It's the right place to start because it forces you to confront object creation, Python's __new__ vs __init__, thread safety, and how patterns interact with the language itself.

Pre-flight Check

Prerequisites — Quick Quiz

Four warm-up questions. Singleton leans on these concepts hard — if you get them, the implementations to come will feel obvious.

Question 1 — Class vs Instance variables

class Counter:
    count = 0                       # What kind of variable is this?

    def __init__(self):
        self.instance_count = 0

    def increment(self):
        Counter.count += 1
        self.instance_count += 1

c1 = Counter()
c2 = Counter()
c1.increment()
c2.increment()

print(Counter.count, c1.instance_count, c2.instance_count)
Correct! Counter.count is a class variable — one copy shared by every instance. self.instance_count is an instance variable — one copy per object. Singleton implementations always use a class variable (like _instance) to store the shared instance, so this distinction is foundational.

Question 2 — Encapsulation in Python

class BankAccount:
    def __init__(self, balance):
        self._balance = balance      # single underscore
        self.__secret = "12345"     # double underscore

account = BankAccount(1000)
print(account._balance)              # works?
print(account.__secret)             # works?
print(account._BankAccount__secret) # works?
Correct! _balance is convention only (still accessible). __secret gets name-mangled to _BankAccount__secret, so the second line fails but the third (using the mangled name) succeeds. Takeaway: Python has no true private — it gives you hints and trust. Any Singleton implementation can be circumvented by a determined caller. Document intent; don't pretend it's a fortress.

Question 3 — Object creation order

class MyClass:
    def __new__(cls):
        print("__new__ called")
        return super().__new__(cls)

    def __init__(self):
        print("__init__ called")

obj = MyClass()
Correct! __new__ creates the object (allocates memory, returns an instance). __init__ initializes it. Most code only customizes __init__; Singleton needs to customize __new__ because we want to intercept creation and sometimes return an existing instance. This is the single most important insight for the classic Singleton implementation.

Question 4 — Which scenario genuinely needs one instance?

Correct! A connection pool manages a finite, shared resource — two pools = double the connections = blown DB limits. Users, carts, and blog posts are domain objects — you legitimately want many. Rule of thumb: Singleton is for infrastructure (config, log, pool, cache, registry). Never for things your domain naturally has many of.

If you got all four: you're ready. The pieces — class variables to store the shared instance, __new__ to intercept creation, no true privacy so we use conventions, and a clear list of when Singleton is actually appropriate — are exactly what the next sections build on.

Motivation

The Problem Singleton Solves

Some resources are expensive to create and dangerous to duplicate. Let's see what happens when we don't control creation.

Your team writes a Database class. Two engineers add features in different modules. Each instantiates Database() to use it. The DB has a hard cap of 50 simultaneous connections. By the end of the quarter, the app is OOM-ing in production and the DB is rejecting 30% of requests. What went wrong?

the_problem.py
▼
class Database:
    def __init__(self):
        print("Creating expensive DB connection...")
        self.connection = "Connected to PostgreSQL"

# Module A:
db1 = Database()    # "Creating expensive DB connection..."

# Module B (someone else's code):
db2 = Database()    # "Creating expensive DB connection..."  AGAIN!

print(db1 is db2)    # False - two separate connections, both alive
What just broke:
  • Resource exhaustion — every module that calls Database() opens a new socket
  • Memory waste — duplicate state, duplicate buffers
  • Inconsistent state — one connection's transaction can't see the other's
  • Hidden contention — you don't know which connection a query went through

What We Want

A way to say: “However many times anyone in this process calls Database(), give them the same one instance.” That's the Singleton pattern in one sentence.

There are 4 standard ways to do this in Python, plus a thread-safety twist. We'll meet each one, and for each one we'll ask the uncomfortable question: “how could a colleague accidentally break this?”

Implementation 1

Approach 1 — The Classic __new__

The textbook implementation. Intercept object creation and return the same instance every time.

The Intuition

Recall from the prereq quiz: __new__ runs before __init__ and is what actually creates the object. If we override it, we can lie. The first time someone calls Database(), we genuinely create an object and stash it on the class. Every subsequent call, we just hand back the stashed one.

01_new_singleton.py
▼
class Database:
    _instance = None            # class variable - holds the one instance

    def __new__(cls):
        if cls._instance is None:
            print("Creating the one and only instance")
            cls._instance = super().__new__(cls)
        return cls._instance       # always the same object

    def __init__(self):
        print("__init__ called")
        self.connection = "postgresql://localhost:5432"

db1 = Database()
# Creating the one and only instance
# __init__ called

db2 = Database()
# __init__ called    <-- !!! runs again on the SAME object

print(db1 is db2)    # True - same object
The __init__ gotcha: Even though __new__ returned the existing instance, Python still calls __init__ on it — every single time someone writes Database(). If __init__ mutates state, you'll silently overwrite the data on each call.

Fix: guard __init__ with an initialized flag

class Database:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False
        return cls._instance

    def __init__(self):
        if self._initialized:
            return          # skip - already set up
        self.connection = "postgresql://localhost:5432"
        self._initialized = True

💥 How a Colleague Can Accidentally Break It

The classic __new__ singleton has four well-known failure modes. Each one is a real story from a real codebase.

💥 Break 1 — Subclassing leaks instances (common beginner mistake)

A very common beginner version hardcodes the parent class name inside __new__ instead of using cls. The first subclass that's instantiated wins; every subsequent call — even from a sibling subclass — returns that same instance with the wrong type.

class Database:
    _instance = None
    def __new__(cls):
        if Database._instance is None:   # MISTAKE: hardcoded `Database`
            Database._instance = super().__new__(cls)
        return Database._instance

class Postgres(Database): pass
class MySQL(Database):    pass

a = Postgres()
b = MySQL()
print(type(a).__name__)   # Postgres
print(type(b).__name__)   # Postgres  !!! should be MySQL
print(a is b)             # True - they share ONE instance

Using cls._instance (instead of hardcoded Database._instance) avoids this particular bug, but introduces a different surprise: each subclass becomes its own singleton, which may not be what you wanted.

Fix: store instances per-class in a dict (_instances = {} keyed by cls) and be explicit about the intent: one-per-hierarchy or one-per-class.

💥 Break 2 — copy.deepcopy() bypasses __new__

deepcopy doesn't call your constructor — it walks the object graph and creates fresh objects directly. Your singleton check never runs.

import copy
db1 = Database()
db2 = copy.deepcopy(db1)

print(db1 is db2)              # False! Two instances exist
print(type(db1) is type(db2))  # True - same class
# You now have two "singletons". The invariant is broken silently.

Fix: implement __copy__ and __deepcopy__ to return self.

💥 Break 3 — pickle creates a new instance on load

Pickling serializes the object state; unpickling reconstructs it via __new__ — but in another process, cls._instance is None again. Cross-process serialization quietly clones your singleton.

import pickle
db1 = Database()
data = pickle.dumps(db1)
db2 = pickle.loads(data)

print(db1 is db2)    # False if loaded in a fresh process
# Distributed apps, Celery workers, multiprocessing - all hit this.

Fix: implement __reduce__ so pickle routes through your factory.

💥 Break 4 — Two threads see _instance is None at the same time

A classic race condition. If two threads both pass the if cls._instance is None check before either assigns, both will create instances. The second assignment overwrites the first, and the first thread walks away with an orphan singleton that nobody else has.

# Timeline (interleaved execution):
# Thread A: if cls._instance is None:  -> True
# Thread B: if cls._instance is None:  -> True (still None!)
# Thread A: cls._instance = super().__new__(cls)  # instance A
# Thread B: cls._instance = super().__new__(cls)  # instance B (overwrites!)
# Thread A held a reference to instance A; everyone else now uses B.

Fix: double-checked locking with threading.Lock() — covered in the Threading section below.

Implementation 2

Approach 2 — Decorator

Keep the class clean. Bolt the Singleton-ness on from outside with a reusable decorator.

The Intuition

A decorator is just a function that takes a class and returns something else. Our decorator replaces the class with a tiny factory function that caches the first instance and returns it every time. The class itself stays pristine — no _instance, no __new__ tricks.

02_decorator_singleton.py
▼
def singleton(cls):
    instances = {}                          # closure - per-decorator cache

    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]

    return get_instance


@singleton
class Database:
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"

db1 = Database()    # "Database initialized"
db2 = Database()    # (silent - cached)
print(db1 is db2)    # True
Why teams like this: the class file looks like a normal class. Singleton behavior is one line: @singleton. The same decorator works for any class. Cleanest separation of concerns of the four approaches.

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — isinstance() stops working

After decoration, the name Database doesn't refer to a class anymore — it refers to get_instance, which is a function. Anyone calling isinstance(x, Database) gets a TypeError.

@singleton
class Database: ...

db = Database()
isinstance(db, Database)
# TypeError: isinstance() arg 2 must be a type, not function

type(Database)    # <class 'function'> - NOT <class 'type'>

A teammate writes a type check; everything blows up in code that worked yesterday. Fix: use a class-based decorator or a metaclass (next approach).

💥 Break 2 — You can't subclass it sanely

Since Database is now a function, class ReadOnlyDatabase(Database) errors out: you can't inherit from a function.

class ReadOnlyDatabase(Database):    # TypeError
    pass
# TypeError: function() argument 'code' must be code, not str

Fix: avoid this decorator when you anticipate inheritance.

💥 Break 3 — Different argument lists silently return the SAME instance

The decorator caches by class, not by args. A second caller passing different config silently gets the first caller's instance — and may believe it's been configured with the new values.

@singleton
class Database:
    def __init__(self, host):
        self.host = host

prod = Database("prod.example.com")
test = Database("localhost")        # IGNORED - args silently dropped

print(test.host)    # "prod.example.com"  !!!

Fix: raise an error if a singleton is called with args after first creation, or document the behavior loudly.

💥 Break 4 — Pickling/copying still doesn't go through the decorator

Same vulnerability as __new__: deepcopy and pickle.loads work on the underlying class object and bypass the cache.

Implementation 3

Approach 3 — Metaclass

The most powerful approach. Hook into the “class of classes.” Survives isinstance(), survives subclassing, but the heaviest machinery.

The Intuition (in one paragraph)

Classes are objects too. Every class is an instance of some metaclass — usually type. When you write Database(), Python actually calls type.__call__(Database). If we replace type with our own metaclass that overrides __call__, we get to control what happens at the call site — before __new__ ever runs. So we cache the first instance there.

03_metaclass_singleton.py
▼
class SingletonMeta(type):
    _instances = {}

    def __call__(cls, *args, **kwargs):
        # __call__ runs when someone writes ClassName(...)
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class Database(metaclass=SingletonMeta):
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"


db1 = Database()      # "Database initialized"
db2 = Database()      # (silent - same instance)
print(db1 is db2)      # True
isinstance(db1, Database)   # True (works!)
Why this wins for libraries: Database stays a real class. isinstance() works. Subclassing works (and each subclass gets its own singleton, since the cache key is cls). __init__ only runs on the first call, naturally — because __call__ only delegates to super().__call__ the first time.

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — Metaclass conflict on multiple inheritance

If you try to mix a singleton class with another base that has a different metaclass (e.g. an ABC), Python refuses: “metaclass conflict”.

from abc import ABC, ABCMeta

class Database(ABC, metaclass=SingletonMeta):  # BOOM
    pass
# TypeError: metaclass conflict
# Need a combined metaclass: class Combined(SingletonMeta, ABCMeta): ...

Fix: build a combined metaclass that inherits from both.

💥 Break 2 — deepcopy / pickle still bypass it

Same root cause as the __new__ approach. deepcopy goes through __deepcopy__ if defined, otherwise constructs a new object directly. pickle.loads reconstructs via __reduce__. Neither calls SingletonMeta.__call__.

💥 Break 3 — Bypass via object.__new__

A determined caller can call object.__new__(Database) directly — this skips the metaclass __call__ entirely and produces a fresh, uninitialized object.

db1 = Database()
db2 = object.__new__(Database)   # bypasses metaclass
print(db1 is db2)               # False - rogue instance
isinstance(db2, Database)         # True - looks legit

Python gives you no way to prevent this; it's a reminder that Singleton is a discipline, not a security feature.

💥 Break 4 — Threading race in __call__

Same race as the __new__ approach. Add a lock in __call__ with double-checked locking.

Implementation 4 — Recommended

Approach 4 — Module-Level Instance (the Pythonic way)

Python imports a module at most once per interpreter. That's already a singleton. Use it.

The Intuition

When you write import database, Python runs the module top-to-bottom once, caches the result in sys.modules, and returns the cached module on every subsequent import. So any object you create at module top-level is automatically a singleton across your entire process. No __new__ trickery, no decorator, no metaclass — just an import.

database.py
▼
class _Database:                  # underscore = "don't instantiate me directly"
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"

    def query(self, sql):
        return f"Executing: {sql}"


# Create THE instance at module load time
database = _Database()
app.py
▼
from database import database

database.query("SELECT * FROM users")
# Every import in every module gets the SAME object.
# No singleton machinery needed.
Why this is the recommended approach in Python:
  • Simplest possible code — no special pattern
  • Thread-safe by default — the import lock guarantees one-time initialization
  • Works with isinstance() against _Database
  • Lazy if you want it (move database = _Database() into a function)

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — Someone instantiates the underlying class directly

The underscore on _Database is a convention, not enforcement. A teammate who imports the class can create more instances.

from database import _Database     # technically allowed
rogue = _Database()              # second instance!

Mitigations: name it __Database (name-mangling makes it harder), or make __init__ guard against re-creation, or just trust your teammates and document intent.

💥 Break 2 — importlib.reload() creates a fresh instance

If a tool (some IDEs, some test runners) reloads the module, the top-level database = _Database() runs again. You now have two instances coexisting — old references hold one, new imports get the other.

import importlib, database
old = database.database
importlib.reload(database)
new = database.database

print(old is new)    # False - two coexisting "singletons"
💥 Break 3 — The same module imported under two paths

Python caches by module name (key in sys.modules). If your project structure (or a relative-vs-absolute import mishap) makes the same file load under two different names, you get two module objects — two singletons.

from myapp.database import database     # sys.modules["myapp.database"]
from database         import database     # sys.modules["database"]
# Different module objects -> different `database` instances

Fix: always use absolute imports; configure the project structure properly.

💥 Break 4 — Multiprocessing breaks every singleton, including this one

A “singleton” is per-Python-process. The moment you fork or use multiprocessing, each child has its own copy of memory and its own singleton. Same with multiple Gunicorn workers, multiple Celery processes, multiple containers. This is true for every Singleton implementation — not unique to modules.

Threading

Making It Thread-Safe: Double-Checked Locking

The race condition we saw in every approach has a standard fix — and a standard optimization.

Naive Lock: Correct but Slow

The obvious fix: wrap the whole __new__ in a lock. Only one thread can be inside at a time, so the race vanishes. But now every call — including the millions of calls after the instance is created — pays for lock acquisition.

import threading

class Database:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        with cls._lock:                  # EVERY call acquires the lock - slow
            if cls._instance is None:
                cls._instance = super().__new__(cls)
            return cls._instance

Double-Checked Locking: Fast and Safe

Check first (cheap, no lock). Only acquire the lock if the instance is missing. Inside the lock, check again — another thread may have built it while we were waiting.

04_thread_safe_singleton.py
▼
import threading

class Database:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:             # 1st check (no lock)
            with cls._lock:
                if cls._instance is None:         # 2nd check (inside lock)
                    cls._instance = super().__new__(cls)
        return cls._instance

Timeline (interleaved threads):

Thread A
check 1: None → acquire lock → check 2: None → create → release
Thread B
check 1: None → wait for lock → (A finished, B enters) → check 2: EXISTS → return
Thread C (later)
check 1: exists → return immediately (no lock acquired, fast path)
The same pattern works for every approach:
  • __new__ approach: lock around the check inside __new__
  • Decorator: lock around the dict access inside get_instance
  • Metaclass: lock around the check inside SingletonMeta.__call__
  • Module-level: already thread-safe — Python's import lock guarantees one-time initialization

Practical note: CPython has the GIL, so in practice the race window is small. But “small” is not “impossible,” and it bites under asyncio, threading with I/O, and most importantly — on free-threaded Python (PEP 703) where the GIL is gone. If you write a Singleton intended to live in a threaded app, use the double-check pattern.

In Practice

Real-World Use Cases

Three places where Singleton genuinely earns its keep.

⚙️
Configuration Manager
One source of truth for application settings: DB URLs, API keys, feature flags. Two configs = two views of the world = bugs.
📝
Logger
Centralize log writes. Multiple loggers fighting over the same file = interleaved / corrupted entries.
🔌
Connection Pool
Bound the number of open sockets to the DB / Redis / message broker. One pool, shared cap.
📊
In-Memory Cache
Sharing data across modules requires one cache — otherwise each module has its own “cache.”
📑
Registry / Plugin Map
Decorators that register handlers (recall the OCP plugin pattern) read/write a shared registry — a Singleton by nature.
⏱️
Thread / Worker Pool
One pool = controlled concurrency. Multiple pools = uncontrolled fan-out.

Pulled-together example: Config + Logger

05_use_cases.py
▼
# config.py - module-level singleton
class _Config:
    def __init__(self):
        self.db_host    = "localhost"
        self.db_port    = 5432
        self.debug      = True
        self.api_key    = "secret_123"

config = _Config()


# logger.py - decorator singleton
def singleton(cls):
    instances = {}
    def get(*args, **kw):
        if cls not in instances:
            instances[cls] = cls(*args, **kw)
        return instances[cls]
    return get

@singleton
class Logger:
    def __init__(self):
        self.file = open("app.log", "a")
    def info(self, msg):
        self.file.write(f"[INFO] {msg}\n")
        self.file.flush()


# anywhere in the app:
from config import config
from logger import Logger
Logger().info(f"connecting to {config.db_host}")
Anti-Patterns

When NOT to Use Singleton

Singleton is the most misused pattern in software. Three concrete smells.

❌ Anti-pattern 1 — The "Utils" god object

▼

A Singleton class that grows methods over time until it has nothing in common. This is just a global variable with a fancy hat.

@singleton
class Utils:
    def format_date(self, d): ...
    def send_email(self, to): ...
    def calculate_tax(self, amt): ...
    def resize_image(self, img): ...
# These have NOTHING to do with each other. Just use modules.

Fix: separate modules; plain functions. Python is already organized around modules; you don't need a Singleton class to namespace utilities.

❌ Anti-pattern 2 — Hidden dependencies (untestable code)

▼

A Singleton reached inside method bodies makes the dependency invisible. Tests can't substitute a fake. Refactoring is dangerous.

❌ Hidden dependency

class OrderService:
    def place(self, order):
        Logger().info("placing")   # hidden
        DB().save(order)              # hidden

# Tests can't replace Logger or DB

✔ Injected

class OrderService:
    def __init__(self, logger, db):
        self.logger = logger
        self.db = db
    def place(self, order):
        self.logger.info("placing")
        self.db.save(order)

Rule: Singletons live at the edge (the composition root). Business code receives its dependencies, doesn't reach for them.

❌ Anti-pattern 3 — Domain objects as Singletons

▼

If your domain naturally has many instances — users, orders, products, blog posts — do not make them Singletons. The pattern exists for infrastructure (one connection pool, one config). A web app with one User object is not a web app.

Summary

Comparison & Decision Guide

All four approaches, side by side, plus a quick decision tree.

ApproachComplexityPythonicThread-safe by defaultBest for
Module-level⭐ lowest⭐⭐⭐ very✅ yesDefault choice in Python
__new__⭐⭐ medium⭐⭐ moderate❌ needs lockTeaching the pattern, fine control

🎯 Quick Decision Tree

Need exactly one instance?
Simple application code → module-level instance
Threaded application → module-level or double-checked locking
Library / framework / need isinstance() + subclassing → metaclass
Several classes need it, want clean code → decorator
Learning / interview question → start with __new__, explain the gotchas

Interview tip: If asked to implement Singleton, write __new__ on the board first — it shows you understand object creation. Then mention thread-safety with double-checked locking. Then say: “In real Python code I'd usually just use a module-level instance — it's the simplest correct singleton in the language.” That answer signals you know the pattern and when not to over-engineer it.

🎯 The One-Line Summary

Singleton ensures exactly one instance of a class per process. In Python, you usually get it for free by exporting an instance at module level. The other three implementations exist for situations where you need isinstance() checks, inheritance, or framework-level control. Always ask first: “do I really need this, or is it just a global in disguise?”
