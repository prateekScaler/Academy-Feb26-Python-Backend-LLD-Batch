Today's focus: Singleton — the most commonly used and most commonly misused pattern. The right place to start because it forces you to confront object creation, __new__ vs __init__, and thread safety all at once.

Pre-flight Check

Prerequisites — Quick Quiz

Five warm-up questions. Singleton leans on these concepts hard — if you get them, the implementations to come will feel obvious.

Question 1 — Class vs Instance variables

class Counter:
    count = 0                       # What kind of variable is this?

    def __init__(self):
        self.instance_count = 0

    def increment(self):
        Counter.count += 1
        self.instance_count += 1

c1 = Counter()
c2 = Counter()
c1.increment()
c2.increment()

print(Counter.count, c1.instance_count, c2.instance_count)
Correct! Class variable = one copy, shared. Instance variable = one copy per object.
Memory layout (one box per object)
class Counter
count = 2  ⬅️ shared
c1 (instance)
instance_count = 1
c2 (instance)
instance_count = 1
↑ c1.increment() bumps the shared count on the class AND its own instance_count. c2.increment() bumps the same shared count but its own instance_count.

Why this matters for Singleton: we'll store the “one and only” instance as a class variable (_instance) — precisely because every instance / subclass / module of code that touches the class sees the same shared box.

Question 2 — Encapsulation in Python

class BankAccount:
    def __init__(self, balance):
        self._balance = balance      # single underscore
        self.__secret = "12345"     # double underscore

account = BankAccount(1000)
print(account._balance)              # works?
print(account.__secret)             # works?
print(account._BankAccount__secret) # works?
Correct! Here is the rule, compactly:
PrefixWhat Python doesAccessible?
nameNothing special — public✅ Yes
_nameConvention only: “don't touch”✅ Yes (but rude)
__nameName-mangled to _ClassName__name✅ via mangled name
__dunder__Reserved for Python (e.g. __init__)✅ Yes

Key takeaways for Singleton:

  • Python has no true private — only hints + trust
  • Any Singleton can be bypassed by a determined caller
  • Document intent; don't pretend it's a fortress

Question 3 — In Python, what is the “constructor”?

Most languages have one thing called “the constructor” that both allocates memory and initializes the object. Python is different. Pause and recall — which method is responsible for what?

Correct! Construction in Python is a two-step process:
StepMethodJobFirst argReturns
1__new__Allocate memory for a new instancecls (the class)The new instance
2__init__Set up the instance's attributesself (the instance)None

99% of Python code only ever defines __init__ because the default __new__ on object handles memory allocation just fine. Singleton is the rare case where we need to override __new__ — because we want to intercept “create a new object” and sometimes say “no, give them the existing one.”

Question 4 — Object creation order

class MyClass:
    def __new__(cls):
        print("__new__ called")
        return super().__new__(cls)

    def __init__(self):
        print("__init__ called")

obj = MyClass()
Correct! __new__ first (creates the object), then __init__ (initializes it). Now let's decode that return super().__new__(cls) line — you'll see it in every Singleton:
Bit of codeWhat it means
super() (with parens)The parent class as a usable proxy. super (no parens) is just the class — you can't call methods on it directly.
super().__new__Reach the parent's __new__. For most classes, the parent is object, and object.__new__ is the one that actually allocates memory.
__new__(cls)We pass cls (our class, e.g. Database) so the new object is of our type, not of type object.
return ...__new__ must return an instance. If it forgets, __init__ is never called.

The mental model: __new__ in your class doesn't allocate memory itself — it delegates that to object.__new__ via super(). Our customisation is just around the allocation: “before allocating, check if we already have one; after allocating, remember it for next time.”

Question 5 — Which scenario genuinely needs one instance?

Correct! A connection pool manages a finite, shared resource — two pools = double the connections = blown DB limits. Users, carts, and blog posts are domain objects — you legitimately want many. Rule of thumb: Singleton is for infrastructure (config, log, pool, cache, registry). Never for things your domain naturally has many of.

If you got all four: you're ready. The pieces — class variables to store the shared instance, __new__ to intercept creation, no true privacy so we use conventions, and a clear list of when Singleton is actually appropriate — are exactly what the next sections build on.

Motivation

The Problem Singleton Solves

Some resources are expensive to create and dangerous to duplicate. Let's see what happens when we don't control creation.

Your team writes a Database class. Two engineers add features in different modules. Each instantiates Database() to use it. The DB has a hard cap of 50 simultaneous connections. By the end of the quarter, the app is OOM-ing in production and the DB is rejecting 30% of requests. What went wrong?

the_problem.py
▼
class Database:
    def __init__(self):
        print("Creating expensive DB connection...")
        self.connection = "Connected to PostgreSQL"

# Module A:
db1 = Database()    # "Creating expensive DB connection..."

# Module B (someone else's code):
db2 = Database()    # "Creating expensive DB connection..."  AGAIN!

print(db1 is db2)    # False - two separate connections, both alive
What just broke:
  • Resource exhaustion — every module that calls Database() opens a new socket
  • Memory waste — duplicate state, duplicate buffers
  • Inconsistent state — one connection's transaction can't see the other's
  • Hidden contention — you don't know which connection a query went through

What We Want

A way to say: “However many times anyone in this process calls Database(), give them the same one instance.” That's the Singleton pattern in one sentence.

There are 4 standard ways to do this in Python, plus a thread-safety twist. We'll meet each one, and for each one we'll ask the uncomfortable question: “how could a colleague accidentally break this?”

Approach 1

Approach 1 — The Classic __new__

The textbook implementation. Intercept object creation and return the same instance every time. We'll meet its two drawbacks — one we fix here, one we fix in Approach 2.

The Intuition

Recall from the prereq quiz: __new__ runs before __init__ and is what actually creates the object. If we override it, we can lie. The first time someone calls Database(), we genuinely create an object and stash it on the class. Every subsequent call, we just hand back the stashed one.

01a_new_basic.py
▼
class Database:
    _instance = None            # class variable - holds the one instance

    def __new__(cls):
        if cls._instance is None:
            print("Creating the one and only instance")
            cls._instance = super().__new__(cls)
        return cls._instance       # always the same object

    def __init__(self):
        print("__init__ called")
        self.connection = "postgresql://localhost:5432"

db1 = Database()
# Creating the one and only instance
# __init__ called

db2 = Database()
# __init__ called    <-- !!! runs again on the SAME object

print(db1 is db2)    # True - same object
The __init__ gotcha: Even though __new__ returned the existing instance, Python still calls __init__ on it — every single time someone writes Database(). If __init__ mutates state, you'll silently overwrite the data on each call.

Fix: guard __init__ with an initialized flag

01b_new_init_guard.py
▼
class Database:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False
        return cls._instance

    def __init__(self):
        if self._initialized:
            return          # skip - already set up
        self.connection = "postgresql://localhost:5432"
        self._initialized = True

💥 The Big Problem with This Approach: Threading

The __init__ gotcha above is real, but easy to fix. The structural problem with the classic __new__ implementation only shows up the moment more than one thread touches the class.

💥 The race — two threads see _instance is None at the same time

A classic race. Two threads both pass the if cls._instance is None check before either has a chance to assign — so both create an instance. The second assignment overwrites the first, leaving an orphan that one thread is still holding a reference to.

Timeline — time flows down ↓

Now the class holds Ⓑ, but Thread A is still using Ⓐ. Two “singletons” coexist.

Fix: double-checked locking with threading.Lock() — the very next section.

Approach 2

Approach 2 — Thread-Safe via Double-Checked Locking

Same Singleton, with a guard around the creation step. This is the implementation that actually holds up in a real (threaded) application.

First attempt: naive lock (correct but slow)

The obvious fix: wrap the whole __new__ in a lock. Only one thread can be inside at a time, so the race vanishes. But now every call — including the millions that happen after the instance is created — pays for lock acquisition.

import threading

class Database:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        with cls._lock:                  # EVERY call acquires the lock - slow
            if cls._instance is None:
                cls._instance = super().__new__(cls)
            return cls._instance

The Refinement: Double-Checked Locking (fast and safe)

Check first (cheap, no lock). Only acquire the lock if the instance is missing. Inside the lock, check again — another thread may have built it while we were waiting.

02_thread_safe_singleton.py
▼
import threading

class Database:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:             # 1st check (no lock - fast path)
            with cls._lock:
                if cls._instance is None:         # 2nd check (inside lock)
                    cls._instance = super().__new__(cls)
        return cls._instance

⏱️ What the three threads see

Thread A — very first call
check 1: None → acquire lock → check 2: still None → CREATE → release
Thread B — arrives during creation
check 1: None → wait for lock → (A finished, B enters) → check 2: EXISTS → return existing
Thread C — arrives later
check 1: exists → return immediately. No lock acquired.
Only the very first concurrent threads pay for the lock. Everyone else uses the fast path.

Practical note: CPython has the GIL, so in pure-Python code the race window is small. But “small” is not “impossible,” and it bites under asyncio, threading with I/O, and most importantly on free-threaded Python (PEP 703) where the GIL is gone. See the threading.Lock docs for the primitive we used here.

Checkpoint

Where We Are So Far

Two approaches in. Let's pin down what we've actually solved.

 Approach 1 — __new__Approach 2 — with double-checked lock
Returns the same instance for every call✅✅
__init__ runs only once (guarded by flag)✅✅
Survives multi-threading❌✅
Fast path after first creation (no lock)n/a✅
This is a perfectly good Singleton for most threaded apps. If you stop reading right here, you can implement a working, thread-safe Singleton in any Python codebase.

But Approach 2 still isn't the only way to write a Singleton in Python — and it isn't always the best way either. There are three alternative styles each suited to a different situation:

  • Module-level instance — the most Pythonic, often the simplest correct option
  • Decorator — bolt singleton-ness onto a class without touching it
  • Metaclass — the most powerful; library/framework code uses this

Each one is interesting and each one has its own failure modes. We'll meet them as optional alternatives, then end with a single hardened singleton that defends against every break we've seen.

Optional — Alternative Implementations

Three Other Ways to Build a Singleton

Each alternative is shorter or cleaner than the locked __new__ in some way — and breaks in a way that approach didn't. Read them as your toolbox, not your default.

The simplest Singleton in Python — just an object at module top-level. Thread-safe for free. Breaks under importlib.reload and multi-process.
🖆️

Reuse a tiny @singleton across many classes. Class file stays clean. Breaks isinstance() and silently drops constructor arguments.

Optional — A

Optional A — Module-Level Instance (the Pythonic way)

Python imports a module at most once per interpreter. That's already a singleton. Often the simplest correct option.

The Intuition

When you write import database, Python runs the module top-to-bottom once, caches the result in sys.modules, and returns the cached module on every subsequent import. Any object you create at module top-level is therefore a singleton across your whole process — no __new__ trickery, no decorator, no metaclass.

database.py
▼
class _Database:                  # underscore prefix - see explanation below
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"

    def query(self, sql):
        return f"Executing: {sql}"


# Create THE instance at module load time
database = _Database()
app.py
▼
from database import database

database.query("SELECT * FROM users")
# Every import in every module gets the SAME object.
# No singleton machinery needed.
❗ About class _Database — what is the underscore doing?
The leading underscore is the Python convention from prereq Q2: “don't touch this from outside the module.” It's not a module-level mechanism, not a Python keyword, and not enforced by the interpreter.

It's a signal to your colleagues: “Don't instantiate _Database() directly — use the database instance I exported.” Python won't stop them; the convention just makes the intent unambiguous in code review.
Name in moduleWhat it means in this pattern
_Database (capital, _ prefix)The class. Private to the module; do not instantiate.
database (lowercase, no prefix)The one public instance everyone should import.
Why this is often the right choice in Python:
  • Simplest possible code — no special pattern
  • Thread-safe by default — the import lock guarantees one-time initialization
  • Works with isinstance() against _Database
  • Lazy if you want it (move database = _Database() into a getter function)

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — Someone instantiates _Database directly

The underscore is convention, not enforcement.

from database import _Database     # technically allowed
rogue = _Database()              # second instance!

Mitigations: rename to __Database (name-mangling raises the bar), or guard __init__ against re-creation, or just trust your teammates and document intent.

💥 Break 2 — importlib.reload() creates a fresh instance

If something reloads the module (some IDEs, some test runners), the top-level database = _Database() runs again. You now have two instances coexisting — old references hold one, new imports get the other.

import importlib, database
old = database.database
importlib.reload(database)
new = database.database

print(old is new)    # False - two coexisting "singletons"
💥 Break 3 — Same file imported under two module names

Python caches by module name in sys.modules. If a relative/absolute import mishap loads the same file twice, you get two module objects — two singletons.

from myapp.database import database     # sys.modules["myapp.database"]
from database         import database     # sys.modules["database"]
# Different module objects -> different `database` instances

Fix: always use absolute imports; configure the project layout properly.

💥 Break 4 — Multiprocessing breaks every singleton

A “singleton” is per-Python-process. The moment you fork or use multiprocessing, each child has its own memory and its own singleton. Same with multiple Gunicorn workers, multiple Celery processes, multiple containers. This is true for every implementation — not unique to modules.

Optional — B

Optional B — Decorator

Keep the class clean. Bolt the Singleton-ness on from outside with a reusable decorator.

First: recall function decorators

You've seen this pattern earlier — a function that takes another function and returns a wrapped version (refresher: Real Python — Primer on Decorators):

def log_calls(fn):              # takes a function
    def wrapper(*args):
        print(f"calling {fn.__name__}")
        return fn(*args)
    return wrapper             # returns a function

@log_calls
def greet(name):
    print(f"hi {name}")

# greet is now `wrapper`. greet("Alice") prints both lines.

Now: a decorator on a class works the same way

Classes are just objects too. @singleton on a class means: take the class, return something else in its place. We return a tiny factory function that caches the first instance.

04_decorator_singleton.py
▼
def singleton(cls):                  # takes a class (just like log_calls takes a fn)
    instances = {}                          # closure - per-decorator cache

    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]

    return get_instance                # returns a function (!)


@singleton
class Database:
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"

# After decoration: `Database` is no longer the class.
# It's the function `get_instance` returned by singleton().
db1 = Database()    # "Database initialized"
db2 = Database()    # (silent - cached)
print(db1 is db2)    # True
Why teams like this: the class file looks like a normal class. Singleton behavior is one line: @singleton. The same decorator works for any class. Cleanest separation of concerns of the four approaches.

💥 How a Colleague Can Accidentally Break It

The Intuition

A decorator is just a function that takes a class and returns something else. Our decorator replaces the class with a tiny factory function that caches the first instance and returns it every time. The class itself stays pristine — no _instance, no __new__ tricks.

04_decorator_singleton.py
▼
def singleton(cls):
    instances = {}                          # closure - per-decorator cache

    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]

    return get_instance


@singleton
class Database:
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"

db1 = Database()    # "Database initialized"
db2 = Database()    # (silent - cached)
print(db1 is db2)    # True
Why teams like this: the class file looks like a normal class. Singleton behavior is one line: @singleton. The same decorator works for any class. Cleanest separation of concerns of the four approaches.

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — isinstance() stops working

After decoration, the name Database doesn't refer to a class anymore — it refers to get_instance, which is a function. Anyone calling isinstance(x, Database) gets a TypeError.

@singleton
class Database: ...

db = Database()
isinstance(db, Database)
# TypeError: isinstance() arg 2 must be a type, not function

type(Database)    # <class 'function'> - NOT <class 'type'>

A teammate writes a type check; everything blows up in code that worked yesterday. Fix: use a class-based decorator or a metaclass (next approach).

💥 Break 2 — You can't subclass it sanely

Since Database is now a function, class ReadOnlyDatabase(Database) errors out: you can't inherit from a function.

class ReadOnlyDatabase(Database):    # TypeError
    pass
# TypeError: function() argument 'code' must be code, not str

Fix: avoid this decorator when you anticipate inheritance.

💥 Break 3 — Different argument lists silently return the SAME instance

The decorator caches by class, not by args. A second caller passing different config silently gets the first caller's instance — and may believe it's been configured with the new values.

@singleton
class Database:
    def __init__(self, host):
        self.host = host

prod = Database("prod.example.com")
test = Database("localhost")        # IGNORED - args silently dropped

print(test.host)    # "prod.example.com"  !!!

Fix: raise an error if a singleton is called with args after first creation, or document the behavior loudly.

💥 Break 4 — Pickling/copying still doesn't go through the decorator

Same vulnerability as __new__: deepcopy and pickle.loads work on the underlying class object and bypass the cache.

Primer

Quick Primer — What Is a Metaclass?

Before we use a metaclass for Singleton, we need to know what a metaclass is. Two questions and one diagram.

Question 1 — In Python, what kind of thing is a class?

Correct! A class in Python is an object — you can assign it to a variable, pass it as an argument, store it in a list. Try this in your REPL: 
class Dog: pass

print(type(Dog))           # <class 'type'>
print(isinstance(Dog, object))  # True
id(Dog)                  # a memory address, like any object

So if Dog is an object, what class is it an instance of? → type. That's the metaclass.

Question 2 — What is a metaclass?

Correct! Just as Dog() creates a Dog instance, type(...) creates a class. The class that creates classes is called a metaclass. type is the default metaclass for everything in Python.
The "instance of" chain
fido = Dog()
fido is an instance of Dog
→
Dog (a class)
Dog is an instance of type
→
type (the metaclass)
type is an instance of type

A custom metaclass lets us intercept what happens when a class is called — that is, when someone writes Dog(). This is exactly the hook Singleton needs. (Deeper dive: Python docs — Metaclasses and Real Python — Metaclasses.)

A tiny metaclass example (not yet Singleton)

Just to anchor the idea: a metaclass that prints whenever any of its classes is instantiated.

class LoudMeta(type):
    def __call__(cls, *args, **kwargs):
        print(f"someone is creating a {cls.__name__}")
        return super().__call__(*args, **kwargs)

class Dog(metaclass=LoudMeta):
    def __init__(self, name): self.name = name

d = Dog("Fido")
# Output: someone is creating a Dog
Reading __call__: when Python sees Dog("Fido"), it asks the metaclass: “hey type (or LoudMeta), please call this class.” The metaclass's __call__ is what then dispatches to __new__ and __init__. By overriding it, we slip our own logic in before either runs.

Now we have everything we need to build a Singleton with a metaclass — the cache lives on the metaclass, and the __call__ returns the cached instance when it exists.

Optional — C

Optional C — Metaclass

The most powerful approach. Survives isinstance(), survives subclassing, but the heaviest machinery.

From the primer to Singleton

From the primer: __call__ on the metaclass is what runs when someone writes Database() — before __new__ or __init__. So we cache the first instance inside __call__ and return it on every subsequent call. That's the whole Singleton.

05_metaclass_singleton.py
▼
class SingletonMeta(type):
    _instances = {}

    def __call__(cls, *args, **kwargs):
        # __call__ runs when someone writes ClassName(...)
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class Database(metaclass=SingletonMeta):
    def __init__(self):
        print("Database initialized")
        self.connection = "Connected"


db1 = Database()      # "Database initialized"
db2 = Database()      # (silent - same instance)
print(db1 is db2)      # True
isinstance(db1, Database)   # True (works!)
Why this wins for libraries: Database stays a real class. isinstance() works. Subclassing works (and each subclass gets its own singleton, since the cache key is cls). __init__ only runs on the first call, naturally — because __call__ only delegates to super().__call__ the first time.

💥 How a Colleague Can Accidentally Break It

💥 Break 1 — Metaclass conflict on multiple inheritance

If you try to mix a singleton class with another base that has a different metaclass (e.g. an ABC), Python refuses: “metaclass conflict”.

from abc import ABC, ABCMeta

class Database(ABC, metaclass=SingletonMeta):  # BOOM
    pass
# TypeError: metaclass conflict
# Need a combined metaclass: class Combined(SingletonMeta, ABCMeta): ...

Fix: build a combined metaclass that inherits from both.

💥 Break 2 — deepcopy / pickle still bypass it

Same root cause as the __new__ approach. deepcopy goes through __deepcopy__ if defined, otherwise constructs a new object directly. pickle.loads reconstructs via __reduce__. Neither calls SingletonMeta.__call__.

💥 Break 3 — Bypass via object.__new__

A determined caller can call object.__new__(Database) directly — this skips the metaclass __call__ entirely and produces a fresh, uninitialized object.

db1 = Database()
db2 = object.__new__(Database)   # bypasses metaclass
print(db1 is db2)               # False - rogue instance
isinstance(db2, Database)         # True - looks legit

Python gives you no way to prevent this; it's a reminder that Singleton is a discipline, not a security feature.

💥 Break 4 — Threading race in __call__

Same race as the __new__ approach. Add a lock in __call__ with double-checked locking.

The Hardened Singleton

A Singleton That Withstands Every Break We've Seen

Combine the techniques. The result is verbose, but it survives subclassing, deepcopy, pickle, threading, and the "instantiate the underlying class" trick.

The recipe

Break we sawDefense in the hardened version
Threading raceDouble-checked locking with threading.Lock()
__init__ runs every call_initialized flag guards the body
Subclassing leaks instancesCache keyed by cls (per-class dict), defined on a metaclass
copy.deepcopy bypasses the cacheImplement __copy__ and __deepcopy__ to return self
pickle.loads bypasses the cacheImplement __reduce__ to return the class itself
object.__new__ bypassCannot fully prevent in Python; document the contract
07_hardened_singleton.py
▼
import threading

class SingletonMeta(type):
    _instances = {}                                    # per-class cache
    _lock = threading.Lock()

    def __call__(cls, *args, **kwargs):
        # Double-checked locking for thread safety
        if cls not in cls._instances:
            with cls._lock:
                if cls not in cls._instances:
                    cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class Database(metaclass=SingletonMeta):
    def __init__(self):
        self.connection = "postgresql://localhost:5432"

    # Defeat deepcopy
    def __copy__(self):     return self
    def __deepcopy__(self, memo): return self

    # Defeat pickle: tell pickle "to recreate me, call Database()"
    # When loaded, our metaclass returns the existing singleton.
    def __reduce__(self):
        return (Database, ())

What this survives

✔ Defends against

  • Threading races (lock)
  • Per-class confusion in subclassing (cache keyed by cls)
  • copy.deepcopy (returns self)
  • pickle.dumps/loads (__reduce__ hands the class back; metaclass re-resolves to cached instance)
  • isinstance() still works (Database is still a real class)

❌ Still can't defend

  • Determined caller using object.__new__(Database) — Python has no way to fully block this
  • Multiple Python processes (singleton is per-process by definition)
  • Module reloaded under two different paths

The honest takeaway: there is no “100% bulletproof” Singleton in Python. The hardened version above defends against every accidental break we've discussed. The remaining gaps are deliberate — a colleague would have to write code that explicitly bypasses your design. At that point, the right answer is a code review, not more machinery.

In Practice

Real-World Use Cases

Three places where Singleton genuinely earns its keep.

⚙️
Configuration Manager
One source of truth for application settings: DB URLs, API keys, feature flags. Two configs = two views of the world = bugs.
📝
Logger
Centralize log writes. Multiple loggers fighting over the same file = interleaved / corrupted entries.
🔌
Connection Pool
Bound the number of open sockets to the DB / Redis / message broker. One pool, shared cap.
📊
In-Memory Cache
Sharing data across modules requires one cache — otherwise each module has its own “cache.”
📑
Registry / Plugin Map
Decorators that register handlers (recall the OCP plugin pattern) read/write a shared registry — a Singleton by nature.
⏱️
Thread / Worker Pool
One pool = controlled concurrency. Multiple pools = uncontrolled fan-out.

Pulled-together example: Config + Logger

# config.py - module-level singleton
class _Config:
    def __init__(self):
        self.db_host    = "localhost"
        self.db_port    = 5432
        self.debug      = True
        self.api_key    = "secret_123"

config = _Config()


# logger.py - decorator singleton
def singleton(cls):
    instances = {}
    def get(*args, **kw):
        if cls not in instances:
            instances[cls] = cls(*args, **kw)
        return instances[cls]
    return get

@singleton
class Logger:
    def __init__(self):
        self.file = open("app.log", "a")
    def info(self, msg):
        self.file.write(f"[INFO] {msg}\n")
        self.file.flush()


# anywhere in the app:
from config import config
from logger import Logger
Logger().info(f"connecting to {config.db_host}")
Anti-Patterns

When NOT to Use Singleton

Singleton is the most misused pattern in software. Three concrete smells.

❌ Anti-pattern 1 — The "Utils" god object

▼

A Singleton class that grows methods over time until it has nothing in common. This is just a global variable with a fancy hat.

@singleton
class Utils:
    def format_date(self, d): ...
    def send_email(self, to): ...
    def calculate_tax(self, amt): ...
    def resize_image(self, img): ...
# These have NOTHING to do with each other. Just use modules.

Fix: separate modules; plain functions. Python is already organized around modules; you don't need a Singleton class to namespace utilities.

❌ Anti-pattern 2 — Hidden dependencies (untestable code)

▼

A Singleton reached inside method bodies makes the dependency invisible. Tests can't substitute a fake. Refactoring is dangerous.

❌ Hidden dependency

class OrderService:
    def place(self, order):
        Logger().info("placing")   # hidden
        DB().save(order)              # hidden

# Tests can't replace Logger or DB

✔ Injected

class OrderService:
    def __init__(self, logger, db):
        self.logger = logger
        self.db = db
    def place(self, order):
        self.logger.info("placing")
        self.db.save(order)

Rule: Singletons live at the edge (the composition root). Business code receives its dependencies, doesn't reach for them.

❌ Anti-pattern 3 — Domain objects as Singletons

▼

If your domain naturally has many instances — users, orders, products, blog posts — do not make them Singletons. The pattern exists for infrastructure (one connection pool, one config). A web app with one User object is not a web app.

Mindmap Summary

Everything at a Glance

One picture — each approach, what it gives you, and how it breaks.

SINGLETON in Python
one instance per process
A1 — __new__
Classic. Override __new__ to cache the instance on the class.
Breaks: __init__ re-runs (use init flag), threading race
A2 — __new__ + double-checked lock
Same idea, with threading.Lock + two-stage check. Fast path is lock-free.
Fixes: threading race. Still breaks: deepcopy, pickle, subclassing.
Optional A — module-level
Just database = _Database() at module top-level. Most Pythonic.
Free: thread-safe via import lock.
Breaks: direct _Database() calls, importlib.reload, two import paths.
Optional B — decorator
@singleton replaces the class with a caching factory.
Breaks: isinstance() raises TypeError, can't subclass, args silently dropped on later calls.
Optional C — metaclass
Override __call__ on a custom metaclass. Class stays a real class. Per-subclass singleton via cache keyed on cls.
Best for: libraries, frameworks, when isinstance() must work. Breaks: metaclass conflict with ABCMeta, object.__new__ bypass.
🎯 Hardened — metaclass + lock + __copy__ + __reduce__
Defends against threading, deepcopy, pickle, and subclassing-leak all at once. Verbose, but bulletproof in practice.
Still can't defend: determined object.__new__ bypass, multi-process, two import paths.

🎯 Decision Tree — pick by question

Q: Do you need exactly one instance?
Simple app, no threading → module-level instance
Threaded app → A2 (__new__ + double-checked lock)
Library / framework + isinstance() + subclassing → metaclass
Many classes, want one liner → decorator
Production-grade, defends against everything → hardened singleton

Interview tip: Write the classic __new__ Singleton on the board first — it shows you understand object creation. Mention the __init__ gotcha. Add double-checked locking when threading comes up. Then say: “In real Python code I'd usually just export a module-level instance — it's the simplest correct singleton in the language.” Mention the metaclass for libraries. That answer shows you know the pattern and when not to over-engineer it.

🎯 The One-Line Summary

Singleton ensures exactly one instance of a class per process. In Python you usually get it for free with a module-level instance. The other approaches exist for threading, isinstance(), inheritance, and framework-level control. Always ask first: “do I really need this, or is it just a global in disguise?”
