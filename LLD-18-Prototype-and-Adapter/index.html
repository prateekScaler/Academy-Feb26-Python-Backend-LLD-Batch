Prototype & Adapter

LLD-18 • The last Creational + the first Structural

When building from scratch is too expensive, clone an existing object — that's Prototype. When two interfaces just don't match, slip a translator in between — that's Adapter. Two small patterns, two everyday problems.

Recap — Factory

Quick Recall — Factory Family Pitfalls

Two checks from LLD-17 before we move on. Factory centralised which concrete class to instantiate. Prototype is going to ask a related-but-different question: how do we create a new object when constructing one from scratch is too expensive?

Quiz 1 — Which Factory variant fits this requirement?

Scenario — themed checkout for a food-delivery app:

  • Three widgets to render: Header, Button, Toast.
  • Three brand themes:
    • McDonald's → red-yellow
    • Starbucks → green-cream
    • Subway → green-yellow
  • Brand can switch mid-session (customer changes restaurant).
  • Invariant: all three widgets on screen must share the same brand — no red Header above a green Button.
C is right. The defining requirement is family consistency — all three widgets must belong to the same brand. That's exactly the problem Abstract Factory solves: each concrete factory (McDFactory, StarbucksFactory) is responsible for producing a coordinated set of related products.
Sample code — minimal Abstract Factory shape:

Why not the others?

  • A (Simple Factory) returns one product at a time — nothing forces the three calls to share a brand.
  • B (Factory Method) defers which subclass to instantiate per product — solves "extend with new types," not "keep families coherent."
  • D (Builder) assembles one complex object step-by-step — here the three widgets are independent peers, not parts of a single whole.

Quiz 2 — Pick the pattern: "A microservice's HttpClient wraps a connection pool. The pool is expensive to create (~300ms) and the rest of the app must always use the same one, otherwise we leak sockets."

B is right. Two clues both point to Singleton:
  • "the rest of the app must always use the same one" — that's literally the Singleton guarantee.
  • "the pool is expensive to create" + "leak sockets if we don't" — you want to pay the construction cost once.
Builder helps when construction takes many optional params — not the issue here. Factory Method / Abstract Factory help when which type is the question — here the type is fixed; the issue is how many instances.

Quiz 3 — Pick the pattern: "Constructing a SearchQuery object can mean any subset of 12 filters (price range, brand, rating, in-stock, free-delivery, …). The constructor takes 12 optional kwargs and call sites are unreadable."

A is right. The complaint is "too many optional params" + "call sites unreadable" — classic telescoping-constructor pain that Builder fixes by making each setter a named fluent step.

Singleton is wrong: every search is a fresh, ephemeral object. Factory Method via subclassing would explode (2^12 = 4096 combinations — one subclass each? no). Abstract Factory solves family consistency, not "too many ways to configure one thing".

Quiz 2 — Which line of code does Factory Method eliminate that Simple Factory still keeps?

# Simple Factory
class NotificationFactory:
    @staticmethod
    def create(kind: str):
        if kind == "email":   return Email()
        elif kind == "sms":  return SMS()
        elif kind == "push": return Push()
        raise ValueError(kind)
B is right. Simple Factory has to edit the if/elif chain every time a new product is added — that's an OCP violation: the factory is open for modification on every change. Factory Method flips this: each product gets its own subclass with a single create(), and adding a new product is a new subclass, never a touch to an existing class. The raise, the decorator, and the type hint are all incidental.

Quiz 3 — Is this code a sensible use of Factory?

class PointFactory:
    @staticmethod
    def create(x: float, y: float) -> Point:
        return Point(x, y)

# Used everywhere as:
p = PointFactory.create(3, 4)   # instead of Point(3, 4)
C is right. Factory earns its keep when there's a real decision the caller would otherwise have to make: which subclass, with which args, possibly cached, possibly validated. Wrapping a single constructor with one line of indirection is the classic over-engineered factory — you've added a class, a static method, and a name to remember, and bought nothing. A is wrong because "always good" is exactly the dogma that produces this kind of code. B is wrong because YAGNI — add the cache when (if) the need arrives. D is wrong because @staticmethod is a perfectly fine choice for Simple Factory; that's not the problem here.

What connects them?

Both patterns are small, everyday, and easy to over-apply. Both have a Python-native shortcut (copy.deepcopy, duck typing) that often makes the explicit pattern unnecessary. The trick is knowing when to reach for them and when to skip them.

Why are these two grouped? Honestly — for pacing. Prototype is the smallest of the creational patterns (and the least often needed in modern Python), and Adapter is the smallest of the structural ones. Pairing them lets us finish the creational chapter and open the structural chapter in one class without either pattern feeling stretched thin. Treat them as two independent tools that happen to share a syllabus slot.

Part 1 — Prototype

Prototype — Clone, don't construct

Sometimes the cheapest way to make a new object is to copy one that already exists.

🔎 Prerequisite check — Python's copy module

Prototype is built on top of copying objects in Python. If the next two quizzes feel surprising, the pattern itself won't make sense — revise these first.

Quiz 0 — Before copy: how would you duplicate this object by hand?

Pretend the copy module doesn't exist. You have a Cart with items and a customer. You want a second cart that's the same as the first but independent. Which of these "by-hand" duplications is actually correct?

class Cart:
    def __init__(self, items, customer):
        self.items = items            # list[str]
        self.customer = customer      # dict[str, str]

c1 = Cart(items=["book"], customer={"name": "Jay"})
C is right — and it's exactly what copy.deepcopy automates for you.
  • A is aliasing — c1 and c2 are the same dict. Mutating one mutates both.
  • B looks safe but the inner items list and customer dict are still shared. Appending to c2.items bleeds into c1.items. (This is what copy.copy does — "shallow" copy.)
    c1 (NEW Cart)
    items: ↓
    customer: ↓
    c2 (NEW Cart)
    items: ↓
    customer: ↓
    ↘ ↙     ↘ ↙
    one shared items list
    one shared customer dict

    Both Carts are new objects, but their fields point at the same inner containers — mutating one mutates both.

  • C explicitly recreates the inner containers too. Fully independent.
  • D copies the dict reference — same bug as A, just dressed up.

That's the whole point of the copy module: it walks the reference graph for you and rebuilds new objects at every level — so you don't have to remember to wrap every nested field in list(...), dict(...), or a fresh constructor call. Without it, every prototype implementation would be a hand-rolled tour of every field. With it, one line: copy.deepcopy(self).

Quiz 1 — What does this print?

import copy

original = {"name": "Ada", "skills": ["python", "go"]}
shallow  = copy.copy(original)
shallow["skills"].append("rust")

print(original["skills"])
B is right. copy.copy() creates a new container but copies the references inside, not the inner objects. original["skills"] and shallow["skills"] are the same list object — mutating one mutates both. To isolate the inner list too, use copy.deepcopy(). This single distinction is the root of 90% of Prototype bugs.

  "skills": ↓ }

shallow ↓

["python", "go", "rust"]

Why this matters: a shallow copy makes one level of new object. Everything inside that object is still pointer-equal to the original. That's why mutating shallow["skills"] shows up in original["skills"] — they're literally the same list, with two different dicts pointing at it.

Quiz 2 — Which is true about copy.deepcopy?

B is right. deepcopy walks the entire reference graph, recreating every object it touches. It also keeps a memo dict so cyclic references don't loop forever (e.g., a.peer = b; b.peer = a still deep-copies correctly). You can customise the behaviour for your class by defining __copy__(self) and __deepcopy__(self, memo) — we'll use this later to make clone cheap.

Deep copy in memory — two separate lists

After deep = copy.deepcopy(original). Both the outer dict and the inner list are freshly allocated:

original (dict)
{ "name": "Ada",
  "skills": ↓ }
deep (NEW dict)
{ "name": "Ada",
  "skills": ↓ }
list object #1
["python", "go"]
list object #2 — NEW
["python", "go"]

After deep["skills"].append("rust"). Only list #2 changes — list #1 isn't reachable from deep:

list object #1 — untouched
["python", "go"]
list object #2
["python", "go", "rust"]

Deep copy walks the reference graph and rebuilds every container. Cost is roughly proportional to how many objects are reachable from the root — shallow is O(1) on the outer object; deep is O(total reachable objects).

Pre-stdlib version — what you'd write by hand: just to see what copy.deepcopy is doing for you, here's the same job written without the module — recursive walk + memo dict for cycles.

def manual_deepcopy(obj, memo=None):
    if memo is None:
        memo = {}
    # Already cloned this object in the current walk? Return the cached clone.
    # This is what prevents cycles from looping forever.
    if id(obj) in memo:
        return memo[id(obj)]

    if isinstance(obj, dict):
        new = {}
        memo[id(obj)] = new          # register BEFORE recursing (handles cycles)
        for k, v in obj.items():
            new[manual_deepcopy(k, memo)] = manual_deepcopy(v, memo)
        return new

    if isinstance(obj, list):
        new = []
        memo[id(obj)] = new
        for item in obj:
            new.append(manual_deepcopy(item, memo))
        return new

    # Immutable atoms (int/str/tuple of immutables) — safe to share
    return obj

That's effectively what copy.deepcopy does — plus a much richer type registry (handles class instances via __deepcopy__, classes via __reduce_ex__, etc.) and battle-tested edge cases (file handles, weakrefs, modules, sockets). The idea is identical to the 15 lines above: recursive walk, memo for cycles.

Worked example — trace the recursion on a tiny input. Call manual_deepcopy({"name": "Ada", "skills": ["python", "go"]}) and walk through what happens:

call manual_deepcopy(d = {"name": "Ada", "skills": ["python", "go"]}, memo={})
  → id(d) not in memo
  → isinstance(d, dict) is True
  → new1 = {}
  → memo[id(d)] = new1     # register BEFORE recursing into children
  → iterate items:
        key = "name", value = "Ada":
            manual_deepcopy("name")  → "name"   # immutable str, returned as-is
            manual_deepcopy("Ada")   → "Ada"    # immutable str, returned as-is
            new1["name"] = "Ada"

        key = "skills", value = ["python", "go"]:
            manual_deepcopy("skills") → "skills"
            manual_deepcopy(["python", "go"], memo)
              → id(list) not in memo
              → isinstance is list → new2 = []
              → memo[id(list)] = new2
              → for item in list:
                    manual_deepcopy("python") → "python"
                    manual_deepcopy("go")     → "go"
              → return new2  # NEW list, same contents
            new1["skills"] = new2

  → return new1            # NEW dict containing the NEW list

Notice line 4 vs line 14: memo[id(d)] = new1 happens before recursing into the children. If a child contained a reference back to d, the recursive call would find it in memo and return the half-built new1 — that's how cycles are handled without infinite loops.

Connecting to last term: we already covered the copy module — shallow vs deep, the memo dict, picklable types — in LLD-12 · Exception Handling, § copy & deepcopy. The Prototype pattern is just "build the cheap-clone API on top of what you already know about copy.deepcopy".

Quiz 3 — = vs copy.copy vs copy.deepcopy on the same object — what does orig.skills end up as?

import copy
orig = {"name": "Ada", "skills": ["python"]}

a = orig                            # (i)   plain assignment
b = copy.copy(orig)                 # (ii)  shallow
c = copy.deepcopy(orig)             # (iii) deep

a["name"]      = "Grace"            # mutate top-level via alias
b["skills"].append("go")            # mutate inner list via shallow
c["skills"].append("rust")          # mutate inner list via deep

print(orig["name"], orig["skills"])
B is right — three flavours of "copy", three different blast radii:
  • (i) a = orig — not a copy at all. a and orig are the same dict; mutating either mutates both. So orig["name"] == "Grace".
  • (ii) b = copy.copy(orig) — new outer dict, but b["skills"] is orig["skills"] is True. b["skills"].append("go") bleeds into orig. So "go" appears.
  • (iii) c = copy.deepcopy(orig) — new dict and new inner list. "rust" stays in c only.
Bottom line: aliasing < shallow copy < deep copy in terms of isolation. Prototype almost always wants the third.

🤯 The problem — "building from scratch" is sometimes very expensive

Case study — Notion's "Duplicate" button. When you click Duplicate on a Notion page, a brand-new page appears in about ~200 ms — complete with all the same blocks, embeds, properties, formulas, and database views as the original. Imagine if Notion didn't have Duplicate, and instead made you re-create the page from scratch every time. That's the difference between clone() and __init__.

Jayendra is building an A/B test platform. The setup mirrors Notion's "Duplicate" exactly — every A/B experiment starts from a BaseConfig that's expensive to build:

  • pulls 200+ feature flags from a slow remote config service (~400ms),

Total: ~1.2 seconds per BaseConfig(). Each experiment needs a config that's 99% identical to the baseline — just one or two flags flipped. The naive approach pays the 1.2s tax 50 times.

🪟 The pattern — clone() instead of new

Prototype's idea, in one sentence:

Have every object that's expensive to construct expose a clone() method. To make a similar object, call existing.clone() — not the constructor.

GoF definition (worth memorising for interviews):

"Specify the kinds of objects to create using a prototypical instance, and create new objects by copying this prototype."

Two motivations the GoF spell out, beyond raw cost:

  • Avoid subclass explosion. If variants differ only in data (a "fast-attack orc" vs a "slow-defend orc" with different HP/damage numbers), don't make a new subclass for each — just clone a configured prototype.
  • The concrete type isn't known until runtime. A game spawns whatever enemy the level config says; an editor spawns whatever shape the user clicks. The caller doesn't write OrcWarrior() — it looks up the prototype by name and clones it.

Rewritten with Prototype:

import copy
from dataclasses import dataclass, field

@dataclass
class BaseConfig:
    flags: dict[str, bool] = field(default_factory=dict)
    pricing: dict[str, float] = field(default_factory=dict)
    segments: dict[str, list[str]] = field(default_factory=dict)

    def __init__(self):
        # Slow one-time setup — 1.2s
        self.flags    = _load_flags_from_remote()
        self.pricing  = _load_pricing_from_db()
        self.segments = _warm_segment_model()

    def clone(self) -> "BaseConfig":
        return copy.deepcopy(self)         # < 1ms


# --- usage ---
prototype = BaseConfig()                       # 1.2s — pay once
for experiment in experiments:
    cfg = prototype.clone()                  # <1ms each
    cfg.flags[experiment.flag] = experiment.value
    run_experiment(cfg)

Why is clone() ~1000× faster than __init__?

It's the difference between re-computing the data and copying already-computed bytes:

Step BaseConfig() — full constructor prototype.clone() — deepcopy
Load 200 feature flags HTTPS call to remote config service
~400 ms (network RTT + JSON decode)		 Walk the in-memory dict, allocate a new one with the same 200 keys/values
~0.2 ms
Load pricing table TCP DB roundtrip, query plan, row decode
~150 ms		 Allocate new dict, copy ~100 entries
~0.1 ms

~600 ms CPU + I/O		 Allocate the same shape of dict/array structures
~0.5 ms
Total ~1200 ms ~0.8 ms ≈ <1 ms

The two costs sit on different orders of magnitude:

  • Constructor does I/O — network calls (10s of ms each), disk reads (1+ ms), CPU compute. Each one is at least a thousand machine instructions plus a wait for a remote system.
  • deepcopy does memory work only — malloc, write bytes, repeat. Modern CPUs do tens of gigabytes of memory copies per second. A few dictionaries with a few hundred entries each is a vanishingly small amount of work.

Said another way: the constructor's time goes to fetching data from somewhere far away. The clone's time goes to duplicating data already sitting in RAM. Same outcome (a usable BaseConfig), wildly different cost.

Caveat: when an object holds genuinely large in-memory data (a 1 GB tensor, a 100k-edge graph), deepcopy stops being <1 ms — it grows with the data size. That's exactly the case where you override __deepcopy__ to share the giant read-only piece instead of duplicating it. See code/11_deepcopy_override_recipes.py, Recipe 1.

The minimal Prototype interface is just one method:

from abc import ABC, abstractmethod

class Prototype(ABC):
    @abstractmethod
    def clone(self) -> "Prototype": ...

In the GoF book this is a formal abstract class — see Design Patterns (Gamma et al., 1994), Chapter 3 — Prototype, p.117 on archive.org for the original write-up. In Python you almost never need the ABC — duck typing handles it — but the contract is the same: every concrete Prototype answers clone().

The cost equation that makes Prototype worth it:

cost(__init__) >> cost(deepcopy) & & you'll need N similar objects

When that inequality doesn't hold — cheap constructor, or you only need one object — Prototype just adds noise. Stick with the constructor.

The pattern is a tool to spend cheaply, not a habit. Ask the inequality before you reach for it.

🎢 Variation A — shallow vs deep clone (and why it matters)

Inside clone() you'll always pick one of two strategies. The choice is not stylistic — it's a correctness call.

  copy.copy — shallow copy.deepcopy — deep
What it does New outer object, inner references shared New outer object, every reachable object also copied
Speed Fast (one allocation) Slower (proportional to graph size)
Safe when Inner objects are immutable (str, tuple, frozenset, numbers) Inner objects are mutable and each clone needs to evolve independently
Trap Mutating clone.list silently mutates original.list too Can blow up on objects holding sockets, file handles, locks, DB connections

When the default isn't right, override the hooks:

class MLPredictor:
    def __init__(self):
        self.model   = _load_giant_model()       # 800 MB, READ-ONLY
        self.history = []                       # per-clone, mutable

    def __deepcopy__(self, memo):
        new = MLPredictor.__new__(MLPredictor)
        new.model   = self.model                # SHARE the model
        new.history = []                        # fresh per clone
        return new

By customising __deepcopy__ you tell Python "share what's safe to share, copy what must be independent." This is the single biggest lever for keeping clone() cheap.

📚 Variation B — Prototype Registry

If callers ask for clones by name — "give me a fresh email-notification template", "give me the staging config" — wrap the prototypes in a registry:

class PrototypeRegistry:
    def __init__(self):
        self._prototypes: dict[str, Prototype] = {}

    def register(self, name: str, proto: Prototype) -> None:
        self._prototypes[name] = proto

    def get(self, name: str) -> Prototype:
        return self._prototypes[name].clone()


# --- one-time setup ---
registry = PrototypeRegistry()
registry.register("welcome-email", EmailNotification(template="Welcome!", retry=3))
registry.register("alert-sms",    SMSNotification(template="Alert!",   retry=5))

# --- usage ---
msg = registry.get("welcome-email")         # fresh clone each time
msg.recipient = "riya@scaler.com"

This is what notification template systems, IDE "new file from template" menus, and game engines (spawn enemy by name) all look like under the hood.

⚠️ Variation C — when Prototype meets Singleton

A subtle interview gotcha: what happens if someone calls copy.deepcopy(my_singleton)? By default, Python happily makes a second instance — quietly defeating the "exactly one" guarantee the Singleton was supposed to enforce.

The fix is to plug into the copy protocol from inside the Singleton and refuse to clone:

class ConfigStore:                       # Singleton
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    # Block clone attempts — both shallow and deep return the SAME instance
    def __copy__(self):           return self
    def __deepcopy__(self, memo):   return self


s1 = ConfigStore()
s2 = copy.deepcopy(s1)
assert s1 is s2                            # Singleton invariant preserved ✓

The lesson: Singleton's "exactly one" is enforced by the constructor (__new__). The copy module bypasses the constructor entirely, so a class that wants to remain a Singleton must also guard the __copy__/__deepcopy__ entry points. This is the same lesson as "Singleton must guard pickle too" — any backdoor that creates objects without calling __new__ is a hole.

How exactly does copy.deepcopy bypass __new__? It uses Python's __reduce_ex__ protocol — the same one that pickle uses to serialise. The default reduce returns a recipe like (cls.__new__, (cls,), state_dict). That is a function pointer to the class's __new__ — but when deepcopy rebuilds, it then calls __setstate__ (or obj.__dict__.update(state)) to load the state on the new instance. If your Singleton's __new__ returns the cached _instance, the rebuilt object IS the same instance — but its state was just overwritten with a deep-copied snapshot. Concurrent writers see surprise wipes.

What happens under the hood — UNSAFE singleton

   a = UnsafeSingleton()
   a.flags["dark_mode"] = True            # live state

   b = copy.deepcopy(a)
       │
       ├— a.__reduce_ex__(2)  → (cls.__new__, (cls,), {"flags": {"dark_mode": True}})
       │
       ├— rebuilt = cls.__new__(cls)
       │       └— Singleton's __new__ returns existing _instance  ⇒ rebuilt IS a
       │
       └— rebuilt.__dict__.update(deepcopy(state))
               └— overwrites a.flags with the snapshot's copy

   ⇒ a is b (True) BUT a.flags has been silently replaced.
       Any other writer who set flags["new_feature"] between the snapshot
       and the deepcopy now sees their write erased.
# The guard — turn both entry points into a no-op
class SafeSingleton:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.flags = {}
        return cls._instance

    def __copy__(self):           return self   # short-circuit BOTH
    def __deepcopy__(self, memo):   return self   # entry points

Now copy.deepcopy(safe) never calls __reduce_ex__ — the dunder fires first and just returns self. No new instance, no state rewrite, invariant preserved. See code/10_proto_pitfalls_reset_and_singleton.py for a runnable demo.

Quiz — What does this print?

import copy

class Cart:

        self.items: list[str] = []

B is right — and this is the #1 Prototype bug. copy.copy made new Cart wrappers, but they all hold a reference to the same items list. c1.items.append("book") mutated the shared list. Fix: use copy.deepcopy(self), or explicitly new.items = list(self.items).

Quiz — You're building a game. spawn_orc() clones a prototype Orc. What's wrong with this code?

@dataclass
class Orc:
    name: str
    max_hp: int = 100
    hp: int = 100                  # current HP, mutates during battle
    target: "Orc" | None = None      # whoever it's currently attacking
    position: tuple[int, int] = (0, 0)

    def clone(self) -> "Orc":
        return copy.deepcopy(self)

# The prototype, used to spawn every orc
orc_proto = Orc(name="orc")

# ... mid-battle, the prototype somehow took 30 damage and got a target ...
orc_proto.hp = 70
orc_proto.target = some_player

new_orc = orc_proto.clone()
print(new_orc.hp, new_orc.target)
B is right. Prototype copies whatever state the prototype object happens to have. If the prototype is also a live participant in the system (the game accidentally uses one shared orc as both "the template" and "an actual orc"), runtime mutations leak into every future clone. Two clean fixes:
  • Separate template from instance — keep the prototype on a shelf, never let game code mutate it directly.
  • Reset on clone: def clone_fresh(self): new = self.clone(); new.hp = new.max_hp; new.target = None; return new
Same pitfall hits ML "pretrained model" clones (training state leaks), HTTP "session template" clones (auth cookies leak), and database "connection template" clones (transaction state leaks).

Quiz — When is full Prototype overkill?

You have a simple frozen @dataclass with five primitive fields, and you want to create a copy with one field changed.

C is right. For simple immutable dataclasses, dataclasses.replace() already does "copy with one field tweaked" in one line — that's Prototype's job, done for you by the standard library. Reach for explicit clone() when the object is mutable, expensive to build, holds non-trivial state, or you want the registry idiom. Don't ceremonially apply Prototype to every data class.

In Python you can drop the formal Prototype interface — duck typing means any class that defines clone() qualifies.

4-step recipe to implement Prototype:

  1. Identify the expensive class. Its __init__ takes meaningful time and the rest of the code wants many similar-but-tweaked instances.
  2. Add a clone(self) method. Default body: return copy.deepcopy(self).
  3. Decide what to share vs. independently copy. If your object holds expensive read-only data (an ML model, a parser table), override __deepcopy__ to share it. If it holds OS resources (sockets, file handles), clone() is the wrong pattern entirely — rethink.
  4. (Optional) Wrap with a registry if callers ask for clones by name (registry.get("welcome-email")).

✅ When Prototype earns its keep

Use Prototype when
  • Construction is genuinely expensive (DB, network, heavy compute)
  • You'll need many similar instances at runtime
  • Object state is mostly data — no sockets, no file handles, no locks
  • You want to clone "by name" (registry pattern)
Skip Prototype when
  • Constructor is fast — just call it
  • Object holds OS resources or external state
  • It's a simple @dataclass — use dataclasses.replace()
  • You only need one or two instances total
Part 2 — Adapter

Adapter — Make two incompatible interfaces talk

The first structural pattern. Instead of changing either side of a mismatch, drop a translator in the middle.

🔌 Before the code — the original "adapter" you already know

The world has 15 different electrical socket shapes. An Indian Type-D socket has three round pins. A US Type-B has two flat pins + a round ground. A UK Type-G has three big rectangular pins with a fuse. Visit any of these countries with a laptop charger built for another and your plug literally will not fit the wall. Watts, volts, current — all fine. The shapes don't match.

Why hasn't the world standardised on one socket?

  • Path dependence. Each country electrified between ~1890 and ~1960 with the tech and patents of its day. Once 100 million homes are wired, switching is impossibly expensive.
  • Voltage / frequency differs too (110V/60Hz in the US, 230V/50Hz in India, 230V/50Hz in the UK…), so the socket shape doubles as a "this socket is the right voltage for the plug" key.
  • Local safety standards diverged. The UK Type-G has a built-in fuse and longer earth pin. India's Type-D doesn't. Each country's standard reflects its own historical preferences.

The traveller's solution — a universal travel adapter

Two incompatible interfaces, neither modified. The adapter holds both shapes — round pins on the side that talks to the wall, flat slots on the side that talks to the plug — and bridges between them.

The travel adapter doesn't change what flows through it — the electricity is still 230V going to a 110V appliance (you need a transformer for that, which is a different kind of adapter for voltage conversion). It just reshapes the interface — the holes & pins — so the foreign plug can engage with the local socket.

That's exactly what the software Adapter pattern does: two systems with non-matching interfaces, neither of which can be modified, with a small wrapper in the middle that reshapes the calls — not the data — so the two sides can talk. The wrapper is so simple that you've used dozens of physical ones; the software version is the same idea, in code.

🔎 Prerequisite check — composition & duck typing

Adapter is the canonical "composition over inheritance" pattern. Two quick checks before we dive in.

Quiz 1 — What is "duck typing" in Python?

B is right. "If it walks like a duck and quacks like a duck, it's a duck." Python doesn't care whether your object inherits from a base class or implements a formal interface — only whether obj.method(...) works at runtime. This matters for Adapter because it explains why the GoF's elaborate class diagrams shrink, in Python, to a single wrapper class.

Duck typing in code — positive & negative cases:

# A function that "needs a duck" — doesn't care about types, only methods
def make_it_quack(thing):
    return thing.quack()

# ✅ Positive — Duck obviously quacks
class Duck:
    def quack(self): return "Quack!"

# ✅ Positive — Person quacks too, with zero inheritance, zero interface declared
class Person:
    def quack(self): return "I'm imitating a duck"

make_it_quack(Duck())     # "Quack!"        works
make_it_quack(Person())   # "I'm imitating..." also works

# ❌ Negative — Dog has no quack(); we only find out at RUNTIME
class Dog:
    def bark(self): return "Woof"

make_it_quack(Dog())      # AttributeError: 'Dog' has no attribute 'quack'

Compare with Java — the same idea would need an interface:

// Java — types matter at COMPILE time. Person has to formally implement Quackable.
interface Quackable { String quack(); }

class Duck   implements Quackable { public String quack() { return "Quack!"; } }
class Person implements Quackable { public String quack() { return "..."; } }
class Dog { public String bark() { return "Woof"; } }

static void makeItQuack(Quackable t) { System.out.println(t.quack()); }

makeItQuack(new Dog());          // won't even COMPILE — Dog doesn't implement Quackable

Why this matters for Adapter:

  • In Java, an Adapter must implements TargetInterface — the wrapper class must be declared as the right type, by name, at compile time.
  • In Python, the wrapper just needs the right methods. No implements, no inheritance, no ABC needed (though we often add one for clarity). The wrapper is "an Adapter" purely by virtue of doing the job.
  • That's why all the GoF Adapter UML — with its explicit "implements Target" arrows — looks heavier than the equivalent Python code: Python doesn't need the arrow.

Quiz 2 — What is "composition over inheritance"?

C is right. When class B inherits from class A, B is permanently glued to A's interface, A's lifecycle, and A's internals — future changes to A ripple into B. When class B holds an A as a field, the coupling is just one method call. Adapter is the textbook example: the Adapter holds the Adaptee and delegates, so the Adaptee can be swapped, mocked, or replaced with zero changes to the Adapter's clients.

Worked example — same job, two ways:

Inheritance — brittle 
class EmailNotifier(SMTPClient):
    def notify(self, user, msg):
        self.send(user.email, msg)

# Pain: EmailNotifier now exposes ALL of
# SMTPClient's methods (connect, quit,
# noop, helo, mail, rcpt, data, login...).
# Callers can do email.quit() — and one
# day will. If SMTPClient renames send()
# in v2, EmailNotifier silently breaks.
Composition — flexible 
class EmailNotifier:
    def __init__(self, client):
        self._client = client     # HAS-A
    def notify(self, user, msg):
        self._client.send(user.email, msg)

# Win: only notify() is public.
# Swap SMTPClient for SendgridClient by
# passing a different object — zero
# changes to EmailNotifier or its callers.
# In tests, pass a MockClient.

Same end behaviour, very different coupling. Adapter formalises the right side: "hold the foreign object as a private field; expose only the interface you want."

🤯 The problem — two interfaces that just don't match

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass(frozen=True)
class PaymentLink:
    provider_link_id: str
    short_url: str
    amount_paise: int

class PaymentGateway(ABC):
    @abstractmethod
    def create_payment_link(self, *, amount_paise, order_id,
                            customer_name, customer_email, customer_phone,
                            description, callback_url) -> PaymentLink: ...
    @abstractmethod
    def verify_webhook(self, payload: bytes, signature: str) -> bool: ...
    @abstractmethod
    def parse_webhook_event(self, payload: bytes) -> "WebhookEvent": ...

# payments/gateways/razorpay_adapter.py — vendor SDK quarantined HERE
import razorpay
from .base import PaymentGateway, PaymentLink

class RazorpayGateway(PaymentGateway):
    def __init__(self, key_id: str, key_secret: str, webhook_secret: str):

        self._webhook_secret = webhook_secret

        link = self._client.payment_link.create({
            "amount": kwargs["amount_paise"],
            "currency": "INR",
            "description": kwargs["description"],
            "customer": {
                "name":    kwargs["customer_name"],

            "callback_url": kwargs["callback_url"],
            "notify": {"sms": True, "email": True},
        })

            provider_link_id=link["id"],
            short_url=link["short_url"],
            amount_paise=kwargs["amount_paise"],
        )

Quiz — Which family does Adapter belong to?

B is right. The three GoF families answer three different questions:
  • Creational — "how do I make this object?" (Singleton, Builder, Factory, Prototype, Abstract Factory)
  • Structural — "how do I compose objects so they fit together?" (Adapter, Decorator, Facade, Proxy, Bridge, Composite, Flyweight)
  • Behavioural — "how do objects collaborate over time?" (Strategy, Observer, Command, State, ...)

Adapter is the first member of Structural — and the simplest: it changes nothing about what the wrapped object is or what work it does. Only how it's accessed from the outside.

🎢 Variation — Object Adapter vs Class Adapter

Classical GoF describes two flavours. In Python, only one is idiomatic.

  Object Adapter (composition) Class Adapter (inheritance)
Mechanism Adapter holds an Adaptee instance Adapter inherits from both Target and Adaptee
Translation Delegates: self._adaptee.foo() Calls inherited: self.foo()
Can adapt subclasses too? Yes — any Adaptee subclass works No — tied to one specific class
Python multiple inheritance needed? No Yes — brittle when Adaptee has its own bases
Idiomatic in Python? ✅ Yes — this is what you'll see in real code ❌ Rarely — multiple inheritance is a code smell here

A class adapter would look like this — you can write it, but you usually shouldn't:

class RazorpayClassAdapter(PaymentGateway, RazorpayClient):   # multi-inheritance
    def pay(self, amount: float, currency: str) -> PaymentResult:
        amount_in_paise = int(amount * 100)
        order  = self.create_order(amount_in_paise, _new_receipt_id())
        result = self.capture_payment(order["id"])
        return PaymentResult(
            success=result["status"] == "captured",
            txn_id=result["id"],
            raw_response=result,

Drawbacks: now RazorpayClassAdapter exposes every public method of RazorpayClient too — create_order(), capture_payment(), etc. — leaking the Adaptee's surface to the world. The object adapter hides it cleanly.

🔁 Two-Way Adapter (rare but interview-citable)

An adapter that implements both interfaces, so calls can flow in either direction. Useful when two systems each expect to drive the other — e.g., bridging two ORMs where each thinks it's the "host."

class TwoWayLogAdapter(NewLogger, OldLogger):
    # Speaks NewLogger to new code; speaks OldLogger to legacy code.
    def log(self, level: str, msg: str):       # NewLogger
        self.write_line(_to_sev(level), msg)

    def write_line(self, sev: int, text: str):  # OldLogger
        self.log(_to_level(sev), text)

Mostly a curiosity in Python — almost always the right answer is two one-way adapters, not one two-way. But naming this in an interview signals you've actually read the GoF chapter.

Another (more famous) two-way adapter — currency converters in front-end forms. A trading dashboard shows the same price in USD and INR. Either field, when edited, should drive the other. Without an adapter you'd write two listeners with duplicate conversion logic. A two-way price adapter speaks both currencies:

class USDINRPriceField:
    # Speaks USD to "set from USD input"; speaks INR to "set from INR input".
    def __init__(self, rate: float):
        self._usd: float = 0.0
        self._rate = rate

    # direction 1: someone types USD → expose INR automatically
    def set_usd(self, usd: float):
        self._usd = usd
    def get_inr(self) -> float:
        return self._usd * self._rate

    # direction 2: someone types INR → expose USD automatically
    def set_inr(self, inr: float):
        self._usd = inr / self._rate
    def get_usd(self) -> float:
        return self._usd

from django.contrib.auth.backends import BaseBackend  # the Target

Quiz — Which of these is not a job for Adapter?

C is right. "We want to switch everything to a faster gateway" is just a refactor — if both gateways already implement the same interface, no Adapter is needed; if not, you do need an Adapter, but the motivation isn't "I want to switch", it's "two interfaces don't match." A, B, D are all interface mismatches between things you can't change — classic Adapter territory.

Why A, B, D are all genuine Adapter scenarios:

  • A — logger argument-order mismatch.
    • Adaptee: old_logger(level=2, msg="oops") — positional (int level, str msg)
    • Target: logger.log("oops", "warning") — positional (str msg, str level)
    • Different positions + level encoding. Adapter translates.
  • B — analytics interface mismatch.
    • Adaptee: Segment.io's analytics.track(event, properties=...)
    • Target: in-house Track with .event(name).property(k, v).flush()
    • Adapter wraps Segment SDK, exposes Track.
  • D — byte-vs-string mismatch.
    • Adaptee: Twitter SDK wants bytes for tweet body.
    • Target: our pipeline produces str objects (encoded later).
    • Adapter encodes on the way in, decodes on the way out.
  • C — not an Adapter problem.
    • Both gateways already implement PaymentGateway. Swapping = config change. The decision is operational, not structural.
   Adapter rule of thumb:
   ─────────────────────────────────────────────────────────────────────
     Do BOTH sides of this fit?              Adapter?
   ─────────────────────────────────────────────────────────────────────
     same interface, want to swap         →   No (refactor / DI)
     different interfaces, both fixed     →   Yes — this is Adapter
     different interfaces, one is mine    →   Just edit my side
     same interface, want extra behaviour →   Decorator

Quiz — You need to integrate Stripe. Stripe's SDK exposes charges.create(amount, currency, source); your codebase calls gateway.pay(amount, currency). Which option is the right one?

C is right. The point of Adapter is that both sides resist modification, for different reasons:
  • A — forking the SDK means you own every Stripe upgrade forever. Their next breaking change is your problem.
  • B — editing every caller spreads Stripe-specific shapes through your codebase. When you add PayPal next quarter, you do it all again.
  • C — an Adapter contains the mismatch in one file. SDK upgrades touch the adapter; new vendors get their own adapters; the rest of the code stays Stripe-agnostic.
  • D — rewriting from scratch ignores why people pay for vendor SDKs in the first place: auth, retries, error types, schema validation, ongoing security patches. You'd be reimplementing a 50-developer-year codebase to avoid a 30-line adapter.

The good answer in code — what C actually looks like:

✅ When Adapter earns its keep

Use Adapter when
  • Two interfaces must work together but don't match
  • You can't (or don't want to) modify either side
  • You want to contain a third-party dependency in one file
  • You're plugging multiple vendors behind one in-house interface (payment gateways, auth providers, analytics)
Skip Adapter when
  • You control both interfaces — just change one
  • The mismatch is one method renaming — a free function will do
  • The "Adapter" is just relaying every call unchanged — you've built a useless wrapper
  • The thing you're wrapping is already trivial to use directly

🏭 Two production conventions worth naming

1. Translate exceptions, not just methods

A leaky exception type is just as bad as a leaky method. If your adapter lets razorpay.errors.SignatureVerificationError propagate, callers now except razorpay.errors.SignatureVerificationError — and you've leaked Razorpay into the rest of the codebase. Map vendor exceptions to your own at the adapter boundary:

The bad design — what it looks like in code:

# payments/razorpay_adapter.py  — method names translated, exceptions NOT
class RazorpayAdapter(PaymentGateway):
    def pay(self, amount, currency):
        order  = self._client.order.create({"amount": int(amount * 100),
                                          "currency": "INR"})
        return self._client.payment.capture(order["id"])
        # <-- no try/except. If Razorpay raises, the exception flies up unchanged.

# checkout/views.py  — caller is forced to know Razorpay exists
import razorpay.errors           # ❌ Razorpay leaked into views.py

def checkout(request):
    gateway = get_gateway()
    try:
        gateway.pay(amount, "INR")
    except razorpay.errors.SignatureVerificationError:    # ❌ vendor type in views
        return JsonResponse({"error": "auth"}, status=401)
    except razorpay.errors.BadRequestError:               # ❌ same
        return JsonResponse({"error": "bad request"}, status=400)
    except razorpay.errors.RazorpayError:                 # ❌ same
        return JsonResponse({"error": "server"}, status=500)

2. Pair Adapter with Factory — transparent vendor selection

A real checkout doesn't hard-code which gateway to use. A factory reads config and hands out the right object — sometimes a native PaymentGateway, sometimes an Adapter — transparently:

class PaymentGatewayFactory:
    @staticmethod
    def create(kind: str) -> PaymentGateway:
        if kind == "stripe":
            return StripeGateway()              # native impl
        elif kind == "razorpay":
            return RazorpayAdapter(KEY, SECRET)    # Adapter around SDK
        elif kind == "paypal":
            return PayPalGateway()              # native impl
        raise ValueError(kind)

# Caller never knows which ones are adapters — that's the point.
gateway = PaymentGatewayFactory.create(settings.payment_provider)
gateway.pay(499.0, "INR")

This is the canonical "two patterns playing together" that interviewers love to drill on: Adapter makes the foreign SDK look native, Factory picks which one to hand back. Today's call uses Stripe natively; tomorrow's a Razorpay adapter; the caller never knows.

Compare

Adapter vs Facade vs Decorator vs Proxy

All four wrap an object. They look identical on a UML diagram. The difference is intent — what's the wrapper actually for?

In interviews, the trap is that all four structural patterns look structurally identical — one class holds another and forwards calls. The pattern names refer to why the wrapping exists, not how it's coded.

Pattern Intent (one sentence) Wrapped object's interface Wrapper's interface
Adapter Make an existing object usable where a different interface is expected Old / incompatible The Target interface (different from the wrapped one)
Decorator Add behaviour (logging, caching, auth) around an object without changing it Some interface X Same interface X, plus extra behaviour
Proxy Stand in for an object — control access, lazy-load, or remote-call it Some interface X Same interface X (transparent stand-in)
Facade Hide a complex subsystem behind one simple front-door API Many objects with many interfaces A small, simpler new interface

The litmus test — one question to disambiguate them:

• Does the wrapper change the interface? — Adapter (yes, to a different one) or Facade (yes, to a simpler one).

• Does the wrapper keep the same interface? — Decorator (yes, to add behaviour) or Proxy (yes, to control access).

In interviews, lead with the intent ("I'd use Adapter here because their interface doesn't match ours") — never with the code structure ("it's a class that holds another class"). Every structural pattern looks like that.

🥇 Cross-family — "why Adapter and not Factory or Strategy?"

The previous table compared Adapter against the rest of the structural family. But the interview follow-up is usually cross-family: "Why not Factory? Why not Strategy?" Boil each pattern down to one question:

Pattern Family The one question it answers Example
Factory Creational WHAT to create? "Stripe or Razorpay or PayPal?" → pick a concrete PaymentGateway
Adapter Structural HOW to make it compatible with my interface? "Razorpay's SDK speaks create_order; I want pay()" → translate calls
Strategy Behavioural HOW to do the same job in different ways? "Sort by price vs by rating vs by date" → swap the sorting algorithm

Concretely: the same domain can need all three, and they don't compete — they compose.

🔌 ADAPTER — structural · "wrap incompatible interfaces"

  • Use when: two interfaces must work together but don't match; you can't change either
  • Three roles: Target (interface client expects) · Adaptee (existing object) · Adapter (implements Target, holds Adaptee)
  • Variations: Object Adapter (composition — idiomatic) vs Class Adapter (multiple inheritance — rarely worth it)
  • Real-world: StringIO/BytesIO · Django auth backends · SQLAlchemy dialects · payment gateway wrappers
  • Skip when: you control both interfaces · the mismatch is one rename (just rename it)
  • #1 bug: leaking the Adaptee (public self.client field) — callers reach past the wrapper

🎯 STRUCTURAL CHEAT — "which wrapper pattern?"

  • Interface changes → Adapter (translate) or Facade (simplify many → one)
  • Interface stays the same → Decorator (add behaviour) or Proxy (control access)

🎯 Interview cheat sheet

If asked "when would you use Prototype?": lead with the cost equation — expensive constructor + many similar instances needed. Mention copy.deepcopy and the shallow-vs-deep trap. Bonus points: mention that dataclasses.replace is often what you actually want in Python.

If asked "when would you use Adapter?": lead with the mismatch — two interfaces, neither under your control. Mention composition (object adapter) over inheritance. Bonus points: name a real-world example (StringIO, Django auth backend, payment gateway wrapper).

If asked "Adapter vs Decorator vs Proxy vs Facade": don't talk about code — talk about intent. All four wrap. The pattern name says why.
