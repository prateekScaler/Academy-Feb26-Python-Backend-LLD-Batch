Types of LLD Interviews & How to Approach Them

LLD-21 • The methodology class — turn what you know into what you ship in 90 minutes

You've spent the last eight classes learning SOLID, design patterns, and UML. This class is about how to use all of that under interview pressure. Same problem solved by two candidates — one panics, one ships. The difference is the approach, not the IQ.

Recap — LLD-20

Recap quizzes — spot the pattern, then decorator & UML

First six: name the design pattern from the diagram alone (we've used neutral domain names so the SHAPE of the boxes and arrows is what reveals it). Then four on Decorator + UML relationships.

Part 1 — Spot the pattern from the UML (6 questions)

Spot Quiz 1 — Which pattern is this? (ReportGenerator writes the same report in many file formats.)

B is right. Signature shape: one context (ReportGenerator) holds one reference to an abstract interface; N concrete implementations of that interface. No wrapping (so not Decorator), no notification fan-out (so not Observer), no object-creation method on the context (so not Factory). "One open variable plugged into a context that uses it" → Strategy.

Spot Quiz 2 — Which pattern is this? (Wrappers stack around a raw byte stream to add behaviour.)

A is right. Signature shape: StreamWrapper both implements DataStream AND holds a DataStream instance — that purple "wraps" arrow loops back up to the same interface. Self-referential composition is what lets wrappers wrap wrappers (e.g. EncryptedStream(GzipStream(RawFileStream()))). Strategy is a flat "Context has-a Strategy" with no loop. Adapter holds a different type than the one it implements. Proxy looks similar but exists to control access, not add behaviour.

Spot Quiz 3 — Which pattern is this? (A PriceTicker fires once per tick; several handlers react independently.)

C is right. A subject keeps a list of references to an abstract type and calls a notify method that fans out. That fan-out is the Observer signature. Mediator differs because it knows each participant by name and routes selectively. Strategy is one-to-one, not fan-out. Chain of Responsibility is a linked sequence where each link decides whether to pass on — not a list of independents.

Spot Quiz 4 — Which pattern is this? (Each logistics company decides which kind of transport it ships with.)

D is right. Signature shape: an abstract class declares a single abstract creation method; each concrete subclass returns a different concrete product from that one method. Builder uses fluent chaining over an under-construction object — not present here. Abstract Factory has a family of related products (multiple create methods) — we only have one. Singleton has zero creation polymorphism.

Spot Quiz 5 — Which pattern is this? (One logger across the whole process.)

A is right. Three signature features: a private constructor, a static reference to its own type, and a static get_instance() that lazily creates and returns it. That trio means "this class controls how many of itself exist, and the answer is one". Factory creates DIFFERENT classes. Prototype clones from an existing instance. Builder accumulates configuration through a fluent API.

Spot Quiz 6 — Which pattern is this? (Wrap a third-party SDK so it matches the contract our code expects.)

B is right. The middle class implements one interface (PaymentGateway) but holds an instance of a different type (RazorpaySDK) and translates calls. The interface implemented is DIFFERENT from the type held — that's what makes it Adapter and not Decorator (where both are the same interface). Facade fronts a complex subsystem with a simpler API but doesn't translate between two incompatible ones. Bridge separates an abstraction hierarchy from an implementation hierarchy — both designed together, not glued post-hoc.

Why this drill matters: in a Tier-2 design discussion you'll often be handed someone else's diagram. The interviewer's next question is almost always "which pattern is this?" Naming it forces you to articulate what is open for change. The labels above are deliberately neutral — you have to read the SHAPE (interface + concrete impls + how the boxes relate) to spot the pattern.

Part 2 — Decorator order & UML relationships (4 questions)

Quiz 1 — Given the code below, which method runs first when the caller calls pricer.total(cart)?

class BasicPricer:
    def total(self, cart):
        return sum(item.price for item in cart)

class TaxDecorator:
    def __init__(self, inner):
        self._inner = inner
    def total(self, cart):
        return self._inner.total(cart) * 1.18   # add 18% GST

class DiscountDecorator:
    def __init__(self, inner, percent):
        self._inner = inner
        self._percent = percent
    def total(self, cart):
        sub = self._inner.total(cart)
        return sub * (1 - self._percent / 100)

# How the caller wires it up:
pricer = DiscountDecorator(TaxDecorator(BasicPricer()), percent=10)
pricer.total(cart)
C is right. Decorators run outside-in. The caller holds a reference to the outermost wrapper (DiscountDecorator), so its total() runs first — it calls self._inner.total() which is TaxDecorator, which in turn calls BasicPricer. Read the constructor chain right-to-left and you get the execution order outside-in.

Bonus — why order matters here: with Discount(Tax(Basic)) the discount applies AFTER tax (you save less). Swap to Tax(Discount(Basic)) and the discount applies BEFORE tax (you save more, GoI tax-code's actual rule). Same components, different stacking order → different result. This is the real reason decorator order is worth thinking about, not just trivia.

Quiz 2 — A House has many Room objects. If the house is demolished, the rooms cease to exist — a room can't migrate to a different house. In UML, which relationship is this?

B is right. Composition is the strongest has-a: shared lifetime and exclusive ownership. Kill the whole, the parts die with it; the parts cannot be transferred to another whole. UML draws the diamond on the WHOLE side (the owning end) and fills it in.

Aggregation looks the same but with an open diamond — that's for parts that outlive the whole. Inheritance is a triangle, not a diamond. Association is just a line — "knows about", no ownership claim.

Quiz 3 — A Team has a list of Player objects. Players exist before the team is formed and survive after it dissolves — the same player can join other teams. In UML, which relationship is this?

D is right. Aggregation is the weaker has-a: the whole holds the parts, but the parts have independent lifetimes and can be shared across wholes. UML draws the diamond on the whole side but leaves it open.

Composition would imply the players die with the team — not the case here. Inheritance and Realisation are about is-a, not has-a.

Quiz 4 — A Doctor has a set of Patient objects they're treating. Neither owns the other; if the doctor leaves the hospital, the patients continue with someone else. In UML, which relationship best fits?

A is right. Association is the most neutral relationship — two classes that know about each other and interact, but neither owns the other. No diamond. UML just draws a line, optionally with multiplicity (1..*) and a role name.

In Python this looks like a list reference with no destruction semantics — either side can hold or release the other freely:

class Patient:
    def __init__(self, name: str):
        self.name = name
        # patient does NOT own the doctor; no back-reference needed

class Doctor:
    def __init__(self, name: str):
        self.name = name
        self.patients: list[Patient] = []   # just a reference, not ownership

    def assign(self, p: Patient) -> None:
        self.patients.append(p)

    def release(self, p: Patient) -> None:
        self.patients.remove(p)        # patient is still alive after this

# both exist independently in some registry
asha = Patient("Asha")
dr_mehta = Doctor("Dr Mehta")
dr_mehta.assign(asha)         # now treats her

dr_mehta.release(asha)        # still alive
del dr_mehta                # patient is still alive (registry holds her)

Composition and Aggregation both imply a "whole" that holds "parts" — not the case between a Doctor and a Patient. Dependency is for short-lived uses (a parameter or local variable), not a long-term relationship.

Why this class matters

You know the theory. Now ship it under pressure.

Eight classes on patterns. Now you face 90 minutes with a stranger asking you to design Splitwise. What separates the candidate who passes from the one who freezes is not the patterns — it's the approach.

Candidate A — jumps in
  • Hears "Design Splitwise" → starts typing in minute 2
  • Writes class User and class Group with no thought to API
  • Halfway through, realises they forgot percentage splits — rewrites
  • At 80 minutes: working demo for "equal split, two people" — nothing else
  • Interviewer asks "how do you handle settlements?" — candidate freezes
Candidate B — runs the playbook
  • 0–5 min: asks 4 clarifying questions, agrees on scope with interviewer
  • 5–15 min: writes 6 entities + 8 APIs on the board
  • 15–65 min: codes the happy path first, then the two edge cases agreed
  • 65–80 min: live demo + trade-off discussion (SQL vs in-mem, concurrency)
  • 80–90 min: extensions they'd build next, interviewer nods

Both candidates know the same patterns. Today's class is the difference between knowing and shipping.

Types of LLD interviews

First the Indian tech tiers, then the six concrete formats

Three tiers of companies in India interview for the same role in three quite different ways. Inside each tier the format also varies. We'll do the tier view first, then the format view.

The three Indian tiers

💵
Tier 1 — Traditional IT

Who: TCS, Infosys, Wipro, Cognizant, Accenture, Capgemini, HCL.
Style: theory-heavy verbal Q&A (30–45 min). Almost no coding.
Asks: "Explain SOLID", "Singleton vs Factory", "What is duck typing", "abstract class vs interface", "thread-safe Singleton".
Prep: memorise GoF pattern names + 2 examples each; SOLID with examples; Python specifics (decorators, GIL, magic methods).

🏢
Tier 2 — Product MNCs

Who: Google, Microsoft, Amazon, Flipkart, PhonePe, Uber, Ola, Paytm.
Style: design process on a whiteboard/doc (45–60 min). Pseudo-code or partial real code.
Asks: "Design Zoomcar / Library / Movie booking". Wants requirements, class diagram, APIs, deep-dive on schema or concurrency.
Prep: the 7-step playbook below; 10+ problems end-to-end on whiteboard.

⚡
Tier 3 — Modern startups

Who: Swiggy, Zomato, Cred, Razorpay, Zepto, Meesho, ShareChat, Dream11.
Style: machine-coding round (90–120 min). Working code in IDE, runnable demo, sometimes test cases.
Asks: "Build Splitwise" / "Build Snake-and-Ladder". Cares about a working demo more than perfect design.
Prep: 90-minute timed mocks; python main.py habit; dataclasses + Enums + comprehensions.

Within each tier — especially Tier 2 and Tier 3 — the concrete format still varies. These are the six you'll actually encounter:

The six concrete formats

⏳
1. Machine coding (90 min)

Format: sit-down, IDE, ship a working solution.
Common at: Flipkart, Walmart, Razorpay, Swiggy, Zomato, Cred, PhonePe.
Judged on: working demo + clean class design + you can extend it live.
Sample problems: Splitwise, Parking Lot, Tic-Tac-Toe, BookMyShow, ride-sharing, in-memory cache.

📝
2. Design discussion (45–60 min)

Format: whiteboard / Google Doc — UML class diagram + API list + trade-offs. No working code required.
Common at: Google, Meta, Amazon (mixed with HLD), Atlassian.
Judged on: clean class diagram, sound APIs, SOLID/pattern awareness.
Sample problems: Uber matching, ATM, vending machine, hotel booking.

🏠
3. Take-home (24–72 hrs)

Format: implement at home, submit a repo with tests, README, design notes.
Common at: startups, Stripe, GitLab, remote-first companies.
Judged on: code quality, test coverage, design choices in README, no shortcuts.
Sample problems: URL shortener, chess engine, file deduper, e-commerce checkout.

🧮
4. System + LLD hybrid (60 min)

Format: half HLD (services, DBs, scale), half LLD (one component drawn in classes).
Common at: senior+ rounds at FAANG, Atlassian, Uber.
Judged on: when to zoom out vs zoom in; ability to switch altitude on demand.
Sample problems: Design Instagram — HLD the feed, LLD the comment model.

🔎
5. Code review (45–60 min)

Format: given a PR-shaped piece of code, find bugs / smells / SOLID violations and suggest fixes.
Common at: Atlassian, Stripe, Twilio, Microsoft.
Judged on: what you notice + how you frame feedback + the fix you propose.
Sample problems: "Here's a 200-line file — what's wrong, what do you change first?"

💬
6. Live design discussion (30 min, screen)

Format: no whiteboard, just talk. "Walk me through how you'd design X."
Common at: phone screens, recruiter pre-screens.
Judged on: can you stay structured without drawing?
Sample problems: "Design a rate limiter — talk me through it."

Quiz 1 — The recruiter says: "90 minutes, IDE of your choice, build a working Parking Lot." Which format is this?

B is right. Time-boxed + IDE + working solution required = machine coding. Take-home is multi-day with a repo. Design discussion is no-code on a whiteboard. Code review starts from existing code, not a blank IDE.

Quiz 2 — "Design Instagram — 30 minutes on the feed at scale, then 30 minutes on the comment model in classes." What's this?

D is right. "Feed at scale" is HLD territory (sharding, caching, fanout). "Comment model in classes" is LLD. The two-part framing is the signature of the hybrid round — common at senior+ FAANG and Atlassian. Pure HLD wouldn't ask for classes; pure LLD wouldn't ask for scale.

Quiz 3 — "Here's a 200-line Python file. Read it for 10 minutes, then walk me through what you'd change." What format?

A is right. Starts from existing code, no new code expected, you talk through changes — that's code review. Stripe and Atlassian use this format heavily. Don't confuse with machine coding (blank IDE) or design discussion (no code at all).

Quiz 4 — You're asked to "draw the class diagram for an ATM — we don't need code." Format?

C is right. "Draw" + "we don't need code" = design discussion. What you sketch on the whiteboard is a rough class diagram — boxes for classes, lines for relationships, and which design pattern each part is using — not pixel-perfect UML with every arrow head correct. Plus an APIs list and verbal trade-offs. This is where the LLD-20 vocabulary helps you talk about design, even when the picture is loose.

Quiz 5 — "We'll send you a problem on Friday. Submit a GitHub repo by Monday." Format?

B is right. Multi-day + GitHub repo = take-home. Different judging axis: they expect tests, a README explaining your decisions, and polish you can't fit in 90 minutes. Submitting a single .py file with no tests is the most common way to fail this format.
The 7-step approach

A repeatable playbook for 90-minute LLD

Same template, every problem. The first three steps look slow; they're what makes the last four fast.

0 — 5 min • Step 1
Clarify the problem
Ask 3–5 specific questions. Pin down scope. Do NOT start coding.
5 — 10 min • Step 2
Write down requirements
Functional (what it does) + non-functional (scale, concurrency, persistence).
10 — 18 min • Step 3
Identify entities & relationships
Nouns become classes. Verbs become methods. Draw a quick UML.
18 — 25 min • Step 4
Define the public APIs
For each entity, list 2–5 method signatures. Names & types only — no bodies yet.
25 — 65 min • Step 5
Code the happy path first
Get the simplest input working end-to-end. Then add the edge cases you agreed on in Step 1.
65 — 80 min • Step 6
Demo & verify
Run the code. Walk the interviewer through one happy + one edge-case run.
80 — 90 min • Step 7
Trade-offs & extensions
"If we had 10 more minutes, I'd…" + concurrency, persistence, SOLID, patterns used.

Step 1 — Clarify (0–5 min)

1a. Overview alignment — agree on what you're building

Before any scope question, confirm you and the interviewer mean the same thing by the product name. Half of all failed Splitwise / Zoomcar / Dunzo interviews start with a student silently guessing what the product does.

✖ Bad — assume + start 
Interviewer: "Design Zoomcar."
You:         "Sure, let me start with a User class..."
             [silently assumes it's like Uber]
             [40 min in, realises Zoomcar is self-drive
              rentals, not ride-hailing]
✔ Good — confirm, then narrow 
Interviewer: "Design Zoomcar."
You:         "Quick check — Zoomcar is the self-drive
              car-rental platform where users book by
              the hour/day. Right?"
Interviewer: "Yes, exactly."
You:         "Got it. Consumer side (booking) or admin
              side (inventory) — which one first?"
Interviewer: "Consumer."

If you genuinely don't know the product, say so out loud:

You: "I haven't used Dunzo — could you give me a one-line description of what it does?" Interviewer: "Hyperlocal delivery: packages, groceries, within a city." You: "So a courier + grocery delivery hybrid. Should I focus on the delivery-assignment flow or the order-management flow?"

Asking is a strength signal, not a weakness. Pretending costs you the round.

Overview-alignment Quiz — Interviewer says "Design Dunzo." You've heard the name but aren't sure exactly what they do. What's the right next move?

B is right. Asking the interviewer to describe the product is normal, low-risk, and shows you'd do the same on the job before designing anything. Pretending (C) means you'll discover 30 minutes in that you were modelling Uber when they wanted package delivery. Asking for a different problem (D) signals you can't recover from ambiguity. Typing without checking (A) is the classic "candidate A" failure from the opening of this class.

1b. Then the scope/scale/out-of-scope sweep

Three categories to cover — pick 1–2 from each:

Scope questions

"Do users have a single group or many?"
"Do we support partial payments, or full only?"
"Is currency conversion in scope?"

Scale questions

"In-memory or persistent?"
"Single-threaded or concurrent users?"
"How many groups / orders do we plan for?"

Out-of-scope questions

"Do we need auth / login flow?"
"UI, or just the engine?"
"Do we generate invoices, or just compute totals?"

Quiz 1 — Interviewer says "Design Splitwise." You have 5 minutes for clarifying questions. Which is the best opener?

D is right. Clarifying questions must be about the problem, not your toolkit. Asking about SOLID, patterns, or tests signals "I'm thinking about what looks good" rather than "I'm thinking about what to build". A scope question like the split-type one pins down the smallest thing that changes your design.

Quiz 2 — The interviewer says "yes, support equal + percent + share splits." How many minutes do you spend asking more questions before moving on?

C is right. Most candidates rush this. The first answer unlocks more questions ("ok, percent — do percentages always sum to 100, or can we round?"). 3–5 minutes is the standard budget — long enough to nail scope, short enough that you still have 85 minutes to build. Spending 8–10 minutes is the opposite failure: you run out of code time. Spending 0–1 is the original mistake.

More worked examples — wrong vs right clarifying (click to expand)

Three different problem shapes. Each is a real interview ask. For each: what most candidates say, vs what gets you ahead.

💰 "Design Splitwise"

▾
✖ Wrong — assume equal split only 
Interviewer: "Design Splitwise."
You:         "OK — I'll model User, Group,
              Expense. Equal split among
              everyone in the group."
              [starts coding]
              [40 min in: realises Bhavna
               actually paid 70% of dinner
               and percent split is a thing]
              [refactors data model]
✔ Right — pin down the split-type spectrum 
You: "Split types — just equal, or
      also percent / share / exact-rupee?"
Int: "Equal + percent + share. Skip exact-rupee."
You: "Settlements — do we record actual
      payments, or just compute who-owes-whom?"
Int: "Both. Show the optimised payment graph too."
You: "Single currency?"
Int: "INR only, no conversion."
You: "OK — let me confirm scope on the
      board before I touch a line of code."

Why this saves you: the moment you hear "percent and share split", you reach for a SplitStrategy ABC from minute 12 instead of refactoring an inheritance tree at minute 40. The clarifying question literally chose your design pattern for you.

🎬 "Design BookMyShow"

▾
✖ Wrong — jump straight to seats 
Interviewer: "Design BookMyShow."
You:         "Theater → Screen → Show → Seat.
              Users pick seats → pay → done."
              [codes happily]
              [interviewer: "what if two
               people pick the same seat?"]
              [you: silence]
✔ Right — surface the locking + payment edges 
You: "Multi-user simultaneous booking —
      how do we handle the seat-lock race?"
Int: "Lock for 10 minutes when added to cart,
      release on timeout or cancel."
You: "Payment — sync or async webhook?
      What about partial failures?"
Int: "Async. Refund flow needed for failures."
You: "One screen one show, or
      multiple shows per screen per day?"
Int: "Multiple. Up to 6 shows per screen."

Why this saves you: seat-locking is the bread-and-butter of this problem — you'll be asked about it whether you ask or not. Asking up-front lets you model SeatLock as a first-class entity (with TTL + idempotency) in Step 3, instead of bolting concurrency control onto a model that doesn't have a place for it.

🚗 "Design Uber's driver-rider matching"

▾
✖ Wrong — "nearest driver wins" 
Interviewer: "Design Uber matching."
You:         "Find nearest available driver
              by lat/long, assign, done."
              [codes a haversine loop]
              [interviewer: "what about surge?
               UberPool? auto vs sedan? what
               if the driver rejects?"]
              [scope explodes mid-coding]
✔ Right — pin the matching axis 
You: "Single ride type, or auto / sedan / suv?"
Int: "Just two: auto + sedan."
You: "Rider gets one driver, or batched
      to a pool (UberPool style)?"
Int: "One driver only. Skip pooling."
You: "Driver-acceptance flow — auto-assigned,
      or driver can decline + we re-match?"
Int: "Can decline. We re-match within 10s."
You: "Is surge pricing in scope, or
      just the matching algorithm?"
Int: "Matching only. Pricing is out of scope."

Why this saves you: "re-match within 10s on decline" is the most non-obvious requirement — it changes your design from a one-shot allocator to a retry-able matching loop with state (driver pool, decline history, timeout). You'd never reach for that without asking.

Pattern across all four examples (Zoomcar, Splitwise, BookMyShow, Uber): the WRONG version codes from a default assumption; the RIGHT version asks one question about the open variable — the place the design is most likely to differ from your first guess. Get that one right and the next 85 minutes flow.

Step 2 — Requirements (5–10 min)

Write them down. Say them out loud. Pin them up where you'll see them while coding.

The 5–6-requirements cap (golden rule)
  • Functional requirements: cap at 4–5.
  • Non-functional: cap at 1–2.
  • Nice-to-haves: park them in a separate "future scope" list. Mention out loud, do NOT implement.
  • Working code for 4 features beats half-broken code for 15.
  • The interviewer would rather see one Strategy slot in cleanly than watch you ship nothing because you took on the full PRD.

Worked example — "Design Spotify (single user, in-memory):"

Functional requirements (what)
  • Stream a song — play / pause / seek
  • Build a playlist; play it in order or on shuffle
  • Search the catalogue by title / artist / album
  • Like a song (add to "Liked Songs" library)
  • Track recent listening history per user
Non-functional requirements (how)
  • In-memory catalogue — no DB for this round
  • Single user — no concurrent listeners
  • Catalogue size: ~10,000 songs
  • Audio decoding out of scope — play() just prints
  • Extensible: a new shuffle / smart-playlist rule is one new class

Quiz 3 — The interviewer says "catalogue is ~10,000 songs." What's the RIGHT thing to do with that number?

A is right. 10,000 is small — a linear scan or a single Python dict handles search and lookup comfortably. No sharding, no cache, no inverted index needed for an in-memory interview. The point of an NFR number is to narrow your design, not blow it up: B, C, D all over-engineer for scale you don't have. Pinning the number on the board means later, when you reach for a fancy algorithm, you catch yourself: "wait, the catalogue is 10K — this is overkill."

Step 3 — Entities & relationships (10–18 min)

Two reliable ways to find your entities. Pick by the shape of the problem.

Approach A — Noun identification

When: business-domain problems (library, parking, e-commerce, food delivery, Splitwise). Anything with users, transactions, inventory.
How: circle the nouns in your requirements — those are your classes. Underline the verbs — those are your methods.

Splitwise: "User, Group, Expense, Payment, Split, Balance, Currency" → entity list. "add_user, add_expense, split, settle, get_balance, simplify" → methods.
Approach B — Visualization

When: games, simulations, real-time systems (chess, snake-and-ladder, tic-tac-toe, an elevator scheduler).
How: picture the gameplay in your head. The visible pieces are the entities; the actions are the methods.

Snake-and-Ladder: picture the board → Board, Player, Dice, Snake, Ladder, Game. Each one obvious from imagining the table the kids are sitting at.

Most problems use one approach cleanly. A few hybrids (Parking Lot is both): nouns give you Vehicle / Spot / Ticket, visualization gives you Floor / multi-level structure.

Approach Quiz — "Design an elevator scheduler — multiple floors, multiple elevators, requests pile up." Which approach do you start with?

A is right.
  • Elevator system is a real-time simulation — floors, cars, directions, requests piling up. Easier to see than to read.
  • Picture it for 20 seconds → entities surface almost instantly: Elevator, Floor, Request, Direction (enum), Scheduler.
  • Noun identification still works — but the requirements text usually doesn't name every entity (e.g. "Direction" rarely appears as a noun), so you'd miss things.
  • ER diagram (D) is wrong layer — that's persistence design, not the object model the interview wants.
  • Jumping to code (C) is the exact failure mode this whole class is fixing.

What "picturing the lobby for 20 seconds" surfaces

Step 4 — Define the public APIs (18–25 min)

For each class, write 2–5 method signatures. Names + parameters + return types. No method bodies. The point: when you start coding in Step 5, you already know exactly what to type.

Splitwise — APIs only, no bodies
collapse▾
from abc import ABC, abstractmethod

class User:
    def __init__(self, user_id: str, name: str): ...

class Group:
    def add_user(self, user: User) -> None: ...
    def add_expense(self, expense: Expense) -> None: ...
    def balances(self) -> dict[User, float]: ...
    def simplified_payments(self) -> list[tuple[User, User, float]]: ...

class Expense:
    def __init__(self, payer: User, amount: float, split: SplitStrategy): ...
    def shares(self) -> dict[User, float]: ...

class SplitStrategy(ABC):
    @abstractmethod
    def split(self, amount: float, members: list[User]) -> dict[User, float]: ...

class EqualSplit(SplitStrategy): ...
class PercentSplit(SplitStrategy): ...
class ShareSplit(SplitStrategy): ...

Notice: Strategy pattern from LLD-19 already shows up — SplitStrategy is an ABC with three implementations. The patterns are tools you reach for in Step 3–4, not slogans you announce.

Quiz 5 — Why write methods as signatures-only in Step 4, instead of starting to fill them in?

C is right. The signature is where you commit to the contract: parameter types, return type, which class owns the method. If the signatures look wrong (e.g. Group.add_expense took a raw dict instead of an Expense object), you fix it in 10 seconds. Once bodies are written, the same fix is 5 minutes of edits across files. Python doesn't need forward declarations (B); A is too small a benefit; the interviewer cares about your reasoning, not your ceremony.

Step 5 — Code the happy path first (25–65 min)

40 minutes is the meat of the interview. Two rules:

  • Happy path first. One group, two users, equal split, one expense. End-to-end. Then add edges.
  • Print as you go. Every class gets a tiny main() snippet that exercises it. If the interviewer asks "does this work?" you run it in 3 seconds.

Quiz 6 — 50 minutes in: equal-split works end-to-end. 40 minutes left. What do you build next?

A is right. Build features in the order you agreed in Step 1. Thread safety, persistence, and tests are all great — but if you said "in-memory, single-threaded" in Step 2, doing them now eats the time you need for the OTHER feature you promised. Most candidates fail by widening scope mid-flight rather than finishing what they agreed to.

Step 6 — Demo & verify (65–80 min)

Run your code in front of the interviewer. Walk one happy path. Walk one edge case. If it crashes, fix the crash on screen — that's a signal of strength, not weakness. Interviewers love watching you debug.

Step 7 — Trade-offs & extensions (80–90 min)

The last 10 minutes decide whether you pass with a "yes" or a "strong yes". Have answers ready for:

  • Concurrency: "I assumed single-threaded. To support concurrent writes, I'd guard Group.add_expense with a lock, or move to per-user queues."
  • Persistence: "Right now it's in-memory dicts. To persist, I'd add a Repository per aggregate — GroupRepository, UserRepository — and keep the domain classes ignorant of storage."
  • SOLID: "SplitStrategy is OCP-friendly — new split types are new classes. The Expense doesn't isinstance-check the split."
  • Extensions: "If we had 10 more minutes, I'd add the payment-graph simplification algorithm."

Quiz 7 — Interviewer asks "How would you scale this to 1M concurrent users?" You designed for 100 in-memory users. Best answer?

D is right. Show the path: identify the bottleneck (in-memory state can't survive crashes or fan out), name the first lever (persistence), name the second (partitioning by a natural key — group_id, since most reads/writes are within a group). A is wrong (in-mem state breaks at any scale). B punts. C drops a buzzword. D is a concrete step-by-step that respects what you already built.

The meta-skill: at every step, you're showing the interviewer your process. Even if your code has bugs, a candidate who follows steps 1–7 audibly — "I'm clarifying", "I'm picking entities", "I'm coding the happy path" — conveys senior-level habits. Silence + furious typing conveys panic, regardless of how clean the code turns out.

Mistakes that tank interviews

Seven habits we audit candidates for — and the fix for each

Every one of these is a real pattern we've seen kill loops in the last 12 months. Recognise them in yourself before the interviewer recognises them in you.

Mistake 1 — Diving into code without clarifying. What's the symptom?

D is right. Rewriting the data model mid-flight is the tell that you guessed at scope. Compiling-on-first-try is good. Finishing in 45 means you under-built (or got an easy problem). Silent interviewer is neutral (they're observing). But "I need to refactor — turns out percentages don't always sum to 100" 35 minutes in is the unmistakable cost of skipping Step 1.

Mistake 2 — Building all 47 features instead of the MVP. The fix is…

B is right. Scope is a co-designed contract. "I'll do equal split + percent split + simplified payments — we'll skip currency, settlement history, and the UI. Sound good?" gets a nod and protects your time budget. C makes it worse. D skips the highest-signal part. A doesn't fix the structural problem.

Mistake 3 — Inheritance for everything. Symptom in code?

A is right. The "deep, wide hierarchy" smell — the chai-shop trap from LLD-20. Most LLD problems want composition (Strategy, Decorator) not inheritance. Protocol classes (C) are a green flag — structural typing without hierarchy. Dataclasses (D) are also fine. Three flat classes (B) usually means under-modelled, not over-modelled.

Mistake 4 — In minute 3, before any design is on the board, you announce: "I'll use Factory + Strategy + Observer here." What does the interviewer most likely hear?

C is right. Patterns are tools you reach for in Step 3–4 when you've recognised the shape of the problem — "the algorithm is the open variable, so Strategy"; "I'm fanning out one event to many independent reactions, so Observer". Naming patterns before the design is on the board signals the opposite: you're pattern-shopping to look senior. Senior candidates introduce patterns silently, as code, and only name them when asked or when justifying a trade-off. Reach for any pattern only when (a) you can name the open variable it solves for, and (b) the cost of NOT using it is concrete in this problem.

Mistake 5 — Naming. Which method name is healthiest?

B is right. Verb + domain noun. A reader knows what the method does without reading the body. doStuff, processData, handle are placeholder names that scream "haven't decided what this is yet". Interviewers read your naming as a proxy for whether you've actually thought about the contract.

Mistake 6 — Code at 70 minutes works. Interviewer says "let's see it run." You…

C is right. Live debugging is the single highest-signal moment in the interview. A candidate who calmly says "ah, I forgot to seed the user list — one sec" and fixes it in 30 seconds is rated higher than one who never runs the code. A signals fragility. B signals panic. D signals avoidance. Running and fixing signals "I do this every day".

Mistake 7 — Last 5 minutes. Interviewer: "trade-offs?" You…

A is right. Have 3 trade-offs ready before you walk in: persistence (where state lives), concurrency (what breaks under contention), and extension (what's the next feature and where would it slot in). "I'd add tests" (B) is too small. C apologises. D abandons the design you just built. The 3-trade-offs answer is rehearsable and converts a passing interview into a strong-yes.

Step 3 in detail — entities & relationships

Parking Lot — the class skeleton you draw in minute 15
collapse▾
from typing import Protocol
from dataclasses import dataclass
from enum import Enum

class VehicleType(Enum):
    CAR = "car"; BIKE = "bike"; TRUCK = "truck"

@dataclass
class Vehicle:
    plate: str
    kind: VehicleType

@dataclass
class Slot:
    slot_id: str
    kind: VehicleType
    occupied: bool = False

class ParkingStrategy(Protocol):
    def pick(self, free_slots: list[Slot]) -> Slot | None: ...

class FirstFit(ParkingStrategy):
    def pick(self, free_slots):
        return free_slots[0] if free_slots else None

class PricingStrategy(Protocol):
    def charge(self, kind: VehicleType, hours: float) -> float: ...

class FlatHourly(PricingStrategy):
    RATES = {VehicleType.CAR: 40, VehicleType.BIKE: 20, VehicleType.TRUCK: 80}
    def charge(self, kind, hours):
        return self.RATES[kind] * max(1, hours)

class ParkingLot:
    def __init__(self, slots, strat, pricing):
        self.slots = slots
        self.strat = strat; self.pricing = pricing
        self.active: dict[str, tuple[Slot, float]] = {}

    def park(self, v: Vehicle, t0: float) -> str | None:
        free = [s for s in self.slots if not s.occupied and s.kind == v.kind]
        slot = self.strat.pick(free)
        if slot is None: return None
        slot.occupied = True
        ticket = f"T-{v.plate}"
        self.active[ticket] = (slot, t0)
        return ticket

    def unpark(self, ticket: str, t1: float) -> float:
        slot, t0 = self.active.pop(ticket)
        slot.occupied = False
        return self.pricing.charge(slot.kind, (t1 - t0) / 3600)

Read what just happened: two Strategy patterns (ParkingStrategy, PricingStrategy) so adding "nearest-to-exit placement" or "weekday vs weekend pricing" is one new class. A dataclass for Vehicle / Slot — immutable enough for this round. The ParkingLot is the orchestrator. You wrote 50 lines of code in 7 minutes because Steps 1–4 already drew the map.

Walk-through Quiz 1 — You'd skip FirstFit and inline free_slots[0] in park(). Worth doing in an interview?

B is right. The Strategy is two extra lines but a major change in optionality. When the interviewer asks "how would you support nearest-to-exit?" you answer in one sentence: "new ParkingStrategy class". Without it you'd have to refactor. C is the trap that kills time later. D is wrong — SOLID doesn't mandate Strategy; you reach for it when the algorithm is the open variable, which here it is.

Walk-through Quiz 2 — Interviewer adds: "support reserved EV slots". Where does that change live?

A is right. Extension via composition: new enum value, new strategy class that knows how to prefer the EV slots, plug it in. ParkingLot itself is unchanged — that's OCP from LLD-13. Rewriting park (B), subclassing the orchestrator (C), or adding inline ifs (D) are all ways to slowly turn the code into a god-object.
Warm-up exercise

Design a Pen — first try, then learn

Before reading any of our solution: spend 10 minutes with just the requirements below and the template that follows. Then scroll down and compare your answer to ours through five evolutions.

✏️ The problem

Design a Pen. Here is everything you know:

  • A pen is anything that can write.
  • Types: Gel, Ball, Fountain, Marker, Throwaway.
  • Ball and Gel pens use a refill (which has a tip/nib and an ink).
  • Ink has a colour.
  • Fountain pens have an ink directly (no refill); their nib has a radius.
  • Refills have a radius.
  • Each pen writes in its own way. Some pens write in the same way as others.
  • Every pen has a brand and a name.
  • Some pens are refillable; some are not (throwaway).

📝 Your turn first — the template

Pause here. Open a doc / notebook. Don't scroll. For 10 minutes, fill in:

  1. Clarifying questions (3–5): what would you ask the interviewer before designing anything?
  2. Entities: which classes? (Use noun-identification on the requirements.)
  3. Relationships: which ones own which? Which are has-a vs is-a?
  4. The write() method: where does it live? How do you avoid an if-tree?
  5. Refilling: how do you stop someone calling change_refill() on a fountain pen?

When you're done, scroll. We'll walk five different designs — each fixes a flaw in the previous one. See how many of these you naturally arrived at.

Pen Quiz 1 — Which of these is the strongest clarifying question to ask FIRST?

B is right. Whether new pen types arrive later decides whether you reach for OCP-friendly designs (Strategy, abstract base, Protocol) or a much simpler single-class with an enum. Answering wrong sends you down 30 minutes of over-engineering or under-engineering. A asks about UX (out of scope here). C asks a triviality. D commits to a pattern before you know the shape.

Evolution 1 — one giant Pen class with a type enum

The first instinct: one Pen class, with a PenType enum and an if-tree inside write().

Class diagram — the god class

class Pen:
    def __init__(self, brand, name, pen_type, price):
        self.pen_type = pen_type
        self.refill = self.ink = self.nib = None  # all nullable

    def write(self):
        if   self.pen_type == PenType.GEL:      print("Gel writes")
        elif self.pen_type == PenType.BALL:     print("Ball writes")
        elif self.pen_type == PenType.FOUNTAIN: print("Fountain writes")
        elif self.pen_type == PenType.MARKER:   print("Marker writes")
        else: raise ValueError("unknown pen")

    def change_refill(self, refill):
        if self.refill and self.refill.refillable:
            self.refill = refill
  • SRP violated. Every pen-type change edits this one class.
  • OCP violated. A new pen type is an edit, not an extension.
  • Null checks everywhere. Fountain pens have no refill; ball pens have no direct ink.
  • Object creation is fragile. Caller has to know which fields apply to which type.

Evolution 2 — subclass per pen type

Pull the type-specific bits into subclasses. Abstract Pen with abstract write(); GelPen / BallPen / FountainPen / ThrowawayPen each implement it.

Class diagram — flat inheritance

  • ✔ SRP / OCP fixed — each class owns one pen type.
  • ✔ No more null checks on irrelevant fields.
  • ✖ LSP broken. FountainPen.change_refill() doesn't exist (or raises) — you can't substitute a FountainPen wherever a Pen is expected.
  • ✖ Code duplication. GelPen and BallPen write() bodies are nearly identical.

Evolution 3 — add Strategy for write() behaviour

Some pens write the same way (smoothly, roughly, etc.). Pull writing behaviour out into a WritingStrategy — same shape as our LLD-19 Strategy.

Class diagram — Strategy injected into Pen

✔ Code duplication gone — GelPen and BallPen now just hand their constructor a strategy. ✖ LSP still broken on change_refill().

Evolution 4 — abstract intermediates for refillable vs not

Split the hierarchy at the right axis: refillable vs non-refillable. RefillablePen abstract owns change_refill(); NonRefillablePen doesn't have it at all.

Class diagram — two-layer hierarchy

✔ LSP fixed — the only places change_refill() exists are pens that actually have one. ✖ You still pay an inheritance tax: behaviour is welded to position in the tree. Adding "rechargeable battery-powered pen" would mean another intermediate.

Evolution 5 — Protocols for capabilities, flat hierarchy

Drop the abstract intermediates. Keep Pen flat. Express "can be refilled" as a Protocol (structural typing); each pen that has a refill simply has the right methods, and mypy enforces the contract at the call site.

from typing import Protocol

class RefillablePen(Protocol):
    def change_refill(self, refill: Refill) -> None: ...
    def is_refillable(self) -> bool: ...

class Pen(ABC):
    def __init__(self, brand, name, price, strategy: WritingStrategy):
        self._strategy = strategy
    def write(self): self._strategy.write()

class GelPen(Pen):                    # implicitly satisfies RefillablePen
    def __init__(self, brand, name, price, refill):
        super().__init__(brand, name, price, SmoothWriting())
        self._refill = refill
    def change_refill(self, refill): self._refill = refill
    def is_refillable(self): return True

class FountainPen(Pen):                # does NOT satisfy RefillablePen
    def __init__(self, brand, name, price, ink, nib):
        super().__init__(brand, name, price, SmoothWriting())
        self._ink, self._nib = ink, nib

# Callers that need refilling demand the protocol:
def refill_in_bulk(pens: list[RefillablePen], new_refill: Refill) -> None:
    for p in pens: p.change_refill(new_refill)

# mypy ERRORS at call site if you pass a FountainPen here. Runtime is fine too.

✔ Flat hierarchy, no LSP issue, capability is a Protocol not a class. ✖ Each refillable pen still repeats the _refill field — structural typing's tax. Trade against E4: less inheritance, more duplication.

Pen Quiz 2 — In E2 (subclass per type), why is calling change_refill() on a FountainPen an LSP violation?

D is right. Liskov's Substitution Principle says any place that takes the base type must work with any subclass. If callers can call change_refill() on a Pen, then every Pen subclass must support it. FountainPen either raises (caller crashes) or no-ops silently (caller confused) — either way, substitutability is broken. E4 fixes this by giving change_refill() only to a RefillablePen intermediate. E5 fixes it by making "refillable" a Protocol — callers ask for that capability explicitly.

Pen Quiz 3 — The interviewer says "we'll definitely add 5 more pen types over the next year." Which evolution do you head for?

C is right. Frequent new types → you'll repeatedly add classes. Protocols + Strategy mean each new pen type is one new class that picks its writing strategy and (if relevant) implements the RefillablePen protocol — zero edits to existing code. E1 turns each new type into an enum edit + an if branch (OCP violation grows). E2 forces inheritance shapes that may not fit (battery-powered? smart pen with bluetooth?). D abandons the question.

Patterns most likely to appear

Cheat-sheet Quiz 1 — "Design a notification system: email, SMS, push." Which pattern is the FIRST you reach for?

D is right. Three swappable channels with the same interface — classic Strategy. Builder is for many-arg construction (not the shape here). Singleton is process-wide state. Decorator wraps to ADD behaviour (e.g. "retry + log" around the channel) but the channel itself is the Strategy.

Cheat-sheet Quiz 2 — "Design an Order — placed → paid → shipped → delivered." Pattern?

B is right. The object's behaviour changes with its lifecycle state (you can't ship before paid). State pattern: each state is a class, transitions are explicit. Strategy swaps an algorithm under your control; State swaps based on internal lifecycle. Observer would fit if you're notifying "shipped" to listeners, but it's not the core modelling pattern here.

Cheat-sheet Quiz 3 — "Order placed → warehouse reserves stock + email confirmation sent + analytics logged." Pattern?

C is right. One event, three independent reactions. Observer. If "email needs the warehouse's tracking number" then it becomes Chain of Responsibility (LLD-20 recap). State is wrong because there's no lifecycle change in Order driving this. Factory is wrong because no creation is involved.

Cheat-sheet Quiz 4 — "HTTP request with 12 optional headers and 6 optional query params." Pattern?

A is right. Builder — many optional construction args, fluent chaining, no telescoping constructors. Decorator wraps to add behaviour (not construction). Factory chooses a TYPE (not a configuration). State is about lifecycle.
