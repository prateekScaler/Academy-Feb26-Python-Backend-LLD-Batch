BookMyShow — Code (Part 2)

LLD-27 • the promise from LLD-26, delivered

We designed this in LLD-26 and left one promise: “there are several ways to keep two users off the same seat — we'll compare them and build the best.” Today we keep it. We build the model (ShowSeat, the HOLD → pay → CONFIRM flow), make “claim a seat” atomic with a per-show lock, and prove the winner: the same race double-books under a naive locker and books exactly once under the lock.

Step 5 — the flow & APIs

HOLD → pay → CONFIRM

The clock (now) is injected on the state-changing calls, so the TTL, the cutoff, and the race are all testable without sleeping. hold() returns a transient Hold receipt — not stored; the truth is each ShowSeat's status.

CallReturns / raisesWhy

Why a hold at all? Without it, a user picks seats, opens their wallet… and someone else books them mid-payment. The hold is a short, exclusive promise: the seats go LOCKED for a few minutes. No new entity — just a status.

The REST API — the LLD-26 homework, answered

Turn each use-case oval into an endpoint. Conventions: resources are nouns, the method is the verb, GET never mutates, the server owns the clock, and every contract violation maps to one status code. A hold is its own resource (it has an id + expires_at).

A quiz on each tricky call — pick the status code:

POST /shows/{id}/holds — two users hold the same seat at once. The loser gets?

B — 409 Conflict. The request was valid but clashes with the current state (the seat just went LOCKED/BOOKED). Maps to SeatUnavailableError. ✗ 404 implies the seat doesn't exist; ✗ 500 is our bug, not the user's; ✗ 200-both is the double-book we're preventing.

POST /holds/{id}/payment — the user pays, but the hold's 5 minutes already lapsed. Status?

C — 410 Gone. The hold existed but its seats were released; the resource is intentionally no longer available. Maps to HoldExpiredError. ✗ 404 implies it never existed; ✗ 200-anyway risks a double-book on seats someone else may now hold.

POST /tickets/{id}/cancel — the user cancels 30 minutes before showtime (cutoff is 1 hour). Status?

A — 409 (or 422 Unprocessable). The cancel conflicts with a business rule on the booking's lifecycle (the cutoff). Maps to CutoffPassedError. ✗ 403 is about permission, not timing; ✗ 200 breaks the rule; ✗ 404 implies no such ticket.

Why is holding seats a POST /shows/{id}/holds and not a PATCH /seats/{id}?

B. The hold is a thing with its own lifecycle (created, has a TTL, becomes a booking or expires) — so you POST to create it and get back a /holds/{id} you can then pay or read. PATCHing the seat would hide that lifecycle and give you nowhere to attach the expires_at or the owner.
Step 6 — the headline (the LLD-26 promise)

Compare the approaches, build the winner

The invariant: a show-seat is BOOKED by at most one user. There are several ways to guarantee it — we make each a pluggable SeatLocker and run the same race under all of them:

Each approach end to end — what happens in your code, in the database, and (the part that's easy to forget) on the screen the user is staring at. Click each to expand.

1 · No lock (the bug)

▼
if seat.status == AVAILABLE:   # check
    seat.status = LOCKED       # ...act — a gap sits between the two steps
🗃️ In the DB / store: two INSERTs for the same seat both succeed (no constraint, no lock).
🖥️ On the UI (what the user sees): both users see “Booking confirmed!” — then one later gets an apologetic refund email. The UI lied.
✅ Best for: never — this is the bug we're fixing.

2 · In-process lock (threading.Lock)

▼
with show.lock:                 # one mutex per show
    if seat.status == AVAILABLE:
        seat.status = LOCKED
🗃️ In the DB / store: n/a — the lock lives in the app process, not the DB.
🖥️ On the UI (what the user sees): a brief spinner (“Reserving…”) while it waits for the lock, then “Booked!” or an honest “Seats just taken.”
✅ Best for: a single process / one server, in-memory.

3 · Pessimistic row lock (SELECT … FOR UPDATE)

▼
BEGIN;
SELECT status FROM show_seat
  WHERE id = :id FOR UPDATE;   -- locks the row; others WAIT here
UPDATE show_seat SET status = 'BOOKED' WHERE id = :id;
COMMIT;                         -- released; next in queue proceeds
🗃️ In the DB / store: the row is locked until COMMIT; others queue and proceed one at a time.
🖥️ On the UI (what the user sees): same spinner-then-result; under load on a hot seat it lasts longer (requests queue).
✅ Best for: one DB, many app servers; correctness over raw speed.

4 · Optimistic concurrency (version / CAS)

▼
-- (1) read the seat AND its current version
SELECT status, version FROM show_seat WHERE id = 42;
--      both T1 and T2 see:  AVAILABLE, version = 7

-- (2) book ONLY if the version is still what you read (compare-and-set):
UPDATE show_seat
   SET status = 'BOOKED', version = 8
 WHERE id = 42 AND version = 7;

Worked example — the same seat, two users:

T1 runs (2) first  →  1 row updated  → BOOKED ✓   (version is now 8)
T2 runs (2) next   →  0 rows updated  → the row's version is 8, not 7
                                       → T2 LOST the race → show “seat just taken” / retry

No lock was ever held — the WHERE version = 7 is the whole trick: only one UPDATE can match, so only one user wins. The loser sees 0 rows and knows to back off.

🗃️ In the DB / store: no lock held; the conditional UPDATE is the only atomic moment.
🖥️ On the UI (what the user sees): feels instant — optimistically marks the seat selected, then rolls back if the CAS fails (“just taken, try another”).
✅ Best for: low contention — speed and no waiting.

5 · DB UNIQUE constraint

▼
-- once:  ALTER TABLE booking ADD UNIQUE(show_id, seat_id);
INSERT INTO booking(show_id, seat_id, user_id)
  VALUES (:s, :n, :u);          -- the 2nd insert -> IntegrityError
🗃️ In the DB / store: the constraint makes a 2nd booking of the same seat physically impossible.
🖥️ On the UI (what the user sees): whatever the UI optimistically showed, the failed insert surfaces as “Seat taken.” The safety net.
✅ Best for: always on — the correctness floor (pair it with one of the above for UX).

6 · Distributed (Redis) lock

▼
SET lock:{show}:{seat} {token} NX EX 30   # atomic set-if-absent + TTL
  # OK  -> book it
  # nil -> someone else holds it, bail
🗃️ In the DB / store: the lock lives in Redis, shared across all servers; the TTL frees a crashed holder.
🖥️ On the UI (what the user sees): same spinner-then-result — but works even with no shared database (microservices).
✅ Best for: many services with no shared DB row to lock.

7 · 🔒 Soft lock / hold — reserve-then-pay (what BookMyShow ships)

▼
Different kind of thing. 1–6 settle the instant clash; this is the 5-minute reservation that holds your seats while you pay — layered on top of one of the locks above.
# acquire the hold UNDER a lock from 2-6:
seat.status       = LOCKED
seat.locked_until = now + 300       # a 5-minute TTL
seat.held_by      = user
# on pay     -> seat.status = BOOKED
# on timeout -> seat.status = AVAILABLE  (lazy / sweep)
🗃️ In the DB / store: a locked_until column, or — more often — a Redis key with a TTL (SET … EX 300) so an abandoned cart frees itself.
🖥️ On the UI (what the user sees): the iconic BookMyShow countdown — “reserved for you · 4:59 left”, and others watch the seats grey out in real time. (Try the visualizer's “Soft lock & expiry” panel.)
✅ Best for: the real product — time to pay without overselling. Not a race-fixer; pair it with a lock (2–6) + the UNIQUE floor.
✖ NaiveLocker — check-then-act 
# both threads, seat A3
if seat is AVAILABLE:   # both read AVAILABLE
    seat = LOCKED       # both write LOCKED
# -> 2 tickets for one seat (double-book)
✔ PerShowLock — check-and-set 
with self.locker.guard(show):   # per-show mutex
    if any seat != AVAILABLE:
        raise SeatUnavailableError
    set them LOCKED
# -> exactly 1 ticket
The demo proves it. The same race (two threads, one seat, a forced interleave) runs under both lockers: NaiveLocker → 2 tickets (the bug), PerShowLock → 1 ticket. It's a SeatLocker strategy, so swapping the approach is one argument.

👁️ The atomic step — the actual hold()

▼
def hold(self, show, seat_ids, user, now):
    with self.locker.guard(show):              # the atomic boundary (swappable)
        self._free_expired(show, now)         # lazy TTL sweep, under the guard
        taken = [s for s in seat_ids
                 if show.show_seat(s).status is not AVAILABLE]
        if taken:
            raise SeatUnavailableError(taken)   # the lost race
        for s in seat_ids:                     # set LOCKED + locked_until = now + TTL
            ss = show.show_seat(s); ss.status = LOCKED; ss.held_by = user.user_id
        return Hold(show, tuple(seat_ids), user.user_id, now + HOLD_TTL)

You're on many app servers sharing one Postgres. Cheapest correct way to stop a double-book?

B. A per-process threading.Lock guards only one server — two servers still race (✗ A). The DB is the one thing they share, and a UNIQUE constraint makes a second booking physically impossible with zero extra moving parts. Add SELECT … FOR UPDATE or an optimistic update for a friendlier error. ✗ D serialises the planet; ✗ C isn't a strategy.

The verdict. In-memory → the per-show lock (simple; different shows never contend). Distributed → a UNIQUE(show_id, seat_id) constraint as the floor (can't be raced), an optimistic update for throughput, and a Redis lock + TTL when there's no shared DB. Granularity: per-show is the sweet spot — global serialises everything, per-seat risks deadlock on multi-seat holds. Design in-memory first; name the distributed mapping out loud.

Deep dive

Optimistic vs Pessimistic — the intuition

Two of the approaches sound technical but the idea is everyday. The whole difference is one question: do you lock before you start, or do you just check at the end?

🔒 Pessimistic — “lock the door first”

You assume a clash will happen, so you grab an exclusive lock up front and hold it while you work. Everyone else waits in line.

Like: the single bathroom key — you take it, lock the door, and nobody else can get in until you come out.

In code: SELECT … FOR UPDATE, a mutex. You pay the cost as waiting.

🎯 Optimistic — “act first, check at checkout”

You assume clashes are rare, so you don't lock — you do your work on a snapshot and, only at the moment of saving, check “did anything change since I started?” If yes, you redo.

Like: editing a Google Doc / a wiki — you type freely, and only on Save does it say “someone else edited this, try again.”

In code: a version column + compare-and-set. You pay the cost as occasional wasted work.

🔒 Pessimistic🎯 Optimistic

Others meanwhilewait their turnrun freely (in parallel)
On a conflictcan't happen — you held the lockdetected at save → retry or abort

When to use which — one rule. Ask: how often do two people actually collide?
• Often (the one hot seat everyone wants on a blockbuster release) → pessimistic. Optimistic would have everyone do the work and then all-but-one throw it away — a retry storm.
• Rarely (updating your profile, a seldom-touched row) → optimistic. No lock overhead, no waiting, and the once-in-a-blue-moon retry is cheap.
For BookMyShow's hot seats: a short pessimistic row lock (or a brief Redis lock) on top of the UNIQUE floor. For everything cold: optimistic.

You update a user's profile bio — collisions almost never happen. Which fits best?

A. Conflicts are rare, so don't make everyone wait for a lock — let writes run free and just check a version at save; the rare clash retries cheaply. A row lock (B) adds waiting you almost never need; a table lock (C) serialises unrelated users; no protection (D) risks a lost update.

Pre-read — check yourself

Transactions — DDIA, Chapter 7

You were asked to read Designing Data-Intensive Applications, Ch. 7 (“Transactions”). It's the theory under everything in this class — the seat race is literally its write-skew example. Start with the one almost everyone gets wrong — is “atomicity” the same as “concurrency-safe”? — then eleven in all to check it landed.

The anomalies, visually — two transactions, one bad interleave

Every anomaly is the same shape: T1 and T2 run at once, and one slips into a gap in the other. Time flows down; blue = a read, amber = a write, red = where it breaks.

…and the isolation ladder — each higher level closes one more anomaly (the price is less concurrency):

✅ prevented · ❌ still possible. The seat race lives in the last column — only Serializable (or an explicit lock / UNIQUE constraint) closes it.

Atomicity and Isolation are both ACID letters — which statement is correct?

B. The classic mix-up. Atomicity has NOTHING to do with concurrency — DDIA says it's really about abortability: if a transaction fails partway, everything it did is undone. Isolation is the concurrency one (our seat race). A transaction can be perfectly atomic and still race another — see the next two questions.

A transaction inserts 3 rows, then the process crashes before commit. Atomicity guarantees…

B. All-or-nothing on failure — DDIA argues atomicity is better named abortability: a crash/abort discards every partial write. (Note: this says nothing about other concurrent transactions — that's isolation.)

Two money transfers each run atomically, at the same time, and the final balances come out wrong. Which ACID property was violated?

C. Both transactions were fully atomic (neither was half-done) — yet the wrong answer came from them racing. That's an isolation failure (a lost update / write skew), not atomicity. The takeaway: atomic ≠ concurrency-safe — exactly the BookMyShow seat problem.

The I in ACID (“Isolation”) actually promises…

B. Isolation = concurrency safety: the result is as if transactions ran serially. (Encryption is unrelated; durability is the D.) In practice databases offer weaker isolation than true serial, which is what Ch.7 is all about.

A dirty read is…

B. You see a value another transaction wrote but hasn't committed — and it may roll back. Read Committed prevents dirty reads (and dirty writes).

Read Committed stops dirty reads/writes — but a transaction reading the same row twice can still see different values. That's…

C. Between your two reads, another committed transaction changed the row — read skew. The fix is snapshot isolation (a.k.a. repeatable read): each transaction sees one consistent snapshot.

Two transactions both read a counter = 10, each add 1, each write 11. The final value is 11, not 12. This bug is…

A — a lost update. The classic read-modify-write race. Fixes: an atomic operation (UPDATE … SET n = n + 1), an explicit lock (SELECT … FOR UPDATE — pessimistic), or a compare-and-set on a version (optimistic).

Two users book the same seat at once; each checks “is it free?”, sees yes, and books. DDIA calls this…

B — write skew (via a phantom). Each transaction's decision depends on rows the other is about to change; the “is it free?” check is a phantom. (Same shape as DDIA's two-doctors-on-call and meeting-room examples.) This is exactly our seat invariant.

DDIA lists three ways to implement serializability. Which trio?

A. Actual serial execution (single-threaded, e.g. Redis/VoltDB), 2PL (pessimistic — acquire locks, can be slow under contention), and SSI (optimistic — run freely, abort on a detected conflict). Note the mapping: 2PL ≈ pessimistic, SSI ≈ optimistic — the very trade-off from the section above.
The through-line: weaker isolation is faster but leaks anomalies — dirty reads, read skew, lost updates, and finally write skew / phantoms (our seat race). Serializable closes them, implemented as serial execution, 2PL (pessimistic), or SSI (optimistic) — the same two strategies you just compared.

Step 7 — Trade-offs

Say these out loud

🔒
Lock granularity

Per-show is the sweet spot. Per-seat is finer but multi-seat holds risk deadlock; global kills concurrency.

⏳
Lazy expiry vs sweep

Lazy frees on access (simple). A background sweep frees seats even when no one's looking — better for the next buyer.

🌏
In-memory vs distributed

The per-show lock is the teaching default; production leans on the UNIQUE floor + optimistic updates + a Redis lock.

🪑
ShowSeat rows: when?

Pre-generate every ShowSeat at show creation (simple reads, more rows) vs on first touch (lean, more logic).
