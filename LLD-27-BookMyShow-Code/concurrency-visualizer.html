🔒 Soft lock & expiry — the hold

A different idea from the race: a soft (advisory) lock — the seat is held LOCKED with a countdown. Pay before it runs out → BOOKED; let it expire → it frees itself and someone else can grab it. This is the hold in the real engine (ShowSeat.status == LOCKED + locked_until).

🔌 How each approach is really implemented on the backend

This page fakes the locks with JavaScript so you can watch them. On a real backend, here's the actual thing each one maps to.

2 · In-process lock — single server, in-memory

# one mutex per show, inside the app process
with show.lock:                 # threading.Lock()
    if seat.status == AVAILABLE:
        seat.status = BOOKED
# ⚠ guards THIS process only — two servers still race

3 · Pessimistic row lock — one DB, many app servers

BEGIN;
SELECT status FROM show_seat
  WHERE show_id=:s AND seat_id=:n
  FOR UPDATE;                  -- locks the row; others WAIT here
-- (status == 'AVAILABLE'?)
UPDATE show_seat SET status='BOOKED'
  WHERE show_id=:s AND seat_id=:n;
COMMIT;                        -- lock released; next in queue proceeds

4 · Optimistic concurrency — no lock; conflicts rare

-- read first, remember the version:
SELECT status, version FROM show_seat WHERE ...;   -- version = 7
-- ...do the slow work UNLOCKED, then commit conditionally:
UPDATE show_seat
   SET status='BOOKED', version = version + 1
 WHERE show_id=:s AND seat_id=:n
   AND version = 7;            -- 0 rows updated => you lost, retry

5 · DB UNIQUE constraint — the correctness floor, always on

-- once, at schema time:
ALTER TABLE booking
  ADD CONSTRAINT uq UNIQUE (show_id, seat_id);
-- per booking — the DB itself refuses the duplicate:
INSERT INTO booking(show_id, seat_id, user_id)
  VALUES (:s, :n, :u);         -- 2nd insert -> IntegrityError

6 · Distributed (Redis) lock — many services, no shared DB

# acquire atomically: set-if-absent + a 5-min TTL
SET lock:{show}:{seat} {token} NX EX 300
   -> OK     # you hold it — go book
   -> (nil)  # someone else holds it — bail out
# release after confirm (or just let the TTL expire)
DEL lock:{show}:{seat}

🔒 The hold — what BookMyShow actually ships

# the LOCKED status IS the hold — usually Redis-backed
HSET show:{show}:seat:{seat} status LOCKED held_by {user}
EXPIRE show:{show}:seat:{seat} 300   # auto-free after 5 min
# paid in time -> status BOOKED + a row in `ticket`
# else        -> the key expires, the seat frees itself
In production you stack them: a UNIQUE(show_id, seat_id) constraint as the non-negotiable floor, a short pessimistic row lock (or Redis lock) on hot seats for a clean "seat taken", and the hold (LOCKED + TTL) for the reserve-then-pay UX. Optimistic is reserved for the cold rows where clashes are rare.
