Concurrency = interleaving on fewer cores. Parallelism = truly simultaneous on multiple cores.

What does this code print?

import threading

def greet(name, times):
    for _ in range(times):
        print(f"Hello {name}!")

t = threading.Thread(target=greet, args=("Rahul", 3))
t.start()
t.join()
args passes arguments to the function as a tuple. Here's how the syntax maps:

threading.Thread(target=greet, args=("Rahul", 3))
                   ↓            ↓    ↓
               which function    name  times

The thread calls greet("Rahul", 3). For a single arg, use trailing comma: args=("Rahul",)
Finishing Last Class

The GIL — What We Didn't Finish

Two experiments. One surprise.

Experiment 1: CPU-bound — sum of squares

00_gil_cpu.py — run this!
▼
import time, threading

def sum_squares(n):
    return sum(i * i for i in range(n))

N = 20_000_000

start = time.time()
for _ in range(4): sum_squares(N)
print(f"Sequential: {time.time()-start:.2f}s")

start = time.time()
threads = [threading.Thread(target=sum_squares, args=(N,)) for _ in range(4)]
[t.start() for t in threads]
[t.join() for t in threads]
print(f"Threaded:   {time.time()-start:.2f}s")

Which is faster for this CPU-heavy task?

GIL = Global Interpreter Lock. A mutex in CPython. Only ONE thread executes Python at any instant.

Experiment 2: I/O-bound — API calls

00_gil_io.py — run this!
▼
import time, threading

def call_api(name):
    time.sleep(1)  # Simulate network wait

start = time.time()
for _ in range(4): call_api("api")
print(f"Sequential: {time.time()-start:.1f}s")

start = time.time()
threads = [threading.Thread(target=call_api, args=("api",)) for _ in range(4)]
[t.start() for t in threads]
[t.join() for t in threads]
print(f"Threaded:   {time.time()-start:.1f}s")

Same question — which is faster for I/O (waiting)?

CPU-bound: GIL hurts. I/O-bound: GIL doesn't matter. This is the most important thing to know about Python concurrency.
CPU-bound (GIL held — threads take turns every ~5ms):
Thread 1: ██████░░░░░░██████░░░░░░    No speedup
Thread 2: ░░░░░░██████░░░░░░██████

I/O-bound (GIL RELEASED during wait):
Thread 1: ██░░░░░░░░░░░░░░██████        Big speedup!
Thread 2: ░░██████████████░░░░░░

Which statement is FALSE?

Python threads ARE real 1:1 OS threads. The OS sees and schedules them. GIL just prevents more than one from running Python bytecode simultaneously.

🔎 Deep Dive: Are Python threads real OS threads? How does GIL actually block them?

▼

Two kinds of threads exist

OS Threads (Kernel)
Created by OS kernel. Real. Heavy (1-8MB stack each).
Java, Python, C++ use these.
Green Threads (User-space)
Created by language runtime. OS doesn't know they exist. Lightweight.
Go's goroutines use these.

Java: 1:1, truly parallel

Thread t1 → OS Thread 1 → Core 1  (running)
Thread t2 → OS Thread 2 → Core 2  (running)
Thread t3 → OS Thread 3 → Core 3  (running)
OS sees all 3. Truly parallel. No lock.

Python: 1:1 OS threads, but GIL on top

┌─── GIL (one mutex) ──────────────────┐
│ Only 1 thread runs Python at a time  │
└──────────────────────────────────────┘
Thread t1 → OS Thread 1 → Core 1  (has GIL → running)
Thread t2 → OS Thread 2 → Core 2  (waiting for GIL → IDLE)
Thread t3 → OS Thread 3 → Core 3  (waiting for GIL → IDLE)

OS gave t2 a core. But t2 spins on GIL. Wasted.

Python threads are REAL OS threads. You pay full cost. But get NONE of the CPU parallelism. This is why multiprocessing exists and Python 3.13+ experiments with "no-GIL."

• GIL = Global Interpreter Lock, a mutex in CPython
• Only one thread executes Python bytecode at any instant
• Python threads are real 1:1 OS threads, but GIL serializes CPU-bound work
• I/O operations release the GIL — threading works for I/O-bound tasks
• For CPU-bound parallelism → multiprocessing (each process has own GIL)

The Solution

Thread Pools & ThreadPoolExecutor

You have 10,000 I/O tasks. How many threads should you create?

You write this to fetch 100 URLs:

too_many_threads.py
▼
import threading, time

def fetch(url):
    time.sleep(1)

urls = [f"https://api.example.com/{i}" for i in range(100)]

# Create 1 thread per URL
threads = [threading.Thread(target=fetch, args=(u,)) for u in urls]
[t.start() for t in threads]
[t.join() for t in threads]

# 100 threads for 100 URLs. Works.
# Now imagine 10,000 URLs...

This works for 100 URLs. Would you do the same for 10,000 URLs?

But how do 50 threads handle 10,000 tasks? They take turns — finish one, grab the next from the queue. That's a thread pool.
Task Queue:  [task1] [task2] [task3] [task4] [task5] [task6] [task7]
                ↓        ↓        ↓
Pool:     [Worker 1] [Worker 2] [Worker 3]
           does t1     does t2    does t3
           done →      done →     done →
           picks t4    picks t5   picks t6
           done →      done →     done →
           picks t7    (idle)     (idle)
3 workers handled 7 tasks. Workers are REUSED.

What we're about to learn

1. executor.submit(func, *args) — submit one task, get a Future back
2. future.done() — is it ready yet?
3. future.result() — give me the answer (blocks until ready)
4. as_completed(futures) — process results as they finish

The with Statement — Auto Cleanup

Remember with open("file") as f: from exception handling? Same pattern here. The with block automatically waits for all tasks and cleans up threads:

threadpool_basics.py
▼
from concurrent.futures import ThreadPoolExecutor
import time

def fetch_url(url):
    time.sleep(1)
    return f"{url}: 200 OK"

# with = context manager = auto cleanup (like with open("file"))
with ThreadPoolExecutor(max_workers=5) as executor:
    future = executor.submit(fetch_url, "https://api.example.com")
    print(future.result())  # blocks until done

# Without "with": you must call executor.shutdown() manually
# to wait for tasks and release threads. "with" does it for free.

What Python pattern is with ThreadPoolExecutor() as executor: using? Where have you seen it before?

Without with, you'd need executor = ThreadPoolExecutor(5) then executor.shutdown() in a finally block. with handles it.

• Thread Pool = fixed set of reusable worker threads picking tasks from a queue
• ThreadPoolExecutor(max_workers=N) from concurrent.futures
• Use with statement for auto cleanup (context manager pattern)

Key Concept

Futures & submit()

Submit a task, get a receipt. Check later if it's done.

🍴 The Restaurant Receipt

Order food → get a receipt. Food isn't ready, but the receipt is a promise.
future = executor.submit(cook, "biryani") — get a receipt
future.done() — "Is my order ready?"
future.result() — "Give me my food" (waits until ready)

submit_demo.py
▼
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def fetch(url, delay):
    time.sleep(delay)
    return f"{url} ({delay}s)"

with ThreadPoolExecutor(max_workers=5) as executor:
    # submit() returns a Future immediately
    futures = {
        executor.submit(fetch, "Razorpay", 3): "Razorpay",
        executor.submit(fetch, "Email", 1): "Email",
        executor.submit(fetch, "SMS", 0.5): "SMS",
    }

    # as_completed: results in COMPLETION order (fastest first)
    for future in as_completed(futures):
        print(future.result())
    # SMS (0.5s) → Email (1s) → Razorpay (3s)

🔎 Deep Dive: executor.map() — simpler alternative to submit()

▼ 
# map() = same function applied to many inputs, results in SUBMISSION order
urls = [f"https://api.example.com/{i}" for i in range(10)]

with ThreadPoolExecutor(max_workers=5) as executor:
    results = executor.map(fetch_url, urls)  # ordered results

for r in results:
    print(r)

map() = simple, ordered. submit() + as_completed() = flexible, fastest-first.
Use map() when: same function, many inputs, order matters.
Use submit() when: need per-task control or fastest-first results.

• Future = placeholder for a pending result from submit()
• .result() blocks until done. .done() checks without blocking.
• as_completed(futures) yields in completion order (fastest first)
• Exceptions captured by Future, re-raised on .result() — use try/except

CPU-Bound

ProcessPoolExecutor

What happens when ThreadPoolExecutor meets CPU-bound work?

threadpool_cpu_fail.py
▼
from concurrent.futures import ThreadPoolExecutor
import time

def heavy_math(n):
    return sum(i*i for i in range(n))

start = time.time()
results = [heavy_math(5_000_000) for _ in range(8)]
print(f"Sequential:    {time.time()-start:.2f}s")

start = time.time()
with ThreadPoolExecutor(max_workers=4) as ex:
    list(ex.map(heavy_math, [5_000_000]*8))
print(f"ThreadPool:    {time.time()-start:.2f}s  — same or SLOWER!")

ThreadPool didn't help for CPU work (GIL). We know processes bypass GIL. But is creating thousands of processes for thousands of tasks a good idea?

Same API, swap one word:
ProcessPoolExecutor — click to reveal
▼
from concurrent.futures import ProcessPoolExecutor

start = time.time()
with ProcessPoolExecutor(max_workers=4) as ex:
    list(ex.map(heavy_math, [5_000_000]*8))
print(f"ProcessPool:   {time.time()-start:.2f}s  — actually faster!")

Workers vs Threads vs Processes

"Worker" is a generic term — it's a unit that picks tasks from the queue.
In ThreadPoolExecutor, each worker IS a thread.
In ProcessPoolExecutor, each worker IS a process.
The pool manages them. You just submit tasks.

• ProcessPoolExecutor = same API as ThreadPoolExecutor, uses processes
• Bypasses GIL — true CPU parallelism
• Rule: I/O-bound → ThreadPool. CPU-bound → ProcessPool.
• Data is pickled when sent to workers — slight overhead

Tuning

How Many Workers?

More workers ≠ more speed. There's a ceiling.

Amdahl's Law — The Theoretical Limit

Speedup = 1 / (S + P/N)
S = sequential fraction. P = parallel fraction. N = workers.

If 10% sequential → max speedup = 10x (even with ∞ cores).
If 50% sequential → max speedup = 2x. The sequential part is the ceiling.

Real Algorithm

Parallel Merge Sort

First, a quick refresher on merge sort. Then: can we speed it up with concurrency?

Merge Sort — divide and conquer:

        [38, 27, 43, 3, 9, 82, 10]
               /              \
      [38, 27, 43, 3]    [9, 82, 10]
        /        \          /      \
   [38, 27]  [43, 3]   [9, 82]  [10]
    /   \     /   \     /   \      |
  [38] [27] [43]  [3] [9]  [82] [10]
    \   /     \   /     \   /      |
   [27, 38]  [3, 43]   [9, 82]  [10]
        \        /          \      /
      [3, 27, 38, 43]    [9, 10, 82]
               \              /
        [3, 9, 10, 27, 38, 43, 82]

Split → sort halves independently → merge back
The "sort halves" step is INDEPENDENT — perfect for parallelism!

Merge sort splits data into independent halves. Is this CPU-bound or I/O-bound? Should we use ThreadPool or ProcessPool?

Sorting = comparing and swapping = pure CPU work. ThreadPool gives no speedup. ProcessPool sorts chunks on separate cores.
parallel_mergesort.py — run this!
▼
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor
import time, random

def merge_sort(arr):
    if len(arr) <= 1: return arr
    mid = len(arr) // 2
    return merge(merge_sort(arr[:mid]), merge_sort(arr[mid:]))

def merge(left, right):
    result, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]: result.append(left[i]); i += 1
        else: result.append(right[j]); j += 1
    return result + left[i:] + right[j:]

data = [random.randint(0, 1_000_000) for _ in range(500_000)]
chunks = [data[i::4] for i in range(4)]

start = time.time()
[merge_sort(c) for c in chunks]
print(f"Sequential:  {time.time()-start:.2f}s")

start = time.time()
with ThreadPoolExecutor(4) as ex: list(ex.map(merge_sort, chunks))
print(f"ThreadPool:  {time.time()-start:.2f}s  (GIL!)")

start = time.time()
with ProcessPoolExecutor(4) as ex: list(ex.map(merge_sort, chunks))
print(f"ProcessPool: {time.time()-start:.2f}s  (faster!)")

Amdahl's Law here

Sort step = parallelizable. Merge step = sequential. If sorting is 90% of time, max speedup = 1/(0.1 + 0.9/4) = 3.1x with 4 workers. Not 4x — the merge is the bottleneck.
