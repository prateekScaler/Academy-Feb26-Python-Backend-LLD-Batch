step 0 · the why

Why tests exist — a story you already know

In LLD-29 you fixed the penny problem: split money in integer paise so ₹100 / 3 sums back to exactly ₹100. Now fast-forward three months…

A teammate is cleaning up the codebase. Your divmod paise logic looks “overly clever”, so they simplify it to round(total / n, 2). Nothing crashes. Every screen renders. The PR looks tidy and gets merged.

₹100.00 split three ways is now ₹33.33 + ₹33.33 + ₹33.33 = ₹99.99. One paisa evaporates from every odd split, thousands of times a day. Finance notices in week three.

🔒 What a test changes

  • One test — assert sum(shares) == total — and that PR goes red in seconds, on the teammate’s laptop, before review.
  • That’s the real job of a suite: regression protection. Not proving today’s code works — keeping tomorrow’s refactors honest.
  • The same bug gets more expensive the later it’s caught: seconds in the editor → minutes in CI → hours in review → weeks + trust in production.
  • Tests are also your safety net for refactoring — the LLD skills you built (extract a Strategy, split a God class) are only safe to apply when a suite guards the behaviour.
“Legacy code is simply code without tests.” — Michael Feathers, Working Effectively with Legacy Code. Untested code isn’t “code that happens to work” — it’s code nobody dares to change.

📁 Run the story yourself: code/01_the_bug_a_test_catches.py — watch the paisa vanish, then watch the test catch it.

step 1 · the map

The testing pyramid

Three kinds of tests, three altitudes. Know which one you’re writing.

  • Unit — one function or class, everything in memory, milliseconds each. Most of your tests live here. Today’s class.
  • Integration — several pieces wired together: the DRF endpoint → service → real (test) DB. Slower, fewer. Next class.
  • E2E — the whole deployed system through a real client. Priceless and painful: keep only a handful.

“POST /expenses authenticates the caller, validates the body, splits the amount and persists rows.” Which kind of test checks that?

The sentence names collaboration: auth → validation → split → persistence. That’s an integration test (endpoint through to DB). The unit test on SplitStrategy is also essential — but it can’t see auth or persistence; and an E2E for every endpoint behaviour is too slow and flaky to run on each commit.
step 2 · the tool

pytest in ten minutes

Python’s de-facto test runner. No classes, no boilerplate — files, functions and plain assert.

🔍 Discovery — how pytest finds your tests

  • Files named test_*.py (or *_test.py) are collected automatically.
  • Inside them, every function named test_* becomes a test.
  • No registration, no base classes — naming is the wiring.
# test_split.py
from splitwise.strategies import split_equal_paise

def test_split_conserves_total():
    assert sum(split_equal_paise(10_000, 3)) == 10_000
💬 What it does: A complete test file. pytest finds the file by its test_ prefix, runs every test_* function, and a bare assert is the whole checking API.

🏃 Running it

pytest                 # run everything discoverable from here
pytest -v              # one line per test, with names
pytest -k "split"      # only tests whose name contains "split"
pytest -x              # stop at the first failure
pytest --lf            # re-run only what failed last time
💬 What it does: The four flags you’ll actually use daily: -v to read names, -k to focus, -x to stop early while debugging, --lf to iterate on failures.

🔬 Failure output — assert introspection

    def test_split_conserves_total():
>       assert sum(split_equal_paise(10_000, 3)) == 10_000
E       assert 9999 == 10000
💬 What it does: When a plain assert fails, pytest rewrites it to show the actual values on both sides — here you instantly see a paisa went missing. No assertEqual boilerplate needed.
💡 unittest vs pytest: Python ships unittest (classes, self.assertEqual, JUnit heritage). It works — but pytest runs unittest suites too, and the industry default for new Python code is pytest: less ceremony, better failure output, fixtures and parametrize.
step 3 · the craft

Anatomy of a good test

Any test can pass. A good test tells you exactly what broke, the moment it breaks.

🏗️ AAA — every test is three paragraphs

def test_payer_is_owed_the_others_shares():
    # Arrange — set the world up
    group = ExpenseGroup(["asha", "bala", "chen"])

    # Act — the ONE thing this test is about
    group.add_expense("asha", 30_000)          # asha pays ₹300

    # Assert — the ONE outcome you care about
    assert group.balance["asha"] == 20_000     # owed the other two shares
💬 What it does: Arrange builds the scenario, Act performs exactly one behaviour, Assert checks exactly one outcome. Anyone can read this top-to-bottom like a sentence: given three friends, when asha pays ₹300, she is owed ₹200.

🔖 Three rules that keep suites livable

  • The name states the behaviour. test_full_lot_returns_none_not_an_exception failing in CI tells you what broke without opening the file. test_park_2 tells you nothing.
  • One behaviour per test. Three asserts about one outcome — fine. Three behaviours stacked in one test — the first failure hides the other two.
  • Test behaviour, not implementation. Assert what the code promises (balances sum to zero), not how it does it (which private method got called) — or every refactor breaks green tests.

⚡ FIRST — the checklist

⚡
Fast
Milliseconds each. A slow suite stops being run — and an unrun suite protects nothing.
🪨
Independent
No test depends on another’s leftovers. Any order, any subset, same result.
🔁
Repeatable
Same result on your laptop, CI, and a plane. No real network, no real clock, no luck.
✅
Self-validating
Pass or fail, by itself. If a human must eyeball printed output, it’s not a test.
⌚️
Timely
Written with the code (or before it — TDD), not as a someday chore.

A suite passes when run in file order but test_refund fails when run alone. Which FIRST property is broken — and by what?

Order-dependence is the classic Independence failure: some earlier test Arranged the world (a module-level object, a row, a global) and test_refund free-rides on it. Fix: every test builds its own world — which is exactly what fixtures are for (next section).
step 4 · edge cases

parametrize — one test, a table of cases

Copy-pasting a test six times with different numbers is a smell. Turn the test into a table.

@pytest.mark.parametrize("total, n", [
    (10_000, 3),      # the classic ₹100 / 3
    (10_000, 1),      # n = 1 — one person pays everything
    (0,      4),      # zero rupees — all shares zero
    (1,      3),      # 1 paisa among 3 — someone pays it
    (9_999,  2),      # odd remainder
    (7,      7),      # total == n — everyone pays exactly 1
    (6,      7),      # total < n — some pay 1, some pay 0
])
def test_split_conserves_total_for_every_boundary(total, n):
    assert sum(split_equal_paise(total, n)) == total
💬 What it does: One test function, seven independent runs — pytest reports each row separately (test_split[...10000-3] etc.), so a failure names its exact case. Adding a regression case later = adding one line to the table.

🧭 Where do the rows come from? Boundaries.

  • For every numeric input ask: 0 · 1 · typical · the value where behaviour changes · the extreme.
  • For a split: remainder 0, remainder 1, remainder n−1, n = 1, total = 0, total < n.
  • For the LLD-23 winner check: all 8 lines (3 rows, 3 columns, 2 diagonals) plus the no-winner cases — a draw and an empty board (false positives are bugs too).

You’re testing cancel_ticket(hours_before_show): full refund > 24h, half refund 2–24h, none < 2h. Which set of test values earns its keep?

Bugs live at the boundaries — the ≥ vs > at exactly 24 and exactly 2. Values deep inside a band (100, 50, 10) all pass even when the boundary operator is wrong; testing all 49 integers is 43 redundant rows that blur the table’s intent. Edges + one representative per band is the craft.
step 5 · reuse the arrange

Fixtures — Arrange once, reuse everywhere

Every test in the last section began by building the same group. Extract the shared Arrange.

@pytest.fixture
def empty_lot():
    return ParkingLot(spots=2)          # a FRESH lot per test

@pytest.fixture
def audit_log():
    log = []
    yield log                           # ← the test runs here
    log.clear()                         # teardown — even if the test failed

def test_parking_assigns_the_first_free_spot(empty_lot):
    ticket = empty_lot.park("KA-01-AA-1111")
    assert ticket.spot == 0
💬 What it does: Declare setup once with @pytest.fixture; a test asks for it by parameter name and pytest injects a fresh copy. yield-style fixtures run their cleanup after the test — pass or fail — so no leftovers leak into the next test (that’s Independence, mechanised). Shared fixtures move to a conftest.py file, visible to the whole folder.
  • Fresh per test by default — two tests asking for empty_lot get two different lots.
  • Fixtures compose — full_lot can build on the same lot class, pre-filled; tests pick the world they need.
  • Dependency injection again! The same idea as injecting a Strategy or a Clock — the test declares what it needs, the framework provides it.

Two tests both ask for the empty_lot fixture. Test A parks a car. What does test B see?

By default a fixture runs once per test that requests it — A and B each get their own lot, so A’s parking can’t leak into B (Independence). Sharing is possible when you opt in (scope="module" for an expensive resource like a DB connection) — a deliberate trade-off, next class.
step 6 · sad paths

Testing errors — and the float trap

Happy paths are half the job. The sad paths are where production incidents live.

💥 When code should raise

def test_overdraw_raises_insufficient_funds():
    wallet = Wallet(balance_paise=500_00)

    with pytest.raises(InsufficientFunds) as excinfo:
        wallet.withdraw(600_00)

    assert excinfo.value.needed == 600_00      # the error carries info
    assert wallet.balance == 500_00            # and nothing half-applied
💬 What it does: pytest.raises asserts the block raises exactly that exception — the test fails if no error (or the wrong error) comes out. Then assert on excinfo.value: a good error object carries data, and a failed operation must leave state untouched.
⚖️ The LLD-24 line, now in tests: a rule violation (overdraw) raises — test it with pytest.raises. An expected outcome (the lot is full) returns a value — test it with a plain assert: assert full_lot.park("KA-01…") is None. If you find yourself raising for answers the caller asked about, the design is wrong — not the test.

🎲 Floats lie

assert 0.1 + 0.2 != 0.3                    # True. really.
assert 0.1 + 0.2 == 0.30000000000000004    # what IEEE-754 actually stores

# floats you can't avoid (rates, averages) → compare with a tolerance
assert average_rating == pytest.approx(4.2)

# money → don't approximate. don't float. INTEGER PAISE.
assert sum([3334, 3333, 3333]) == 10_000   # exact, always
💬 What it does: Binary floating point cannot represent 0.1 exactly — so equality on computed floats is a coin toss. pytest.approx compares within a tolerance for genuinely-continuous values. But money is not continuous: keep it in integer paise (the LLD-29 rule) and equality becomes exact again — no epsilon needed.

Your test does assert total_price == 129.99 and fails with 129.99000000000001 != 129.99. The best fix is…

approx and round both make the test pass while the code keeps accumulating float error — the next penny loss ships anyway. The root fix is the LLD-29 one: money lives in integer paise, arithmetic is exact, and the assert needs no tolerance at all. (approx is right for genuinely continuous values — averages, rates — not for money.)
step 7 · the flaky enemy

Testing time — inject the clock

A test that calls datetime.now() gives a different answer every run. Sound familiar? It’s the LLD-30 lesson wearing a testing hat.

class Clock:                                  # production
    def now(self): return datetime.now(timezone.utc)

class FakeClock:                              # tests
    def __init__(self, t): self.t = t
    def now(self): return self.t
    def advance(self, **kw): self.t += timedelta(**kw)

def test_reminder_fires_at_the_boundary():
    reminder = Reminder(MEETING_10AM, minutes_before=15)
    clock = FakeClock(utc(2026, 7, 6, 9, 45))      # freeze 9:45

    assert reminder.is_due(clock)                  # ≥ boundary fires

def test_advancing_the_clock_is_time_travel():
    clock = FakeClock(utc(2026, 7, 6, 9, 0))
    assert not reminder_at_945.is_due(clock)
    clock.advance(minutes=45)                      # no sleep(2700)!
    assert reminder_at_945.is_due(clock)
💬 What it does: Code depends on a clock object, never on datetime.now() directly. Production passes the real Clock; tests pass a FakeClock frozen at any instant — so you can test “9:45 on a Monday” at 2am on a Saturday, and advance() replaces sleeping. This is the same dependency-injection move as Strategy and fixtures.
  • Boundaries again: freeze the clock exactly at the fire time — is ≥ vs > right?
  • Same trick for randomness: inject random.Random(seed) — seeded “random” is deterministic, so the test is Repeatable.
  • Never time.sleep() in a test — it’s slow and still flaky on a busy CI machine.

A token-expiry test passes locally but fails in CI at midnight UTC. The root cause is almost certainly…

Midnight-flaky = real-clock dependency: the test computed “today” at 23:59:59 and the code computed it at 00:00:00. Bigger leeways just hide it (and the cache stores which tests failed, not their results). The fix is structural: inject a FakeClock, freeze the boundary, and the test passes at any hour on any machine.
step 8 · the new paradigm

Beyond asserts — when there is no right answer

Everything today assumed one deterministic answer. Now let your backend call an LLM: “summarize this support ticket.” Run it twice — two different, both perfectly fine, summaries. What exactly do you assert?

  • Equality is dead here. There is no single expected string to == against — and there never will be.
  • So the assert evolves into a grade: score the output against a rubric (did it keep the order id? the amount? under 25 words?), require score ≥ threshold.
  • And one run proves nothing: the model is stochastic — run it N times and assert the pass rate: pass_rate ≥ 0.8. One sloppy output doesn’t fail the build; a degraded model does.
  • This discipline is called evals — and it is to LLM-powered backends exactly what this class’s tests are to deterministic ones.
def grade(summary: str) -> float:            # the rubric — not an equality
    facts = sum(f in summary.lower() for f in ["4521", "1499", "refund"]) / 3
    return facts * (1.0 if len(summary.split()) <= 25 else 0.5)

def test_summarizer_pass_rate_is_at_least_80_percent():
    scores = [grade(summarize(TICKET, seed)) for seed in range(20)]
    pass_rate = sum(s >= 0.7 for s in scores) / len(scores)

    assert pass_rate >= 0.80                 # a STATISTICAL assert
💬 What it does: Same AAA skeleton you learned today — but the Assert is statistical: grade 20 sampled outputs against the rubric, then threshold the rate. Notice the grader itself gets ordinary unit tests (pin it on a known-good and a known-bad output) — your deterministic testing skills don’t retire, they supervise the new layer.
Classic test (today)Eval (the new paradigm)
Outputdeterministic — one right answerstochastic — a distribution of acceptable answers
Checkassert actual == expectedgrade(actual) ≥ threshold — rubric / checklist / LLM-as-judge
Verdictone run decidespass rate over N runs decides
Regressiongolden valuesa golden set of inputs + minimum scores, tracked over time

Your team adds “AI reply suggestions” to the support app. How should CI check the feature?

Two layers, two tools. The deterministic plumbing (prompt building, parsing, fallbacks) gets ordinary unit tests with the LLM mocked — fast and stable, next class’s topic. The model’s quality gets an eval: graded samples, thresholded pass rate, tracked on a golden set. Exact-string asserts break on every model update even when quality is fine; humans-only doesn’t scale and drifts.
