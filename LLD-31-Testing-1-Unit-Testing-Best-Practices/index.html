step 0 · the why

Why tests exist — the bug nobody notices

The worst bugs don’t crash. They return a slightly wrong answer, quietly, thousands of times a day. Two stories — one famous, one painfully ordinary.

📈 Knight Capital, 2012. A deploy goes out to 7 of 8 servers; on the 8th, an old feature flag silently re-activates dead code. No crash, no alert — just wrong orders streaming into the market. In 45 minutes the firm loses $440 million and effectively ceases to exist. No test guarded the behaviour that flag switched on.
🍴 Closer to home: the coupon bug. Your food-delivery checkout applies a 10% offer and a ₹50 coupon. The business rule: percentage on the subtotal first, then the flat coupon — a ₹500 order costs 500 × 0.9 − 50 = ₹400.

During a refactor someone reorders the two lines: (500 − 50) × 0.9 = ₹405. Nothing crashes. Every screen renders. The PR looks tidy and gets merged — and every discounted order overcharges by ₹5, thousands of times a day, until support tickets pile up in week three.

🔒 What a test changes

  • One test — assert checkout_total(500_00, pct=10, coupon=50_00) == 400_00 — and that refactor goes red in seconds, on the author’s laptop, before review.
  • That’s the real job of a suite: regression protection. Not proving today’s code works — keeping tomorrow’s refactors honest.
  • The same bug gets more expensive the later it’s caught: seconds in the editor → minutes in CI → hours in review → weeks + trust in production.
  • Tests are also your safety net for refactoring — the LLD skills you built (extract a Strategy, split a God class) are only safe to apply when a suite guards the behaviour.
“Legacy code is simply code without tests.” — Michael Feathers, Working Effectively with Legacy Code. Untested code isn’t “code that happens to work” — it’s code nobody dares to change.

📁 Run the story yourself: code/01_the_bug_a_test_catches.py — watch the coupon refactor overcharge, then watch one test catch it.

step 1 · the map

The testing pyramid

Three kinds of tests, three altitudes. Know which one you’re writing.

  • Unit — one function or class, everything in memory, milliseconds each. Most of your tests live here. Today’s class.
  • Integration — several pieces wired together: the DRF endpoint → service → real (test) DB. Slower, fewer. Next class.
  • E2E — the whole deployed system through a real client. Priceless and painful: keep only a handful.

“POST /expenses authenticates the caller, validates the body, splits the amount and persists rows.” Which kind of test checks that?

  • The sentence names collaboration: auth → validation → split → persistence.
  • That’s an integration test (endpoint through to DB).
  • The unit test on SplitStrategy is also essential — but it can’t see auth or persistence; and an E2E for every endpoint behaviour is too slow and flaky to run on each commit.
  • Tooling: in our Django world that’s pytest + DRF’s APIClient, with pytest-django spinning up a throwaway test database — next class’s toolkit.

“SplitStrategy.split(10_000, 3) returns shares that sum back to the total.” Which kind of test — and what tooling runs it?

One object, one promise, no collaborators — the definition of a unit test.
  • Why not integration: persistence adds nothing to this behaviour — it only slows the feedback loop from milliseconds to seconds.
  • Why not E2E: end-to-ending arithmetic is using a crane to lift a teaspoon.
  • Tooling: plain pytest — assert + parametrize, exactly what today’s class uses; everything in code/ runs at this layer.

“A user signs up on her phone, creates a group, adds an expense — and her friend’s app shows the updated balance.” Which kind of test, and what tooling?

The sentence spans two clients, the network, auth, and the real backend — that’s the whole system, so it’s E2E.
  • Tooling: Playwright or Selenium driving a real browser / device against a deployed environment.
  • Why only a handful: powerful but slow and flaky — run them nightly / pre-release, not on every commit.
  • Why not integration: DRF’s APIClient exercises one server process — no real phones, no network hops.
  • Why not unit: faked users test the math, not the journey.
🔨 The tooling, layer by layer:

🟩 Unit — one function / class, in memory (today)

▼
  • Tooling: pytest — one-time pip install pytest. (The built-in unittest needs no install — trade-offs in the next section.)
  • Who owns it: developers — written with the code.
  • When it runs: every save & every commit · milliseconds each.

🟦 Integration — endpoint → service → DB together (next class)

▼
  • Tooling: pytest + DRF’s APIClient + pytest-django (throwaway test DB).
  • Who owns it: developers.
  • When it runs: every push, in CI · seconds.

🟥 E2E — the whole deployed system, as a user

▼
  • Tooling: Playwright / Selenium driving a real browser or device.
  • Who owns it: developers + QA/SDET — QA typically owns & maintains the harness.
  • When it runs: nightly / pre-release · minutes — keep only a handful.

🧺 Manual & exploratory — what scripts can’t judge

▼
  • Tooling: a human, a checklist, and curiosity — UX, odd flows, “does this feel right?”
  • Who owns it: QA.
  • When it runs: before releases — and every finding becomes a new automated test.

Where QA fits: not as a safety net for unit tests developers skipped — the pyramid’s base belongs to the people writing the code. QA adds the layers automation can’t: exploratory judgment, and (as SDETs) owning the E2E harness. A bug QA finds that a unit test could have caught is a process smell, not a QA win.

step 2 · the tool

pytest in ten minutes

Python’s de-facto test runner. No classes, no boilerplate — files, functions and plain assert.

🔍 Discovery — how pytest finds your tests

  • Files named test_*.py (or *_test.py) are collected automatically.
  • Inside them, every function named test_* becomes a test.
  • No registration, no base classes — naming is the wiring.
# test_split.py
from splitwise.strategies import split_equal_paise

def test_split_conserves_total():
    assert sum(split_equal_paise(10_000, 3)) == 10_000
💬 What it does:
  • A complete test file.
  • pytest finds the file by its test_ prefix, runs every test_* function, and a bare assert is the whole checking API.

🏃 Running it

pip install pytest     # one-time install (it's a third-party tool)

pytest                 # run everything discoverable from here
pytest -v              # -v  = Verbose: one line per test, with names
pytest -k "split"      # -k  = Keyword: only tests whose name matches
pytest -x              # -x  = eXit on first failure
pytest --lf            # --lf = Last Failed: re-run only what failed
💬 What it does: The four flags you’ll actually use daily, and what the letters stand for:
  • -v = verbose (one named line per test)
  • -k = keyword (filter tests by a name expression, e.g. -k "split and not float")
  • -x = exit on first failure (stop early while debugging)
  • --lf = last failed (re-run only yesterday’s red tests).

🔬 Failure output — assert introspection

    def test_split_conserves_total():
>       assert sum(split_equal_paise(10_000, 3)) == 10_000
E       assert 9999 == 10000
💬 What it does:
  • When a plain assert fails, pytest rewrites it to show the actual values on both sides — here you instantly see a paisa went missing.
  • No assertEqual boilerplate needed.
💡 What about unittest, the built-in?
  • Zero install: unittest ships with Python — import unittest and go. pytest is one command away: pip install pytest.
  • So why isn’t it enough? unittest makes you write a class for every group of tests (class TestSplit(unittest.TestCase)) and memorise a family of assert methods (assertEqual, assertRaises, assertAlmostEqual…) — where pytest is plain functions and one bare assert with rich failure output.
  • And it lacks the power tools: no parametrize (its subTest is a clunkier cousin), no fixture injection by parameter name (only setUp/tearDown methods per class).
  • Best of both: pytest runs unittest suites unchanged — legacy tests keep working while everything new goes pytest-style. That’s why pytest is the industry default for new Python code.
step 3 · the craft

Anatomy of a good test

Any test can pass. A good test tells you exactly what broke, the moment it breaks.

🏗️ AAA — every test is three paragraphs

def test_payer_is_owed_the_others_shares():
    # Arrange — set the world up
    group = ExpenseGroup(["asha", "bala", "chen"])

    # Act — the ONE thing this test is about
    group.add_expense("asha", 30_000)          # asha pays ₹300

    # Assert — the ONE outcome you care about
    assert group.balance["asha"] == 20_000     # owed the other two shares
💬 What it does:
  • Arrange builds the scenario, Act performs exactly one behaviour, Assert checks exactly one outcome.
  • Anyone can read this top-to-bottom like a sentence: given three friends, when asha pays ₹300, she is owed ₹200.

🥇 Apply it — which structure is right?

A fresh scenario: you’ve written cancel_order() and now want a test around it. Three candidates — read them, then decide:

# the function you just wrote — now you want a test around it
def cancel_order(order):
    """Cancel an order: mark it CANCELLED, return the refund in paise.
    Shipped orders cannot be cancelled."""
    if order.status == "SHIPPED":
        raise CannotCancel("already shipped")
    order.status = "CANCELLED"
    return order.amount_paise

# ── candidate 1 ──
def test_cancel_order():
    order = Order(amount_paise=25_000, status="PENDING")
    assert cancel_order(order) == 25_000
    shipped = Order(amount_paise=10_000, status="SHIPPED")
    try:
        cancel_order(shipped); assert False
    except CannotCancel:
        pass

# ── candidate 2 ──
def test_cancelling_a_pending_order_refunds_the_full_amount():
    order = Order(amount_paise=25_000, status="PENDING")

    refund = cancel_order(order)

    assert refund == 25_000
    assert order.status == "CANCELLED"

# ── candidate 3 ──
def test_cancel():
    print(cancel_order(Order(amount_paise=25_000, status="PENDING")))

Which candidate is the correct way to test cancel_order()?

  • Candidate 2 is the one: the name states the behaviour, the body reads Arrange → Act → Assert, and both asserts check the same outcome (the cancellation) — if it fails, you know exactly what broke.
  • Candidate 1 stacks two behaviours (refund and the shipped rule): when the first assert fails, the second behaviour is never even checked — and its name tells you nothing. The try/except/assert False dance is hand-rolling what pytest.raises does properly (Step 6). Right move: a second AAA test — test_cancelling_a_shipped_order_raises.
  • Candidate 3 is not a test: no assert — it passes even when the refund is wrong. A human eyeballing printed output breaks Self-validating (the S in FIRST).
  • Coverage isn’t fewer tests doing more — it’s more small tests, each pinning one promise.

🔖 Three rules — discover them yourself

Three head-to-heads. Pick the better test in each — the rule reveals itself. Answer all three and the summary unlocks.

Both tests check the same thing. Which one do you want failing in CI at 2 AM?

📧 Rule 1 — the name states the behaviour.
  • A failing test_full_lot_returns_none_not_an_exception tells you what broke before you even open the file.
  • test_park_2 tells you nothing — you must read the body (and probably test_park_1 too) to understand the failure.
  • Write the name as the sentence you’d say to a teammate: given / when / then compressed into words.

Two suites for ExpenseGroup. Which is better?

✂️ Rule 2 — one behaviour per test.
  • When the combined test goes red, which of the three behaviours died? The name can’t say, and the first failing assert hides the other two.
  • Three small tests fail independently — the failure list itself is the diagnosis.
  • Multiple asserts are fine when they check one outcome (refund amount + status) — not three unrelated ones.

settle_up() should clear all debts. Which assert belongs in the test?

🎯 Rule 3 — test the behaviour, not the implementation.
  • The promise is “debts are cleared” — assert that. How the code gets there (caches, helper calls, private flags) is its own business.
  • Implementation asserts break on every refactor even when the behaviour is still correct — green-to-red with no bug is how teams learn to ignore their suite.
  • Rule of thumb: if renaming a private method fails your test, the test was looking at the wrong thing.
🔓 The three rules — in one breath:
  • Name = the behaviour.
  • One behaviour per test.
  • Test the promise, not the plumbing.

⚡ FIRST — earn the checklist

Five properties make a suite trustworthy. Five questions — a different flavour each. Answer all five and the checklist unlocks.

TRUE / FALSE  A thorough suite that takes 25 minutes protects you better than a quick 5-second one.

⚡ F — Fast.
  • A 25-minute suite stops being run locally — developers push and hope. The 5-second suite runs on every save.
  • An unrun suite protects nothing; speed is a correctness feature, not a luxury.
  • Unit tests should cost milliseconds each — in memory, no I/O (that’s what keeps them at the pyramid’s base).
cart = ShoppingCart()

def test_add_item():
    cart.add("chai", qty=2)
    assert cart.count == 2

def test_remove_item():
    cart.add("samosa", qty=1)
    cart.remove("samosa")
    assert cart.count == 2

CODE  test_remove_item passes when the whole file runs, but fails when run alone with -k remove. Why?

🪨 I — Independent.
  • Run together: chai (2) + samosa (1) − samosa = 2 → passes. Run alone: 1 − 1 = 0 → fails. The test’s answer depends on who ran before it.
  • The count isn’t “wrong” — it’s order-dependent, which is worse: it lies differently depending on how you run it. (And -k only filters by name; it skips nothing else.)
  • Fix: every test builds its own world — a fresh cart per test via a fixture (next section).
def test_coupon_is_valid():
    coupon = Coupon(expires=date(2026, 12, 31))
    assert coupon.is_valid(today=date.today())

CODE  This test is green today. When does it start failing — and why?

🔁 R — Repeatable.
  • date.today() smuggles the real world into the test: same code, different day, different result — the definition of unrepeatable.
  • One morning in 2027 the suite goes red with zero code changes — and the team’s first instinct will be to distrust the suite, not the test.
  • Fix: inject the date (is_valid(today=date(2026, 6, 1))) or a FakeClock — Step 7 does exactly this. Same rule for randomness and network.

PICK ONE  Three “tests” of settle_up(). Which one is actually a test?

✅ S — Self-validating.
  • A test must answer pass or fail by itself — the assert is the verdict.
  • Printed output needs a human every single run; the log-diff needs a QA ritual. Both “pass” forever in CI while the behaviour rots — nobody reads green noise.
  • If a human must look at something to know the result, it’s a demo, not a test.

SCENARIO  You just finished the refund feature; the sprint ends Friday and two more features are queued. When do the tests get written?

⌚️ T — Timely.
  • “Next sprint” tests are written by someone who’s forgotten the edge cases — or (usually) never written at all.
  • Tests written with the code are cheap: the scenarios, boundaries and gotchas are already loaded in your head. Waiting throws that context away.
  • And behaviour “that might change” is exactly what needs a safety net while it changes. (Write them before the code and you’ve discovered TDD.)

A suite passes when run in file order but test_refund fails when run alone. Which FIRST property is broken — and by what?

  • Order-dependence is the classic Independence failure: some earlier test Arranged the world (a module-level object, a row, a global) and test_refund free-rides on it.
  • Fix: every test builds its own world — which is exactly what fixtures are for (next section).
🔓 Unlocked — FIRST, in one breath:
  • Fast — milliseconds, or it stops being run.
  • Independent — any order, any subset, same result.
  • Repeatable — same verdict on any machine, any day.
  • Self-validating — the assert is the verdict.
  • Timely — written with the code, not someday.
step 4 · edge cases

parametrize — one test, a table of cases

Copy-pasting a test six times with different numbers is a smell. Turn the test into a table.

@pytest.mark.parametrize("total, n", [
    (10_000, 3),      # the classic ₹100 / 3
    (10_000, 1),      # n = 1 — one person pays everything
    (0,      4),      # zero rupees — all shares zero
    (1,      3),      # 1 paisa among 3 — someone pays it
    (9_999,  2),      # odd remainder
    (7,      7),      # total == n — everyone pays exactly 1
    (6,      7),      # total < n — some pay 1, some pay 0
])
def test_split_conserves_total_for_every_boundary(total, n):
    assert sum(split_equal_paise(total, n)) == total
💬 What it does:
  • One test function, seven independent runs — pytest reports each row separately (test_split[...10000-3] etc.), so a failure names its exact case.
  • Adding a regression case later = adding one line to the table.

🧭 Where do the rows come from? Boundaries.

  • For every numeric input ask: 0 · 1 · typical · the value where behaviour changes · the extreme.
  • For a split: remainder 0, remainder 1, remainder n−1, n = 1, total = 0, total < n.
  • For the LLD-23 winner check: all 8 lines (3 rows, 3 columns, 2 diagonals) plus the no-winner cases — a draw and an empty board (false positives are bugs too).

You’re testing cancel_ticket(hours_before_show): full refund > 24h, half refund 2–24h, none < 2h. Which set of test values earns its keep?

  • Bugs live exactly at the cutoffs — the ≥-vs-> decision at 24 and at 2. You need the cutoff itself and a neighbour on each side: 25 / 24 / 23 and 3 / 2 / 1.
  • First option’s trap: 0, 3, 23, 48 all sit safely inside bands — a wrong operator at either cutoff passes every one of those values. “Implied by the bands” is exactly how off-by-one refunds ship.
  • Second option’s trap: risk-weighting sounds mature, but it guards one boundary and abandons the other — the 2-hour edge decides whether customers get anything at all.
  • Values deep inside a band add rows, not information — edges + one representative per band is the whole craft.
step 5 · reuse the arrange

Fixtures — Arrange once, reuse everywhere

Every test in the last section began by building the same group. Extract the shared Arrange.

@pytest.fixture
def empty_lot():
    return ParkingLot(spots=2)             # a fresh lot for every test

@pytest.fixture
def full_lot():
    lot = ParkingLot(spots=2)              # fixtures compose:
    lot.park("KA-01-AA-1111")              # same lot, pre-filled
    lot.park("KA-01-BB-2222")
    return lot

def test_parking_assigns_the_first_free_spot(empty_lot):
    ticket = empty_lot.park("KA-01-AA-1111")
    assert ticket.spot == 0

def test_full_lot_returns_none(full_lot):
    assert full_lot.park("KA-01-CC-3333") is None
💬 What it does:
    • Declare the setup once with @pytest.fixture.
    • A test asks for it by parameter name — pytest sees empty_lot in the signature and injects a fresh one.
    • full_lot shows fixtures compose: same lot, pre-filled — each test picks the world it needs.
    • Fixtures shared across files live in conftest.py, visible to the whole folder.
  • Fresh per test by default — two tests asking for empty_lot get two different lots.
  • Fixtures compose — full_lot can build on the same lot class, pre-filled; tests pick the world they need.
  • Dependency injection again! The same idea as injecting a Strategy or a Clock — the test declares what it needs, the framework provides it.

Two tests both ask for the empty_lot fixture. Test A parks a car. What does test B see?

  • By default a fixture runs once per test that requests it — A and B each get their own lot, so A’s parking can’t leak into B (Independence).
  • Sharing is possible when you opt in (scope="module" for an expensive resource like a DB connection) — a deliberate trade-off, next class.
step 6 · sad paths

Testing errors — and the float trap

Happy paths are half the job. The sad paths are where production incidents live.

💥 When code should raise

def test_overdraw_raises_insufficient_funds():
    wallet = Wallet(balance_paise=500_00)

    with pytest.raises(InsufficientFunds) as excinfo:
        wallet.withdraw(600_00)

    assert excinfo.value.needed == 600_00      # the error carries info
    assert wallet.balance == 500_00            # and nothing half-applied
💬 What it does:
  • pytest.raises asserts the block raises exactly that exception — the test fails if no error (or the wrong error) comes out.
  • Then assert on excinfo.value: a good error object carries data, and a failed operation must leave state untouched.
⚖️ The LLD-24 line, now in tests: a rule violation (overdraw) raises — test it with pytest.raises. An expected outcome (the lot is full) returns a value — test it with a plain assert: assert full_lot.park("KA-01…") is None. If you find yourself raising for answers the caller asked about, the design is wrong — not the test.

🎲 Floats lie

assert 0.1 + 0.2 != 0.3                    # True. really.
assert 0.1 + 0.2 == 0.30000000000000004    # what IEEE-754 actually stores

# floats you can't avoid (rates, averages) → compare with a tolerance
assert average_rating == pytest.approx(4.2)

# money → don't approximate. don't float. INTEGER PAISE.
assert sum([3334, 3333, 3333]) == 10_000   # exact, always
💬 What it does:
  • Binary floating point cannot represent 0.1 exactly — so equality on computed floats is a coin toss.
  • pytest.approx compares within a tolerance for genuinely-continuous values.
  • But money is not continuous: keep it in integer paise (the LLD-29 rule) and equality becomes exact again — no epsilon needed.

Your test does assert total_price == 129.99 and fails with 129.99000000000001 != 129.99. The best fix is…

  • approx and round both make the test pass while the code keeps accumulating float error — the next penny loss ships anyway.
  • The root fix is the LLD-29 one: money lives in integer paise, arithmetic is exact, and the assert needs no tolerance at all. (approx is right for genuinely continuous values — averages, rates — not for money.)
step 7 · the flaky enemy

Testing time — inject the clock

A test that calls datetime.now() gives a different answer every run. Sound familiar? It’s the LLD-30 lesson wearing a testing hat.

class Clock:                                  # production
    def now(self): return datetime.now(timezone.utc)

class FakeClock:                              # tests
    def __init__(self, t): self.t = t
    def now(self): return self.t
    def advance(self, **kw): self.t += timedelta(**kw)

def test_reminder_fires_at_the_boundary():
    reminder = Reminder(MEETING_10AM, minutes_before=15)
    clock = FakeClock(utc(2026, 7, 6, 9, 45))      # freeze 9:45

    assert reminder.is_due(clock)                  # ≥ boundary fires

def test_advancing_the_clock_is_time_travel():
    clock = FakeClock(utc(2026, 7, 6, 9, 0))
    assert not reminder_at_945.is_due(clock)
    clock.advance(minutes=45)                      # no sleep(2700)!
    assert reminder_at_945.is_due(clock)
💬 What it does — piece by piece:
  • Clock is a one-method wrapper: now() returns the real current instant (aware UTC). This is the only place in the whole codebase that touches datetime.now().
  • FakeClock looks identical from the outside (same now() method) but returns whatever instant you constructed it with — frozen. Call it ten times, get the same answer ten times.
  • The trick that makes it work: reminder.is_due(clock) takes the clock as a parameter. The reminder never asks the OS what time it is — it asks whoever called it. Production passes Clock(); a test passes FakeClock(…). Neither the reminder nor the test can tell the difference.
  • First test, line by line: the reminder should fire 15 min before the 10:00 meeting → 9:45. The test freezes the clock at exactly 9:45 and asserts is_due — probing the ≥ boundary on purpose (would a > bug slip through? this test catches it).
  • Second test: start at 9:00 (not due), then advance(minutes=45) pushes the fake time to 9:45 (due). That one line replaces time.sleep(2700) — 45 minutes of waiting simulated instantly.
  • Why you care: you can now test “Monday 9:45” at 2 AM on a Saturday, in any timezone, a thousand times a second — deterministic, fast, no flakes. Same dependency-injection move as Strategy and fixtures.
  • Boundaries again: freeze the clock exactly at the fire time — is ≥ vs > right?
  • Same trick for randomness: inject random.Random(seed) — seeded “random” is deterministic, so the test is Repeatable.
  • Never time.sleep() in a test — it’s slow and still flaky on a busy CI machine.

A token-expiry test passes locally but fails in CI at midnight UTC. The root cause is almost certainly…

  • Midnight-flaky = real-clock dependency: the test computed “today” at 23:59:59 and the code computed it at 00:00:00.
  • Bigger leeways just hide it (and the cache stores which tests failed, not their results).
  • The fix is structural: inject a FakeClock, freeze the boundary, and the test passes at any hour on any machine.
step 8 · the new paradigm

Beyond asserts — when there is no right answer

Everything today assumed one deterministic answer. Now let your backend call an LLM: “summarize this support ticket.” Run it twice — two different, both perfectly fine, summaries. What exactly do you assert?

  • Equality is dead here. There is no single expected string to == against — and there never will be.
  • So the assert evolves into a grade: score the output against a rubric (did it keep the order id? the amount? under 25 words?), require score ≥ threshold.
  • And one run proves nothing: the model is stochastic — run it N times and assert the pass rate: pass_rate ≥ 0.8. One sloppy output doesn’t fail the build; a degraded model does.
  • This discipline is called evals — and it is to LLM-powered backends exactly what this class’s tests are to deterministic ones.
def grade(summary: str) -> float:            # the rubric — not an equality
    facts = sum(f in summary.lower() for f in ["4521", "1499", "refund"]) / 3
    return facts * (1.0 if len(summary.split()) <= 25 else 0.5)

def test_summarizer_pass_rate_is_at_least_80_percent():
    scores = [grade(summarize(TICKET, seed)) for seed in range(20)]
    pass_rate = sum(s >= 0.7 for s in scores) / len(scores)

    assert pass_rate >= 0.80                 # a STATISTICAL assert
💬 What it does:
  • Same AAA skeleton you learned today — but the Assert is statistical: grade 20 sampled outputs against the rubric, then threshold the rate.
  • Notice the grader itself gets ordinary unit tests (pin it on a known-good and a known-bad output) — your deterministic testing skills don’t retire, they supervise the new layer.

  • The deterministic plumbing (prompt building, parsing, fallbacks) gets ordinary unit tests with the LLM mocked — fast and stable, next class’s topic.
