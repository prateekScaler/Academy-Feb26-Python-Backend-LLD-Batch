Warm-up · recap from BookMyShow

Concurrency — concept check

Last class we cracked concurrency on BookMyShow. Before we design Splitwise, five questions to lock the core ideas in — kept general, not tied to any one system. Reason before you click.

1 · Two transactions both read a counter, add to it, and write it back. The final value reflects only one of the two additions. Which anomaly — and the fix?

Classic lost update: two read-modify-write cycles interleave so one increment is overwritten. Dirty read is reading uncommitted data; write skew is reading an overlapping set and writing disjoint rows. Cheapest fix: make the write atomic (x = x + n in the DB) or hold a lock across the read and the write.

How the race happens

Both transactions read the same value before either writes — so the second write is computed from a stale read and clobbers the first.

Five ways to fix it

1 · Atomic write
Do the math in the DB — no app-side read-modify-write, so there’s nothing to interleave. Best when the change is a delta.
# one statement, no read
UPDATE accounts
SET balance = balance + 50
WHERE id = 1;
2 · Pessimistic lock
Lock the row first, then read → modify → write inside the txn. Serialises writers — good under high contention.
BEGIN;
SELECT balance FROM accounts
  WHERE id=1 FOR UPDATE;
# read → add → write
COMMIT;
3 · Optimistic (version CAS)
No lock; guard the write with the version you read. 0 rows changed → someone won → retry. Good under low contention.
# read version v, then
UPDATE accounts SET balance=?,
  version=v+1
WHERE id=1 AND version=v;
4 · Serializable isolation
Let the DB detect the conflict and abort one transaction; you retry. Strongest and simplest to reason about — costs throughput.
SET TRANSACTION
  ISOLATION LEVEL SERIALIZABLE;
# DB aborts one on conflict
# → catch & retry
5 · App / distributed lock
A per-key lock around the critical section — for when the resource isn’t one DB row (spans rows / services).
# Redis: per-key lock
SET lock:acct:1 me NX PX 3000
# critical section, then
DEL lock:acct:1
When the change is a simple delta, the atomic write is the cleanest fix. When it isn’t (read → decide → write), reach for a lock (pessimistic, high contention) or a version check (optimistic, low contention). Serializable is the strongest and simplest to reason about, at a throughput cost. Q2 and Q3 below dig into when to pick which.

The anomaly zoo — one diagram each

Each is two transactions interleaving on shared data — read each top-to-bottom as time. The first three are the options above; the last two are the other classics you’ll meet in DDIA’s isolation chapter.

2 · A single row is updated by many concurrent transactions — conflicts are frequent. Which concurrency control performs better?

Rule of thumb: optimistic for low contention (cheap when you usually win), pessimistic for high contention (retry storms waste work when writers keep colliding). A perpetually-hot row is the high-contention case.

3 · Optimistic concurrency holds no lock while a transaction runs. How does it detect that another transaction changed the same row first?

Optimistic = compare-and-set on a version (or timestamp) column. No lock is held while you work; the conflict surfaces at write time as 0 rows affected, your cue to retry. A UNIQUE constraint only catches duplicate inserts, not a lost update on an existing row.

4 · Does optimistic concurrency always need a dedicated version column? If not, how else can the write tell the row changed since you read it?

The essence of optimistic CC is a compare-and-set: the UPDATE’s WHERE must fail if the row changed since you read it. A monotonic version is the cleanest, but matching on the old field values, an updated_at timestamp, or a row hash all give the same CAS. Version columns are preferred because they dodge the ABA problem (a value edited away and back looks unchanged) and don’t depend on clock resolution.

Setup — a 10-minute reservation

Reserve the seat, pay in another app, then confirm — or let it expire. The reservation must survive the user’s think-time without freezing the seat for everyone else.

5 · You’re booking a concert ticket. The app reserves your seat for 10 minutes while you pay in a separate UPI app. Two ways to build that reservation — (A) hold a DB lock on the seat row for the whole 10 minutes (i.e. keep one DB transaction open that entire time), or (B) a soft lock: set the seat’s status to HELD with an expires_at, in a quick transaction. Which, and why?

“Hold a lock for 10 minutes” — what does that even mean? A row lock isn’t a thing with its own timer. It exists only while a transaction is open, and it’s released when that transaction commits, rolls back, or its connection drops — not after some fixed time. So “hold a DB lock for 10 minutes” literally means “keep one database transaction (and its connection) open for 10 minutes” — that’s the resource you tie up (and many databases will actively kill such a long-idle transaction). The soft lock is the opposite: a quick transaction writes status = HELD + expires_at and commits immediately — nothing stays locked. After 10 minutes nothing “unlocks”; the hold is simply read as expired once now > expires_at.

The two-locks distinction. The hold is a business reservation measured in minutes (a status + expires_at); a DB lock held that long ties up a transaction and a connection across your think-time. You still need a short DB lock or version-CAS to flip the seat to HELD atomically — so two users can’t both grab it (that rules out option C) — but that’s a millisecond critical section, not a 10-minute one. Different jobs, different time-scales:
What does “status” mean? It’s the resource’s lifecycle state stored as a field on the row — e.g. a seat is AVAILABLE, then HELD while someone pays, then BOOKED. The hold is just “set status = HELD and remember expires_at”; releasing it is “set status back to AVAILABLE.” No locks needed for the wait — only a short one to flip the state safely.

The throughline: any shared mutable resource under concurrent writers needs a guard — a counter, a balance, a seat, an inventory row, all the same problem. Pick the guard by contention (optimistic vs pessimistic), keep business holds out of the DB transaction (a hold = status + TTL), and never trust a background sweep for correctness (expire lazily on read).

Step 4 · the open variable

The split strategies

The contract: split(amount, participants, args) → list[Split], where the splits sum to the total (FR-9). A new way to split is one new class — the engine never changes.

◠
EqualSplit
amount / n each. The penny problem: ₹100 / 3 = ₹33.33 × 3 = ₹99.99 — a paisa vanishes. FR-9 forces a deterministic rule for the leftover.
🧮
ExactSplit
The caller gives exact amounts; validate they sum to the total, else reject.
📊
PercentSplit
The caller gives percentages; validate they sum to 100, then amount × pct.

₹100 split equally 3 ways. amount / n gives ₹33.33 each — that’s ₹99.99. What does FR-9 force you to do?

FR-9 is exact: splits must sum to the total, no money created or lost. Compute the floor share, then distribute the remaining paisa deterministically (e.g. to the first k participants). Floats silently lose precision — use integer paise. This rounding nuance is exactly what interviewers probe.

This is the same “open variable → Strategy” move as Parking’s pricing and BookMyShow’s pricing — derived straight from FR-4. When a requirement says “one of these ways, and more later,” that’s a Strategy family, not an if/elif chain.

Step 5 · balances & settle-up

The balance graph & debt simplification

The invariant: across everyone, balances sum to zero — every rupee owed is owed to someone. The headline algorithm settles the whole group with the fewest payments.

Per-pair edges

{(debtor, creditor) → amount}. Keeps the detail (“why do I owe this?”), but grows with every expense.

Per-user net

Each user’s (owed to them − they owe). Loses the detail, but it’s exactly what you need to simplify.

Step 6 · trade-offs

Say these out loud

The senior signal isn’t the class diagram — it’s naming the tensions you chose between.

Edges vs net balances
Edges keep the audit trail (“why do I owe this?”); net is what you simplify. Real systems keep both — edges for history, net for settle-up.
The penny / rounding problem
Equal splits don’t divide evenly; FR-9 forces a deterministic rule for the leftover paisa. Use integer paise, never floats.
Simplify on write vs on demand
Simplify lazily — when someone hits “settle up” — not after every expense. Cheaper, and the detail stays available.
Concurrency (callback to BMS)
Two expenses added to the same group at once both read-modify-write the balance graph — the lost update again. Guard the group’s balance update (a per-group lock / a transaction), exactly like the seat race.
Extensions = one new class
Multi-currency, recurring expenses, multiple payers, a SharesSplit (2:1:1) — each is one new strategy or field, not an engine rewrite.
