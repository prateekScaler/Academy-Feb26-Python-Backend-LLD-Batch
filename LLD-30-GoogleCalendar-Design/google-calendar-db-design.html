Google Calendar — Database Design

A Minimal Modeling walk-through · logical model first, then SQL

Design first, model in your head, then write the tables. Requirements → anchors (nouns you can count) → attributes (as questions) → links (with cardinality sentences) → physical SQL.

📚 This page turns the excellent databasedesignbook.com Google Calendar tutorial into an interactive, bullet-by-bullet walk-through — every concept, in the same style as the LLD design page. Where that page asks “what classes?”, this one asks “what tables?” — a complementary data-modelling lens.
the method

Minimal Modeling — logical first, physical later

Map business requirements to a small logical model in plain sentences, before touching SQL. Only model what you actually need.

⚓
1 · Anchors
The nouns you can count — entities that get their own table. Validate with a sentence: “there are several X in our database”.
❓
2 · Attributes
Data on an anchor, written as a question: “What is the email of this User?” — plus an example value to confirm your thinking.
🔗
3 · Links
Relationships as two cardinality sentences, one each way: “User creates several DayEvents / a DayEvent is created by one User.”
💾
4 · Physical
Map the logical model to SQL: anchors→tables, attributes→columns, 1:N→foreign keys, M:N→junction tables.
Why questions & sentences? Short column names (end_date, is_skipped) can’t carry meaning by themselves. The logical layer keeps the semantics in human-readable form, and the two-way sentences catch modelling mistakes early: if a sentence doesn’t match reality, you just prevented a bug.

💡 The core principle — model only what you know you need

▼
  • Minimal Modeling deliberately resists adding abstractions for hypothetical futures.
  • Trade-off: too little → you may overfit to today’s known data; too much → friction from complexity that never pays off.
  • The cure for both is the same: write the requirement as a sentence and check it against reality.
the problem

What we’re modelling

A Google-Calendar clone — “every feature of calendaring, and just enough of the rest to discuss the interesting parts.”

📋 Four kinds of event

  • All-day events, non-repeating — e.g. a Company Retreat spanning Jan 14–15 (single or multi-day).
  • Timed events, non-repeating — a Catch-up meeting 12:30–13:15, with a time zone (can even cross zones, like a flight).
  • Repeating all-day events — daily / weekly / monthly / annually, with intervals and stop conditions.
  • Repeating timed events — same recurrence machinery, with times.

🎯 What each event must support

  • Attributes: title, description, location, begin/end date-time.
  • Recurrence: daily/weekly/monthly/annually, every N of those; weekly picks weekdays; monthly picks same date vs same weekday; stop forever / until a date / after N reps.
  • Instance overrides: move or skip a single occurrence; change its location, guests, attendance — without touching the series.
  • Pattern changes: edit the series even after some occurrences happened (“switch Tue+Thu weekly → every other Friday”).
  • Multi-user: events belong to a creating user (sharing is acknowledged but out of scope here).
Scope for this walk-through: we implement the calendaring core in full and keep users minimal. Sharing, attendees/RSVP, reminders, colours, locations, free/busy and full time-zone rules are left as extensions (see Gaps).
step 1

Basic all-day events

Start with the simplest slice: non-repeating, date-based events that can span multiple days.

⚓ Anchors & attributes

  • User — “What is the email of this User?” → email (string, e.g. cjdate@example.org).
  • DayEvent — “What is the name?” → name; “When does it begin/end?” → begin_date, end_date (dates).
  • Multi-day is the general case: a single-day event just has begin_date == end_date — one uniform shape.

🔗 Link

  • User : DayEvent = 1 : N — “a User creates several DayEvents / a DayEvent is created by exactly one User.” → FK day_events.user_id.

💾 Physical tables (preview)

▼
CREATE TABLE users (
  id    INTEGER NOT NULL PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(64) NOT NULL
);

CREATE TABLE day_events (
  id         INTEGER NOT NULL PRIMARY KEY AUTO_INCREMENT,
  user_id    INTEGER NOT NULL,
  name       VARCHAR(128) NOT NULL,
  begin_date DATE NOT NULL,
  end_date   DATE NOT NULL
);
step 2

Timed events & time zones

Add clock times — and the thorniest decision in the whole model: how to store a time.

You schedule a billiard game for 09:30 on 6 Sep 2058, Cologne time. How do you store it?

Store local time + zone. Time zones change — we don’t yet know 2058’s UTC offset for Cologne. Storing UTC now would bake in an offset that legislation may move; storing local time without the zone loses the information needed to render it. So keep the data exactly as the user entered it and apply the (possibly future) offset later. (Note: this is the opposite of the LLD page’s “store UTC” default — different lens, different trade-off; see the contrast at the end.)

⚓ Anchors & attributes

  • Timezone — name (e.g. Europe/Kyiv). Minimal on purpose: UTC offsets, DST rules, historical changes and retirement are acknowledged but not modelled here.
  • TimeEvent — name, begin_local_time, end_local_time (DATETIME, local).

🔗 Links — two time zones per event

  • User : TimeEvent = 1 : N → time_events.user_id.
  • Timezone : TimeEvent for the start = 1 : N → start_timezone_id.
  • Timezone : TimeEvent for the end = 1 : N → end_timezone_id.
  • Why two? A flight departs Amsterdam and lands in London — start and end can be in different zones. Most events share one; the two-zone design is the general case.

💾 Physical table

▼
CREATE TABLE timezones (
  id   INTEGER NOT NULL PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64) NOT NULL
);

CREATE TABLE time_events (
  id                INTEGER NOT NULL PRIMARY KEY AUTO_INCREMENT,
  user_id           INTEGER NOT NULL,
  start_timezone_id INTEGER NOT NULL,
  end_timezone_id   INTEGER NOT NULL,
  name              VARCHAR(128) NOT NULL,
  begin_local_time  DATETIME NOT NULL,
  end_local_time    DATETIME NOT NULL
);
step 3

Repeated events — recurrence

The rich part: frequencies, intervals, weekday sets, monthly modes and stop conditions — all on the event row, using tangled attributes.

🧵 Tangled attributes

  • A tangled attribute is only meaningful when another is set — signalled by phrasing the question with a condition: “For monthly events: which day of the month?”
  • Physically, tangled attributes are nullable columns; the application validates the combination.

📅 DayEvent gains these attributes

  • repeated — daily / weekly / monthly / annually (NULL = one-off).
  • repetition_step — every N (e.g. 2 = every other).
  • repeated_monthly_on — same_day vs same_weekday (only for monthly).
  • repeated_until — forever / until_date / N_repetitions.
  • repeated_until_date — the end date (only if until_date).
  • repeated_reps — the count (only if N_repetitions).

A weekly event repeats on Mon, Wed & Fri. How do you store the chosen weekdays?

M:N via a junction. DayOfTheWeek is a well-known anchor — a fixed 7-row set (“Mon”…“Sun”, string ids), like currencies or countries. Modelling it as a proper anchor keeps the logical model uniform and defers the storage choice; a JSON array hides a relationship at the logical level, and 7 booleans don’t generalise.

🌐 Well-known anchor: DayOfTheWeek

  • Fixed ids "Mon"…"Sun" — unusual string keys, no growth expected.
  • M:N: “a weekly DayEvent happens on several DaysOfTheWeek / a DayOfTheWeek holds several DayEvents.” → junction day_event_dows (and time_event_dows).

  PRIMARY KEY (day_event_id, day_of_week),
  KEY (day_of_week)
);
step 4

Rendering the calendar — slots

Querying raw recurrence rules to paint a week is painful. So materialise each occurrence as a slot.

🔍 The problem

  • To show “the week of Feb 26” from rules alone you must expand every recurrence, honour exceptions, and clip to the window — expensive and fiddly on every read.

⚓ DaySlot — one materialised occurrence

  • the_date — which day this slot happens (can differ from the series if it was moved).
  • is_skipped — yes/no; a cancelled single occurrence (TINYINT, default 0).
  • DayEvent : DaySlot = 1 : N → day_slots.day_event_id.

Why create a DaySlot even for a non-repeating event?

Uniform rendering. “Always create a slot” means the calendar view is a single query over day_slots — no conditional logic for repeating vs one-off. Per-instance moves/skips/locations/guests all hang off the slot too.

⚠️ Trade-off: infinite recurrences (the birthday problem)

▼
  • An annual birthday “forever” can’t materialise infinite slots.
  • Options: (a) a bounded window (e.g. 100 years), (b) generate on demand when a view is requested, (c) a hybrid — materialise a window, generate beyond. The tutorial leaves the choice open.
  • Date edge cases: Feb 29 birthdays and “the 31st” monthly need a rule (reject, adjust, or special-case).

➕ Per-instance extras (just add links)

  • Different location, guest list, or attendance for one occurrence → add more links from DaySlot to other anchors. The pattern scales without reshaping the core.
step 5

Time slots

The same slot pattern for timed events — carrying times and their zones.

  • TimeSlot — begin_local_time, end_local_time, is_skipped; created even for non-repeating TimeEvents (same uniformity).
  • TimeEvent : TimeSlot = 1 : N → time_slots.time_event_id.
  • Timezone : TimeSlot (start & end) = 1 : N each → start_timezone_id, end_timezone_id — a moved slot can even land on a different day, so it keeps its own times and zones.

💾 Physical: time_slots

▼
CREATE TABLE time_slots (
  id                INTEGER NOT NULL PRIMARY KEY AUTO_INCREMENT,
  time_event_id     INTEGER NOT NULL,
  begin_local_time  DATETIME NOT NULL,
  end_local_time    DATETIME NOT NULL,
  start_timezone_id INTEGER NOT NULL,
  end_timezone_id   INTEGER NOT NULL,
  is_skipped        TINYINT UNSIGNED NOT NULL DEFAULT 0
);

step 7

Physical design — the SQL

One clean strategy: one table per anchor (7 tables) + one table per M:N link (2 junctions) = 8–9 tables.

🔄 Conversion rules

  • Anchor → table (plural): User→users, DayEvent→day_events.
  • Attribute → column; logical type → physical type; tangled → NULL, required → NOT NULL.
  • 1:N → foreign-key column on the N-side (user_id, start_timezone_id).
  • M:N → junction table with a composite primary key on both ids.

📌 Indexing

  • Junctions carry a composite PK (both ids) + a secondary KEY (day_of_week) for reverse lookups.
  • “Obvious” indexes like day_events.user_id are deliberately deferred — what to index depends on how the app actually queries. (Recommended read: Use The Index, Luke.)
  • Skipped attributes (location, description, user name/password, attendees, RSVP, reminders, colour, free/busy) are left as exercises — add rows to the catalog and columns to the schema.
the interesting parts

Six design decisions & their trade-offs

Each is a fork with a clear reason — test yourself, then read the why.

Should DayEvent and TimeEvent be one unified entity or two?

Stay separate (for now). Logical modelling lets you defer the unify-or-not call until you’ve seen how alike the two really are. Premature unification bakes in assumptions; the model stays honest by waiting.

For a recurring series, when do you create the slot rows?

Materialise slots. It simplifies rendering to a single query; the cost is handling unbounded recurrences via a window or on-demand generation — a deliberate, contained trade-off.

repeated_until_date only matters when repeated_until='until_date'. Model it as…

Nullable + app validation. Minimal Modeling keeps tangled attributes as nullable columns rather than over-normalising into extra tables — simpler, at the price of application-level checks.

📑 The other three, in one line each

▼
  • Local time vs UTC → store local + zone (zones change; keep the user’s intent).
  • Weekdays: array vs junction → junction + well-known anchor (uniform logical model).
  • Indexing → composite PKs on junctions now; everything else deferred to real query patterns.
the method, distilled

Minimal Modeling principles

The reusable techniques behind the whole design.

⚓ Anchor test — can you count them?

▼
  • A real anchor passes a sentence: “there are several X” / “a new X is added when…”. If it fails, it’s an attribute, not an anchor.

❓ Attributes as questions

▼
  • Define each attribute as “What is the X of this Anchor?” with an example value — the question carries the meaning a short column name can’t.

🔗 Links as two cardinality sentences

▼
  • Every link gets one sentence each way with a cardinality word (one / several).
  • If a sentence doesn’t match reality, you’ve caught a design mistake.
  • Three shapes: 1:1 (rare), 1:N, M:N.

🧵 Tangled attributes

▼
  • Meaningful only under a condition; phrase the question with that condition; implement as a nullable column validated in code.

🌐 Well-known anchors

▼
  • Small, stable, fixed-value sets (currencies, countries, days). May use non-integer ids; storage (table vs constant) is a physical-layer choice.

⚖️ Logical vs physical separation

▼
  • Finish the logical model before SQL — it keeps semantics readable and lets the schema evolve smoothly.
honest scope

What’s intentionally not modelled

Minimal Modeling names its gaps rather than hiding them — each is an add-a-link/anchor exercise.

  • Sharing & permissions — multi-user sharing is acknowledged; only the creating user is stored.
  • Attendees / invitations / RSVP — would be an anchor + M:N link to events (with status).
  • Reminders / notifications — an extra anchor per event.
  • Event colour / calendar assignment, location, description — add columns / links.
  • Free/busy & conflict detection — not addressed.
  • Full time-zone rules — UTC offsets, DST start/end/offset, historical changes, retirement — a separate technical exercise.
  • Deeper per-instance exceptions — multiple attributes changing per occurrence.
The point isn’t that these don’t matter — it’s that you add them the same way: a new anchor, or a new link from an existing one, validated by a sentence.

Example data walk-throughs

Three concrete inserts, from the simplest event to a recurring one with an override.

1️⃣ Simple all-day event — “Company Retreat”, Jan 14–15

▼
INSERT INTO users (id, email) VALUES (3, 'alice@example.com');

INSERT INTO day_events (id, user_id, name, begin_date, end_date, repeated)
VALUES (20, 3, 'Company retreat', '2024-01-14', '2024-01-15', NULL);

INSERT INTO day_slots (id, day_event_id, the_date, is_skipped) VALUES
  (1, 20, '2024-01-14', 0),
  (2, 20, '2024-01-15', 0);

-- render a week: just query the slots
SELECT e.name, s.the_date
FROM day_events e JOIN day_slots s ON s.day_event_id = e.id
WHERE s.the_date BETWEEN '2024-01-14' AND '2024-01-20' AND e.user_id = 3;

2️⃣ Weekly meeting Mon/Wed/Fri — skip & move one instance

▼
INSERT INTO time_events (id, user_id, start_timezone_id, end_timezone_id,
       name, begin_local_time, end_local_time)
VALUES (1, 3, 1, 1, 'Project Status', '2024-02-12 14:00', '2024-02-12 15:00');

INSERT INTO time_event_dows (time_event_id, day_of_week)
VALUES (1,'Mon'), (1,'Wed'), (1,'Fri');

-- materialised occurrences (dates computed by app logic)
INSERT INTO time_slots (id, time_event_id, begin_local_time, end_local_time,
       start_timezone_id, end_timezone_id, is_skipped) VALUES
  (1, 1, '2024-02-12 14:00', '2024-02-12 15:00', 1,1, 0),
  (2, 1, '2024-02-14 14:00', '2024-02-14 15:00', 1,1, 0),
  (3, 1, '2024-02-16 14:00', '2024-02-16 15:00', 1,1, 0);

-- cancel Feb 14
UPDATE time_slots SET is_skipped = 1
WHERE time_event_id = 1 AND begin_local_time = '2024-02-14 14:00';

-- move Mar 1 to 16:00
UPDATE time_slots SET begin_local_time='2024-03-01 16:00', end_local_time='2024-03-01 17:00'
WHERE time_event_id = 1 AND begin_local_time = '2024-03-01 14:00';

▼

DB-design vs the LLD class-design page

Same problem, two complementary modelling lenses — worth holding both.

This page (DB / Minimal Modeling)The LLD page (OO class design)
UnitAnchor / table (nouns you can count)Class (nouns + behaviour)
Recurrencetangled columns on the event + materialised slotsan optional RecurrenceRule object, expanded on read
Timestore local + zone (future-proof against law changes)store UTC, render local (one instant)
OccurrencesDaySlot / TimeSlot rowscomputed from the rule (+ EXDATE/override)
WeekdaysM:N to a DayOfTheWeek anchorbyday field in the rule
Attendeesan exercise / extra linkan Attendee association class (RSVP on the join)
Neither is “more correct”. The DB lens optimises for storage & queries (materialise, index, normalise); the OO lens optimises for behaviour & change (strategies, services, expand-on-read). Strong engineers move between them fluently.
