Falsehoods About Time — True or False?

A quiz on the classic list · guess, then learn the gotcha & the fix

Most of what we “know” about time is wrong somewhere. Each statement below is either true or false — decide, tap, and read the plain-English explanation (with simple, annotated Python).

📚 The tricky statements are from Noah Sussman’s “Falsehoods programmers believe about time” (all of those are false) — mixed here with some genuinely true statements so you have to actually think.
the tl;dr

Five rules that dodge most of these

Internalise these and the rest mostly follow.

🌐
Store aware UTC
Keep instants as aware UTC (or epoch). Convert to a local zone only to display.
🕑
Monotonic for durations
Time elapsed with time.monotonic() — never wall-clock subtraction.
📅
Calendar math, not hour math
Add days / months with a date library; a “day” isn’t 24 hours.
📄
ISO-8601 to exchange
YYYY-MM-DD — unambiguous, sortable, locale-free.
🤖
Don’t trust the clock
Client clocks lie; use server time + a little skew leeway.
round 1

Days, weeks, months, years

The calendar is irregular — and the boundaries don’t line up.

💡 Quick reference — how to read datetime(...)

Python builds one exact moment as datetime(year, month, day, hour, minute, tzinfo=zone). Each number is a position:

  • 2024 → the year
  • 3 → the month — 1 = January … 12 = December, so 3 = March
  • 10 → the day of the month
  • 9 → the hour on a 24-hour clock — 9 = 9 AM, 20 = 8 PM
  • 0 → the minute
  • tzinfo= → the time zone — timezone.utc for UTC, or ZoneInfo("America/New_York") for a named zone that knows its own DST rules

So datetime(2024, 3, 10, 9, 0, tzinfo=ZoneInfo("America/New_York")) means 9:00 AM on 10 March 2024, New York time.

There are always 24 hours in a day.

❌ False. A normal day is 24 hours — but the day daylight-saving starts is only 23 hours, the day it ends is 25, and leap seconds occasionally add one. So “same time tomorrow” is +1 day, not +24 hours.
🛠️ Do this: add days to an aware datetime and let the library handle the wall clock.
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

t = datetime(2024, 3, 10, 9, 0, tzinfo=ZoneInfo("America/New_York"))  # 9 AM, DST morning
t + timedelta(hours=24)   # 2024-03-11 10:00  (an hour off!)
t + timedelta(days=1)     # 2024-03-11 09:00  (correct)
💬 What it does: Here datetime(2024, 3, 10, 9, 0, tzinfo=…) is 2024 = year, 3 = month (March), 10 = day, 9 = hour (9 AM), 0 = minute, and tzinfo = New York time (which has DST). Because that day is only 23 hours, adding hours=24 overshoots to 10 AM, while adding days=1 correctly stays at 9 AM.

A leap year has 366 days — and 2024 is a leap year.

✅ True. Years divisible by 4 are leap years (except centuries not divisible by 400, like 1900). 2024 qualifies, so February 2024 has 29 days and the year has 366.
import calendar
calendar.isleap(2024)   # True  -> 366 days
💬 What it does: calendar.isleap(year) answers “is this a leap year?” — True for 2024, so the year has 366 days.

Every month has either 30 or 31 days.

❌ False. February breaks the rule with 28 or 29 days, so “the end of the month” is never a fixed number.
🛠️ Do this: ask the calendar for the length.
import calendar
calendar.monthrange(2024, 2)[1]   # -> 29
💬 What it does: monthrange(year, month) returns a pair (first_weekday, day_count); the [1] picks the day count — 29 for February 2024.

February always has exactly 28 days.

❌ False. In a leap year it has 29 — the classic Feb-29 birthday and month-end-billing bug.
🛠️ Do this: never hard-code 28; compute it with calendar.monthrange (as above).

On the morning daylight saving begins, the local day is only 23 hours long.

✅ True. When clocks “spring forward” (e.g. 02:00 jumps straight to 03:00), one hour simply doesn’t exist that day, so it lasts 23 hours. In autumn the clock falls back and the day is 25 hours. This is exactly why “a day” is not “24 hours.”

Every year has exactly 365 days.

❌ False. Leap years have 366, so “one year from today” is not reliably +365 days (and a Feb-29 date won’t exist next year).
🛠️ Do this: use real date arithmetic and handle the Feb-29 rollover explicitly.

Any 24-hour period begins and ends on the same calendar day.

❌ False. A 24-hour span that starts in the evening ends the next day — and can just as easily cross a week or month boundary. So “the next 24 hours” is not the same as “today.”
🛠️ Do this: define a day by its date, build that day’s real start/end, and filter with a half-open range — instead of adding a fixed 24 hours to “now.”
from datetime import datetime, timedelta, date, time, timezone
from zoneinfo import ZoneInfo

tz = ZoneInfo("America/New_York")
# GOAL: list everything that happens on 31 Jan 2024 (New York time).

# WRONG -- "now .. now + 24h" is a moving window that spills into the next day:
now = datetime(2024, 1, 31, 20, 0, tzinfo=tz)   # 8 PM
now, now + timedelta(hours=24)                  # ...ends 8 PM on 1 Feb

# RIGHT -- anchor the day to its DATE, get its real bounds, convert to UTC:
def day_bounds_utc(d, tz):
    start = datetime.combine(d, time.min, tzinfo=tz)                      # 00:00 that day (local)
    end   = datetime.combine(d + timedelta(days=1), time.min, tzinfo=tz)  # 00:00 next day (local)
    return start.astimezone(timezone.utc), end.astimezone(timezone.utc)

start, end = day_bounds_utc(date(2024, 1, 31), tz)
# query UTC-stored events where:  start <= event.start < end   (half-open range)
# on a DST day this span really is 23h or 25h -- the UTC conversion captures that.
💬 What it does: What to do, in words: pick the day as a date, compute its real local start/end with datetime.combine(day, 00:00) (and the next day), then convert both to UTC and query events with the half-open range start <= t < end. Because the bounds are anchored to the date (not to “now + 24h”) they never leak into tomorrow, and they stay correct on DST days — there the real span is 23 or 25 hours, which the UTC conversion captures automatically. (Tip: converting to UTC also avoids Python’s “same-tzinfo” subtraction quirk, where local_end − local_start would wrongly report 24h.) To count which calendar days a span touches, iterate date objects from a.date() to b.date().

A week always begins and ends within the same month.

❌ False. Weeks constantly straddle month ends — e.g. the week of Jan 29–Feb 4.
🛠️ Do this: iterate the actual dates rather than bucketing by month.

The last days of December can belong to the first ISO week of the next year.

✅ True. An ISO week belongs to whichever year contains its Thursday, so 31 December 2025 lands in ISO week 1 of 2026.
from datetime import date
date(2025, 12, 31).isocalendar()   # (2026, 1, 3)
💬 What it does: isocalendar() returns (ISO_year, ISO_week, weekday). For 31 Dec 2025 it’s (2026, 1, 3) — ISO year 2026, week 1, weekday 3 (Wednesday).

A week always begins and ends within the same year.

❌ False. Because of ISO weeks (above), a single week can span two years.
🛠️ Do this: group by week with date.isocalendar(), which returns the correct ISO year and week.
round 2

Time zones

Your host’s zone isn’t yours, and the rules keep changing.

The machine your program runs on is always in the GMT / UTC time zone.

❌ False. Servers, laptops and containers can be in any zone, and a naive datetime.now() carries no zone at all — so you can’t tell what instant it means.
🛠️ Do this: always work in aware UTC.
from datetime import datetime, timezone
datetime.now(timezone.utc)   # aware + unambiguous
💬 What it does: datetime.now(timezone.utc) reads the current instant and tags it as UTC, so it’s an aware value you can safely convert to any local zone later.

Storing instants in UTC and converting to local only for display avoids most time-zone bugs.

✅ True. One canonical instant (UTC) with per-viewer conversion at render time is the standard cure: there’s a single source of truth, and DST is applied only when you format for a human.

The time zone your program runs in will never change.

❌ False. Deploys move regions, laptops travel across zones, and orchestrators reschedule containers onto other hosts.
🛠️ Do this: never depend on the host zone; store UTC and attach an explicit zone for display.

Time-zone rules — offsets and DST dates — never change.

❌ False. Governments change them regularly, sometimes with weeks of notice (countries abolish DST, shift offsets, even skip a day). Hard-coded rules like “IST = UTC+5:30 forever” slowly rot.
🛠️ Do this: resolve offsets through the IANA database via zoneinfo, and keep the OS tzdata updated.
from zoneinfo import ZoneInfo
ZoneInfo("Europe/Berlin")   # offset + DST come from tzdata
💬 What it does: ZoneInfo("Europe/Berlin") loads Berlin’s current offset and DST dates from the operating system’s time-zone database. Update tzdata and your app follows any law change — no code edits.

Because those rules change by law, offsets should come from the IANA tz database rather than being hard-coded.

✅ True. The IANA (Olson) database tracks every legal change; zoneinfo reads it, so your code stays correct across law changes without edits — you just update tzdata.

The server and the client are set to the same time zone.

❌ False. They rarely are, and a bare wall-clock string like “09:00” carries no zone to reconcile them.
🛠️ Do this: exchange UTC or ISO-8601 with an offset, and convert to the viewer’s zone only to display.
round 3

The system clock

Wall clocks are wrong, drift, jump — and sometimes must be faked safely.

The system clock is always set to the correct time.

❌ False. Clocks drift, get misconfigured, and are set by hand. For anything security- or ordering-sensitive, the client’s clock cannot be trusted.
🛠️ Do this: rely on an NTP-synced, server-authoritative time.

A machine with a dead CMOS battery can boot thinking it is 1970 or 2000.

✅ True. The real-time clock is kept alive by a small battery; when it dies, the clock resets to its hardware epoch (often 1970-01-01 or 2000-01-01) at every boot until it re-syncs.

Even a wrong clock is never wildly off.

❌ False. It can be years off — see the dead-battery case, or a VM restored from an old snapshot.
🛠️ Do this: validate incoming times and reject or clamp absurd values.

If the clock is wrong, it is at least off by a constant number of seconds.

❌ False. NTP both steps (jumps) and slews (speeds up / slows down) the clock, so the error itself changes over time.
🛠️ Do this: never derive elapsed time from wall-clock differences — use a monotonic clock (see the Duration round).

The system clock is never set to the distant past or far future.

❌ False. 1970, the 2038 32-bit overflow, and even year 9999 all turn up in real data — from bugs, bad imports, or fat-fingered input.
🛠️ Do this: use 64-bit time types and range-check before you compute or store.

For scheduling and tests, you should inject a “clock” object instead of changing the OS system time.

✅ True. Passing a Clock dependency lets tests and features (“run as if it were month-end”) control “now” in isolation — without disturbing everything else on the machine.
from datetime import datetime, timezone

class Clock:            # production
    def now(self): return datetime.now(timezone.utc)

class FakeClock:        # tests / simulations
    def __init__(self, t): self.t = t
    def now(self): return self.t
💬 What it does: Every place that needs “now” calls clock.now(). In production you pass a real Clock; in a test you pass a FakeClock(fixed_time) to freeze time — without ever touching the real OS clock.

You will never need to set the system time to anything but the correct time.

❌ False. Simulations, schedulers and “time-travel” features all need a controllable notion of now.
🛠️ Do this: inject a clock (as above) rather than touching the OS.

Faking the clock is only ever needed in tests, never in production.

❌ False. Production schedulers, back-fills and simulations need it too — and mutating the real OS clock would break every other process on the box.
🛠️ Do this: use the injected Clock in production as well.
round 4

Server vs client clocks

Two machines, two clocks — don’t order events by comparing them.

The server clock and the client clock are always set to the same time.

❌ False. They are two independent clocks; exact agreement is luck, not a guarantee — so you cannot order events by comparing their raw timestamps.
🛠️ Do this: assign order on the server, or use a logical sequence.

Token-expiry checks usually allow a small “leeway” because client clocks drift.

✅ True. A few seconds of skew is normal even with NTP, so JWT / OTP validation adds a tolerance window — otherwise a slightly-fast client is wrongly rejected.
LEEWAY = 60  # seconds of tolerated clock skew

if now > token_expiry + LEEWAY:
    reject()
💬 What it does: Only reject the token once now is past its expiry plus a 60-second cushion, so a client whose clock runs a little fast isn’t kicked out unfairly.

The two clocks are at least always roughly the same.

❌ False. Skew of seconds to minutes is common; on misconfigured machines it is far worse.

The two clocks are never off by decades.

❌ False. Dead-battery clients genuinely report the year 2000 or 1970 — decades away.
🛠️ Do this: sanity-check a client’s time against the server before trusting it.

If the two clocks are out of sync, it is by a constant number of seconds.

❌ False. The skew itself drifts and jumps, so you can’t “subtract a constant” to line them up.
🛠️ Do this: order events with a server-assigned timestamp or a logical clock, not client time.

To order events across machines reliably, use a server-assigned timestamp or a logical sequence.

✅ True. A database sequence, a single server’s timestamp, or a Lamport / vector clock gives a consistent order that does not depend on any wall clock agreeing.
round 5

Duration & monotonic time

A minute here isn’t a minute there, and the wall clock can jump.

Every time representation has an earliest and a latest value it can hold.

✅ True. There is always a floor and ceiling: the Unix epoch (1970), the 2038 cliff for 32-bit time, datetime.max at year 9999. “Time has no beginning or end” is false for any real data type.

time.monotonic() never goes backwards, so it is the right tool for timing how long code runs.

✅ True. A monotonic clock only moves forward and is immune to NTP steps, DST and clock resets — so the elapsed value can never be negative or jump.
import time

start = time.monotonic()
do_work()
elapsed = time.monotonic() - start   # seconds, always >= 0
💬 What it does: time.monotonic() returns a steadily increasing number of seconds from an arbitrary start point. Read it before and after the work and subtract — the gap is the true elapsed time and can never go negative.

One minute measured on one clock is exactly one minute on any other clock.

❌ False. Clocks tick at slightly different rates and are corrected independently, so “a minute” on two machines rarely matches exactly.
🛠️ Do this: measure any duration by reading one monotonic clock twice.

Subtracting two time.time() (wall-clock) readings is a safe way to measure elapsed time.

❌ False. The wall clock can jump — NTP corrections, DST, leap seconds, or a VM being suspended and resumed — so the difference can come out negative or absurdly large.
🛠️ Do this: use time.monotonic() for durations; keep time.time() only for “what instant is it now.”

A suspended-then-resumed VM (or a laptop with the lid closed) can make the wall clock jump forward by hours.

✅ True. While paused, the guest clock stops; on resume it either sits behind and then leaps forward when it re-syncs, or is corrected in one big step. This is a real reason wall-clock deltas are unsafe for timing.
round 6

Precision & uniqueness

Sub-second precision varies, and timestamps aren’t unique keys.

The smallest unit of time you need to care about is one second.

❌ False. Milliseconds, microseconds and nanoseconds show up constantly in databases, logs and tracing.
🛠️ Do this: keep the precision your source provides; don’t truncate to seconds by accident.

time.time_ns() returns an integer number of nanoseconds since 1970.

✅ True. It gives whole nanoseconds as an int (no float rounding), which is what you want when precision actually matters.
import time
time.time_ns()   # e.g. 1718000000123456789
💬 What it does: time.time_ns() gives whole nanoseconds since 1970 as an integer — no floating-point rounding, so it stays exact.

Millisecond precision is as fine as timestamps ever get.

❌ False. Nanosecond timestamps are routine; assuming milliseconds silently discards detail.

All of your timestamp sources use the same precision.

❌ False. One feed gives whole seconds, another milliseconds, another nanoseconds — mixing them corrupts comparisons and sorting.
🛠️ Do this: normalize everything to one unit on ingest.
def to_ns(ts, unit):
    factor = {"s": 1e9, "ms": 1e6, "us": 1e3, "ns": 1}
    return int(ts * factor[unit])
💬 What it does: Multiply each incoming value by how many nanoseconds its unit is worth, so every timestamp ends up in the same unit (nanoseconds) before you compare or sort them.

A high-precision timestamp is unique enough to use as an id.

❌ False. Two events can land within a single clock tick, and the clock’s resolution caps how many distinct values exist — collisions happen.
🛠️ Do this: add a tiebreaker; never key on time alone.
import uuid, time
key = (time.time_ns(), uuid.uuid4())
💬 What it does: Pair the timestamp with a random uuid4(): even two events at the same nanosecond get different keys, while the timestamp still gives you rough ordering.

Adding a sequence number or UUID keeps a key unique even when two events share a timestamp.

✅ True. The extra component breaks ties, so the pair is unique even at the same instant — while the timestamp still gives you rough ordering.
round 7

Timestamps & human formats

Units, formats, meanings and locales all differ — normalize everything.

A number like 1339972628 unambiguously identifies one instant.

❌ False. Is it epoch seconds, milliseconds, or microseconds? The digits alone don’t say — and some arrive as strings.
🛠️ Do this: record / agree the unit and store a canonical form.
from datetime import datetime, timezone

datetime.fromtimestamp(1339972628, tz=timezone.utc)          # read as seconds
datetime.fromtimestamp(1339972628000 / 1000, tz=timezone.utc)  # ms -> divide by 1000
💬 What it does: fromtimestamp(n, tz=utc) treats n as seconds since 1970 and returns an aware UTC datetime. If your number is milliseconds, divide by 1000 first — the digits alone can’t tell you which.

All incoming timestamps use the same format.

❌ False. Real inputs mix ISO-8601, epoch numbers, RFC-2822 and locale strings.
🛠️ Do this: parse defensively, then normalize to one canonical form (aware UTC / ISO-8601).
from datetime import timezone
datetime.fromisoformat(s).astimezone(timezone.utc)
💬 What it does: fromisoformat(s) parses an ISO string into a datetime; .astimezone(timezone.utc) then converts it to UTC so everything downstream is one consistent format.

ISO-8601 dates like 2011-07-05 are unambiguous and sort correctly as plain text.

✅ True. Year-month-day, largest unit first, zero-padded: there’s only one reading, and lexical (string) order equals chronological order — which is why it’s the format to store and exchange.

A record’s timestamp always means when the event actually happened.

❌ False. It might be when the row was written, received, or back-filled — and the source’s clock may be skewed.
🛠️ Do this: distinguish event-time from processing-time; carry both when it matters.
event = {
    "occurred_at": device_time,   # when it happened (may be skewed)
    "ingested_at": server_now(),  # when we recorded it (trusted)
}
💬 What it does: Store two times: when it happened on the device (which may be wrong) and when your server recorded it (authoritative). Then each use (billing, analytics) can pick the right one.

A record’s timestamp might be when it was ingested, not when the event occurred.

✅ True. In logging, streaming and analytics the stored time is often the moment of receipt or processing. If event-time matters (billing, ordering), you must capture it separately.

The date 05/07/11 is understood the same way everywhere.

❌ False. Is it 7 May (US, MDY), 5 July (EU, DMY), or 2005-07-11 (YMD)? It’s genuinely unknowable without the locale.
🛠️ Do this: use ISO-8601 YYYY-MM-DD for storage / exchange; format locale-aware only for display.
from datetime import date
date(2011, 7, 5).isoformat()   # '2011-07-05'
💬 What it does: date(2011, 7, 5) is year 2011, month 7 (July), day 5; .isoformat() prints 2011-07-05 — one unambiguous, sortable form.
