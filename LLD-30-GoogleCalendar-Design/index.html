Step 0 · the problem

Picture your typical week

Google Calendar lets people create, manage, and share events. Before any classes, live the workflow — then ask the hard questions.

You create a “Team Standup” every Monday, Wednesday & Friday at 10 AM. You invite your teammates, and it shows up on their calendars. One week you need to skip Wednesday, so you delete just that one occurrence. Meanwhile your colleague in London sees it at 3 PM their time.

Simple to use — but each line hides a design question. Reveal them one at a time and sit with each before the next:

🔄 Recurrence. How do you represent a meeting that repeats — “every Mon/Wed/Fri” — without saving thousands of separate events?
🤝 Sharing & RSVP. How does one event appear on many people’s calendars, each with their own yes / no / maybe?
✂️ Exceptions. How do you cancel a single occurrence while the rest of the series lives on?
🌎 Time zones. Why does the same meeting read 10 AM for you and 3 PM in London — and who keeps it right across daylight saving?
📆 Free / busy. When you invite five people, how do you find a slot when everyone’s actually free?
How do you tackle these? That’s exactly what we design in today’s class — overview → clarify → FRs → the hard parts (recurrence, attendees, time zones, free/busy) → trade-offs.

Step 3 · from FRs to classes

🔄 Recurrence

FR An event can repeat by a rule — daily / weekly / monthly — until a date or for N occurrences.

💭 What noun / class & attributes come out of this?

▼
  • Noun → RecurrenceRule: the repeat pattern (“every Monday”).
  • Choice: freq/interval/byday columns on Event? a RecurringEvent subclass? → neither. Give Event an optional RecurrenceRule (0..1); one-off events just leave it null.
  • What does 0..1 mean? It’s UML shorthand for how many rules an event may hold — at least 0, at most 1. A one-off meeting has none (0); a repeating one has exactly one (1) — never two rules on the same event. Picture a single slot that’s either empty or filled once. (For contrast: 1 = exactly one, always there · * = any number · 1..* = one or more — an event’s reminders are 0..*.)
  • How it repeats is the open variable — the deep dive is Step 4.
RecurrenceRule
- freq: Freq (DAILY|WEEKLY|MONTHLY)
- interval: int
- byday
- until | count

What each field means — with example values:

  • freq — how often it repeats: DAILY / WEEKLY / MONTHLY. e.g. WEEKLY
  • interval — every N of those: 1 = every week, 2 = every other week. e.g. 2
  • byday — which weekdays (weekly / monthly): [MO, WE, FR]. “every Mon/Wed/Fri”
  • until / count — when it stops: until = 2024-12-31 or count = 10.

Put together, “every other Mon & Fri until year-end” = freq=WEEKLY, interval=2, byday=[MO,FR], until=2024-12-31.

➕ Event gains: recurrence?: RecurrenceRule (optional)
FR A single occurrence can be edited or deleted without changing the rest — an exception / override.

💭 Does this need a new class?

▼
  • No new top-level class — the RecurrenceRule carries its exceptions: removed dates (EXDATE) plus one-off override events.
  • So the base rule stays intact for everyone else; only that one date changes.
RecurrenceRule
…
- exceptions: date[] (EXDATE)
- overrides: Event[]

Concrete example — the Wednesday standup you moved to 11:00:

  • exceptions (EXDATE) — dates removed from the series: [2024-02-14]. The rule stops generating the 10:00 slot on Feb 14.
  • overrides — one-off replacement events: Event(title="Standup", start=2024-02-14 11:00, end=2024-02-14 11:15) — just for that date.

Everyone else’s Mondays are untouched — only Feb 14 is carved out and replaced.

FR A user can view events by day / week / month, see free/busy, find a common free slot, and get a conflict warning.

💭 Where does this behaviour live — on Event?

▼
  • No — these verbs span many events, so they aren’t data on one Event.
  • Noun → SchedulingService (service layer): expands recurrences, computes free/busy, finds slots. Deep dives in Steps 6–7.
SchedulingService
+ expand(rule, window)
+ free_busy(users, window)
+ find_slot(users, duration, window)

What each method does — in plain words, with example values:

  • expand(rule, window) — turn a repeat rule into the concrete dates that fall inside a date window. e.g. expand(WEEKLY MO/WE/FR, Feb 12–18) → [Feb 12, Feb 14, Feb 16]
  • free_busy(users, window) — for a set of users over a time window, return their merged busy blocks. e.g. free_busy([A,B], 9–5) → [9:00–10:00, 12:00–12:30] busy
  • find_slot(users, duration, window) — find the earliest gap where everyone is free for duration. e.g. find_slot([A,B], 30 min, Mon 9–5) → 10:00–10:30

window = the date/time range you care about (a day, a week); duration = how long the meeting needs to be.

Step 4 · the open variable (deep dive)

Recurrence — one rule, many instances

We just derived that an Event points to an optional RecurrenceRule. Now the hard part: how do you represent “every Monday at 10” — thousands of occurrences over the years — and expand it on read? Decide first, then see:

“Every weekday for a year” — store every instance, or store the rule?

Store one recurrence rule (FREQ / INTERVAL / BYDAY / UNTIL or COUNT) and expand it to concrete dates only for the window you’re showing. It’s tiny to store, trivial to edit the whole series, and never balloons. Materialising every instance is wasteful and a nightmare to edit.

You move just next Monday’s 10:00 standup to 11:00. How?

A recurring event = the rule + a few exceptions: EXDATE the changed date and add a one-off override event. Splitting the series would move every future Monday (you wanted just one); leaving the 10:00 in place double-books that day.

Moving one occurrence — three ways, and when each fits:

  • EXDATE + override (best for a one-off): keep the single rule, remove just that date (EXDATE), and add one standalone override event at 11:00. The series stays whole and “edit the whole series” still works.
  • Split into two rules: close rule 1 the day before, open rule 2 after, and drop the odd day as a standalone event. This is the right tool when you’re changing the pattern from here on (“Fridays from now on”) — but for one moved day it fragments a clean series into two + a loose event and makes later edits messy.
  • One-off event, leave the 10:00 in place: double-books that day — wrong.

Better choice: a single changed occurrence → EXDATE + override; a permanent change going forward → split the rule.

So: keep the rule, not the instances. A recurring event is a rule that expands into occurrences on read, plus a few exceptions. And how it repeats (daily / weekly / monthly) is the open variable — a RecurrenceRule strategy, just like Parking’s pricing or Splitwise’s split.

Model it as Event + an optional RecurrenceRule (FREQ, INTERVAL, BYDAY, UNTIL/COUNT) + a set of exceptions (removed dates + override events). Expansion is a pure function: rule.occurrences(window) → [datetimes], minus exceptions, plus overrides.

Step 5 · the recurring shape

Attendees & RSVP

An event and its guests are a many-to-many with data on the link — the same association-class shape you’ve seen all course.

An event has many attendees, each with their own RSVP. Where does the RSVP status live?

RSVP is per (event, user) pair, so it can’t sit on User or Event alone. A map/list crammed onto the Event is non-atomic (breaks 1NF) — you can’t index or query one user’s RSVP, and it falls apart when attendees change. The pairing earns its own class: Attendee(user, event, status), an association class — the shape you’ve met all course (ShowSeat, Split / UserExpense, Membership).
Step 6 · the time twist

Time zones & DST

An event is a single instant in time; zones are a display concern.

Delhi user schedules 9:00 with a London colleague. Store the time as…

Store one absolute instant (UTC) — an event happens at a single moment everywhere. Convert to each viewer’s zone for display, applying DST then. Storing a wall-clock string is ambiguous and breaks across DST; two copies drift. (Recurring events are the subtle case: keep the rule in the organiser’s zone so “every Monday 9am” survives DST.)
Rule of thumb: store UTC, render local. Keep the user’s zone on the calendar/event so a recurring “9am Monday” stays 9am through daylight-saving shifts.

🕷️ DST edge cases that actually bite — and two great reads

▼
  • Spring-forward gap: on the night clocks jump 02:00 → 03:00, the wall-clock 02:30 never happens. An event stored as “02:30 local” has no valid instant — you must pick a rule (shift it to 03:30, or reject the input).
  • Fall-back overlap: when clocks fall 02:00 → 01:00, the wall-clock 01:30 happens twice. “01:30 local” is ambiguous — which of the two instants? You need a policy (usually the earlier one).
  • Recurring “Mon 9 AM” across a boundary: the wall-clock stays 9 AM but the underlying UTC instant shifts by an hour after the switch. That’s exactly why you store the rule in the organiser’s zone (not a frozen UTC offset) and re-resolve each occurrence.
  • The classic gotcha: computing “UTC + fixed offset” once and caching it — it silently goes wrong for half the year.

Step 7 · scheduling

Free / busy & conflicts

Both “am I double-booked?” and “when are we all free?” reduce to interval overlap.

Two events [s1, e1) and [s2, e2). They conflict iff…

The clean overlap test: each starts before the other ends. Touching (e1 == s2) is not a conflict with half-open intervals. To find a free slot for everyone: merge all attendees’ busy intervals and look for a gap long enough.

How “find a free slot” actually works

The client asks; the server does interval math. Walk it slowly:

  1. Client calls POST /freeBusy with {attendees, duration, window} (“find 30 min for A, B, C this week”).
  2. Server gathers busy intervals — for each attendee, fetch their events in the window (expanding recurrences) into [start, end) blocks.
  3. Merge everyone’s busy blocks into one sorted, non-overlapping timeline.
  4. Scan the gaps between busy blocks; return the earliest gap ≥ duration (or the top few).

💻 The merge + gap, in code

▼
# busy = all attendees' [start, end) blocks
busy.sort()
merged = []
for s, e in busy:
    if merged and s <= merged[-1].end:   # overlaps previous → extend
        merged[-1].end = max(merged[-1].end, e)
    else:
        merged.append(Interval(s, e))

# a gap between consecutive busy blocks that fits
for a, b in zip(merged, merged[1:]):
    if b.start - a.end >= duration:
        return Slot(a.end, a.end + duration)

Conflict check on create is the same idea, smaller: POST /events runs the overlap test s1 < e2 AND s2 < e1 against your existing events and warns if any overlaps.

Step 9 · trade-offs

Say these out loud

Rule vs materialised instances
Store the rule + exceptions and expand on read — not one row per occurrence. Cheap, editable, unbounded series.
Store UTC, render local
One absolute instant; convert per viewer. Keep the zone for recurring events so “9am Monday” survives DST.
RSVP on the join
Attendee(user, event, status) — the association class, the course’s recurring shape.
Overlap is interval math
s1 < e2 AND s2 < e1; find-a-slot = merge busy intervals, find the gap.
Reminders via a scheduler
A due-time queue / cron fires reminders — the same “don’t depend on the sweep for correctness” lesson as BookMyShow’s holds.
Extensions = one more class/field
Rooms / resources, attachments, shared calendars, working hours — each is additive, not a rewrite.
