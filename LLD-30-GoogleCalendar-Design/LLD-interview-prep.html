Know the rounds

Three flavours of LLD round

Each rewards a different thing. Read the prompt and play to it.

⌨️
Machine coding (60–120 min)
Build a working mini-system (parking lot, splitwise…). Judged on: it runs, clean OO, extensibility, edge cases. Working > complete.
📐
Design discussion (45 min)
Often no code — class diagram, APIs, trade-offs aloud. Judged on: requirement clarity, entity modelling, the right patterns, naming the tensions.
💬
Conceptual / viva (30 min)
Rapid-fire on patterns, SOLID, OOP, DB, concurrency. Judged on: crisp definitions + when to use, not textbook recital.
The speed playbook

Machine coding — fast yet LLD-correct

A repeatable time-box for a ~90-minute round. The order matters: a running skeleton early beats a perfect half.

phase~timedo
1 · Clarify & scope5 minList FRs out loud, cut scope, state assumptions. Agree what you will not build.
2 · Entities & enums10 min@dataclass for the nouns, Enum for fixed sets (status, type). No magic strings.
3 · Seams10 minName the open variable → an abstract Strategy; inject via the constructor. Define interfaces before bodies.
4 · Happy path25 minThe main flow end-to-end with in-memory dict repositories. Make it work for one case.
5 · Edge cases15 minValidation, custom exceptions, boundaries (full lot, double-book, empty input).
6 · Demo10 minA runnable main() with asserts that prints green. This is what they remember.
buffer15 minA couple of unit tests / polish / talk through extensions.
Code faster
  • Skeleton first — signatures + pass, then fill bodies.
  • @dataclass + Enum — zero boilerplate.
  • In-memory dict repos; never wire a real DB.
  • Constructor injection with a sensible default strategy.
  • One orchestrator Service; keep models dumb.
  • Narrate as you type — decisions, not just code.
Common pitfalls
  • Coding before listing requirements.
  • One god class doing everything.
  • Over-engineering — patterns the problem doesn’t need.
  • Magic strings instead of enums.
  • No demo / it doesn’t run.
  • Ignoring edge cases & shared mutable state.
What they look for

The LLD checklist

Tick these and you’ve covered ~90% of the rubric.

  • ✅ Requirements stated & scoped (you said what you’d skip).
  • ✅ Nouns → classes; fixed sets → enums.
  • ✅ The open variable is a Strategy — new behaviour = new class (OCP).
  • ✅ SOLID, especially SRP (one reason to change) and DIP (depend on abstractions).
  • ✅ Layered: models / strategies / repositories / service.
  • ✅ Encapsulation — private state, behaviour on the object that owns the data.
  • ✅ A runnable demo with asserts.
  • ✅ Trade-offs named out loud.
Quick-revise

Design patterns — UML + when to use

For each: bullets on when to reach for it and the LLD tell-tale, a generic UML class diagram, and a short sketch.

Strategy — swap an algorithm at runtime

▼
  • When: a behaviour has several interchangeable variants (pricing, split, locking, spot-choice).
  • Tell-tale: the requirement says “…one of these ways, and more later.” New variant = new class, engine untouched (OCP).
class PricingStrategy(ABC):
    def price(self, ticket): ...
service = ParkingService(pricing=FlatPricing())   # injected

Factory — create without naming the concrete class

▼
  • When: you decide which subclass to build from input (a type code, config).
  • Tell-tale: an if type == …: return XVehicle() chain → move it into a factory.
def make_vehicle(kind):
    return {"car": Car, "bike": Bike}[kind]()

Singleton — one shared instance

▼
  • When: exactly one of something (config, registry, ID generator).
  • Tell-tale: global shared state.
  • Watch: thread-safety & testability — a single injected instance is often cleaner than a true singleton.

Observer — notify many on change

▼
  • When: one change must fan out to many listeners (event → reminders, notifications, logging).
  • Tell-tale: “when X happens, also do A, B, C” — decouple via subscribe / notify.

Decorator — add behaviour without subclass explosion

▼
  • When: features combine freely (coffee + milk + sugar; notifier + retry + log).
  • Tell-tale: you’d need 2ⁿ subclasses — wrap instead.

Builder — assemble a complex object step by step

▼
  • When: many optional fields / invalid half-built states (a big Event with optional recurrence, attendees, reminders).
  • Tell-tale: a constructor with 8 args, half of them None.

Adapter — make an incompatible interface fit

▼
  • When: a third-party / legacy API has the wrong shape.
  • Tell-tale: “wrap the SDK so the rest of my code sees my interface.”

State — behaviour changes with mode

▼
  • When: an object acts differently per state and transitions between them (Ticket ISSUED→PAID; Event DRAFT→PUBLISHED).
  • Tell-tale: big if self.status == … blocks in every method. Vs Strategy: the object switches its own behaviour.

Command — an action as an object

▼
  • When: you need undo/redo, queues, or to log/replay actions.
  • Tell-tale: “every operation should be undoable / schedulable.”

Repository — collection-like data access

▼
  • When: hide storage behind save / find / all so the service doesn’t know about the DB.
  • Tell-tale: swap an in-memory repo for SQL without touching the service.

Which pattern? — quick quiz

Pricing can be hourly, flat, or surge — swappable at runtime, and more types later.

A family of interchangeable algorithms behind one interface, chosen/injected at runtime — new type = new class. That’s Strategy.

Build a Car, Bike, or Truck from a string code coming from the request.

Choosing the concrete class from input is a Factory. (Builder is for assembling one complex object step-by-step.)

A Ticket behaves differently as ISSUED → PAID → CLOSED and controls its own transitions.

Per-mode behaviour with self-managed transitions is State. Strategy is picked from outside; State the object switches itself.

When an event is created, also send reminders, emails, and an audit log — without coupling them.

One change fanning out to many decoupled listeners is Observer (publish/subscribe).
Quick-revise

LLD concepts — the essentials

Composition vs Aggregation vs Association (+ association class)

▼
  • Composition (◆): the part can’t live without the whole — Order ◆ OrderLine.
  • Aggregation (◇): shared / independent lifetime — Team ◇ Player.
  • Association: they just reference each other.
  • Association class: carries data about the link in a many-to-many — ShowSeat, Split / UserExpense, Membership, Attendee.

SOLID in five lines

▼
  • SRP — one reason to change.
  • OCP — open to extend (new class), closed to modify.
  • LSP — a subtype must be usable as its base.
  • ISP — small, focused interfaces.
  • DIP — depend on abstractions, inject them.

Favour composition over inheritance

▼
  • Inheritance is rigid — deep trees, fragile base class.
  • Composition (has-a + Strategy) flexes at runtime and avoids the 2ⁿ-subclass blow-up.
  • Use inheritance only for a true is-a with shared behaviour.

Enums over magic strings / ints

▼
  • Fixed sets (status, type, role) are Enums — type-safe, autocompletes, no typos.
  • You get exhaustiveness checks and one source of truth.
  • "PAID" scattered as strings is a bug farm.

Repository vs Service layering

▼
  • Repository: persistence — save / find / all.
  • Service: orchestration / business rules.
  • Models: data + own-data behaviour.
  • Strategies: the open variables.
  • Each layer stays swappable and testable.

Concurrency: optimistic vs pessimistic

▼
  • Pessimistic (lock the row, SELECT … FOR UPDATE): high contention.
  • Optimistic (version + retry, no lock): low contention.
  • The seat / balance race is a lost update — guard the read-modify-write.
  • A business hold (status + TTL) is not a DB lock.

Idempotency

▼
  • Same request applied twice = same result (retries, double-clicks).
  • Achieve via an idempotency key, a UNIQUE constraint, or a state check (“already BOOKED → no-op”).
  • Crucial for payments & bookings.

DB: normalization & indexes

▼
  • 1NF — atomic cells.
  • 2NF — no partial dependency on a composite key.
  • 3NF — no transitive dependency.
  • Index the columns you filter / join on; a composite index serves its leftmost prefix too.

Concept check

“User X owes ₹Y on this expense” — where does the amount live?

It’s per-pair data on a many-to-many → an association class (Split / UserExpense). The recurring shape across the whole course.

You add a new pricing type. In a good design you…

Open/Closed: new behaviour = a new class plugged in, no edits to working code.

Splitting ₹100 three ways without losing a paisa, you store money as…

Integer paise keeps arithmetic exact; give the leftover paisa to the first participant(s). Floats drift.
Conceptual Q&A

Answer first, then reveal

Try each aloud. Open the hint only if stuck, the solution to check.

Strategy vs State — what’s the difference?

💡 Hint

▼

Both swap behaviour behind an interface. Think about who changes it and whether the object transitions.

✅ Solution

▼

Strategy is chosen from outside and usually fixed for the object’s life (pick a pricing algorithm). State is the object switching its own behaviour as it moves between states (Ticket ISSUED→PAID), and states often trigger the next transition. Same structure, opposite intent.

Factory vs Builder — when each?

💡 Hint

▼

One picks which class; the other assembles one complex object.

✅ Solution

▼

Factory when the concrete type depends on input (Car vs Bike from a code). Builder when a single object has many optional parts / invalid half-states (an Event with optional recurrence, attendees, reminders) — build it step-by-step, validate at .build().

Why “favour composition over inheritance”?

💡 Hint

▼

Think about runtime flexibility and how subclasses multiply.

✅ Solution

▼

Inheritance fixes behaviour at compile time and explodes (a subclass per combination); a fragile base ripples to all children. Composition (has-a + injected Strategy) swaps behaviour at runtime and combines freely. Reserve inheritance for a genuine is-a with shared implementation.

How do you make “book this seat” idempotent & race-safe?

💡 Hint

▼

A retry must not double-book; two users must not both win.

✅ Solution

▼

Idempotent: check state first (already BOOKED by me → return the same result), or an idempotency key. Race-safe: make the claim an atomic check-and-set — a row lock (FOR UPDATE) / version CAS / a UNIQUE(show, seat) on insert — so the read-modify-write can’t interleave (the lost-update fix).

Singleton — what goes wrong, and the cleaner alternative?

💡 Hint

▼

Think tests and threads.

✅ Solution

▼

Global mutable state hurts testability (shared across tests) and needs care for thread-safety (double-checked locking). Cleaner: create one instance at the composition root and inject it — you get “one instance” without the global.

Where do association classes come from, and name four you’ve built.

💡 Hint

▼

Look for data that belongs to a link, not to either endpoint, in a many-to-many.

✅ Solution

▼

When a many-to-many relationship carries its own data, that (X × Y) pairing earns a class. You’ve built ShowSeat (BookMyShow), Split / UserExpense (Splitwise), Membership (group roles), and Attendee (Calendar RSVP).
