JWT — when it shines, when it bites

A JWT isn’t always the right tool. Here are real situations — for each, decide: is a JWT a good fit here, or is it about to hurt you?

A mobile app talks to a REST API; users stay logged in for weeks across app restarts. Access via a stateless token. Good fit for JWT?

Stateless + no browser cookies = JWT’s home turf.
  • Native apps have no cookie jar and no CSRF; they store the token in secure OS storage (Keychain/Keystore) and send it as a Bearer header. JWT fits perfectly.
  • ‘Weeks’ is the refresh token’s job: a short access token (~15 min) plus a long refresh token keeps users logged in without a fragile forever-token.
  • This is exactly what djangorestframework-simplejwt is built for.

A bank must let a user click “log out everywhere” and have every device kicked out instantly. Store auth purely as a stateless JWT?

Instant revocation is the one thing stateless JWTs can’t do.
  • There’s nothing to delete — the server stores no record of a JWT, so it can’t take one back. It’s valid until exp.
  • Fixes: server-side sessions (delete the row = instant), or keep JWTs but make access tokens short and revoke by refusing to refresh (drop the refresh token / bump a per-user token_version).
  • “Need instant global logout” is the classic signal to add a little state back.

To save DB calls, a dev stuffs the user’s full profile and a base64’d avatar image into the JWT payload. Good idea?

The payload is public and travels on every request — keep it tiny and non-secret.
  • A JWT is sent with every API call; a fat payload is bandwidth you pay constantly. Cookies also cap around 4 KB.
  • The payload is base64-encoded, not encrypted — anyone can read it. Never put anything private (PII, card numbers, images you wouldn’t publish) inside.
  • Put a small sub (user id) in the token and fetch the profile server-side.

A React SPA stores its JWT in localStorage so it survives refreshes. Safe?

localStorage is readable by JS — and so by any XSS.
  • Per-origin isolation doesn’t help against XSS: the malicious script runs on your origin, so localStorage.getItem("token") just works for it.
  • A stolen signed token is fully usable — the signature stops tampering, not theft.
  • Safer patterns: token in an HttpOnly cookie (JS can’t read it), or access token in memory + refresh token in an HttpOnly+Secure+SameSite cookie.

Microservices: service A logs users in and issues tokens; services B and C must verify them independently, with no shared session store. Good fit for JWT?

Stateless verification across services is exactly why JWTs exist.
  • With RS256, A holds the private key (only it can mint tokens); B and C hold the public key and verify locally — no call back to A, no shared Redis.
  • A shared session store would make every service depend on one database on every request — the bottleneck JWTs remove.
  • Just remember the trade-off you keep meeting: revocation is harder, so keep access tokens short.

CORS, CSRF & the SameSite flag — untangled

Three things every real app hits the moment a browser is involved — and beginners mix them up constantly. Let’s pull them apart with simple examples.

👀 Start here. Your React app at localhost:3000 does a GET to your Django API at localhost:8000. The console prints “blocked by CORS” and your .then() never runs. Did the request actually reach Django and execute?

For a simple request the browser sends it and lets it run — then withholds the response. CORS isn’t a gate on the way out.
  • The cross-origin GET executed on Django — and if it had been a state-changing call it might even have written to your database. CORS is a browser rule that acts on the response: it withheld the reply from your JavaScript because :8000 never sent Access-Control-Allow-Origin: http://localhost:3000.
  • Why not “negotiated first”? A simple request (a GET, or a form-encoded POST) has no preflight — the browser just sends it. Only non-simple requests (a JSON POST, a custom header) get a preflight OPTIONS that can stop the real request — but that’s still the browser deciding, never a server-side firewall.
  • Proof it’s browser-only: run the same call from curl and it works fine. curl doesn’t enforce CORS — nothing outside a browser does.
  • The fix, in Django, exactly: pip install django-cors-headers, then in settings.py add "corsheaders" to INSTALLED_APPS, put CorsMiddleware near the top of MIDDLEWARE (above CommonMiddleware), and list the caller: CORS_ALLOWED_ORIGINS = ["http://localhost:3000"]. Restart the server — settings are read once at boot.
  • Where exactly: it’s a project setting, not a per-view one — so by default the policy is global to the whole API.
  • “But different endpoints need different policies!” — that happens more often than you’d think; see the next box.

That one console error is what this whole section untangles. To explain it we need one idea first — what a browser calls an origin.

🌐 First: what is an “origin”?

An origin is the combination of scheme + host + port. Change any one and it’s a different origin — which is the whole trigger for CORS.

▼

Every URL has a port — it’s just usually invisible, because the browser fills in the scheme’s default for you:

  • Writing site.com:8000 simply says “don’t use the default — use 8000.” That’s all the colon means.
  • And now the row above makes more sense: http://site.com vs https://site.com differ twice over — different scheme and different implicit port (80 vs 443). Either alone is enough to make it a different origin.
  • Practical upshot: your React dev server on :3000 and Django on :8000 are different origins — which is exactly why you hit CORS in development but usually not in production, where both sit behind one domain on :443.

💬 What it does: Rule of thumb: one tight global allow-list, then widen deliberately for the few endpoints that are genuinely public — and never combine * with credentials (the browser rejects it anyway).

🔌 CORS — “who may READ my API’s response?”

Your React app runs at localhost:3000; your Django API at localhost:8000. Different origins. When the app fetch()es the API, the request does reach your server — but the browser refuses to hand the response back to the app’s JavaScript unless the API explicitly says “that origin is allowed” (an Access-Control-Allow-Origin header).

📝 What values can Access-Control-Allow-Origin actually have?

▼

Fewer than people expect — it is not a list. The header takes exactly one of these:

Click a row to reveal its cells — guess each first.

ValueMeaningWhen you’d use it
https://app.example.comone specific origin — the normal, safe answeralmost always. Your server echoes back the caller’s origin if it’s on your allow-list
*any origin may read itgenuinely public, non-authenticated data — a public API, fonts, a CDN
nullthe origin is opaque (sandboxed iframe, file://)essentially never — treat as a red flag; it’s spoofable
(header absent)no cross-origin reading allowed at allthe default when you haven’t configured CORS
  • You can’t list several origins. Allow-Origin: a.com, b.com is invalid. The server picks one value per response — which is why libraries keep an allow-list and echo back whichever origin matched (and add Vary: Origin so caches don’t mix responses up).
  • The big gotcha: if the request sends credentials (cookies / Authorization), * is rejected outright by the browser. With Access-Control-Allow-Credentials: true you must name an exact origin. This is deliberate — it stops ‘allow everyone’ from leaking logged-in data.
  • In Django that’s exactly the difference between CORS_ALLOWED_ORIGINS = [...] (echoes one match) and CORS_ALLOW_ALL_ORIGINS = True (sends *) — the second is the one you can’t combine with credentials.
💡 The beginner trap: CORS is not a server-side security guard. The cross-origin request already ran on your server. CORS only controls whether the browser lets another site’s JavaScript read the reply. It protects your users’ data from being slurped by other sites’ scripts — it does not stop anyone from calling your API (curl ignores CORS entirely).

🔗 Your Django API allows CORS only from your own frontend (a strict allow-list). An attacker puts a hidden, auto-submitting <form> on evil.com that POSTs to your /transfer endpoint while your user is logged in. Does your CORS setting stop this?

CORS guards reading a response; it never blocks a request from being sent — so it does nothing against CSRF.
  • Why the attack still lands: a hidden <form> submit is a plain browser navigation, not a fetch/XHR — CORS doesn’t even come into play. The browser sends it and attaches the user’s cookie, so Django sees a valid session and runs the transfer.
  • Why not “strips the cookie”? Deciding whether the cookie rides along is SameSite’s job, not CORS’s. CORS never touches which credentials are sent — only whether your JS may read what comes back.
  • So CORS and CSRF solve opposite problems: one guards reading your data from another origin, the other abuses your cookie being sent from another origin. The real fix is SameSite / a CSRF token — exactly what’s next.

🛡️ So how do you actually stop CSRF?

Is SameSite alone enough?

  • For most apps in 2024 — yes, nearly. Every current browser defaults to SameSite=Lax, which already blocks the classic forged cross-site POST.
  • But don’t rely on it alone, for three reasons: old browsers may ignore it; it doesn’t protect a state-changing GET; and the moment you need SameSite=None (a payment iframe, an embed), the protection is gone by design.
  • So: SameSite is the seatbelt, the CSRF token is the airbag. Django ships both — keep both.

Exactly what to do in Django

# 1. It's already ON. Just keep this middleware (it ships enabled):
MIDDLEWARE = [ ..., "django.middleware.csrf.CsrfViewMiddleware", ... ]

# 2. Harden the cookies (settings.py)
SESSION_COOKIE_SAMESITE = "Lax"     # CSRF_COOKIE_SAMESITE = "Lax" too
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SECURE   = True      # HTTPS only, in production

# 3. In a template form -> one tag, done:
#    <form method="POST">{% csrf_token %} ... </form>

# 4. Calling from JS? send the token back in a header:
fetch("/transfer/", {method: "POST", headers: {"X-CSRFToken": getCookie("csrftoken")}})

# 5. DRF with SessionAuthentication -> CSRF is enforced for you.
#    DRF with JWT/Bearer only -> no cookie, so no CSRF to worry about.
💬 What it does: ⚠️ The one thing not to do: slapping @csrf_exempt on a view to make an error go away. That switches the protection off — fix the token instead.
🎮 See all three gates work: open code/csrf_demo.html and switch the defence between none, CSRF token and Bearer while keeping SameSite=None — the attack succeeds only when every gate is down.

🎟️ That last option said “Bearer” — what is that?

The CSRF-immune option was “don’t use a cookie — send the token yourself.” You do that in one HTTP header called Authorization, and its value always has the same two-part shape: a scheme word, then the credential.

Why is it called “Bearer”?

Because it works like cash or a cinema ticket: whoever bears (carries) it gets in, no questions asked. The server doesn’t check that you are you — it only checks that a valid token was presented. Possession is the proof. That is also the catch: a stolen bearer token works for the thief exactly as well as for you, until it expires. That’s why bearer tokens are short-lived and only sent over HTTPS.

“Bearer” vs “the token” — not the same thing

  • The token is the actual credential — often a JWT (eyJ…), sometimes just a random opaque string the server looks up.
  • Bearer is only the scheme label in front of it — it tells the server “what follows is a possession token, use it as-is.” Bearer is not a synonym for JWT: you can put an opaque token after Bearer too.

Where does a Bearer token live?

Unlike a cookie — which the browser stores and re-sends for you automatically — a bearer token is stored and attached by your own code. Common homes: a JavaScript variable held in memory (safest, but gone on refresh), sessionStorage, or localStorage (survives refresh, but any XSS can read it). On mobile it’s the OS keychain. The trade-off in one line: a bearer header is CSRF-immune (nothing auto-sends it) but XSS-exposed (JS can read it) — the mirror image of an HttpOnly cookie.

🔎 Find it live in the browser (do this during Demo 2): log in to get a token, then open DevTools → Network, click an authenticated request (e.g. /api/me/), and under Request Headers you’ll see the line Authorization: Bearer eyJ… your JS added. To see where the token itself is parked, open DevTools → Application → Local Storage (or type localStorage.getItem("access") in the Console). Compare with a cookie under Application → Cookies — notice the cookie is there even though your code never touched it.

🏹 CSRF — the opposite worry

CORS worries about another site reading. CSRF worries about another site making your browser send. Because the browser auto-attaches your cookies to any request to a site, a hidden form on evil.com can make your browser POST to yourbank.com/transfer — with your logged-in cookie riding along. You never clicked a thing.

🧩 First: what is “middleware,” and which two do we touch?

Middleware is a stack of small checkpoints every request falls through on the way in — and every response climbs back up on the way out. Think airport lanes: security, then passport, then boarding. Each one can inspect the request, change it, or turn it away before it ever reaches your view.

Django already ships a sensible stack. For today only two checkpoints matter:

Click a row to reveal its cells — guess each first.

CheckpointShips with Django?What it does — (tap)
CsrfViewMiddlewareYes — already in the listOn every unsafe request (POST/PUT/DELETE) it demands the CSRF token. No token → 403. You don’t add it; you just don’t remove it.
CorsMiddlewareNo — from the django-cors-headers packageOn the way out it stamps Access-Control-Allow-Origin onto the response so the browser will let an allowed origin read it. This one you install and place yourself.

🛠️ Wire both up on a brand-new project — the whole recipe

▼

Starting from an empty folder, this is every step. CSRF needs nothing installed; CORS needs one package.

# 1. a fresh project
django-admin startproject config .
python manage.py migrate

# 2. install the ONE third-party piece (CSRF is already built in)
pip install django-cors-headers

3. Register the app — settings.py

INSTALLED_APPS = [
    # ...Django's defaults...
    "corsheaders",          # <-- add this line
]

4. Place the middleware — order is the whole trick

MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",          # <-- as HIGH as possible
    "django.middleware.common.CommonMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",      # <-- already here, keep it
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    # ...
]
⚠️ Why CorsMiddleware goes near the top: it must add the Allow-Origin header before any middleware below it can short-circuit and return a response early (e.g. CommonMiddleware issuing a redirect). Put it low and some responses go out with no CORS header — and the browser blocks them, with no obvious reason in your logs.

5. Say who may read the API — settings.py

CORS_ALLOWED_ORIGINS = [
    "http://localhost:3000",     # your React dev server
    "http://127.0.0.1:5500",     # a static page you serve locally
]
# never CORS_ALLOW_ALL_ORIGINS = True on an API that uses cookies

That’s it. Restart the server (settings are read once at boot) and the two checkpoints are live. Demo 1 below is exactly this project, already wired.

// paste your access token from step 2

// your code attaches the header by hand — the browser never does this for you

OAuth 2, the intuitive way

We rushed OAuth last time. Let’s slow down and build the intuition — no jargon first, just the idea.

🚒 The valet key

Fancy cars come with a valet key: it drives the car and unlocks the doors, but it won’t open the trunk or the glovebox, and you can throw it away without changing your real key. OAuth is a valet key for your data: you let an app do one limited thing (read your contacts) without handing it your real key (your password), and you can revoke it anytime.

😱 The problem it kills

Before OAuth, an app that wanted your Gmail contacts asked you to type your Gmail password into the app. Now the app has your password — it can read every email, change your password, delete the account — and if the app is hacked, so is your Gmail. OAuth’s whole point: never hand your password to a third-party app.

🎭 The four players, in plain words

👤
You
the owner of the data (your Google account).
📱
The app
wants a peek at some of your data. Never sees your password.
🏛️
Google (auth server)
asks you “is this OK?” and issues the app a limited token.
🗃️
Google’s API
hands over just the data the token is allowed to touch.

🔄 The dance, as a story

Watch it build up one step at a time.

① The app sends you to Google

You click “Login with Google.” The app doesn’t ask you anything — it bounces your browser to Google, saying “I’m app X and I’d like to read contacts.”

② You log in at Google and say yes

Google — not the app — checks your password and shows “App X wants to read your contacts. Allow?” You approve. The app never saw any of it.

③ Google hands the app a token

Google does not hand over the token yet. It first gives the app a short code — think of it as a cloakroom ticket. The ticket is worthless by itself; the app’s server still has to walk up to Google’s counter and trade it in for the real thing: an access token.

For example. Your browser lands back on the app at https://theapp.com/callback?code=4/0AeanS0b…. The app’s server posts that code to Google and gets back a token like ya29.a0Af….

That token is good for about an hour, and it opens one door: contacts.readonly. Ask it for your Gmail and Google simply says no. The code is single-use — try to trade the same ticket twice and it’s already gone.

④ The app uses the token — and gets only what you allowed

The app calls Google’s API with the token and gets your contacts. Not your email. Not your files. And you can revoke it anytime from your Google account.

🤔 Wait — one thing should bother you

Look at step ③ again. That one-time code travels back to the app through your browser — it lands in your address bar as ?code=4/0Ae9.... Which means it is briefly visible to your browser history, an installed extension, a shared laptop, a corporate proxy’s logs.

🤔 Discuss first — So… if someone copied that code out of the URL, could they walk off with your contacts?

▼
  • What would stop them from posting that code to Google themselves?
  • A server-rendered app also sends a client secret on that swap. It is sent to Google — but on a direct server→Google call (the back channel), never through your browser. So it never appears anywhere the thief was looking, and they are missing a piece.
  • Now the uncomfortable part: a mobile app or a SPA has nowhere safe to keep a secret. Anyone can unzip the APK or read the JavaScript. For those apps, the stolen code really was enough.

🔓 That hole is exactly what PKCE plugs

PKCE (say “pixy”) replaces the secret-you-cannot-keep with a secret you invent fresh, per login — so there is nothing to steal from the app in the first place.

  • Before sending you off, the app makes up a big random string — the verifier. It never leaves the app.
  • It sends Google only the hash of it — the challenge — along the visible browser redirect.
  • At the token swap it must present the original verifier. Google re-hashes it and checks it matches the challenge it stored.
  • A thief holding only the code has the hash, and cannot run a hash backwards. The stolen code is now worthless.

The picture: you mail a photo of your padlock ahead of time. Anyone can see the photo; only you hold the key that opens it.

code has no verifier — and can’t reverse the challenge (SHA-256 is one-way) → the stolen code is useless

🔄 The same dance, now with the safety pieces in

Nothing about the story changed — steps ① and ④ just carry the two extra values.

🔑 Three words you’ll keep hearing

  • Scope — what the token may touch (contacts.readonly). The app asks; you approve exactly that.
  • Consent — the Google screen where you say yes. It’s why the app can’t silently grab more.
  • Redirect URI — the one pre-registered address Google will send the code back to. Stops an attacker pointing the code at their own site.

🧩 And the safety bits, in one line each

▼
  • state — a random value the app sends and checks on return; stops a CSRF on the callback.
  • OIDC — a thin layer that also gives the app an ID token (a JWT) so it learns who you are — that’s the “login” in “Login with Google.”

In “Login with Google,” where do you type your Google password?

You authenticate at Google, not at the app.
  • You always land on Google’s domain to log in — that’s the point. The app only ever receives a token scoped to what you approved.
  • If an ‘OAuth’ flow ever asks for your Google password on the app’s own page, it’s a phishing attempt — real OAuth never does.
  • Passwords aren’t gone — you still have a Google password; you just don’t share it with third-party apps.

🤕 “Wait — is this OAuth or OpenID Connect?”

Almost everyone blurs these two. The one-line fix: OAuth 2 answers “what may this app do?” (authorization). OpenID Connect answers “who is this user?” (authentication). OIDC isn’t a rival to OAuth — it’s a thin identity layer that sits right on top of it.

📚 Where did OIDC come from? (30-second history)

▼
  • 2012 — OAuth 2.0 ships for exactly one job: authorization — letting an app touch your data with a scoped access token. It deliberately said nothing about identity.
  • But everyone wanted “Log in with Google/Facebook.” So apps faked login on top of OAuth: grab the access token, call some ‘who am I’ endpoint. Every provider did it differently — and an access token only proves “the bearer may access X,” not who signed in. That gap caused real security bugs (an app could be fooled about which user it was).
  • 2014 — OpenID Connect standardises it. Ask for scope=openid and you also get an id_token: a signed JWT that proves who logged in (sub, iss, aud, exp), plus a standard /userinfo endpoint. Every “Login with Google” today is OIDC under the hood.

Single Sign-On (SSO) — log in once, use everything

You log into Gmail, then open Docs, Calendar and YouTube — and none of them ask for your password again. That’s SSO, and it’s built directly on the OIDC we just met.

🌟 The idea in one breath

  • One central Identity Provider (IdP) owns your login — Google, Okta, Azure AD, or your company’s SSO portal.
  • Each app (a relying party) never checks your password itself — it delegates login to the IdP.
  • The first app redirects you to the IdP; you log in once, and the IdP sets a session cookie on its own domain and hands the app a token proving who you are.
  • The next app also redirects to the IdP — but the IdP already sees that session cookie, so it issues a token silently, with no second login. That silent step is the whole magic of the word ‘single.’

💡 How SSO relates to what you just learned: where OAuth delegates authorization for one app, and OIDC adds “who are you”, SSO reuses that one authentication across many apps. OIDC is the bridge that made SSO work on the modern web.
⚠️ The trade-off: one login is convenient and centrally controllable (disable the account → instantly locked out of everything) — but the IdP becomes a single point of failure: if it’s down or breached, every connected app is affected. That’s why IdPs are hardened hard (MFA, monitoring, short IdP sessions).

At work you log into your email, then open the HR portal and it lets you straight in — no password prompt. Which is the real reason?

SSO isn’t password-sharing or network trust — it’s one IdP session being reused.
  • Apps under SSO never see your password — only the IdP does. They receive a token the IdP issues, not your credentials.
  • Being ‘on the network’ isn’t authentication — that assumption is exactly how attackers move laterally once inside. The portal trusted the IdP’s proof, not your IP.
  • The IdP kept a session cookie from your first login; the HR portal’s redirect hit that session, so the IdP minted a token silently. That reuse is single sign-on.

Auth in interviews — what they actually ask

The whole arc (Auth-1 → 4) condensed into the questions that really come up. Each one: what the interviewer is actually probing, the crisp answer, and a diagram. Open one at a time and try answering out loud first.

🎓 The meta-point: almost none of these are memory tests. Interviewers use auth to see whether you can reason about trade-offs — “it depends, and here’s on what” beats a textbook definition every time.

🧩 Round 1 — the warm-ups (Auth-1)

“What’s the difference between authentication and authorization?”

▼

🎯 What they’re really testing: that you don’t use the words interchangeably — and that you know the status codes.

  • AuthN = who are you (prove identity). AuthZ = what may you do (permissions). Identity first, always.
  • 401 Unauthorized really means unauthenticated → show a login. 403 Forbidden means ‘I know you, you still can’t’ → access denied.
  • One-liner that lands: “the passport check is AuthN; whether your ticket opens the lounge is AuthZ.”

“How would you store user passwords?”

▼

🎯 What they’re really testing: the single most common auth question. They want hash + unique salt + deliberately slow — and to hear you reject encryption.

  • Hash them — never store plaintext, and never encrypt (encryption is reversible; a leaked key exposes everyone).
  • Use a slow, salted KDF: argon2id (today’s default) or bcrypt (cost ≥ 12). Both salt automatically.
  • Say why slow: a user logs in once and never notices 0.3 s; an attacker doing billions of guesses can’t afford it.

“Why not just use SHA-256? And what does the salt actually do?”

▼

🎯 What they’re really testing: depth. Lots of candidates say ‘use bcrypt’ but can’t explain what breaks otherwise.

  • SHA-256 is built for speed — ~billions of guesses/sec on a GPU, so even a salted password falls fast. Password hashing wants the opposite of speed.
  • Salt is a unique random value per user, stored in the open next to the hash. It kills precomputed rainbow tables and hides that two users share a password.
  • The catch to name: salt does not slow down a single guess — that’s the work factor’s job. You need both.

🎫 Round 2 — sessions vs tokens (Auth-2/3)

“Session or JWT — which would you pick?”

▼

🎯 What they’re really testing: whether you answer “it depends” with the actual dependency. Picking one unconditionally is the red flag.

  • Session = server holds the truth; you hold an opaque id. Revocation is instant (delete the row), but every request needs a lookup in a shared store.
  • JWT = the token holds the signed truth; any server verifies it locally. Scales out beautifully — but you cannot un-issue it.
  • The deciding question: do I need instant revocation, or do I need to scale/verify across services? Single server or ‘log out everywhere’ → session. Microservices, mobile, cross-origin → JWT.

“A user clicks ‘log out everywhere’. With JWTs, how?”

▼

🎯 What they’re really testing: whether you know JWT’s biggest weakness — and the standard production workaround.

  • Honest opener: a stateless JWT can’t be revoked — there’s no server record to delete. It’s valid until exp.
  • So you keep the access token short (~15 min) and revoke at the refresh step: drop/blacklist the refresh token, or bump a per-user token_version so old tokens stop validating.
  • Worst case the attacker has <15 minutes — you’ve traded perfect revocation for bounded exposure. Naming that trade-off is the answer.

“Is a JWT encrypted? What’s actually inside it?”

▼

🎯 What they’re really testing: a classic trap. Many candidates say ‘encrypted’ — it isn’t.

  • header.payload.signature, all base64url. Header & payload are encoded, not encrypted — anyone with the token can read every claim.
  • The signature is a keyed hash (HMAC-SHA256): it proves the token wasn’t tampered with and came from someone holding the secret. Integrity, not confidentiality.
  • So: never put a secret in the payload (card, PII). Put an id and fetch server-side.

“Where do you store the token in the browser?”

▼

🎯 What they’re really testing: whether you know this is an XSS-vs-CSRF trade-off rather than a ‘best’ answer.

  • localStorage → convenient, immune to CSRF (nothing auto-sends it), but any XSS can read it.
  • HttpOnly cookie → JavaScript can’t touch it (XSS-safe), but the browser auto-sends it → you must add SameSite/CSRF protection.
  • Strong answer: short-lived access token in memory + refresh token in an HttpOnly+Secure+SameSite cookie — the token never lands in storage an XSS can read.

🔑 Round 3 — OAuth (Auth-3/4)

“Walk me through ‘Login with Google’.”

▼

🎯 What they’re really testing: can you narrate a real flow end to end without hand-waving? Name the four players and the code-for-token swap.

  • The app redirects you to Google with its client_id, the scope it wants, and a pre-registered redirect_uri. You log in at Google, not at the app.
  • You consent → Google redirects back to the app’s callback with a short-lived, single-use code.
  • The app’s server swaps that code (plus its secret and the PKCE verifier) for an access token, then calls the API with it — getting only the scoped data.
  • The headline: the app never sees your password, and you can revoke it anytime.

“Why return a code first? Why not just hand back the token?”

▼

🎯 What they’re really testing: whether you understand front-channel vs back-channel — this separates people who’ve read about OAuth from people who get it.

code has no verifier — and can’t reverse the challenge (SHA-256 is one-way) → the stolen code is useless
  • The redirect travels through the browser (the front channel) where URLs leak — history, logs, referrers. You don’t want the actual token there.
  • So the browser only carries a useless-on-its-own code; the valuable token is fetched server-to-server (back channel), authenticated with the client secret.
  • PKCE closes the last gap: the app proves it’s the same one that started the flow, so even a stolen code can’t be redeemed. (The old ‘implicit flow’ that returned tokens in the URL is deprecated for exactly this reason.)

🌐 Round 4 — browser security (Auth-4)

“What is CSRF, and how do you prevent it?”

▼

🎯 What they’re really testing: whether you can explain why the browser makes it possible — not just name the fix.

  • The browser auto-attaches your cookies to any request to a site — even one another site triggered. So a hidden form on evil.com can POST to your bank as you.
  • Modern fix: SameSite=Lax (the default now) — the cookie isn’t sent on cross-site POSTs. Classic fix: a CSRF token only your own pages know.
  • Bonus point: APIs authenticated by an Authorization: Bearer header are CSRF-immune, because nothing auto-attaches that header.

“We enabled CORS — does that secure our API?”

▼

🎯 What they’re really testing: the most common misconception in the whole topic. They want to hear a firm no.

  • No. CORS is a browser rule about who may read a response. The cross-origin request still reached and ran on your server.
  • It is not authentication and not a firewall — curl, Postman, and any server-side client ignore CORS entirely.
  • It also isn’t CSRF protection: CORS guards reading; CSRF is about your cookie being sent. Opposite directions.

🏗️ Round 5 — the open-ended design question

“Design authentication for our product: a web app, a mobile app, and several backend services.”

▼

🎯 What they’re really testing: structure. They want you to ask questions, then choose deliberately and name the trade-offs.

  • Clarify first: do we need instant revocation? Is there a third-party login? How many services verify tokens? Web-only or mobile too?
  • Passwords: argon2id (or bcrypt cost ≥ 12), constant-time compare, rate-limit the login endpoint.
  • Tokens: short JWT access token (15 min) + long refresh token. Mobile → Bearer header + Keychain/Keystore. Web → refresh in an HttpOnly+Secure+SameSite cookie, access in memory.
  • Services: sign with RS256 so each service verifies with the public key — no shared session store, no call back to the issuer.
  • Revocation: per-user token_version bumped on ‘log out everywhere’ / password change. Third-party: OAuth 2 + PKCE via OIDC.
  • Close by stating the trade-off you accepted: “stateless scale, with up to 15 minutes of revocation lag.”
🛑 Answers that sink candidates: “we encrypt passwords” (you hash them) · “JWTs are encrypted” (signed, and readable) · “just use JWT” with no trade-off · “CORS secures the API” · “salt makes it slow” (the work factor does) · storing tokens in localStorage with no mention of XSS.
