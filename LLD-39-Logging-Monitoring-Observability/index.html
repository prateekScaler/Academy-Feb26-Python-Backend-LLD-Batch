the problem

The outage you couldn’t see

Your LLD-38 circuit breaker did its job last night: tripped OPEN at 3:07 AM, protected the system beautifully… and nobody knew until customers tweeted at 9.

📡 Monitoring = watching known numbers against known thresholds — questions you decided in advance, asked on repeat.

🔭 Observability = asking new questions of a running system without shipping new code — including questions you never predicted.

Three pillars + one pager

📝
Logs
“What happened?” — one searchable line per event.
📈
Metrics
“How much / how fast?” — cheap numbers over time, for dashboards & alerts.
🔎
Traces
“Where did the time go?” — one request’s journey across services.

🤔 Support pings: “the site feels slow.” No dashboards exist yet. What do you ask for FIRST — and why that, before anything else?

▼
  • Scope first: everyone or one user? one page or all? since when? Each answer halves the search space.
  • Then in pillar order: metrics to confirm and narrow (is p95 actually up? which endpoint?) → traces to find the hop → logs to explain it.
  • The trap answer is “ssh into a box and read logs” — you don’t even know you’re on the right box. This exact question is a classic interview; the structure of your answer is the answer.
pillar 1

Logs — from print() to production

Start where we all started: print(). It works on your laptop, once, while you watch. Then production happens.

Your Django app print()s “payment failed!” when a charge fails. Production runs 12 replicas behind a load balancer. Last night one customer’s payment failed. What can you actually do this morning?

You’re stuck — and the ways you’re stuck ARE the requirements.
  • Which of the 12 consoles? Container stdout isn’t kept unless something ships it. And even if you find it — printed WHEN, for WHICH order?
  • You can’t reproduce someone else’s card decline. Production-only failures are the norm, not the exception.
  • Work backwards from the pain and you’ve designed logging: every event needs a time, a severity, a source, and context IDs — and must land somewhere searchable.

The machinery: four Lego pieces

  • Logger — what your code talks to: log = logging.getLogger(__name__); the name says who’s speaking.
  • Level — the volume knob; below the threshold → silently dropped.
  • Handler — a destination (console, file, HTTP); one logger can feed many.
  • Formatter — the line’s shape: text for humans, JSON for machines.

Levels: the volume knob

📌 Scenario: A payment-gateway call times out, your code retries once, the retry succeeds; the customer never noticed. Log the first timeout at WARNING — a rising rate of these is exactly how you see the gateway degrading before it dies (your LLD-38 breaker’s early-warning feed). Log it at ERROR and you train everyone to ignore ERROR.

Same scenario, one change: the retry ALSO fails and the user sees “payment failed, try again.” What gets logged now?

Level = consequence, not drama.
  • The first timeout was still a handled surprise — WARNING. The moment the operation gives up, THAT’s the ERROR, once, with the traceback (log.exception).
  • Two ERRORs for one failure double-counts on the dashboard and buries the real signal in retries.
  • CRITICAL is for “the service itself is dying” (can’t bind port, DB pool gone) — one failed payment hurts one user, not the process.

🐍 Generic Python

import logging

logging.basicConfig(
    level=logging.INFO,                      # the volume knob
    format="%(asctime)s %(levelname)-8s %(name)s :: %(message)s",
)
log = logging.getLogger(__name__)

log.info("order %s created by user %s", order_id, user_id)   # lazy %s!
try:
    charge(card)
except GatewayTimeout:
    log.warning("gateway timeout, retrying order %s", order_id)
except Exception:
    log.exception("charge failed for order %s", order_id)    # traceback included, free

🌱 Django

# settings.py — Django's LOGGING is the SAME pipeline, as a dict
LOGGING = {
    "version": 1,
    "formatters": {
        "line": {"format": "%(asctime)s %(levelname)-8s %(name)s :: %(message)s"},
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler", "formatter": "line"},
    },
    "root": {"handlers": ["console"], "level": "INFO"},
    "loggers": {
        "django.request": {"level": "WARNING"},  # 4xx/5xx logged for free
        "orders":         {"level": "DEBUG"},    # your app, chattier
    },
}
# any views.py:
import logging
log = logging.getLogger(__name__)     # name becomes "orders.views"
log.info("order %s created", order.id)

How it works: Same four-piece pipeline on both sides — Django just declares it as config, so ops can retune levels per environment without a code change (12-factor). And log.exception(...) inside an except attaches the full traceback free — never log.error(str(e)), which throws the stack away.

🎛️ The knobs, in plain words

  • level — minimum severity that gets through — prod runs INFO; flip one logger to DEBUG only while hunting
  • log.info("... %s", x) — lazy formatting — template + raw values; the string is built only if the message will actually print. Walkthrough below ↓
  • getLogger(__name__) — loggers form a dot-tree (orders.views inherits from orders) — one config line tunes a whole subsystem
  • Together: code emits at the right level with lazy args; config decides per-environment what’s heard and where it lands

🐢 Lazy %s vs f-strings — in plain words

A restaurant kitchen: an f-string cooks the dish first, then asks if anyone ordered it. Lazy %s asks first, cooks only if yes — and for DEBUG lines in production, “nobody ordered” is the normal case.

user = load_user(42)        # imagine str(user) is costly: it walks the whole cart

# f-string: work FIRST, question later
log.debug(f"cart for {user}")
#  1. Python builds the full text "cart for <User 42, 83 items...>" RIGHT NOW
#  2. hands the finished string to the logger
#  3. logger checks the level: DEBUG is off -> string thrown away
#  -> you paid for str(user) on EVERY call, for nothing

# lazy %s: question FIRST, work only if needed
log.debug("cart for %s", user)
#  1. logger checks the level FIRST: is DEBUG even on?
#  2. off  -> returns immediately; str(user) NEVER runs   (the normal case)
#  3. on   -> only then builds the string                 (the rare case)
💬 What it does: In production this line sits at DEBUG while the app runs at INFO — the f-string version pays on every request for a string that’s thrown away. Proof, live: logging_basics.py chapter 7 counts the str() calls — f-string: 1 with DEBUG off; lazy %s: 0.

When to use which — the complete cheat-sheet

You’re writing…Reach forExampleWhy
Any log call, any levellazy %slog.debug("cart %s", cart)free when the level is off; and the constant template lets tools group all “cart ...” lines as ONE event
Log call with cheap values (an int id)still lazy %slog.info("user %s in", uid)consistency — one habit, zero decisions; the template IS the event name
An exception messagef-stringraise ValueError(f"bad amount {amt}")if it raises, the string is ALWAYS needed — laziness buys nothing
A string used unconditionally (path, key, response text)f-stringkey = f"cart:{user_id}"it’s always built anyway — f-strings are the fastest and clearest way
Joining many pieces in a loop"".join(parts)",".join(str(i) for i in ids)repeated += re-copies the string each pass; join builds once
Old % / .format() in normal codef-stringf"{x:.2f}" not "%.2f" % xsame power, more readable — the old styles survive only inside loggers and legacy code
The rule in one line: f-strings everywhere — except inside log calls, where the logger’s own lazy %s wins (it skips work the level would throw away, and keeps the message template constant for grouping).

Logs a machine can query

🤔 The PM asks: “how many payments over ₹5000 failed in the last hour?” Your logs are lines like payment of 7999 failed for rahul. How do you get the number — and how confident are you in it?

▼
  • You’re about to write a regex over gigabytes — and it will miss ₹7,999 formatting, count refunds as failures, and double-count retries.
  • The fix isn’t a better regex. It’s logging fields, not prose: event=payment_failed amount=7999 — then the question is a one-line query.
  • That’s all “structured logging” means: JSON lines. structlog makes it painless — bind(request_id=..., user_id=...) once, and every later line carries those fields automatically.

One request across many services

A checkout touches web → orders → payments: three services, millions of interleaved log lines. You want to read ONE request’s whole story. Where must its correlation ID be born?

Once, at the edge — then it travels.
  • If every service mints its own, the IDs never match across services — the whole point dies.
  • The order’s PK doesn’t exist for the first half of the request, and says nothing about requests that never create an order.
  • Honoring an incoming X-Request-ID lets the mobile app or load balancer start the chain even earlier — and echoing it in the response means support can ask a user for it.
📌 Scenario: Support ticket: “my payment failed around 3 AM, order #991.” With correlation IDs: find one log line for order 991, copy its req_id, grep it — the request’s entire four-service story appears in timestamp order. Without: three log streams, millions of lines, guesswork. This is implemented end-to-end in django_request_logging.py.

One search box for the whole fleet

  • The container rule: log JSON to stdout, full stop — the platform’s agent ships it. No log files, no rotation code in your app (12-factor).
  • Names to know: the classic ELK stack (expanded right below), Grafana Loki (“Prometheus for logs”), SaaS: Datadog/Splunk.

The ELK stack — the classic log pipeline, letter by letter

  • E — Elasticsearch: the database — stores every line and builds the inverted index (word → which lines contain it, like a book index) that makes search over billions of lines feel instant.
  • L — Logstash (today usually lighter agents: Beats, Fluent Bit): the mover — tails container stdout, parses text into fields, enriches (adds host/service/env), ships to Elasticsearch.
  • K — Kibana: the face — the search bar (reason:card_declined AND amount>5000), visualizations, dashboards, and alerting on top.

Inside Kibana — a 60-second tour

📌 Scenario: 3 AM, a 500-spike. Open Kibana, type level:error AND path:/checkout, bucket by minute: spike started 14:02, first errors are a card_declined flood from one card-BIN range. Time to answer: ~90 seconds — without ssh-ing into a single server.

Why not just Postgres for logs?

Your logs sit in Postgres. WHERE message LIKE '%card_declined%' over 2 billion rows takes ~40 minutes. The SAME search in Elasticsearch returns in 200 ms. What’s the trick?

Pay a little on every write; make every read instant.
  • LIKE '%...%' can’t use a normal B-tree index (the wildcard is on the left too) — so Postgres must read all 2B rows, every time you search.
  • Faster hardware shrinks a scan; it doesn’t remove it. The inverted index removes it — the cost became O(words in the query), not O(rows).
  • The honest trade: writes get heavier and the index eats disk — the classic read-vs-write trade-off, chosen correctly for logs (written once, searched thousands of times).
  • Fun fact: Postgres CAN do this too (tsvector + GIN full-text indexes) — Elasticsearch is that idea productized, distributed, and given Kibana as a face.

🔧 Ops corner — why search is fast, rotation, and what logs cost

▼
  • Why not SQL? Elasticsearch builds an inverted index (word → which lines contain it, like a book index) — milliseconds over billions of lines vs a full LIKE scan.
  • On a bare VM rotation is your job — RotatingFileHandler(maxBytes=10_000_000, backupCount=5) — or the disk fills and takes the service with it.
  • Cost levers, in order: right levels (DEBUG off) → sample the boring (keep 1% of 200-OK lines, 100% of errors) → 7–30 days hot, archive the rest.

⚠️ The five logging sins — each one is a real incident

Five ways teams burn themselves with logging. For each: guess the failure before the reveal — every one of these has paged someone at 3 AM.

Sin #1. To debug a flaky login, a teammate adds log.debug("login attempt user=%s pass=%s", email, password) — “relax, it’s DEBUG, it’s off in prod.” Ship it?

The never-list has no “but it’s only DEBUG” clause.
  • The whole point of levels is that DEBUG will be switched on in prod someday — during an incident, when everyone is stressed and nobody reviews what starts printing.
  • The never-list: passwords & attempts, session tokens/JWTs, API keys, card numbers/CVV (PCI), government IDs, health data, and PII like emails (GDPR — log user_id=42, not the address).
  • Enforce at the formatter/filter (one choke point that masks sk-…7d2f), never by trusting fifty call sites to remember.
  • Logs leak: aggregators are widely readable inside companies, and leaked log dumps are a classic breach vector.

Sin #2. The payment gateway wobbles daily; retries absorb it. A teammate logs every retry at ERROR — “so we never miss a real outage.” A month later the real outage hits. What actually happens?

Crying wolf works exactly once.
  • Levels are a trust system: ERROR = “a human should look today.” Spend that meaning on handled retries and it’s gone when you need it.
  • The handled retry is a WARNING — a dashboard counts it, and a rising rate becomes an alert long before the outage.
  • The spike-detection hope fails too: the noise floor is now so high and jittery that the real spike is statistically invisible.
  • And alert rules built on level=ERROR counts (very common) fire constantly — which is Sin #2 feeding the alert-fatigue diagram you’ll meet in the Alerts section.

Sin #3. One failed request produced the SAME traceback four times in the logs. There’s no loop, one replica, one handler. What’s the likely culprit?

Log where you HANDLE, not where you pass through.
  • Repo view: views.py logs+raises, services.py logs+raises, gateway.py logs+raises, then Django’s handler logs the 500. One failure, four tracebacks.
  • Rule: log at the layer that handles the error (or the top-level boundary) — everywhere else, just raise.
  • Four handlers would also duplicate — but then EVERY line would appear 4×, not just tracebacks. That’s the tell.
  • Cost isn’t just noise: on-call reads the same stack four times wondering if it failed four times — duplicated logs multiply time-to-understanding.

Sin #4. You add ONE innocent log.info("processed %s", item.id) to a batch loop. Throughput drops from 50k to 12k items/sec and the log bill triples. How can one line cost that much?

Per-item cost × items/sec = your new bottleneck.
  • A log call is not free: build the record, format the string, take the handler lock, write to the stream — microseconds each, times 50,000/sec, is most of a core plus blocking I/O.
  • The fix is altitude, not silence: INFO “batch done: 50k items, 12 failed, 4.1s” once, per-item lines at DEBUG for when you’re actually hunting.
  • “Never log in loops” overshoots — DEBUG lines in loops are fine because prod runs at INFO and lazy %s makes them nearly free (the kitchen rule from earlier).
  • The bill matters too: logs are the most expensive pillar per byte — volume discipline IS cost discipline.

Sin #5. Two teammates log the same failure. A: log.error("Payment #991 for rahul@x.com of Rs.7999 failed (card declined) after 2 retries -- check the gateway dashboard!")  B: log.error("payment_failed order_id=991 reason=card_declined retries=2 amount=7999"). Which ships?

Write for the query engine; it will read this line a million times.
  • A feels friendlier but can’t be counted, graphed, or filtered — and “how many card declines today?” is now a regex problem again (the ₹5000 diagram all over).
  • A also committed Sin #1: an email address in the logs. B references order_id; the order record holds the contact — behind proper access control.
  • Field names are the contract: pick event=, reason=, order_id= once, and dashboards, alerts and greps compound forever.
  • Human context isn’t lost — it lives in the runbook link and the event name, not in prose that varies by author and mood.
pillar 2

Metrics — the numbers that keep score

Logs tell stories. Metrics throw the stories away and keep only the score — and that trade is the whole point.

Your logs already record every single request. Why do teams run a SECOND system — metrics — that stores strictly LESS information?

It’s a compression, not a duplicate.
  • “Requests/sec right now?” from logs = scan millions of lines, every dashboard refresh. A counter answers instantly, forever.
  • Structured logs CAN be graphed — but at 500 MB/day vs a few MB/day you can’t afford always-on, year-long, per-second graphs from logs.
  • And the app-behaviour metrics are the ones that page you: error rate and p95 are application numbers, not infra numbers.

Read a real dashboard first

Before the theory, the destination — this is what “metrics” buys you. Four panels, and only three kinds of number behind all of them:

Three shapes

📌 Scenario: Deploy at 14:00. Counter: rate(errors_total) jumps from 0.2/s to 9/s at 14:02 — the deploy did it. Gauge: queue_depth climbing steadily since 14:00 — workers are dead, nobody’s consuming. Histogram: checkout p99 went from 300ms to 2s while p50 didn’t move — something is choking only the heavy requests.

🧭 Which metric type do I use? (30-second decision tree)

▼
  • Cumulative total that only increases? → Counter (requests, errors, bytes). Graph its rate().
  • Current snapshot that goes up and down? → Gauge (CPU %, queue depth, active connections).
  • Care how values are distributed? → Histogram (latency, sizes) — percentiles come from its buckets.
  • Need exact percentiles, single instance, no fleet merging? → the rare Summary. Default to Histogram — it aggregates across replicas.

Which numbers? RED for the service, USE for its resources

📌 Scenario: Friday sale, 2× traffic. RED says: rate doubled, errors flat, p95 up 40%. Healthy-ish — but USE says the DB pool is at 9/10 with 3 waiters. That’s tomorrow’s outage, visible today: add capacity (or a bulkhead) before errors start.

RED per endpoint answers 90% of “is it healthy?”. Google’s Four Golden Signals are the same idea, one older and one wider:

⏱️
Latency
p50/p95/p99 — tracked separately for successes vs failures (fast errors fake a good graph).
📈
Traffic
Demand: requests/sec, concurrent users.
❌
Errors
Explicit (5xx) and implicit (wrong data, timeouts), as a % of traffic.
🧋
Saturation
How full you are: pool usage, queue depth — the early warning that fires before errors do (your LLD-38 bulkhead filling up shows here first).

Percentiles: why nobody graphs the average

Your average latency is a healthy 90ms, but p99 is 1.2s and rising. Support says “some users say checkout hangs.” Who’s right?

The tail is the truth.
  • The average is dragged toward the happy majority — it mathematically hides a minority in pain.
  • The session math is the killer: pages fire many requests, so the chance a session hits the slow 1% compounds fast.
  • Rising p99 with flat p50 smells like a resource at its limit — a lock, a connection pool, GC — hurting only the requests that queue.

Collection: the pull model

🐍 Generic Python

from prometheus_client import Counter, Histogram, start_http_server
import time

REQS = Counter("http_requests_total", "requests", ["path", "status"])
LAT  = Histogram("http_request_seconds", "latency", ["path"])

start_http_server(8000)                     # exposes GET /metrics

def handle(path):
    t0 = time.perf_counter()
    try:
        result, status = do_work(path), "200"
    except Exception:
        result, status = error_page(), "500"
    REQS.labels(path=path, status=status).inc()          # count it
    LAT.labels(path=path).observe(time.perf_counter()-t0) # time it
    return result

How it works: Your app never sends anything — it keeps counters in memory and serves them as text on /metrics; Prometheus scrapes on a schedule; Grafana and Alertmanager query Prometheus. App stays dumb, collection stays central.

🎛️ The knobs, in plain words

  • labels (path, status) — one metric becomes sliceable series (“errors on /checkout only”). Never label by user_id — every distinct value is a new series (cardinality explosion)
  • Histogram buckets — latency bins; percentiles are computed from bucket counts — cheap and mergeable across the fleet
  • scrape interval (15s) — your resolution; finer = more storage
  • Together: app counts in memory with labels; the scraper turns counts into time series; dashboards and alerts do math on the series

The dashboard language (PromQL)

# requests per second, per endpoint (5-min window)
rate(http_requests_total[5m])

# error rate as a percentage of traffic
rate(http_requests_total{status=~"5.."}[5m])
  / rate(http_requests_total[5m]) * 100

# p99 latency, computed from histogram buckets
histogram_quantile(0.99, rate(http_request_seconds_bucket[5m]))
💬 What it does: Every Grafana panel and every alert rule is one of these expressions saved with a threshold — rate() turns counters into slopes, histogram_quantile() turns buckets into percentiles. Dashboards stop being magic.
pillar 3

Traces — where did the time go?

Metrics say checkout p95 tripled. Every team checked their own service: “we’re fine.” Everyone is innocent — and the request is still slow.

🤔 How can EVERY service look fine in its own logs while the end-to-end request takes 3× longer — and what single piece of evidence would end the argument?

▼
  • Each service only measures its own work. Time hides between them: network hops, retries, queueing — and in serial call chains nobody owns.
  • Per-service averages stay flat while one request’s path got longer (a new serial call, a retry loop).
  • The argument-ender: one picture of ONE slow request with per-hop timing. That picture is a trace.

p95 on /checkout jumped from 300ms to 900ms right after yesterday’s deploy. What’s the FASTEST route to the culprit?

Diff the waterfalls.
  • Two waterfalls side by side point at the exact hop in minutes: “the new code calls pricing serially in a loop.”
  • Nobody logged the word “slow” — grepping for it is the black box all over again.
  • Rollback is a fine mitigation to run in parallel — but the question was finding the culprit, and data-shaped regressions survive rollbacks.
  • Span = one timed unit of work (a handler, a DB query, an HTTP call) with a start, duration, and parent.
  • Trace = all spans of one request, glued by a shared trace ID, drawn as the waterfall.
📌 Scenario: The waterfall above answers in one glance what no amount of per-service log reading can: 480ms total, and 350 of them are inside payments.charge — specifically the bank API call. Bonus finding: auth and cart ran serially and could have run in parallel.

How spans find each other

The correlation-ID trick, standardized: the W3C traceparent header carries the trace ID across hops; each service reports its spans; the collector reassembles the tree. OpenTelemetry auto-instruments Django/httpx/psycopg and exports anywhere (Jaeger, Tempo, Datadog). Tracing everything is costly — keep ~1–10%, tail-sampled: always keep the slow and failed ones.

the human loop

Alerts — waking humans, carefully

Dashboards are useless at 3 AM — nobody’s watching. An alert is the system deciding a human must be fetched. Design it like YOU are that human.

🤔 Budget constraint: you may add exactly ONE alert to the new checkout service. What do you page on — which number, what threshold, what duration? Defend each part.

▼
  • Symptom over cause: users feel error rate and latency; they don’t feel CPU. Page on what users feel.
  • A ratio, not a count: 50 errors means nothing without traffic — errors/requests > 5% survives traffic spikes and lulls.
  • A duration: “for 10 minutes” — one bad second is normal (GC, one slow client); sustained breach is an incident.
  • Everything else starts life as a ticket — it earns the right to page with data.

Disk on the analytics DB hits 82% (growing ~1%/day). Error rate and latency are normal. What should this trigger?

Urgent ≠ important: ticket it.
  • At +1%/day you have ~2 weeks of runway — perfect ticket material: fixed during work hours by a rested human.
  • The sneaky part: “prevention beats reaction” is TRUE — and the ticket IS the prevention. Paging isn’t the only proactive tool.
  • “Nothing” chooses a guaranteed future 3 AM page over a calm Tuesday ticket.
  • Page on symptoms (users hurting NOW: error rate, latency); ticket the causes that can wait (disk 82%, growing 1%/day).
  • Every page must be actionable — if the response is “huh, it self-healed” three times, delete or demote the alert.
# the anatomy of a good alert rule (Prometheus-style, in words)
ALERT  CheckoutErrorsHigh
IF     rate(errors_total{path="/checkout"}[5m])
         / rate(requests_total{path="/checkout"}[5m])  > 0.05   # symptom, as a ratio
FOR    10m                                                      # sustained -- not one blip
LABELS    severity=page                                          # wakes a human
ANNOTATIONS runbook="wiki/runbooks/checkout-errors"              # what to DO about it
💬 What it does: Four parts, each defensible: a user-facing ratio, a threshold, a duration, a runbook. A page without a runbook is organized panic.

Alert fatigue: the silent outage-maker

  • The four tests of a good page: Actionable (there’s something to do) · Urgent (can’t wait for morning) · Clear (context + runbook link) · Rare (a healthy on-call week is mostly silence).
  • On-call hygiene: a rotation with handoffs, every page reviewed weekly (keep/tune/delete), and blameless postmortems — blame teaches people to hide what they saw.

SLOs & the error budget — alerting’s grown-up form

Mid-month, a bad deploy burned 30 of your 43.8-minute monthly error budget. Engineering wants to ship a risky migration this week. The error-budget policy says…

The budget is the speed limit.
  • The whole point: the speed-vs-safety argument gets settled by arithmetic, not by whoever argues loudest.
  • Budget healthy → ship boldly. Budget spent → users already absorbed this month’s risk.
  • A blanket “no risky ships after the 15th” ignores the data — some months you’ve spent nothing by the 25th.
  • SLI — Service Level Indicator: a measured ratio of good events — % of requests under 300ms.
  • SLO — Service Level Objective: your promise about the SLI — 99.9% succeed, per month.
  • SLA — Service Level Agreement: the same promise with a contract and refunds attached — SLOs are internal targets, SLAs are legal ones.
  • Error budget: 100% − SLO — failure reframed as a resource you spend.

Interview corner

Observability questions are judgment questions in disguise — structure beats trivia every time.

“Users say the site is slow. Walk me through what you do.”

▼

🎯 What they’re really testing: Whether you debug with a method or by vibes. They want to hear the pillars used in the right order.

  • Scope (metrics): is p95 actually up? Since when? Which endpoints/regions? — confirms & narrows in 2 minutes.
  • Localize (traces): open slow-request waterfalls; find the span that grew.
  • Explain (logs): read that service’s logs around those request IDs for the actual error/change.
  • Correlate with changes: deploys, feature flags, traffic spikes. “What shipped at 14:00?” solves half of all incidents.
  • Bonus points: mention mitigating in parallel (rollback/flag off) while diagnosing — users first, root cause second.

“Logs vs metrics vs traces — when would you reach for each?”

▼

🎯 What they’re really testing: That you know they answer different questions, not that one replaces another.

  • Metrics: is something wrong, how big, since when — cheap, always-on, alertable.
  • Traces: where in a multi-service path — the only pillar with cross-service timing.
  • Logs: why exactly — the detailed event record once you know where to look.
  • Sharp closer: “metrics to detect, traces to localize, logs to explain — correlation/trace IDs tie the three together.”

“Design the logging for our payments service.”

▼

🎯 What they’re really testing: Whether you think in fields, levels, and safety — not just log statements everywhere.

  • Structured JSON to stdout; aggregated centrally (they may ask “why stdout?” — 12-factor, containers, the agent ships it).
  • Every line: event, request_id (honored or minted at the edge, echoed in the response header), order_id/user_id, outcome, duration_ms.
  • Levels with intent: INFO = money-trail events (created/authorized/captured/refunded), WARNING = retries/fallbacks, ERROR = failed operations with log.exception.
  • Safety: mask PANs/tokens at the formatter level (never trust call sites); never log full card data — PCI. Retention & access control on the aggregator.
  • Close with the audit angle: for payments, INFO logs double as the reconciliation trail — which is why prose-free, field-rich lines matter.

“Why do we alert on p99 latency instead of average? And why the ‘for 10m’ clause?”

▼

🎯 What they’re really testing: Percentile literacy + alert-fatigue awareness in one question.

  • Average hides the tail: p99 at 1.2s can coexist with a 90ms average — and the tail compounds per session (many requests per user).
  • Alerts fire on sustained breach because single-sample spikes are normal (GC, cold cache, one slow client) — the FOR clause is the anti-flapping, anti-fatigue clause.
  • If they push: mention SLO-based alerting — page when the error budget burn rate says the monthly promise is in danger, not on every threshold twitch.

“What’s a correlation ID and how would you add one to Django?”

▼

🎯 What they’re really testing: Practical middleware knowledge + understanding of propagation.

  • Middleware at the top of the stack: read X-Request-ID or mint uuid4().hex; stash in a contextvar; add to every log record via a logging Filter; echo in the response header.
  • Propagate it on every outbound call (httpx headers, Celery task kwargs) — an ID that doesn’t travel is just a local label.
  • Name-drop the grown-up version: W3C traceparent + OpenTelemetry auto-instrumentation gives you this plus timing = distributed tracing.
  • It’s implemented end-to-end in django_request_logging.py — run it and curl with/without the header.
same patterns, new stack

Observability in the AI era

An LLM app is a distributed system whose flakiest, priciest dependency happens to think. Everything transfers — plus two new first-class signals: cost and quality.

  • Logs: every model/tool call is an event — event=llm_call, model, tokens, latency_ms. New twist: prompts carry user PII, so redaction needs content filters, not just field masks.
  • Metrics: RED plus tokens/sec, cost/day per feature, cache-hit rate, eval scores — teams alert on cost burn rate exactly like an error budget.
  • Traces: an agent run IS a trace — every LLM call, tool call and retrieval is a span (see waterfall). OTel’s GenAI conventions standardize it; LangSmith/Langfuse are the traces+evals tools.
  • Alerts: same symptom rule, new symptoms — 429 storms, time-to-first-token p95, cost burn, and eval-score drift (the model got quietly worse — a bad deploy you didn’t make).
  • The new pillar — quality: classic systems fail loudly (500s); LLMs fail plausibly (fluent, confident, wrong). So you run evals on samples of live traffic — no traceback fires when the answer is merely bad.
📌 Scenario: Your support-bot bill jumps 6× overnight. The cost-burn alert fires at 7 AM; the trace shows one user’s question sending an agent into a retry loop — 40 LLM calls per session. Without cost-as-a-metric, this is a surprise invoice at month-end; with it, it’s a Tuesday-morning bugfix.
🤖 The transfer, in one line: logs → what did the model see and say · metrics → tokens, dollars, latency, scores · traces → the agent’s path as spans · alerts → cost & quality drift, not just errors.

🎓 Homework

  • Logging tour: run python3 logging_basics.py. Then break it on purpose: set the console handler to DEBUG and watch the noise; log a fake token and write the masking line yourself.
  • JSON logs: run structured_logging.py; add a cart_size field to the checkout flow and a duration_ms to one more step. Then write the one-line “query” (in words) that finds failed payments over $100.
  • Django middleware: run django_request_logging.py; curl all three endpoints. Send your own X-Request-ID: test-123 header and confirm it’s honored end-to-end. Then add a fourth view that logs at WARNING when duration_ms > 1000.
  • Alerting judgment: run alert_watcher.py. Change the threshold to 2% and the FOR-duration to 2s — count the flapping pages. Now 10%/30s — how late is the page? Write down the trade-off you just felt: that’s alert tuning.
  • Audit something real: take any project you’ve built. Which remote calls log nothing on failure? Where would you NOT be able to answer “which request caused this traceback”? Add one correlation ID and one WARNING you wish you’d had.
