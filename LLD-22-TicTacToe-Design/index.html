Pen design recap

From the requirements to the clean design

You submitted class diagrams against these requirements in the GitHub discussion. Re-read them once — then we evolve the design in five steps and you compare each step against what you drew.

Functional requirements (numbered — the evolution below cites them as R1…R9)
  1. A pen is anything that can write.
  2. Types of pens: Gel, Ball, Fountain, Marker, Throwaway.
  3. Ball Pen and Gel Pen use a Refill (which has a tip/nib and an Ink) to write.
  4. A Refill has a radius.
  5. Ink has a colour.
  6. Fountain pens have an Ink directly (no refill); their nib has a radius.
  7. Each pen writes in its own way. Some pens write in the same way as others.
  8. Every pen has a brand and a name.
  9. Some pens are refillable; some are not (throwaway).

Putting it together — the final shape we landed on

Every decision from the five evolutions, in one file. Compare to your submission:

Pen — final design (E5 from LLD-21)
collapse▾
from abc import ABC, abstractmethod
from typing import Protocol
from dataclasses import dataclass

# Supporting types
@dataclass
class Ink:
    colour: str
    brand: str

@dataclass
class Nib:
    radius: float

@dataclass
class Refill:
    nib: Nib
    ink: Ink

# Writing behaviour as a Strategy (Q5)
class WritingStrategy(ABC):
    @abstractmethod
    def write(self) -> None: ...

class SmoothWriting(WritingStrategy):
    def write(self): print("writes smoothly")

class RoughWriting(WritingStrategy):
    def write(self): print("writes roughly")

# Pen base — flat hierarchy (Q2, Q6)
class Pen(ABC):
    def __init__(self, brand: str, name: str, strategy: WritingStrategy):
        self.brand, self.name, self._strategy = brand, name, strategy
    def write(self): self._strategy.write()

# Refilling as a capability — Protocol (Q4)
class RefillablePen(Protocol):
    def change_refill(self, refill: Refill) -> None: ...

# Concrete pens
class GelPen(Pen):
    def __init__(self, brand, name, refill: Refill):
        super().__init__(brand, name, SmoothWriting())
        self._refill = refill
    def change_refill(self, refill: Refill): self._refill = refill

class BallPen(Pen):
    def __init__(self, brand, name, refill: Refill):
        super().__init__(brand, name, RoughWriting())
        self._refill = refill
    def change_refill(self, refill: Refill): self._refill = refill

class FountainPen(Pen):
    def __init__(self, brand, name, ink: Ink, nib: Nib):
        super().__init__(brand, name, SmoothWriting())
        self._ink, self._nib = ink, nib

# Callers ask for the CAPABILITY they need, not the concrete class
def restock_in_bulk(pens: list[RefillablePen], r: Refill) -> None:
    for p in pens: p.change_refill(r)

# mypy errors at the call site if you pass a FountainPen.

Full runnable version: code/01_pen_final_design.py. Run it; tweak it; see how the design supports each requirement.

Why TicTacToe

First end-to-end LLD problem — small enough to ship, rich enough to use 3 patterns

A classic machine-coding problem. Common at Flipkart, Cred, Razorpay, Zomato. Two reasons we pick it as our first problem:

⏳
Small enough to ship

A complete working version (CLI, 2 humans, 3×3 board, win & draw detection) is about 80 lines of Python.
You can comfortably do it in 60 minutes — leaving 30 for trade-offs and AI.

Rich enough to use 3 patterns

Strategy — the win-rule (any line of N) is the open variable; swap it to support 4-in-a-row, Connect Four, or N×N boards.
State — the Game has a lifecycle (in-progress → won → over).
Factory (later) — making AI vs human players.

Interview-flag: extension questions

Interviewers love asking "now add …": N×N board, third player, time-limited turns, undo, AI opponent.
Your design has to make each one easy. We'll show how.

This class is the DESIGN. Steps 1–4 of the playbook: clarify, requirements, entities, APIs. Plus the patterns we'll reach for. Next class (LLD-23) is steps 5–7: we code it live and run trade-offs.

The second sweep — feature suggestions that score points

After the core questions, offering features the interviewer didn't mention is a strong signal — it shows product sense. You're not committing to build them; you're showing you see them. Five classics for any turn-based game:

⏳ Timed moves

"Do we want to time a move — skip the turn or declare the other player winner if it doesn't happen within X seconds?"

↶ Undo

"Do we want to support undoing the last move?" (This is also the classic side-assignment — think Memento / a move stack.)

👓 Spectators

"Can some users just watch without playing?" (Observer pattern territory — watchers subscribe to move events.)

📊 Analytics

"Do we store history — past games, who played which move when?" (Changes persistence answer in Step 7.)

🏆 Tournaments

"Support for tournaments — a set of matches between registered players?" (This is why Player must outlive a Game — aggregation!)

Default answers we'll use in this design:
  • Board: generalised N×N with K-in-a-row to win (default 3×3, K=3 — the classic).
  • Players: exactly 2 for now, but represented so more players is one new instance — not a rewrite.
  • Opponents: human-vs-human for the MVP. Bots (with difficulty levels) are the Step-7 extension — we design the door for them now.
  • Ways to win: K-in-a-row today, but the win rule is pluggable (you'll see why in Entities).
  • Output: CLI, one game per process. Timed moves, undo, spectators, analytics, tournaments — named, parked in future scope.

Quiz — Interviewer says "3×3 only, K=3, 2 players, CLI." You have 60 minutes left to design + code. What do you do?

D is right. Honour the scope (3×3 for the MVP) but design so the trade-off discussion at minute 80 doesn't need a rewrite. Use BOARD_SIZE = 3 and WIN_LEN = 3 as constants you reference everywhere. Hard-coding (A) makes the Step-7 extension answer ("I'd just change two constants") false. Pre-emptively building N×N (B) loses time on a feature that wasn't asked for. C abandons the requirement.

FR-1 🤔 What does the game get played ON? Pin down the geometry first. ▾
The game is played on an N×N board of cells. The classic version uses a 3×3 board.
What it seeds: the nouns board and cell. Board has state (the grid) and behaviour (place / is-it-full / show) → a class. The cell looks like one value (symbol-or-empty) — until the obstacle variant ("some cells start BLOCKED") gives it a second fact. Then Cell is a class too: symbol + blocked, with is_empty() / can_place() as its rules. "Classic is 3" → BOARD_SIZE = 3 as a constant. The full reasoning is in Entities below.
FR-2 🤔 WHO plays — and what distinguishes one player from the other? ▾
Two players play the game, and each player is allotted a distinct symbol.
What it seeds: Player (name + symbol travelling together → dataclass) and Symbol (small named set → enum). The word distinct hides a validation: Game.__init__ must reject two players with the same symbol. Writing players as a list (not player_x/player_o fields) makes the N-player extension free.
FR-3 🤔 Simulate one round in your head. What hidden state shows up? ▾
The players take turns alternately, and any player can make the first move.
What it seeds: the hidden state is whose turn is it now — no noun in the prompt names it. It becomes a turn pointer in Game: an index into the players list, advanced with (i + 1) % len(players). That modulo is why 3 players cost nothing. "Any player can start" is one constructor parameter, not a feature.
FR-4 🤔 What could a user do WRONG? Every game needs a rejection rule. ▾
A player can place their symbol only in an empty cell that is inside the board.
What it seeds: InvalidMoveError, and a placement decision: bounds + emptiness belong to Board.place() (it owns the grid); wrong-turn and game-over belong to Game.make_move() (it owns the flow). A rejected move must NOT flip the turn. Try it live — the demo just paused; click an occupied cell.
FR-5 🤔 How does someone WIN? This sentence defines the game itself. ▾
The first player to get K consecutive symbols in a row, a column, or a diagonal wins the game.
What it seeds: notice the sentence contains no noun — it's a rule, and rules that vary across the family are Strategy candidates. WinRule (abstract) + KInARowRule(k). Writing K decouples win length from board size; Connect Four, Gomoku, misère are each one new class, zero edits to Game.
FR-6 🤔 Win is one ending. Keep asking "how does it END?" until you've found them all. ▾
If the board becomes full and nobody has won, the game ends in a draw.
What it seeds: the third state — and therefore GameStatus as an enum (IN_PROGRESS / WON / DRAW), not an is_over bool. Plus an ordering rule: check the win before checking fullness, because a winning move can also fill the board. The draw is the ending candidates forget — until their demo loops forever.
FR-7 🤔 Who ELSE could be making the moves — beyond humans? ▾
A player can be either a human or a bot, and every bot has a difficulty level.
What it seeds: Player becomes an abstract contract with choose_move(board); HumanPlayer reads input; BotPlayer carries a difficulty and delegates to a MoveStrategy (Random → Minimax — difficulty maps to strategy, killing the if-else tree). Profile data lives in a shared User so concurrent games don't copy profile images (Flyweight). Game never knows which kind it's talking to.
FR-8 🤔 Walk the player's experience: I move… then what do I look at? ▾
After every move, the players can see the current state of the board.
What it seeds: a render() kept separate from make_move(). Game and Board compute; the presentation layer displays. Print inside the mutation and the engine is welded to the CLI — keep them apart and the same Game drives a web UI tomorrow.

Non-functional requirements — also full sentences

  • The game runs in memory, in a single process, on a single thread.
  • The board defaults to 3×3 with K = 3; both numbers live as constants in exactly one place.
  • Adding a new way to win means adding one new class — never editing existing ones.
  • Moves and commands are entered through a CLI — and because of FR-8's boundary, the engine itself never knows that.

Entities (10–18 min) — walking the eight FRs in order

Don't list classes from memory — derive them. Take the eight requirement sentences you just wrote, in order. Every FR donates something to the design. For each noun we meet, we make one of three calls:

🏘️ Class

It has state + behaviour of its own. Other code talks to it.

🏷️ Field

It's a single value that belongs to something else. No behaviour.

🔢 Enum

It's a value from a small fixed set. Named, typo-proof, exhaustive.

And watch for the FRs with no noun at all — they donate the other things a design is made of: a method, a rule object, or an exception.

FR-1 — "The game is played on an N×N board of cells. The classic version uses a 3×3 board."

Decision quiz — does Cell deserve to be a class? Yes or no?

Yes — in OUR design. But the honest answer is "it depends on the requirements", and that's the lesson. Run the three-way test twice and watch the answer flip. Vanilla Tic-Tac-Toe: a cell is exactly one fact ("empty, X, or O") — a value, Symbol | None in the grid, and a Cell class would be speculative bloat; "No" would be correct. Our design took the obstacle variant from the feature sweep — some cells start BLOCKED and can never be played — so a cell now carries TWO facts (symbol, blocked) and the rules relating them: is_empty() is "no symbol AND not blocked"; can_place() must refuse blocked cells even when symbol-free. State + behaviour → class. The tempting halfway houses both fail: a bare dataclass with no methods leaves the invariant logic to leak into Board, and Board.is_empty(r, c) is feature envy — every new cell fact (frozen? bonus?) would edit Board again. (Chess flips this same test even harder — see the companion doc.)

💬 Reveal the discussion

▾

Two nouns. The board clearly has state (the N×N contents) and behaviour (place a symbol, check fullness) — a Board class, no debate. "Classic is 3" → BOARD_SIZE = 3 as a constant. The cell looks like one value (symbol-or-empty)… but mid-design the interviewer adds a wrinkle: "support an obstacle variant — some cells start BLOCKED and can never be played." Re-run the three-way test:

FR-1 donates: Board ✔ class  ·  Cell ✔ class (symbol + blocked → is_empty() / can_place())  ·  BOARD_SIZE ✔ constant

FR-2 — "Two players play the game, and each player is allotted a distinct symbol."

Think first: only two marks exist (X and O), so even a boolean technically works. Which representation do you pick for the mark — and what's your argument against the alternatives?

💬 Reveal the discussion

▾

Player bundles two values that always travel together (a name and a mark) — small state, no behaviour yet, so a @dataclass. The word distinct hides a validation rule: whoever assembles the game must reject two players with the same mark. The interesting decision is the mark itself. Four candidates:

# candidate 1 — boolean
is_x: bool                  # True means X, False means O

# candidate 2 — string
symbol: str                  # "X" or "O"... or "x"? " X"? "ex"?

# candidate 3 — int constant
symbol: int                  # 1 = X, 2 = O (0 = empty?)

# candidate 4 — enum
class Symbol(Enum):
    X = "X"
    O = "O"

The pick: the enum. Walk the failures of each candidate:

  • Boolean (A): place(0, 0, True) — true what? Call sites lose all meaning. And the moment the interviewer says "extend to 3 players" (your clarifying question 2 already raised it!), a bool literally cannot represent the third player — you'd rewrite every signature. A bool that encodes a choice between named things is a smell even when there are only two of them today.
  • String (B): "X" vs "x" vs " X" all type-check fine and fail silently at runtime. Nothing stops board.place(0, 0, "banana").
  • Int (C): magic numbers — quick, is 1 X or O? Every reader must memorise the mapping.
  • Enum (D): Symbol.X is self-documenting, a typo is an AttributeError at the line that's wrong, you can iterate for s in Symbol, and the generalised FR-2 (up to N−1 players choosing symbols) is "add members", not "redesign".

The general rule: a value drawn from a small named set should be an enum the moment two pieces of code need to agree on it — even if today the set has only two members.

FR-2 donates: Player ✔ dataclass  ·  Symbol ✔ enum  ·  "distinct" ✔ a validation in Game.__init__

FR-3 — "The players take turns alternately, and any player can make the first move."

💬 Reveal the discussion

▾

Is "turn" a class? Run the test: a turn has no state of its own beyond whose it is, and no behaviour. It's the textbook field — an index into the players list, owned by Game, advanced with (i + 1) % len(players). That modulo is why your 3-player extension costs nothing. "Any player can make the first move" is one constructor parameter (starting_index=0), not a feature. Not every concept in the requirements is a class — alternation is one int.

FR-4 — "A player can place their symbol only in an empty cell that is inside the board."

💬 Reveal the discussion

FR-5 — "The first player to get K consecutive symbols in a row, a column, or a diagonal wins the game."

Decision quiz — where does the win-checking logic live?

A is right. This is the Strategy decision from LLD-19/21, made on evidence rather than reflex: the interviewer's favourite follow-ups ("now Connect Four", "now 5-in-a-row") all vary this exact logic and nothing else. Pulling it into WinRule.winner(board) → Symbol | None means each follow-up is one new class and zero edits to Game — the OCP answer you give at minute 80. B is genuinely fine for a game that will never change — but you already know it will, because you asked in Step 1. C puts game policy inside a dumb container; Board should know "what's at (r,c)", not "what winning means" — mixing those means Connect-Four-Board and TicTacToe-Board diverge for no reason. D loses the swap-ability (you'd pass functions around — workable in Python, but the class form carries config like k more cleanly).

💬 Reveal the discussion

▾

The sentence that defines the game contains no noun — it's a rule. And your clarifying question 4 ("can there be different ways to win?") already told you this rule varies: Connect Four is "4 in a row with gravity"; Gomoku is "5 on a 15×15"; misère Tic-Tac-Toe is "3 in a row loses". Rules that vary across the family are Strategy candidates.

FR-5 donates: WinRule ✔ abstract class (Strategy)  ·  KInARowRule(k) ✔ default implementation  ·  WIN_LEN ✔ constant, decoupled from N

FR-6 — "If the board becomes full and nobody has won, the game ends in a draw."

👁️ Reveal the analysis

▾

The draw sentence smuggles in a hidden noun that never appears as a word: the game's status. With FR-5 the game could be playing or won; FR-6 adds a third outcome. The lazy encoding is a boolean:

✖ Boolean + nullable 
is_over: bool
winner:  Player | None

# 4 combinations representable:
# is_over=False, winner=None   ok (playing)
# is_over=True,  winner=Ajit   ok (won)
# is_over=True,  winner=None   ok (draw)
# is_over=False, winner=Ajit   ???  ← BUG STATE
✔ Enum 
class GameStatus(Enum):
    IN_PROGRESS = "in_progress"
    WON         = "won"
    DRAW        = "draw"

# exactly 3 states representable —
# the bug state cannot be expressed.

Decision quiz — is_over: bool technically works today. Why does the GameStatus enum still beat it?

B is right.
  • Count the states: FR-5 + FR-6 define three — playing, won, drawn. A bool holds two.
  • So the bool smuggles in a second field (winner) plus an unwritten rule: "winner only means something when is_over is True".
  • Unwritten rules get broken: is_over=False, winner=Ajit compiles, runs, and corrupts whatever reads it.
  • The enum makes that bug state unrepresentable — "make illegal states unrepresentable" is the most quotable line you can say in a design interview.
  • Why not the others: A is false (enums are marginally slower); C is false (bools work fine in dataclasses); D is made up.
  • General rule: more than two real states — or might ever become more (chess grows this enum to CHECKMATE / STALEMATE / RESIGNED) — reach for the enum on day one. Retrofitting after ten if game.is_over call sites is a refactor; starting with it is free.
FR-6 donates: GameStatus ✔ enum (IN_PROGRESS, WON, DRAW)  ·  an ordering rule ✔ check win before full

FR-7 — "A player can be either a human or a bot, and every bot has a difficulty level."

💬 Reveal the discussion

▾

This FR upgrades Player from a dataclass into an abstract contract: choose_move(board) → (row, col). Two children: HumanPlayer reads the move from input; BotPlayer carries a difficulty: Difficulty and delegates to a MoveStrategy — RandomMove for EASY, MinimaxMove for HARD. Difficulty maps to a strategy object, so there is no if-else tree inside the bot (the SRP/OCP fix from the reference design). Game calls choose_move() on whoever's turn it is and genuinely cannot tell human from bot. Human profile data (name, email, photo) stays in a shared User object so fifty concurrent games don't copy fifty profile images (Flyweight).

FR-7 donates: Player ✔ abstract contract (choose_move)  ·  HumanPlayer / BotPlayer ✔ classes  ·  Difficulty ✔ enum  ·  MoveStrategy ✔ Strategy (Random → Minimax)

FR-8 — "After every move, the players can see the current state of the board."

💬 Reveal the discussion

▾

Also no new entity — FR-8 donates a method, render(), and a boundary: presentation stays OUT of make_move(). Game and Board compute; whoever called them decides how to show it. Weld a print() into the mutation path and your engine is married to the CLI — keep them apart and the same Game drives a web UI tomorrow. (This is the "separation of concern" line item interviewers literally have on their rubric.)

FR-8 donates: Board.render() / Game.render() ✔ methods  ·  a boundary ✔ logic computes, presentation displays

🎲 Snake & Ladder — the FRs through the same framework

▾

Functional requirements (vs the Tic-Tac-Toe FR it echoes):

  1. The game is played on a linear board of 100 numbered positions. (≈ FR-1, but 1-D — only the geometry changes)
  2. Two to six players play the game, and each player has a token on the board. (≈ FR-2 — more players; a token replaces the symbol)
  3. The players take turns in a fixed order, and each turn consists of rolling a die and moving forward by the rolled amount. (≈ FR-3 + the BIG difference: chance replaces choice — no (row, col) input exists)
  4. A player who lands at the bottom of a ladder moves to its top, and a player who lands on a snake's mouth slides to its tail. (NEW — board-triggered jumps have no TTT equivalent)
  5. A player must land on the final position exactly to win; an overshooting roll leaves the token in place. (≈ FR-5 — but it's a movement rule, not a line-scan, and house rules vary → Strategy again)
  6. The first player to reach the final position wins, and the game ends immediately. (≈ FR-5/6 — and NO draw exists, so the status enum shrinks)
  7. After every turn, the players can see all token positions. (= FR-8, verbatim role)

Potential classes (run the same tests):

  • Game — identical orchestrator; the (i+1) % len(players) turn pointer is reused verbatim for 2–6 players.
  • Board — size + ONE jumps: dict[int, int] (a ladder is start < end, a snake is start > end).
  • Player — name + position: int. The Cell test, opposite answer: a position has no second fact, so it stays a number.
  • Dice — a class (not a function) so tests can inject a LoadedDice.
  • MovementRule Strategy — ExactLanding / OvershootAllowed / BounceBack house rules.
  • GameStatus — just IN_PROGRESS / WON. The enum shrinks; the structure stays.

♔ Chess — the FRs through the same framework

▾

Functional requirements (vs the Tic-Tac-Toe FR it echoes):

  1. The game is played on an 8×8 board of squares. (= FR-1, with N fixed)
  2. Two players play the game; one commands the white pieces and the other the black. (= FR-2 — colour plays the symbol's role)
  3. Each player starts with sixteen pieces of six kinds, and each kind of piece moves according to its own rule. (NEW — and it flips the cell-content question into a class hierarchy)
  4. The players take turns alternately, and white always moves first. (= FR-3, minus "any player can start")
  5. A player can move a piece only to a square permitted by that piece's rule, and a move may not leave their own king in check. (≈ FR-4 — validation grows from one check into the hardest 60% of the problem)
  6. A piece that moves onto a square occupied by an opponent's piece captures it. (NEW)
  7. A player with no legal move while in check is checkmated and loses; with no legal move while NOT in check, the game is a stalemate draw. (≈ FR-5 + FR-6 — the endings multiply, so the status enum GROWS)
  8. After every move, the players can see the board and the full move history. (≈ FR-8 + history is now a requirement — notation and undo come built-in)

Potential classes (same tests, two answers flip):

  • Game — same orchestrator; end-check delegates to the pieces.
  • Board — 8×8 grid of Piece | None.
  • Piece — ABC + King / Queen / Rook / Bishop / Knight / Pawn: the square's occupant has colour, has-moved state AND its own movement logic — the Cell test answers YES loudly, and the one-WinRule idea multiplies into per-piece rules.
  • Square — a frozen value object (file, rank); chess code reads move(e2, e4), so naming the pair pays.
  • Move — dataclass with captured stored — undo, notation and repetition-detection all fall out of the history list.
  • Colour enum · GameStatus grown to CHECK / CHECKMATE / STALEMATE / DRAW… (this is why we never used a bool).
