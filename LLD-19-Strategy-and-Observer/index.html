Strategy & Observer

LLD-19 • First two behavioural patterns

When you find yourself writing if mode == "a": ... elif mode == "b": ..., the Strategy pattern is asking to be born. When you find yourself manually calling 5 things every time something changes, Observer is asking to be born. Behavioural patterns are the patterns of collaboration over time.

Recap — Prototype & Adapter

Quick Recall — plus two ideas we didn't get to

Standard recap of LLD-18 — and two variations we ran out of time for live: the Prototype Registry and the Adapter variations (Object Adapter vs Class Adapter, Two-Way Adapter). The quiz explanations teach the missed pieces in full so you can carry both into today's behavioural patterns.

🎯 First — the bits we did cover

Quiz 1 — When is Prototype the right tool?

"Stack Overflow's 'Ask Question' page boots a rich-text editor with syntax highlighting, markdown preview, tag autocomplete, and a duplicate-detection worker. Booting the editor takes ~600 ms. The same user often closes and reopens the editor several times during one visit (write a draft, switch tabs, come back, edit again, post). Each session needs its own draft state — but the heavy editor machinery is identical between sessions."

C is right. Two clues both point to Prototype + custom __deepcopy__:
  • "expensive once" + "several similar instances per visit" — the Prototype cost equation.
  • "per-session draft attached to the same machinery" — share the heavy read-only setup, isolate the small mutable state. That's Recipe 1 from code/11_deepcopy_override_recipes.py in LLD-18.
A is wrong because each session needs its own draft — one shared editor would mix drafts across opens. B and D answer different questions (too many params; which subclass).

What the answer looks like in code:

import copy

class RichTextEditor:
    def __init__(self):
        # The slow stuff — runs ONCE when the prototype is built (~600 ms)
        self.highlighter   = _load_syntax_highlighter()        # big, read-only
        self.preview       = _init_markdown_preview()
        self.tag_index     = _load_tag_autocomplete_index()    # big, read-only
        self.dup_worker    = _spawn_duplicate_detector()
        # The fast stuff — PER-SESSION mutable draft state
        self.draft_text: str           = ""
        self.cursor_position: int     = 0
        self.attached_tags: list[str]  = []

    def __deepcopy__(self, memo):
        new = RichTextEditor.__new__(RichTextEditor)   # skip __init__ — don't pay 600ms again
        # SHARE the heavy machinery by reference
        new.highlighter = self.highlighter
        new.preview     = self.preview
        new.tag_index   = self.tag_index
        new.dup_worker  = self.dup_worker
        # RESET per-session state so each clone starts empty
        new.draft_text       = ""
        new.cursor_position  = 0
        new.attached_tags    = []
        return new

    def clone(self) -> "RichTextEditor":
        return copy.deepcopy(self)             # <1 ms — just a shallow shell


# --- one-time setup on page load ---
prototype = RichTextEditor()      # 600 ms, paid ONCE

# --- each time the user opens the editor ---
session1 = prototype.clone()      # <1 ms, independent draft
session2 = prototype.clone()      # <1 ms, independent draft
session3 = prototype.clone()      # <1 ms, independent draft

session1.draft_text = "What is the difference between..."
session2.draft_text = "How do I configure CORS..."
# session1 and session2 have INDEPENDENT drafts
# but session1.highlighter IS session2.highlighter — same object
assert session1.highlighter is session2.highlighter   # True — shared
assert session1.draft_text != session2.draft_text     # True — isolated

The two-line summary of what __deepcopy__ does here: share what's safe to share (highlighter, preview, tag_index, dup_worker — they're read-only), isolate what must be per-clone (draft_text, cursor_position, attached_tags — mutable state belongs to the session). Cost: build once at 600 ms, clone in <1 ms.

Quiz 2 — A new vendor SDK shows up. Which is not a job for Adapter?

C is right. Adapter exists for interface mismatch. If both services already implement the same interface, swapping is just a dependency-injection refactor — no adapter needed. A, B, D all have a "we want X, they speak Y" interface gap, with one side outside our control.

🔎 We didn't get to — the Prototype Registry

When callers want clones by name — "spawn an orc", "give me a fresh welcome-email template", "instantiate the staging config" — you wrap the prototypes in a registry. The explanations below teach the pattern; the quizzes are the carrier.

Quiz 3 — You're designing Notion's "templates" feature

When a user types /template, they see a list of 20+ ready-made page templates (Meeting Notes, Project Brief, Daily Standup, …). Picking one inserts a fresh copy into their workspace. Two requirements from the product team:

  • Each inserted page must be independent — editing one doesn't affect the template or other inserted copies.
  • Adding a new template to the menu should not require shipping code — admins drop a template definition into a folder, restart the service, and it appears.

How should the codebase be structured?

B is right — and this is the Prototype Registry pattern.
The shape: 
class PrototypeRegistry:
    def __init__(self):
        self._prototypes: dict[str, Prototype] = {}

    def register(self, name: str, proto: Prototype) -> None:
        self._prototypes[name] = proto

    def get(self, name: str) -> Prototype:
        return self._prototypes[name].clone()   # fresh clone every time


# --- one-time setup ---
registry = PrototypeRegistry()
registry.register("meeting-notes", PageTemplate(blocks=[...]))
registry.register("project-brief", PageTemplate(blocks=[...]))

# --- usage from the /command menu ---
new_page = registry.get("meeting-notes")   # <1ms, fully independent clone
new_page.title = "2026-06-02 standup"

Why this beats a Factory Method:

  • Open for extension at runtime. Admins add new templates by calling register(...). With Factory Method you'd ship a code release.
  • Templates can be loaded from data. Read 20 template JSON files from disk on startup, build a PageTemplate from each, register by name. No code per template.
  • Construction is paid once. Heavy initialisation runs at registration time; clone() at insertion time is <1 ms.

The same pattern under different names: IDE "New file from template", game engine "spawn enemy by name", notification "fetch template by template_id". All are a Prototype Registry.

Prototype Registry — UML

Admin writes to the registry at startup (or whenever a new template lands on disk). Client reads a clone at every /command menu open. The two parties never see each other.

Quiz 4 — When is a Prototype Registry overkill?

B is right. Registry adds value when (i) construction is expensive (or data-driven), or (ii) the set of variants is dynamic/extensible. If both inequalities flip — cheap construction AND known-at-compile-time variants — a plain if/elif or a dict literal of factory functions is simpler. 
# Cheap + closed set — no registry needed
EMAIL_TEMPLATES = {
    "welcome":        lambda: EmailTemplate("Welcome!"),
    "reset_password": lambda: EmailTemplate("Reset link..."),
    "alert":          lambda: EmailTemplate("Alert!"),
}
msg = EMAIL_TEMPLATES["welcome"]()
Don't ceremonially apply Prototype Registry to every "lookup by string" problem. Reach for it when expense or extensibility justify it.

🔎 We didn't get to — Adapter variations

GoF describes two adapter flavours; in Python only one is idiomatic. There's also a "two-way" variant worth naming in interviews.

Quiz 5 — Two adapter implementations for the same job. Which one is the idiomatic Python choice?

Both wrap a vendor RazorpayClient SDK to expose our in-house PaymentGateway interface. Both have a working pay(). They differ only in how they get hold of the SDK.

Approach 1

class RazorpayAdapter(PaymentGateway, RazorpayClient):
    def pay(self, amount, currency):
        order  = self.create_order(int(amount * 100), "rcpt")
        result = self.capture_payment(order["id"])
        return PaymentResult(success=result["status"] == "captured", ...)

Approach 2

class RazorpayAdapter(PaymentGateway):
    def __init__(self, key, secret):
        self._client = RazorpayClient(key, secret)

    def pay(self, amount, currency):
        order  = self._client.create_order(int(amount * 100), "rcpt")
        result = self._client.capture_payment(order["id"])
        return PaymentResult(success=result["status"] == "captured", ...)

Which one is the idiomatic Python adapter?

B is right. Approach 1 is a Class Adapter (multiple inheritance); Approach 2 is an Object Adapter (composition). The latter is the idiomatic Python choice.

Approach 1 — Class Adapter (the brittle one)

  • Adapter is-a both Target and Adaptee: gains all of RazorpayClient's methods through inheritance.
  • Leaks the entire vendor surface: create_order, capture_payment, utility.verify_webhook_signature, … are now public on our adapter. Any caller can bypass pay() and reach the raw SDK — defeating the whole point of containing it.
  • Brittle MRO: if RazorpayClient has its own base classes, multiple inheritance interacts in surprising ways. If RazorpayClient v2 adds an __init__ param, the adapter constructor signature changes silently.
  • Tied to one specific class — can't swap RazorpayClient for a mock or subclass without changing the adapter's bases.

Approach 2 — Object Adapter (the idiomatic one)

  • Adapter has-a Adaptee: holds a RazorpayClient as a private field and delegates.
  • Only pay() is public — the SDK is sealed behind _client. The vendor surface stops at the adapter boundary.
  • Works for any RazorpayClient subclass or mock — just inject a different object in tests.
  • Composition-over-inheritance — the textbook Python idiom for this exact case.

The leak is the killer. The whole reason we built an Adapter was to contain the vendor SDK in one file. Class Adapter undoes that the moment it inherits.

Two adapter flavours — UML

Quiz 6 — A currency-input form has a "USD" field and an "INR" field. Editing either one updates the other. Which variation fits?

B is right.

One-line refresher — what an Adapter does:

An Adapter is a small wrapper that sits between your code (which speaks one interface) and some other class (which speaks a different interface), translating calls so the two can talk. The wrapper exposes the interface your code expects (the Target) and holds an instance of the foreign class (the Adaptee) which it delegates to. Most adapters are one-way: your code calls in → the wrapper translates → the adaptee responds.

Standard one-way Adapter

Two-Way Adapter is the GoF variant where the wrapper implements both interfaces so calls can flow in either direction. Each side thinks it's the host. 

class USDINRPriceField:
    def __init__(self, rate: float):
        self._usd: float = 0.0
        self._rate = rate

    # direction 1: someone types USD → expose INR
    def set_usd(self, usd):   self._usd = usd
    def get_inr(self):       return self._usd * self._rate

    # direction 2: someone types INR → expose USD
    def set_inr(self, inr):   self._usd = inr / self._rate
    def get_usd(self):       return self._usd

When is it actually worth it? Mostly a curiosity in Python — almost always the right answer is two one-way adapters, not one two-way. Use it when both sides genuinely drive the conversation (form fields, ORM bridge adapters where each side thinks it's the host). Naming this variant in an interview signals you've read the GoF chapter.

Two-Way Adapter — UML

When the user types into the USD field, the adapter stores the USD value and the INR field reads it through get_inr(). When the user types into INR, the adapter stores via set_inr() and the USD field reads through get_usd(). One source of truth (_usd), two interfaces.

Part 1 — Strategy

Strategy — swap the algorithm without touching the caller

When the same job can be done several different ways, hand the caller a strategy object instead of an if/elif chain.

🤯 The problem — the if/elif chain that won't stop growing

Sneha is building a discount engine for an e-commerce app. The first version was simple:

def calculate_discount(order, discount_type: str) -> float:
    if discount_type == "none":
        return 0.0
    elif discount_type == "percentage":
        return order.total * 0.10
    elif discount_type == "flat":
        return 50.0

Three months later, the function looks like this:

def calculate_discount(order, discount_type: str, user, coupon) -> float:
    if discount_type == "none":
        return 0.0
    elif discount_type == "percentage":
        return order.total * 0.10
    elif discount_type == "flat":
        return 50.0
    elif discount_type == "bulk":
        if order.item_count >= 10:   return order.total * 0.15
        elif order.item_count >= 5: return order.total * 0.08
        return 0.0
    elif discount_type == "loyalty":
        tier = user.get_loyalty_tier()                           # DB call
        return {"silver": 0.05, "gold": 0.12, "platinum": 0.20}[tier] * order.total
    elif discount_type == "coupon":
        if coupon.expired():               return 0.0
        if coupon.type == "percent":    return order.total * coupon.value
        if coupon.type == "flat":       return coupon.value
    elif discount_type == "first_time":
        if user.order_count() == 0:        return 100.0
        return 0.0
    elif discount_type == "festival":
        ...
    # 11 more elif branches

Three things have gone wrong:

  • Open-Closed violation. Every new discount type means editing this function — risking regressions in the other branches.
  • SRP violation. The function knows about 11 different domains: bulk pricing, loyalty tiers, coupon validation, first-time-buyer rules, festival promotions, …
  • Testability collapse. Unit testing one branch means setting up a full order, user, coupon object even when only one of the three is relevant to that branch.

The shape of the problem: the same job (compute a discount) has many different algorithms. Each algorithm has its own data needs, its own validation, and its own evolution timeline. They're being conflated into one function.

🪟 The pattern — one interface, many algorithms

Strategy's idea, in one sentence:

Define a family of algorithms behind a common interface. Hand the caller an algorithm object — not a string telling them which branch to take.

Three roles to name:

The Context delegates "how" to the Strategy — without knowing which one.

Sneha's discount engine, rewritten:

from abc import ABC, abstractmethod

# --- 1. Define the common interface ---
class DiscountStrategy(ABC):
    @abstractmethod
    def calculate(self, order, user) -> float: ...


# --- 2. One concrete class per algorithm ---
class NoDiscount(DiscountStrategy):
    def calculate(self, order, user): return 0.0

class FlatDiscount(DiscountStrategy):
    def __init__(self, amount: float): self.amount = amount
    def calculate(self, order, user): return self.amount

class LoyaltyDiscount(DiscountStrategy):
    TIER_RATE = {"silver": 0.05, "gold": 0.12, "platinum": 0.20}
    def calculate(self, order, user):
        return order.total * self.TIER_RATE.get(user.get_loyalty_tier(), 0)

class CouponDiscount(DiscountStrategy):
    def __init__(self, coupon): self.coupon = coupon
    def calculate(self, order, user):
        if self.coupon.expired(): return 0.0
        return order.total * self.coupon.value if self.coupon.type == "percent" else self.coupon.value


# --- 3. The Context holds whichever strategy was chosen ---
class Checkout:
    def __init__(self, discount: DiscountStrategy):
        self._discount = discount

    def total_after_discount(self, order, user) -> float:
        return order.total - self._discount.calculate(order, user)


# --- usage ---
checkout = Checkout(discount=LoyaltyDiscount())
final = checkout.total_after_discount(order, user)
Before

17-branch if/elif. New discount = edit existing code. Test = construct everything.

After (Strategy)

One class per algorithm. New discount = new class, no edits. Test each algorithm in isolation.

The win is OCP — for real this time. Adding FestivalDiscount means writing one new class. Nothing else in the codebase changes. The 17-branch original was the textbook OCP violation; Strategy is the textbook OCP fix.

🎢 Three ways to wire up a Strategy

"Hand the caller an algorithm object" leaves when open. Three idioms, each shown in code with its pros & cons:

🏭
Wiring 1 — Constructor injection

Strategy is decided once, at object creation. The Context holds it for its lifetime.

class Checkout:
    def __init__(self, discount: DiscountStrategy):
        self._discount = discount

    def total(self, order, user):
        return order.total - self._discount.calculate(order, user)

# usage — pick once at construction
checkout = Checkout(discount=LoyaltyDiscount())
checkout.total(order, user)
Pros
  • Dependency injection-friendly — trivial to mock in tests
  • Strategy can't change unexpectedly mid-call — predictable behaviour
  • Most common shape; reads naturally to most developers
Cons
  • If the strategy should change later, you have to construct a new Context
  • Bad fit when the strategy is request-scoped (you'd build a new Checkout per request)
🔒
Wiring 2 — Setter / property

Strategy can be swapped any time after the Context is created.

class Checkout:
    def __init__(self):
        self._discount: DiscountStrategy = NoDiscount()

    @property
    def discount(self): return self._discount

    @discount.setter
    def discount(self, value: DiscountStrategy):
        self._discount = value

    def total(self, order, user):
        return order.total - self._discount.calculate(order, user)

# usage — swap mid-flight
checkout = Checkout()
checkout.total(order, user)              # no discount
checkout.discount = CouponDiscount(coupon)  # user applies a coupon
checkout.total(order, user)              # now uses the coupon
Pros
  • Same Checkout object across many requests — just swap the strategy
  • Natural fit for UI state machines (user picks a discount mid-checkout)
Cons
  • Strategy can change silently — harder to reason about; bugs from one place setting the strategy and another forgetting
  • Threading hazard if Checkout is shared and one thread mutates discount while another is computing
🎯
Wiring 3 — Per-call argument

Strategy is passed in with each method call. The Context holds no strategy at all.

class Checkout:
    @staticmethod
    def total(order, user, discount: DiscountStrategy):
        return order.total - discount.calculate(order, user)

# usage — strategy is request-scoped
Checkout.total(order, user, discount=LoyaltyDiscount())
Checkout.total(order, user, discount=CouponDiscount(c))
Pros
  • Stateless — safest under concurrency; the Context isn't carrying anything
  • Natural for one-off requests where each call's strategy is computed from request data
  • Exactly the shape sorted(items, key=...) uses
Cons
  • Strategy must be passed at every call site — risks repetition / inconsistency
  • Doesn't fit if the strategy carries setup cost (you'd reconstruct it per call)

In Python a Strategy is often just a callable — no class required:

# Strategy as a function — Pythonic when the algorithm has no state
def total(order, user, discount=lambda o, u: 0.0) -> float:
    return order.total - discount(order, user)

total(order, user, discount=lambda o, u: o.total * 0.10)   # 10% off

# Same idea as sorted(...)'s key= parameter:
sorted(items, key=lambda i: i.price)         # Strategy: price-key
sorted(items, key=lambda i: i.rating)        # Strategy: rating-key
sorted(items, key=operator.attrgetter("date"))# Strategy: date-key

Python's stdlib uses Strategy everywhere — usually as plain callables. Each of these stdlib functions takes a strategy object (a function) that parameterises the algorithm. When asked "give a Strategy example you've used", these are all valid answers.

One snippet per stdlib Strategy — what's the algorithm, what's the parameter?

1. sorted(items, key=…) — the algorithm is "sort"; the strategy decides by what

products = [{"name": "A", "price": 100, "rating": 4.2},
            {"name": "B", "price": 50,  "rating": 4.8}]

sorted(products, key=lambda p: p["price"])     # cheapest first
sorted(products, key=lambda p: -p["rating"])  # highest-rated first

The mergesort algorithm doesn't change — only the comparison key. Two strategies (price-key, rating-key), one sort.

2. min(items, key=…) / max(items, key=…) — reduce-to-one with a chosen metric

max(products, key=lambda p: p["rating"])         # best-rated product
min(employees, key=lambda e: e.join_date())     # most senior
max(words, key=len)                              # longest word

The algorithm ("scan once, keep the extremum") is fixed. The strategy answers "extremum of what?"

3. filter(predicate, items) — "keep" / "drop" rule, decided per call

list(filter(lambda p: p["price"] < 100, products))  # cheap items
list(filter(str.isdigit, ["42", "hi", "7"]))       # keep digit strings

Same iteration. Different predicate strategy → different surviving set.

4. functools.reduce(op, items, initial) — fold with a chosen combiner

from functools import reduce
import operator

reduce(operator.add, [1, 2, 3, 4], 0)              # sum  → 10
reduce(operator.mul, [1, 2, 3, 4], 1)              # product → 24
reduce(lambda a, b: a if a > b else b, nums)    # max via fold

Reduce always walks left-to-right and threads an accumulator. The strategy (op) decides what "combine" means — add, multiply, max, set-union, …

5. heapq.nlargest(n, items, key=…) — top-N by chosen metric

import heapq

# Top 3 most expensive products
heapq.nlargest(3, products, key=lambda p: p["price"])

# Top 5 slowest endpoints from a metrics dump
heapq.nlargest(5, endpoints, key=lambda e: e.p99_ms)

The algorithm (maintain a min-heap of size N, push/pop) is fixed. The strategy says "largest by what?".

The pattern that ties all five together: each function has a fixed algorithm (sort / scan-for-extremum / filter / fold / top-N heap) and one open parameter — the strategy. Swapping the strategy doesn't change the algorithm; it changes the question the algorithm answers. That's exactly what Strategy means.

🌐 Strategy in the wild

🧠 ML training loops — swap optimizers

▼

PyTorch's torch.optim ships SGD, Adam, AdamW, RMSprop, … — all implementing the same step() / zero_grad() interface. The training loop holds whichever optimizer was constructed; researchers swap optimizers by changing one line. The training loop never knows.

# Optimizer = the Strategy. Training loop = the Context.
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
# or torch.optim.SGD(...) / AdamW(...) — same interface

for batch in data:
    optimizer.zero_grad()
    loss = forward(model, batch)
    loss.backward()
    optimizer.step()         # the Strategy's algorithm runs here

📚 Compression libraries — pick gzip vs brotli vs zstd

▼

HTTP servers (Nginx, Caddy) and CDNs accept a list of compression algorithms — each one a Strategy implementing compress(bytes) → bytes. The same response goes through whichever algorithm matches the client's Accept-Encoding.

🏪 Spotify's "shuffle" — pick a queueing algorithm

▼

Spotify's queue accepts pluggable shuffle strategies: random shuffle, smart shuffle (interleaves new + familiar), DJ mode (transition-aware). The player holds whichever one is active; switching shuffle modes swaps the strategy object — no other code changes.

🛒 E-commerce checkout — pricing rules per region

▼

Amazon / Flipkart pricing differs by country (tax included? loyalty points? GST? state-specific levies?). A PricingStrategy per region keeps the checkout code clean — checkout.set_pricing(IndiaPricing()) at session start.

⚠️ Pitfalls — quiz-driven

Quiz — Which of these is the WRONG candidate for Strategy?

C is right — classic over-engineering. Strategy earns its keep when (i) there's a real family of algorithms with meaningful differences, AND (ii) adding new variants is plausible in the foreseeable future. "We might want to vary x + 1 later" is not a real reason — it just buries a primitive operation behind ceremony. YAGNI: introduce Strategy when you have 2-3 actual variants in hand, not in case you might.

Quiz — Two pricing strategies. Which interface design is better?

Both versions compute the same total. Pick the one you'd ship.

Design A

class PricingStrategy(ABC):
    @abstractmethod
    def price(self, checkout) -> float: ...

class RegularPricing(PricingStrategy):
    def price(self, checkout):
        return checkout.cart.total + checkout.shipping.cost - checkout.applied_coupon.value

class FestivalPricing(PricingStrategy):
    def price(self, checkout):
        base = checkout.cart.total * 0.9
        return base + checkout.shipping.cost

Design B

class PricingStrategy(ABC):
    @abstractmethod
    def price(self, subtotal: float, shipping: float, coupon_value: float = 0.0) -> float: ...

class RegularPricing(PricingStrategy):
    def price(self, subtotal, shipping, coupon_value=0.0):
        return subtotal + shipping - coupon_value

class FestivalPricing(PricingStrategy):
    def price(self, subtotal, shipping, coupon_value=0.0):
        return subtotal * 0.9 + shipping
B is right. Design A passes the whole Context to every strategy; Design B declares exactly what each strategy consumes. Three concrete reasons B is better:

1. Coupling surface. Design A's strategies "know" that Checkout has cart.total, shipping.cost, applied_coupon.value. Rename applied_coupon to coupon, or restructure shipping into a list, and every strategy breaks — even FestivalPricing which doesn't use the coupon field. Design B's strategies only break if the things they actually consume change.

2. Testability. To unit-test a Design A strategy you need a full Checkout object with cart, shipping, applied_coupon all populated — even when testing a strategy that uses only one of them. With Design B, you call strategy.price(100, 10) with three floats. No mocks, no fixtures.

3. Reusability. Design B's RegularPricing doesn't care whether it's being used inside a Checkout, an Estimate, or a Quote — any caller with three numbers can use it. Design A's strategies are bound to one specific class shape.

Same trap shows up in other patterns:

  • Observer: handlers that take the whole Subject vs handlers that take a small frozen Event — same coupling argument.
  • Command: a Command that reaches back into the Invoker for its parameters vs one that holds its parameters as constructor args.
  • Builder: a step that mutates the half-built Product directly vs one that just returns a small value the Builder applies.

The general rule: when designing an interface someone else will implement, ask "what does the minimum implementation actually need to read?" — and pass only that. Anything wider creates coupling that doesn't earn its keep.

✅ When Strategy earns its keep

Use Strategy when
  • You have an if/elif chain over a "mode" parameter that's grown past 3 branches
  • Each branch has its own dependencies (different DB tables, different external calls)
  • You expect new variants to be added by future-you or by other teams
  • You want each algorithm testable in isolation
Skip Strategy when
  • Two short branches — an if/else is clearer than a class hierarchy
  • The "variants" are all the same algorithm with different constants — pass a parameter instead
  • The variant is determined globally and never changes — a config flag works
  • You're inventing variants that don't exist yet (YAGNI)
Part 2 — Observer

Observer — one event, many reactions

When one object's state change must ripple to N listeners, neither side should know about the other. The Subject keeps a list; the Observer just registers.

🤯 The problem — "when X happens, also do Y, Z, A, B, …"

Aryan is wiring up order processing. When an order moves to PAID, four things must happen:

  • Send a confirmation email to the customer
  • Notify the warehouse to start fulfilment
  • Update the analytics service with the conversion
  • Award loyalty points to the customer's account

First draft:

class Order:
    def mark_paid(self):
        self.status = "PAID"
        self.save()
        # All the things that have to happen:
        email_service.send_confirmation(self.customer, self)
        warehouse_service.queue_fulfilment(self)
        analytics.track_conversion(self)
        loyalty_service.award_points(self.customer, self.total)

Six months later, the list has grown to nine downstream effects (fraud check, inventory decrement, partner commissions, …) and the Order class has become a directory of every other team's code. Three things have gone wrong:

  • SRP violation. The Order class knows about email, warehouse, analytics, loyalty, fraud, inventory, …
  • Tight coupling. Changing the analytics service signature requires editing Order. Adding a new "on paid" effect means a code review on the Order class.
  • Testing nightmare. Unit-testing mark_paid() requires mocking all four (later nine) services.

The shape of the problem: Order's only real job is to manage its own state. But it's accumulating everyone else's reactions to its state changes. The right people to know "Order became PAID" are the listeners — not the Order itself.

🪟 The pattern — the Subject publishes; Observers subscribe

Observer's idea, in one sentence:

The Subject keeps a list of Observers. When its state changes, it loops through the list and notifies each. Neither side knows the other's identity beyond the agreed interface.

Two roles:

Subject
Maintains the list of observers
Emits change events

Aryan's order code, rewritten:

from abc import ABC, abstractmethod

# --- 1. Observer interface ---
class OrderObserver(ABC):
    @abstractmethod
    def on_paid(self, order) -> None: ...


# --- 2. Concrete observers, each with one job ---
class EmailObserver(OrderObserver):
    def on_paid(self, order):
        email_service.send_confirmation(order.customer, order)

class WarehouseObserver(OrderObserver):
    def on_paid(self, order):
        warehouse_service.queue_fulfilment(order)

class AnalyticsObserver(OrderObserver):
    def on_paid(self, order):
        analytics.track_conversion(order)


# --- 3. Subject maintains the list ---
class Order:
    def __init__(self):
        self._observers: list[OrderObserver] = []

    def subscribe(self, observer: OrderObserver):
        self._observers.append(observer)

    def unsubscribe(self, observer):
        self._observers.remove(observer)

    def mark_paid(self):
        self.status = "PAID"
        self.save()
        # Notify — Order knows nothing about WHO is listening
        for obs in self._observers:
            obs.on_paid(self)


# --- usage: wire up reactions at app startup ---
order = Order()
order.subscribe(EmailObserver())
order.subscribe(WarehouseObserver())
order.subscribe(AnalyticsObserver())
# Adding a new effect = .subscribe(NewObserver()) — Order untouched

order.mark_paid()    # all three observers fire
Before

Order hard-codes every downstream effect. Adding one = editing Order.

After (Observer)

Order just calls self._observers. Adding effects = registering a new observer at startup.

🎢 Push vs Pull — what does the Subject hand the Observer?

Two conventions for what the Subject puts in the update(...) call:

 PushPull
What gets passedThe data the Observer needs: obs.on_paid(self.total, self.customer)Just the Subject: obs.on_paid(self) — Observer reaches back for what it wants
Subject knows…What each Observer cares aboutNothing — passes itself
Observer knows…Nothing about the Subject's internalsSubject's full API
When push winsStable event shape, many observers—
When pull wins—Observers need different subsets of state

A cleaner push variant: define a small event object that captures everything observers might need:

@dataclass(frozen=True)
class OrderPaidEvent:
    order_id: str
    customer_id: str
    total: float
    paid_at: str

class OrderObserver(ABC):
    @abstractmethod
    def on_paid(self, event: OrderPaidEvent) -> None: ...

Observers get a frozen, well-typed event — not the full mutable Subject. This is the shape Django Signals, Kafka events, and AWS SNS messages all share.

⏱️ Sync vs async — when does the Observer run?

Out of the box, self._observers + for means observers run synchronously, in registration order, in the publisher's thread. That's often not what you want for an HTTP request handler:

  • Slow observers block the response (email service times out → the user's payment confirmation page hangs).
  • An exception in observer #2 means observers #3, #4, … never run.

Three production shapes for "decouple the publisher from observer execution":

👣
Best-effort sync — trap each observer's exception

Run observers in order; try/except around each so a bad one doesn't poison the rest. Cheap, but slow observers still block.

def notify(self, event):
    for obs in self._observers:
        try:
            obs.on_paid(event)
        except Exception as e:
            log.exception("observer %s failed: %s", obs, e)
🏃
Fire-and-forget — enqueue, let workers consume

Publisher writes the event to a queue (Redis Streams, Kafka, RabbitMQ, Celery broker). Observers are workers that pull from the queue. Publisher returns immediately. Used in any non-trivial Django app via Celery.

def mark_paid(self):
    self.status = "PAID"; self.save()
    bus.publish("order.paid", OrderPaidEvent(...))   # < 1 ms
    # Workers pick it up, run observer logic in their own process
🤠
async/await — concurrent observers in one event loop

In an asyncio app: await asyncio.gather(*[obs.on_paid(event) for obs in obs_list]) runs all observers concurrently — the publisher waits for the slowest, but doesn't sum their times.

import asyncio

class AsyncOrder:
    def __init__(self):
        self._observers: list[AsyncObserver] = []

    async def mark_paid(self, event):
        # Kick off every observer at once; await them as a group.
        # return_exceptions=True so one observer crashing doesn't cancel the others.
        results = await asyncio.gather(
            *[obs.on_paid(event) for obs in self._observers],
            return_exceptions=True,
        )
        # Surface any failures without losing the others' work
        for obs, r in zip(self._observers, results):
            if isinstance(r, Exception):
                log.exception("observer %s failed: %s", obs, r)

Why this is fast. Three observers that each await for 200/300/150 ms sequentially take ~650 ms total — the sum. With asyncio.gather, the event loop schedules all three at the same time and the publisher resumes when the slowest (300 ms) finishes. Runnable demo: code/10_async_observer.py — the timing comparison is printed inside.

📝 Observer at a glance — the UML, plus what each role is called

Observer pattern — UML

Terminology — same idea, many names. Observer is the one pattern where every framework picks its own vocabulary. They all mean the same thing:

Role in GoFAlso calledWhat it doesWhere you've seen this name
Subject Publisher · Observable · Sender · Emitter · Source Owns the state. When it changes, calls every registered observer. Django Signals (sender) · RxJS (Observable) · Node.js (EventEmitter) · Kafka (Publisher)
Observer Subscriber · Listener · Handler · Receiver · Sink Registers itself with the Subject. Has one method that runs when the Subject notifies. JavaScript (addEventListener) · Django Signals (receiver) · Kafka / Redis (subscriber)

Tiny clarification on the word "observee". You sometimes see students write "observee" when they mean "the thing being observed" — but the standard term for that role is Subject (or Observable / Publisher). There is no formal "observee" role in Observer; if an interviewer or textbook says it, they mean the Subject.

Two interaction styles also worth knowing:

  • Push: Subject sends the data the observer needs — obs.on_paid(event). Most common; we used it above.
  • Pull: Subject just sends itself — obs.on_paid(self). The observer then reads whatever it wants from the Subject. More coupling, sometimes useful.

🌐 Observer in the wild — you've used it everywhere

👋 Django Signals — the textbook Observer

▼

Django ships built-in signals: post_save, pre_delete, user_logged_in. Connect a handler — Django invokes it whenever the matching event fires, in any view, anywhere in the codebase. The model code never knows who's listening.

from django.db.models.signals import post_save
from django.dispatch import receiver

@receiver(post_save, sender=Order)
def send_confirmation_email(sender, instance, created, **kw):
    if instance.status == "PAID":
        email_service.send(instance.customer, ...)

Sender = Subject. Receiver = Observer. The @receiver decorator is sugar over post_save.connect(handler, sender=Order) — a registration call.

🎞 Browser events / Node's EventEmitter / Python's asyncio.Event

▼

button.addEventListener("click", handler) in the browser, emitter.on("event", handler) in Node, websocket.onmessage = handler in JS — all literal implementations of Observer. The DOM element is the Subject; the registered handler is the Observer.

🔌 Spreadsheet recalculation — cell → dependents

▼

When you edit cell A1 in Excel/Sheets, every formula referencing A1 recomputes. Each formula cell subscribed to A1; A1 publishes its change; observers (the dependent cells) recompute. Reactive frameworks (React, Vue, MobX) generalise this idea to whole UIs.

⚡ Pub/sub message brokers — Kafka, Redis Streams, AWS SNS

▼

Distributed Observer. Publishers post to a topic; an arbitrary number of subscribers consume. The broker is the infrastructure-level "Subject's list of observers" — durable, retryable, cross-process. The pattern's the same, the scale isn't.

⚠️ Pitfalls — quiz-driven

Quiz — A web app creates and destroys 10,000 Cart objects per minute. Each Cart subscribes to PriceFeed for live pricing. After an hour, memory usage has climbed 4 GB. What's likely wrong?

B is right — the classic Observer memory leak. When you call subject.subscribe(observer), the Subject's observer list holds a strong reference to the Observer. If the Observer is supposed to be short-lived but the Subject keeps it referenced, GC can never collect it — and every event the Subject fires keeps calling the dead observer.

Two fixes:

  • Always pair subscribe/unsubscribe. Most natural in a context manager: with feed.subscription(cart): ...
  • Hold observers in a WeakSet. Python's weakref.WeakSet lets GC collect the observer as soon as the application drops its last strong reference — the Subject's reference doesn't keep it alive.
import weakref

class PriceFeed:
    def __init__(self):
        self._observers = weakref.WeakSet()    # GC can reclaim

    def subscribe(self, observer):
        self._observers.add(observer)         # weak ref

    def notify(self, event):
        for obs in self._observers:           # dead ones already gone
            obs.on_price(event)
Django Signals uses weak references by default for this exact reason.

Quiz — Observer A reacts to Order events by updating Inventory. Inventory has its own observers, one of which updates Pricing. Pricing's observers include the Order display. Press "Pay" — what could happen?

B is right. When publishers and observers form a graph (especially when Observer A's reaction publishes its own events to Subject B), small state changes trigger sprawling cascades — or worse, cycles that hang the system. Three guards:
  • Keep observers passive. Reactions should not, themselves, fire new events on the same Subject. If they must, route through a queue so cycles can be detected and broken.
  • Make events immutable. Frozen dataclass / namedtuple. Observers can't tamper with the event in-flight.
  • Bound the propagation depth. If you find yourself debugging "why did the price update three times after one Pay click", you have a notification storm — identify the cycle.

✅ When Observer earns its keep

Use Observer when
  • One state change has multiple, unrelated downstream effects
  • Those effects should be add/removable without touching the Subject
  • The Subject shouldn't know which subsystems care about its events
  • You want each effect testable in isolation
Skip Observer when
  • There's only one downstream reaction, and it always runs — just call it directly
  • The Subject's events must be reliably consumed even on crash — use a durable broker (Kafka), not in-process Observer
  • You need ordered, guaranteed delivery across machines — same answer (broker), not Observer
  • Reactions need to know about each other (e.g. step 3 needs step 2's result) — that's Chain of Responsibility / a workflow, not Observer

Strategy vs Observer vs Command — and the cross-family check

All three behavioural patterns "encapsulate something you want to do." The pattern name picks what gets encapsulated and who drives it.

A quick mental test for the behavioural patterns you'll meet repeatedly. All four "encapsulate a unit of work" — the pattern name says which unit and who triggers it.

Pattern What's encapsulated Who triggers execution Example one-liner
Strategy An algorithm (one method) The Context, when it needs the algorithm "Pay using THIS pricing rule"
Observer A reaction to an event The Subject, when its state changes "When Order becomes PAID, email + warehouse + analytics react"
Command An action to perform (queued, undoable, replayable) The invoker, when the user clicks / a queue fires "On Ctrl+Z, undo the last Command"
State A set of allowed transitions bound to an object's current mode The Context, when an event hits "In DRAFT state, only .submit() is allowed; in REVIEW state, only .approve()"

🥇 Strategy vs State — the subtle one

Both wrap "what to do next" behind a class. The difference is whether the choice is external or internal:

  • Strategy — the caller picks. You set checkout.discount = Loyalty() from outside; the Checkout uses whatever's set.
  • State — the object picks (transitions itself). A Document in DraftState calls .submit(), which transitions to ReviewState. The next call's allowed actions depend on the new state.

If you can swap the strategy from outside at any time without breaking invariants — it's Strategy. If swapping is only legal after specific transitions — it's State.

🥇 Cross-family check — one-question disambiguator

"I want to vary something at runtime." — vary what?

  • Which concrete class to instantiate → Factory
  • How interfaces fit together → Adapter
  • Which algorithm to use for one job → Strategy
  • Who reacts to one event → Observer

Quiz — A UI builder lets users drag a "Submit" button onto a form and pick what runs on click: "Save Draft", "Email", "Webhook", "Run Script". Each one is configurable and the user can attach multiple of them to a single button. Which pattern fits the click handler?

B is right — Command. Two clues both point there:
  • Each action is a self-contained unit of work that can be parameterised, stored, queued, replayed, undone — that's Command's signature.
  • The button holds a list of them — not one Strategy per call.
Strategy would fit if it were "pick exactly one algorithm." Observer would fit if the actions registered themselves and the button just published — but the button explicitly attaches the actions, so it's not an arms-length subscription. Command is the right shape for a queueable action.

Mindmap & Interview Cheat Sheet

LLD-19 — on one page

🎮 STRATEGY — behavioural · "swap the algorithm"

  • Use when: an if/elif over "mode" has grown past 3 branches; each branch has its own dependencies
  • Three roles: Context (holds strategy) · Strategy (interface) · ConcreteStrategy (one per algorithm)
  • Three wirings: constructor · setter · per-call argument
  • Python shortcut: a function is often Strategy enough — sorted(key=), filter(pred, ...)
  • Real-world: PyTorch optimizers · HTTP compression · pricing rules · sort comparators
  • Skip when: two short branches; variants are just different constants; over-engineered "in case we need it"
  • #1 bug: Strategy reaches back into the Context's internals — coupling restored. Pass only what each strategy consumes.

📣 OBSERVER — behavioural · "publish change, observers react"

  • Use when: one state change must trigger multiple unrelated downstream effects
  • Two roles: Subject (holds observer list, emits events) · Observer (registers a callback)
  • Push vs Pull: push an immutable event object (cleanest) vs pull from the Subject
  • Sync vs async: in-process best-effort sync · fire-and-forget via queue · async/await gather
  • Real-world: Django Signals · browser events · spreadsheet recalc · Kafka / Redis Streams / SNS
  • Skip when: one fixed reaction (just call it) · need durable delivery (use a broker, not in-process Observer)
  • #1 bug: memory leak — subscribers never unsubscribe; Subject's strong refs keep them alive. Fix: WeakSet or paired subscribe/unsubscribe in a context manager.

🎯 CROSS-FAMILY CHEAT — "vary what?"

  • Vary which class → Factory
  • Vary which interface fits with another → Adapter
  • Vary how to do one job → Strategy
  • Vary who reacts to one event → Observer

🎯 Interview cheat sheet

If asked "when would you use Strategy?": lead with the OCP win — a growing if/elif over a "mode" parameter, each branch with different dependencies. Mention sorted's key= as the everyday Python example. Bonus: name the three wirings (constructor / setter / per-call).

If asked "when would you use Observer?": lead with decoupling one publisher from N unrelated reactions. Name Django Signals as a built-in example. Bonus: distinguish sync (in-process, blocks) from async (broker / queue) — and call out the memory-leak trap with WeakSet.

If asked "Strategy vs State?": who picks — caller picks → Strategy; object transitions itself → State.

If asked "Observer vs pub/sub broker?": same pattern, different scale. In-process & in-memory → Observer. Cross-process / durable → broker.
