Semaphores & Async I/O

LLD-08 • Controlling Concurrency & Going Thread-Free

Last class: mutex (1 at a time) and deadlocks.
Today: semaphores (N at a time) and async/await (no threads at all).

Warm-Up

Recap — Last Class

Act 1: Two threads, plain global int. Is this thread-safe?

balance = 0

def add():
    global balance
    for _ in range(1_000_000):
        balance += 1

def subtract():
    global balance
    for _ in range(1_000_000):
        balance -= 1

# Run both in threads → balance = ?
CPython checks the GIL eval breaker only at loop boundaries, so balance += 1 on a plain int runs uninterrupted. But this is an implementation accident, not a guarantee.

Act 2: Same logic, but balance is behind @property. Now what?

class Account:
    def __init__(self): self._balance = 0

    @property
    def balance(self): return self._balance

    @balance.setter
    def balance(self, v): self._balance = v

# acc.balance += 1 in two threads → acc.balance = ?
Act 1 and Act 2 are semantically identical. Only difference: attribute access goes through a function call. Enough to break the accidental atomicity. The bug was always there.

Act 3: How do you make it actually safe?

Click to reveal

▼ 
with acc._lock:          # Lock the read-modify-write
    acc.balance += 1     # Safe by DESIGN, not by accident

Always use a Lock. Never rely on CPython's accidental atomicity.

Homework: This code deadlocks. How would you fix it?

locks = {"Alice": Lock(), "Bob": Lock()}

def transfer(from_acc, to_acc, amount):
    with locks[from_acc]:
        with locks[to_acc]:
            # move money

# Thread 1: transfer("Alice", "Bob", 100)  → locks Alice, wants Bob
# Thread 2: transfer("Bob", "Alice", 50)   → locks Bob, wants Alice

Click to reveal answer

▼ 
def transfer(from_acc, to_acc, amount):
    # Sort accounts — BOTH threads lock in same order
    first, second = sorted([from_acc, to_acc])
    with locks[first]:
        with locks[second]:
            # move money

# Now both threads lock Alice first (A < B alphabetically)
# Same order = no circular wait = no deadlock

Semaphore

🚗 Scenario: Highway Toll Booths

A highway toll plaza has 3 booths. Each booth can serve 1 car at a time. A car must pay at a booth before passing — it's a shared resource (only so many booths exist).

6 cars arrive. Without any control, all 6 rush the booths — chaos. We need some way to control access.

Step 1: No Lock — Violations

toll_no_lock.py — run this!
▼
import threading, time

booths_in_use = 0
MAX_BOOTHS = 3

def pay_toll(car):
    global booths_in_use
    booths_in_use += 1
    if booths_in_use > MAX_BOOTHS:
        print(f"  Car {car}: VIOLATION! {booths_in_use} cars in {MAX_BOOTHS} booths!")
    else:
        print(f"  Car {car}: booth {booths_in_use} of {MAX_BOOTHS}")
    time.sleep(1)
    booths_in_use -= 1

threads = [threading.Thread(target=pay_toll, args=(i,)) for i in range(6)]
[t.start() for t in threads]
[t.join() for t in threads]
# Output: "VIOLATION! 4 cars in 3 booths!" — more cars than booths!

Step 3: Semaphore — Just Right

toll_with_semaphore.py — run this!
▼
import threading, time

booths_in_use = 0
MAX_BOOTHS = 3
sem = threading.Semaphore(MAX_BOOTHS)  # Allow 3 at a time
lock = threading.Lock()                # Just for the counter

def pay_toll(car):
    global booths_in_use
    with sem:                          # Wait if 3 already inside
        with lock: booths_in_use += 1
        print(f"  Car {car}: booth {booths_in_use} of {MAX_BOOTHS}")
        time.sleep(1)
        with lock: booths_in_use -= 1

threads = [threading.Thread(target=pay_toll, args=(i,)) for i in range(6)]
[t.start() for t in threads]
[t.join() for t in threads]
# Output: booth 1, booth 2, booth 3... then booth 1 again. ~2 seconds!
# Never more than 3 at a time. No DB errors.

Classic Pattern: Producer-Consumer

One thread produces items. Another consumes them. Between them: a buffer (a shelf with limited space).

Producer-Consumer — The Setup
👨‍🍳

→

👨‍💻

Two problems to solve

1. Buffer full — producer makes items faster than consumer processes them. Buffer fills up. Producer must WAIT until consumer frees a slot.

2. Buffer empty — consumer is fast but producer is slow. Buffer is empty. Consumer must WAIT until producer adds an item.

Two semaphores solve this:
• space_sem = Semaphore(5) — counts empty slots. Producer acquires (waits if 0). Consumer releases (frees a slot).
• items_sem = Semaphore(0) — counts available items. Consumer acquires (waits if 0). Producer releases (signals new item).

Attempt 1: No Protection

producer_consumer_broken.py
▼
buffer = []
MAX_SIZE = 3

def producer():
    for i in range(8):
        buffer.append(f"item-{i}")   # Just shove it in — no check!
        print(f"  Produced item-{i}  (buffer: {len(buffer)})")
        time.sleep(0.3)

def consumer():
    for _ in range(8):
        item = buffer.pop(0)       # Grab from front — crashes if empty!
        print(f"  Consumed {item}")
        time.sleep(0.5)

Problems: buffer overflows past MAX_SIZE. Consumer crashes with IndexError if buffer is empty. No coordination.

Attempt 2: Mutex?

producer_consumer_mutex.py
▼
lock = threading.Lock()

def producer():
    for i in range(8):
        with lock:
            if len(buffer) >= MAX_SIZE:
                pass  # Buffer full... but we can't WAIT here!
                      # Mutex has no way to say "sleep until space opens"
            buffer.append(f"item-{i}")

Mutex protects the buffer from race conditions. But can it make the producer WAIT when the buffer is full?

We need something that can signal between threads: "hey, space opened up!" or "hey, new item available!" That's what semaphore does — it's not just a lock, it's a signalling mechanism.

Attempt 3: Semaphore — Signalling Between Threads

Key insight: A semaphore isn't just "N at a time." It's a signalling tool.
One thread release()s (signals) → another thread that was acquire()ing (waiting) wakes up.

• space_sem: consumer signals producer "I freed a slot, you can produce now"
• items_sem: producer signals consumer "I added an item, you can consume now"

producer_consumer_semaphore.py — run this!
▼
import threading, time, queue

buffer = queue.Queue(maxsize=3)
items_sem = threading.Semaphore(0)  # 0 items to start
space_sem = threading.Semaphore(3)  # 3 empty slots to start

def producer():
    for i in range(8):
        space_sem.acquire()        # WAIT until space available
        buffer.put(f"item-{i}")
        print(f"  [PRODUCE] item-{i}  (buffer: {buffer.qsize()})")
        items_sem.release()        # SIGNAL: "new item ready!"
        time.sleep(0.3)

def consumer():
    for _ in range(8):
        items_sem.acquire()        # WAIT until item available
        item = buffer.get()
        print(f"  [CONSUME] {item}")
        space_sem.release()        # SIGNAL: "slot freed!"
        time.sleep(0.5)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()
Semaphore as a Signalling Mechanism
Producer                          Consumer
   │                                 │
   │  space_sem.acquire()            │
   │  "any empty slots?"             │
   │     ↓ yes → produce             │
   │                                 │
   │  items_sem.release() ──────►    │  items_sem.acquire()
   │  "hey! new item ready!"         │  "any items? yes → consume"
   │                                 │
   │                          ◄──────│  space_sem.release()
   │  space_sem.acquire()            │  "hey! slot freed!"
   │  "any empty slots? yes!"        │
   │     ↓ produce again             │

Producer and consumer SIGNAL each other through semaphores. No busy-waiting. No deadlock.

Why is Producer-Consumer so famous?

It's not just a textbook problem — it's everywhere in real systems:

• Kafka / RabbitMQ — producers push messages, consumers process them. The queue is the buffer.
• Web servers — incoming requests (produced by users) go into a queue. Worker threads (consumers) pick and process them.
• YouTube uploads — you upload a video (produce). A background job (consumer) encodes it into different resolutions.
• Print spooler — you hit "Print" 10 times (produce 10 jobs). The printer processes them one at a time (consume).

Every system where "thing A generates work faster than thing B can handle it" is a producer-consumer problem. The two semaphores solve: "don't produce if buffer is full" and "don't consume if buffer is empty."

In Kafka, producers write messages faster than consumers process them. What happens to the messages in between?

Kafka, RabbitMQ, Redis queues, Celery — all producer-consumer. The semaphore-based coordination you just learned is the foundation of ALL of them.

Where Semaphores Are Used in Production

Database Connection Pools
PostgreSQL's max_connections = 100. Django/SQLAlchemy connection pool uses semaphore internally to limit concurrent connections.
API Rate Limiting
Stripe API: max 25 requests/second. Your web scraper: max 5 concurrent downloads. asyncio.Semaphore(5) in async code.
Thread Pool Size
ThreadPoolExecutor(max_workers=10) uses a semaphore internally to limit how many threads are active.

In practice: higher-level abstractions

You rarely use raw threading.Semaphore() in production Python. Instead:
• ThreadPoolExecutor(max_workers=N) — limits threads for you
• asyncio.Semaphore(N) — limits async concurrency
• SQLAlchemy pool_size=N — limits DB connections

But all of these use semaphores under the hood. Understanding the concept helps you configure them correctly.

5 threads. ~8MB each = 40MB. Context switching. Locks needed.
And they're SLEEPING 95% of the time.

5 threads, each uses 8MB, and they're idle 95% of the time. What if we could handle all 5 tasks with ZERO threads?

This is async I/O. No threads, no locks, no GIL issues. JavaScript (Node.js) has done this since day 1.
The Event Loop — 1 Thread Does Everything
Event Loop (1 thread):

 [Start A's request]  →  A is waiting for network...
 [Start B's request]  →  B is waiting for network...
 [Start C's request]  →  C is waiting for network...
 [Start D's request]  →  D is waiting for network...
 [Start E's request]  →  E is waiting for network...
     ... loop checks: any responses back?
 [C's response arrived!] → process C's data
 [A's response arrived!] → process A's data
 [E's response arrived!] → process E's data
     ...

1 thread. 0 context switches. 0 locks.
All 5 requests in flight simultaneously.

🍴 The Super Waiter

Threads = 5 waiters, each stands at 1 table waiting for food.
Event loop = 1 super waiter. Takes order from table 1, goes to table 2 while kitchen cooks, takes order from table 3... comes back to each table when their food is ready.

ONE person. ZERO idle time. No locks (only 1 person, can't have race conditions).

New Paradigm

Async I/O — async / await

If you know Node.js, this is the same idea. Python got it in 3.5.

Same concept as Node.js

Node.js was BUILT on this idea. Everything in Node is async by default — callbacks, Promises, async/await.
Python added it later: asyncio (Python 3.4) and async/await syntax (Python 3.5).

Same event loop concept. Different syntax.
Node: fetch(url).then(data => ...)
Python: data = await fetch(url)

The Problem Without Async

sequential.py — slow
▼
import time

def fetch(url):
    time.sleep(1)  # Simulate network wait
    return f"{url}: OK"

start = time.time()
r1 = fetch("razorpay.com")   # Wait 1s
r2 = fetch("email-api.com")   # Wait 1s
r3 = fetch("sms-api.com")     # Wait 1s
print(f"Total: {time.time()-start:.0f}s")  # 3 seconds!

Building the Async Version — Step by Step

Step 1: Import asyncio instead of threading

import asyncio, time   # asyncio replaces threading

Step 2: Add async before def — this makes the function a "coroutine" (it CAN pause)

async def fetch(url):          # ← "async" added before "def"
    ...                           # This function can now use "await"

Step 3: Replace time.sleep(1) with await asyncio.sleep(1) — tells the event loop "I'm waiting, go do other things"

async def fetch(url):
    await asyncio.sleep(1)     # ← "await" = pause here, let others run
    return f"{url}: OK"        #    (time.sleep would BLOCK everything!)

Step 4: Use asyncio.gather() to run multiple coroutines concurrently — like submitting multiple tasks to a pool

async def main():              # ← also needs "async"
    results = await asyncio.gather(  # ← "await" because gather is async
        fetch("razorpay.com"),
        fetch("email-api.com"),
        fetch("sms-api.com"),
    )

Step 5: Start the event loop with asyncio.run() — called ONCE from regular (non-async) code

asyncio.run(main())            # ← starts the event loop, runs main()
                               #    this is the ONLY line that's not "async"

All Together

async_fix.py — run this!
▼
import asyncio, time

async def fetch(url):                        # Step 2: async def
    await asyncio.sleep(1)                    # Step 3: await (non-blocking)
    return f"{url}: OK"

async def main():                            # Step 2: async def
    start = time.time()
    results = await asyncio.gather(           # Step 4: gather (run concurrently)
        fetch("razorpay.com"),
        fetch("email-api.com"),
        fetch("sms-api.com"),

    print(f"Total: {time.time()-start:.0f}s")  # 1 second!

Quick Reference: Where does each keyword go?

async def → on ANY function that uses await inside it
await → before ANY call that does I/O (asyncio.sleep, aiohttp.get, asyncio.gather)
asyncio.gather() → when you want to run multiple async functions concurrently
asyncio.run() → ONCE, at the very top, to start everything. Called from regular (non-async) code.

The 4 Key Concepts

async def
"This function can pause." Declares a coroutine. Must be called with await.
await
"I'm waiting for I/O. Event loop, go do other things." Only works inside async def.
asyncio.gather()
Run multiple coroutines concurrently. Returns when ALL are done.
asyncio.run()
Starts the event loop. Call once. Everything async runs inside this.

What's the difference between time.sleep(1) and await asyncio.sleep(1)?

This is the #1 async mistake. time.sleep in async = everything freezes. ALWAYS await asyncio.sleep.

What happens if you forget await?

async def main():
    result = fetch("a.com")  # Missing await!
    print(result)
Always await coroutines. Python will also show a warning: "coroutine was never awaited."

• async def = coroutine. await = non-blocking pause.
• asyncio.gather(*coros) = run concurrently, wait for all
• asyncio.run(main()) = start the event loop
• Single-threaded: no GIL issues, no locks needed
• NEVER use blocking calls (time.sleep, requests.get) inside async — use asyncio.sleep, aiohttp

Side by Side

Threading vs Async — When to Use Which

It depends on what LIBRARIES your code uses.

What are "blocking" vs "async" libraries?

When your code calls an API or database, it uses a library. That library is either blocking or async:

Blocking library = when you call it, your code STOPS and waits. Nothing else runs.
• requests.get("...") — the most popular HTTP library. Blocks until response.
• psycopg2 — PostgreSQL driver. Blocks until query completes.
• time.sleep(1) — blocks the thread.
• To make these concurrent: use ThreadPoolExecutor (each thread blocks independently).

Async library = when you call it with await, it YIELDS to the event loop. Other tasks run during the wait.
• aiohttp — async version of requests. await session.get("...")
• asyncpg — async version of psycopg2. await conn.fetch("SELECT ...")
• asyncio.sleep(1) — async version of time.sleep.
• To make these concurrent: use asyncio.gather() (no threads needed).

You're using requests.get() to call 10 APIs. Can you use asyncio.gather()?

You can't mix blocking calls with async. A blocking call inside async blocks THE ENTIRE event loop — nothing else runs. Choose: threading + blocking lib, OR async + async lib.

The Complete Picture

Which Tool for Which Job?

After 4 concurrency classes, here's the decision guide.

CPU-bound (math, image resize)  →  ProcessPoolExecutor
                                    (bypasses GIL, true parallelism)

I/O-bound + blocking libs       →  ThreadPoolExecutor
  (requests, psycopg2)              (GIL released during I/O)

I/O-bound + async libs          →  asyncio
  (aiohttp, asyncpg, FastAPI)       (single thread, no locks, lightest)

Limit concurrency               →  Semaphore(N)
  (max N connections at once)       (works with threads AND async)

Mutual exclusion                →  Lock (mutex)
  (only 1 thread modifies data)     (Semaphore(1) is equivalent)

You're building a FastAPI app that calls 3 external APIs per request. Which approach?

FastAPI + aiohttp = fully async. Handles thousands of concurrent requests on a single thread.

You need to resize 1000 images. Which approach?

CPU-bound = processes. Always.

• CPU-bound → ProcessPoolExecutor (only way to bypass GIL)
• I/O-bound + blocking libs → ThreadPoolExecutor
• I/O-bound + async libs → asyncio (lightest, scales best)
• Limit concurrency → Semaphore (works with both threads and async)
• Protect shared data → Lock/Mutex (threading) or single-threaded async
