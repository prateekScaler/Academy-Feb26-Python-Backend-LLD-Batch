Recap 1

OCP — Quick Revision

Last class we covered “open for extension, closed for modification.” Let's check what stuck — then revisit the part that most people get wrong.

Quiz 1: Which of these is the strongest signal of an OCP violation?

Correct! The OCP smoking gun is “edit existing code to add a new type.” Growing if/elif chains and isinstance branches are the same pattern in two costumes.

Quiz 2: We have total_area(shapes) that branches on isinstance(s, Circle), isinstance(s, Rectangle). What is the cleanest fix?

Correct! Push behavior into the type itself. sum(s.area() for s in shapes) stays unchanged forever — new shapes are new classes with their own .area().

Quiz 3: Sneha argues, “OCP means every class needs an ABC, just in case.” Is she right?

Correct! Apply OCP where change is happening. The signal: you have edited the same file two or three times for the same kind of feature. That is when you reach for an abstraction.

🕒 Deep-Dive: 4 Ways to Honor OCP Without Inheritance

This is the section most people skim. OCP is about abstraction, not the ABC keyword. Below are four production-grade patterns that satisfy OCP without a class hierarchy.

🧰 1. Composition — inject a behavior object

▼

Scenario: a shopping cart needs to apply a discount. The kind of discount can change per order — flat-off, percent-off, festival, employee, ...

❌ Without OCP

class Cart:
    def __init__(self, items, kind="none"):
        self.items = items
        self.kind = kind

    def total(self):
        sub = sum(i.price for i in self.items)
        if self.kind == "flat50":
            return sub - 50
        elif self.kind == "percent10":
            return sub * 0.9
        elif self.kind == "festival":
            return sub * 0.75
        # new discount = edit this method
        return sub

Every new discount type means re-opening Cart.total().

✔ With OCP (composition)

# Discount is just any object with .apply(sub)
class Flat:
    def __init__(self, amt): self.amt = amt
    def apply(self, sub):    return sub - self.amt

class Percent:
    def __init__(self, pct): self.pct = pct
    def apply(self, sub):    return sub * (1 - self.pct)


class Cart:
    def __init__(self, items, discount=None):
        self.items = items
        self.discount = discount    # injected!

    def total(self):
        sub = sum(i.price for i in self.items)
        return self.discount.apply(sub) if self.discount else sub

# New discount = new tiny class. Cart.total() is untouched.
class Festival:
    def apply(self, sub): return sub * 0.75

Cart just calls discount.apply(sub). The discount is a value passed in — no inheritance involved.

⚡ 2. Callbacks / First-Class Functions

▼

Scenario: a "find the first matching number in a list" utility. The matching rule keeps changing — first even, first negative, first > 100, ...

❌ Without OCP

def find_first_even(nums):
    for n in nums:
        if n % 2 == 0:
            return n

def find_first_negative(nums):
    for n in nums:
        if n < 0:
            return n

def find_first_big(nums):
    for n in nums:
        if n > 100:
            return n
# Each new rule = a brand new function (copy-paste-tweak).

The looping logic is duplicated; only the condition differs.

✔ With OCP (callback)

def find_first(nums, predicate):
    for n in nums:
        if predicate(n):
            return n


# Each "rule" is just a function/lambda passed in.
find_first(nums, lambda n: n % 2 == 0)   # first even
find_first(nums, lambda n: n < 0)        # first negative
find_first(nums, lambda n: n > 100)      # first big

# find_first() never changes. New rules = new lambdas.
# This is exactly how sorted(items, key=...) works.

The function is the extension point. No class, no ABC — just “here, take this function and use it.”

🔌 3. Plugins / Registry Pattern

▼

Scenario: a CLI that runs commands like greet, add, quit. The set of commands grows every sprint.

❌ Without OCP

def run(cmd, *args):
    if cmd == "greet":
        print("Hello!")
    elif cmd == "add":
        print(sum(args))
    elif cmd == "quit":
        exit()
    else:
        print("unknown command")
# Adding a new command = open run() and add an elif.

All commands live in one growing if/elif chain.

✔ With OCP (registry)

COMMANDS = {}

def command(name):
    def wrap(fn):
        COMMANDS[name] = fn
        return fn
    return wrap


@command("greet")
def _greet(*args): print("Hello!")

@command("add")
def _add(*args):   print(sum(args))


def run(cmd, *args):
    COMMANDS[cmd](*args)

# Adding a new command = a new function with @command("name").
# run() never changes. Pytest, Click, Flask all work this way.

Each plugin registers itself. The dispatcher never knows the list of plugins.

⚙️ 4. Configuration-Driven Dispatch

▼

Scenario: tax rate depends on the country. Today: India, US, UK. Tomorrow: Germany, Brazil, ...

❌ Without OCP

def tax_for(country, price):
    if country == "IN":
        return price * 0.18
    elif country == "US":
        return price * 0.07
    elif country == "GB":
        return price * 0.20
    else:
        raise ValueError("unknown country")

# Adding Germany = open tax_for() and add an elif.

Code branches grow with every country.

✔ With OCP (config table)

# Behaviors live in a table - data, not branches
TAX_RULES = {
    "IN": 0.18,
    "US": 0.07,
    "GB": 0.20,
}

def tax_for(country, price):
    return price * TAX_RULES[country]

# Adding Germany = one new dict entry. tax_for() unchanged.
TAX_RULES["DE"] = 0.19

# Bonus: the table can come from YAML / DB / feature flags,
# so non-engineers can add countries without touching code.

The dispatcher is “look it up, multiply.” The set of countries lives in data.

🔬 Myth vs Reality — OCP (True or False?)

True or False: “Make every class extensible, just in case.”

Reality: Speculative abstraction creates ABCs you have to maintain forever for benefits you may never realize. The Rule of Three: wait until you have edited the same file at least twice for the same shape of change before introducing an abstraction.

True or False: “If I use inheritance, my code is automatically OCP-compliant.”

Reality: Inheritance can still violate OCP — e.g., when the parent class needs editing every time a child is added (template-method base classes that grow with each subclass). OCP is about who edits whom, not about which Python keyword you use.
Recap 2

LSP — Quick Revision

“Subtypes must be substitutable for their base types without altering program correctness.” We covered why inheritance can lie. Let's check the muscle, then revisit the 4 contracts that make or break substitution.

Quiz 1: A subclass overrides a method and adds raise NotImplementedError. Which principle is most likely violated?

Correct! The classic LSP smoking gun. Any caller expecting the parent's promise will crash when given the child. (ISP is also often violated in the same code — we'll come back to that.)

Quiz 2: When is “Square IS-A Rectangle” wrong in code, despite being right in geometry?

Correct! LSP is about behavior, not labels. If the parent's API supports independent width/height changes, Square cannot honor that contract without surprising the caller. The fix: Square as a sibling of Rectangle under a Shape base — not as its child.

Quiz 3: FastUserRepo.find_all() returns an unsorted list, while its parent UserRepo.find_all() always returned a sorted one. Which contract did it break?

Correct! The parent guaranteed sorted output — the child guarantees less. That is a weakened postcondition: callers who relied on alphabetical-first now get something else, silently.

🕒 Deep-Dive: The 4 Contracts a Subclass Must Honor

1. Preconditions
Cannot be strengthened
2. Postconditions
Cannot be weakened
3. Exceptions
Cannot throw new ones
4. Invariants
Must be preserved

🔢 1. Preconditions cannot be strengthened

▼

A precondition is what the method requires from the caller. The child cannot demand more than the parent did — otherwise calls that worked on the parent suddenly fail on the child.

class User:
    def set_email(self, email):
        # Parent accepts ANY non-empty string
        self.email = email

class AdminUser(User):
    def set_email(self, email):
        # Child demands MORE: must end with @company.com
        # Tightened precondition -> LSP violation
        if not email.endswith("@company.com"):
            raise ValueError("company email required")
        self.email = email

def register(u: User, email):
    u.set_email(email)            # works for User

register(AdminUser(), "alice@gmail.com")
# CRASH - the caller used to work, now it doesn't.

🔢 2. Postconditions cannot be weakened

▼

A postcondition is what the method guarantees to the caller. The child cannot promise less.

class UserRepo:
    def find_all(self):
        # Parent guarantees: returns a list sorted by name
        return sorted(self._users, key=lambda u: u.name)

class FastUserRepo(UserRepo):
    def find_all(self):
        # Child guarantees LESS: returns unsorted
        # Postcondition weakened -> LSP violation
        return self._users

# Caller relied on parent's sorted guarantee:
def first_user(repo: UserRepo):
    return repo.find_all()[0]   # expects alphabetical first

first_user(FastUserRepo())   # returns RANDOM user - silent bug

🔢 3. No new exceptions (the LSP smoking gun)

▼

The child cannot throw exception types the parent never promised.

class PaymentGateway:
    def charge(self, amount):
        # Parent's contract: throws PaymentError on failure
        if amount < 0:
            raise PaymentError("invalid amount")
        ...

class CryptoGateway(PaymentGateway):
    def charge(self, amount):
        # Child throws a DIFFERENT exception type -> LSP violation
        if amount < 0:
            raise CryptoNetworkError("bad amount")
        ...

def process(gw: PaymentGateway, amt):
    try:
        gw.charge(amt)
    except PaymentError:
        log("refunding...")

process(CryptoGateway(), -5)   # CryptoNetworkError escapes -> CRASH

🔢 4. Invariants must be preserved

▼

An invariant is a property of the object that is always true. The child cannot break it.

class BankAccount:
    """Invariant: balance is never negative."""
    def __init__(self, balance=0):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientFundsError()
        self.balance -= amount


class OverdraftAccount(BankAccount):
    def withdraw(self, amount):
        # Allows negative balance -> INVARIANT BROKEN
        self.balance -= amount

# Any code that assumed balance >= 0 now has a silent corruption.
def render_ui(acc: BankAccount):
    assert acc.balance >= 0     # used to be safe; now fails

Spotting LSP violations in code review: any time you see raise NotImplementedError, pass, or if isinstance(child, ...) in a method that an “abstract” parent declared, you have an LSP smell. The fix is almost always: restructure the hierarchy, don't patch around it.

Principle 4

I — Interface Segregation Principle

“No client should be forced to depend on methods it does not use.”

Wait — Python doesn't have an interface keyword. So why are we talking about “Interface Segregation” here at all? Genuinely good question. Before we look at code, let's clear it up.

“Python has no interface. Does ISP even apply?” — Yes. Here's why.

The word “interface” in ISP doesn't mean the Java/C# language keyword. It means the API surface a client depends on — the set of methods the caller has been told it can rely on. Python has at least four ways to express that surface, and ISP applies to every single one of them:

How “interface” shows up in Python How ISP applies
abc.ABC + @abstractmethod If a subclass is forced to implement methods it cannot meaningfully provide (look for pass / NotImplementedError), the ABC is too fat.
typing.Protocol (structural typing) Same rule. If a Protocol demands 10 methods but a function parameter typed as that Protocol only uses 2, the Protocol is too wide.
A plain base class / mixin Children inheriting a base they only half-implement is the most common ISP smell in real codebases.
Duck-typed contracts Even without a base class, if a function says “pass me an object with .x(), .y(), .z()” but uses only .x(), every caller has to fake out two extra methods.
So the precise statement is: ISP applies anywhere a class or function requires a contract that is wider than what it actually uses. The keyword is missing — the smell is not.

The Fat Interface Problem

Read the code below carefully. What is the problem here? A Waiter in our restaurant is being told it must cook(), manage inventory, and generate reports — even though no real waiter does those. What smell is this, and what does it cost us?

fat_interface.py — spot the problem
▼
from abc import ABC, abstractmethod

class IWorker(ABC):
    @abstractmethod
    def cook(self): pass
    @abstractmethod
    def serve(self): pass
    @abstractmethod
    def clean(self): pass
    @abstractmethod
    def manage_inventory(self): pass
    @abstractmethod
    def generate_report(self): pass


# A Waiter is forced to implement cook()??
class Waiter(IWorker):
    def cook(self):
        raise NotImplementedError       # dead method
    def serve(self): ...
    def clean(self): ...
    def manage_inventory(self):
        raise NotImplementedError       # dead method
    def generate_report(self):
        raise NotImplementedError       # dead method
The diagnosis: IWorker bundles cooking, serving, cleaning, inventory, and reporting into one interface. Every concrete class is forced to implement methods it has no business implementing — the NotImplementedError blocks are the smell. Worse, any caller that takes an IWorker can't trust the methods it calls. This is an ISP violation: clients depend on methods they do not use.

The Fix: Split the Interface

Each role gets its own small interface. A class composes the ones it actually needs.

❌ One bloated interface

class IWorker(ABC):
    @abstractmethod
    def cook(self): pass
    @abstractmethod
    def serve(self): pass
    @abstractmethod
    def clean(self): pass
    @abstractmethod
    def manage_inventory(self): pass
    @abstractmethod
    def generate_report(self): pass

class Waiter(IWorker):
    def cook(self):
        raise NotImplementedError
    def serve(self): ...
    def clean(self): ...
    def manage_inventory(self):
        raise NotImplementedError
    def generate_report(self):
        raise NotImplementedError

✔ Segregated interfaces

class ICook(ABC):
    @abstractmethod
    def cook(self): pass

class IServer(ABC):
    @abstractmethod
    def serve(self): pass

class ICleaner(ABC):
    @abstractmethod
    def clean(self): pass

class IManager(ABC):
    @abstractmethod
    def manage_inventory(self): pass
    @abstractmethod
    def generate_report(self): pass

# Each role implements ONLY what it needs
class Waiter(IServer, ICleaner):
    def serve(self): ...
    def clean(self): ...

class Chef(ICook, ICleaner):
    def cook(self): ...
    def clean(self): ...

🚩 Signs of ISP Violation

  • Empty / stub implementations: methods that just pass or raise NotImplementedError
  • One ABC with many methods — and clients that only use a subset of them
  • Test setup keeps creating stub methods nothing under test calls
  • Interface names like IService, IManager — usually fat-by-default

💡 How to Apply ISP — Worked Example: Order Service

An e-commerce backend's IOrderService has 6 methods. Three different clients use it: the customer portal, the warehouse system, and accounting. Each client uses only its own 2 methods.

Step 1: List every client and the methods that client actually uses
Step 2: Group methods by client role
Step 3: Each group becomes its own small ABC / Protocol
Step 4: A concrete class can implement multiple small interfaces — clients only see the one they need

❌ Before: one fat interface

class IOrderService(ABC):
    @abstractmethod
    def create_order(self): pass
    @abstractmethod
    def cancel_order(self): pass
    @abstractmethod
    def ship_order(self): pass
    @abstractmethod
    def track_shipment(self): pass
    @abstractmethod
    def generate_invoice(self): pass
    @abstractmethod
    def process_refund(self): pass


# Every client depends on ALL 6 methods,
# even if it only uses 2 of them.
def customer_portal(svc: IOrderService):
    svc.create_order()

def warehouse(svc: IOrderService):
    svc.ship_order()

def accounting(svc: IOrderService):
    svc.generate_invoice()

✔ After: 4 steps applied

# Step 1 audit:
#   portal     -> create_order, cancel_order
#   warehouse  -> ship_order, track_shipment
#   accounting -> generate_invoice, process_refund

# Step 2 + 3: each role -> its own small ABC
class IOrderCreation(ABC):
    @abstractmethod
    def create_order(self): pass
    @abstractmethod
    def cancel_order(self): pass

class IOrderShipping(ABC):
    @abstractmethod
    def ship_order(self): pass
    @abstractmethod
    def track_shipment(self): pass

class IOrderAccounting(ABC):
    @abstractmethod
    def generate_invoice(self): pass
    @abstractmethod
    def process_refund(self): pass


# Step 4: concrete class composes all three
class OrderService(IOrderCreation, IOrderShipping, IOrderAccounting):
    def create_order(self): ...
    def cancel_order(self): ...
    def ship_order(self): ...
    def track_shipment(self): ...
    def generate_invoice(self): ...
    def process_refund(self): ...

# Clients see only the slim interface they need
def customer_portal(svc: IOrderCreation): ...
def warehouse(svc: IOrderShipping): ...
def accounting(svc: IOrderAccounting): ...

🔬 Myth vs Reality — ISP (True or False?)

True or False: “Every interface should have exactly one method.”

Reality: ISP says no client should depend on methods it doesn't use. An interface with read(), readline(), readlines() is fine if every client uses all three.

True or False: “Python doesn't have interfaces, so ISP doesn't apply.”

Reality: Python has abc.ABC, typing.Protocol, mixins, and duck-typed contracts. Any of them can force a class to implement unnecessary methods. The keyword is absent — the smell is not.

True or False: “ISP just means split everything into tiny interfaces.”

Reality: ISP is client-driven. The split is determined by which methods real callers use together — not by your aesthetic preference.

True or False: “ISP is the same as SRP.”

Reality: SRP is about classes having one reason to change. ISP is about interfaces being slim enough that clients don't drag along unused methods. Siblings, not synonyms.
Clarification

LSP vs ISP — Not the Same

Both can be triggered by the same smell (NotImplementedError in a subclass). They fix different things.

  LSP (Liskov) ISP (Interface Segregation)
What it cares about Behavior of subclasses Size of the interface
The question it asks Can I use the child anywhere the parent is expected, without breaking callers? Is this client being forced to depend on methods it never calls?
Typical smell Child overrides a method and changes its contract Class implements an interface but several methods are pass / NotImplementedError
Typical fix Restructure the inheritance hierarchy Split the fat interface into smaller ones
Direction of pain The caller gets surprised by subclass behavior The implementer is forced to write methods it doesn't need

The Penguin Example — Both at Once

penguin_fixed.py
▼
from abc import ABC, abstractmethod

# ISP: split the fat Bird interface into capabilities
class IFlyable(ABC):
    @abstractmethod
    def fly(self): pass

class ISwimmable(ABC):
    @abstractmethod
    def swim(self): pass

class IWalkable(ABC):
    @abstractmethod
    def walk(self): pass


# LSP: each bird only claims what it can deliver
class Sparrow(IFlyable, IWalkable):
    def fly(self):  return "flapping"
    def walk(self): return "hopping"

class Penguin(ISwimmable, IWalkable):
    # NOT IFlyable - no fly() at all
    def swim(self): return "swimming"
    def walk(self): return "waddling"


def takeoff(b: IFlyable):
    print(b.fly())

takeoff(Sparrow())   # works
# takeoff(Penguin())   # type checker rejects: Penguin is not IFlyable
🎯 Final verdict: When you see NotImplementedError in an override, both LSP and ISP are usually being violated at once. The fix is always the same shape: split capabilities into smaller interfaces, and let each class claim only the ones it actually delivers.
  • ISP says: “Stop forcing Penguin to depend on fly().”
  • LSP says: “Stop letting Penguin pretend to honor fly().”
Quick Primer

Before DIP — What is Composition?

DIP is going to lean heavily on composition. Let's pin down what it means — in 5 minutes.

The Two Relationships in OOP

  Inheritance (IS-A) Composition (HAS-A)
The relationship A child class is a kind of the parent One class contains / uses another as a field
Python syntax class Dog(Animal): self.engine = Engine() (or constructor arg)
How to read aloud “A Dog is an Animal” “A Car has an Engine”
Coupling Tight — child inherits structure + behavior Loose — the outer class only knows the inner's public API
Swap at runtime? No — fixed when the class is defined Yes — pass a different inner object

Example: Car HAS-A Engine

👋 Inheritance (IS-A) — for comparison

class Vehicle:
    def move(self):
        print("moving...")

class Car(Vehicle):       # Car IS-A Vehicle
    def honk(self):
        print("beep!")

c = Car()
c.move()    # inherited from Vehicle
c.honk()    # own method

Use IS-A when the child is genuinely a kind of the parent — and honors the parent's contract (recall LSP!).

✔ Composition (HAS-A)

class Engine:
    def start(self):
        print("vroom")

class Car:                # Car HAS-A Engine
    def __init__(self, engine):
        self.engine = engine    # field, not parent

    def drive(self):
        self.engine.start()    # delegate
        print("driving...")

c = Car(Engine())
c.drive()

Car doesn't become an Engine — it holds one and asks it to do its job. Want an electric car? Pass an ElectricEngine.

A Few More HAS-A Examples

composition_examples.py
▼
# 1) An Order HAS-A list of LineItems
class Order:
    def __init__(self, items):
        self.items = items     # list of LineItem - composed

    def total(self):
        return sum(i.price for i in self.items)


# 2) A House HAS-A Address (and HAS many Rooms)
class House:
    def __init__(self, address, rooms):
        self.address = address     # Address object
        self.rooms   = rooms       # list of Room


# 3) An OrderService HAS-A Database, EmailSender, Logger
#    (this is the form DIP will use)
class OrderService:
    def __init__(self, db, mailer, logger):
        self.db = db
        self.mailer = mailer
        self.logger = logger


# 4) A Pizza HAS-A list of Toppings (each with its own price)
class Pizza:
    def __init__(self, base_price, toppings):
        self.base_price = base_price
        self.toppings = toppings   # list of Topping

    def price(self):
        return self.base_price + sum(t.price for t in self.toppings)

When to Pick Which

Use Inheritance when the child is genuinely a kind of the parent AND can honor the full parent contract (LSP).
Example: VegPizza(Pizza) — a veg pizza IS a pizza
Use Composition when one class uses / needs another to do its job — especially if you might want to swap it.
Example: OrderService(db=...) — the service needs a DB; the DB isn't a kind of service
Rule of thumb in modern Python: default to composition. Reach for inheritance only when there is a real IS-A relationship and you have written down the parent's contract. The community-wide saying is “favor composition over inheritance” — and you'll see why in the next section, because DIP is composition + abstraction working together.
Principle 5

D — Dependency Inversion Principle

“High-level modules should not depend on low-level modules. Both should depend on abstractions.”

If OrderService directly creates MySQLDatabase() inside its constructor, what happens when you switch to PostgreSQL? You have to rewrite OrderService. But OrderService shouldn't care WHICH database it uses.

The Tight Coupling Problem

tightly_coupled.py — what's wrong?
▼
class MySQLDatabase:
    def save(self, data):
        # MySQL-specific save logic
        ...


class OrderService:
    def __init__(self):
        # Directly creates the dependency!
        self.db = MySQLDatabase()       # TIGHT COUPLING

    def place_order(self, order):
        ...
        self.db.save(order)
Three problems, all stemming from one root cause:
  1. Cannot switch to PostgreSQL without editing OrderService.
  2. Cannot test without a real MySQL connection.
  3. The high-level business class knows it is using MySQL — the wrong direction.

The Fix: Depend on Abstractions, Inject from Outside

❌ High-level depends on low-level

class OrderService:
    def __init__(self):
        # concrete dep created here
        self.db = MySQLDatabase()

    def place_order(self, order):
        self.db.save(order)

✔ Both depend on abstraction

class Database(ABC):
    @abstractmethod
    def save(self, data): pass

class MySQLDatabase(Database):     def save(self, data): ...
class PostgresDatabase(Database):  def save(self, data): ...

class OrderService:
    def __init__(self, db: Database):
        # Injected from outside
        self.db = db

    def place_order(self, order):
        self.db.save(order)

# Usage: wire concrete at the edge
svc = OrderService(PostgresDatabase())
# For testing: inject a fake
test_svc = OrderService(FakeDatabase())

🚩 Signs of DIP Violation

  • Concrete instantiation inside __init__: self.db = MySQLDatabase(), self.smtp = smtplib.SMTP(...)
  • Importing concrete libraries (psycopg2, sendgrid) in business-logic files
  • Hard-coded configuration: host names, ports, API keys baked into a class
  • Test setup needs a real database / real API — you can't mock
  • Switching one library forces edits across unrelated business classes

💡 How to Apply DIP — Worked Example: Signup Flow

A SignupService saves a user to Postgres, sends a welcome email via SendGrid, and logs to a file. Today it works. Tomorrow we need to test it without those services and migrate the email provider. Walk the 4 steps:

Step 1: List every concrete dependency the class touches
Step 2: Create an ABC / Protocol for each one — named after the role, not the technology (EmailSender, not SendGridClient)
Step 3: Inject via constructor
Step 4: Wire concrete implementations at the composition root (main.py / app factory) — never inside business logic

❌ Before: concrete deps hard-coded

import psycopg2
import sendgrid

class SignupService:
    def __init__(self):
        self.db = psycopg2.connect("...")
        self.email = sendgrid.Client("API_KEY")
        self.logfile = open("signup.log", "a")

    def signup(self, user):
        self.db.execute("INSERT ...", user)
        self.email.send(user.email, "Welcome")
        self.logfile.write(f"signed up {user.id}")

# - Can't test without real Postgres + SendGrid
# - Migrating away from SendGrid = editing SignupService

✔ After: 4 steps applied

🐍 DIP in the Python Ecosystem

In Python you rarely need a heavy DI framework — constructor injection is enough for 95% of cases. But the ecosystem does have battle-tested libraries when you want explicit wiring, scoping, and lifecycle management. Here's the landscape, ordered from “just Python” to “full container.”

Tool What it gives you When to reach for it
Plain constructor injection Just def __init__(self, db: Database). Wire concretes in main.py / a factory. Default. Most Python apps never need more than this.
FastAPI's Depends() Built into the framework. Declare dependencies in route signatures; FastAPI resolves them per request. Web APIs — request-scoped dependencies (DB session, current user, etc.).
dependency-injector Declarative container with providers, singletons, factories, configuration loading. The most popular Python DI framework. Large apps with many wirings, env-specific overrides, and lifecycle management.
injector Google Guice-inspired. Annotation-driven, module/binding style. Teams coming from Java / Guice. Idiomatic but heavier than constructor injection.
antidote Modern, type-hint driven. Lazy resolution, scopes, async support. Type-hint-first teams; works very well with mypy and modern Python.
kink / lagom / python-inject Lightweight containers. Decorator-based registration; minimal ceremony. You want a container but not a framework.

⚡ FastAPI — DI built into the framework

from fastapi import FastAPI, Depends

app = FastAPI()

# A "provider" - returns the concrete object to inject
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

# Route declares its dependency. FastAPI injects per-request.
@app.get("/users/{uid}")
def get_user(uid: int, db = Depends(get_db)):
    return db.query(User).get(uid)
# Testing: app.dependency_overrides[get_db] = lambda: fake_db

📚 dependency-injector — the explicit container

from dependency_injector import containers, providers

class Container(containers.DeclarativeContainer):
    # Configuration from env / yaml
    config = providers.Configuration()

    # Singleton: one instance shared across the app
    db = providers.Singleton(PostgresUserRepo, dsn=config.db.dsn)

    # Factory: a new one each call
    mailer = providers.Factory(SendGridSender, key=config.sendgrid.key)

    # SignupService gets db + mailer injected automatically
    signup = providers.Factory(SignupService, repo=db, mail=mailer)


# main.py
container = Container()
container.config.from_yaml("config.yml")
svc = container.signup()           # fully wired

🧮 DIP in Django — what we actually do

Django has no DI container. It also doesn't really need one for most apps, because the framework does dependency inversion through configuration, not through a wiring object. Here's how it plays out in practice:

1. settings.py is Django's composition root

You name an abstraction ("the database", "the cache", "the email backend") and point it at a concrete class via a string. Django resolves it at runtime.

# settings.py - swap implementations by changing a string
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        # swap to sqlite3 for dev, mysql for prod
    }
}

EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"
# Testing? settings.EMAIL_BACKEND = "...backends.locmem.EmailBackend"
# Local dev?            "...backends.console.EmailBackend"

CACHES = {
    "default": {"BACKEND": "django_redis.cache.RedisCache"}
}

DEFAULT_FILE_STORAGE = "storages.backends.s3boto3.S3Boto3Storage"
# Django depends on the abstraction (the backend interface),
# not on Redis / Postgres / SMTP / S3 directly.

2. The "services layer" pattern for business logic

Django views can quickly turn into god functions that touch the ORM, send email, hit Stripe, and write logs — classic DIP violation. The community convention is to push that work into a services.py module with constructor-injected dependencies.

# orders/services.py - business logic, framework-free
class CheckoutService:
    def __init__(self, repo, mailer, payment):
        self.repo = repo
        self.mailer = mailer
        self.payment = payment

    def checkout(self, cart):
        order = self.repo.save(cart)
        self.payment.charge(order.total)
        self.mailer.send(order.email, "Order confirmed")
        return order


# orders/views.py - the view wires concretes at the edge
def checkout_view(request):
    svc = CheckoutService(
        repo    = DjangoOrderRepo(),
        mailer  = DjangoMailer(),
        payment = StripeGateway(settings.STRIPE_KEY),
    )
    order = svc.checkout(cart_from(request))
    return redirect("thanks", order_id=order.id)

Tests instantiate CheckoutService with fakes — no Django test client, no DB, no Stripe sandbox needed.

3. Signals & middleware — Django's plugin hooks

Both are OCP/DIP-flavored. Your app registers handlers; Django invokes them without knowing what they do.

# orders/signals.py - decoupled "post-order" reactions
from django.db.models.signals import post_save
from django.dispatch import receiver

@receiver(post_save, sender=Order)
def send_confirmation_email(sender, instance, created, **kw):
    if created:
        EmailService().send_order_confirmation(instance)


# settings.py - middleware is a registry of plug-ins
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "myapp.middleware.RateLimitMiddleware",   # add new behavior
    "myapp.middleware.RequestIdMiddleware",   # without editing Django
]
The Django takeaway: instead of a DI container, Django gives you configuration-driven DIP (settings strings), service-layer DIP (constructor injection in your business code), and plugin-style DIP (signals, middleware, custom backends). Reach for dependency-injector only if your app outgrows these — e.g., you have many environments, complex scoping, or many shared singletons to manage.

🔬 Myth vs Reality — DIP (True or False?)

True or False: “DIP means you need a Dependency Injection framework.”

Reality: In Python, constructor injection is enough: def __init__(self, db: Database). You don't need Spring or a DI container. Just pass dependencies in instead of creating them inside.

True or False: “Every class needs an abstract interface.”

Reality: Only create abstractions at boundaries — database, external APIs, email, payment. Internal helpers that are unlikely to change don't need an interface.

True or False: “DIP and Dependency Injection are the same thing.”

Reality: DI is one technique for achieving DIP. The principle says “depend on abstractions”; injection is the most common way to honor that, but factories, service locators, and config-based wiring also count.

True or False: “DIP is just OCP renamed.”

Reality: They overlap but differ in focus. OCP is about extending behavior without modifying. DIP is about which direction your dependencies point — high-level policy must not import low-level details.

Takeaways

Key Takeaways

What to walk away with.

🔒
OCP ≠ inheritance
Composition, callbacks, plugins, configuration all honor OCP. Reach for an abstraction when change is happening, not just in case.
🔄
LSP = 4 contracts
Subclasses must honor preconditions, postconditions, exceptions, and invariants. Breaking any one = LSP violation.
✂
ISP exists in Python
Even without an interface keyword. ABCs, Protocols, mixins, and duck-typed contracts all need to stay slim.
🔌
DIP unlocks testing
High-level business code must not import concrete libraries. Inject role-named abstractions; wire concretes at the edge.
🧐
LSP vs ISP
Same smell (NotImplementedError), two angles. Real fixes usually need both.

Interview tip: When asked “How would you design X?”, name the principles you're applying as you go. “I'd extract payment processing behind a PaymentGateway ABC (DIP) so we can add new providers as new classes (OCP), each honoring the same charge/refund contract (LSP), and clients only see the slim payment interface (ISP).”

Counterpoint

Arguments Against SOLID

SOLID is taught as gospel. It is not. Several respected engineers have written serious critiques — particularly Ted Kaminski's 2019 essay. Understanding the critique is part of understanding the principles.

Why study the critique? Principles are heuristics, not laws. The best engineers know when each principle helps and when it gets in the way. Below: the strongest argument against each, and what to actually take away.

⚒ SRP — “the most confusingly stated principle in SOLID”

▼

The argument: SRP conflates class design with module design and tries to solve both with one slogan (“one reason to change”). In practice that slogan is too vague — reasonable engineers disagree about what counts as “one” reason.

Concrete example — reasonable people disagree:

class Money:
    def __init__(self, amount, currency):
        self.amount = amount
        self.currency = currency

    def add(self, other):              # arithmetic
        ...
    def convert(self, to_currency, rates): # currency conversion
        ...
    def format_for_display(self, locale):  # UI formatting
        ...
    def to_json(self):                  # serialization
        ...

Engineer A: “This violates SRP! Money does arithmetic and conversion and formatting and serialization. Split into Money, MoneyConverter, MoneyFormatter, MoneySerializer.”

Engineer B: “These are all aspects of one responsibility — representing money. Splitting just creates four classes that always travel together.”

Both are reasonable. SRP can't settle the argument because “one reason to change” depends entirely on whose perspective you're taking.

What it misses: Good module design is mostly about deciding what not to expose and what not to depend on — concepts SRP doesn't really address.

Take it forward as: “Watch out for god classes” is a useful heuristic. “Every class must have exactly one responsibility” is a debate, not a rule. When you split, ask: am I reducing what callers depend on?

🔒 OCP — “quietly favors objects over data, without acknowledging the trade-offs”

▼

The argument: Extensibility is a goal at system boundaries (library APIs, plugins, public interfaces). Inside your own codebase, code is cheap to modify — making it “open for extension” just adds layers nobody asked for.

Concrete example 1 — over-engineering a stable conditional:

✅ Pragmatic (stays this way for years)

def unit_label(unit):
    if unit == "C": return "°C"
    if unit == "F": return "°F"
    if unit == "K": return "K"

⚠️ "OCP-compliant" (ceremony)

class UnitLabel(ABC):
    @abstractmethod
    def label(self): ...

class Celsius(UnitLabel):
    def label(self): return "°C"
class Fahrenheit(UnitLabel):
    def label(self): return "°F"
class Kelvin(UnitLabel):
    def label(self): return "K"

REGISTRY = {"C": Celsius(), "F": Fahrenheit(), "K": Kelvin()}

Three units of temperature are not going to grow. The if/elif ages perfectly. The “OCP-compliant” version is 4× the code and adds zero real flexibility.

Concrete example 2 — the abstraction itself is closed:

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount): ...

# 12 subclasses across 8 microservices implement this.
# Year 2: we need refunds. We add:
class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount): ...
    @abstractmethod
    def refund(self, txn_id): ...   # NEW

# BOOM: every implementer breaks, including ones owned
# by other teams. "Closed for modification" is a lie -
# the interface itself wasn't closed; it was just hard to change.

Extensibility only flows one way (new implementers). Evolving the interface is still a breaking change — OCP doesn't actually buy you forward-compatibility, it just shifts who has to update what.

What it misses: Sometimes a small if/elif is genuinely fine. Abstracting it just creates ceremony.

Take it forward as: Apply OCP at boundaries (your library's plugin system, your framework's hook points). For everyday business code, the rule of three is honest: don't abstract until you have edited the same shape of branch at least twice.

🔄 LSP — “rigorously followed, it bans implementation inheritance entirely”

▼

The argument: The principle itself is sound. But almost every real use of implementation inheritance violates it somewhere. Taken to its logical end, LSP says: stop using implementation inheritance.

Concrete example 1 — even Python's stdlib breaks LSP:

from collections import OrderedDict

# Parent: dict.popitem() removes and returns SOME pair.
# Child: OrderedDict.popitem(last=True) removes by insertion order,
#                                 and accepts an extra argument.
d  = {"a": 1, "b": 2}
od = OrderedDict([("a", 1), ("b", 2)])

d.popitem()                # fine
od.popitem(last=False)     # fine for OrderedDict
d.popitem(last=False)      # TypeError - signature differs!

# Function written against `dict` cannot reliably take an
# OrderedDict if it relies on popitem - strict LSP violation.

If you took LSP literally, you'd condemn the design of OrderedDict, defaultdict, and most of collections. These are widely loved classes — not bugs.

Concrete example 2 — sometimes inheritance is the right tool, contract-violation and all:

class EventEmitter:
    def emit(self, event): ...
    def on(self, fn):       ...

class DebouncedEmitter(EventEmitter):
    def emit(self, event):
        # Suppresses duplicate events within 100ms.
        # Technically: weakens parent's postcondition
        #   ("every emit reaches subscribers").
        ...

# Strict LSP: VIOLATION - silently dropping events.
# Pragmatic: this is exactly the contract a debouncer SHOULD have.

The point isn't that LSP is wrong — it's that “preserve the parent's contract” presumes the parent has a contract precise enough to preserve. Most real classes don't.

What it misses: Casual invocation. People shout “LSP violation!” at minor inconveniences without checking what the contract actually was — or whether the parent should have existed.

Take it forward as: Prefer composition over inheritance by default. When you do inherit, write down the contract (return type, exceptions, invariants) before adding a child. If the child can't honor it, it isn't really a child.

✂ ISP — “pretty vague; really only applies at system boundaries”

▼

The argument: “Don't depend on methods you don't use” matters most at versioned/public boundaries. Inside one team's codebase, slicing interfaces too fine just trades one kind of clutter for another.

Concrete example — fragmenting an interface that always co-varies:

✅ Reasonable (one cohesive interface)

class FileLike(ABC):
    @abstractmethod
    def read(self, n): ...
    @abstractmethod
    def write(self, data): ...
    @abstractmethod
    def close(self): ...

# Every caller in our codebase uses ALL three.
# Grouping them is honest, not bloat.
def copy(src: FileLike, dst: FileLike):
    dst.write(src.read(4096))
    src.close(); dst.close()

⚠️ "ISP-zealot" (fragmented)

class Readable(ABC):
    @abstractmethod
    def read(self, n): ...

class Writable(ABC):
    @abstractmethod
    def write(self, data): ...

class Closable(ABC):
    @abstractmethod
    def close(self): ...

# Every concrete file class now lists 3 bases.
# Every caller signature needs an intersection type.
def copy(src: "Readable & Closable",
         dst: "Writable & Closable"): ...

If every caller in your codebase uses read, write, and close together, splitting them adds ceremony without removing any real coupling. The split is honest only when there are real callers that need just one of the three.

What it misses: The cost of fragmentation. Twelve one-method interfaces are not always clearer than one cohesive five-method interface.

Take it forward as: Slim interfaces are most valuable at API boundaries (public libraries, RPC contracts, plugin SPIs). Inside a single service, group methods that genuinely co-vary — let actual client usage drive the split.

🔌 DIP — “partly backwards; many 'concretions' are actually abstractions”

▼

The argument: The real goal isn't “avoid concrete dependencies.” It's “don't expose internals callers shouldn't reach.” datetime, json, uuid, hashlib — these are concrete imports and perfectly good abstractions. Wrapping them in an ABC just to satisfy DIP is pure ceremony.

Concrete example — YAGNI in action:

✅ Pragmatic (direct import)

import json, uuid
from datetime import datetime

class AuditEntry:
    def __init__(self, action, user_id):
        self.id        = str(uuid.uuid4())
        self.timestamp = datetime.utcnow()
        self.action    = action
        self.user_id   = user_id

    def to_json(self):
        return json.dumps(self.__dict__, default=str)

# No ABCs. Tests can still pass; freezegun handles datetime,
# json is deterministic, uuid is fine to monkeypatch.

⚠️ "DIP-pure" (over-engineered)

class Clock(ABC):
    @abstractmethod
    def now(self): ...

class IdGenerator(ABC):
    @abstractmethod
    def new_id(self): ...

class Serializer(ABC):
    @abstractmethod
    def dumps(self, obj): ...

class AuditEntry:
    def __init__(self, action, user_id,
                 clock: Clock,
                 ids:   IdGenerator,
                 ser:   Serializer):
        self.id        = ids.new_id()
        self.timestamp = clock.now()
        ...
    def to_json(self):
        return self.ser.dumps(self.__dict__)

Three ABCs and three injected dependencies — for capabilities nobody is ever going to swap. datetime already is an abstraction over “wall clock”; uuid already is an abstraction over “random identifier”. Wrapping them adds layers without buying anything.

The DIP-pays-off contrast:

# vs. THIS, where DIP genuinely pays off:
class CheckoutService:
    def __init__(self, payment: PaymentGateway, mailer: Mailer):
        ...
# Payment provider changes (Stripe -> Razorpay). Mailer
# changes (SendGrid -> AWS SES). These DO need to be swapped.
# That's where DIP earns its keep.

What it misses: Sometimes the easiest, clearest design is to import the “low-level” thing directly because it has a perfectly good API.

Take it forward as: Inject dependencies you legitimately need to swap (DB, mailer, payment gateway). For stable stdlib calls and pure-logic helpers, a direct import is fine.

Putting it together: SOLID isn't wrong — it's incomplete. The principles work best at the right scale: at system boundaries (libraries, plugins, public APIs) and around the things that actually change (payment providers, persistence, notifications). Applied indiscriminately to every class, they become ceremony. The senior-engineer move is to use SOLID where it pays and ignore it where the design is already obvious.
