Builder Design Pattern

LLD-16 • Creational Patterns

Stop writing constructors that take ten boolean parameters in a row. Build complex objects step-by-step with a clean, fluent API — and keep validation out of __init__.

Recap

Quick Recall — Singleton

Three quick checks from LLD-15 before we move on. Builder is the second creational pattern; Singleton was the first.

Quiz 1 — The __init__ trap

class DB:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        self.count = 0
        self.count += 1

a = DB()
b = DB()
c = DB()

print(a.count, b.count, c.count, a is b)
Correct! Only one instance exists, but __init__ runs on every DB() call — resetting count to 0 each time, then incrementing to 1.

Step-by-step:

  1. a = DB() → __new__ creates the instance; __init__ sets count = 0, then += 1 → count = 1
  2. b = DB() → __new__ returns the same instance; but __init__ runs again — resets to 0, then += 1 → count = 1
  3. c = DB() → same story. Every call clobbers the state.

Fix: guard __init__ with an _initialized flag, set once on first call:

class DB:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False     # marker on the new instance
        return cls._instance

    def __init__(self):
        if self._initialized:                       # bail on subsequent calls
            return
        self.count = 0
        self._initialized = True
        self.count += 1

a = DB()
b = DB()
c = DB()

print(a.count, b.count, c.count)    # 1 1 1 - but state preserved across calls

Now __init__ runs exactly once (on the first DB() call). Subsequent calls return the same instance untouched.

Quiz 2 — Inheritance + naive Singleton

class Singleton:
    _instance = None
    def __new__(cls):
        if Singleton._instance is None:
            Singleton._instance = super().__new__(cls)
        return Singleton._instance

class DB(Singleton): pass
class Cache(Singleton): pass

db = DB()
cache = Cache()

print(type(db).__name__)
print(type(cache).__name__)
Correct! The bug lives in this one line: 
if Singleton._instance is None:    # hardcoded - all subclasses share this slot
    Singleton._instance = super().__new__(cls)
return Singleton._instance

Step-by-step:

  1. DB() runs first. Singleton._instance is None → True. We create a DB instance and stash it on the parent class.
  2. Cache() runs. Singleton._instance is None → False (we just set it). So we return the existing… DB instance. Cache never gets built.
  3. type(cache).__name__ is therefore "DB", not "Cache". Type-confusion bomb.

The fix: store one instance per class in a dict keyed by cls — not a single shared slot on the parent.

class Singleton:
    _instances = {}                              # dict, one slot per class

    def __new__(cls):
        if cls not in cls._instances:        # keyed by cls!
            cls._instances[cls] = super().__new__(cls)
        return cls._instances[cls]

class DB(Singleton):    pass
class Cache(Singleton): pass

db = DB()
cache = Cache()

print(type(db).__name__)     # DB
print(type(cache).__name__)  # Cache
print(db is cache)                              # False

Now each subclass gets its own slot. DB instances are shared across calls; Cache instances are shared across calls; they don't collide.

Quiz 3 — pickle + Singleton

Vipul has a working Singleton. He pickles it (sends it to a Celery worker), then unpickles it on the other side. Is the loaded object the same Singleton instance?

Correct! Pickle creates a new instance via __reduce_ex__; the singleton check never runs on the receiving side. Before the fix, a quick refresher on the two terms in this question:
TermWhat it isWhy it matters here
picklePython's stdlib module that serializes any Python object to bytes (pickle.dumps) and rebuilds it from those bytes (pickle.loads). Useful for caching, sending objects between processes, saving state to disk.The rebuild step doesn't call __init__ normally — it goes through __reduce_ex__ / __new__. Our singleton guard never fires on the receiving end.
Celery workerA separate Python process that picks up background tasks from a queue (Redis / RabbitMQ). Your web server pickles a task + arguments → the worker process unpickles them and runs the task.It's a different Python process, so its cls._instance starts as None regardless of what your web server has. Unpickle → brand-new instance → singleton invariant broken across the network.

Same story for: caching with pickle, multiprocessing with spawn, concurrent.futures.ProcessPoolExecutor, RPC frameworks — anything that ships Python objects across process boundaries.

The fix — teach pickle how to reconstruct your Singleton:

import pickle

class DB:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __reduce__(self):
        # Tells pickle: "to rebuild me, call DB() with no args."
        # pickle.loads -> DB() -> __new__ -> routes through our singleton check.
        return (DB, ())


a = DB()
blob = pickle.dumps(a)

# Simulate a fresh worker process: same-process cls._instance is still set,
# but in a *real* worker, this would be the very first DB() call.
b = pickle.loads(blob)

print(a is b)              # True - singleton preserved

Each format __reduce__ returns has the shape (callable, args_tuple). Pickle stores that, then on load does callable(*args) — here, DB() — which goes through our __new__ and returns the existing singleton on that process. For a deeper guard against copy.deepcopy too, also define __copy__ and __deepcopy__ to return self.

Going forward: Singleton controlled how many objects exist. Builder controls how an object gets put together. Different problem, same family (Creational). Today we'll see why a constructor with 10 booleans is a design smell — and how Builder makes the same code clean.

What & Why

What is the Builder Pattern?

Separate the construction of a complex object from its representation — so the same construction process can produce different objects, and the constructor stays small.

❌ Without Builder
Notification("alice@x.com",
"Welcome!", "Hello!",
True, False, True,
False, "high", None)
→
✔ With Builder
NotificationBuilder()
  .to("alice@x.com")
  .subject("Welcome!")
  .html().high_priority()
  .build()
Same outcome — one is a parameter cliff, the other speaks for itself.

🎯 The four ingredients

Every Builder you'll ever write has the same four pieces. Memorize them:

1. Product
The complex object. Simple constructor — just assigns fields.
→
2. Builder
Holds the in-progress state. Mutable.
3. Setters that return self
One method per field. Enables chaining.
→
4. build()
Validates everything, then constructs the Product.
The promise: the Product's __init__ stays trivial. All validation, business rules, defaults, and combinatorial logic move to the Builder. The user gets a clear, readable construction API; the codebase gets a maintainable, testable design.

Builder is a Creational pattern (like Singleton). It joins the catalog of object-creation strategies: Singleton (one instance), Builder (step-by-step assembly), Factory (delegate the class choice), Prototype (clone). All four solve different flavors of the same question: how should objects come into existence?

Pre-flight Check

Prerequisites — Quick Quiz

Seven warm-ups. Each one shows a specific pain point that Builder is designed to solve, or a Python idiom it relies on. If you can name what's going on in every question, you already understand why Builder exists.

Question 1 — The 10-parameter constructor

A real-world notification service class — the kind every backend has:

class Notification:
    def __init__(self, recipient, subject, body, is_html, send_now,
                 track_opens, archive_after_send, priority, schedule_at, retry):
        ...

welcome = Notification("alice@x.com", "Welcome!", "Hi Alice",
                       True, True, False, True, "high", None, 3)

What's wrong with this construction?

Correct! This is "boolean hell" — a real code smell that shows up in every notification service, payment client, and HTTP request library.
  • Swap two booleans by accident? Silent bug — the type checker can't help (all bool).
  • Want a plain text notification with all defaults? Still 10 args.
  • Add a new flag (e.g. encrypted)? Every caller in the codebase breaks.
Builder fixes all three by giving each field a named setter you can chain — NotificationBuilder().to("alice@x.com").subject("Welcome!").html().high_priority().build().

Question 2 — The two-phase construction trap

An engineer decides to make construction "flexible" by allowing field-by-field setting. What goes wrong?

class User:
    def __init__(self):
        self.name = None
        self.email = None

    def set_name(self, n):  self.name = n
    def set_email(self, e): self.email = e

# Caller:
u = User()
u.set_name("Alice")
send_welcome_email(u)        # What happens here?
u.set_email("a@x.com")
Correct! The deeper problem is two-phase construction:
  • Phase 1: object exists but is incomplete
  • Phase 2: someone "finishes" it later
Anyone who gets a reference between phase 1 and phase 2 sees a broken object. Builder solves this elegantly: the in-progress state lives on the Builder, not the Product. The Product only comes into existence (via build()) after everything is set and validated — so it's complete from the first instant.

Question 3 — Telescoping constructors

In Java/C++ you write multiple overloaded constructors:

class HttpRequest:
    def __init__(self, url): ...
    def __init__(self, url, method): ...
    def __init__(self, url, method, headers): ...
    def __init__(self, url, method, headers, body): ...
    def __init__(self, url, method, headers, body, timeout): ...
Correct! Python allows only one __init__ per class. Each new definition silently replaces the previous one. So the “telescoping constructor” anti-pattern from Java/C++ is doubly broken in Python — it doesn't even compile in the form you wanted.

The workaround — default arguments — helps but still hits combinatorial explosion: with 5 optional parameters there are 2&sup5; = 32 meaningful argument combinations. Builder lets each caller set only what they need without 32 constructor signatures.

Question 4 — Business logic in the constructor

class Database:
    def __init__(self, host, port, user, password):
        if not self._is_reachable(host):    # network call!
            raise Exception("unreachable")
        if port < 1024:                       # validation
            raise Exception("bad port")
        self.host, self.port = host, port
        self.user, self.password = user, password

Why is this a poor design?

Correct! The constructor should be a simple ceremony — just stash the values. The moment it starts validating, making network calls, or running business logic, it becomes:
  • Hard to test (mocking _is_reachable for every Database test)
  • Slow to instantiate
  • Annoying to inherit from (subclass __init__ has to repeat all the checks)
Builder keeps the Product's __init__ trivial. Validation, network checks, and business rules all live in build() — where they belong.

Question 5 — Which SOLID principle does that constructor most clearly violate?

Look back at the Database.__init__ in Q4 (validation + network call + assignment all in one place). Which principle does it break first?

Correct! It's SRP. The constructor is doing at least three unrelated jobs — validating input, making a network call, and assigning fields. Each has its own reason to change:
  • Validation rules change → constructor changes
  • Network library changes → constructor changes
  • A new field is added → constructor changes

SRP says: a class (or method) should have one reason to change. Three reasons → three responsibilities → SRP violation.

How Builder fixes it:

  • Database.__init__ → only assigns fields. One reason to change: the field set itself.
  • Builder.build() → runs validation + business logic. Owns the “is this object valid?” question.
  • The two concerns are physically separated — you can change one without touching the other.

(You could argue DIP too — _is_reachable is a hardcoded concrete dependency. SRP is the most direct violation; DIP is a secondary one.)

Question 6 — When does @staticmethod belong on a method?

Look at parse_temperature below. It belongs logically with the Temperature class — but does it need self or cls?

class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius

    @staticmethod
    def parse_temperature(text):
        # e.g. parses "23.5C" -> 23.5
        return float(text.rstrip("C"))

celsius_value = Temperature.parse_temperature("23.5C")
t = Temperature(celsius_value)

Why is @staticmethod the right choice here?

Correct! parse_temperature doesn't read or write any instance state, and doesn't need the class either. It's just a utility — but conceptually it belongs to Temperature, so we namespace it there with @staticmethod.
DecoratorFirst argUse when
(none)selfYou need instance data
@classmethodclsYou need the class itself — e.g. alternative constructor that respects subclasses
@staticmethodnothingUtility or factory; no instance and no class state needed

Why does this matter for Builder? — you'll see in a moment that the entry point of a Builder (e.g. Database.builder()) is exactly this kind of method: called on the class, no self, no cls. @staticmethod is the natural fit.

Question 7 — What makes method chaining work?

First, the intuition. You've already seen method chaining without knowing the term:

# pandas - each call returns a DataFrame
df.dropna().sort_values("age").head(10)

# Django QuerySet - each call returns a QuerySet
User.objects.filter(active=True).exclude(banned=True).order_by("name")

# string methods - each call returns a str
"  Hello World  ".strip().lower().replace(" ", "-")

In all three, every call returns something you can call the next method on. The "fluent" reading is just this trick.

From LLD-11 (lambdas & FP) you also saw the functional cousin of this idea — chaining transformations on iterables. The exact same pattern (each step returns something the next step consumes) shows up with map / filter / reduce and lambdas:

from functools import reduce

nums = [-2, 3, -1, 4, 5]

# Filter -> square -> sum. Three steps, each fed by the previous one.
reduce(lambda a, b: a + b,
       map(lambda x: x * x,
           filter(lambda x: x > 0, nums)))
# 50  (3*3 + 4*4 + 5*5)

# sorted() with a lambda key - same shape: result feeds the next call
sorted(users, key=lambda u: u.age)[:3]

In the functional style, each layer returns an iterable that the next layer consumes — the pipeline shape. In the OO style (pandas, Django, our Builder), each method returns the object itself so the next method can be called on it — the fluent shape. Different syntax, exact same mental model: each step hands something usable to the next step.

Now look at our Builder — what makes this chain work?

class Builder:
    def set_name(self, name):
        self._name = name
        return self                # <--- this line

    def set_age(self, age):
        self._age = age
        return self

b = Builder().set_name("Alice").set_age(25)
Correct! Without return self, the setter returns None (Python's implicit default). Then .set_age(25) tries to call a method on None — AttributeError.

The "fluent interface" is just this one trick repeated. Remove return self from any setter in the chain and that link breaks. It's the same mechanic as df.dropna().sort_values(...) — only the returned type differs (Builder here, DataFrame there).

If you got all seven: you now know the smells Builder cures — boolean hell, two-phase construction, telescoping constructors, business logic in __init__ (and the SRP violation it causes) — plus the two Python idioms it relies on: @staticmethod for the entry point, and return self for chaining. The pattern itself is the mechanical fix; the hard part was diagnosing the smell.

Motivation

The Problem — A Concrete Scenario

Let's watch a "simple" Pizza class grow into an unmaintainable mess.

Vipul is building the notification service for a SaaS product. A notification has a recipient, subject, body, plus a bunch of flags (HTML or plain, track opens, archive after send, send now vs. scheduled, priority, retry count). He writes the obvious constructor. Six months later he has 30 callers across the codebase and nobody can tell what any of them mean. Where did this go wrong?

Smell 1: Boolean hell in the constructor

notification_v1.py
▼
class Notification:
    def __init__(self, recipient, subject, body, is_html, send_now,
                 track_opens, archive_after_send, priority, schedule_at, retry):
        self.recipient          = recipient
        self.subject            = subject
        self.body               = body
        self.is_html            = is_html
        self.send_now           = send_now
        self.track_opens        = track_opens
        self.archive_after_send = archive_after_send
        self.priority           = priority
        self.schedule_at        = schedule_at
        self.retry              = retry


# Callers in the wild:
welcome = Notification("alice@x.com", "Welcome!", "Hi Alice",
                       True, True, False, True, "high", None, 3)

reminder = Notification("bob@x.com",  "Reminder", "Your trial ends...",
                       True, False, True, False, "low", "2026-06-01", 5)

# Quick - did the reminder track opens? Was it sent now or scheduled? Count positions!
Why this hurts:
  • No self-documenting code — a stream of True, False, True tells the reader nothing
  • Swap two args by accident — silent bug; type checker can't catch it (all booleans)
  • Adding a flag (e.g. encrypted) — every single caller in the codebase breaks

Smell 2: Business logic creeping into the constructor

database_v1.py
▼
class Database:
    def __init__(self, host, port, username, password):
        # Validation
        if not host:                          raise ValueError("host required")
        if port < 1024 or port > 65535:    raise ValueError("bad port")
        if not username or not password:     raise ValueError("creds required")

        # Side effect: a network call!
        if not self._is_host_reachable(host):
            raise ConnectionError("unreachable")

        # Finally, the actual init
        self.host, self.port = host, port
        self.username, self.password = username, password
        self.connection = self._open_connection()    # another side effect
What's wrong: four concrete pains the constructor causes. Each one is small in isolation; together they add up.

💥 1. Testing is painful — every Database(...) needs a reachable host

▼

You can't construct the object without a real network connection. So either every test is an integration test, or you monkey-patch around the constructor.

# What you WANT to write
def test_query_formatting():
    db = Database("localhost", 5432, "u", "p")
    assert db.format_query("SELECT 1") == "SELECT 1;"

# What ACTUALLY happens on a laptop with no DB running
# ConnectionError: unreachable
# - the test fails before it even gets to assert


# Workaround #1: every test needs a real DB. CI is slow + flaky.
# Workaround #2: monkey-patch is_reachable for every test (ugly).
def test_query_formatting(monkeypatch):
    monkeypatch.setattr(Database, "_is_reachable", lambda *a: True)
    db = Database("localhost", 5432, "u", "p")
    ...

With Builder: the Product is a plain @dataclass — you construct it in tests with no network involved.

💥 2. Subclassing is fragile — subclass __init__ inherits all the baggage

▼

When the parent's __init__ runs validation and a network call, every subclass has to either re-run all of that or carefully avoid calling super().__init__().

# Subclass wants different validation rules (e.g. read-replica
# doesn't need the same reachability check)
class ReadReplica(Database):
    def __init__(self, host, port, user, password):
        super().__init__(host, port, user, password)
        # oops - parent already ran _is_reachable, but we wanted a different host!

# Option A: skip super and re-write all the logic (DRY violation)
class ReadReplica(Database):
    def __init__(self, host, port, user, password):
        if not self._is_reachable_replica(host):
            raise ConnectionError("replica unreachable")
        self.host, self.port = host, port           # duplicated
        self.user, self.password = user, password   # duplicated

# Option B: empty __init__ that skips super (silently bypasses parent's checks)
class TestDB(Database):
    def __init__(self, host, port, user, password):
        self.host, self.port = host, port
        self.user, self.password = user, password
        # Did NOT call super - now parent invariants don't hold!

With Builder: the Product is a plain data class — subclassing it has no behavioral surprises. Specialised validation goes in a specialised Builder.

💥 3. Failures are opaque — what state was the object in when it crashed?

▼

If __init__ raises midway through, you can't introspect the half-built object — it never makes it back to the caller. You also can't tell which check failed without parsing exception messages.

db = Database("db.example.com", 5432, "admin", "secret")
# ConnectionError: unreachable

# What we CAN'T do at this point:
print(db.host)              # NameError - 'db' was never assigned
print(db._partial_state())  # no such thing

# Did the host check fail? The port check? Was the network down briefly?
# All we have is one exception. No state to inspect, no checks to introspect.

With Builder: the Builder is a real, fully-formed object holding all the in-progress state. If build() fails, the Builder is still around — you can print(b._host, b._port, ...) and see exactly what you tried to construct.

💥 4. Can't build incrementally — everything needed upfront

▼

Some configuration comes from environment variables, some from a config file, some from CLI flags — arriving at different points in your code. With this constructor, you have to gather all of it before you can construct anything.

# Real-world startup: config arrives in pieces

config = load_config("app.yaml")             # gives us host + port
secrets = fetch_from_vault("db-creds")        # gives us user + password
flags = parse_cli()                            # may override host

# With business logic in __init__ we MUST have everything before this line.
db = Database(
    host=flags.db_host or config.db_host,
    port=config.db_port,
    user=secrets["user"],
    password=secrets["password"],
)
# Network call happens HERE. If the vault is slow, we delay all of startup.

With Builder: assemble the configuration as it arrives, validate and connect at the very end:

builder = Database.builder().set_host(config.db_host).set_port(config.db_port)
if flags.db_host: builder.set_host(flags.db_host)
secrets = fetch_from_vault("db-creds")
builder.set_username(secrets["user"]).set_password(secrets["password"])

db = builder.build()        # validation + connection happen HERE, when everything is ready

Smell 3: The keyword-args band-aid (and where it falls short)

Python doesn't allow overloaded constructors, so people reach for keyword arguments. It helps — but it has limits.

❌ Keyword args with defaults

class HttpRequest:
    def __init__(self, url, method="GET",
                 headers=None, body=None,
                 timeout=30, retries=3,
                 verify_ssl=True, follow_redirects=True):
        ...

req = HttpRequest("https://api.com",
                  "POST",
                  {"Auth": "token"},
                  {"data": 1},
                  60, 5, True, True)

Better, but: 8 parameters still hard to read. Skipping a middle field means passing None explicitly. Validation still lives in __init__.

✔ Builder

req = (HttpRequestBuilder()
       .url("https://api.com")
       .method("POST")
       .add_header("Auth", "token")
       .body({"data": 1})
       .timeout(60)
       .build())

Reads top-to-bottom. Each setting is named. Skip what you don't need. Validation runs once in build().

That's the problem in three smells. The Builder pattern's job is to kill all three at once — with a Product that has a trivial __init__ and a separate Builder that handles the messy parts.
The Pattern

Building the Builder — in 4 Steps

Let's construct a Database Builder live. Four steps, each adds one piece. By the end we have the textbook implementation.

1Start with a simple Product

No validation, no business logic. Just a class that holds four fields. Using @dataclass makes the boilerplate vanish.

from dataclasses import dataclass

@dataclass
class Database:
    host: str
    port: int
    username: str
    password: str

    def connect(self):
        print(f"connecting to {self.host}:{self.port} as {self.username}")
📚 A quick word on @dataclass (Python 3.7+, PEP 557):

It's a decorator that generates boilerplate methods from the class's type-annotated fields. The 4 fields above (host, port, username, password) tell Python what the class holds — @dataclass writes the rest:

You writeYou get for free
@dataclass__init__ — assigns each field
(same line)__repr__ — Database(host='x', port=5432, ...)
(same line)__eq__ — compares all fields
@dataclass(frozen=True)Above — plus the object is immutable after creation

In other words: a 5-line dataclass is what a 20-line hand-written class would do. That's why it's such a good fit for the Product half of Builder — you want the Product to be data, nothing more.

Quick check — what does @dataclass give you for free?

from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p1 = Point(1, 2)
p2 = Point(1, 2)

print(p1)
print(p1 == p2)
Correct! The output of the snippet is: 
Point(x=1, y=2)         # <-- __repr__ given for free
True                    # <-- __eq__ compares the fields (1==1 and 2==2)

Without @dataclass you'd have to write __init__, __repr__, and __eq__ by hand — 15+ lines of boilerplate. With it, you write the field declarations and the rest is generated. Plus you can add frozen=True to make instances immutable (a property the Builder pattern often wants for the Product).

🧰 Under the hood — how @dataclass works (toy version)

▼

Nothing magic. @dataclass is a decorator — the same thing we used in LLD-15 for @singleton, and the same thing we just used in Q6 (@staticmethod). A decorator is just a function that takes a class and returns a (modified) class.

Here's a ~15-line toy version that captures the essence of what the real @dataclass does. The real one in the standard library has many more knobs (frozen, order, slots, etc.) but the core mechanic is exactly this:

def my_dataclass(cls):
    # Step 1: read the type hints written on the class
    #         e.g. {'x': int, 'y': int}
    fields = cls.__annotations__

    # Step 2: generate an __init__ that assigns each annotated field
    def __init__(self, **kwargs):
        for name in fields:
            setattr(self, name, kwargs[name])

    # Step 3: generate a __repr__ like "Point(x=1, y=2)"
    def __repr__(self):
        parts = [f"{name}={getattr(self, name)!r}" for name in fields]
        return f"{cls.__name__}({', '.join(parts)})"

    # Step 4: generate __eq__ that compares all field values
    def __eq__(self, other):
        if not isinstance(other, cls): return False
        return all(getattr(self, n) == getattr(other, n) for n in fields)

    # Step 5: attach the generated methods to the class and return it
    cls.__init__ = __init__
    cls.__repr__ = __repr__
    cls.__eq__   = __eq__
    return cls


# Usage - same as the real @dataclass
@my_dataclass
class Point:
    x: int
    y: int

p = Point(x=1, y=2)
print(p)                    # Point(x=1, y=2)   - from our __repr__
print(p == Point(x=1, y=2))   # True              - from our __eq__
The two ideas this rests on — both from earlier classes:
  • Decorators (LLD-11 & LLD-15): a decorator is a function that takes a class/function and returns a (modified) class/function. Same shape as @singleton.
  • Classes are objects (LLD-15 metaclass primer): we can read cls.__annotations__, attach new methods like cls.__init__ = __init__, and Python treats the result as a normal class. Nothing special about @dataclass — you could write this yourself in 15 lines.

What the real @dataclass adds on top: frozen=True (raises FrozenInstanceError on attribute writes), order=True (generates __lt__/__le__/__gt__/__ge__), slots=True (generates __slots__), field(default_factory=...) for mutable defaults, and a lot of edge-case handling. But the core trick — "read annotations, generate methods, return the class" — is exactly what we just wrote.

There's a full runnable version of this in code/06_dataclass_under_hood.py.

Back to the recipe: the Product is trivial. Crucially: no validation in __init__. We'll do that in the Builder.

One method per field. Each returns self so the next call in the chain has something to call on. This is the only trick behind the fluent API.

4build() validates and constructs

All validation runs here — not in the Product. If anything is missing or wrong, the Product never gets created; the caller gets a clear error from build().

from dataclasses import dataclass

@dataclass
class Database:
    host: str
    port: int
    username: str
    password: str

    def connect(self):
        print(f"connecting to {self.host}:{self.port} as {self.username}")

    @staticmethod
    def builder():

    class Builder:
        def __init__(self):
            self._host = None
            self._port = None
            self._username = None
            self._password = None

        def set_host(self, host):         self._host = host;         return self
        def set_port(self, port):         self._port = port;         return self
        def set_username(self, username): self._username = username; return self
        def set_password(self, password): self._password = password; return self

        def build(self) -> "Database":
            self._validate()
            return Database(self._host, self._port, self._username, self._password)

        def _validate(self):
            if not self._host:                         raise ValueError("host required")
            if not self._port:                         raise ValueError("port required")
            if not (1024 <= self._port <= 65535):  raise ValueError("port out of range")
            if not self._username:                     raise ValueError("username required")
            if not self._password:                     raise ValueError("password required")

Using it — the three cases

# 1. Happy path

        .set_host("localhost")
        .set_port(5432)
        .set_username("admin")
        .set_password("secret")
        .build())
db.connect()
# connecting to localhost:5432 as admin


# 2. Invalid value - caught early, in build(), with a clear message

    db = (Database.builder()
            .set_host("localhost")
            .set_port(80)                  # out of range
            .set_username("admin")
            .set_password("secret")
            .build())
except ValueError as e:
    print(e)
# port out of range


# 3. Missing field - same place, same kind of error

    db = (Database.builder()
            .set_host("localhost")
            .set_port(5432)
            .build())                       # forgot creds!
except ValueError as e:
    print(e)
# username required
Notice what just happened:
  • The Product (Database) constructor is trivial — just @dataclass
  • All validation lives in build()
  • Each setter has a name — no boolean hell
  • You can skip optional fields by simply not calling their setter
  • The same Builder can produce many Databases with different configs

Mental model: the Builder is a mutable workspace — you can add things, change things, validate things. The Product is immutable, complete, and valid from the moment it exists. Builder is the messy kitchen; the Product is the finished dish.

Variations

Three Ways to Wire a Builder

Same pattern, three placements. Pick the one that fits your codebase — or the one your team already uses.

🎯 Variation A — Builder as an inner class (recommended)

▼

Builder lives inside the Product. The relationship is obvious; the API is the cleanest. This is what we just built.

class Database:
    # ... product fields ...

    @staticmethod
    def builder():
        return Database.Builder()

    class Builder:
        # ... builder logic ...

# Caller
db = Database.builder().set_host("localhost").build()

Pros: tight encapsulation, clear relationship, clean entry point.
Cons: one big file when both classes are large.

🧰 Variation B — Separate Builder class

▼

Builder lives in a sibling class — often a separate file. Useful when the Builder grows large or has its own dependencies.

# database.py
@dataclass
class Database:
    host: str
    port: int
    username: str
    password: str


# database_builder.py - separate file, separate testing surface
class DatabaseBuilder:
    def __init__(self):
        self._host = None
        # ... etc ...

    def set_host(self, host):
        self._host = host
        return self

    def build(self):
        # ... validate then construct ...
        return Database(...)

db = DatabaseBuilder().set_host("localhost").build()

Pros: separation of concerns; easier to test the Builder in isolation; the Product file stays tiny.
Cons: two imports for callers; relationship less obvious without a naming convention.

When to add a Director:
  • The same setter chain appears in three or more places in your codebase
  • The chain represents a named real-world scenario (“local dev”, “test”, “scraper”)
  • You want callers to not see the assembly details — just “give me the production DB”

When to skip it: if you have only one or two presets and no reuse, the Director is just a wrapper. Use the Builder directly.

Pros: named contract for common configurations; callers don't see the assembly.
Cons: one more layer to read through — only worth it when presets repeat.

Which to pick?
  • Default to A (inner class) — cleanest API, clearest relationship
  • Reach for B when Builder is non-trivial and benefits from its own file/tests
  • Add C on top only when you have real recurring presets — not speculation
In Practice

Three Real-World Builders

Order for variable composition, HTTP request for optional knobs, SQL query for accumulated state. Same pattern, three flavors.

🛒 Order Builder — variable composition

An Order in any e-commerce backend has a list of items, an optional list of discount codes, and a few flags (gift wrap, expedited shipping). The Builder lets each caller add as many items and discounts as they need — without growing the constructor.

02_order_builder.py
▼
from dataclasses import dataclass, field
from typing import List, Tuple

@dataclass
class Order:
    customer: str
    items: List[Tuple[str, int]]               # [(product, qty), ...]
    discount_codes: List[str] = field(default_factory=list)
    gift_wrap: bool = False
    expedited: bool = False


class OrderBuilder:
    def __init__(self):
        self._customer = None
        self._items = []
        self._discounts = []
        self._gift_wrap = False           # sensible defaults
        self._expedited = False

    def for_customer(self, name):
        self._customer = name
        return self

    def add_item(self, product, quantity=1):     # call many times!
        self._items.append((product, quantity))
        return self

    def apply_discount(self, code):              # call many times!
        self._discounts.append(code)
        return self

    def enable_gift_wrap(self):
        self._gift_wrap = True
        return self

    def expedite(self):
        self._expedited = True
        return self

    def build(self):
        if not self._customer:
            raise ValueError("customer required")
        if not self._items:
            raise ValueError("at least one item required")
        return Order(self._customer, list(self._items),
                     list(self._discounts), self._gift_wrap, self._expedited)


# Usage
simple_order = (OrderBuilder()
                  .for_customer("alice@x.com")
                  .add_item("book-101", 2)
                  .build())

birthday_gift = (OrderBuilder()
                  .for_customer("bob@x.com")
                  .add_item("book-101", 1)
                  .add_item("pen-set", 1)
                  .add_item("card", 1)
                  .apply_discount("BDAY20")
                  .enable_gift_wrap()
                  .expedite()
                  .build())

Why this is nicer than a 7-parameter constructor: the simple order has zero noise; the birthday gift order reads top-to-bottom like an order ticket — customer, items, discount, options. Two more items? Add two more .add_item() calls. No constructor signature to update.

🌐 HTTP Request Builder — lots of optional knobs

Some calls need just a URL. Others need headers, body, timeout, auth, retries. Every caller pays only for what they use.

03_http_request_builder.py
▼
from dataclasses import dataclass, field

@dataclass
class HttpRequest:
    url: str
    method: str = "GET"
    headers: dict = field(default_factory=dict)
    body: dict | None = None
    timeout: int = 30


class HttpRequestBuilder:
    def __init__(self):
        self._url, self._method, self._timeout = None, "GET", 30
        self._headers, self._body = {}, None

    def url(self, url):              self._url = url; return self
    def method(self, method):        self._method = method.upper(); return self
    def add_header(self, k, v):       self._headers[k] = v; return self
    def body(self, body):            self._body = body; return self
    def timeout(self, s):            self._timeout = s; return self

    def build(self):
        if not self._url:
            raise ValueError("url required")
        return HttpRequest(self._url, self._method, dict(self._headers),
                           self._body, self._timeout)


# Usage
simple = HttpRequestBuilder().url("https://api.example.com").build()

with_auth = (HttpRequestBuilder()
              .url("https://api.example.com/users")
              .method("POST")
              .add_header("Content-Type", "application/json")
              .add_header("Authorization", "Bearer xyz")
              .body({"name": "Alice"})
              .timeout(60)
              .build())

This is exactly the shape of requests.PreparedRequest, urllib3.Request, and most HTTP client builders in the wild.

📊 SQL Query Builder — accumulated state

A query is built up clause by clause. The Builder accumulates the parts; build() assembles them in the right SQL order.

04_query_builder.py
▼
from dataclasses import dataclass

@dataclass
class Query:
    columns: str
    table:   str
    where:   str | None
    order_by: str | None
    limit:   int | None

    def to_sql(self):
        sql = f"SELECT {self.columns} FROM {self.table}"
        if self.where:    sql += f" WHERE {self.where}"
        if self.order_by: sql += f" ORDER BY {self.order_by}"
        if self.limit:    sql += f" LIMIT {self.limit}"
        return sql


class QueryBuilder:
    def __init__(self):
        self._cols, self._table = "*", None
        self._where = self._order = self._limit = None

    def select(self, *cols):       self._cols = ", ".join(cols); return self
    def from_(self, table):       self._table = table; return self
    def where(self, cond):         self._where = cond; return self
    def order_by(self, col):       self._order = col; return self
    def limit(self, n):            self._limit = n; return self

    def build(self):
        if not self._table:
            raise ValueError("from_() required")
        return Query(self._cols, self._table, self._where, self._order, self._limit)


# Usage
q = (QueryBuilder()
      .select("name", "email", "age")
      .from_("users")
      .where("age >= 18")
      .order_by("name")
      .limit(10)
      .build())

print(q.to_sql())
# SELECT name, email, age FROM users WHERE age >= 18 ORDER BY name LIMIT 10

Django's QuerySet, SQLAlchemy's select(), and most ORM query APIs are essentially this pattern — immutable products built by chained, named setters.

Notice the shape: in all three examples the API reads top to bottom like English. large pizza with thin crust, pepperoni, sausage, bacon. POST to URL with header X, body Y, timeout 60. SELECT these columns FROM this table WHERE this condition. That's not a coincidence — it's why fluent builders are so easy to read.

Pitfalls

Common Mistakes & Best Practices

Four traps that bite even experienced engineers, and five habits that keep your Builders clean.

🔬 Spot the issue — can you find each one?

Four short snippets, each with one common bug. Read carefully and pick the issue before checking your answer.

Mistake 1 — what's wrong with this Builder?

class UserBuilder:
    def set_name(self, name):
        self._name = name

    def set_age(self, age):
        self._age = age
        return self

    def build(self):
        return User(self._name, self._age)

b = UserBuilder().set_name("Alice").set_age(25).build()
Correct! set_name returns None (Python's default). So .set_age(25) is called on None — AttributeError. Fix: add return self at the end of every setter. This is the single most common Builder bug; remove that one line from any setter in the chain and everything downstream breaks.

Mistake 2 — what's wrong with this build()?

class DatabaseBuilder:
    def __init__(self):
        self._host = self._port = self._user = self._password = None

    def set_host(self, h): self._host = h; return self
    # ... other setters ...

    def build(self):
        return Database(self._host, self._port, self._user, self._password)

db = DatabaseBuilder().set_host("localhost").build()
db.connect()
Correct! build() doesn't check that the required fields are set. The caller only set host, but build() happily constructs a Database with port=None, user=None, password=None. The crash surfaces inside connect() — far from the actual bug.

Fix: add a _validate() call at the top of build():

def build(self):
    self._validate()       # <-- raises clear errors HERE, not in connect()
    return Database(...)

def _validate(self):
    if not self._host:     raise ValueError("host required")
    if not self._port:     raise ValueError("port required")
    # ... etc

The earlier and louder the failure, the easier the bug is to fix.

Mistake 3 — why might db2 behave unexpectedly?

b = Database.builder()

db1 = b.set_host("host1").set_port(5432).build()
db2 = b.set_host("host2").build()

print(db1.host, db2.host)
print(db1.port, db2.port)
Correct! The Builder holds state. The first build() doesn't reset it. So db2 ends up with:
  • host = "host2" — correctly set
  • port = 5432 — silently inherited from db1's chain!
Worse, if either db1 or db2 mutates a shared list/dict on the Builder, both Products are affected.

Fix: one Builder per Product:

db1 = Database.builder().set_host("host1").set_port(5432).build()
db2 = Database.builder().set_host("host2").set_port(5432).build()

A fresh chain per Product. Cheap, clear, no surprises.

Mistake 4 — spot what undoes the pattern

# Product
class Database:
    def __init__(self, host, port, user, password):
        if not is_reachable(host):
            raise ConnectionError("unreachable")
        if port < 1024:
            raise ValueError("bad port")
        self.host, self.port = host, port
        self.user, self.password = user, password

# Builder
class DatabaseBuilder:
    # ... setters that return self ...
    def build(self):
        return Database(self._host, self._port, self._user, self._password)
Correct! The whole point of Builder is that the Product's __init__ is trivial. The moment validation, network calls, or business logic slip back into the Product, you've lost:
  • Testability — can't construct a Database in tests without the network
  • SRP — Product has multiple reasons to change (recall Q5!)
  • The whole reason you wrote a Builder in the first place

Fix: move all logic to the Builder. Product becomes a @dataclass:

@dataclass
class Database:
    host: str
    port: int
    user: str
    password: str

class DatabaseBuilder:
    def build(self):
        self._validate()                   # validation HERE
        if not is_reachable(self._host):  # network check HERE
            raise ConnectionError(...)
        return Database(...)

✔ Best practices

🧮
Keep the Product trivial
Just assigns fields. A @dataclass usually does it for free.
✅
Validate in build()
One place to look for “why is this object invalid?” — the same place that produces it.
🎯
Sensible defaults in __init__
If method is usually "GET", default it in the Builder's __init__. Callers only override what they need.
📝
Use descriptive setter names
add_topping("pepperoni") beats set("topping", "pepperoni") every time. Be explicit about plurality and intent.
🔒
Copy mutable defaults into the Product
In build(), pass list(self._toppings) not self._toppings. Otherwise mutating the Builder later silently mutates an already-built Product.
📝
Document required vs optional
Required fields raise from _validate(). Optional fields have defaults. Anyone reading build() can tell which is which in five seconds.
Decision Guide

When to Use Builder — and When Not To

A pattern is a tool. The tool earns its keep only when the problem fits the shape. Three scenarios first — your call.

Scenario 1 — A 2D Point for a geometry library

class Point:
    def __init__(self, x: float, y: float):
        self.x, self.y = x, y

Both fields are required, no validation, used millions of times in a rendering loop. Should you wrap this in a Builder?

Skip Builder. Two required arguments, no validation, hot loop — the constructor is already optimal. A Builder here would mean PointBuilder().set_x(1).set_y(2).build() — longer, slower, and zero benefit. Rule: if the constructor signature is already self-explanatory, leave it alone.

Scenario 2 — An HTTP client with 12 optional config options

You're designing a Python HTTP client library (like requests). The client needs: base_url, timeout, retries, headers (dict), auth, proxies, verify_ssl, follow_redirects, max_redirects, allow_cookies, user_agent, hooks. Most callers will only set 2-3 of these. Some need to validate combinations (“SSL on requires HTTPS scheme”). Should you use a Builder?

Use Builder. 12 optional fields with cross-field validation is the textbook case. Keyword args alone would mean HttpClient(base_url="...", timeout=30, retries=3, ..., verify_ssl=True, ...) — long, hard to scan, and validation has nowhere clean to live. A Builder lets each caller set only what they need and runs validation once at build().

Scenario 3 — A LogEntry object created on every log call

@dataclass
class LogEntry:
    timestamp: float
    level:     str
    message:   str
    module:    str

# created on every log call, hundreds of thousands per second

A high-traffic service produces ~500k log entries / second. All 4 fields are required, no optional configuration, no validation. Should LogEntry have a Builder?

Skip Builder. Each Builder allocation is a Python object with its own attributes — cheap individually, expensive at 500k/s. Plus there's nothing for the Builder to do: no optional fields, no validation, no fluent assembly. LogEntry(now, "INFO", "msg", "auth") is already the best API. Rule: in hot paths and for plain data, leave the constructor alone.

Got the pattern? Here's the rule, summarised:

✔ Reach for Builder when…

  • Many parameters, especially optional ones (4+ becomes uncomfortable)
  • Validation needs to span multiple fields (e.g., “SSL on requires port 443”)
  • You want immutable Products with flexible construction
  • Step-by-step assembly is natural to read (query, HTTP request, recipe)
  • Combinations of presets and overrides are common
  • You're writing a public API and self-documenting code matters

❌ Skip Builder when…

  • 2–3 required fields — Point(x, y) doesn't need a Builder
  • Object is created in a hot loop — the extra allocations matter
  • All fields required, no validation — constructor is already perfect
  • You'd write more Builder boilerplate than Product code — YAGNI
  • Python's keyword arguments with defaults already solve your problem cleanly
⚠️ The rule of three: don't introduce a Builder until you've seen the constructor explode at least twice. Speculative Builders accumulate methods that nobody ever calls and obscure the real intent of the Product.

🎯 Interview cheat sheet

If asked “implement a Builder for X”:

  1. Sketch the Product first — just the fields. Use @dataclass.
  2. Add the inner Builder class with one private field per Product field, plus sensible defaults.
  3. One setter per field, each returning self. Use add_* for list fields, set_* for scalars.
  4. build(): call _validate(), then construct and return the Product. Make defensive copies of mutable state.
  5. Add a @staticmethod entry point on the Product: def builder(): return Cls.Builder().
  6. Mention when not to use it — that's the signal you've understood the pattern, not just memorized it.

🎯 One-line summary

Builder separates how an object is assembled from what it is. The Product is small and dumb; the Builder is the one that knows how to put it together, validate it, and hand it back complete. Use it when you have many optional fields or complex construction logic — not when a 2-arg __init__ already does the job.

        self._host = self._port = self._user = None

    def set_host(self, h): self._host = h; return self
    def set_port(self, p): self._port = p; return self
    def set_user(self, u): self._user = u; return self

    def build(self):
        if not self._host:
            raise ValueError("host required")
        if not (1024 <= self._port <= 65535):
            raise ValueError("bad port")
        return Database(self._host, self._port, self._user)

db = (DatabaseBuilder()
       .set_host("localhost")
       .set_port(5432)
       .set_user("admin")
       .build())

✔ Same thing with Pydantic

from pydantic import BaseModel, Field

class Database(BaseModel):
    host: str
    port: int = Field(ge=1024, le=65535)
    user: str


db = Database(host="localhost", port=5432, user="admin")

# Invalid value? Validated at construction:
Database(host="localhost", port=80, user="admin")
# pydantic.ValidationError:
#   port: Input should be greater than or equal to 1024

# Missing field? Also caught:
Database(host="localhost", port=5432)
# pydantic.ValidationError: user - Field required
Notice what disappeared: no separate Builder class, no _validate(), no build(), no return self chain. Field(ge=1024, le=65535) on the type annotation does the range check; missing required fields raise automatically; type coercion is built in. Pydantic also gives you .model_dump() for JSON serialization, custom validators, nested models, and more.

So when does Pydantic replace the Builder?

  • ✔ Your construction is “take a dict → validate → get an object” (HTTP request bodies, config files, env vars). Pydantic was built for exactly this.
  • ✔ You want immutable objects with rich type-and-value validation, but don't need step-by-step assembly.

When does Builder still win?

  • ✔ You genuinely need step-by-step assembly — values arrive across multiple files / async calls / branching code paths (recall the “build incrementally” point in the Problem section)
  • ✔ You need cross-field business rules at construction (“if HTTPS is on, port must be 443”) — Pydantic can do this with validators, but the logic gets verbose
  • ✔ The team doesn't use Pydantic — introducing a dependency just for one class is overkill

The honest take: for HTTP request bodies and config-style data, reach for Pydantic first. For domain objects you assemble piece-by-piece in business logic, Builder reads better and keeps you dependency-free. Many real codebases use both, in different layers.
