start here · the problem

Why you don’t send email on the request thread

Before any theory, a bug you will absolutely ship at least once. Let’s feel the pain first — then fix it.

🤔 A user clicks Sign up. Your view creates the account and then calls send_welcome_email(), which talks to an SMTP server, before returning the response. What can go wrong?

▼
  • The SMTP call takes 3–8 seconds on a good day. The user watches a spinner that whole time — for an email they don’t need right now.
  • If the mail server is slow or down, the request times out — and the user sees a 500, even though their account was created fine.
  • That web thread is a scarce resource. While it waits on SMTP, it can’t serve anyone else. A burst of signups can exhaust your thread pool and take the whole site down.

🔫 The scenario, drawn out

The email is slow, flaky, and not urgent — three properties that scream “don’t do this inline.” The fix is to hand the job to something else and return immediately.

🌐 Real world: A checkout that sends its confirmation email inline will happily pass every test on your laptop — then fall over on Black Friday, because your mail provider rate-limits you and every web thread ends up parked on a slow SMTP socket. The order succeeded; the site went down anyway.

🌱 The shift: do it later, somewhere else

Return the response the instant the important work (create the account) is done. The email is a background job — record “send a welcome email to X” somewhere durable and let a separate process handle it. The user gets their 200 in milliseconds.

But where does that “separate process” live, and how durable does it need to be? There’s a whole ladder of answers — let’s climb it before reaching for the heavy tool.

the decision

First — what are your options?

A message queue is powerful, but it isn’t the only way to run work later, and it isn’t always the right one. Here’s the ladder of choices, simplest to most robust — and how to tell which rung your problem is on.

1 · Just do it inline (synchronous)

The default: do the work in the request handler, before returning. Perfect for anything fast that must complete for the response to make sense — writing the user’s row, charging the card, validating input. It only becomes a trap when the work is slow, flaky, or not needed right now — like our email, which then holds the user hostage.

2 · Spawn a background thread

Kick off a thread inside the web process and return. It feels async and needs no new infrastructure. That makes it fine for truly fire-and-forget, low-stakes work you can afford to lose — a best-effort cache warm, a non-critical metric bump. But the moment the work actually matters:

You move the email into a background threading.Thread spawned inside the web process, and return immediately. Why is this still not production-grade?

In-process background work is invisible and unreliable — here’s what actually breaks:
  • The job lives only in that process’s memory. A deploy, an OOM kill, or a crash between ‘return’ and ‘email sent’ silently loses it — the user never gets their email and nobody knows.
  • There’s no retry when SMTP hiccups, no visibility into how many jobs are pending, and you can’t scale the email work independently — it’s glued to your web servers.

3 · A durable table + a worker (the “poor-man’s queue”)

Write the job as a row in your database (an “outbox”), and run a small worker that polls the table, processes rows, and marks them done. Now it’s durable — a crash can’t lose it — and you already have a database. Great for low volume where a little delay is fine: nightly digests, retrying failed webhooks every few minutes.

The catch: polling adds latency, a busy table doesn’t scale, and you slowly reinvent locking, retries, and backoff by hand. At that point you’re building a worse version of… a message queue.

🔎 The three catches, concretely — how each one bites

▼
  • 1) Polling adds latency. The worker sleeps, then checks the table every N seconds. A job that lands just after a check waits nearly the full N before anyone notices (see above). Shorten N to cut the delay and you just pay in wasted queries hammering the DB. A real queue pushes instead, so there’s no wait.
  • 2) A busy table doesn’t scale. Every worker runs SELECT … FOR UPDATE on the same hot pending rows to claim work, so they fight over row locks; the table bloats with done + pending jobs; and all of it lands on your primary database — the one thing you least want to overload.
  • 3) You reinvent queue logic by hand. Claiming a row so two workers don’t grab it (locking), counting attempts (retries), computing the next-try time (backoff), shunting give-ups aside (dead-letter) — every one of these is now your code to write, test and debug. A broker ships all of it, correct, on day one.

4 · A real message queue

A purpose-built broker plus a worker fleet, with durability, retries, backoff, dead-letters, and horizontal scaling already solved. You reach for it when the work is slow/flaky and must-not-be-lost, and/or high-volume, and/or you want to scale and observe it on its own. A welcome email at real scale ticks every box — so that’s where we’re headed.

🧠 The decision, out loud

  • Must it finish before you can answer the user? → keep it inline.
  • Can you shrug if it occasionally vanishes, and volume is tiny? → a background thread is the least machinery.
  • Must it survive restarts, but volume is modest and some delay is fine? → a DB table + worker — a real, durable queue from parts you already have.
  • Slow, flaky, must-not-lose, and busy? → that’s a message queue, and it’s what the rest of this class builds.
💡 The point isn’t ‘always use a queue.’ It’s to climb to one deliberately — when the reliability and scale are worth the broker you take on.
the core idea

Message queues — producer, broker, consumer

One durable buffer in the middle, and two sides that never have to know about each other. This is the whole pattern; everything else is detail.

📋 The three roles

📤
Producer
Whoever creates work. Your web view drops a small message — “send welcome email to alice@x.com” — onto the queue and returns. It never waits for the work to finish.
📥
Broker / Queue
The durable middle-man (Redis, RabbitMQ, SQS…). It stores messages until a consumer takes them, and doesn’t lose them if a worker — or the producer — restarts.
⚙️
Consumer / Worker
A separate process that pulls messages and does the slow work. Add more workers to go faster. They can live on entirely different machines.

🔢 Why the middle-man earns its keep

💡 The mental model: the queue is a to-do list that survives restarts. Producers add to-dos; workers cross them off. Neither needs the other to be online at the same moment — that time-decoupling is the superpower.
reliability

Getting it there: acks, retries & dead letters

A queue is only useful if work actually completes even when things fail. Three mechanisms do the heavy lifting — and they explain a surprising interview favourite: why duplicates are normal.

✅ Acknowledgements — “only cross it off when it’s truly done”

A worker pulls a message but the broker keeps holding it until the worker sends an ack (“done!”). If the worker crashes before acking, the broker assumes it failed and redelivers to another worker. Nothing is lost — this is at-least-once delivery.

A worker pulls the “send email to Bob” job, sends the email, but the process is killed by a deploy one line before it acks. With at-least-once delivery, what happens?

No ack = “assume it failed” = redeliver. That’s the safe default.
  • The broker can’t tell ‘crashed after sending’ from ‘crashed before sending’ — both look like ‘no ack.’ To avoid losing work, it redelivers.
  • So the email might be sent twice. At-least-once trades ‘maybe duplicated’ for ‘never lost’ — almost always the right trade.
  • The fix for the duplicate isn’t ‘better delivery’ — it’s making the consumer idempotent (next section).

🔄 Retries with exponential backoff

Most failures are transient — the mail server blipped, the network flickered. Don’t give up, and don’t hammer it: retry after a growing delay (1s, 2s, 4s, 8s…). Backoff gives a struggling dependency room to recover instead of piling on.

⚠️ Add a little jitter (randomness) to the delay so 10,000 jobs that failed together don’t all retry at the exact same instant — that synchronized stampede is its own outage.

🎉 Why jitter matters — the New Year’s-midnight problem

At the stroke of midnight on New Year’s Eve, millions of people hit “send” on “Happy New Year!” in the same second — and phone networks buckle. Not because the texts are hard, but because they arrive together. Spread the same messages over a few minutes and the network wouldn’t even notice.

Retries behave identically. If 10,000 jobs fail during one blip, they all become “retry in 1s” — so at t+1s they slam the just-recovering service in a single spike and knock it over again (a thundering herd). A random 0–1s jitter smears that spike into a steady trickle.

The math, roughly: N retries landing at the same instant give a peak load of ~N. Spread them evenly over a window W and the peak drops to about N / W per second. For 10,000 retries over 30s, that’s a fall from a 10,000-tall spike to ~330/s — same work, a 30× gentler peak.

☠️ The dead-letter queue — where poison messages go

Some jobs never succeed — a malformed payload, a permanently invalid address. Retrying forever would clog the queue. After N attempts, move the message to a separate dead-letter queue (DLQ): it’s out of the way, nothing is lost, and a human (or an alert) can inspect it later.

One job has a corrupt payload and throws on every attempt. Without a dead-letter queue, what happens to your system?

A poison message with infinite retries is a slow-motion outage.
  • With no cap, the broker keeps handing the poison job back. Workers burn cycles on something that will never succeed.
  • Worse, on an ordered or single-worker setup it can head-of-line block — healthy jobs pile up behind the one that won’t die.
  • A DLQ is the release valve: cap retries, shunt the failure aside, alert someone. The queue keeps flowing; the bad message is preserved for debugging.
the interview favourite

Duplicates are normal — so make consumers idempotent

At-least-once delivery means your consumer will occasionally see the same message twice. You don’t fight that with the broker — you design the consumer so a repeat is harmless.

🔄 What “idempotent” means

An operation is idempotent if doing it twice has the same effect as doing it once. DELETE user 42 is idempotent — the second delete is a no-op.

charge the card ₹500 is not — run it twice and you’ve double-charged. Queues turn “might run twice” from a rare bug into an everyday event, so any consumer doing non-idempotent work must be made safe.

🔑 The standard fix: an idempotency key

Give every job a stable unique id (an idempotency key). Before doing the effect, check whether that key was already handled; if so, skip. Record the key atomically with the effect so a crash can’t leave “done but not recorded.”

# consumer, made idempotent
def send_welcome(job):
    key = job["idempotency_key"]          # e.g. "welcome:user:42"
    if SentEmails.exists(key):            # already handled? no-op
        return
    smtp.send(job["email"])               # the real (non-idempotent) effect
    SentEmails.insert(key)                # remember we did it
# a redelivery of the same key now short-circuits at line 4.
💬 What it does: A DB unique constraint on the key is the bulletproof version: the second insert fails, and you treat that failure as ‘already done.’

Your payment worker gets messages at-least-once. Which change makes a redelivered “charge ₹500” safe?

You can’t buy your way out with delivery mode — you design the effect to be repeat-safe.
  • ‘Exactly-once delivery’ across a network is effectively a myth (next section). Relying on it is how you get double charges in production.
  • The idempotency key lets the worker recognise a repeat and skip the second charge — turning at-least-once delivery into effectively-once processing.
  • The payment provider gives you this hook for real: pass an Idempotency-Key header and they dedupe on their side too. Same idea, one layer down.
two shapes & two myths

Work-queue vs pub/sub — and the ordering myths

Two delivery shapes cover most needs, and two ‘requirements’ you’ll be asked for that you should gently push back on.

🔄 One message, one worker — vs — one event, everyone

Click a row to reveal its cells — guess each first.

PatternOne message goes to…Use it when…
Work queue (point-to-point)exactly one of the competing workersyou have tasks to get done once — send this email, resize this image. Add workers to go faster.
Pub/Sub (fan-out)every subscriber gets its own copyone event must trigger many independent reactions — ‘order placed’ → email + analytics + inventory + push, each decoupled.

An order.placed event must trigger four independent things: a confirmation email, an analytics update, an inventory decrement, and a push notification — each owned by a different team. Which shape fits?

‘Many independent reactions to one event’ is the textbook pub/sub case.
  • A single worker doing all four couples unrelated teams: if analytics is down, the email doesn’t send. And you can’t scale them separately.
  • With pub/sub, checkout publishes order.placed once and moves on. Each service consumes its own copy, retries its own failures, and deploys on its own schedule.
  • Rule of thumb: a task to do once → work queue; an event others react to → pub/sub.

🤷 “We need messages in order” — do you, though?

A plain work queue with several competing workers gives no global ordering — job 2 can finish before job 1. Strict order costs you: it means a single consumer (no parallelism) or per-key partitioning (Kafka-style).

But often you don’t need total order — just per-entity order (all events for user 42, in order). Routing by a key gives you that cheaply, without serialising everything.

💡 Before asking for global ordering, ask: do I need every message ordered, or just messages about the same thing? The second is far cheaper — route by a key so one entity’s events land on one partition/worker.

🏹 The “exactly-once delivery” myth

Everyone wants exactly-once. But across an unreliable network it’s effectively unachievable at the delivery layer: the ack can be lost even when the work succeeded, so the sender must choose — risk losing it (at-most-once), or risk repeating it (at-least-once).

So in practice you pick at-least-once + idempotent consumers. Reprocessing is harmless, so the effect happens exactly once — the outcome you actually wanted.

A candidate says “I’ll configure the queue for exactly-once delivery so I never handle a message twice.” Best response?

Aim for exactly-once processing, achieved by at-least-once + idempotency — not a magic delivery mode.
  • A lost ack is indistinguishable from lost work, so the sender must risk a duplicate or a loss. ‘Exactly-once delivery’ as a network guarantee is marketing more than reality.
  • At-most-once (fire and forget) never duplicates but loses messages on failure — unacceptable for a welcome email, let alone a payment.
  • The real answer — at-least-once delivery + an idempotency key — makes reprocessing harmless, so the effect happens exactly once. That’s what ‘exactly-once’ should mean.

🐚 Celery — the Python task queue

Celery is the standard way Python apps run background jobs. You write a normal function, mark it a task, and call .delay(...) to enqueue it. A broker (Redis/RabbitMQ) holds the job; a Celery worker process pulls and runs it — with retries, backoff, and dead-lettering built in.

# tasks.py
from celery import shared_task

@shared_task(bind=True, max_retries=5, acks_late=True)
def send_welcome_email(self, email):
    try:
        send_mail("Welcome!", "Glad you're here.", "no-reply@app.com", [email])
    except SMTPException as exc:
        # retry after 2**attempt seconds: 1s, 2s, 4s, 8s, 16s
        raise self.retry(exc=exc, countdown=2 ** self.request.retries)

# views.py  ->  the producer side, in your request handler
send_welcome_email.delay(user.email)   # enqueue and return NOW
return JsonResponse({"status": "queued"})
💬 What it does: .delay() drops a message on the broker and returns in ~1ms. The worker — a separate process, often on another machine — does the slow send. acks_late=True means the job is only acked after it finishes, so a mid-send crash gets it redelivered.
going deeper · optional

Kafka, one level deeper

We’ve treated Kafka as ‘the log-shaped one.’ Here’s its architecture and vocabulary in plain terms — enough to hold your own in a system-design chat — and the confusions that trip people up.

🧩 A partition is an append-only log (not a queue)

This is the one idea that unlocks Kafka. A topic is a stream of messages; each topic is split into partitions, and a partition is an append-only log: producers add at the tail, every message gets a sequential offset, and — crucially — nothing is deleted when you read it. Each consumer simply remembers its own offset, so it can rewind and replay.

👥 Consumer groups — how Kafka parallelises

Consumers join a named consumer group. Inside a group, each partition is handled by exactly one consumer — so you scale by adding consumers, but only up to the number of partitions. Beyond that, extra consumers sit idle. Meanwhile a different group reads the same partitions on its own offsets — that’s the pub/sub side of Kafka.

🧐 Common Kafka confusions — myth vs reality

Click a row to reveal its cells — guess each first.

The mythThe reality — (tap)
“Kafka is just a message queue.”It’s a distributed log. A queue deletes a message once consumed; Kafka keeps it for the retention window and consumers track offsets — so many consumers, and re-runs, can read the same data.
“More consumers always = more throughput.”Parallelism is capped at the partition count. On a 3-partition topic, a 4th consumer in the group just sits idle. Add partitions to scale further.
“Kafka gives me global ordering.”Only per-partition ordering. Across partitions there’s none. Send related events with the same key to keep those in order.
“Kafka is real-time / instant.”It’s high-throughput, not low-latency RPC. Consumers poll, so there’s a small delay — great for streams, wrong tool for ‘reply in 5 ms.’
“Exactly-once is just a checkbox.”Possible (idempotent producer + transactions), but subtle. The robust everyday choice is still at-least-once + idempotent consumers — same lesson as the rest of this class.
“Kafka needs ZooKeeper.”Not anymore — modern Kafka runs in KRaft mode and manages its own metadata; ZooKeeper is being retired.

🍏 macOS gotcha (so the demo doesn’t die on stage): if the worker crashes the instant a task runs, with a fork() / __NSPlaceholderDate error, start terminal B with the fork-safety guard instead: OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES celery -A config worker -l info.

📜 What does celery -A config worker -l info actually say?

▼
  • celery — the Celery command-line tool (it comes with the celery package, so it only exists inside the venv).
  • -A config — the app: “look in the config package for the Celery app” (our config/celery.py). That’s how the worker discovers your tasks and the broker URL.
  • worker — run a worker process: the consumer that pulls messages off the broker and runs the task functions. (Other subcommands exist, e.g. celery -A config beat for scheduled tasks.)
  • -l info — log level = info, so you watch each task get received, retried, and finished. -l warning is quieter.
  • Handy extras: -c 4 sets concurrency (4 worker processes at once); -Q emails would make this worker consume only a queue named emails.

Now watch the split happen

  • Enqueue & return instantly: curl -i "http://127.0.0.1:8000/signup/?email=normal@example.com" → HTTP 202 {"status":"queued"} in about 4 ms. The request never touched SMTP.
  • See it sent off-thread: flip to terminal B — a moment later the worker log prints [sent] welcome email delivered to normal@… on attempt 1. That’s the work happening after the response already went out.
  • See a retry: curl ".../signup/?email=fail@example.com" → the worker logs [retry] … attempt 1 … in 1s, then attempt 2 … in 2s, then [sent] … on attempt 3 — the transient-failure loop, live.
  • See a dead-letter: curl ".../signup/?email=poison@example.com" → four failing attempts (backoff 1s→2s→4s), then [dead-letter] giving up … — a DeadLetter row is written instead of the worker crashing.
  • See idempotency: fire the same normal@example.com signup twice — the second run logs [idempotent] … already sent -- skipping duplicate. Duplicate delivery, zero double-emails.
🎯 The one thing to take away from the demo: terminal C answered in ~4ms while terminal B did the slow, flaky, retryable work. That gap — between ‘request done’ and ‘job done’ — is the entire point of a message queue.
prep

Message queues in interviews

System-design rounds lean on this constantly. Each answer is about trade-offs, not definitions — try saying each out loud before opening it.

“A user action needs to send an email / SMS / push. Walk me through it.”

▼

🎯 What they’re really testing: whether you instinctively move slow, non-urgent work off the request path.

  • Do the critical part inline (create the account), then enqueue the notification and return — the response shouldn’t wait on a mail server.
  • Name the pieces: producer (the web view), broker (Redis/SQS), consumer (a worker), with retries + backoff and a DLQ for permanent failures.
  • Mention idempotency unprompted — at-least-once means the send can fire twice, so dedupe on a key.

“Your queue delivers at-least-once. How do you avoid double-charging a customer?”

▼

🎯 What they’re really testing: that you know delivery guarantees can’t be wished away — you fix it at the consumer.

  • Make the consumer idempotent: attach a unique idempotency key to each charge and skip a key you’ve already processed — ideally enforced by a DB unique constraint.
  • Note that the payment provider also accepts an Idempotency-Key, so the dedupe holds even if your worker retries after a lost response.
  • Reframe the goal: not exactly-once delivery, but exactly-once effect.

“One event needs to update five different services. Queue or pub/sub?”

▼

🎯 What they’re really testing: work-queue vs fan-out, and decoupling teams.

  • Pub/Sub: publish the event once; each service subscribes and reacts independently, with its own retries and deploy schedule.
  • A single worker doing all five couples them — one slow/broken consumer shouldn’t block the others.
  • Contrast with a work queue, which you’d use when the event is really one task to be done by one worker.

“What happens to a job that keeps failing?”

▼

🎯 What they’re really testing: retry policy and the dead-letter safety valve — do you have a plan for permanent failure?

  • Retry a bounded number of times with exponential backoff + jitter — most failures are transient.
  • After the cap, route it to a dead-letter queue so it stops burning workers and can be inspected/alerted on.
  • Never retry forever inline — a poison message with infinite retries is an outage, and can head-of-line block healthy work.
