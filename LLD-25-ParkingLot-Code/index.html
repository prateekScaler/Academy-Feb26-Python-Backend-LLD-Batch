💭 What does "ids, not live refs — outlives the stay" mean?

▾
  • The Ticket stores the spot's id (a string like "F1-M0"), not a live Spot object. So ticket.spot_id == "F1-M0", not a pointer to the actual Spot sitting in memory.
  • "Outlives the stay" — a ticket is a record. It's billed, audited, and may live in a database long after the car has driven off and the in-memory Spot object is gone. Its data has to stay valid and self-contained on its own.
  • Why not a live reference? Holding the live Spot object would pin it in memory, break the moment you save the ticket to a file or DB (you can't cleanly serialise a live object), and tangle the ticket's lifetime with the spot's. An id is just plain data — it survives a restart, a DB round-trip, even a different machine.
  • The rule: records point at other things by id, not by object — the same reason a database uses a foreign key, not a pointer. That spot_id is literally the FK column in the schema.

Now derive the methods — from the FRs, one verb at a time

The boxes above carry only the fields (the nouns). The methods aren't drawn yet, on purpose — same drill as Tic-Tac-Toe: read each FR as a verb and ask "whose job is it?" Warm up on three.

FR-5 — "pays a fee from the parked duration and the spot's size." Whose method is fee()?

B. FR-8 ("the pricing scheme can change independently") is the tell — pricing is a Strategy, so fee() lives on PricingStrategy and TieredHourly / WeekendFlat swap with zero edits. Ticket / Payment hold data, not the rule; ParkingLot just delegates.

FR-2 / FR-4 — a vehicle fits only a free spot of its size. Whose method is can_fit()?

C. The rule needs the spot's size AND status — both already live on Spot, so the rule belongs there too (reaching into another object's data would be feature envy). The strategy decides which spot to try; the spot answers whether it can take this vehicle.

FR-3 + FR-8 — assign a free spot, by a policy that can change. Whose method is pick()?

B. FR-8 again — "the spot-assignment policy can change independently" → Strategy. A floor sees only itself, but placement is a cross-floor decision; ParkingLot delegates to the injected strategy, blind to which one.

Now — what arguments should each method take?

Knowing where a method lives is half of it; the signature is the other half. The arguments decide how coupled — and how testable — the method is.

What should pick() receive?

B. pick needs exactly two things: the floors it may choose among, and the vehicle (to look up its required size). Passing the whole ParkingLot (A) drags in payment and ticket state the strategy has no business seeing — the Interface Segregation Principle: hand it the narrowest input. Just the vehicle (C) can't place anything (no floors); a single Floor (D) can't make a cross-floor choice like LeastCrowded. Narrow inputs = a strategy that can't reach for what it shouldn't.

What should fee() receive?

B. You bill the resource you occupied — the spot's size — not the vehicle (a truck squeezed into a small spot pays the small rate). And take the raw unit, seconds, letting the pricing rule own the rounding (deep-dive below). The whole Ticket (C) over-couples the strategy to ticket internals; (size, hours) (D) pre-rounds and steals a decision the strategy should make.
Deeper on fee's duration — why seconds, not hours?
  • Pass the rawest unit; let the policy round. "Hours" has already baked in a rounding decision — but rounding belongs to the pricing rule, not the caller.
  • Different strategies round differently — TieredHourly rounds up to the next hour; a per-minute scheme wouldn't. Seconds keep each one free to decide.
  • It's lossless and free — now - entry_time already gives you seconds (a float). Converting to hours at the boundary throws away precision the strategy might want.
  • The rule of thumb: push precise, raw data inward; let the policy at the edge interpret it — the same instinct as injecting the clock (now) instead of reading it.

API & design decisions — quiz

You designed the REST endpoints in Discussion #20. Before we lock the method signatures, pressure-test the calls interviewers actually probe.

📋 The 9 functional requirements — the contract we're coding to

▾
  1. The parking lot has one or more floors, and each floor has a fixed set of parking spots.
  2. Every spot has a size (small / medium / large), and every vehicle type maps to exactly one spot size (bike→small, car→medium, truck→large).
  3. A vehicle entering is assigned a free spot, and the driver receives a ticket recording the vehicle, the spot, and the entry time.
  4. If no suitable spot is free, the vehicle is turned away at the gate.
  5. A leaving vehicle surrenders its ticket and pays a fee from the parked duration and the spot's size.
  6. The moment a vehicle leaves, its spot becomes free for the next.
  7. The lot can report free spots per size — per floor and in total.
  8. The spot-assignment policy and the pricing scheme can each change independently.
  9. A ticket is paid exactly once, before exit — the gate opens only for a paid ticket (cash / card / UPI).

REST endpoints — turning use cases into an API

A vehicle enters and you issue a ticket. Which endpoint?

C is right.
  • 📍 Endpoint — /tickets: a ticket is a new item in the tickets collection
  • 🔧 Method — POST: creates a resource → returns 201 Created
  • 📦 Body — { "vehicle": { "plate": "KA-01-1234", "type": "car" } }
  • ✗ Not the rest — GET must never mutate (A) · /park is a verb, not a noun (B) · the spot's occupy is a side-effect, not the resource you return (D)

The lot is full when the car arrives. What should POST /tickets return?

C is right.
  • 📍 Endpoint — POST /tickets (the same call as a normal entry)
  • 📨 Response — 200 { "ticket": null } (or 409 Conflict): a full lot is an expected answer, not a crash. Mirrors the engine's Ticket | None
  • ✗ Not the rest — 500 = we broke (A) · 404 = route/lot missing (B) · 402 is for unpaid exit (D)
  • 💡 Contrast — real violations DO get codes: exit-before-pay→402, unknown ticket→404, double pay→409

The booth shows what's owed so far. Which call?

B is right.
  • 📍 Endpoint — /tickets/{id}/due: the amount is a sub-fact of the ticket
  • 🔧 Method — GET: a pure read, safe to call twice, nothing changes
  • 📦 Body — none (the server fills in now from its own clock)
  • ✗ Not the rest — POST is for changes (A, D) · /pay/{id} names the wrong resource (C)

The driver pays. Which call records it?

B is right.
  • 📍 Endpoint — /tickets/{id}/payments: paying creates a Payment under the ticket
  • 🔧 Method — POST: creates a record → 201 Created
  • 📦 Body — { "method": "upi" }
  • ✗ Not the rest — {paid:true} loses the payment details (A) · /pay is a verb (D) · GET must not mutate (C)

The car leaves. Is exit a DELETE on the ticket?

B is right.
  • 📍 Endpoint — /tickets/{id}/exit: an action on the ticket
  • 🔧 Method — POST: a state transition (stamp exit_time, free the spot, open the gate), not a deletion — the ticket lives on for audit
  • 📦 Body — none
  • ✗ Not the rest — DELETE throws away the record you need (A) · PUT /spots is the tempting wrong answer (C, below) · GET must not mutate (D)

Why PUT /spots/{id} (C) feels right but isn't: freeing the spot is just one side-effect of exiting, not the operation itself. Address the spot directly and you:

  • skip the gate's paid-check — an unpaid car frees its own spot and drives off (FR-9 gone);
  • never stamp the ticket's exit_time — so the fee, billing, and audit trail stay open forever;
  • hand the caller an invariant the service owns — "a spot frees only via a valid exit." Any client could now flip a spot to FREE on a whim.

Exit is a ticket-level transaction — verify paid → free the spot → stamp the time → open the gate — and the spot change is the lot's job inside that transaction, never the client's.

A ticket is already paid; a second payment arrives. Status code?

B is right.
  • 📍 Endpoint — POST /tickets/{id}/payments (the second attempt)
  • 📨 Status — 409 Conflict: the request conflicts with the resource's current state (already paid)
  • 🔧 Engine — AlreadyPaidError, which the controller maps to 409
  • ✗ Not the rest — 200 would silently double-charge (A) · 402 means "you still owe" (C) · 5xx is a crash (D)

An unpaid car tries to exit. Status code?

B is right.
  • 📍 Endpoint — POST /tickets/{id}/exit
  • 📨 Status — 402 Payment Required: the gate opens only for a paid ticket (FR-9)
  • 🔧 Engine — UnpaidExitError
  • ✗ Not the rest — 403 = never allowed (A) · 404 = ticket missing, not the issue (C) · 200 would let an unpaid car out (D)

Show free MEDIUM spots on floor 2. Which call?

B is right.
  • 📍 Endpoint — /availability?size=medium&floor=2: filters live in the query string
  • 🔧 Method — GET: a read, safe and cacheable
  • 📦 Body — none (the filters are the query params; both are optional)
  • ✗ Not the rest — POST misuses a read (A) · path-baked filters get rigid (C, D) — "all sizes / all floors" needs a whole new route

Admin marks spot F2-M0 out of order. Which call?

B is right.
  • 📍 Endpoint — /spots/{id}: the spot already exists, addressed by id
  • 🔧 Method — PATCH: changing one field (status), not replacing the whole object
  • 📦 Body — { "status": "OUT_OF_ORDER" }
  • ✗ Not the rest — DELETE removes the spot, which still exists (A) · PUT needs every field (C) · /break is a verb (D)

Design decisions interviewers probe

Spot status: occupied: bool or status: SpotStatus (an enum)?

C. Our SpotStatus already has three states — FREE / OCCUPIED / OUT_OF_ORDER — and a bool can't say "neither free nor taken" (oil spill, broken sensor). Even at two states an enum is self-documenting and future-proof (RESERVED, EV_ONLY land as one line). Bools are for true binaries like is_deleted. (The GameStatus lesson from TTT, again.)

TicketRepository mints ids. Auto-increment T-0001, UUID, or timestamp?

C. For our single-lot MVP, T-0001 is readable and fine — just mention thread-safety. The moment there are several entry gates (distributed), a shared counter races and leaks your volume; switch to a UUID or a hybrid (TKT-{ts}-{short-uuid}). The win: the repository owns id allocation (next_id()), so swapping the scheme touches one method and nothing else.
The id schemes, at a glance — pros & cons:
  • Auto-increment (T-0001) — ✅ short, readable, sortable, easy to debug · ❌ needs a lock to be thread-safe, breaks across distributed gates, leaks your volume (a rival counts your tickets).
  • UUID — ✅ globally unique, no coordination, distributed-safe, hides volume · ❌ long & unreadable, not time-sortable, heavier as a DB key.
  • Timestamp-based — ✅ time-sortable, fairly readable · ❌ collides within the same tick (needs a suffix), and clock skew bites in distributed setups.
  • Hybrid (TKT-{ts}-{short-uuid}) — readable prefix + sortable + collision-safe; the usual production compromise.

Why pay() and exit_lot() as two methods, not one pay_and_exit()?

B. Paying and leaving are distinct events, and between them the ticket is paid but the car is still parked — exactly the state the gate checks before lifting the barrier ("paid? open"). Fusing them hides that state and the FR-9 guard, and blocks "pay online now, drive out later." One method is right only when the two are always atomic — here they aren't.

repo.find(ticket_id) for a ticket that isn't there — return None, raise, or a Null Object?

B. find() returning None keeps the repository dumb about meaning — "not here" is data, not a verdict. The service draws the line: for pay()/exit_lot() a missing ticket is a violation, so it raises InvalidTicketError; but find() itself shouldn't presume. A Null Object (C) silently no-ops and hides bugs; always-raising (A) steals the caller's choice. (The FR-4 flip once more: expected-absence is a value; the service decides when it's a violation.)
Step 5 — APIs

Signatures, and why not the alternative

Warm-up quiz — every method is told the current time as an argument (now) instead of reading the clock itself. Why hand the time in from outside?

B — it makes the fee testable.
  • The problem if a method reads the clock itself: how do you check "a 2-hour stay costs ₹180"? You'd have to actually wait 2 hours.
  • The fix: hand the time in. The demo just writes park(…, now=0) and exit_lot(…, now=2*HOUR) — the fee is checked instantly and exactly.
  • The rule of thumb: anything unpredictable — the clock, random numbers, the network — gets passed in, not reached for. (Same trick as the LoadedDice in Snake & Ladder.)
  • In production you pass the real time.time() at exactly one spot: the call site (the gate).

park(vehicle, now) → Ticket | None — why not raise on full?

▾

The LLD-24 flip, now in the signature: a full lot is an expected outcome (the gate shows "FULL"), not a contract violation — so it's a value, not an exception. The type hint Ticket | None makes mypy force every caller to handle the full case. The Aug-25 batch's reference design raises NoSpotAvailableException here instead — defensible! — but then a routine Tuesday morning runs on exceptions. State your criterion either way.

pay() and exit_lot() — why two methods, not one pay_and_exit()?

▾

Because they are two real-world events with time between them: you pay at the booth, then drive five minutes to the barrier. Welding them together makes the in-between state (paid-but-still-parked) unrepresentable — and that state is exactly what the exit gate checks. Separating them is also what creates FR-9's contract: pay() twice → AlreadyPaidError; exit_lot() unpaid → UnpaidExitError. Each method guards its own rule. (amount_due() completes the trio as a pure read — the booth display calls it every second and nothing mutates.)

exit_lot(ticket_id, now) — why the id and not the Ticket object?

▾

Because that's what physically happens: the driver hands over a paper id, and the lot looks up its own record in _active. Accepting a caller-supplied Ticket object means trusting state you didn't produce — a forged or stale object walks right in. Rule of thumb with a long life ahead of it (every web API you'll ever write): accept ids, look up your own truth.

ParkingStrategy.pick(floors, vehicle) — why floors, not the whole lot?

▾

The strategy needs exactly one thing: the floors to search. Hand it the whole ParkingLot and it can reach _payments, pricing, even call exit_lot() — nothing stops next month's clever strategy from depending on all of it, and now the lot's internals are load-bearing. Narrow parameter = enforced ISP. Same reason WinRule.winner(board) took the board, not the Game.

PricingStrategy.fee(size, seconds) — why the spot size, not the vehicle?

▾

You pay for the resource you occupied, not the vehicle you drove — if policy someday lets a bike take a medium spot, it pays medium rates, and no pricing code changes. And why not pass the whole Ticket? Pricing needs two facts; couple every scheme to the Ticket's shape and adding a field means re-checking five strategies. Counter-argument worth voicing: a loyalty scheme might need the plate or visit history — at that point you widen the signature deliberately. Start narrow, widen on evidence.

Spot.can_fit(vehicle) — why does the spot decide?

▾

"Free AND sized for this vehicle" is the invariant of FR-2 + FR-6, and it lives in exactly one place — on the object that owns both facts (and it consults SPOT_SIZE_FOR, so the policy dict stays the single source of the mapping). Put it in each strategy instead and one of them eventually forgets the size check; a truck gets a bike spot; nobody knows which class to blame. Tell, don't ask: the spot knows.

Step 6 — Patterns & edge cases

What the code must honour

🎯 Two Strategies, independent

Placement (FirstFit/LeastCrowded) and billing (TieredHourly/WeekendFlat) vary on separate axes — two objects, injected separately. The demo swaps each without touching the other.

🧮 The records, again

TTT's moves list reappears twice: the ticket log (who's parked where) and the payment log (who paid what). Billing reads them, audit IS them, replay rebuilds the lot. Event-log thinking, third appearance.

🔗 Policy as data

SPOT_SIZE_FOR and the tiered RATES table are dicts, not code. Adding scooters, buses, or a new rate card is a data edit — the classes never hear about it.

The four layers, as four folders

Read the tree top-to-bottom and you've read the backend stack we map onto at the end — the folders are the layers, named in advance:

cli.py → Controller — parse input, call the service, format the result, map exceptions to messages. Built on the carried console.py; the only file that calls input()/print().
service.py → Service — ParkingLot: business rules + orchestration. Holds the two Strategies and two Repositories; knows no HTTP and (now) no storage details.
repositories/ → Repository — the storage seam: save / find / delete / exists. In-memory dicts today; swap for DB-backed classes and the service never notices.
models/ + enums + config → Domain — Spot, Floor, Ticket, Payment, the four enums, the size mapping. Pure objects; importable anywhere; testable with zero setup. strategies/ sit beside them as the two pluggable policies.

The one real upgrade over the single file: dicts become repositories

In plain words: a repository is a small object whose only job is "where the data lives." It can save something, find it by id, and answer exists? — and nothing else in the code knows whether a dict, a file, or a database sits underneath.

⭕ Tic-Tac-Toe had none

A game is played and thrown away. Its state lives in memory for one match — nothing to look up later, bill, or keep after a restart. No data outlives the call, so there's nothing to store.

🅿 A parking lot is a system

Tickets and payments get looked up, billed, audited, and must survive a restart. The moment data outlives a single call you have storage — and storage deserves its own object, not a loose dict buried in the service.

  • The pay-once guard is now a query — ticket_id in self._payments → self.payments.exists(ticket_id); the service can't tell a dict from a SELECT 1 … WHERE ticket_id = ?. In a DB that invariant is a UNIQUE(ticket_id) constraint.

How to design a repository — the recipe

  • One per aggregate root — TicketRepository, PaymentRepository; not one giant "DAO" for everything.
  • A tiny, intention-revealing contract — only the verbs the service needs: save(entity) · find(id) → entity | None · exists(id) → bool · delete(id) · next_id().
  • Speak the domain, not the database — methods take and return domain objects (Ticket), never rows or SQL strings; the repo translates between the two.
  • Absence is data, not an error — find() returns None, it doesn't raise; the service decides when "missing" is a violation.
  • No business logic inside — a repo stores and retrieves; rules (pay-once, fees) live in the service. The moment it grows an if about money, it's leaking.
  • Injected, not new-ed inside — a fake in-memory repo drops in for tests, a DB-backed one for prod, service unchanged.
class TicketRepository:              # one per aggregate root
    def __init__(self):
        self._by_id: dict[str, Ticket] = {}
        self._seq = count(1)
    def next_id(self) -> str:          return f"T-{next(self._seq):04d}"
    def save(self, t: Ticket) -> None:   self._by_id[t.ticket_id] = t
    def find(self, id: str) -> Ticket | None:  return self._by_id.get(id)
    def exists(self, id: str) -> bool:   return id in self._by_id
    def delete(self, id: str) -> None:   self._by_id.pop(id, None)

Quick check — you swap TicketRepository for a Postgres-backed one. Which file changes?

C. That's the entire point of the seam. The service depends on the contract — save / find / delete / next_id — not on the implementation. A new class honouring those four methods drops in; you change the one place that wires it up (main.py or a factory), and service.py never learns the difference. }


# === Errors — only for contract violations (FR-4 returns None instead) ======
class InvalidTicketError(Exception):
    """Unknown or already-used ticket — unlike a full lot, this IS exceptional."""


class AlreadyPaidError(Exception):
    """A ticket is paid exactly once (FR-9)."""


class UnpaidExitError(Exception):
    """The gate opens only for a paid ticket (FR-9)."""


@dataclass(frozen=True)
class Vehicle:
    plate: str
    kind: VehicleType


# === Spot — the Cell analogue: two facts + the rules relating them ===========
@dataclass
class Spot:
    spot_id: str
    size: SpotSize
    status: SpotStatus = SpotStatus.FREE

    def is_free(self) -> bool:
        return self.status is SpotStatus.FREE

    def can_fit(self, vehicle: Vehicle) -> bool:
        return self.is_free() and self.size == SPOT_SIZE_FOR[vehicle.kind]

    def occupy(self) -> None:
        self.status = SpotStatus.OCCUPIED

    def free(self) -> None:
        self.status = SpotStatus.FREE

Stage 2 — Floor, Ticket, Payment

Floor answers its own questions (FR-7). The two records store ids, not live objects — they outlive the stay. Payment is frozen: money doesn't mutate.

# === Floor — identity + its own queries (FR-7) ===============================
class Floor:
    def __init__(self, number: int, spots: list[Spot]):
        self.number = number
        self.spots = spots

    def free_spots(self, size: SpotSize) -> list[Spot]:
        return [s for s in self.spots if s.is_free() and s.size == size]

    def free_count(self, size: SpotSize) -> int:
        return len(self.free_spots(size))

Stage 3 — the two open variables

Each policy is one class. Adding NearestToExit or WeekdayPeak touches nothing else — that's the FR-8 promise, kept. Note the tiered table is itself data.

# === Strategy 1: where to put the vehicle (FR-8) =============================
class ParkingStrategy(ABC):
    @abstractmethod
    def pick(self, floors: list[Floor], vehicle: Vehicle) -> tuple[Floor, Spot] | None: ...


class FirstFit(ParkingStrategy):
    """First free spot of the right size on the lowest floor — minimises walking."""

    def pick(self, floors: list[Floor], vehicle: Vehicle) -> tuple[Floor, Spot] | None:
        for floor in floors:
            for spot in floor.spots:
                if spot.can_fit(vehicle):
                    return floor, spot
        return None


class LeastCrowded(ParkingStrategy):
    """Floor with the most free spots of that size — spreads congestion."""

    def pick(self, floors: list[Floor], vehicle: Vehicle) -> tuple[Floor, Spot] | None:
        size = SPOT_SIZE_FOR[vehicle.kind]
        best = max(floors, key=lambda f: f.free_count(size), default=None)
        if best is None or best.free_count(size) == 0:
            return None
        return best, best.free_spots(size)[0]


# === Strategy 2: what to charge (FR-5 + FR-8) ================================
class PricingStrategy(ABC):
    @abstractmethod
    def fee(self, size: SpotSize, seconds: float) -> float:
        """You pay for the spot you occupied, not the vehicle you drove."""


class TieredHourly(PricingStrategy):
    """First hour at one rate, every extra hour at another — per spot size."""

    RATES = {  # size: (first_hour, each_extra_hour)
        SpotSize.SMALL: (50, 80),
        SpotSize.MEDIUM: (80, 100),
        SpotSize.LARGE: (100, 120),
    }

    def fee(self, size: SpotSize, seconds: float) -> float:
        hours = max(1, math.ceil(seconds / 3600))   # minimum 1 hour, round up
        first, extra = self.RATES[size]
        return first + (hours - 1) * extra


class WeekendFlat(PricingStrategy):
    """Flat ticket regardless of duration — mall promo."""

    def fee(self, size: SpotSize, seconds: float) -> float:
        return 100.0

Stage 4 — ParkingLot, the orchestrator

Read the command trio top to bottom: park asks the strategy → marks the spot → writes the record; pay guards pay-once → writes the second record; exit_lot guards paid → frees → stamps.

# === ParkingLot — the orchestrator ===========================================
class ParkingLot:
    def __init__(self, floors: list[Floor],
                 parking: ParkingStrategy, pricing: PricingStrategy):
        self.floors = floors
        self.parking = parking
        self.pricing = pricing
        self._active: dict[str, Ticket] = {}
        self._payments: dict[str, Payment] = {}
        self._ids = count(1)

    # --- commands ---------------------------------------------------------
    def park(self, vehicle: Vehicle, now: float) -> Ticket | None:
        """None when no suitable spot exists — expected flow, not an error."""
        picked = self.parking.pick(self.floors, vehicle)
        if picked is None:
            return None
        floor, spot = picked
        spot.occupy()
        ticket = Ticket(f"T-{next(self._ids):04d}", vehicle,
                        floor.number, spot.spot_id, entry_time=now)
        self._active[ticket.ticket_id] = ticket
        return ticket

    def pay(self, ticket_id: str, method: PaymentMethod, now: float) -> Payment:
        ticket = self._require_active(ticket_id)
        if ticket_id in self._payments:
            raise AlreadyPaidError(f"{ticket_id} is already paid (FR-9: pay exactly once)")
        amount = self.pricing.fee(self._spot_of(ticket).size, now - ticket.entry_time)
        payment = Payment(f"P-{next(self._ids):04d}", ticket_id, amount, method, now)
        self._payments[ticket_id] = payment
        return payment

    def exit_lot(self, ticket_id: str, now: float) -> Ticket:
        ticket = self._require_active(ticket_id)
        if ticket_id not in self._payments:
            raise UnpaidExitError(f"{ticket_id} is unpaid — the gate stays down")
        self._spot_of(ticket).free()             # FR-6: free the moment it leaves
        ticket.exit_time = now
        del self._active[ticket_id]
        return ticket

    # --- queries (FR-7) ---------------------------------------------------
    def amount_due(self, ticket_id: str, now: float) -> float:
        """What the booth display shows — a read, no mutation."""
        ticket = self._require_active(ticket_id)
        return self.pricing.fee(self._spot_of(ticket).size, now - ticket.entry_time)

    def available(self, size: SpotSize) -> int:
        return sum(f.free_count(size) for f in self.floors)

    def per_floor(self, size: SpotSize) -> dict[int, int]:
        return {f.number: f.free_count(size) for f in self.floors}

    def render(self) -> str:
        marks = {SpotStatus.FREE: " {} ", SpotStatus.OCCUPIED: "[{}]",
                 SpotStatus.OUT_OF_ORDER: " # "}
        return "\n".join(
            f"F{f.number}: " + " ".join(
                marks[s.status].format(s.size.value[0]) for s in f.spots)
            for f in self.floors)

    # --- internals --------------------------------------------------------
    def _require_active(self, ticket_id: str) -> Ticket:
        ticket = self._active.get(ticket_id)
        if ticket is None:
            raise InvalidTicketError(f"unknown or already-used ticket: {ticket_id}")
        return ticket

    def _spot_of(self, ticket: Ticket) -> Spot:
        floor = next(f for f in self.floors if f.number == ticket.floor_no)
        return next(s for s in floor.spots if s.spot_id == ticket.spot_id)

The dynamic view

The objects, talking — a sequence diagram

The class diagram is a photo: who exists, who owns whom. It froze the question "whose job is each method?" A sequence diagram is the film: the same objects, but now who calls whom, in what order. It's the artefact that answers the interviewer's very next line — "walk me through what happens when a car parks."

Three views, one system — know which question each answers:
  • Class diagram — the nouns and who-owns-whom. Static. (We drew it at the top.)
  • Sequence diagram — the verbs, ordered in time, across objects. Dynamic, one use case. (Here.)
  • State machine — one object's legal states and the moves between them. One entity's whole life. (Below — and it's where the exceptions come from.)

Use case: "a car parks"

One sentence, one diagram. Read it top-to-bottom: time flows down; a solid arrow is a call, a dashed arrow is a return, a bar means "this object is on the stack right now", and the «create» arrow is where the Ticket is born — its lifeline starts there, not at the top.

Notice what the picture makes obvious that the code hides: ParkingLot is the hub — every arrow either leaves it or returns to it. The strategy, the spot, the repository never talk to each other; they each answer the service and go quiet. That single-hub shape is the Mediator-flavoured orchestration the service layer exists to provide.

…and the rest of its life: pay then exit

Two more short use cases, same shape. Rather than redraw the lifelines, read them as a message trace — each line is one arrow:

💳 pay(T-0001, UPI, t2)
  1. Driver → lot: pay(T-0001, UPI, t2)
  2. lot → tickets: find(T-0001) → the ticket (else InvalidTicketError)
  3. lot → payments: exists(T-0001) → false (the pay-once guard)
  4. lot → pricing: fee(MEDIUM, 2h) → 180
  5. lot → payments: «create» + save(Payment)
  6. lot ⤓ Driver: Payment(₹180)
🚪 exit_lot(T-0001, t2)
  1. Driver → lot: exit_lot(T-0001, t2)
  2. lot → tickets: find(T-0001) → the ticket
  3. lot → payments: exists(T-0001) → true (else UnpaidExitError)
  4. lot → spot: free() (FR-6 — instantly reusable)
  5. lot → tickets: delete(T-0001)  ✗ lifeline ends
  6. lot ⤓ Driver: ticket (exited)

How to derive one — the seven-step recipe

You don't invent a sequence diagram — you read it off the class diagram plus one use case. The hard thinking ("whose job is this method?") already happened; the sequence only puts those calls in time order.

  1. Pick ONE use case, one sentence. "A car parks." Not the whole system — one story per diagram.
  2. List the participants left→right in call order, human actor on the far left. Each gets a box on top and a dashed lifeline dropping down.
  3. Walk the sentence as verbs. Each verb is a message — a solid arrow to the object whose method it is (you decided that on the class diagram; don't re-litigate it here).
  4. Mark activation. A bar on a lifeline = "on the call stack right now." It opens when called, closes when it returns. Nested calls stack deeper bars.
  5. Draw the returns that carry something — dashed arrows for the ticket, the fee, the spot. Skip the void returns; they're noise.
  6. Births and deaths: a call that builds an object is «create» and its lifeline starts there; a call that ends one closes the lifeline with an ✗.
  7. Branches and loops become fragments: alt (either/or — spot-found vs lot-full), opt (maybe), loop (for each floor…). Only draw the fragment when the branch actually matters to the story.

Finding the lifecycle — two questions hide under that word

"What's the object's lifecycle?" is really two different questions, and a good answer separates them.

🧮 (a) Memory lifecycle — when is it born, when does it die? (read it off the diamonds)

▾
  • Composition (filled ◆) → born with the whole, dies with it. A Spot is created inside a Floor, a Floor inside the lot — so on the sequence diagram their lifelines are already there at the top, no «create» arrow.
  • The records are the interesting ones. Ticket is «create»d at park() and retired at exit() — a lifeline with a clear start and an ✗. Payment is born at pay() and never dies (an immutable fact, kept for audit).
  • Injected collaborators don't get a birth. The two Strategies and two Repositories are handed in at construction — their lifelines predate the use case, so they enter from the top with no arrow creating them. (That's aggregation, the open ◇, on the picture.)
  • The diagrams cross-check each other. Anything with a «create» inside the flow is a candidate for composition; anything already present is borrowed. If your sequence creates an object your class diagram drew with an open diamond, one of them is wrong — go fix it.

🔄 (b) State lifecycle — what legal states, in what order? (the trick that finds your exceptions)

▾

For any record entity, write down its legal verbs and the order they're allowed in. That ordering IS the lifecycle — and the illegal orderings are exactly where your guards (exceptions) live. For a Ticket:

The third one isn't on the diagram — it's off it. Once a ticket is EXITED the repository delete()s it, so any later pay() / exit() / amount_due() finds nothing → InvalidTicketError. Touching a state that no longer exists is the last illegal move.

The payoff — your exceptions were never a brainstorm. Three states, three illegal moves, three exceptions — they line up one-to-one: exit-before-pay = UnpaidExitError, pay-twice = AlreadyPaidError, touch-a-gone-ticket = InvalidTicketError. When the interviewer asks "what can go wrong?", you don't guess — you draw the entity's state machine and read off the arrows it's not allowed to have. A guard in code is just an illegal transition the language refuses to take.

From engine to backend

This is where Module 1 reconnects

Tic-Tac-Toe was a CLI toy. A parking lot is a system — so today's engine slots straight into the layered stack you built with Django in Module 1.

Controller / view layer — parses HTTP, converts "CAR" → VehicleType.CAR, maps exceptions to status codes (UnpaidExitError → 402, InvalidTicketError → 404, full lot → 200 with {"spot": null}). Knows nothing about parking rules.
Service layer — this is the ParkingLot class we just wrote. Business rules, orchestration, the strategies. No HTTP, no SQL.
Repository layer — today it's two dicts (_active, _payments). Swap them for classes with save()/find_by_id() and the database can replace them without the service noticing — that's the whole pattern.
Domain layer — Spot, Floor, Ticket, Payment, the enums. Pure objects; importable anywhere; testable with zero setup.

Layering quiz — a request arrives to issue a ticket for vehicle type "BOAT". Where should validation live?

D is right — but "its own concern" is doing the work. The controller validates format: is "BOAT" a member of VehicleType? (string → enum conversion fails fast, returns 400). From engine to database

The schema falls out of the class diagram

Same move as the REST endpoints: the in-memory model has a one-to-one shadow in a relational database. Each class becomes a table; each composition diamond and each "id, not a live ref" becomes a foreign key. You're not designing a schema from scratch — you read it off the diagram.

First derive it — don't just read it off

Each floor has many spots; each spot sits on exactly one floor. The floor↔spot cardinality?

B — one-to-many. One floor holds many spots; a spot belongs to exactly one floor. In SQL the many side carries the foreign key → spot gets a floor_id column. (N:M would need a join table — overkill, since a spot never belongs to two floors.) This is just the composition diamond Floor ◆ Spot read as a relationship.

A ticket records which spot it took. Which table holds the spot_id column?

B. The ticket points at a spot, so the FK column (spot_id) lives on ticket — the rule of thumb: the foreign key goes on the table doing the referencing. A join table (C) is only for many-to-many; a ticket has exactly one spot. D is the "ids, not live refs" trap — a row stores an id, never an object.

A ticket is paid at most once. What's ticket↔payment, and how does the DB enforce "once"?

B. One ticket has zero-or-one payment. Put the FK payment.ticket_id and add a UNIQUE(ticket_id) constraint — a second payment row becomes impossible. That's the database enforcing the same pay-once rule the service's exists() enforced in memory. A bool (D) loses the amount, method and time you need for receipts and refunds.

Now check yourself against the schema — every FK arrow below is one of those answers:

Step 7 — Trade-offs

The two questions every parking interview ends on

1 — Two gates at once

Both gates run park() at the same instant and both are handed spot F1-M2. Which two lines form the race?

A is right — classic check-then-act. Gate 1 and gate 2 both call pick(), both see F1-M2 free, both get it returned; then both call occupy() — the second call changes nothing, and two cars drive to one spot. The fix is to make check-and-claim atomic: re-verify inside a lock and retry if the spot was stolen. B and D are real concerns but cause id collisions or dict races, not double-allocation — and C is a stale read on a display board: annoying, not catastrophic. Lock granularity: one lock per floor, not per lot — gates parking on different floors shouldn't queue behind each other. 
# the sketch we close with — re-check inside the lock, retry on theft
class ThreadSafeLot(ParkingLot):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self._locks = {f.number: threading.Lock() for f in self.floors}

    def park(self, vehicle, now):
        while True:
            picked = self.parking.pick(self.floors, vehicle)
            if picked is None:
                return None                      # genuinely full
            floor, spot = picked
            with self._locks[floor.number]:      # one lock PER FLOOR
                if spot.can_fit(vehicle):        # re-check: still ours?
                    spot.occupy()
                    break                        # claimed atomically
            # spot stolen between pick() and lock — loop, pick again
        ...

2 — What survives a restart

The lot process restarts mid-day. Only the ticket and payment logs survived. How do you rebuild the occupancy state?

C is right. Every ticket without an exit_time is a car still parked — walk the log, call occupy() on each referenced spot, and the lot is back; the payment log even tells you who still owes money. The records storing ids (floor_no, spot_id, ticket_id) instead of live object references is what makes this possible — ids survive serialization; pointers don't. Third time the lesson appears: TTT's move list was the save format, the ticket + payment logs are the lot's. The fancy name is event sourcing; you already own the idea.
