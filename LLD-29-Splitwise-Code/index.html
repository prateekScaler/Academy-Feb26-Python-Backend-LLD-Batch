FR-4 · add an expense (the heart of the model)

“To add an expense, a user specifies either the group or the other users involved, along with who paid what and who owes what, plus a description.”

✅ description and amount are plain fields on Expense. The two subtle halves each need a decision:

Fork 1 — the FR says “who paid what.” How do you model the payer(s) on an Expense?

“Who paid what” is already plural. A {User: amount} map costs nothing for the common single-payer case (a one-entry map) yet avoids a rewrite the day two friends split the bill at the counter. Choose the general shape when the FR hints at it and the cost is near-zero.

“Shouldn’t paid be its own class, like Split?” Yes — and it is. The map is just the easy in-memory view; in storage both sides become rows in one table, differing only by a type. Example — Ananya pays ₹1200, split equally 4 ways:

Fork 2 — the FR says “who owes what.” Where does “user X owes ₹Y on this expense” live?

Why not a map {user: owed}, like we used for paid? You can — it’s symmetric and fine for a toy build. But an owed share often needs to carry more than a number: how was it computed (EQUAL / PERCENT)? is it settled yet? A map of bare numbers can’t hold that, so the (expense × user) pairing wants its own object — Split, an association class (the same shape as BookMyShow’s ShowSeat). Store the shares as owed_by: Map<User, amount> in one Expense column. What’s the core relational problem?

First normal form (1NF) demands atomic column values. A map crammed into a column is opaque to the DB: no index on its keys/values, and every “does user X owe?” means loading and deserializing the entire blob. The fix is to make each entry its own row.

You unify “paid” and “owed” into one UserExpense junction table. What’s the cleaner schema?

A single amount + type makes every relationship a uniform, indexable row and avoids the always-NULL column that separate amount_paid/amount_owed would create. The composite index (user_id, expense_id, type) turns “what does X owe on this expense?” into one lookup.

Where should an expense’s currency live — on Expense, or on each UserExpense row?

Storing currency once on the Expense is the normalized choice. Copying it onto every UserExpense row is redundant and invites an update anomaly — change it in one place, forget another, and the rows disagree. One fact, one home.

Normal forms — a quick MCQ set

Quick check — which design breaks 1NF (first normal form)?

1NF wants atomic values — one value per cell. Stuffing a list into a cell (comma-separated, JSON, …) breaks it: you can’t index or query one value without parsing the whole thing.
optionbreaks 1NF?why
A separate row per phone number✅ noeach cell holds one value — atomic, the 1NF-correct fix
A table that has a primary key✅ noa PK is unrelated to 1NF — perfectly fine
One phones cell = “98765…, 91234…”❌ yesseveral values in one cell — not atomic

A table’s key is the pair (student_id, course_id) and it also stores student_name. Why does that break 2NF?

2NF (on top of 1NF) bans partial dependencies: with a composite key, every non-key column must depend on the whole key. student_name belongs in a students table keyed by student_id.

A table is (employee_id [PK], dept_id, dept_name). Why does it break 3NF?

3NF (on top of 2NF) bans transitive dependencies: a non-key column must depend on the key directly, not via another non-key column. Move dept_id → dept_name into a departments table.
Memory hook: every non-key column must depend on the key, the whole key, and nothing but the key. 1NF = atomic cells · 2NF = no partial dependency on a composite key · 3NF = no transitive dependency through another non-key column.
2NF vs 3NF — in one line

3NFdepend on nothing but the keya column depends on another non-key column (transitive dependency)always

Both say “non-key columns must depend on the key.” 2NF closes the “only part of the key” loophole (so it only bites with composite keys); 3NF closes the “via another non-key column” loophole.

3NF, concretely. Take employees(employee_id [PK], dept_id, dept_name). The key fixes dept_id, and dept_id fixes dept_name — so the dependency runs employee_id → dept_id → dept_name. dept_name hangs off a non-key column (dept_id): a transitive dependency.

FR-5 · “see your total owed” (subtle)

“A user can see their total owed amount.”

Fork 3 — “see your total owed” and “settle up” both need balances. Store a running balance, or recompute from expenses each time?

Reads (“what do I owe?”) vastly outnumber writes (“add expense”), so optimise the read:
approachread “what do I owe?”write “add expense”
Recompute from all expensesO(all expenses) — scan history every timeO(1) — just append
Running net (BalanceSheet)O(1) — one lookupO(participants) — update a few edges
Reads ≫ writes, so the running net wins. Trade-off: that balance is the lost-update hot spot (the BookMyShow seat race) — guard its update with a per-group lock / transaction.
What the BalanceSheet looks like — and how it updates

It’s just a map of net debts: balances[debtor][creditor] = paise. Adding an expense calls add_debt(ower, payer, share) for each ower, which first cancels any reverse debt — so we never store both a→b and b→a.

FR-8 · can’t query a foreign group (subtle)

“Users shouldn't be able to query about groups they are not a member of.”

“Only the creator can add or remove members.” Where and how do you enforce that rule?

Authorisation is a server-side decision: compare the authenticated caller against the stored owner and reject if they differ. Hiding a button is UX only — the endpoint is still callable directly. And a CHECK constraint validates column values; it has no idea who is calling (no notion of the current user/session), so it can’t express “only the creator may do this.”
Hiding data they may not see (FR-8). Don’t rely on the UI hiding a button — the API is still callable. The server filters reads: every group/expense query is scoped to the caller’s memberships, so users simply never receive rows from groups they’re not in. FR-9 · only the creator edits members (subtle)

“Only the user who has created a group can add/remove members to the group.”

First, the cardinality

A user can belong to many groups, and a group has many users — User–Group is many-to-many. A many-to-many relationship is modelled with a join (association) class: Membership(user, group) — which you need anyway just to record who’s in which group.

Given that Membership join, where does “who is allowed to manage the group” belong?

Because User–Group is many-to-many, you already have a Membership join class. “Who can manage” is an attribute of that membership, so it lives there as a role — role-based access control, and the creator is simply the first ADMIN. The other two options try to cram a many-to-many fact into a single column on Group: a comma-separated list is the 1NF trap (non-atomic, unindexable), and a multi-valued created_by breaks its meaning (it records who created the group). Same recurring move — a relationship that carries data becomes a join row, exactly like the expense’s shares became UserExpense.

Concept — Role-Based Access Control (RBAC)

Intuition: don’t pin permissions to individual people — pin them to a few roles, and give people roles. “What you can do” follows your role, not your name. Adding someone to a role grants everything that role can do; changing a role once updates everyone who has it.

Owner flag
Just created_by — one privileged user. Dead simple, but control can’t be shared.
Per-user ACL
List each user’s allowed actions. Flexible, but explodes (users × actions) and is hard to audit.
RBAC ✓
Users → roles → permissions. Assign a role; it carries the permissions. Scales cleanly.

The solution here: Membership carries a role, and the service checks the role, not the identity. The creator is simply the first ADMIN; you grant control by setting someone’s role to ADMIN.

rolecan do
ADMINadd / remove members, rename or delete the group — plus everything a member can
MEMBERadd expenses, view balances, settle up
Need OWNER / ADMIN / MEMBER / VIEWER tomorrow? Just more values in the role enum and a role→permission map — the check stays has_permission(caller_role, action), no new per-user branching.

The code, walked through

Three ideas, in real code

The whole engine is small. Three pieces carry the weight — the penny-safe split, the self-netting balance sheet, and the greedy simplifier. Click to expand each.

The split rule is the open variable: one abstract contract — split(amount, participants, args) → list[Split], where the shares sum to the total — with three implementations. A new way to split is one new class; the engine never changes.

1a · EqualSplit — the penny fix

▼

What happens: split evenly — each pays amount // n. The leftover paise (amount % n) would vanish, so the first few people each absorb one extra paisa; the shares then sum to exactly the total.

def split(self, amount, participants, args=None):
    n = len(participants)
    base, remainder = divmod(amount, n)        # base each; remainder = leftover paise
    return [Split(u, base + (1 if i < remainder else 0))
            for i, u in enumerate(participants)]

₹100 / 3: divmod(10000, 3) = (3333, 1) → [3334, 3333, 3333] = ₹100.00.

1b · ExactSplit — validate the sum

▼

What happens: the caller already knows each share (args = {user: paise}); we only validate they add up to the total, then return them unchanged.

def split(self, amount, participants, args):   # args = {user: paise}
    if sum(args.values()) != amount:
        raise SplitError("exact shares must sum to the total")
    return [Split(u, args[u]) for u in participants]

1c · PercentSplit — % then round

▼

What happens: the caller gives percentages (args = {user: percent}); validate they sum to 100, convert each to paise, and give the rounding remainder to the last person so the total is exact.

def split(self, amount, participants, args):   # args = {user: percent}
    if sum(args.values()) != 100:
        raise SplitError("percentages must sum to 100")
    splits, allocated = [], 0
    last = len(participants) - 1
    for i, u in enumerate(participants):
        if i < last:
            share = amount * args[u] // 100
            allocated += share
        else:
            share = amount - allocated          # last absorbs the rounding
        splits.append(Split(u, share))
    return splits

₹100 split equally 3 ways: divmod(10000, 3) gives a base and a remainder. The shares (paise) are…

divmod(10000, 3) = (3333, 1): base 3333 each, remainder 1 paisa → the first participant gets +1 → 3334 + 3333 + 3333 = 10000. Integer paise keeps it exact.

ExactSplit is called with shares summing to ₹999 on a ₹1000 expense. What happens?

Every strategy must keep the invariant Σ shares = total. ExactSplit enforces it up front, so malformed input is rejected instead of corrupting the balance sheet.

2 · BalanceSheet — debts that net themselves

▼

Before recording “debtor owes creditor”, check the reverse edge. If they already owe the other way, cancel against it first — so we never store both a→b and b→a, and opposite debts wash out.

def add_debt(self, debtor, creditor, amount):
    reverse = self.balances[creditor][debtor]   # owed the other way?
    if reverse >= amount:
        self.balances[creditor][debtor] = reverse - amount
    else:
        self.balances[debtor][creditor] += amount - reverse
    self._prune()                             # drop zeroed edges
B owes A ₹50, then A owes B ₹30 → the sheet stores just B owes A ₹20.

3 · DebtSimplifier — fewest payments

▼

Compute each person's net (sums to 0), then repeatedly settle the biggest creditor against the biggest debtor. Greedy net-and-match — the standard answer; the exact minimum is NP-hard.

while creditors and debtors:
    creditors.sort(key=lambda x: -x[1])     # biggest first
    debtors.sort(key=lambda x: -x[1])
    c, d = creditors[0], debtors[0]
    pay = min(c[1], d[1])
    payments.append(Payment(d[0], c[0], pay))
    c[1] -= pay; d[1] -= pay            # whoever hits 0 drops out
Nets A +₹2000 / B −₹250 / C −₹1750 → C→A ₹1750, B→A ₹250 — 3 edges become 2 payments.

4 · ExpenseService.add_expense — the flow

▼

Pick the strategy, compute the splits, assert they sum to the total (the invariant), then apply to the balance sheet. The service never knows how a split is computed — that's the strategy's job.

def add_expense(self, description, paid_by, participants, split_type, args=None, group=None):
    amount = sum(paid_by.values())
    splits = self.strategies[split_type].split(amount, participants, args)
    if sum(s.amount for s in splits) != amount:
        raise SplitError("splits must sum to the total")
    exp = Expense(description, amount, dict(paid_by), splits, group)
    self.expenses.append(exp); self.sheet.apply(exp)
    return exp

Trade-offs & extensions

Say these out loud

Integer paise, not floats
All money is int paise. Floats would drift; the penny problem becomes a clean integer remainder.
Net edges vs full history
The sheet keeps the net per pair (cheap reads, self-cancelling). Keep raw expenses too for the audit trail.
Simplify lazily
simplify_group runs on demand, scoped to one group's expenses — not after every expense.
Concurrency (callback to BMS)
Two expenses on one group both read-modify-write the balance — the lost update. Guard the group's balance with a lock / transaction.
New split = one new class
A SharesSplit (2:1:1) is one more SplitStrategy — the engine never changes.
Multiple payers
paid_by is a {user: paise} map; apply already splits each ower's debt across payers proportionally.
Why integer paise, not floats?

Computers store decimals in binary, and most money values have no exact binary form — 0.1, 0.20, 0.33 are all tiny approximations. Per value it’s invisible; over thousands of expenses the error accumulates, and the “do the splits sum to the total?” check starts failing.

Floats drift
>>> 0.1 + 0.2
0.30000000000000004
>>> 33.33 * 3
99.99000000000001
Integer paise — exact
3334 + 3333 + 3333
== 10000   # always true

So every amount is an integer count of paise — ₹33.34 is 3334. All arithmetic stays exact; division uses divmod and the leftover paise is an exact integer (the penny rule). We convert to “₹x.xx” only at display via fmt().

1 · Debt simplification — the algorithm

Every expense leaves IOUs — “I owe you” debts, one person owing another (the edges in a debt graph). Settling each IOU one-by-one is wasteful — debts cancel and chain. The goal: clear everyone with the fewest payments.

A tiny example.
  • A pays ₹3000 for A/B/C — B and C each owe A ₹1000.
  • B pays ₹1500 for B/C — C owes B ₹750.
Pay every IOU — 3 payments
fromtoamount
BA₹1000
CA₹1000
CB₹750
Net each person → 2 payments
personnet
A+₹2000
B−₹250
C−₹1750
sums to 0 → C→A ₹1750, B→A ₹250

The key insight: don’t follow the edges. Collapse everyone to a single net (it always sums to 0), then make the net-negative people pay the net-positive ones.

Three ways to turn those nets into payments — click each for the intuition, how to implement it, and the cost:

Greedy net-and-match — the practical default

▼

Intuition

The person owed the most should be paid by the one who owes the most — that single payment zeroes at least one of them. Repeat until everyone is at 0.

Where you’ve seen it

Literally LeetCode 465 — “Optimal Account Balancing.” In real life it’s a trip treasurer squaring up (deepest-red hands cash to most-owed) or a bank netting payments at close of day instead of wiring every invoice.

Trace it

Nets A +₹2000, B −₹250, C −₹1750:

  1. Round 1: A (+₹2000) vs C (−₹1750) → C pays A ₹1750; A now +₹250, C settled.
  2. Round 2: A (+₹250) vs B (−₹250) → B pays A ₹250. Done — 2 payments.

How to write it

nets is a map {user: net} — iterating nets.items() hands you each (u, n): u is the person, n is their net (owed if +, owes if −). Split into creditors (n > 0) and debtors (n < 0, stored as a positive “owed” amount); each round take the biggest of each, pay the smaller amount, drop whoever hits 0.

# nets = {user: net paise}  e.g. {A:+2000, B:-250, C:-1750}
# each item (u, n) = (the person, their net)
creditors = [[u, n]  for u, n in nets.items() if n > 0]   # [[A, 2000]]
debtors   = [[u, -n] for u, n in nets.items() if n < 0]   # [[C, 1750], [B, 250]]

while creditors and debtors:
    creditors.sort(key=lambda x: -x[1])   # biggest creditor first
    debtors.sort(key=lambda x: -x[1])     # biggest debtor first
    c, d = creditors[0], debtors[0]       # c[0]=user, c[1]=amount
    pay = min(c[1], d[1])
    payments.append(Payment(d[0], c[0], pay))   # debtor pays creditor
    c[1] -= pay; d[1] -= pay
    if c[1] == 0: creditors.pop(0)   # settled → drop
    if d[1] == 0: debtors.pop(0)

Where’s the max-heap? This version re-sorts each round — simplest to read (O(n log n) per round). To grab the biggest in O(log n) instead, keep each side in a max-heap. Python’s heapq is a min-heap, so push negative amounts to fake a max-heap: heapq.heappush(creditors, (-amount, user)). Same logic, faster picks — that’s the “heaps” the cost line refers to.

Step-by-step (4 people)

nets A +500, B +300, C −600, D −200:

roundcreditors (biggest first)debtors (biggest first)settleresult
1A 500, B 300C 600, D 200C → A ₹500A done · C 100 left
2B 300D 200, C 100D → B ₹200D done · B 100 left
3B 100C 100C → B ₹100all settled

→ 3 payments: C→A ₹500, D→B ₹200, C→B ₹100.

Cost

~O(n log n) with heaps (our simple code re-sorts each round → O(n²)); always ≤ n−1 payments, near-optimal. The exact minimum is NP-hard — the backtracking version of LC 465.

Cycle-cancelling on the debt graph

▼

Intuition

A debt cycle A→B→C→A means everyone owes “around the loop.” Subtract the loop’s smallest edge from every edge in it — at least one edge drops to 0 and vanishes.

Where you’ve seen it

The cycle-cancelling idea behind min-cost max-flow (kill negative-cost cycles); in finance it’s multilateral / “ring” netting — a clearing house cancels circular debts so members move far less cash.

Trace it

A owes B ₹100, B owes C ₹100, C owes A ₹100 — a pure cycle:

  1. Loop min = ₹100. Subtract ₹100 from each edge → all three become ₹0.
  2. Nobody pays anyone — the whole cycle cancels. 0 payments.

Two more, to see what happens: a partial cycle leaves a shorter chain; a longer cycle cancels just the same.

A more tangled one: a cycle embedded in other debts — cancel the loop, then settle whatever’s left.

How to write it

# edge[debtor][creditor] = amount
while a cycle exists (DFS / Tarjan):
    m = min edge weight around the cycle
    subtract m from every edge in the cycle
    drop edges that hit 0
settle the leftover (now acyclic) debts

Cost

Cycle detection is O(V+E) per pass over several passes — heavier. Minimises edges, not guaranteed the fewest transactions. Handy when you must preserve who-owes-whom.

Optimal (subset partition) — exact but exponential

▼

Intuition

The true minimum asks: which subsets of people can settle entirely among themselves (net to 0)? A zero-sum group of k people needs k−1 payments — so the more independent zero-sum groups you carve out, the fewer total. Minimise transactions = maximise zero-sum groups.

Where you’ve seen it

The optimal solution to LeetCode 465 (backtracking); the subset-sum / partition family — provably NP-hard.

Trace it

Nets A +30, B +20, C −50, D +40, E −40:

  1. {A +30, B +20, C −50} nets to 0 → 2 payments.
  2. {D +40, E −40} nets to 0 → 1 payment.
  3. Total 3 — the hard part is finding those subsets.

How to write it

def dfs(i):              # nets[]: each person's net
    while i < n and nets[i] == 0: i += 1
    if i == n: return 0
    best = inf
    for j in range(i+1, n):
        if nets[j] * nets[i] < 0:      # opposite signs
            nets[j] += nets[i]
            best = min(best, 1 + dfs(i+1))
            nets[j] -= nets[i]             # undo
    return best

Cost

Exponential (≈ 2ⁿ) — NP-hard. Only for tiny groups; greedy is what you ship.

What does “NP” even mean? The whole idea is the gap between solving a problem and checking an answer.

  • P — you can solve it fast (time grows politely as the input grows).
  • NP — you can check a given answer fast, even if finding it is hard. (“NP” = nondeterministic polynomial — not “not polynomial”, the common myth.)
  • NP-hard — at least as hard as the hardest problems in NP; as far as anyone knows, finding the best answer needs trying almost all combinations — exponential time.

The everyday example — Sudoku. Hand someone a finished grid and they can check it’s valid in seconds; but solving a hard one can take ages. “Easy to check, hard to solve” — that’s the entire idea.

“Find the best answer” = computing the single optimal solution yourself (e.g. the shortest route, the fewest payments) — the hard half. “Check” just means verifying one you’re handed. NP-hard problems are easy to check but hard to solve.

Why it matters here: settling debts in the provably fewest payments is Subset-Sum-flavoured — NP-hard. So we don’t chase the exact optimum; we ship greedy net-and-match: fast, always valid, near-best.

Does greedy net-and-match give the theoretical minimum number of transactions?

Minimising the exact transaction count is NP-hard (a subset-sum / partition flavour). Greedy net-and-match is the practical answer — always valid, finishes in ≤ n−1 payments, and usually near the minimum.

After computing each person’s net, what is greedy’s repeated step?

Take the extreme of each side and cancel as much as possible in one payment — that’s exactly the DebtSimplifier loop in the code above. Paying the raw edges is what we’re trying to avoid.

2 · Database models — constraints & indexes

Recall the normalized UserExpense table (one row per (user, expense, type)). The interesting part is making it correct (constraints) and fast (indexes):

Constraints — let the schema reject bad data

▼

PK on id; FK to users/expenses with ON DELETE CASCADE; CHECK for amount >= 0 and (for percent splits) percentage BETWEEN 0 AND 100; NOT NULL on every column that must exist.

CREATE TABLE user_expense (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
  expense_id  BIGINT NOT NULL REFERENCES expenses(id) ON DELETE CASCADE,
  amount      BIGINT NOT NULL CHECK (amount >= 0),   -- paise
  type        TEXT   NOT NULL CHECK (type IN ('PAID', 'OWED'))
);
CREATE INDEX ix_ue_user_type ON user_expense (user_id, type);
CREATE INDEX ix_ue_lookup    ON user_expense (user_id, expense_id, type);

Indexes — driven by the query patterns

▼

(user_id, type) → “total user X owes” = sum X’s OWED rows. (user_id, expense_id, type) → “what does X owe on this expense?” in one lookup — and by the leftmost-prefix rule it also serves user_id and user_id+expense_id queries.

To get “total amount user X owes across all expenses” fast, what helps most?

The query filters by user and type, then sums amount. An index on (user_id, type) lets the DB seek directly to X’s OWED rows. Indexing amount doesn’t help a filter on user/type.

Why a composite (user_id, expense_id, type) index instead of three single-column indexes?

A composite index matches a combined filter exactly. The leftmost-prefix rule means it also answers queries on user_id alone or user_id+expense_id — one index, several query shapes.
Leftmost-prefix, by example. Picture the index as a phone book sorted by (last name, then first name): you can look someone up by last name, or last + first — but not by first name alone. A composite index on (user_id, expense_id, type) behaves the same:
query — WHERE …uses the index?why
user_id = 7✅ yesleftmost prefix
user_id = 7 AND expense_id = 42✅ yesa prefix
user_id = 7 AND expense_id = 42 AND type = 'OWED'✅ yesfull match — one seek
expense_id = 42❌ noskips user_id (the leftmost column)
type = 'OWED'❌ nonot a prefix

Real queries: “what does user 7 owe on expense 42?” → WHERE user_id=7 AND expense_id=42 AND type='OWED' — one indexed seek. “everyone in expense 42?” filters on expense_id alone → this index can’t help, so add a separate INDEX(expense_id).

Which rule belongs as a database CHECK constraint?

A CHECK validates a row’s column values. Authorisation needs the current user (application/session logic, not a column rule), and the penny-rounding rule is split logic — neither is a CHECK.
