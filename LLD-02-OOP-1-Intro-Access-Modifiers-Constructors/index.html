OOP-1: Classes, Constructors & Access

LLD-02 • Object-Oriented Programming Foundations

Last class you learned WHY structure matters. Now learn the first tool for structuring code.

The Problem

Why OOP? What's Wrong Without It?

Read this procedural code. Spot the problems.

customer_service.py — procedural approach
▼
customer1 = {"name": "Rahul", "email": "rahul@gmail.com", "balance": 5000}

def withdraw(customer, amount):
    if amount > customer["balance"]:
        return "Insufficient funds"
    customer["balance"] -= amount

# Anyone can do this:
customer1["balance"] = -99999    # No protection!
customer1["blance"] = 5000      # Typo — creates a NEW key silently
del customer1["email"]          # Now other functions crash

What are the problems with using plain dicts for data?

Data is unprotected and unstructured. OOP solves all four of these problems:
The OOP version — click to reveal
▼
class Customer:
    def __init__(self, name, email, balance):
        self.name = name
        self.email = email
        self.__balance = balance  # Private

    def withdraw(self, amount):
        if amount > self.__balance:
            raise ValueError("Insufficient funds")
        self.__balance -= amount

    def get_balance(self):
        return self.__balance

rahul = Customer("Rahul", "rahul@gmail.com", 5000)
rahul.withdraw(1000)       # Goes through validation
rahul.__balance = -99999   # Doesn't work — name mangling

What OOP gives you

1. Data and behavior bundled — withdraw() lives WITH the balance it modifies.
2. Protection — __balance can't be directly set from outside.
3. Validation enforced — must go through withdraw() which checks the amount.
4. Structure defined — Customer always has name, email, balance.

You have 50 functions that operate on customer dicts scattered across 10 files. A new developer joins and adds a field "phone" but spells it "phne" in 3 of those files. How long until you find the bug? How would you even find it?

With OOP, the class defines the structure. A typo in an attribute name is caught by the IDE immediately.

Vocabulary

Attributes and Methods

In OOP, we don't say "variables and functions." We have specific words.

📦
Attribute = Data
What an object knows. A dish knows its name, price, and whether it's vegetarian. These are its attributes.
⚙️
Method = Behavior
What an object can do. A dish can describe itself, calculate its discounted price. These are its methods.
dish.py
▼
class Dish:
    def __init__(self, name, price):
        self.name = name      # ← Attribute (what it KNOWS)
        self.price = price    # ← Attribute (what it KNOWS)

    def describe(self):       # ← Method (what it can DO)
        return f"{self.name} costs Rs.{self.price}"

biryani = Dish("Biryani", 300)      # ← Object (instance)
print(biryani.describe())              # "Biryani costs Rs.300"

A class bundles related attributes and methods together. A Dish knows its name and price (attributes), and can describe itself (method). The data and behavior that belong together live together.

Context

Programming Paradigms

A paradigm is a style of organizing code. Same problem, very different approaches.

Let's solve the same problem in 4 paradigms: "Calculate total price of vegetarian dishes."

📝
Procedural
Step-by-step instructions. YOU tell the computer every step.

Languages: C, Bash, early Python
Best for: Scripts, automation
# YOU loop, YOU check, YOU add
total = 0
for dish in dishes:
    if dish["is_veg"]:
        total += dish["price"]
🧹
Object-Oriented
Objects with data + behavior. Ask the object to do it.

Languages: Java, C++, Python, C#
Best for: Modeling real entities
# Ask the MENU to do it
menu = Menu(dishes)
total = menu.veg_total()
⚡
Functional
Transform data with functions. No loops, no variables changing.

Languages: Haskell, Erlang, Elixir
Best for: Data pipelines, concurrency
# Chain transformations
total = sum(map(
    lambda d: d["price"],
    filter(lambda d: d["is_veg"], dishes)
))
🔍
Declarative
Describe WHAT, not HOW. The engine figures out the steps.

Languages: SQL, HTML/CSS
Best for: Database queries, UI
-- Just say what you want
SELECT SUM(price)
FROM dishes
WHERE is_veg = TRUE;

How are they different?

Procedural vs Functional: Both work with functions, but procedural MUTATES data (total += price changes total), while functional TRANSFORMS data without changing anything (filter and map create new data, the original is untouched).

Procedural vs Declarative: Procedural says "loop through each dish, check if veg, add price" (HOW). Declarative says "give me the sum of veg prices" (WHAT) and lets the engine figure out the loop.

Functional vs Declarative: Functional still describes transformations step by step (filter then map then sum). Declarative is even more abstract — one statement, no steps at all.

When you write SELECT * FROM dishes WHERE price > 200, which paradigm is that?

Declarative. You didn't tell the database to scan rows or compare prices. You said "I want this" and it decided HOW.

Your company is building a food delivery app with users, restaurants, orders, dishes, payments, drivers. Which paradigm fits best?

OOP. The problem has clear entities with their own data and behavior. But you'll still use SQL (declarative) for the database and functional patterns for data transformations!
Foundations

The Four Pillars of OOP

Today: Abstraction and Encapsulation. Next class: Inheritance and Polymorphism.

1 Abstraction — "Show only what matters"

▼

The word "abstract" means to pull away details and focus on what's essential. It appears everywhere:

🎨
In Art
An abstract painting shows the essence, not every detail. You recognize a cat without seeing every whisker.
🗻
In Maps
A metro map hides real distances. It only shows which stations connect — that's ALL you need.
🚗
In Driving
Press accelerator, car speeds up. You don't know about fuel injection or crankshaft rotation.
🐍
In Python
sorted([3, 1, 2]) — give it a list, get back a sorted list. The algorithm is hidden.

Abstraction in OOP

Expose WHAT an object can do, hide HOW it does it. When you call order.calculate_total(), you don't care about discount logic or tax calculation inside. You just get the total.

When you call sorted([3, 1, 2]) in Python, what is abstracted away?

Layers of abstraction. Python's sorted() uses Timsort (a hybrid of mergesort and insertion sort), handles memory, detects partially sorted sequences for optimization — you never see any of it. Same with len(), print(), open() — simple interface, complex internals.

2 Encapsulation — "Bundle and Protect"

▼

💊 The Capsule Analogy

Think of a medicine capsule. Now see how each aspect maps to a Python class:

1. It holds things together — ingredients are bundled inside one shell.
    → In Python: a class holds attributes (data) and methods (behavior) together. balance and withdraw() live in the same BankAccount class, not scattered as global variables and loose functions.

2. It protects from outside — you can't tamper with contents.
    → In Python: self.__balance (private) can't be directly changed from outside. You can't do account.__balance = -99999.

3. It has a controlled interface — swallow the capsule, don't inject ingredients.
    → In Python: you interact through methods like withdraw() and get_balance(), which validate before modifying.

See it in code — arrows show each capsule aspect:

encapsulation_mapped.py
▼
class BankAccount:          # ← THE CAPSULE (holds everything together)

    def __init__(self, balance):
        self.__balance = balance  # ← PROTECTED INSIDE (can't tamper from outside)

    def withdraw(self, amount):  # ← CONTROLLED INTERFACE
        if amount > self.__balance:  #    (validates before modifying)
            raise ValueError("Insufficient funds")
        self.__balance -= amount

    def get_balance(self):       # ← CONTROLLED INTERFACE
        return self.__balance     #    (read-only access)

account = BankAccount(5000)
account.withdraw(1000)          # ← Must use the interface
# account.__balance = -99999    ← BLOCKED (can't break into capsule)

Abstraction says: "You can withdraw money" (WHAT).
Encapsulation says: "But you MUST go through withdraw(), and I'll validate the amount" (HOW access is controlled).

They work together. Abstraction decides what's visible. Encapsulation enforces the boundary.

Think of an ATM.
The abstraction is: you see "Withdraw", "Check Balance", "Transfer" on the screen.
The encapsulation is: you can't open the ATM and grab cash directly. You MUST use the buttons.

What happens to a bank if ATMs had no encapsulation — if anyone could open them?

Core Concept

Constructors — Building Objects Right

The method that runs automatically when you create an object.

0 First — what is self?

▼

Every method inside a class gets self as its first parameter. It means "this specific object."

self_basics.py
▼
class Counter:
    def __init__(self):       # self = the object being created
        self.count = 0        # attach 'count' to THIS object

    def increment(self):     # self = the object calling this method
        self.count += 1      # modify THIS object's count

c1 = Counter()              # Python: Counter.__init__(c1)  — self = c1
c2 = Counter()              # Python: Counter.__init__(c2)  — self = c2
c1.increment()              # Python: Counter.increment(c1) — self = c1
c1.increment()
print(c1.count)  # 2
print(c2.count)  # 0 — completely independent!

What's the bug here?

class BrokenCounter:
    def __init__(self):
        self.count = 0

    def increment(self):
        count += 1          # Hmm...
Always use self. to access instance data. Without it, Python looks for a local variable named count, doesn't find one, and crashes.

1 Non-Parameterized Constructor

▼
counter.py
▼
class Counter:
    def __init__(self):
        self.count = 0

c1 = Counter()  # count = 0
c2 = Counter()  # count = 0, independent from c1

What does __init__ actually do?

When you write c1 = Counter(), Python does two things:
1. Creates an empty object in memory (allocates space) — this is done by __new__ (you rarely touch this).
2. Calls __init__(self) on that empty object to initialize its attributes — this is YOUR setup code.

If you don't write __init__ at all? Python provides a default empty one automatically. The object gets created, but with no attributes — it's a blank slate.

no_init.py — what happens without __init__
▼
class Empty:
    pass              # No __init__ — Python uses a default empty one

e = Empty()           # Works! Object is created, but has no attributes
print(e.__dict__)     # {} — empty! No data attached
e.name = "added later"  # You CAN add attributes after, but this is messy

2 Parameterized Constructor — Objects born ready

▼

Read this code. Can you spot any problems?

dish_v1.py — spot the problem
▼
class Dish:
    def __init__(self):
        pass  # Empty constructor

    def describe(self):
        return f"{self.name} costs Rs.{self.price}"

dish = Dish()
dish.name = "Biryani"    # Setting attributes AFTER creation
dish.price = 300
dish.describe()          # Works... this time

dish2 = Dish()
dish2.name = "Dosa"
# Forgot to set price!
dish2.describe()         # CRASH: AttributeError: 'Dish' has no attribute 'price'

What's the problem with this Dish class?

An object should be READY TO USE from birth. The fix:
dish_v2.py — the fix — click to reveal
▼
class Dish:
    def __init__(self, name, price):   # REQUIRE name and price
        self.name = name
        self.price = price

    def describe(self):
        return f"{self.name} costs Rs.{self.price}"

dish = Dish("Biryani", 300)    # Can't forget name or price!
dish.describe()                 # Always works

# Dish()  — TypeError: missing required arguments
# Dish("Dosa")  — TypeError: missing 'price'

3 Defaults + Validation — The complete picture

▼
restaurant.py
▼
class Restaurant:
    def __init__(self, name, cuisine, rating=0.0, is_open=True):
        if not name:
            raise ValueError("Restaurant must have a name")
        if not 0 <= rating <= 5:
            raise ValueError(f"Rating must be 0-5, got {rating}")
        self.name = name           # Required
        self.cuisine = cuisine     # Required
        self.rating = rating       # Optional, default 0.0
        self.is_open = is_open     # Optional, default True

Restaurant("Biryani House", "Indian")             # rating=0.0, is_open=True
Restaurant("Sushi Bar", "Japanese", rating=4.5)   # is_open=True
Restaurant("", "Indian")                            # ValueError!
Restaurant("Bad", "Indian", rating=7)              # ValueError!

Good practice summary

1. Required parameters for essential data — don't let incomplete objects exist
2. Default values for optional data — rating=0.0
3. Validation in constructor — bad objects should never be created

You're building a PaymentTransaction. Which approach is best?

Validate at creation. A PaymentTransaction with amount = -500 should never exist. The constructor is your first line of defense.

Access Modifiers & Name Mangling

Public, Protected, Private — and why Python's "private" isn't truly private.

bank_account.py
▼
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner              # Public — anyone
        self._account_type = "savings"  # Protected — convention
        self.__balance = balance        # Private — name mangling

account = BankAccount("Rahul", 5000)

print(account.owner)                    # "Rahul" — works
print(account._account_type)            # "savings" — works, linter warns
print(account.__balance)                # AttributeError!
print(account._BankAccount__balance)    # 5000 — name mangling!

Wait — Python's "Private" Isn't Truly Private?

name_mangling_revealed.py
▼
class Secret:
    def __init__(self):
        self.__password = "hunter2"

s = Secret()
print(s.__password)              # AttributeError ✗
print(s._Secret__password)       # "hunter2" ✓  — Wait, what?!

If Python's __ isn't truly private, why bother using it?

Python's philosophy: "We're all consenting adults here." Name mangling prevents name collisions in inheritance, not security breaches. Read the classic StackOverflow discussion →
Encapsulation in Practice

@property — Pythonic Encapsulation

A way to add validation to attributes without changing how they're used.

The problem: You want to validate data when it's set (like "price can't be negative"). In Java, you'd write getPrice() and setPrice(). Python has a cleaner way.

1 Step 1: The ugly Java way

▼ 
class Dish:
    def __init__(self, name, price):
        self.__name = name
        self.__price = price

    def get_price(self):       # Getter
        return self.__price

    def set_price(self, value):  # Setter with validation
        if value < 0:
            raise ValueError("Price can't be negative")
        self.__price = value

dish = Dish("Biryani", 300)
print(dish.get_price())        # 300 (verbose!)
dish.set_price(350)            # (verbose!)

It works, but dish.get_price() is ugly. You have to remember "is it .price or .get_price()?" everywhere.

2 Step 2: The Pythonic way — @property

▼
dish_property.py
▼
class Dish:
    def __init__(self, name, price):
        self.name = name
        self.price = price       # This calls the @price.setter below!

    @property                    # Makes dish.price CALL this method
    def price(self):
        return self.__price

    @price.setter                # Makes dish.price = X CALL this method
    def price(self, value):
        if value < 0:
            raise ValueError("Price can't be negative")
        self.__price = value

dish = Dish("Biryani", 300)
print(dish.price)              # 300 — looks like attribute, calls getter
dish.price = 350               # looks like assignment, calls setter + validates
dish.price = -50               # ValueError: Price can't be negative

The magic: dish.price LOOKS like reading a simple attribute, but behind the scenes it calls your getter. dish.price = 350 LOOKS like a simple assignment, but it calls your setter which validates. Clean syntax AND protection.

3 Real Example: Order Status

▼
order_status.py
▼
class Order:
    VALID = ["pending", "confirmed", "preparing", "delivered", "cancelled"]

    def __init__(self, customer, items):
        self.customer = customer
        self.items = items
        self.__status = "pending"

    @property
    def status(self):
        return self.__status

    @status.setter
    def status(self, new_status):
        if new_status not in self.VALID:
            raise ValueError(f"Invalid status: {new_status}")
        if self.__status == "delivered":
            raise ValueError("Cannot change delivered order")
        self.__status = new_status

order = Order("Rahul", ["Butter Chicken"])
order.status = "confirmed"     # Validates — allowed
order.status = "delivered"      # Validates — allowed
order.status = "pending"        # ValueError: Cannot change delivered order
order.status = "delievered"     # ValueError: typo caught!

Without @property, someone writes order.status = "delievered" (typo). What happens?

Silent corruption is the worst kind of bug. With @property, the typo is caught the MOMENT it happens, not days later in production.
